Case Study: Why Uber Migrated from Postgres to MySQL

A close reading of Uber's widely-cited 2016 engineering post, rewritten in our own words. The post argues that specific Postgres storage-engine internals hurt Uber's write-heavy, high-index workload — and that MySQL/InnoDB fit them better. Every fact below is drawn from that post and cited in §8. It is an opinionated, Postgres-critical piece from one team and one era; we present its claims as "Uber reported / argued" and keep a balanced note that Postgres has since evolved and the trade-offs are workload-specific.
Why this case study is worth memorizing

It is the canonical "how do storage-engine internals decide your database choice" story. It forces you past the marketing-tier "SQL vs. NoSQL" framing and down to the level that actually matters under load: how rows are laid out on disk, how a secondary index points at them, what a single UPDATE costs, and how those costs multiply across replication. Read it as a worked example of matching an engine's physical design to your write and index pattern — not as proof that one database beats another.

1. The Problem — Context and Scale

Uber began, in their telling, as a monolithic Python backend that used Postgres for persistence. As the business grew, that early choice ran into limits the team traced to how Postgres stores and replicates data. In July 2016 Uber engineer Evan Klitzke published a post explaining why they had moved much of that data onto MySQL — usually behind their own sharding layer.

The deployment they were running

  • A Postgres primary with streaming replicas. Uber described a primary plus replicas in a West Coast colocation, with disaster-recovery replicas on the East Coast, wired together using cascading replication.
  • Large, memory-rich hosts. Their largest Postgres replicas had 768 GB of memory, of which only about 25 GB was resident (RSS) memory — leaving 700+ GB to the Linux page cache. That detail matters later: most reads were served from cache, so write and replication costs dominated the pain.
  • An analysis pinned to Postgres 9.2. Uber noted their analysis was based on Postgres 9.2; some legacy instances still ran 9.2 while the then-current GA release was 9.5. This is the single most important caveat in the whole piece — remember it for §6.

The workload shape that made it hurt

The defining characteristic was a write-heavy workload against tables carrying many indexes. Uber's example table has a primary key plus several secondary indexes (they use a users table with a primary key, a (first, last) name index, and a birth_year index). When most of your cost is updating rows that participate in many indexes — and streaming every one of those changes across the country to replicas — the way the engine represents rows and propagates changes stops being an implementation detail and becomes the decisive factor.

2. The Postgres Internals Uber Said Hurt Them

The heart of the post is a mechanism-by-mechanism argument. Each item below is a claim Uber made about how Postgres 9.2 worked and why it was costly for their workload.

Immutable tuples and the ctid

Postgres stores each row version as an immutable "tuple." Under MVCC, an update does not overwrite a row in place — it writes a new tuple and leaves the old one until vacuum reclaims it. Every tuple has a ctid, which Uber describes as identifying its physical location on disk (its page and offset). Because a row can have several live tuple versions over time, multiple ctids can refer to what is logically the same row.

Secondary indexes point at the physical tuple

This is the key point. In Postgres, every index — primary and secondary alike — stores the ctid (the on-disk location) of the tuple it points to. Uber's phrasing: "When a tuple location changes, all indexes must be updated." Because the index entry references a physical position rather than a logical key, moving or re-versioning a row means every index that points at it has to be repointed.

Write amplification, quantified by Uber's example

Uber walks through updating a single indexed field — a user's birth_year. Because the update creates a new tuple, and every index must now point at that new tuple, the operation required at least four physical writes: the new tuple written to the table, plus updates to the primary-key index, the (first, last) index, and the birth_year index — even though only birth_year actually changed. And each of those writes is also written to the WAL. Their generalization: on a table with a dozen indexes, an update to one indexed field must propagate to all twelve indexes, because they all reference the tuple's physical location.

MVCC bloat and vacuum

Because old tuples linger until reclaimed, an update-heavy table accumulates dead row versions — bloat. Postgres relies on autovacuum to reclaim them, and Uber notes vacuuming entails scanning tables to find and free dead tuples, which is expensive work competing with live traffic.

Replication amplification over the WAL

Postgres replication is physical: the primary ships its write-ahead log (WAL) — a stream of on-disk byte-level changes — and replicas apply it so they match the primary byte for byte. Uber's key argument: because a single logical update already fanned out into many physical writes (§ above), write amplification becomes replication amplification. The WAL stream turns "extremely verbose," and Uber reported that over their cross-country links, WAL archival to a storage service couldn't keep pace at peak.

Two further replication pains Uber cited

No true replica-side MVCC. A long-running read transaction on a replica can block WAL application; to avoid the replica falling arbitrarily behind, Postgres cancels the transaction after a timeout. Uber found this hostile to ORMs that hold a transaction open across blocking I/O. Cross-version upgrades are hard. Because replication is physical, you generally cannot stream the WAL between different GA versions, so a major upgrade meant taking the primary down, running pg_upgrade in place (hours of work), then rebuilding each replica from a snapshot.

A concrete corruption incident (as reported)

Uber also described a Postgres 9.2 replication bug: after a timeline switch, some replicas misapplied WAL records, failing to mark certain old tuples inactive — so a query could return duplicate rows with different ctids. Their fix was to resync the affected replicas from a fresh primary snapshot. We flag this as a version-specific bug, not an inherent property of Postgres.

Connection cost: process per connection

Finally, Postgres uses a process-per-connection model: each connection is a forked backend process. Uber argued this costs more memory than a thread-per-connection design, makes inter-process communication more expensive, and — on 9.2, using System V shared memory — struggled past a few hundred active connections. They ran pgbouncer for connection pooling to cope.

3. Why MySQL/InnoDB Fit Uber Better

Uber's argument for MySQL is essentially the mirror image of §2: InnoDB's physical design happened to line up with their write-heavy, many-index pattern.

Clustered index + logical secondary indexes

InnoDB stores the table itself as a clustered index on the primary key: the row data lives in the leaf of the PK index, sorted by PK. Crucially, secondary indexes store the primary-key value of the row they point to, not a physical on-disk pointer. Uber's summary of the payoff: "if a row offset changes, only the primary index needs to be updated" — secondary indexes are undisturbed by a row physically moving, because they reference the logical PK.

The consequence for updates

Because secondary indexes key on the PK, an update only touches the indexes whose columns actually changed. Updating birth_year updates the birth_year index and nothing else — the (first, last) index is untouched. Contrast Postgres, where the same update repointed every index at the new tuple. This is the single mechanism that most directly answered Uber's write-amplification problem.

Uber was honest about the trade-off

The logical-PK design is not free: a secondary-index lookup now takes two steps — search the secondary index to get the PK, then search the clustered index to reach the row — whereas a Postgres index points straight at the tuple. Uber explicitly called this a slight disadvantage for reads, accepted because their pain was on the write and replication side.

In-place updates and cheaper MVCC cleanup

InnoDB updates rows in place and keeps old versions in a rollback (undo) segment for MVCC, rather than leaving dead tuples scattered through the table. Uber argued this makes reclaiming old versions more efficient than Postgres autovacuum's table scans.

Logical replication over the binlog

MySQL replication is logical: it ships the binary log (binlog), which supports statement-based, row-based, and mixed formats. Because replicas receive logical changes and re-derive their own index updates, Uber argued the binlog is significantly more compact than a physical WAL stream. Logical replication also gave them true replica-side MVCC (reads don't block replication), more resilience to the kind of catastrophic corruption they hit, and easier cross-version upgrades — upgrade replicas one at a time, then promote one to primary.

Buffer pool and connection model

  • InnoDB buffer pool. InnoDB manages its own userspace LRU buffer pool, giving it control over cache eviction and avoiding some of the lseek/read syscall overhead Uber attributed to Postgres's reliance on the OS page cache.
  • Thread per connection. MySQL uses a thread-per-connection model, which Uber said scaled to roughly 10,000 concurrent connections — versus the few-hundred ceiling they felt with Postgres 9.2 processes.

4. Schemaless — Uber's Sharding Layer on MySQL

Uber did not simply point their monolith at raw MySQL. They described Schemaless — in their words, "a novel database sharding layer built on top of MySQL" — as the target for most data that had lived in Postgres. Conceptually it is an append-only, sharded key-value/columnar store that uses MySQL instances as the underlying storage engine, so applications get horizontal sharding and an append-friendly write model while MySQL/InnoDB handles durability and replication underneath.

Scope note

The 2016 post introduces Schemaless only briefly, as the destination for the migration; the deep design of Schemaless is covered in Uber's separate posts and is out of scope here. We mention it because it is why "Uber moved to MySQL" is more precisely "Uber moved to Schemaless-on-MySQL" for most of their data — with some specialized cases going to other stores such as Cassandra.

5. The Core Mechanism — Physical vs. Logical Index Pointers

If you remember one diagram from this chapter, make it this one. It is the single difference that drives most of Uber's argument: what a secondary index actually stores. In Postgres it stores the tuple's physical location; in InnoDB it stores the primary key. Follow the arrows to see why an indexed-column update touches every index in one engine and only the changed index in the other.

The core mechanism: Postgres indexes reference the physical tuple (ctid), so a new tuple version forces every index to be repointed; InnoDB secondary indexes reference the primary key, so an indexed-column update touches only the changed index plus the in-place clustered row — at the cost of an extra hop on secondary reads.

6. Trade-offs and Balance — Read This Before You Quote the Post

This post is opinionated and Postgres-critical, written by one team for one workload at one moment in time. It is a superb teaching artifact and a genuine account of real pain — but it is not a timeless verdict that "MySQL beats Postgres." Several things must be said alongside its claims:

  • It is anchored to Postgres 9.2 (analysis published July 2016). Uber said so themselves. Postgres has evolved substantially since; a critique of a specific old version is not a critique of the database in 2026.
  • Postgres already had, and has improved, mitigations. Postgres's HOT (Heap-Only Tuple) updates can avoid touching indexes entirely when the changed column is not indexed and the new tuple fits on the same page — directly softening the write-amplification example. Later releases brought major work on vacuum, replication, and more; the community published detailed responses at the time arguing the post overstated inherent weaknesses.
  • Postgres runs at enormous scale elsewhere. Plenty of large organizations run write-heavy Postgres successfully. Uber's experience does not generalize to "Postgres can't scale."
  • The trade-off is real and cuts both ways. InnoDB's logical secondary indexes cost an extra lookup hop on reads; Postgres's physical pointers make secondary reads a single hop. Which side you want depends on your read/write mix and index count.
The actual lesson

The transferable insight is not "pick MySQL." It is: a database's storage-engine internals — on-disk row representation, what indexes point at, update-in-place vs. new-version, physical vs. logical replication — directly determine its cost on your specific write and index pattern. Uber's pattern (write-heavy, many indexes, cross-country physical replication) happened to be a bad fit for Postgres 9.2's physical-tuple/WAL design and a good fit for InnoDB's clustered-index/binlog design. Match the engine to the workload; don't rank engines in the abstract.

7. Interview Angle — How to Use This

This case study is fuel for any "pick a database" / "SQL vs. NoSQL" / "why would you choose engine X" question. Cite it correctly and it sends a strong signal; cite it as absolute truth and a good interviewer may (rightly) push back.

What signal it sends

  • You reason about databases at the level of storage-engine internals, not brand names — you can name what a secondary index physically stores and why that matters.
  • You connect a low-level mechanism (physical vs. logical index pointers) to a system-level consequence (write amplification → replication amplification across a WAN).
  • You show intellectual honesty: you present the post's era, its known trade-offs, and Postgres's counter-mechanisms (HOT), instead of repeating a one-sided conclusion. That balance is itself a senior signal.
"Uber reported that on Postgres 9.2, secondary indexes pointed at the physical tuple location, so a single indexed-column update created a new tuple and had to repoint every index — and because replication shipped the physical WAL, that write amplification became replication amplification across their cross-country replicas. InnoDB's secondary indexes reference the primary key instead, so the same update touched fewer indexes. That said, it's a 9.2-era, workload-specific argument — Postgres has HOT updates and has evolved a lot since — so the real lesson is matching engine internals to your write/index pattern."

Probe questions and crisp answers

Q: What is write amplification in a database, and how can index design cause it?
Write amplification is when one logical write turns into many physical writes. In Postgres 9.2, an UPDATE writes a new immutable tuple, and because every index stores the tuple's physical location (ctid), every index must be repointed at the new tuple — so updating one indexed field could mean four-plus writes (new tuple + each index), all also written to the WAL. On a table with a dozen indexes, that's twelve index updates for one field change.

Q: Contrast a clustered-index (InnoDB) table with a heap (Postgres) table.
InnoDB stores the row inside the primary-key index (clustered), sorted by PK, and secondary indexes store the PK value. Postgres uses a heap: rows sit in heap pages and every index — including the PK — points at the physical tuple. Consequence: in InnoDB a row moving or re-versioning only disturbs the clustered/PK structure, so an indexed-column update touches only changed indexes; in Postgres it repoints all indexes. The InnoDB trade-off is that secondary reads take two hops (secondary index → PK → clustered row) instead of one.

Q: How do physical (WAL) and logical (binlog) replication differ, and why did it matter to Uber?
Physical replication ships byte-level on-disk changes so replicas are byte-for-byte copies; logical replication ships statement/row changes and lets replicas re-derive their own index updates. Uber's write amplification inflated the physical WAL stream ("extremely verbose") and their cross-country WAL archival couldn't keep up at peak; a logical binlog is more compact, allows replica-side MVCC without cancelling long reads, and makes cross-version upgrades easier. The cost of logical replication is more work re-applying changes on replicas and format/consistency subtleties.

Q: Does this post mean MySQL is better than Postgres?
No — and saying so is the trap. It's a Postgres-9.2-era, workload-specific account (write-heavy, many indexes, WAN replication). Postgres has HOT updates that avoid index writes when the changed column isn't indexed, and has improved vacuum/replication since. Many teams run Postgres at large scale. The real takeaway is to match storage-engine internals to your write/index/replication pattern rather than ranking databases in the abstract.

Terminology & Acronyms

Quick reference for the key terms in this chapter.

TermMeaning
RSS (resident set size)The portion of a process's memory actually held in physical RAM, versus what the OS page cache holds.
MVCC (Multi-Version Concurrency Control)Keeping multiple versions of a row so readers never block writers and vice versa.
TuplePostgres's term for a single on-disk row version; an update writes a new tuple rather than editing in place.
ctidPostgres identifier for a tuple's physical location on disk — its heap page and offset.
Secondary indexAny non-primary-key index used to find rows by other columns (here, the name and birth_year indexes).
Write amplificationWhen one logical write expands into many physical writes on disk.
WAL (write-ahead log)Postgres's byte-level log of on-disk changes, written before pages and shipped for physical replication.
BloatAccumulation of dead row versions in a table that must later be reclaimed.
AutovacuumPostgres background process that scans tables to find and free dead tuples.
Physical replicationShipping byte-level on-disk changes (the WAL) so replicas are byte-for-byte copies of the primary.
ORM (object-relational mapping)A library that maps database rows to application objects.
pg_upgradePostgres tool that upgrades a cluster's data files in place across major versions.
pgbouncerLightweight connection pooler for Postgres, used to cope with the process-per-connection limit.
InnoDBMySQL's default transactional storage engine, built on a clustered-index row layout.
Clustered indexAn index whose leaves hold the row data itself, sorted by primary key; InnoDB stores tables this way.
Logical replicationShipping statement- or row-level changes so replicas re-derive their own index updates.
Binlog (binary log)MySQL's logical change log, supporting statement-based, row-based, and mixed formats.
Buffer poolInnoDB's userspace LRU (least-recently-used) cache of table and index pages.
HOT (heap-only tuple)Postgres optimization that avoids index writes when the changed column isn't indexed and the new tuple fits the same page.
SchemalessUber's append-only, sharded datastore layer built on top of MySQL, the target of the migration.
