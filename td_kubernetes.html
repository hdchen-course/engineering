Kubernetes — a Practical Deep-Dive

What container orchestration actually is, and how Kubernetes does it: the problem it solves, the control-plane/node architecture, the core objects and their YAML, the reconcile loop that makes it self-healing, and the networking, storage, scheduling, rollout, and debugging pieces you're expected to reason about out loud. Every manifest below is valid and every command flag is real.
Read this like a story

The sections build from "why would anyone run this" to "walk me through a rolling update and debug a stuck Pod." If you already know the objects, skip to §4 (the reconcile loop) — it's the mental model that makes everything else click. Kubernetes ("K8s" — eight letters between K and s) was originally created at Google, open-sourced in 2014, and is now governed by the vendor-neutral Cloud Native Computing Foundation (CNCF); everything here is generic, public knowledge.

1. What Problem Kubernetes Solves

You have containers — packaged, isolated processes. On one laptop, docker run is enough. But a real service is dozens of container instances spread across many machines, and you need them to survive crashes, reschedule when a node dies, scale with load, and roll out new versions without downtime. Doing that by hand — SSH-ing to hosts, restarting dead processes, editing load-balancer configs — does not scale. Kubernetes is a cluster orchestrator: you declare the desired state, and it continuously works to make reality match.

Imperative vs. declarative — the core shift

The old way is imperative: "start this process on that host; if it dies, page someone." Kubernetes is declarative: you submit an object that says "I want 3 replicas of this image, reachable on port 80" and the system figures out the how — which nodes, restarting failures, replacing dead Pods — and keeps doing so forever. You describe the destination, not the turn-by-turn directions.

# the whole philosophy in one line
you declare desired state # "3 healthy replicas of web:1.2 on port 80"
K8s observes actual state # "only 2 are running; one node just died"
K8s acts to close the gap # schedule 1 more Pod on a healthy node → 3

What you get from that one idea

  • Scheduling & bin-packing: the scheduler places Pods onto nodes that have enough CPU/memory, spreading or packing them per your rules.
  • Self-healing: a crashed container is restarted; a Pod on a dead node is recreated elsewhere; a Pod that fails its health check is replaced.
  • Horizontal scaling: change one number (or let an autoscaler change it) and the replica count adjusts.
  • Service discovery & load balancing: a stable virtual IP + DNS name in front of a churning set of Pods, so callers never track individual IPs.
  • Rollouts & rollbacks: ship a new version gradually, pause or roll back if health checks fail — no downtime.
  • Declarative config & secrets: configuration, credentials, and storage claims are versioned objects, not hand-edited files on hosts.

When you do not need it

Kubernetes is not free

It adds a genuine operational tax: a control plane to run (or pay a cloud to run), a networking layer, RBAC, and a steep learning curve. For a single app on one or two servers, a low-traffic side project, a purely serverless design (functions + managed queues), or a tiny team without spare capacity, a PaaS, a managed container service, or plain VMs is usually the better call. Reach for K8s when you have many services, real scale/HA needs, and the people to operate it.

Interview signal

Volunteering "here's when I would not use Kubernetes" reads as senior. The tool is a means to reliability and velocity at scale — not a default for every workload.

2. Architecture: Control Plane & Nodes

A cluster is split into the control plane (the brain that makes decisions and stores state) and the worker nodes (the muscle that runs your containers). The control plane's parts talk to each other only through the API server — it is the single front door and the only component that reads/writes the datastore.

Every control-plane component talks only through the API server; only the API server touches etcd. Each node's kubelet watches the API server and drives the local runtime.

Control-plane components

ComponentJob
kube-apiserverThe front door and hub. Exposes the REST API, validates and authenticates every request, and is the only component that reads/writes etcd. All other parts (and kubectl) go through it.
etcdThe cluster's source of truth: a distributed, strongly-consistent key-value store holding all objects. Uses the Raft consensus protocol, so a write is committed only after a quorum (majority) of its members persist it; run an odd member count (3 or 5) so a given cluster size tolerates the most failures.
kube-schedulerWatches for Pods with no assigned node and picks one for each — filtering nodes that don't fit (resources, taints, selectors), then scoring the survivors. It only decides; the kubelet does the running.
kube-controller-managerRuns the built-in controllers (Deployment, ReplicaSet, Node, Job, …) — each a reconcile loop driving actual state toward desired (§4).
cloud-controller-managerOptional: integrates with a cloud provider for load balancers, node lifecycle, and storage — keeping cloud-specific code out of the core.
etcd is the crown jewels

Lose etcd and you lose the cluster's state. It must be backed up; run an odd member count (3 or 5) so a given cluster size tolerates the most failures. Because it's Raft-based and consistent, a write is acknowledged only after a majority of members persist it — that's the "C" and consistency guarantee the whole system leans on.

Node components

ComponentJob
kubeletThe node's agent. Watches the API server for Pods assigned to its node, tells the container runtime to start/stop containers, runs the health probes, and reports Pod & node status back.
kube-proxyPrograms the node's packet-routing rules (iptables or IPVS) so that traffic to a Service's virtual IP is load-balanced to the backing Pods (§5). On many modern clusters a CNI plugin can take over this role.
container runtimeThe software that actually runs containers — containerd or CRI-O, spoken to over the Container Runtime Interface (CRI). (Docker's built-in shim was removed in v1.24; Docker-built images still run fine — they're standard OCI images.)

3. Core Objects

You rarely create low-level things directly. You describe a Deployment and a Service, and higher-level controllers create the rest. Here is the ladder, smallest to highest.

The object ladder

  • Pod — the smallest deployable unit: one or more containers that share a network namespace (same Pod IP, same localhost) and can share volumes. Pods are ephemeral — you don't nurse them; you replace them.
  • ReplicaSet — keeps exactly N identical Pods running, replacing any that die. You seldom write one by hand.
  • Deployment — manages ReplicaSets to give you declarative updates: change the image and it rolls out a new ReplicaSet while scaling the old one down, with rollback (§8). This is what you actually author for stateless apps.
  • Service — a stable virtual IP + DNS name in front of a churning set of Pods, selected by label (§5).
  • Namespace — a virtual cluster partition for grouping objects and scoping names, quotas, and access — e.g. team-a vs. team-b, or staging vs. prod.
Deployment → ReplicaSet → Pods

A Deployment owns one or more ReplicaSets; the current ReplicaSet owns the live Pods. That three-level ownership is exactly what makes a rolling update and a one-command rollback possible — the old ReplicaSet is kept (scaled to 0) so it can be scaled back up.

Service types

TypeWhat it exposesUse
ClusterIP (default)A virtual IP reachable only inside the clusterInternal service-to-service traffic
NodePortThe Service on a static port (default range 30000–32767) on every node's IPSimple external access / behind your own LB
LoadBalancerProvisions an external cloud load balancer that forwards to the ServicePublic entry point on a cloud provider
ExternalNameA DNS CNAME to an external host (no proxying)Aliasing an out-of-cluster dependency

A minimal, valid Deployment + Service

Three replicas of a web container, with resource requests/limits and health probes, plus a ClusterIP Service that load-balances to them by label. The --- separates two YAML documents in one file.

# web.yaml — apply with: kubectl apply -f web.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
  namespace: shop
  labels:
    app: web
spec:
  replicas: 3
  selector:
    matchLabels:
      app: web             # MUST match template labels below
  template:
    metadata:
      labels:
        app: web
    spec:
      containers:
        - name: web
          image: nginx:1.27
          ports:
            - containerPort: 80
          resources:
            requests:              # used for scheduling
              cpu: "100m"          # 0.1 core
              memory: "128Mi"
            limits:                # enforced at runtime
              cpu: "250m"
              memory: "256Mi"
          readinessProbe:
            httpGet:
              path: /healthz
              port: 80
            initialDelaySeconds: 5
            periodSeconds: 10
          livenessProbe:
            httpGet:
              path: /healthz
              port: 80
            initialDelaySeconds: 15
            periodSeconds: 20
---
apiVersion: v1
kind: Service
metadata:
  name: web
  namespace: shop
spec:
  type: ClusterIP
  selector:
    app: web                # routes to Pods carrying app=web
  ports:
    - name: http
      port: 80              # the Service's port
      targetPort: 80        # the Pod's containerPort
The #1 beginner bug

The Deployment's spec.selector.matchLabels must match the Pod template.metadata.labels, and the Service's spec.selector must match those same Pod labels. A typo means the Deployment manages zero Pods, or the Service routes to nothing (and returns connection errors). This is the first thing to check when "my Service has no endpoints."

4. The Reconcile Loop

This is the beating heart of Kubernetes. A controller is a loop that watches one kind of object and works to make the world match its spec (desired) — recording what it sees in its status (actual). Nearly everything — Deployments, ReplicaSets, Nodes, Jobs — is "just" a controller running this loop.

A controller's reconcile loop: read desired, observe actual, compute the difference, act to shrink it, then loop — continuously.

Level-triggered, not edge-triggered

This is the subtle, senior-level point. An edge-triggered system reacts to events ("a Pod died!") — and if it misses the event (a crash, a dropped message), the world stays broken. Kubernetes is level-triggered: the controller repeatedly compares the current desired vs. actual and acts on the difference. It doesn't matter whether it saw the specific event — it keeps re-checking the level, so a missed notification just gets caught on the next pass.

# every controller, forever:
for each object:
  desired = object.spec
  actual = observe_world()
  if actual != desired: take one step to close the gap
# idempotent: running it again when already correct does nothing
Why declarative wins

Because reconciliation is level-triggered and idempotent, the system is self-healing and eventually consistent by construction. Re-applying the same manifest is safe. A transient failure — a lost API event, a node blip — is recovered automatically on the next loop, with no human in the path. That's the property imperative "do X then Y" scripts can't give you.

5. Networking

Kubernetes networking rests on one strong rule that makes the rest simple to reason about.

The flat-network model

Every Pod gets its own IP address, and every Pod can reach every other Pod directly, without NAT — one big flat network. Containers within a Pod share that IP and reach each other over localhost. (The IP plumbing is implemented by a pluggable CNI network plugin — Calico, Cilium, Flannel, etc.)

Why Services exist

Pod IPs are ephemeral — Pods come and go, and each new one gets a new IP. You can't hard-code them. A Service gives a stable virtual IP (the ClusterIP) and DNS name that front a dynamic set of Pods chosen by label selector. The Service's backing set is tracked as Endpoints / EndpointSlices, updated automatically as Pods pass or fail their readiness probe.

A caller resolves the Service's DNS name to its stable ClusterIP; kube-proxy's rules load-balance each connection to one healthy backing Pod, whatever their (changing) IPs.

How kube-proxy actually routes

  • iptables mode (default): kube-proxy writes iptables rules that DNAT a packet destined for the ClusterIP to one of the backend Pod IPs, chosen with roughly equal probability. Simple and solid; rule evaluation grows with the number of Services.
  • IPVS mode: uses the Linux kernel's IPVS load balancer — better performance at large scale and real LB algorithms (round-robin, least-conn, etc.).

DNS and Ingress

DNS: the in-cluster DNS server (CoreDNS) gives every Service a name. The fully-qualified form is <service>.<namespace>.svc.cluster.local; a Pod in the same namespace can just use <service>. That's how service discovery works without any external registry.

Ingress (L7): a Service of type LoadBalancer gives you one external IP per service, which gets expensive and is L4 only. An Ingress is an L7 (HTTP/HTTPS) router: host- and path-based rules ("/api → api-service, shop.example.com → web-service") and TLS termination, all behind one entry point. An Ingress object is inert without an Ingress controller (e.g. an NGINX- or cloud-based controller) running in the cluster to fulfill it.

Layers, quickly

ClusterIP/NodePort/LoadBalancer operate at L4 (IP/port). Ingress operates at L7 (HTTP routing, virtual hosts, TLS). The newer Gateway API is the evolving successor to Ingress for richer L7/L4 routing — good to name, not required.

6. Config & Storage

Keep configuration and secrets out of the image, and give stateful Pods durable storage that outlives them.

ConfigMap & Secret

  • ConfigMap — non-confidential key/value config (env vars, flags, whole config files) injected into Pods as environment variables or mounted files. Changing it doesn't rebuild the image.
  • Secret — the same idea for sensitive data (passwords, tokens, TLS keys).
A Secret is not encryption

By default a Secret's data is only base64-encoded in etcd — encoding, not encryption. To actually protect it you must enable encryption at rest for etcd (an EncryptionConfiguration, ideally backed by a KMS) and lock down access with RBAC. Saying "a Secret is base64, not encrypted, so I'd turn on etcd encryption-at-rest and restrict RBAC" is a strong security signal.

Volumes, PV, PVC, StorageClass

A container's filesystem is ephemeral — it's gone when the container restarts. Kubernetes storage fixes that in layers:

ObjectWhat it is
Volume (e.g. emptyDir)Storage tied to a Pod's lifetime; emptyDir is scratch space shared by a Pod's containers, erased when the Pod is removed.
PersistentVolume (PV)A piece of durable storage in the cluster (a cloud disk, an NFS share) — a cluster-level resource, independent of any one Pod.
PersistentVolumeClaim (PVC)A user's request for storage ("10Gi, ReadWriteOnce"). It binds to a matching PV; the Pod mounts the PVC, not the PV directly.
StorageClassA template for dynamic provisioning: when a PVC references it, the cluster creates a PV on demand (e.g. spins up a cloud disk) — no pre-provisioning.

Access modes on a claim spell out sharing: ReadWriteOnce (one node), ReadOnlyMany, ReadWriteMany (many nodes — only some backends support it). Stateful workloads (databases) typically pair a StatefulSet with per-Pod PVCs so each replica gets its own stable disk and identity.

7. Scheduling & Resources

Requests vs. limits — the distinction that trips people up

  • Request = what the container is guaranteed. The scheduler uses the sum of requests to find a node with enough allocatable capacity. It affects placement.
  • Limit = the ceiling the container may use. The kubelet/runtime enforces it at runtime via cgroups. It affects runtime behavior.
CPU throttles; memory kills

The two resources behave differently at the limit. CPU is compressible: exceed the CPU limit and the container is merely throttled (slowed). Memory is incompressible: exceed the memory limit and the container is OOMKilled (terminated with OOMKilled, then restarted per its policy). This is why an under-set memory limit shows up as mysterious restarts, and why memory limits deserve careful sizing.

QoS classes (derived from requests/limits)

ClassConditionEviction priority under node pressure
GuaranteedEvery container sets CPU and memory, with request == limitEvicted last (most protected)
BurstableAt least one request/limit set, but not GuaranteedEvicted in the middle
BestEffortNo requests or limits at allEvicted first

When a node runs low on memory, the kubelet evicts Pods to reclaim it, and QoS class sets the order — BestEffort go first, Guaranteed are the last to be sacrificed.

Steering Pods onto nodes

  • nodeSelector: the simplest — schedule only onto nodes carrying a label (e.g. disktype: ssd).
  • Affinity / anti-affinity: richer rules, required (hard) or preferred (soft): node affinity ("prefer GPU nodes"), and Pod (anti-)affinity ("spread replicas across zones," "co-locate with the cache").
  • Taints & tolerations: the inverse — a taint on a node repels Pods; only a Pod with a matching toleration may land there. Used to reserve nodes (GPU pools, dedicated tenants) or to keep workloads off control-plane nodes.
Affinity vs. taints — which way it points

Affinity is the Pod saying "I want this kind of node." A taint is the node saying "keep out unless you tolerate me." One attracts; the other repels. Interviewers like to hear that contrast.

Autoscaling (HPA)

The HorizontalPodAutoscaler adjusts a Deployment's replica count to hit a target metric (commonly average CPU utilization, or custom metrics). It reads metrics (via the metrics-server) and recomputes the desired replicas:

desiredReplicas = ceil( currentReplicas × (currentMetric / desiredMetric) )
# e.g. 4 replicas at 80% CPU, target 50%:
ceil(4 × (80 / 50)) = ceil(6.4) = 7 replicas

HPA changes the number of Pods (horizontal). Its cousins: the Vertical Pod Autoscaler tunes requests/limits of existing Pods, and the Cluster Autoscaler adds/removes nodes when Pods can't be scheduled or nodes sit idle.

8. Rollouts & Health

How a rolling update works

Change a Deployment's image and, by default, it performs a RollingUpdate: it creates a new ReplicaSet and shifts Pods from old to new gradually, keeping the app available throughout. Two settings bound the churn:

  • maxSurge — how many Pods above the desired count may exist during the roll (default 25%). Higher = faster, more temporary capacity.
  • maxUnavailable — how many may be unavailable during the roll (default 25%). Lower = safer, slower.

The Deployment scales the new ReplicaSet up and the old one down step by step, always respecting both bounds, until the new one holds all replicas. The alternative strategy, Recreate, kills all old Pods before starting new ones — a brief outage, used when two versions can't run at once.

# replicas=4, maxSurge=25% (→1), maxUnavailable=25% (→1)
step: add 1 new (surge to 5) → wait until new is Ready → kill 1 old
repeat until all 4 are the new version, never dropping below 3 available

Rollback

Because the old ReplicaSet is retained (scaled to 0), reverting is one command — kubectl rollout undo scales the previous ReplicaSet back up and the bad one down. No image rebuild, no manual surgery.

The three probes

ProbeQuestion it answersOn failure
readiness"Ready to receive traffic right now?"Pod is removed from Service endpoints (no traffic) — but not restarted. Recovers when it passes again.
liveness"Is the process alive, or stuck?"The container is restarted.
startup"Has a slow-starting app finished booting?"Holds off liveness/readiness until it succeeds, so a slow boot isn't mistaken for a hang and killed.
Readiness vs. liveness — don't conflate them

A classic outage: pointing liveness at a check that fails under load (or during a slow dependency). The kubelet then restarts healthy-but-busy containers, making things worse. Use readiness to pull a temporarily-overloaded Pod out of rotation (no restart), and reserve liveness for "truly stuck, only a restart fixes it." Add a startup probe for apps with long init so their boot time doesn't trip liveness.

9. Practical kubectl & Debugging

kubectl is the CLI that talks to the API server. A compact, correct working set:

# --- inspect ---
kubectl get pods -n shop -o wide          # list Pods (+ node, IP)
kubectl get deploy,svc,ep -n shop         # deployments, services, endpoints
kubectl describe pod web-abc123 -n shop   # full detail + Events (scheduling, pulls, probes)
kubectl get events -n shop --sort-by=.lastTimestamp

# --- logs ---
kubectl logs web-abc123 -n shop           # current container logs
kubectl logs web-abc123 -n shop --previous   # logs from the PRIOR crashed container
kubectl logs -f deploy/web -n shop        # follow (stream) a Deployment's Pods

# --- apply / change ---
kubectl apply -f web.yaml                 # declarative create-or-update
kubectl set image deploy/web web=nginx:1.28 -n shop   # triggers a rolling update
kubectl scale deploy/web --replicas=5 -n shop

# --- rollout ---
kubectl rollout status deploy/web -n shop   # watch the roll finish
kubectl rollout history deploy/web -n shop
kubectl rollout undo deploy/web -n shop     # roll back to previous revision

# --- get inside / reach in ---
kubectl exec -it web-abc123 -n shop -- /bin/sh   # shell into a container
kubectl port-forward svc/web 8080:80 -n shop     # local:8080 → Service:80

Debugging a CrashLoopBackOff

CrashLoopBackOff means the container keeps starting and then exiting/failing, so the kubelet restarts it with an increasing back-off delay (roughly 10s, 20s, 40s … capped at 5 minutes). It's a symptom, not a root cause.

# the drill
1. kubectl logs <pod> --previous # WHY did the last run die? (stack trace, bad config)
2. kubectl describe pod <pod> # Events + Last State: exit code, OOMKilled?
3. check: crash on startup? bad env/ConfigMap? missing dependency? failing liveness probe?
  • Exit code + --previous logs usually reveal it: a config error, an unreachable dependency, a panic on boot.
  • Last State: Terminated · Reason: OOMKilled in describe → the memory limit is too low (§7). Raise it or fix the leak.
  • Liveness probe too aggressive → the app is restarted before it finishes booting. Add/loosen a startup probe (§8).

Debugging a Pending Pod

Pending means the Pod exists but hasn't been scheduled onto a node (or its images/volumes aren't ready). The scheduler records exactly why in the Pod's Events:

kubectl describe pod <pod> # read the Events at the bottom
# common causes:
• Insufficient cpu/memory — no node has room for the requests → add nodes / lower requests
• node(s) had untolerated taint — needs a matching toleration
• node affinity/selector didn't match — no node has the required label
• unbound PersistentVolumeClaim — the PVC has no PV / StorageClass to satisfy it
The universal first move

For almost any misbehaving Pod, kubectl describe pod <name> and kubectl get events tell you what the control plane tried and why it stopped. Read the Events before guessing.

10. Trade-offs & Interview Framing

The complexity cost — and managed vs. self-hosted

What K8s buys you
  • Self-healing, declarative, portable across clouds
  • One consistent model for deploy, scale, rollout, discovery
  • A huge ecosystem and standard operational vocabulary
What it costs
  • Real operational + cognitive overhead
  • A control plane, networking, RBAC, and upgrades to run
  • Easy to over-engineer for small workloads

Managed (a cloud's Kubernetes service) runs and upgrades the control plane and etcd for you — you manage workloads and (sometimes) nodes. It's the default for most teams: you skip the hardest operational parts. Self-hosted gives full control and avoids lock-in but means you own etcd backups, upgrades, and availability — justified mainly by special compliance, on-prem, or cost constraints. Naming this trade-off — and defaulting to managed unless there's a concrete reason not to — is the senior answer.

Probe questions & crisp answers

Q: What is a Service, really?
A stable virtual IP + DNS name that load-balances to a dynamic set of Pods selected by label. Pod IPs are ephemeral; the Service is the fixed handle. kube-proxy programs iptables/IPVS rules on each node to DNAT traffic for the ClusterIP to a healthy backend, and readiness probes govern which Pods are in the endpoint set. Types: ClusterIP (internal), NodePort, LoadBalancer, ExternalName.

Q: Requests vs. limits — and what's an OOMKill?
Requests are the guaranteed amount the scheduler uses to place a Pod; limits are the runtime ceiling the kubelet enforces via cgroups. CPU over its limit is throttled (compressible); memory over its limit is OOMKilled — the container is terminated and restarted. So a too-low memory limit shows up as CrashLoopBackOff with Reason: OOMKilled.

Q: Readiness vs. liveness probe?
Readiness = "should I get traffic now?" — failing pulls the Pod out of the Service (no restart). Liveness = "am I stuck?" — failing restarts the container. Misusing liveness for load-sensitive checks causes restart storms; use readiness to shed load and a startup probe for slow boots.

Q: Walk me through a rolling update.
Changing the image makes the Deployment create a new ReplicaSet and shift Pods gradually, bounded by maxSurge (extra Pods allowed) and maxUnavailable (missing Pods allowed) — both default 25%. New Pods must pass readiness before old ones are removed, so the app stays available. The old ReplicaSet is kept at 0 so rollout undo can revert in one step.

Q: What's etcd's role, and why does consistency matter?
etcd is the cluster's single source of truth — every object lives there, and only the API server touches it. It uses Raft, so writes need a quorum of a majority of an odd member set (3/5), giving strong consistency. That consistency is what lets controllers trust the observed desired state; lose etcd (or quorum) and the cluster can't make reliable decisions — hence back it up and run it HA.

One-line summary

Kubernetes is a declarative, level-triggered orchestrator: you state the desired end state and controllers continuously reconcile reality toward it. Master the control-plane/node split, the Pod→ReplicaSet→Deployment→Service ladder, the reconcile loop, requests-vs-limits and the probes, and you can reason about deploying, scaling, and debugging almost anything on a cluster — and say clearly when not to reach for it.
