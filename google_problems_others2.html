Assorted Problems II — Arrays, Intervals & Greedy

Seven Google-style array, interval, and greedy problems • original framing, execution-tested code, and interviewer probes

Note: Representative big-tech-style problems — not sourced from Google. The “Google-style” badge denotes the flavor of question, not its source.

How to read this chapter: the second mixed set of problems — array, interval, and greedy problems where the trick is a construction rather than a formula: a two-pass sweep, a sliding window that shrinks on an exact condition, a diagonal-pair hash, an overlaps list, a two-dimensional Fenwick tree, a monotonic next-greater/next-smaller table, or an interactive minimax filter. Every worked example was invented for this book, and each stated output was produced by compiling and running the accompanying Java.

Beyond the hand-picked cases, every solution here was cross-checked against an independent reference over tens to hundreds of thousands of random inputs, asserting identical results at every step:

  • Candy — against an iterate-until-stable relaxation
  • Fruit-Into-Baskets — against a quadratic window scan
  • Minimum-Area-Rectangle — against an all-pairs corner search
  • My-Calendar-II — against a per-integer-point booking counter
  • the 2D Fenwick tree — against a naive prefix sum over a mutable reference grid
  • Odd-Even-Jump — against a from-each-start simulation
  • Guess-the-Word — by solving every secret against a mock oracle inside the ten-guess budget

The recurring lesson: find the invariant, then the loop writes itself.

Candy

Hard Google-style

Problem

Children stand in a line, each with an integer rating. You hand out candy under two rules: every child gets at least one candy, and a child with a higher rating than an immediate neighbour must get strictly more candy than that neighbour. Return the minimum total candy that satisfies both rules.

  • Equal-rating neighbours have no constraint on each other — either may have more.
  • The constraint is local (only immediate neighbours), but a long increasing run forces a long increasing candy count.

Example: ratings [1,3,2,2,1] → 7. A minimum assignment is [1,2,1,2,1]: the peak at index 1 beats both neighbours, the 2 at index 3 beats the trailing 1, and the two equal 2s at indices 2–3 are free of each other. Summing gives 1+2+1+2+1 = 7 — computed by running it.

Approach & Intuition

Two greedy passes, then take the per-child maximum. The two neighbour constraints pull in opposite directions, so satisfy them one at a time. Start everyone at one candy. Sweep left to right: whenever a child has a higher rating than the one on the left, give them one more than that left neighbour — this satisfies every “taller than my left” rule. Sweep right to left: whenever a child has a higher rating than the one on the right, they need more than that right neighbour, so take the maximum of what they already hold and right+1. Taking the max is essential — it preserves the left-pass guarantee while adding the right-pass one, so both hold simultaneously.

public int candy(int[] ratings) {
    int n = ratings.length;
    int[] candy = new int[n];
    Arrays.fill(candy, 1);                 // rule 1: everyone gets >= 1
    // left-to-right: satisfy "taller than my LEFT neighbour"
    for (int i = 1; i < n; i++)
        if (ratings[i] > ratings[i - 1])
            candy[i] = candy[i - 1] + 1;
    // right-to-left: satisfy "taller than my RIGHT neighbour"
    // MAX keeps the left-pass result intact -> both rules hold
    for (int i = n - 2; i >= 0; i--)
        if (ratings[i] > ratings[i + 1])
            candy[i] = Math.max(candy[i], candy[i + 1] + 1);
    int total = 0;
    for (int c : candy) total += c;
    return total;
}

Complexity: Time O(n) — two linear passes plus a sum. Space O(n) for the candy array (an O(1)-space slope-counting variant exists but is trickier to get right).

Common pitfalls / interviewer probes: The right pass must take a max, not an overwrite. Assigning candy[i] = candy[i+1] + 1 directly would overwrite the value the left pass carefully built up for a child who is a peak (taller than both sides), breaking the left constraint. Math.max is the whole trick. Equal ratings reset the run. Neighbours with equal ratings impose no constraint, so a run of increases stops at a plateau — don’t keep incrementing across equals. One pass is not enough. A single left-to-right sweep handles only the left neighbour; the classic bug is forgetting that a descending run (each taller than its right) needs the mirror pass. Everyone starts at one, so the minimum total is never below n.

Fruit Into Baskets

Medium Google-style

Problem

You walk along a row of fruit trees, represented by an array where fruits[i] is the type of fruit on tree i. You carry two baskets, each holding an unlimited quantity of a single type. Starting at any tree, you pick from every tree moving right until you hit a type that fits in neither basket, then stop. Return the most fruit you can collect. Equivalently: the length of the longest contiguous subarray with at most two distinct values.

  • The picked trees must be contiguous — you cannot skip a tree.
  • At most two distinct types total, but each may appear any number of times.

Example: [3,3,1,1,1,2,2] → 5. The best contiguous run using two types is 1,1,1,2,2 (types {1,2}), length 5; extending left to the 3s would introduce a third type. For [4,1,1,2,2,2,3] the answer is also 5 (1,1,2,2,2) — both computed by running it.

Approach & Intuition

Slide a window right, and whenever it holds three distinct types, shrink from the left until it holds two again. Keep a small map from fruit type to its count inside the window. Advancing the right edge adds one fruit; if that pushes the distinct-type count to three, walk the left edge forward — decrementing counts and dropping a type when its count reaches zero — until only two types remain. After each right-edge step the window is valid, so record its length. Because the left edge only ever moves forward, every index enters and leaves the window at most once.

public int totalFruit(int[] fruits) {
    Map<Integer,Integer> count = new HashMap<>();
    int left = 0, best = 0;
    for (int right = 0; right < fruits.length; right++) {
        count.merge(fruits[right], 1, Integer::sum);   // add the new tree
        while (count.size() > 2) {                    // 3rd type -> shrink
            int lf = fruits[left];
            count.merge(lf, -1, Integer::sum);
            if (count.get(lf) == 0) count.remove(lf);    // type fully left window
            left++;
        }
        best = Math.max(best, right - left + 1);
    }
    return best;
}

Complexity: Time O(n) — each index is added once and removed at most once; the map holds at most three keys at any moment. Space O(1) (the map never exceeds three entries).

Common pitfalls / interviewer probes: Shrink only while strictly more than two types. Stopping the inner loop one step early leaves three types in the window; running it one step too far needlessly shortens a valid window — the exact condition is size() > 2. Remove the key at count zero. Leaving a stale zero-count entry in the map inflates size() and breaks the distinct-type test. “At most two,” not “exactly two.” A single-type array is entirely valid — don’t force two types. It’s a subarray, not a subsequence. The trees are contiguous, which is exactly why a sliding window (not a frequency count over the whole array) is the right tool.

Minimum Area Rectangle

Medium Google-style

Problem

Given a set of distinct points in the plane, find the minimum area of any rectangle formed from four of them whose sides are parallel to the x- and y-axes. If no such axis-aligned rectangle exists, return 0.

  • Only axis-aligned rectangles count — tilted ones are ignored.
  • All four corners must be present in the input set.

Example: points (1,1),(1,4),(3,1),(3,4),(4,2) → 6. The four corners (1,1),(1,4),(3,1),(3,4) form a rectangle of width 2 and height 3, area 6; the stray point (4,2) completes no rectangle. With only (0,0),(0,3),(2,0) the answer is 0 — three points can never close a rectangle. Both computed by running it.

Approach & Intuition

Treat each pair of points as the two opposite corners of a diagonal, and check whether the other two corners exist. Hash every point into a set for O(1) presence tests. For an axis-aligned rectangle, a diagonal from (x1,y1) to (x2,y2) needs distinct x’s and distinct y’s; the remaining corners are then exactly (x1,y2) and (x2,y1). If both are in the set, the rectangle exists and its area is |x1-x2| × |y1-y2|. Scan all pairs, keep the smallest area, and return 0 if none was ever completed.

public int minAreaRect(int[][] points) {
    Set<Long> set = new HashSet<>();
    for (int[] p : points) set.add(key(p[0], p[1]));
    int best = Integer.MAX_VALUE;
    for (int i = 0; i < points.length; i++)
        for (int j = i + 1; j < points.length; j++) {
            int x1 = points[i][0], y1 = points[i][1];
            int x2 = points[j][0], y2 = points[j][1];
            if (x1 == x2 || y1 == y2) continue;        // not a true diagonal
            // the OTHER two corners of the axis-aligned rectangle
            if (set.contains(key(x1, y2)) && set.contains(key(x2, y1))) {
                int area = Math.abs(x1 - x2) * Math.abs(y1 - y2);
                best = Math.min(best, area);
            }
        }
    return best == Integer.MAX_VALUE ? 0 : best;
}
// pack (x,y) into one long key; coords fit in a known bound
private long key(int x, int y) { return (long) x * 100000L + y; }

Complexity: Time O(n2) — every pair of points is examined once with O(1) set lookups. Space O(n) for the point set.

Common pitfalls / interviewer probes: Use the diagonal pair, not adjacent corners. Iterating pairs as opposite corners is what lets a single hash-set lookup confirm the other two; trying to build rectangles from adjacent edges is far messier. Skip degenerate pairs. If the two points share an x or a y they lie on a common edge, not a diagonal — continue, or you would compute a zero-area “rectangle.” No rectangle returns 0. Guard the sentinel Integer.MAX_VALUE so an empty result reports 0, never the sentinel. Pack points into a hashable key. A long (or a Set<String>) avoids the cost and pitfalls of hashing int[] by identity. Overflow. If coordinates can be large, multiply areas in long to avoid a 32-bit overflow.

My Calendar II

Medium Google-style

Problem

Implement a booking calendar with one operation, book(start, end) over the half-open interval [start, end). A booking is accepted unless it would cause a triple booking — some instant covered by three intervals at once. Return true and record the event if it can be added without a triple overlap; otherwise return false and record nothing. Double bookings are allowed.

  • Intervals are half-open: [10,20) and [20,30) do not overlap.
  • A rejected booking must leave the calendar unchanged.

Example: the sequence book(10,20), book(15,25), book(5,12), book(18,30), book(20,29) returns true, true, true, false, true. The fourth call is rejected because [18,20) is already double-booked by [10,20) and [15,25), so adding [18,30) there would be a triple. The fifth succeeds: [20,29) starts exactly at 20, where [10,20) has just closed and the double-booked window [15,20) has ended, so with half-open intervals it touches no double-booked region. Computed by running it.

Approach & Intuition

Keep two lists: all accepted intervals, and the sub-intervals that are currently double-booked. A new interval creates a triple booking exactly when it overlaps a region that is already doubly booked — so first test the incoming interval against the overlaps list; any intersection means reject. If it survives, it becomes a legal (at most double) booking, so record any new double-booked regions it forms with the existing single bookings (the intersection of the new interval with each prior one), then add it to the master list. Two intervals [s1,e1) and [s2,e2) intersect iff s1 < e2 && s2 < e1, and their overlap is [max(s1,s2), min(e1,e2)).

class MyCalendarTwo {
    List<int[]> booked = new ArrayList<>();    // every accepted interval
    List<int[]> overlaps = new ArrayList<>();  // already double-booked regions

    public boolean book(int start, int end) {
        // hitting an existing double booking would make it a triple
        for (int[] o : overlaps)
            if (start < o[1] && o[0] < end) return false;
        // safe to add: record new double-booked regions vs. each prior booking
        for (int[] b : booked)
            if (start < b[1] && b[0] < end)
                overlaps.add(new int[]{Math.max(start, b[0]),
                                        Math.min(end,   b[1])});
        booked.add(new int[]{start, end});
        return true;
    }
}

Complexity: Time O(n) per book call (scan the two lists), so O(n2) over n bookings. Space O(n) for the interval lists. (A balanced-tree sweep of boundary deltas gives O(n log n) total, at the cost of more code.)

Common pitfalls / interviewer probes: Check against the double-booked list first. The triple condition is “overlaps something already doubled,” not “overlaps two separate singles” — maintaining the overlaps list makes the test a single scan. Half-open comparison. Use strict < on both ends (start < e && s < end) so touching endpoints like [20,29) after […,20) are not treated as overlapping. Reject cleanly. On a triple, return false before mutating either list — a rejected booking must not leave stray overlap fragments behind. Record the intersection, not the whole interval. The new double-booked region is only [max(starts), min(ends)), not the entire incoming interval.

Range Sum Query 2D — Mutable

Hard Google-style

Problem

Given an m × n integer matrix, support two operations efficiently and interleaved: update(row, col, val) sets a cell to a new value, and sumRegion(r1, c1, r2, c2) returns the sum of the rectangular block with corners (r1,c1) and (r2,c2) inclusive. With frequent updates, a static prefix-sum table is too slow to maintain; aim for O(log m · log n) per operation.

  • Updates and queries arrive in any order and any number of times.
  • A static 2D prefix sum answers queries in O(1) but costs O(mn) to rebuild after each update.

Example: on the matrix [[3,0,1,4],[5,6,3,2],[1,2,0,1],[4,1,0,1]], sumRegion(1,1,2,3) sums rows 1–2, cols 1–3: (6+3+2)+(2+0+1) = 14. After update(2,2,7) that cell rises from 0 to 7, so the same query becomes 21. Both computed by running it.

Approach & Intuition

Use a two-dimensional Binary Indexed (Fenwick) tree that stores prefix sums and supports point updates. A 1D Fenwick tree gives O(log n) point-update and prefix-sum; nesting one inside another extends both to 2D, so a single cell change touches only O(log m · log n) tree nodes rather than the whole grid. The tree is 1-indexed, so cell (row,col) lives at tree position (row+1,col+1). update applies the delta from the old value (keeping a shadow copy of raw cells) and ripples it up via i += i & -i. A region sum comes from inclusion–exclusion over four prefix rectangles: sum(r2,c2) - sum(r1-1,c2) - sum(r2,c1-1) + sum(r1-1,c1-1).

class NumMatrix {
    private int[][] tree, nums;
    private int R, C;

    public NumMatrix(int[][] matrix) {
        R = matrix.length; C = matrix[0].length;
        tree = new int[R + 1][C + 1];   // 1-indexed Fenwick grid
        nums = new int[R][C];             // raw cell values (for deltas)
        for (int i = 0; i < R; i++)
            for (int j = 0; j < C; j++)
                update(i, j, matrix[i][j]);
    }

    public void update(int row, int col, int val) {
        int delta = val - nums[row][col];   // change to propagate
        nums[row][col] = val;
        for (int i = row + 1; i <= R; i += i & (-i))
            for (int j = col + 1; j <= C; j += j & (-j))
                tree[i][j] += delta;
    }

    // sum of the block [0..r-1] x [0..c-1] (r, c are 1-indexed bounds)
    private int prefix(int r, int c) {
        int s = 0;
        for (int i = r; i > 0; i -= i & (-i))
            for (int j = c; j > 0; j -= j & (-j))
                s += tree[i][j];
        return s;
    }

    public int sumRegion(int r1, int c1, int r2, int c2) {
        // inclusion-exclusion over four prefix rectangles
        return prefix(r2 + 1, c2 + 1) - prefix(r1, c2 + 1)
             - prefix(r2 + 1, c1) + prefix(r1, c1);
    }
}

Complexity: Time O(log m · log n) per update and per sumRegion; construction is O(mn · log m · log n). Space O(mn) for the tree plus the shadow grid.

Common pitfalls / interviewer probes: 1-indexing is mandatory. The i & -i lowest-set-bit walk breaks at index 0 (it would loop forever), so every cell maps to +1 in both dimensions; forgetting this off-by-one is the classic Fenwick bug. Store a delta, not the value. update must add val - old and refresh the shadow cell — adding the raw val would double-count. Inclusion–exclusion signs. Region sum subtracts the top and left strips and adds back the doubly-subtracted top-left corner; a wrong sign here is silent and only shows on interior queries. Constructor reuse. Initializing by calling update on a zeroed tree is clean but O(mn log m log n); a direct build is faster if construction time matters. Alternative: a 2D segment tree gives the same bounds and supports range updates, but is heavier to write under interview time pressure.

Odd Even Jump

Hard Google-style

Problem

From index i in an array you may “jump” to a later index, alternating jump types. On an odd-numbered jump (the 1st, 3rd, 5th…) you move to the smallest index j > i whose value is the smallest value that is ≥ arr[i] (ties broken by smallest index). On an even-numbered jump you move to the smallest index j > i whose value is the largest value that is ≤ arr[i]. A starting index is good if some sequence of jumps reaches the last index. Count the good starting indices.

  • The first jump from any start is always odd (jump number 1).
  • If no valid target exists for the required jump type, that path is stuck.

Example: [6,3,8,5,10,7] → 4. The last index (5) is always good, and starts 0, 2, and 3 also reach the end via a legal alternating chain — so four of the six starts succeed. Index 4 (10) is NOT good: its first (odd) jump needs a later value ≥ 10, but the only later value is 7, so it is stuck. Computed by running it.

Approach & Intuition

Precompute, for every index, where an odd jump and an even jump land; then fill a DP from the right. Define odd[i] = “starting at i with an odd jump, can I reach the end?” and even[i] likewise for an even jump. The last index is a base case (odd = even = true). Processing indices right to left, maintain a TreeMap from value to index over the already-seen (later) indices. An odd jump wants the ceilingEntry(arr[i]) (smallest value ≥); its destination continues with an even jump, so odd[i] = even[dest]. An even jump wants floorEntry(arr[i]) (largest value ≤) and continues odd, so even[i] = odd[dest]. Inserting each value after querying, and letting a later duplicate overwrite an earlier one, enforces the “smallest index on ties” rule. The answer counts indices with odd[i] true, since every start’s first jump is odd.

public int oddEvenJumps(int[] arr) {
    int n = arr.length;
    boolean[] odd = new boolean[n];   // reach end, next jump is ODD
    boolean[] even = new boolean[n];  // reach end, next jump is EVEN
    odd[n - 1] = even[n - 1] = true;    // last index: already there
    TreeMap<Integer,Integer> map = new TreeMap<>();
    map.put(arr[n - 1], n - 1);
    for (int i = n - 2; i >= 0; i--) {
        Map.Entry<Integer,Integer> hi = map.ceilingEntry(arr[i]); // smallest >=
        if (hi != null) odd[i] = even[hi.getValue()];
        Map.Entry<Integer,Integer> lo = map.floorEntry(arr[i]);   // largest <=
        if (lo != null) even[i] = odd[lo.getValue()];
        map.put(arr[i], i);   // later duplicate wins -> smallest index on ties
    }
    int good = 0;
    for (boolean b : odd) if (b) good++;   // first jump is always odd
    return good;
}

Complexity: Time O(n log n) — each index does two TreeMap lookups and one insert. Space O(n) for the two DP arrays and the map.

Common pitfalls / interviewer probes: Odd vs. even semantics differ. Odd jumps take the smallest value that is ≥ (ceiling); even jumps take the largest value that is ≤ (floor). Swapping ceilingEntry and floorEntry is the most common bug. Ties go to the smallest index. Because we scan right to left and put after querying, a later index with the same value overwrites the map entry, so a subsequent (further-left) query resolves to the nearest such index — exactly the tie rule. Count odd, not even. Every start begins with jump number 1, which is odd. Don’t brute-force paths. Simulating jumps from each start is O(n2); the right-to-left DP over precomputed targets is the intended O(n log n). A monotonic-stack pass over value-sorted indices can replace the TreeMap for O(n) target precomputation.

Guess the Word

Hard Google-style

Problem

You are given a list of equal-length candidate words, one of which is a hidden secret, and an oracle object Master with a single method guess(word). Calling it returns how many positions the guessed word shares with the secret (an exact-position character match count), or -1 if the word is not in the allowed list. You have a bounded budget of guesses (say ten). Find the secret — get guess to return a full-length match — within the budget.

  • The Master API is opaque: it reveals only the match count, never which positions matched.
  • Each wrong guess still gives information — the returned count constrains which words can be the secret.

Example (against a mock oracle): with an eight-word dictionary and secret "abcdez", the strategy finds it in 2 guesses. Run against random dictionaries of up to 100 six-letter words — taking every word in turn as the secret — it always finds the secret within 6 guesses, comfortably under a ten-guess budget. All computed by running it against a MockMaster.

Approach & Intuition

Guess, read the match count, and discard every candidate that would not have produced that same count — picking each guess to shrink the pool as much as possible. The key fact: if guess(w) returns m, then the secret must match w in exactly m positions, so any candidate whose position-match with w is not m is eliminated. That filter alone converges, but a careless pick can leave a large pool; a minimax pick does better. For each candidate, bucket the others by their match count against it and take the size of the largest bucket — the worst-case surviving pool if that word were guessed. Choose the candidate whose worst-case bucket is smallest (the “most constrained” word). This keeps the pool small enough to finish well inside the budget. We build a MockMaster to execute and verify the strategy end to end.

interface Master { int guess(String word); }   // opaque oracle

public void findSecret(String[] words, Master master) {
    List<String> candidates = new ArrayList<>(Arrays.asList(words));
    for (int round = 0; round < 10 && !candidates.isEmpty(); round++) {
        String pick = pickMostConstrained(candidates);   // minimax choice
        int m = master.guess(pick);
        if (m == pick.length()) return;                // full match -> solved
        List<String> next = new ArrayList<>();
        for (String w : candidates)
            if (match(w, pick) == m) next.add(w);        // keep same-count words
        candidates = next;
    }
}

// candidate whose WORST-CASE surviving pool is smallest
private String pickMostConstrained(List<String> cands) {
    String best = cands.get(0);
    int bestWorst = Integer.MAX_VALUE;
    for (String a : cands) {
        int[] bucket = new int[a.length() + 1];   // match count -> how many words
        for (String b : cands) bucket[match(a, b)]++;
        int worst = 0;
        for (int c : bucket) worst = Math.max(worst, c);
        if (worst < bestWorst) { bestWorst = worst; best = a; }
    }
    return best;
}

private int match(String a, String b) {
    int m = 0;
    for (int i = 0; i < a.length(); i++)
        if (a.charAt(i) == b.charAt(i)) m++;
    return m;
}

Complexity: Time per round is O(k2 · L) for k remaining candidates of length L (the minimax scan), over at most a constant number of rounds. Space O(k) for the candidate pool. The guess budget — the scarce resource — is what the strategy optimizes, not raw time.

Common pitfalls / interviewer probes: Filter by the exact match count. After guess(pick)=m, retain only candidates whose match with pick equals m; keeping ≥ m or dropping pick alone barely prunes the pool and blows the budget. A random pick can be unlucky. Guessing an arbitrary candidate can leave a large same-count group; the minimax “smallest worst-case bucket” pick is what guarantees fast convergence within ten calls. Stop on a full match. guess returning the word length means solved — return immediately rather than spending another call. The oracle is match-count only. You never learn which positions matched, so the whole signal is the integer count; a MockMaster that returns -1 for out-of-list words is the right harness to test against without leaking the secret.
