Designing Mobile-Backed Systems — Offline-First, Sync & the Flaky-Network Reality
A phone is not a small server. It has a battery, a patchy network, limited RAM, and an app-store release cycle measured in days. This chapter ties the System Design Playbook to the mobile client: offline-first storage, background sync with conflict resolution, push, media upload, mobile-shaped APIs (BFF), secure token storage, and a full worked "offline notes / chat" design.

What Makes Mobile Different

Before any boxes-and-arrows, name the constraints a phone forces on you that a browser or another backend service never would. Get these out loud and the interviewer knows you actually ship mobile.

The analogy: a backend service is an office worker at a desk with fibre internet and unlimited coffee. A mobile client is a hiker — sometimes on WiFi at base camp, sometimes on one bar in a tunnel, sometimes fully offline in the woods — carrying a battery that must last all day and a backpack (RAM/disk) that's already half full of other apps. You cannot design for the hiker the way you design for the office worker.

INSIGHT

Every mobile design decision traces back to one of five constraints: flaky networks, battery, limited resources, app-store release latency, and version fragmentation. If you can recite these and show which one is driving each choice, you sound senior. If you design as if the phone is a reliable always-connected client, you sound like a backend engineer who has never owned a crash-rate dashboard.

Where the mobile client sits in the system

TIP

Open a mobile design round by partitioning responsibility: "The phone owns local state and the UX; the edge/BFF owns shaping data for this client; the backend owns the source-of-truth business logic. Most of the hard problems live at the seam between the phone's local store and the backend's store — that's where sync and conflicts live." That sentence frames the whole interview.

TRAP

Treating the network as reliable. The classic no-hire move is a design where the tap handler calls the API synchronously and shows a spinner. On a phone that spinner becomes a 5-second hang, a lost write on a dropped connection, and a duplicate write on the retry. If your write path doesn't survive "the request succeeded on the server but the response never came back," you haven't designed for mobile.

"A phone is a partially-connected, resource-constrained client on a release cycle I can't hot-fix. So I design offline-first, make every write idempotent and retriable, batch to save battery, and keep the API additively versioned so old app versions in the wild never break."

Interview angle

INTERVIEW ANGLE

Interviewers use "design X for mobile" to see whether you reach for the phone's constraints unprompted. Lead with the five constraints, then let them drive your architecture. The strongest candidates spell out their reasoning: "The reason I'm making the local DB the source of truth is the flaky-network constraint; the reason I'm batching is battery; the reason the API is additive-only is release latency." Mapping each choice to a constraint is the L5→L6 signal.

Offline-First Architecture

The single most important mobile pattern: the UI reads and writes the local store, and a background sync engine reconciles with the backend. The network becomes an optimization, not a dependency.

The analogy: think of the local database as your personal notebook and the server as the shared team wiki. You always write in your own notebook first (instant, works in a tunnel). Later, when you have signal, a helper copies your new pages up to the wiki and brings down anything others changed. You never make the user wait for the wiki to load before they can write a note.

INSIGHT

Local store = source of truth for the UI. The UI never calls the network directly; it observes the local DB. Writes go to the local DB and an append-only outbox (mutation queue). A sync engine drains the outbox to the server and applies server changes back into the local DB. Result: the app is fully usable offline, feels instant (optimistic UI), and the network is just a background reconciler.

The building blocks

1Local storeSQLITE▶

A real embedded DB — Room (Android) or Core Data / SwiftData / GRDB (iOS), both on SQLite. The UI observes it via a reactive stream (Flow / @Query / NSFetchedResultsController) so any local write instantly re-renders the screen.

2Outbox / mutation queueDURABLE▶

An append-only table of pending changes, each with a client-generated mutation_id (idempotency key), the entity id, the base version it was made against, and a payload. Survives app kill. Drained in order.

3Sync engineBACKGROUND▶

Triggered by connectivity, app foreground, or an OS scheduler (WorkManager / BGTaskScheduler). Pushes the outbox, pulls a delta, resolves conflicts, updates local DB, clears applied mutations. Retries with backoff.

4Sync metadataCURSORS▶

Per-entity version / updated_at and a sync_token (server cursor) so the next pull only fetches what changed. Covered in the Data Sync tab.

WATCH

The stepper shows the case people forget: a second device changes the same record while Device A is offline. When A reconnects it pushes a mutation whose base_version (v1) no longer matches the server (now v2). That mismatch is a conflict — and how you resolve it is the whole interview.

Conflict resolution strategies

StrategyHow it decidesGood forThe catch
Last-write-wins (LWW)Highest timestamp (or highest version) wins; the other write is dropped.Single-user-owned data, presence, "last known setting".Silent data loss; clock skew makes "last" ambiguous across devices.
Field-level mergeMerge non-overlapping fields; only truly co-edited fields conflict.Records with independent fields (profile: name vs. avatar).Needs per-field version tracking; two edits to the same field still conflict.

CRDTsData types (counters, sets, RGA text) mathematically merge with no conflict.Collaborative text, counters, sets, shared docs.Larger payloads/metadata; not every data shape has a natural CRDT.

NOTE — LWW vs version vectors, the crisp difference

LWW asks "which edit is newer?" and throws the older one away. Version vectors ask a different question first: "did these two edits actually happen concurrently, or did one build on the other?" If one descends from the other, there's no conflict at all — just apply the newer. Only when the vectors are incomparable (genuine concurrent divergence) do you invoke a merge rule. LWW skips that detection step, which is why it can silently discard a legitimate change.

// Version-vector conflict detection (server-side, illustrative)
// vv maps replicaId -> counter. "dominates" = knows everything the other knows, and strictly more.
fun resolve(incoming: Change, current: Change): Resolution {
    val inc = incoming.versionVector
    val cur = current.versionVector
    return when {
        inc.sameAs(cur) -> Resolution.Ignore              // identical resend: no-op, idempotent
        inc.dominates(cur) -> Resolution.Accept(incoming)   // incoming is strictly newer
        cur.dominates(inc) -> Resolution.Ignore            // server already has a superset
        else -> Resolution.Conflict(merge(incoming, current))     // concurrent: must merge
    }
}

// Compare over the union of keys, treating a missing replica as 0 — never structural equality.
fun VersionVector.sameAs(other: VersionVector): Boolean =
    (this.keys + other.keys).all { (this[it] ?: 0) == (other[it] ?: 0) }

// dominates: mine >= other on every replica (missing = 0) AND strictly greater somewhere.
fun VersionVector.dominates(other: VersionVector): Boolean {
    val keys = this.keys + other.keys
    return keys.all { (this[it] ?: 0) >= (other[it] ?: 0) } &&
           keys.any { (this[it] ?: 0) > (other[it] ?: 0) }
}
TRAP

"Just use LWW with the client timestamp." Client clocks are not trustworthy — they drift, users change time zones, some are set wrong by minutes. LWW keyed on client wall-clock lets a device with a fast clock always win and can resurrect deleted data. If you use LWW, key it on a server-assigned monotonic version or a hybrid logical clock, and state that explicitly. Naked client-timestamp LWW is a correctness bug, not a strategy.

TRAP

Deletes are the sneakiest conflict. If a delete on one device races an edit on another, LWW may "win" the edit and the record comes back from the dead — or the delete wins and silently eats an edit. Use tombstones (soft-delete rows with their own version) so a delete is a normal versioned change that participates in conflict detection, and GC tombstones only after all replicas have seen them.

"Local DB is the UI's source of truth; writes also append to a durable outbox keyed by a client-generated mutation_id so retries are idempotent. A background sync engine pushes the outbox with the base_version, and the server detects conflicts. For user-owned single records I'd use server-versioned last-write-wins; for genuinely concurrent multi-device edits I'd track version vectors and fall back to a field-level merge, surfacing a manual choice only for irreplaceable content."

Interview angle

INTERVIEW ANGLE

The interviewer often injects a conflict ("what if two devices edit the same note offline?"). Weak candidates hand-wave "the server decides." Strong candidates (1) name the idempotency key that makes retries safe, (2) distinguish detecting a conflict from resolving it, (3) pick a strategy matched to the data shape and justify it, and (4) call out deletes/tombstones and clock-skew unprompted. Say "there is no single right strategy — it depends on whether the data is single-owner, field-partitioned, or truly co-edited," then map each.

Data Sync & Pagination

How the phone pulls "everything that changed since last time" cheaply, and how it lists large collections without loading them into RAM.

The analogy: you don't re-read the entire newspaper every morning — you read today's new pages. Delta sync is the same: the client remembers a bookmark (cursor) and asks the server only for changes since that bookmark.

INSIGHT

Two problems, two mechanisms. Delta sync = "give me everything that changed since my cursor" (a sync_token / high-water mark). Pagination = "give me this collection in bounded chunks" (cursor-based, never offset-based on mobile). Both exist to keep payloads small, memory bounded, and battery cheap.

Delta sync with a sync token

  • High-water mark: the client stores the largest updated_at / server version it has seen. The pull request sends it; the server returns only rows changed after it, plus a new token.
  • Opaque cursor beats raw timestamp: return an opaque sync_token the server controls, so you can change the underlying implementation (add sharding, change the clock) without breaking clients in the wild.
  • Deletes must be explicit: a delta pull can't express "row X is gone" by omission — the client would keep the stale row forever. Return tombstones in the delta.
  • Idempotent + resumable: if the app is killed mid-sync, re-requesting the same token yields the same delta. Only advance the stored token after the batch is durably applied.
// Delta pull response — small, resumable, tombstone-aware
{
  "changed": [
    { "id": "note_42", "version": 7, "title": "Buy oat milk", "deleted": false }
  ],
  "tombstones": [
    { "id": "note_17", "version": 4, "deleted": true }
  ],
  "next_sync_token": "eyJ2IjoxMDI0fQ",   // opaque; advance ONLY after apply
  "has_more": true                        // server chunks large deltas
}

WATCH

Feeds are almost always cursor/keyset-paginated on mobile. Offset pagination on an infinite-scroll feed produces the notorious "I saw that post twice / a post vanished" bug whenever items are inserted at the head between page loads.

Full-sync vs delta-sync — and the reset case

  • Initial / cold start: a bounded full sync (paginated) to hydrate the local DB, then switch to deltas.
  • Token too old / server pruned history: the server can reply "token expired — do a full resync." Clients must handle this gracefully (rehydrate, don't crash).
  • Compaction: the server can't keep every historical change forever; define a retention window for the change log and a full-resync fallback beyond it.
TIP

Sync on the right triggers, not a timer: app foreground, connectivity regained, a push "something changed" ping (silent push), and a user-initiated pull-to-refresh. Polling on a fixed interval is a battery anti-pattern — prefer server-signalled sync.

Interview angle

INTERVIEW ANGLE

Expect "how does the client know what changed?" and "how do you paginate the feed?" Nail three things: an opaque server-controlled cursor (not a raw timestamp), tombstones for deletes (omission can't express deletion in a delta), and advance-token-only-after-apply for crash safety. For lists, say "keyset, not offset" and give the duplicate-post reason. Bonus: mention the "token expired → full resync" fallback — it shows you've operated a real sync system.

Push Notifications (APNs / FCM)

How a server wakes an app or shows a banner without the phone polling — the battery-friendly way to say "something happened."

The analogy: polling is calling the post office every five minutes to ask "any mail?"; push is the postman ringing your bell only when mail arrives. Push exists because polling drains the battery and wastes the radio.

INSIGHT

You never talk to the device's radio directly. You hand a payload to the platform push service — APNs (Apple) or FCM (Firebase/Android) — which owns a single persistent, battery-optimized connection to every device and delivers on your behalf. Your job is: manage device tokens, and send the right payload to the right token.

End-to-end architecture

Notification vs data (silent) push

  • Alert / notification push: OS shows a banner even if the app is dead. Best-effort, may be throttled/coalesced by the OS. Use for user-facing messages.
  • Silent / data push: no banner; wakes the app briefly to sync in the background ("you have new data, come pull it"). Heavily rate-limited by the OS; never rely on 100% delivery.
  • Pattern — push to notify, pull to fetch: keep payloads tiny and send an ID, not the content. The app then does an authenticated delta sync to fetch the real data. This keeps secrets out of the push channel and survives dropped pushes (the next foreground sync catches up).
TRAP

Treating push as a reliable message queue. Push is best-effort: the OS may drop, delay, coalesce, or throttle it; the device may be off for days; tokens rotate. If your feature requires the payload to arrive, you've built a correctness bug. Push is a hint to sync, and the durable state lives in your backend + the client's delta pull. Say this and you avoid the most common push anti-pattern.

WATCH

Token hygiene is a real operational task: tokens change on reinstall/restore/OS-update, and sending to a dead token wastes quota. Store token → userId → platform, handle the "unregistered/invalid token" response by deleting the row, and de-dupe when one user has many devices (fan-out to all their tokens).

"I register the device token on login and store token→user→platform. To notify, I look up the user's tokens and send a small payload — an event id, not the content — through APNs/FCM. The client treats the push as a signal to run a delta sync. Push is best-effort, so correctness never depends on delivery; the foreground sync is the backstop. I prune tokens on 'unregistered' responses."

Interview angle

INTERVIEW ANGLE

The trap the interviewer is fishing for: do you think push is reliable? Volunteer "push is best-effort; I use it as a sync trigger, not a delivery guarantee, and keep the payload to an id so the client pulls the real content over an authenticated channel." Then show operational awareness: token registry, rotation, pruning dead tokens, per-user multi-device fan-out, and OS throttling of silent pushes. That combination reads as someone who has actually run push at scale.

Media & Image Upload / Handling

Photos and video are big, uploads happen on flaky links, and every screen wants a different size. Design the pipeline so a 12 MB photo survives a tunnel and a thumbnail costs kilobytes.

The analogy: shipping a large parcel. You don't hand the whole thing to a courier in one go over a shaky handoff — you get a shipping label first (pre-signed URL), send it in trackable segments (chunked/resumable), and the warehouse makes small catalogue photos (server-side variants) so browsers don't download the full-res original.

INSIGHT

Three moves define good mobile media: (1) upload directly to object storage via a pre-signed URL (don't proxy bytes through your API servers), (2) make uploads resumable and idempotent so a dropped connection resumes instead of restarting, and (3) generate size variants server-side + serve via CDN so the client fetches the smallest image that fits the view.

Upload path

  1. Client asks backend for a pre-signed upload URL (backend does auth, quota, content-type checks, returns a URL + an asset_id).
  2. Client compresses/downscales locally first — never upload a 12 MP original when the product needs 1080px. Saves battery, data, and time.
  3. Client uploads directly to object storage using chunked/resumable upload; on drop, resume from the last acked byte range.
  4. Storage fires an event → a worker validates, strips EXIF/GPS, transcodes, and generates variants (thumb / medium / full, or HLS renditions for video). Close the loop on the retained original: either overwrite it in place with the sanitized copy once processing succeeds, or keep the raw original in a private bucket that is never served to clients — only the stripped variants get a CDN URL — so GPS/location can't leak from the original you held onto.
  5. Client polls or gets a push that the asset is "ready"; the record now references the CDN URL.

Serving & display

  • Multiple variants: thumbnail, list, full. Request by size; never download full-res for a 100px avatar.
  • Progressive / blurhash placeholder: show a tiny blurred preview or dominant color instantly while the real image streams — perceived performance.
  • Client cache with bounds: disk-cache decoded images with an LRU size cap; the phone will evict your app if you hoard.
  • Video = HLS/DASH: adaptive bitrate so a weak connection drops to a lower rendition instead of stalling.
TRAP

Proxying upload bytes through your API tier. Streaming multi-megabyte uploads through your application servers burns their bandwidth, memory, and connection slots, and couples upload throughput to your API's capacity. Upload direct-to-storage with a pre-signed URL; your API only issues the URL and records metadata. Also: strip EXIF/GPS server-side — users don't expect a shared photo to leak their home coordinates.

WATCH

Make uploads survive the app dying mid-transfer: an upload is a durable outbox item too. Use the OS background transfer (URLSession background / WorkManager) with a resumable, idempotent upload keyed by asset_id so a re-attempt continues rather than duplicating.

Interview angle

INTERVIEW ANGLE

"Design photo upload" is a rich prompt because it touches storage, CDN, background work, and privacy at once. Hit: pre-signed direct-to-storage upload, client-side downscale, resumable/idempotent transfer, server-side variant generation + CDN delivery, and EXIF stripping. The senior touch is treating the upload as a durable background task (survives app kill) and picking the smallest variant per view — connecting media back to the battery/resource constraints from tab 1.

API Design for Mobile

Chatty, generic APIs punish a phone with round-trips and over-fetching. Shape the API for the client: fewer round-trips, exactly the fields the screen needs, and a contract old app versions can't break on.

The analogy: a generic backend API is a wholesale warehouse — you'd have to visit five aisles (five calls) and haul home crates you don't need (over-fetching). A Backend-for-Frontend (BFF) is a personal shopper who knows exactly what this screen needs and hands you one ready bag.

INSIGHT

Every network round-trip on a phone can cost hundreds of milliseconds and a radio wake. The goal is one round-trip per screen with exactly the fields that screen renders. Three tools get you there: a BFF that composes/aggregates per screen, batching, and GraphQL (client picks fields) — each with trade-offs.

The options

NOTE — why the BFF fits mobile release latency

Because you can't hot-fix an app in the wild, the BFF becomes your steering wheel: it absorbs backend changes so clients don't have to update, and it can reshape responses, add fields, or fan out to new services without an app release. That directly addresses the release-latency constraint from tab 1.

// Over-fetching / chatty (BAD on mobile): 3 round-trips for one screen
GET /users/42
GET /users/42/orders
GET /users/42/recommendations

// One screen, one round-trip, exactly the fields rendered (GraphQL or BFF)
{
  user(id: "42") {
    name
    orders(last: 3) { id total status }
    recommendations(limit: 5) { id title thumbUrl }
  }
}

Cross-cutting API rules for mobile

  • Additive, backward-compatible changes only: never remove/rename a field an old client reads. Version the endpoint or negotiate capabilities. Old versions live for weeks.
  • Idempotency keys on writes: the client sends a key so a retried request after a dropped response doesn't double-charge / double-post.
  • Pagination + partial responses: bounded pages, sparse fieldsets; let the client ask for less.
  • Compression + efficient encoding: gzip/br; consider protobuf for hot paths. Fewer bytes = less battery.
  • Server-driven UI / config for the un-fixable: feature flags and kill switches so you can disable a broken feature without an app release.
TRAP

GraphQL "solves over-fetching" — and quietly adds N+1 and caching pain. A naive resolver fetches related objects one-by-one (N+1); you need dataloaders/batching. And you lose simple HTTP/CDN caching because every query is a POST to one endpoint — you need persisted queries + application caching. Don't present GraphQL as free; name the mitigations.

TRAP

Per-platform BFFs drift. Separate iOS and Android BFFs sound clean but duplicate logic and diverge over time. Options: one shared BFF with light per-platform shaping, or a single GraphQL layer. Call the trade-off out rather than spawning a BFF per client blindly.

"I'd put a BFF in front so each screen is one round-trip with exactly the fields it renders — that minimizes radio wakes and shields the app from backend changes I can't hot-fix. Writes carry an idempotency key so a retry after a dropped response is safe. All API changes are additive because many app versions are always live. If field needs vary a lot across versions, I'd consider GraphQL, but I'd budget for N+1 (dataloaders) and persisted-query caching."

Interview angle

INTERVIEW ANGLE

The question behind "REST or GraphQL?" is really "do you optimize round-trips and think about version fragmentation?" Frame it as round-trip minimization + backward compatibility, not framework preference. Volunteer idempotency keys (retry safety), additive-only schema evolution (release latency), and the BFF-as-steering-wheel point. If you pick GraphQL, immediately name N+1 and caching costs — that honesty is the senior signal.

Auth & Secure Token Storage

A phone gets lost and stolen. Store credentials in hardware-backed secure storage, keep access tokens short-lived, and rotate refresh tokens so a leaked token has a short blast radius.

The analogy: a long-lived password on the device is like leaving your house key under the mat forever. Instead, keep a well-guarded master key in a safe (the Keychain/Keystore), and use it to mint short-lived day passes (access tokens). If a day pass leaks, it expires in minutes; the safe stays shut.

INSIGHT

Two rules cover most of it: (1) store secrets in the platform's secure storage — iOS Keychain / Android Keystore, whose encryption keys are protected by hardware (Secure Enclave on iOS, TEE/StrongBox on supported Android devices) so secrets are encrypted at rest and never persisted as plaintext — never in plain files, SharedPreferences, or UserDefaults; and (2) use short-lived access tokens + long-lived rotating refresh tokens so a stolen access token dies fast and a stolen refresh token can be detected and revoked.

The token model

TokenLifetimeStored whereJob
Access tokenMinutes (e.g. 5–60 min)Memory; optionally Keychain/KeystoreSent on each API call; expires fast so leaks are low-impact
Refresh tokenDays–weeks, rotatingKeychain / Keystore onlyExchanged for a new access token; rotated on every use

Refresh-token rotation & reuse detection

  • Rotate on every refresh: each refresh returns a new refresh token and invalidates the old one.
  • Reuse = theft signal: if an old (already-rotated) refresh token is presented again, assume it was stolen — revoke the whole token family and force re-login.
  • Bind + scope: tie tokens to a device id; keep scopes minimal. Support server-side revocation (logout-all-devices).
// iOS — store the refresh token in the Keychain, gated by device unlock
let query: [String: Any] = [
    kSecClass as String: kSecClassGenericPassword,
    kSecAttrAccount as String: "refresh_token",
    kSecValueData as String: token.data(using: .utf8)!,
    // only readable when the device is unlocked; never migrates to backups/other devices
    kSecAttrAccessible as String: kSecAttrAccessibleWhenUnlockedThisDeviceOnly
]
SecItemAdd(query as CFDictionary, nil)

// Android — hardware-backed storage via Jetpack Security EncryptedSharedPreferences
val masterKey = MasterKey.Builder(context)
    .setKeyScheme(MasterKey.KeyScheme.AES256_GCM)   // key lives in the Android Keystore
    .build()

val securePrefs = EncryptedSharedPreferences.create(
    context, "auth", masterKey,
    EncryptedSharedPreferences.PrefKeyEncryptionScheme.AES256_SIV,
    EncryptedSharedPreferences.PrefValueEncryptionScheme.AES256_GCM
)
securePrefs.edit().putString("refresh_token", token).apply()
CURRENCY

Jetpack Security Crypto (EncryptedSharedPreferences/MasterKey) was deprecated by Google in 2024, so for new work prefer wrapping encryption yourself with Google Tink (or a hardware-backed Keystore key) and persisting the ciphertext via DataStore — the underlying hardware-backed Android Keystore approach shown here remains the recommended concept.

TRAP

Storing tokens in UserDefaults / SharedPreferences / a plain file. These are not encrypted and are readable on a rooted/jailbroken device or via a backup. Refresh tokens especially must live in Keychain/Keystore. Also: don't log tokens, don't put them in analytics, and use certificate pinning on the auth endpoint if the threat model warrants it.

WATCH

Concurrency bug to preempt: many in-flight requests all 401 at once when the access token expires. Without care they trigger N parallel refreshes and rotate each other into invalidation. Use a single-flight refresh: one refresh runs, the others await its result. This is a very common real-world mobile auth bug — naming it is a strong signal.

"Access tokens are short-lived and sent per request; the refresh token lives only in the Keychain/Keystore, hardware-backed and device-only. Refresh tokens rotate on every use, and reuse of a rotated token triggers family revocation as a theft signal. On expiry I do a single-flight refresh so concurrent 401s don't stampede. Logout and 'sign out all devices' are server-side revocations."

Interview angle

INTERVIEW ANGLE

Say the storage location by name — "Keychain on iOS, Keystore-backed encryption on Android" — and explain why (hardware-backed, encrypted at rest, survives device theft better than plaintext). Then cover the token lifecycle: short access + rotating refresh + reuse detection + server revocation. The two details that separate strong candidates: refresh-token rotation with reuse detection and the single-flight refresh for concurrent 401s. Tie it to the lost-phone threat model.

Observability for Mobile

You can't SSH into a user's phone. Observability is your only window — and it has to be battery-cheap, privacy-safe, and resilient to the same flaky network everything else fights.

The analogy: a backend gives you live logs on tap; a phone is a black box in someone's pocket. Mobile observability is like a flight recorder — the device records events locally and periodically ships a batched black-box report when it has signal.

INSIGHT

Mobile telemetry is offline-first too: buffer events in a local queue, batch-upload on connectivity/foreground, and sample to protect battery and data. The signals that matter most differ from backend: crash-free rate, ANR/hang rate, cold/warm start time, network success by radio type, and app-version adoption — because your fix ships through the store, adoption is a reliability metric.

The four mobile signal groups

1StabilityCRITICAL▶
  • Crash-free sessions/users % — the headline mobile SLI.
  • ANR / hang rate (main-thread blocked).
  • Symbolicated stack traces, grouped by build.
2PerformanceUX▶
  • Cold / warm startup time.
  • Frame drops / jank, scroll smoothness.
  • Screen render + time-to-interactive.
3NetworkFLAKY▶
  • Request success/error rate by radio type (WiFi vs cellular).
  • Latency percentiles from the client's vantage point.
  • Sync success, outbox depth, conflict rate.
4Adoption & resourcesFLEET▶
  • App-version & OS distribution (how fast fixes roll out).
  • Battery / memory footprint, background wake counts.
  • Feature-flag exposure & funnel.
TRAP

Client latency ≠ server latency. Your backend p99 can look great while users suffer — the extra time is DNS, TLS setup, radio wake, and last-mile RTT that server-side metrics never see. Measure from the client — Real User Monitoring (RUM), telemetry gathered from actual devices in the field. Also: measure success by radio type, because "5% error rate" might be "0.5% on WiFi, 20% on cellular" — two very different bugs.

TRAP

Telemetry that ignores its own constraints. Shipping every event immediately drains battery and data and fails offline. Buffer locally, batch, back off, and sample. And scrub PII on-device — don't let a crash breadcrumb ship someone's email or auth token. Privacy and battery are first-class here, not afterthoughts.

"On mobile I can't inspect the device, so I instrument it: crash-free rate and ANRs for stability, startup and jank for performance, network success by radio type from the client's vantage, and version adoption because a fix only helps once it's installed. Telemetry is offline-first — buffered, batched, sampled, PII-scrubbed — so observing the app doesn't violate the same battery and privacy constraints the app respects."

Interview angle

INTERVIEW ANGLE

Reuse the backend observability vocabulary (SLIs, percentiles, error budgets) but prove you know what's mobile-specific: crash-free rate as the headline SLI, client-side RUM (server metrics miss last-mile), success-by-radio-type, and version adoption as a reliability metric because releases are slow. Close with the meta-point: telemetry itself must be offline-first, sampled, and privacy-scrubbed — observing the app can't break the app's own constraints.

Worked Design: Offline-Capable Chat / Notes

Putting every tab together in one end-to-end answer. Prompt: "Design a mobile chat (or offline notes) app that works offline, syncs across devices, and feels instant." Here's how to drive it in ~40 minutes.

Step 1 — Clarify & scope (state assumptions, don't stall)

  • Scale: assume 50M users, 1–3 devices each, 1:1 + small group chats, messages mostly text with occasional images. State it, invite correction.
  • Requirements: send/receive offline, messages appear instantly (optimistic), sync across a user's devices, ordered per conversation, delivery/read receipts, media attachments.
  • Non-goals (bound it): not designing E2E crypto internals, not video calls — say so to control scope.

Step 2 — Client architecture (offline-first)

  • Local SQLite DB is the source of truth: conversations, messages, outbox. UI observes it reactively so sends render instantly.
  • Sending a message = write to local DB (status pending) + append to outbox with a client-generated message_id (idempotency key + client sort key).
  • Sync engine drains the outbox over a persistent channel; on ack, flips status pending → sent.

Step 3 — Transport & delivery

  • Foreground: a persistent connection (WebSocket) for low-latency send/receive.
  • Background / app killed: push notification wakes a sync (push-to-notify, pull-to-fetch — payload carries an id, not the message body).
  • Fan-out: server writes the message to the conversation log and fans out to each recipient device's inbox; each device delta-syncs its inbox.

Step 4 — Ordering & the multi-device sync

  • Server assigns a per-conversation sequence number on receipt — the canonical order. Clients sort by it; the local client sort key is provisional until the server seq arrives.
  • Each device keeps a per-conversation sync_token and delta-pulls new messages + receipts.
  • Idempotency: the client message_id dedupes the "sent but response dropped, so I retried" case — the server recognizes the id and returns the existing message instead of creating a duplicate.

Step 5 — Media, receipts, and conflicts

  • Images: pre-signed direct upload (tab 5); the message references the asset_id and shows a local thumbnail immediately while the upload runs as a background task.
  • Receipts: delivered/read are small delta-synced state changes, coalesced to save battery.
  • Conflicts: chat messages are append-only — naturally conflict-free (each has a unique id; order is server-assigned). Editable content (notes, message edits) uses the tab-2 strategy: LWW on server version for single-owner, merge/version-vectors for true co-editing.

TIP

Notice notes and chat are the same design: local store as truth + outbox + delta sync + conflict policy. Chat adds a persistent channel and server sequence numbers; notes add richer conflict resolution. Saying "these are the same backbone with two knobs turned" reads as pattern mastery, not memorized answers.

Interview angle

INTERVIEW ANGLE

Drive the room: clarify scope, state assumptions, then build outward from the offline-first backbone rather than starting at the server. Explicitly map each decision back to one of the five constraints (the table above is your closing move). The strongest finish is the meta-observation that chat and notes share one backbone — it demonstrates you learned a pattern, not a rehearsed answer. If time allows, volunteer the two hard sub-problems worth raising: message ordering (server sequence) and the send-retry duplicate (idempotency key).

Terminology & Acronyms

Quick reference for the key terms in this chapter.

TermMeaning
Offline-firstArchitecture where the UI reads/writes the local store and background sync reconciles with the server; the network is an optimization, not a dependency.
BFFBackend-for-Frontend — a per-client gateway that composes/aggregates backend calls into one response tailored to each screen.
OutboxDurable, append-only queue of pending local mutations, each with an idempotency key, drained to the server by the sync engine.
Idempotency keyClient-generated id (e.g. a mutation_id) that lets the server dedupe a retried write so it is applied only once.
Sync engineBackground component that pushes the outbox, pulls a delta, resolves conflicts, and merges results into the local DB.
LWWLast-write-wins — conflict rule where the highest version or timestamp wins and the other write is discarded.
Version vectorsPer-replica counters that detect whether two edits are causally ordered or genuinely concurrent.
CRDTConflict-free Replicated Data Type — a data type (counter, set, text) that merges concurrent edits with no conflict.
TombstoneSoft-delete marker with its own version, so a deletion participates in conflict detection and delta sync instead of vanishing by omission.
Delta syncFetching only the records that changed since the client's last cursor, rather than the full dataset.
Sync tokenOpaque, server-controlled cursor (high-water mark) that marks how far a client has synced; advanced only after a batch is applied.
Keyset paginationCursor-based paging anchored to a real row key; stable under inserts, with a seek cost independent of page depth (an O(log n) index lookup) — unlike offset paging, which scans O(offset) rows.
APNs / FCMApple Push Notification service / Firebase Cloud Messaging — platform services that deliver push messages to devices.
Silent pushData-only notification that wakes the app to sync in the background, with no user-visible banner; heavily rate-limited by the OS.
Pre-signed URLTime-limited URL that lets a client upload directly to object storage without proxying the bytes through the API tier.
EXIFExchangeable Image File Format — photo metadata (including GPS coordinates) that should be stripped server-side before serving.
HLS / DASHHTTP Live Streaming / Dynamic Adaptive Streaming over HTTP — adaptive-bitrate protocols that adjust video quality to the connection.
Keychain / KeystoreiOS / Android secure storage for secrets, encrypted at rest with hardware-protected keys.
Secure Enclave / TEEApple's secure coprocessor / Trusted Execution Environment — isolated hardware that protects encryption keys (StrongBox on supported Android).
Access / refresh tokenShort-lived credential sent per API call / long-lived rotating credential (stored in Keychain/Keystore) exchanged for new access tokens.
Single-flight refreshCoalescing concurrent token refreshes so only one runs while the others await its result, avoiding a refresh stampede on expiry.
ANRApplication Not Responding — an Android hang where the main thread is blocked too long; a key stability signal.
RUMReal User Monitoring — performance and reliability telemetry gathered from real devices in the field, not synthetic tests.
