Redis Overview

What Redis is, why it's fast, and how it manages memory — the foundational knowledge for any interview discussion.

What is Redis?

Redis (Remote Dictionary Server) is an open-source, in-memory data structure store used as a database, cache, message broker, and streaming engine. Unlike simple key-value stores, Redis supports rich data structures (strings, hashes, lists, sets, sorted sets, streams, bitmaps, HyperLogLogs).

"Redis is fundamentally an in-memory data structure server with optional persistence. It's not just a cache — it provides atomic operations on complex data structures, which makes it ideal for use cases like rate limiting, leaderboards, and distributed locks."

Why is Redis Fast?

In-Memory Storage

All data resides in RAM. No disk I/O on reads. Memory access is ~100ns vs ~10ms for disk seeks — a 100,000x difference.

Single-Threaded Event Loop

No context switching, no lock contention, no race conditions. One thread processes all commands sequentially using I/O multiplexing (epoll/kqueue).

Efficient Data Structures

Purpose-built C implementations: SDS for strings, skiplists for sorted sets, ziplists for small collections — optimized for the exact access patterns needed.

Non-blocking I/O

Uses multiplexed I/O (epoll on Linux, kqueue on macOS) to handle thousands of connections without threading overhead.

PERFORMANCE NUMBERS

Single Redis instance: ~100K-200K operations/sec. With pipelining: up to 1M ops/sec. Average latency: <1ms. These are on commodity hardware.

Threading Model

INTERVIEW INSIGHT

When asked "isn't single-threaded a bottleneck?" — explain that Redis is I/O bound, not CPU bound. The bottleneck is network bandwidth, not CPU. A single core at 100K ops/sec with sub-ms latency is sufficient for most workloads. For more throughput, shard across multiple instances.

LICLicensing & the Valkey Fork (2024-2025)EcoSystem▶
NOTE

This is a licensing / ecosystem story, not a data-structure one — but it shows up in system-design and "tell me about a tech decision" rounds, and it directly changes what your cloud provider actually ships. Know the timeline and the one-sentence nuanced answer.

The timeline

Origins → March 2024: The Redis core shipped under the BSD 3-Clause license for its entire life — a permissive, OSI-approved open-source license. (Some Redis Ltd. add-on modules, e.g. RediSearch/RedisGraph, had already moved off open-source terms — Commons Clause in 2018, then RSAL in 2019 — but the core stayed BSD.) In March 2024, Redis Ltd. (the company, formerly Redis Labs) relicensed the core, starting with Redis 7.4, to a dual license: RSALv2 (Redis Source Available License v2) OR SSPLv1 (Server Side Public License v1). Both are source-available — you can read and modify the code — but neither is OSI-approved open source. The stated target was hyperscalers reselling Redis-as-a-service without contributing back.

The fork — Valkey: Within days (late March 2024), core contributors plus the Linux Foundation forked the last BSD-licensed commit (Redis 7.2.4) into Valkey, kept under the original BSD 3-Clause license. It was rapidly adopted as the drop-in replacement by AWS (ElastiCache & MemoryDB), Google Cloud Memorystore, Oracle, Ericsson, Snap, and others. Valkey is wire-protocol and API compatible — same RESP protocol, same commands, same client libraries — so migration is typically a config/endpoint change.

May 2025 → Redis 8.0: Redis reversed course and added AGPLv3 as a third license option in Redis 8.0 (GA May 2025), making it a tri-license: RSALv2 / SSPLv1 / AGPLv3. AGPLv3 is OSI-approved open source, so Redis 8.0 can again legitimately be called "open source" under that option. antirez (Salvatore Sanfilippo), who had rejoined Redis, championed the move.

Comparison at a glance

ReleaseLicense(s)GovernanceOSI open source?
Redis (pre-7.4)BSD 3-ClauseRedis Ltd.Yes
Redis 7.4 – 7.xRSALv2 or SSPLv1 (dual, source-available)Redis Ltd.No
Redis 8.0+ (May 2025)RSALv2 or SSPLv1 or AGPLv3 (tri-license)Redis Ltd.Yes, via AGPLv3
Valkey (fork, Mar 2024)BSD 3-ClauseLinux Foundation (community)Yes
TIP

The distinction that matters is "source-available" vs "open source." RSALv2 and SSPLv1 let you see and modify source, but SSPLv1 in particular imposes copyleft-style obligations on anyone offering the software as a service — which is precisely why the OSI does not consider it open source and why cloud providers forked rather than adopt it.

WATCH

If your production cache is on AWS ElastiCache/MemoryDB or GCP Memorystore's newer tiers, you are very likely running Valkey, not Redis Ltd.'s Redis — even if the console still says "Redis OSS compatible." Verify the engine before assuming Redis 8.x-only features are available.

"Is Redis open source?" — the nuanced answer

"It depends on the version. Redis was BSD open source until March 2024, when 7.4 went source-available under RSALv2/SSPLv1 — which OSI does not count as open source and which triggered the community's Valkey fork under the Linux Foundation, still BSD. Then Redis 8.0 in May 2025 re-added a genuinely open-source option, AGPLv3, making it a tri-license. So today: Redis 8+ can be open source under AGPLv3, and Valkey is the fully-BSD, cloud-provider-backed drop-in fork."
INSIGHT

The takeaway for design discussions: Redis-the-protocol won so decisively that its own relicensing couldn't dislodge it — the ecosystem simply forked and kept the API. When you say "Redis" in an architecture, you're really committing to the RESP protocol and command surface, which both Redis 8 and Valkey honor.

Data Structures

The most interview-critical section. Know the internal implementation, time complexity, and when to use each structure.

1. String (SDS) GET / SET / INCR CRITICAL ▶

Internal Implementation: Simple Dynamic String (SDS)

Not a C string! SDS stores: len (used bytes), alloc (allocated bytes), flags (type), buf[] (data). Benefits over C strings:

  • O(1) length retrieval (no strlen traversal)
  • Binary safe (can store \0 bytes)
  • Pre-allocation prevents frequent realloc (doubles up to 1MB, then +1MB)
  • Lazy free — doesn't immediately release on shrink

Encoding Variants

EncodingConditionMemory
intValue is integer in long range8 bytes (stored as long)
embstrString <= 44 bytesSingle allocation (robj + SDS together)
rawString > 44 bytesTwo allocations (robj + SDS separate)

Key Operations & Complexity

CommandComplexityNote
GET / SETO(1)Basic read/write
INCR / INCRBYO(1)Atomic increment
SETNXO(1)Set if not exists (for locks)
MGET / MSETO(N)Batch operations, reduces RTTs
SETEXO(1)Set with expiry (atomic)

When to Use

  • Caching: Store serialized objects, HTML fragments
  • Counters: INCR is atomic — page views, API quotas
  • Distributed locks: SET key value NX EX 30
  • Rate limiting: INCR + EXPIRE for fixed window
"I'd use a Redis String with INCR for the counter because it's atomic without requiring locks — a single Redis command is always atomic since the server is single-threaded."
// Cache pattern
SET user:1001 "{\"name\":\"Alice\",\"age\":30}" EX 3600

// Atomic counter
INCR page:views:homepage
INCRBY inventory:item:42 -1

// Distributed lock (Redis 2.6.12+)
SET lock:order:123 "owner-uuid" NX EX 30
2. Hash HGET / HSET / HGETALL CRITICAL ▶

Internal Implementation

Two encodings based on size:

EncodingConditionStructure
listpack (was ziplist)<= 128 fields AND all values <= 64 bytesContiguous memory block, linear scan
hashtableExceeds above thresholdsdict with chaining, incremental rehashing

Listpack is extremely memory-efficient (no pointers, no per-entry overhead) but O(N) access. For small hashes (<128 fields), this is faster than hashtable due to cache locality.

Incremental Rehashing

When the hashtable grows, Redis doesn't block. It maintains two hash tables simultaneously and migrates entries in small batches during each command execution until complete.

Key Operations & Complexity

CommandComplexityNote
HGET / HSETO(1)Single field access
HMGET / HMSETO(N)Multiple fields
HGETALLO(N)All fields — careful with large hashes!
HINCRBYO(1)Atomic increment on field
HSCANO(1)/callIterate without blocking

When to Use

  • Object storage: User profiles (partial reads/updates vs GET/SET full JSON)
  • Memory optimization: Store many small objects in one hash (Instagram technique: 1000 objects per hash key saves ~5x, roughly 75-80% memory)
  • Configuration: Store app config as hash fields
"I'd model the user profile as a Redis Hash rather than a serialized String. This way we can read/update individual fields without deserializing the entire object — HGET user:1001 email is O(1) and saves bandwidth."
// Object storage
HSET user:1001 name "Alice" email "alice@example.com" age 30
HGET user:1001 email
HINCRBY user:1001 login_count 1

// Memory optimization pattern (Instagram)
// Instead of SET user:1001 "..." (overhead per key)
// Pack 1000 users per bucket:
HSET users:1 1001 "{...}" 1002 "{...}" ...
// bucket = user_id / 1000, field = user_id
PITFALL

Never use HGETALL on a hash with thousands of fields in production — it blocks the event loop. Use HSCAN for iteration. Configure hash-max-listpack-entries and hash-max-listpack-value based on your data.

3. List (Quicklist) LPUSH / RPOP / LRANGE HIGH ▶

Internal Implementation: Quicklist

A doubly-linked list of listpacks (previously ziplists). Combines benefits of both:

  • Linked list: O(1) push/pop at head/tail
  • Listpack nodes: cache-friendly, memory-efficient for each segment
  • Configurable node size: list-max-listpack-size (default -2 = 8KB per node)
  • Compression: middle nodes can be LZF compressed (list-compress-depth)

Key Operations & Complexity

CommandComplexityNote
LPUSH / RPUSHO(1)Add to head/tail
LPOP / RPOPO(1)Remove from head/tail
LINDEXO(N)Random access — avoid!
LRANGEO(S+N)S=offset, N=count. OK for small ranges.
LLENO(1)Stored in metadata
BRPOPO(1)Blocking pop — for queues

When to Use

  • Message queue: LPUSH + BRPOP (simple task queue)
  • Recent items: LPUSH + LTRIM (keep last N items, e.g., recent activity feed)
  • Timeline: Twitter-style fan-out-on-write
// Task queue pattern
LPUSH queue:emails "{\"to\":\"user@example.com\",\"subject\":\"...\"}"
BRPOP queue:emails 30  // Blocking pop with 30s timeout

// Recent items (keep last 100)
LPUSH user:1001:feed "posted photo"
LTRIM user:1001:feed 0 99
LRANGE user:1001:feed 0 9  // Get latest 10
PITFALL

For reliable queues, List alone is not enough (messages lost on consumer crash). Use RPOPLPUSH/LMOVE to a processing list, or better — use Redis Streams for production message queues.

5. Sorted Set (ZSet) ZADD / ZRANGE / ZRANGEBYSCORE CRITICAL ▶

Internal Implementation: Skip List + Hash Table

Sorted Set uses TWO data structures simultaneously:

  • Skip list: Maintains elements sorted by score — O(log N) insert, delete, range queries
  • Hash table: Maps member -> score — O(1) score lookup by member

For small sorted sets (<= 128 elements, values <= 64 bytes), uses listpack encoding instead.

Key Operations & Complexity

CommandComplexityNote
ZADDO(log N)Insert/update with score
ZREMO(log N)Remove member
ZSCOREO(1)Get score (via hashtable)
ZRANKO(log N)Get rank by score
ZRANGEO(log N + M)Range by rank, M = returned count
ZRANGEBYSCOREO(log N + M)Range by score
ZREMRANGEBYSCOREO(log N + M)Remove by score range

When to Use

  • Leaderboard: Score = points, member = player_id
  • Rate limiter (sliding window): Score = timestamp, member = request_id
  • Priority queue: Score = priority, member = task_id
  • Time-series index: Score = timestamp, member = event_id
  • Autocomplete: Score = frequency, member = term
"For the leaderboard, I'd use a Redis Sorted Set. ZADD gives us O(log N) insertions, ZREVRANGE gives top-K in O(log N + K), and ZRANK gives any player's position in O(log N). It's the perfect data structure for ordered data with fast rank queries."
// Leaderboard
ZADD leaderboard 1500 "player:alice" 2300 "player:bob" 1800 "player:carol"
ZREVRANGE leaderboard 0 9 WITHSCORES  // Top 10
ZRANK leaderboard "player:alice"       // Alice's rank

// Sliding window rate limiter
// Score = timestamp, Member = unique request ID
ZADD rate:user:1001 1706000001.123 "req-uuid-1"
ZADD rate:user:1001 1706000001.456 "req-uuid-2"
ZREMRANGEBYSCORE rate:user:1001 0 (now - window_size)
ZCARD rate:user:1001  // Current count in window

// Priority queue
ZADD tasks:priority 1 "critical-task" 5 "normal-task" 10 "low-task"
ZPOPMIN tasks:priority  // Get highest priority (lowest score)
WHY SKIP LIST OVER BALANCED TREE?

Redis author Salvatore Sanfilippo (antirez) chose skip lists because: (1) simpler implementation, (2) easy range operations (just follow forward pointers), (3) same O(log N) expected performance, (4) memory-efficient and tunable (the level probability is configurable; Redis uses p=1/4). Concurrency was not among the reasons — Redis runs commands single-threaded.

6. Stream XADD / XREAD / XREADGROUP HIGH ▶

Internal Implementation

Streams are an append-only data structure built on a radix tree of macro-nodes. Each node contains multiple entries stored in a listpack, keyed by entry ID (timestamp-sequence).

  • Entry IDs: <ms-timestamp>-<sequence> (auto-generated or explicit)
  • Consumer groups: independent cursors on the same stream, with acknowledgment
  • Pending Entries List (PEL): tracks delivered-but-unacknowledged messages

Key Operations

CommandComplexityNote
XADDO(1)Append entry (amortized)
XREADO(N)Read entries (can block)
XREADGROUPO(N)Consumer group read
XACKO(1)Acknowledge processing
XLENO(1)Stream length
XTRIMO(N)Cap stream size

When to Use

  • Event sourcing: Immutable event log with consumer groups
  • Message queue (reliable): Unlike List, supports ACK and re-delivery
  • Activity feed: Time-ordered events with fan-out
  • Audit log: Append-only with automatic trimming
// Create stream entry
XADD orders * user_id 1001 product "widget" qty 3

// Consumer group
XGROUP CREATE orders processing $ MKSTREAM
XREADGROUP GROUP processing worker-1 COUNT 10 BLOCK 5000 STREAMS orders >
XACK orders processing "1706000001234-0"

// Trim to max 10000 entries
XTRIM orders MAXLEN ~ 10000  // ~ means approximate (faster)
STREAMS VS PUB/SUB

Pub/Sub is fire-and-forget (no persistence, offline subscribers miss messages). Streams persist data, support consumer groups with ACK, and allow replaying history. Use Streams for reliable message processing; Pub/Sub for real-time broadcasting where message loss is acceptable.

7. Bitmap SETBIT / GETBIT / BITCOUNT MEDIUM ▶

Internal Implementation

Bitmaps are not a separate data type — they are Strings with bit-level operations. A String can hold up to 512MB = 2^32 bits (4 billion bits).

Key Operations

CommandComplexityNote
SETBITO(1)Set/clear a specific bit
GETBITO(1)Get value of a bit
BITCOUNTO(N)Count set bits (uses popcount CPU instruction)
BITOPO(N)AND/OR/XOR/NOT between bitmaps
BITPOSO(N)Find first set/unset bit

When to Use

  • Daily active users: One bit per user_id. SETBIT dau:2024-01-15 user_id 1
  • Feature flags: Which users have feature X enabled
  • Bloom filter (manual): Multiple hash functions, set bits
  • Online status: SETBIT online user_id 1/0
// Daily Active Users tracking
SETBIT dau:2024-01-15 1001 1  // user 1001 visited
SETBIT dau:2024-01-15 1002 1  // user 1002 visited
BITCOUNT dau:2024-01-15       // -> 2 active users

// Weekly active users (OR of 7 daily bitmaps)
BITOP OR wau:2024-w03 dau:2024-01-15 dau:2024-01-16 ... dau:2024-01-21
BITCOUNT wau:2024-w03

// Memory: 100M users = 12.5 MB per day bitmap
MEMORY EFFICIENCY

For 100 million users: Bitmap = 12.5 MB/day. A Set of the same 100M user IDs = several GB/day (~60-90 bytes overhead per member). Bitmap wins dramatically for dense populations. But if only 1% of users are active, the bitmap wastes space — use a Set or HyperLogLog instead.

8. HyperLogLog PFADD / PFCOUNT / PFMERGE MEDIUM ▶

Internal Implementation

Probabilistic data structure for cardinality estimation. Uses 16384 registers (6 bits each). Key properties:

  • Fixed memory: 12 KB maximum regardless of cardinality
  • Standard error: 0.81% (for 16384 registers)
  • Can count up to 2^64 unique elements
  • Mergeable: PFMERGE combines multiple HLLs
  • Two encodings: sparse (memory-efficient for small counts) and dense (12KB fixed)

Key Operations

CommandComplexityNote
PFADDO(1)Add element
PFCOUNTO(1)Get estimated cardinality
PFMERGEO(N)Merge multiple HLLs

When to Use

  • Unique visitor count: When 0.81% error is acceptable
  • Unique search queries per day: Massive cardinality, low memory
  • Unique IP addresses: Network monitoring
  • NOT for: Cases requiring exact count or membership testing
"For counting unique visitors where we don't need exact precision, I'd use HyperLogLog. It gives us constant 12KB memory per counter regardless of cardinality, with only 0.81% standard error. If we need exact counts, we'd use a Set, but that could be GBs of memory for high-cardinality data."
// Unique visitors (12 KB vs potentially GBs with Set)
PFADD unique:visitors:2024-01-15 "user:1001" "user:1002" "user:1003"
PFCOUNT unique:visitors:2024-01-15  // ~3 (approximate)

// Monthly unique visitors (merge daily HLLs)
PFMERGE unique:visitors:2024-01 unique:visitors:2024-01-01 ... unique:visitors:2024-01-31
PFCOUNT unique:visitors:2024-01

Common Use Cases

Problem-to-solution patterns with data structure choices, code patterns, and gotchas. These are the patterns that come up in system design interviews.

1. Cache (Cache-Aside, Write-Through, Write-Behind) Caching Patterns CRITICAL ▶

Cache-Aside (Lazy Loading)

Application manages cache. Read: check cache first, on miss read from DB and populate cache. Write: update DB, then invalidate/update cache.

// Cache-Aside (most common pattern)
def get_user(user_id):
    # 1. Check cache
    cached = redis.get(f"user:{user_id}")
    if cached:
        return deserialize(cached)

    # 2. Cache miss - read from DB
    user = db.query("SELECT * FROM users WHERE id = ?", user_id)

    # 3. Populate cache with TTL
    redis.setex(f"user:{user_id}", 3600, serialize(user))
    return user

def update_user(user_id, data):
    db.update("UPDATE users SET ... WHERE id = ?", user_id)
    redis.delete(f"user:{user_id}")  # Invalidate (safer than update)

Write-Through

Every write goes to both cache and DB synchronously. Ensures cache is always fresh but adds write latency.

Write-Behind (Write-Back)

Write to cache immediately, asynchronously flush to DB in batches. Lower write latency but risk of data loss if Redis crashes before flush.

CACHE-ASIDE PROS

Only requested data is cached (no wasted memory). Works even if cache goes down (graceful degradation). Simple to implement.

CACHE-ASIDE CONS

Cache miss = extra latency (DB read + cache write). Stale data possible between DB update and cache invalidation. Thundering herd on popular key expiry.

PITFALLS

Thundering herd: Popular key expires, 1000 requests simultaneously hit DB. Solution: use locking (SETNX) so only one request rebuilds cache. Inconsistency: Delete cache after DB write (not before). Use SET ... EX with TTL as a safety net. Cache penetration: Queries for non-existent data always miss. Solution: cache null results with short TTL, or use Bloom filter.

2. Session Store Hash + TTL MEDIUM ▶

Problem

HTTP is stateless. Need server-side session storage that works across multiple app servers (horizontal scaling). Traditional: sticky sessions (bad for HA) or DB-backed sessions (slow).

Solution

// Store session as Hash (partial read/write of fields)
HSET session:abc123 user_id 1001 role "admin" cart_size 3 last_active 1706000000
EXPIRE session:abc123 1800  // 30 min TTL

// Read specific fields (efficient)
HMGET session:abc123 user_id role

// Update on activity (reset TTL)
HSET session:abc123 last_active 1706001000
EXPIRE session:abc123 1800

// OR use String with serialized JSON for simpler access
SET session:abc123 "{\"user_id\":1001,\"role\":\"admin\"}" EX 1800

Design Decisions

PITFALL

Before Redis 7.4, EXPIRE could only be set on the whole key, not individual hash fields — so per-field TTL required separate keys or application-level expiry. As of Redis 7.4 you can set per-field TTL natively with HEXPIRE/HPEXPIRE (and inspect/clear it with HTTL/HPERSIST); on older versions the whole-key limitation still applies. Also: session fixation attacks — always regenerate session ID on login.

3. Rate Limiter Fixed Window + Sliding Window CRITICAL ▶

Fixed Window (Simple)

// Fixed window: 100 requests per minute
key = f"rate:{user_id}:{current_minute}"
count = INCR key
if count == 1:
    EXPIRE key 60  // First request in window
if count > 100:
    return 429  // Too Many Requests

Problem: Boundary issue. User sends 100 requests at 12:00:59 and 100 more at 12:01:00 = 200 requests in 2 seconds.

Sliding Window with Sorted Set (Production-grade)

// Sliding window: 100 requests per 60 seconds
def is_allowed(user_id, limit=100, window=60):
    key = f"rate:{user_id}"
    now = time.time()
    pipe = redis.pipeline()   # redis-py pipelines default to transaction=True (MULTI/EXEC), so the ops below run atomically; for conditional logic use a Lua/EVAL script instead

    # Remove entries outside window
    pipe.zremrangebyscore(key, 0, now - window)
    # Count remaining entries
    pipe.zcard(key)
    # Add current request
    pipe.zadd(key, {str(uuid4()): now})
    # Set expiry on key as safety net
    pipe.expire(key, window)

    results = pipe.execute()
    current_count = results[1]

    return current_count < limit
"For a sliding window rate limiter, I'd use a Redis Sorted Set where the score is the request timestamp. On each request: ZREMRANGEBYSCORE to remove expired entries, ZCARD to count current requests in the window, and ZADD for the new request — wrapped in a Lua script (or MULTI/EXEC) so the count-check and insert run atomically, with no other client interleaving between them."
PITFALLS

Memory: Sorted Set stores every request ID — for high-volume APIs, this uses significant memory. Consider fixed-window with INCR for most cases, or the sliding window log only for low-volume endpoints that need precision. Race condition: Use MULTI/EXEC or Lua script for atomicity between ZCARD check and ZADD.

4. Distributed Lock SETNX + Redlock CRITICAL ▶

Simple Lock (Single Instance)

// Acquire lock (atomic SET NX EX)
SET lock:order:123 "owner-uuid-abc" NX EX 30
// NX = only if not exists, EX = expire in 30s

// Release lock (must verify ownership!)
// Use Lua script for atomic check-and-delete:
EVAL "if redis.call('get',KEYS[1]) == ARGV[1] then
        return redis.call('del',KEYS[1])
      else return 0 end"
      1 lock:order:123 "owner-uuid-abc"

Why Owner UUID Matters

Without ownership check: Client A acquires lock, takes too long (lock expires), Client B acquires lock, Client A finishes and deletes B's lock. With UUID: Client A can only delete its own lock.

Redlock Algorithm (Multi-Instance)

For environments where a single Redis instance is not acceptable for safety:

  1. Get current time in milliseconds
  2. Try to acquire lock on N (typically 5) independent Redis instances with same key/value/TTL
  3. Lock is acquired if: majority (N/2 + 1) instances grant lock AND total elapsed time < TTL
  4. If lock fails, unlock all instances
  5. Effective lock validity = TTL - elapsed_time_to_acquire
CRITICAL PITFALL: MARTIN KLEPPMANN'S CRITIQUE

Redlock assumes bounded clock drift and bounded process pauses. In practice: (1) GC pauses can exceed lock TTL, (2) clock jumps can invalidate timing assumptions. If you need strong mutual exclusion, use fencing tokens (monotonic counter) alongside the lock, or use a consensus system like ZooKeeper/etcd. Redis locks are best for efficiency (prevent duplicate work) not correctness (prevent data corruption).

"I'd use Redis SET with NX and EX flags for a distributed lock. The key consideration is the lock must have an owner identifier and TTL to prevent deadlocks. For release, a Lua script ensures atomic check-and-delete. However, I want to note this only provides efficiency guarantees, not correctness — for strict correctness under network partitions, we'd need fencing tokens or a CP system like ZooKeeper."

TXPipelining, Transactions, Lua & FunctionsEXECUTION▶
"Pipelining bundles the network, MULTI bundles the intent, Lua bundles the logic — only the last two bundle atomicity, and even MULTI won't roll back a mistake."

Four mechanisms that all reduce round-trips or group commands, but they differ sharply on atomicity and where the logic runs. A common probe is the gap between "batched" and "atomic".

1. Pipelining — batch the wire, not the atom

The client writes many commands to the socket without waiting for each reply, then reads all replies at the end. This collapses N network round-trips (RTT) into essentially 1, which is the dominant win for chatty workloads on high-latency links.

INSIGHT: Pipelining is purely a client-side / transport optimization. The server still executes each command independently, and because Redis is single-threaded it processes your pipelined commands in order — but there is no isolation guarantee: nothing prevents other clients' commands from being served around the batch (a pipeline drained in a single socket read runs consecutively, but once it spans multiple reads other clients can be interleaved). No atomicity.

NOTE: Keep pipeline batches bounded (e.g. a few thousand commands). A giant pipeline forces the server to buffer all replies in the output buffer, inflating memory and latency for other clients.

2. MULTI / EXEC / WATCH — transactions with optimistic locking

Wrap commands between MULTI and EXEC. Commands are queued (each returns +QUEUED) and then executed as a single isolated, serialized unit at EXEC — no other client's commands run in the middle. DISCARD flushes the queue and cancels the transaction before EXEC.

WATCH key [key ...] adds optimistic locking (compare-and-swap): if any watched key is modified by anyone between WATCH and EXEC, the whole transaction aborts and EXEC returns a nil reply — the client must retry. UNWATCH clears all watches. This is the canonical pattern for check-then-set without holding a lock.

TRAP: MULTI/EXEC has NO rollback. Redis distinguishes two error classes:
• Queuing-time errors (e.g. a syntactically wrong command or unknown command name): detected during queuing, and since Redis 2.6.5 the server flags the transaction so that EXEC refuses to run and discards the whole batch.
• Runtime errors (e.g. running INCR against a key holding a list — a wrong-type error only knowable at execution): the offending command fails, but every other command in the transaction still executes and commits. There is no undo. If you sent SET a 1, LPUSH a x, SET b 2, then a=1 and b=2 both persist and only the LPUSH errors. This is deliberate: Redis has no rollback machinery because such errors are programming bugs, and skipping rollback keeps it fast and simple.

3. Lua scripting — EVAL / EVALSHA (server-side atomic)

EVAL script numkeys key... arg... ships a Lua script to the server and runs it atomically: because Redis is single-threaded, the script runs to completion with no other command interleaved (same isolation as EXEC, but you get real control flow, conditionals, and computation server-side — eliminating client round-trips inside the logic).

SCRIPT LOAD caches a script and returns its SHA1; EVALSHA <sha1> ... then invokes it by digest to avoid re-sending the body. If the server doesn't have it cached you get a NOSCRIPT error and fall back to EVAL.

TIP: Pass keys via KEYS[] (not hardcoded) so the script is cluster-safe — Redis can verify every key maps to the same hash slot and route correctly — and pass other data via ARGV[]. (You no longer need to obsess over determinism: since Redis 5.0, scripts replicate their write effects rather than the script body, so the old "no unguarded RANDOMKEY/TIME/SRANDMEMBER" rule is largely relaxed.) Keep scripts short — a long-running script blocks the entire server; only SCRIPT KILL (if no write has happened yet) or SHUTDOWN NOSAVE can stop it.

4. Redis Functions — FUNCTION LOAD (the persistent successor)

Introduced in Redis 7.0 (GA April 2022), Functions are the modern, first-class replacement for the "load a Lua script on every deploy" pattern. You FUNCTION LOAD a library of named functions (registered via redis.register_function in the default Lua engine), then invoke them with FCALL. Use FCALL_RO to invoke in read-only mode: it refuses to run any function not flagged no-writes (and by extension is the variant usable on read-only replicas/connections) — the same relationship as EVAL_RO/EVALSHA_RO vs EVAL.

INSIGHT: The key advantage over EVAL is persistence & replication. Loaded functions are part of the dataset — they survive restarts (saved in RDB), are written to the AOF, and propagate to replicas. With plain scripts the SHA1 cache is ephemeral and must be reloaded after a restart or failover. Functions also support declarative flags (e.g. no-writes); a library is named and replaced in place via FUNCTION LOAD REPLACE, and managed with FUNCTION DUMP/RESTORE/DELETE/LIST.

Persistence

How Redis durably stores data despite being in-memory. Critical for interview discussions about data loss trade-offs.

RDB Snapshots

Point-in-time snapshot of the entire dataset saved as a compact binary file (dump.rdb).

How It Works

1. Redis forks a child process
2. Child writes dataset to temp RDB file
3. Parent continues serving (COW pages on write)
4. When complete, child atomically replaces old RDB
5. Triggered by config rules (e.g., "save 900 1" = save if 1+ change in 900s)

Trade-offs

Pros: Compact file, fast restarts, minimal performance impact (fork COW)

Cons: Data loss between snapshots (minutes of data), fork can be slow with large datasets (COW memory spike)

AOF (Append-Only File)

Logs every write operation. On restart, replays the log to reconstruct state.

How It Works

1. Every write command appended to AOF buffer
2. Buffer fsynced to disk per policy:
  - always: fsync every command (safest, slowest)
  - everysec: fsync every second (good balance)
  - no: OS decides (fastest, most risk)
3. AOF rewrite: compacts log by generating minimal command set

Trade-offs

Pros: Minimal data loss (1 sec with everysec), human-readable, append-only is crash-safe

Cons: Larger file than RDB, slower restarts (replay commands), AOF rewrite causes I/O spike

RDB + AOF Hybrid (Redis 4.0+)

Best of both worlds: AOF rewrite generates an RDB-format prefix + AOF-format suffix. Fast restarts (load RDB part) with minimal data loss (replay AOF tail).

When to Use Which

ScenarioRecommendationRationale
Pure cache (data can be regenerated)No persistence (or RDB for faster restarts)No durability needed, maximize performance
Session storeRDB + AOF hybridSessions are important but recoverable; fast restart preferred
Primary data storeAOF (everysec) + periodic RDB backupsMinimize data loss, RDB for offsite backup
High-write workloadAOF everysec (not always)always fsync destroys write throughput
Disaster recoveryRDB shipped to remote storageCompact, portable, fast to load anywhere
"For this service, I'd enable the hybrid AOF persistence mode — it gives us fast restart times since the bulk of data loads from the RDB prefix, while the AOF tail ensures we lose at most one second of writes. We'd also take periodic RDB snapshots for disaster recovery and ship them to object storage."
FORK MEMORY OVERHEAD

When Redis forks for RDB/AOF-rewrite, Linux uses copy-on-write (COW). If the parent writes heavily during the fork, pages get copied — worst case 2x memory usage. Solutions: (1) set vm.overcommit_memory=1, (2) schedule saves during low-write periods, (3) provision 2x memory headroom.

Cluster & High Availability

Sentinel for HA, Cluster for sharding. Understanding these architectures is critical for scaling discussions in interviews.

Redis Sentinel (HA without Sharding)

Sentinel provides high availability through monitoring, notification, automatic failover, and configuration provider. It does NOT shard data — all data lives on one primary.

Sentinel Failover Process

  1. Sentinels detect primary is unreachable (SDOWN -> ODOWN after quorum agrees)
  2. Sentinel leader is elected (Raft-like)
  3. Leader selects best replica (priority, replication offset, runID)
  4. Promotes replica to primary (REPLICAOF NO ONE; SLAVEOF is the deprecated alias)
  5. Reconfigures other replicas to replicate from new primary
  6. Clients are notified via Sentinel to connect to new primary

Redis Cluster (Sharding)

Distributed implementation with automatic sharding across multiple nodes. Data is partitioned using 16384 hash slots.

Consistency Model

CRITICAL: ASYNC REPLICATION

Redis Cluster uses asynchronous replication. After a write is acknowledged to the client, it's replicated to replicas asynchronously. On primary failure, the promoted replica may be missing the last few writes. Redis does NOT guarantee strong consistency. It provides best-effort consistency with a "last failover wins" approach.

Data Loss Scenarios

  1. Primary failure before replication: Client gets OK, primary dies, replica promoted without that write = data lost
  2. Network partition (split brain): Primary isolated from majority. Minority partition still accepts writes for cluster-node-timeout period. When partition heals, those writes are discarded.
  3. Mitigation: min-replicas-to-write N — primary refuses writes if fewer than N replicas are connected. This shrinks the data-loss window but does NOT make replication synchronous: the primary still acks the client without waiting for a replica, so an acked write can still be lost on failover (unlike Kafka's acks=all, which withholds the ack until the in-sync replicas have it — use the WAIT command for closer-to-synchronous behavior)

Split-Brain Scenario

"Redis provides eventual consistency with asynchronous replication. In a failover, we could lose the last few milliseconds of acknowledged writes. If this is unacceptable, we'd need the WAIT command for stronger, closer-to-synchronous durability (at the cost of latency — replication is still async, WAIT just blocks until N replicas ack), or choose a CP system. For most use cases like caching and rate limiting, this trade-off is acceptable."

Common Interview Questions

Q: How would you design a rate limiter using Redis? COMMON ▶

Answer framework:

  1. Clarify requirements: fixed window vs sliding window, precision needed, scale
  2. For simple fixed window: INCR + EXPIRE (O(1), minimal memory)
  3. For sliding window: Sorted Set with timestamp scores (precise but more memory)
  4. For distributed: a Lua script (or a MULTI/EXEC transaction) for atomicity across multi-step operations — a plain pipeline only batches round-trips and is NOT atomic
  5. Discuss failure modes: what if Redis is down? (fail open vs fail closed)
"I'd implement a sliding window rate limiter using a Redis Sorted Set. Each request adds an entry with the current timestamp as the score. Before allowing a request, I remove entries outside the window, count remaining entries, and compare against the limit. I'd wrap this in a Lua script for atomicity. If Redis is unavailable, I'd fail open to avoid blocking all traffic, with a local in-memory fallback."
Q: How does Redis handle the thundering herd problem? COMMON ▶

Problem: Popular cache key expires, hundreds of concurrent requests all miss cache and hit the database simultaneously.

Solutions:

  1. Locking: Use SETNX to allow only one request to rebuild cache. Others wait or get stale data.
  2. Stale-while-revalidate: Cache stores expiry in value. Return stale data while one process refreshes.
  3. Probabilistic early expiration: Each request has a small chance of refreshing before TTL (XFetch algorithm).
  4. Never expire: Use background job to refresh popular keys, never set TTL on hot keys.

Q: What happens when Redis runs out of memory? COMMON ▶

Answer: Behavior depends on the configured maxmemory-policy:

  • noeviction: Returns an out-of-memory (OOM) error on writes (reads still work)
  • allkeys-lru: Evicts least recently used keys (best for general caches)
  • allkeys-lfu: Evicts least frequently used (better for skewed access patterns)
  • volatile-*: Only evicts keys with TTL set (allows persistent + cache data to coexist)

Key points: Redis LRU is approximated (samples N keys, not true LRU). In production, always set maxmemory to prevent OOM killer from terminating the process. Monitor evicted_keys metric — high eviction rate means cache is too small.

Q: Can Redis lose data? When? COMMON ▶

Yes. Data loss scenarios:

  1. No persistence configured: All data lost on restart
  2. RDB only: Data since last snapshot lost on crash (could be minutes)
  3. AOF everysec: Up to 1 second of data lost on crash
  4. Async replication failover: Writes acknowledged but not replicated are lost when primary fails
  5. Split-brain: Minority partition accepts writes that are discarded on heal
  6. Eviction: Keys evicted under memory pressure are gone

Mitigation: AOF always (slowest, safest), WAIT command for closer-to-synchronous durability (blocks until N replicas ack; replication stays async), min-replicas-to-write, proper monitoring.

Trade-offs to Discuss

Memory vs Speed

Redis is fast BECAUSE it's in-memory. But RAM is expensive. Discuss: hot/warm/cold data tiers, TTL strategies, compression (listpack encodings), memory-optimized instances.

Consistency vs Availability

Redis is AP (available + partition-tolerant). Async replication means eventual consistency. For CP needs, consider: WAIT command, min-replicas-to-write, or switching to etcd/ZooKeeper.

Simplicity vs Features

Single-threaded simplicity enables atomicity without locks. But limits CPU-bound operations. For CPU-intensive (Lua scripts, large SORT), consider offloading to application layer.

Persistence vs Performance

No persistence = fastest. AOF always = safest but 10-30% write overhead. Fork for RDB = memory spike. Hybrid = good balance. Choose based on data criticality.

OPSOperational Pitfalls: SCAN vs KEYS, Expiration, Big/Hot KeysPROD▶
"Redis executes commands on a single thread, so any O(N) command doesn't just slow itself down — it stalls every other client for the duration. Most production incidents are a KEYS * or a big-key operation, not a hardware limit."

1. Never KEYS in production → use the SCAN family

KEYS pattern walks the entire keyspace in a single blocking call: O(N) over all keys. Because command execution is single-threaded, a multi-million-key KEYS * monopolizes the main thread for hundreds of ms to seconds, during which all reads/writes queue behind it.

TRAP

TRAP — KEYS blocks the whole server. It is not just slow for the caller. While KEYS * runs, the single command-execution thread is busy, so latency-sensitive traffic times out, health checks fail, and the node can look "down" to clients and to Sentinel/Cluster failure detectors — potentially triggering a spurious failover. The same danger applies to SMEMBERS, HGETALL, LRANGE 0 -1, and SORT on large keys.

SCAN cursor [MATCH pat] [COUNT n] [TYPE t] is the safe replacement: a cursor-based, incremental iterator. Each call is roughly O(1) amortized and returns a small batch plus the next cursor; iteration ends when the cursor returns to 0. Collection variants iterate the fields/members of one key: HSCAN (hash), SSCAN (set), ZSCAN (sorted set).

PropertyWhat to know
COUNTA hint for work per call, default 10. Not a page-size guarantee — a call can return 0 elements yet a non-zero cursor (keep going until cursor is 0).
GuaranteeEvery element present for the full duration of the scan is returned at least once; elements may be returned more than once (caller must dedupe/be idempotent).
MATCHFiltering happens after retrieval from the table, so a highly selective MATCH can still cost many empty-looking iterations.
HSCAN NOVALUESSince Redis 7.4, HSCAN key cursor NOVALUES returns fields only — cheaper when you don't need values.
TIP

TIP. Drive iteration with redis-cli --scan --pattern 'user:*' (wraps SCAN for you), and bound throughput with --count. For collections that have grown huge, HSCAN/SSCAN/ZSCAN let you delete members in batches instead of one blocking DEL — or use UNLINK (Redis 4.0+) to free the key on a background thread.

2. Key expiration: passive vs active

A key with a TTL is not deleted exactly at its expiry instant. Redis reclaims expired keys via two complementary mechanisms:

Passive (lazy) expiration
When a client accesses a key, Redis checks its TTL; if expired, it deletes it then and returns "not found." Zero background cost, but a key that is never touched again would otherwise leak memory forever — hence active expiration is also needed.
Active (proactive) expiration
A background cycle (activeExpireCycle) runs on the server frequency hz (default 10 → ~10x/sec). Per database it: (1) samples ~20 keys from the set of keys that have a TTL, (2) deletes the expired ones, (3) if more than 25% of the sampled keys were expired, it repeats immediately; otherwise it moves on. This adaptively drains large batches of just-expired keys while staying bounded when few are expiring.
NOTE

NOTE. Consequences worth stating in an interview: (a) memory for expired-but-untouched keys is freed lazily, so RSS can lag real logical size; (b) on replicas, keys are not expired independently — the primary drives expiry and propagates a DEL/UNLINK to replicas, so a replica may still hold an expired key but a correct Redis will not serve it. lazyfree-lazy-expire yes makes expiry deletions happen off-thread, avoiding a stall when a big collection expires.

4. Big keys & hot keys

Big keys (a single hash/set/zset/list with millions of elements, or a multi-MB string) are dangerous on two fronts. On the command path, any O(N) op — DEL, HGETALL, a synchronous big delete — blocks the single command thread. On the persistence/replication path the cost is different: BGSAVE and the initial replica sync run in a forked child process, so serialization doesn't stall the main thread — instead a big dataset inflates fork() latency and copy-on-write memory pressure (page faults as the parent keeps writing), plus diskless-transfer time. Mitigation: shard the value across many keys (e.g. hash:{id}:part:0..N), delete with UNLINK or incremental HSCAN+HDEL batches, and set lazyfree-lazy-* options so frees run off-thread.

Hot keys (one key taking a disproportionate share of traffic) can saturate a single shard/node even in a Cluster, since one key hashes to one slot. Mitigation stack:

TechniqueNotes
Client-side caching (RESP3 tracking)Server-assisted caching added in Redis 6.0: with RESP3, CLIENT TRACKING ON lets the server push invalidation messages when a cached key changes, so clients safely cache hot reads locally. Broadcast mode (BCAST) tracks by key prefix without per-key bookkeeping.
Read replicasFan out hot reads across replicas (accept eventual consistency / replication lag). Doesn't help hot writes.
Local (in-process) cacheA short-TTL near-cache (e.g. Caffeine) in front of Redis absorbs the hottest reads entirely; pair with pub/sub or tracking invalidation to bound staleness.
Key replication / sharding of the hot keyWrite the value to N suffixed copies (hotkey:0..N-1) and have clients read a random copy to spread load across slots.
INSIGHT

INSIGHT. The unifying theme of every gotcha here is Redis's single-threaded command execution: KEYS, big-key ops, and synchronous big deletes are all bad for the same reason — they hold the one thread. The fixes rhyme too: make the work incremental (SCAN, batched deletes), asynchronous (UNLINK, lazyfree-*), or elsewhere (replicas, client-side cache).

LFULeast Frequently Used — eviction of the least-accessed key (Redis 4.0+).
LRULeast Recently Used — eviction of the key unused for the longest time; Redis approximates it by sampling.
LZFFast lossless compression (Lempel–Ziv family) applied to interior quicklist nodes.
PELPending Entries List — stream entries delivered to a consumer group but not yet acknowledged via XACK.
RDBRedis Database snapshot — a compact point-in-time binary dump of the whole dataset (dump.rdb).
RedlockRedis's distributed-lock algorithm that acquires a lock on a majority of N independent instances.
RESPREdis Serialization Protocol — the client/server wire protocol; RESP3 adds server-assisted client-side caching.
RSALv2 / SSPLv1Redis Source Available License v2 / Server Side Public License v1 — source-available (not OSI open source) licenses Redis adopted in 2024.
RTTRound-Trip Time — the client-to-server-and-back network latency that pipelining collapses across many commands.
SDSSimple Dynamic String — Redis's binary-safe string type with O(1) length and pre-allocation.
SDOWN / ODOWNSubjectively Down / Objectively Down — one Sentinel's local suspicion vs quorum-confirmed primary failure.
Sorted Set (ZSet)Score-ordered collection backed by a skip list plus hash table; O(log N) inserts and range queries.
TTLTime To Live — expiry set on a key (or, since 7.4, a hash field) after which it is removed.
WAITCommand that blocks until N replicas acknowledge a write; replication stays async, so it is closer-to-synchronous, not fully synchronous.
