Amazon DynamoDB Deep Dive

Comprehensive guide to a managed serverless key-value / document store: partition & sort keys, single-table design, GSIs vs LSIs, capacity modes, hot partitions, Streams, TTL, transactions, and consistency — framed for staff-level system design interviews.

What DynamoDB Is

DynamoDB is a fully managed, serverless, multi-region NoSQL database that offers key-value and document data models. It descends from the 2007 Amazon Dynamo paper — a highly available, eventually consistent key-value store — but the public service (launched 2012) is a distinct, hosted system. Its defining promise is predictable single-digit-millisecond latency at any scale: performance is a function of your access pattern, not of how much data you store.

▶ Design Philosophy in One Sentence

DynamoDB deliberately trades away the flexible ad-hoc querying of a relational database in exchange for bounded, horizontally scalable performance. You cannot run an arbitrary JOIN or a WHERE on a non-indexed attribute cheaply; instead you design your keys and indexes up front around the exact queries your application will make.

The mental model shift: In relational design you normalize first and figure out queries later — the query planner adapts. In DynamoDB you enumerate access patterns first, then design keys and indexes so every pattern is a direct key lookup or a narrow range query. Modeling is query-driven, not entity-driven.

Architecture at a Glance

A table is transparently split into partitions — units of storage and throughput distributed across many nodes. The partition key is hashed to route each item to a partition; the service replicates each partition (typically 3 copies across Availability Zones within a Region) and handles all placement, splitting, repair, and failover for you.

Fig 1: A table is sharded into partitions by a hash of the partition key; each partition is replicated across AZs.
Interview Insight: The single most important consequence of this architecture is the per-partition throughput ceiling: roughly 3,000 RCU and 1,000 WCU per physical partition. If your traffic concentrates on one partition key ("hot partition"), you can be throttled even while the table's total provisioned capacity is barely used. Good key design spreads load across partitions.

Primary Keys: Partition Key & Sort Key

Two Key Schemas▶
  • Simple primary key — partition key only (a.k.a. hash key). The partition key must be unique across the table. Access is a direct GetItem by that key.
  • Composite primary key — partition key + sort key (a.k.a. range key). Uniqueness is on the pair. All items sharing a partition key form an item collection, physically stored together and sorted by sort key.

The sort key unlocks the two most valuable relational-free capabilities: range queries (begins_with, between, >, <) and storing heterogeneous related items together in one collection so a single Query retrieves them in one round trip.

// Query one partition, one round trip, results sorted by SK:
Query(
  KeyConditionExpression = "PK = :pk AND begins_with(SK, :prefix)",
  ExpressionAttributeValues = { ":pk": "USER#42", ":prefix": "ORDER#" }
)
// Returns all of user 42's orders, ordered by the SK (e.g. ORDER#<timestamp>).
Key type rules: Partition and sort key attributes must be scalar — String, Number, or Binary. You cannot use a Boolean, list, map, or set as a key attribute.

The 400 KB trap: item size counts attribute names too. Long descriptive attribute names ("customerShippingAddressLine1") multiplied across millions of items waste both size budget and money. Standard single-table designs use short names (PK, SK, GSI1PK, data).

Single-Table Design

Why One Table Instead of Many▶

Because DynamoDB has no joins, the standard pattern is to store multiple entity types in a single table and use generic key attributes (PK, SK) plus overloaded values so that related entities land in the same item collection. A single Query then fetches a parent and its children together — the "pre-computed join."

  • Key overloading: the same PK/SK attributes hold different meanings for different item types, distinguished by a type prefix (USER#, ORDER#, PRODUCT#).
  • Fewer round trips: retrieve a user profile and their recent orders in one request.
  • Fewer moving parts / cost: one table's capacity, alarms, and backups instead of a dozen.
Honest caveat: single-table design is powerful but hard to evolve and hard for newcomers to read. Many teams pragmatically use a small number of tables (one per bounded context). In an interview, know the pattern and its tradeoffs — do not claim "always one table."

Worked example: e-commerce single-table layout

Access patterns to satisfy: (1) get a user profile, (2) list a user's orders newest-first, (3) get an order with its line items, (4) look up an order by its order id, (5) list all orders in a given status.

// Pattern 2: list user 42's orders, newest first
Query(PK = "USER#42", SK begins_with "ORDER#", ScanIndexForward = false)

// Pattern 3 & 4: look up order 1001 by its id and get its line items in ONE query
Query(PK = "ORDER#1001")   // returns the METADATA row + every ITEM# row

// Pattern 5: all shipped orders — served by a GSI (see Indexes tab)
Query(IndexName = "GSI1", GSI1PK = "STATUS#SHIPPED")
Sort-key design is a superpower: putting a zero-padded timestamp or ISO-8601 date inside the SK (ORDER#2026-08-01#1001) makes "newest first" a free ScanIndexForward=false scan — no sorting, no filtering.

Secondary Indexes Enable New Access Patterns

The base table only lets you query by its primary key. Secondary indexes let you query by other attributes. DynamoDB offers two kinds, and choosing correctly is a classic interview discriminator.

Global Secondary Index (GSI)
  • A different partition key and (optional) sort key from the base table.
  • Stored as a separate, asynchronously-maintained table behind the scenes.
  • Eventually consistent only — no strongly consistent reads.
  • Own capacity (provisioned) or shares the table's on-demand billing.
  • Up to 20 per table (default quota); can add or delete any time.
Local Secondary Index (LSI)
  • Same partition key as the base table, but a different sort key.
  • Stored in the same partition as the base item (shares the item collection).
  • Supports strongly consistent reads.
  • Shares the table's provisioned throughput; no separate capacity.
  • Up to 5 per table, and must be created with the table — never added later.
The 10 GB LSI catch: because an LSI lives in the base item's partition, the presence of any LSI caps each item collection (all items with the same partition key, across base + LSIs) at 10 GB. GSIs have no such limit because they are stored separately. When in doubt, prefer a GSI.

GSI vs LSI — Decision Table

PropertyGSILSI

Rule of thumb: reach for a GSI by default. Use an LSI only when you specifically need strong consistency on an alternate sort order within the same partition key and are confident item collections stay under 10 GB. In practice GSIs cover the vast majority of needs.

Projections — What Gets Copied Into the Index

An index does not necessarily contain every attribute. The projection controls which non-key attributes are copied. This is a direct cost/latency lever: a smaller projection is cheaper to store and write, but querying a non-projected attribute forces an extra fetch from the base table.

Projection typeContainsWhen to use
KEYS_ONLYIndex key + base table key onlySmallest/cheapest; when you only need the keys, then batch-get the rest.
INCLUDEKeys + a chosen list of extra attributesThe best balance: project exactly the attributes your query returns → covering index.
ALLEvery attribute of the itemFastest reads (no base-table fetch) but highest storage + write cost.
Non-projected attribute penalty (GSI): if a query requests an attribute that is not projected into a GSI, DynamoDB does not automatically fetch it — you get only projected attributes back. You must issue a separate GetItem/BatchGetItem against the base table. (LSIs can auto-fetch non-projected attributes from the base item, at extra read cost, because they are co-located.)

GSI Write Amplification & Throttling

Fig 2: Every base-table write that changes a projected/key attribute propagates to each relevant GSI, consuming that GSI's write capacity.
  • An item write updates every GSI whose key or projected attributes changed — so N GSIs can mean up to N+1 write operations' worth of capacity.
  • GSI maintenance is asynchronous: the base write succeeds immediately, and the index converges shortly after (the source of eventual consistency).
  • If a provisioned GSI runs out of write capacity, it can back-pressure and throttle writes to the base table. A common cause of "my writes are throttled and I don't know why."
  • Sparse indexes: an item only appears in a GSI if it has the GSI's key attributes. Omitting the attribute keeps items out of the index — a cheap, powerful filter (e.g. only "OPEN" tickets carry a gsiStatus attribute).

Capacity Units: RCU & WCU

🔢 The Arithmetic (memorize this)
OperationCost
1 RCU (read capacity unit)1 strongly consistent read/sec of an item up to 4 KB
Eventually consistent read2 reads/sec of up to 4 KB per RCU (i.e. half the cost)
Transactional read2 RCU per 4 KB (double the cost)
1 WCU (write capacity unit)1 write/sec of an item up to 1 KB
Transactional write2 WCU per 1 KB (double the cost)

Sizes always round up to the next 4 KB (reads) or 1 KB (writes). A 6 KB item costs 2 RCU (strong) or 1 RCU (eventual, 6 KB → 2× 4 KB units → round to 2 units → half = 1); a 1.5 KB write costs 2 WCU.

// Example: 100 strongly-consistent reads/sec of 8 KB items
//   8 KB → 2 units of 4 KB → 2 RCU per read → 200 RCU
// Same as eventually consistent: 100 RCU (half cost)
// Example: 50 writes/sec of 3 KB items
//   3 KB → 3 units of 1 KB → 3 WCU per write → 150 WCU

On-Demand vs Provisioned

On-Demand
  • Pay per request (per million reads/writes); no capacity planning.
  • Scales instantly with traffic; ideal for spiky, unpredictable, or new workloads.
  • Instantly serves up to 2× your previous peak; ramps higher automatically.
  • Optional max throughput setting to cap runaway cost.
  • Typically pricier per request at steady high volume than well-tuned provisioned.
Provisioned
  • You set RCU/WCU; pay for provisioned capacity whether used or not.
  • Cheapest for steady, predictable traffic.
  • Pair with auto scaling (target utilization, e.g. 70%) to track demand.
  • Reserved capacity gives large discounts for 1- or 3-year commitments.
  • Under-provisioning → throttling (ProvisionedThroughputExceededException).
Switching modes: you can flip a table between on-demand and provisioned. Historically limited to once per 24 hours; today the switch is far more flexible. A common lifecycle: launch on-demand to learn the traffic shape, then move steady workloads to provisioned + auto scaling + reserved capacity for cost.

Auto Scaling & Burst

How Provisioned Capacity Tracks Demand▶
  • Application Auto Scaling adjusts provisioned RCU/WCU toward a target utilization (default 70%) between a min and max you set. It reacts to CloudWatch metrics over minutes — it is not instantaneous, so it smooths trends but does not absorb sudden spikes.
  • Burst capacity lets a partition draw on up to ~300 seconds of previously unused capacity to absorb short spikes — a built-in cushion, not a guarantee.
  • For truly spiky traffic where auto scaling lags, on-demand mode is usually the better answer.

Hot Partitions & Adaptive Capacity

Fig 3: A low-cardinality partition key concentrates traffic; a high-cardinality key spreads it across partitions.
  • Hot partition = disproportionate reads/writes to one partition key. Because a single partition tops out near 3,000 RCU / 1,000 WCU, a hot key throttles even when the table has spare total capacity.
  • Adaptive capacity (automatic, always on) does two things: it reshuffles capacity toward busy partitions, and it can split partitions by item access frequency — isolating a single hot item onto its own partition. It reacts quickly but cannot beat the per-partition physical ceiling for one key.
  • Write sharding is the classic fix for an unavoidably hot key: append a suffix (METRIC#2026-08-13#<0-9>) to spread writes across N synthetic partitions, then scatter-gather on read.
Interview one-liner: "Adaptive capacity handles imbalance for free, but it can't raise the ceiling of a single partition key. If one key must absorb more than ~1,000 writes/sec, shard the key." Great keys are high-cardinality and access-uniform (user id, not "status" or "true").

DynamoDB Streams

Change Data Capture for Your Table▶

A Stream is an ordered, immutable log of item-level modifications (create/update/delete). It is the foundation for event-driven architectures on top of DynamoDB.

  • Retention: stream records are available for 24 hours.
  • Ordering: records for the same partition key appear in the correct order; there is no total order across different keys (mirrors the shard model).
  • View types (StreamViewType): KEYS_ONLY, NEW_IMAGE, OLD_IMAGE, NEW_AND_OLD_IMAGES.
  • Consumers: AWS Lambda (most common — event source mapping polls shards for you) or the Kinesis Client Library via the DynamoDB Streams Kinesis Adapter.
  • Alternative: Kinesis Data Streams for DynamoDB emits the same change events to a Kinesis stream for longer retention and larger fan-out.
Common uses: maintaining a materialized/aggregate view, replicating to OpenSearch for search, invalidating a cache, fanning out notifications, and — internally — powering Global Tables (multi-Region replication is built on Streams).

TTL (Time To Live)

Automatic Expiry Without Consuming Write Capacity▶
  • You designate one numeric attribute holding a Unix epoch time in seconds. When that time passes, the item becomes eligible for deletion.
  • Deletion is a background process — items are typically removed within a couple of days of expiry, not instantly. Expired-but-not-yet-deleted items can still appear in reads.
  • TTL deletes do not consume write capacity and incur no extra charge — a major cost win versus manually deleting old rows.
  • TTL deletions appear in Streams as delete records, tagged with a principal of the DynamoDB service, so you can archive expired data (e.g. to S3) via a Lambda consumer.
Filter expired items in reads if correctness matters: because deletion lags expiry, add a FilterExpression (expiresAt > :now) to hide logically-expired items until the background sweep removes them.

Conditional Writes & Optimistic Locking

Compare-and-Set Without a Lock▶

Any single-item write (PutItem, UpdateItem, DeleteItem) can carry a ConditionExpression. The write is applied atomically only if the condition holds; otherwise it fails with ConditionalCheckFailedException and consumes capacity but changes nothing.

// Idempotent create — fail if the item already exists
PutItem(Item = {...}, ConditionExpression = "attribute_not_exists(PK)")

// Optimistic locking with a version attribute (no pessimistic lock needed)
UpdateItem(
  Key = { PK: "ACCOUNT#7" },
  UpdateExpression = "SET balance = :new, version = :v1",
  ConditionExpression = "version = :v0",
  Values = { ":new": 90, ":v1": 6, ":v0": 5 }
)   // fails if another writer already bumped version → caller retries

// Atomic counter (no read needed; last-writer-safe increment)
UpdateItem(Key={...}, UpdateExpression = "ADD viewCount :one", {":one": 1})
Why this matters: DynamoDB has no row locks you hold across round trips. Concurrency is handled with optimistic concurrency control (version attribute + conditional write) and atomic update expressions (ADD, SET x = x + :n). This is a classic concurrency question you may get: "how do you prevent lost updates?"

Transactions

ACID Across Multiple Items▶
  • TransactWriteItems — all-or-nothing across up to 100 items / 4 MB, spanning multiple tables in one Region and account. Supports Put, Update, Delete, and ConditionCheck actions.
  • TransactGetItems — a consistent snapshot read of up to 100 items.
  • Serializable isolation. If any item's condition fails or two transactions conflict, the whole transaction is rejected (TransactionCanceledException with per-item reasons).
  • Cost: transactional operations are 2× the normal capacity (2 WCU/KB write, 2 RCU/4KB read) because of the two-phase prepare/commit protocol.
  • Idempotency: pass a ClientRequestToken so a retried transaction is not applied twice (dedup window ~10 minutes).
Design guidance: transactions are the right tool for cross-item invariants (transfer money between two accounts; enforce a uniqueness sentinel alongside the main item). But they cost double and add contention — prefer a single-item conditional write or single-partition design when you can express the invariant within one item.

Strong vs Eventual Consistency

Read typeBehaviorCostAvailable on
Eventually consistent (default)May reflect a slightly stale copy; converges within ~1s. Cheapest.0.5 RCU / 4 KBBase table, LSI, GSI
Strongly consistentReflects all writes acknowledged before the read; served from the leader.1 RCU / 4 KBBase table, LSI
Transactional readSerializable snapshot across items.2 RCU / 4 KBBase table
GSIs are eventually consistent — always. There is no strongly consistent read on a Global Secondary Index, because the index is maintained asynchronously. If you need read-your-writes on an alternate key, either use an LSI (strong, same partition key) or design so the base-table key covers the pattern. Global Tables (multi-Region) are also eventually consistent across Regions with last-writer-wins conflict resolution.
CAP framing for interviews: within a Region DynamoDB gives you the choice per read (strong vs eventual). Across Regions (Global Tables) it favors availability and low latency (AP-leaning), reconciling concurrent writes by last-writer-wins on a per-item basis.

Access-Pattern-First Modeling Method

🔍 The Repeatable Framework
  1. Enumerate every access pattern as a sentence: "get X by Y", "list all Z for a W newest-first", "find all items in state S." Do this before touching keys.
  2. List the entities and relationships (an ER diagram is still useful) — but treat it as input, not the schema.
  3. Assign primary keys so the highest-frequency patterns are direct GetItem/Query calls. Co-locate items that are read together into one item collection.
  4. Cover the rest with GSIs (inverted index, sparse index, status index). Choose projections to make hot queries covering.
  5. Validate: for each access pattern, write the exact query and confirm it is a key/index lookup — never a table Scan or a FilterExpression doing the heavy lifting.
Red flag to call out: if a pattern can only be served by a full Scan or a broad FilterExpression, the model is wrong — filters run after capacity is consumed reading the rows. Redesign keys or add a GSI.

Worked Interview Prompt: Design a URL Shortener on DynamoDB

From access patterns to keys, indexes, and capacity▶

Access patterns: (1) resolve short code → long URL (hot, read-heavy), (2) create a short code (must be unique), (3) list a user's links newest-first, (4) count clicks per link, (5) auto-expire temporary links.

ItemPKSKNotes
Short linkLINK#abc123LINK#abc123longUrl, ownerId, createdAt, ttl (epoch s), clicks
User→link edgeUSER#42LINK#2026-08-13#abc123SK date prefix → newest-first list
  • Pattern 1 (resolve): GetItem(PK=LINK#abc123) — a single-partition point read, single-digit ms. Front with DAX (in-memory cache) if read volume is extreme.
  • Pattern 2 (unique create): PutItem with ConditionExpression="attribute_not_exists(PK)" — regenerate code on collision.
  • Pattern 3 (list user links): Query(PK=USER#42, begins_with(SK,"LINK#"), ScanIndexForward=false).
  • Pattern 4 (click count): atomic UpdateItem ... ADD clicks :one. If a single link is wildly hot, write-shard the counter across N suffixes and sum on read.
  • Pattern 5 (expiry): set the ttl attribute; TTL sweep deletes for free and emits a Stream record for archival.
  • Capacity: spiky/unknown launch traffic → on-demand; once steady, move to provisioned + auto scaling; reserved capacity for the baseline.

When to Use DynamoDB — and When Not To

Great fit
  • Known, key-based access patterns at massive scale (user sessions, shopping carts, device state, feature flags).
  • Need predictable low latency regardless of data volume.
  • Serverless / event-driven stacks (pairs naturally with Lambda + Streams).
  • Spiky or unpredictable traffic (on-demand mode).
  • Multi-Region active-active with Global Tables.
Poor fit
  • Ad-hoc analytics / OLAP aggregations → Redshift, BigQuery, ClickHouse.
  • Rich relational querying, many-way JOINs, complex reporting → RDS/Aurora, Spanner.
  • Full-text / relevance search → OpenSearch/Elasticsearch.
  • Unknown, evolving query patterns during early product discovery.
  • Large objects → store in S3, keep a pointer (400 KB item cap).
Companion services worth naming: DAX (write-through/read-through microsecond cache in front of DynamoDB), PartiQL (SQL-compatible query syntax over the same key-based access — it does not add joins or remove the need for indexes), zero-ETL to OpenSearch/Redshift for search and analytics, and PITR (point-in-time recovery, continuous backups up to 35 days).

Rapid-Fire Q&A

Q: Why did my write get throttled even though total capacity looks fine?▶

Almost always a hot partition: traffic concentrated on one partition key hits the ~1,000 WCU / ~3,000 RCU single-partition ceiling. Adaptive capacity helps with imbalance but can't exceed one partition's ceiling for one key. Also check whether a GSI ran out of write capacity and back-pressured the base table. Fixes: higher-cardinality key, write sharding, or on-demand mode.

Q: GSI or LSI?▶

Default to GSI (different partition key, add/remove anytime, no 10 GB collection cap, own capacity). Use an LSI only when you need strong consistency on an alternate sort key within the same partition key, and you must decide at table-creation time. LSIs impose a 10 GB per-item-collection limit; GSIs do not.

Q: How do you prevent lost updates without locks?▶

Optimistic concurrency: keep a version attribute; every UpdateItem asserts ConditionExpression="version = :expected" and bumps it. A conflicting concurrent writer fails and retries. For pure counters, use the atomic ADD/SET x = x + :n update expression, which needs no read.

Q: Strongly consistent read on a GSI?▶

Not possible — GSIs are maintained asynchronously and are always eventually consistent. If you need read-your-writes, use an LSI (strong) or make the base-table primary key serve the pattern.

Q: How does DynamoDB do multi-Region?▶

Global Tables: active-active replication built on Streams. Reads/writes are local and fast in each Region; replication is asynchronous and eventually consistent, with last-writer-wins conflict resolution per item. Good for low-latency global reads and Region-failure resilience; not for strict cross-Region serializability (that's Spanner's niche).

Q: Scan vs Query — and why avoid Scan?▶

Query targets a single partition key (+ optional sort-key condition) and reads only matching items — efficient. Scan reads the entire table and applies filters afterward, consuming capacity for every item examined. Reserve Scan for rare full-table jobs (exports, migrations), ideally parallel-segmented and rate-limited. A well-modeled table almost never needs a Scan on the hot path.
