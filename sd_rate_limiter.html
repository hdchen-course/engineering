Design a Rate Limiter

The first "classic" system-design problem: how to cap how fast clients hit a service — from a single in-memory counter a high-schooler can reason about, up to a strictly-consistent limiter shared across hundreds of nodes. Every formula and number below is stated precisely so you can quote it in an interview.
Read this like a story

Start at the top even if you already know the algorithms — the sections build from "why would anyone need this" to "make it exact across N nodes under a network partition." The math for each algorithm is boxed so you can find it fast on a re-read.

1. The Problem & Why We Rate Limit

A rate limiter controls how many requests a client may send in a window of time. If the client stays under the limit, requests pass through. If it goes over, the extra requests are rejected (or delayed) — typically with an HTTP 429 Too Many Requests. Think of it as a bouncer at a club door counting how many people each group sends in per minute.

Why bother? Four reasons interviewers want to hear

  • Protect the service (stability). A downstream database or third-party API has a finite capacity. Without a limiter, one runaway client — a buggy retry loop, a scraper — can saturate it and take everyone down. This is the "noisy neighbor" problem.
  • Fairness (isolation). On a shared/multi-tenant system, one tenant should not be able to consume all the capacity. Per-tenant limits give each customer a predictable slice.
  • Cost control. If every API call costs you money (a paid ML inference, an SMS send, a metered cloud API), a limit caps the bill and enforces your pricing tiers (free vs. paid plans).
  • Abuse & security. Rate limits blunt brute-force login attempts, credential stuffing, scraping, and volumetric denial-of-service (DoS). They are one layer of defense, not the whole story.

Where does the limiter sit?

(a) client-side self-throttle · (b) gateway limiter — the usual answer · (c) per-service limiter for internal fairness
  • Client side: the app throttles itself (good manners, but untrusted — a malicious client just removes it). Never your only line of defense.
  • API gateway / reverse proxy: the standard place. One choke point sees all traffic before it reaches your services, so it protects everything behind it. This is almost always the interview's default answer.
  • Per-service (middleware): each service also limits internal callers, giving fairness and defense-in-depth even for east-west traffic the gateway never sees.

Requirements to pin down

Functional

  • Limit by what key? per user ID, per API key, per IP, per (user × endpoint). State it.
  • Limit rule: e.g. "100 requests per minute," possibly tiered (free vs. paid).
  • Correct reject behavior: return 429 with headers telling the client when to retry.
  • Rules should be configurable without a redeploy.

Non-functional

  • Low latency: the limiter is on the hot path of every request — budget single-digit milliseconds, ideally < 1 ms.
  • Accuracy: how strict? A hard billing cap needs exactness; abuse-protection tolerates approximation.
  • Distributed: must work correctly across many limiter nodes.
  • High availability + failure mode: decide fail-open vs. fail-closed (below).
Fail-open vs. fail-closed

If the counter store (Redis) is unreachable, what do you do? Fail-open = allow the request (favor availability; risk is a flood slips through). Fail-closed = reject it (favor protection; risk is you reject legitimate traffic during an outage). Most public APIs fail-open so a limiter outage doesn't become a full outage; a strict billing or security gate may fail-closed. Saying which one, and why, is a senior signal.

2. Back-of-the-Envelope Estimation

Sizing tells you whether a single Redis instance suffices or you need sharding, and how much memory the counters cost.

Traffic (QPS)

Suppose 1,000,000 daily active users, each making ~100 requests/day that pass through the limiter.

requests/day = 1,000,000 × 100 = 100,000,000 (108)
seconds/day = 86,400 ≈ 105
average QPS = 108 / 86,400 ≈ 1,160 QPS # ≈1,000 using the ÷10⁵ shortcut
peak QPS = average × (peak factor 5–10) ≈ 11,600 QPS

Because the limiter runs on every request, its own throughput must be at least peak QPS. A single Redis node handles ~100k simple ops/sec, so ~12k QPS fits comfortably on one node — but each request may cost 1–2 Redis ops, so keep that headroom in mind.

Memory per counter, and how many counters

The key insight: you only store state for active keys in the current window, not all users ever.

AlgorithmState per keyRough bytes/key*1M active users
Fixed / sliding-window counterkey + one integer (+ TTL)~100 bytes~100 MB
Token bucketkey + {tokens, last_refill_ts}~120 bytes~120 MB
Sliding-window logkey + up to L timestamps (8 B each)~1 KB (L≈100)~1 GB

*Includes Redis per-key overhead (object headers, expiry metadata), not just the raw value — a bare 8-byte int in Redis really costs ~50–100 B once overhead is counted.

Takeaway

Counter-based algorithms fit a single Redis node's RAM for millions of users. The log approach is ~10× heavier — that memory cost is the whole reason we invent the cheaper approximations below.

3. The Algorithms

Five algorithms, each with a picture, the exact math, and when to reach for it. Two dials matter throughout: does it allow bursts (let a client spend saved-up allowance quickly) and how accurate is it at window boundaries.

3.1 Token Bucket — the default; allows bursts

Picture a bucket that holds up to C tokens (the capacity). Tokens are added at a steady refill rate r (tokens/second). Each request must take one token: if a token is available, the request passes and one token is removed; if the bucket is empty, the request is rejected. Because a full bucket lets a client spend C tokens at once, token bucket permits short bursts up to the capacity while holding the long-run average to r.

Tokens drip in at rate r up to capacity C; each request removes one, or is rejected when the bucket is empty.

The exact refill math

You don't run a background timer per bucket (that wouldn't scale). Instead you do lazy refill: store the token count and the timestamp of the last refill, and recompute on each request based on elapsed time.

# on a request arriving at time `now` (seconds)
elapsed = now − last_refill_ts
tokens = min(C, tokens + elapsed × r) # refill, never exceed capacity C
last_refill_ts = now

# admission (cost defaults to 1; use cost = k for weighted requests)
if tokens ≥ cost: tokens = tokens − cost ; ALLOW
else: REJECT (429)

Long-run sustained rate = r requests/sec; maximum instantaneous burst = C requests (when the bucket is full). Pick C = how big a burst you tolerate, r = the steady rate you'll sustain. Example: r = 10/s, C = 10 means "10/sec on average, but a client idle for a second can fire up to 10 at once."

Pros
  • Smooth average rate, but tolerates natural bursts
  • Tiny state: 2 numbers per key
  • Memory-cheap, easy to make atomic
Cons
  • Two params (C and r) to tune
  • A burst of C can still briefly overload a fragile downstream
When to use

The default choice for API rate limiting (used by many cloud APIs). Reach for it whenever occasional bursts are fine and you want a simple, memory-cheap limiter.

3.2 Leaky Bucket — constant outflow, smooths bursts away

Now picture a bucket with a hole in the bottom that leaks at a constant rate r. Incoming requests are water poured in; they queue in the bucket (capacity C) and drain out at exactly r per second. If the bucket is full, new requests overflow and are dropped. Implemented as a FIFO queue processed at a fixed rate.

Bursty input, constant output. The queue absorbs spikes; anything over capacity C overflows and is dropped.
# queue length q, drains at rate r; request arrives at `now`
leaked = (now − last_leak_ts) × r
q = max(0, q − leaked) ; last_leak_ts = now
if q < C: q = q + 1 ; ENQUEUE / ALLOW
else: REJECT (queue full · 429)
Pros
  • Perfectly smooth, constant outflow — kind to fragile downstreams
  • Predictable load shape
Cons
  • No bursts allowed — spiky-but-legit traffic gets delayed/dropped
  • Queuing adds latency; a full queue can hold stale requests
When to use

When the thing you protect needs a steady input rate (e.g. a downstream that melts under spikes, or an outbound stream to a metered third party). Token bucket favors burst-friendliness; leaky bucket favors smoothness — that's the core trade-off between them.

Same coin, two faces

A "leaky bucket as a meter" (no real queue, just a counter that leaks) is mathematically the mirror image of token bucket. The boxed formula above is exactly that lazy/meter-style computation — the same math you'd use to implement the queue's admission check without maintaining a real FIFO. Both the FIFO-queue model (what most people mean by leaky bucket) and this meter computation yield the same q < C ⇒ admit decision.

3.3 Fixed Window Counter — simplest; the boundary-burst trap

Chop time into fixed windows of length W (say, each calendar minute). Keep one counter per window per key. Increment on each request; allow while the counter is ≤ L (the limit); reset to zero when the next window starts. Very simple — one integer.

The boundary-burst problem: 5 requests just before the reset + 5 just after = 10 in a span shorter than one window, despite a "5 per window" limit.
window_id = floor(now / W) # which fixed bucket we're in
count[key, window_id] += 1
if count[key, window_id] ≤ L: ALLOW
else: REJECT (429) # counter auto-expires after W
The boundary burst

A client can send L requests in the last instant of one window and another L in the first instant of the next — up to 2L requests within a span of one window length W. So a "100/min" limit can permit ~200 requests inside a single 60-second stretch that straddles the boundary. This is the classic flaw the sliding-window methods fix.

Pros
  • Simplest possible: one integer + TTL
  • Maps directly to Redis INCR+EXPIRE
  • Cheapest memory
Cons
  • 2× burst at boundaries
  • Reset causes a "stampede" of allowance at each window start

3.4 Sliding Window Log — exact, but memory-heavy

Store a timestamp for every accepted request, in a sorted structure per key. On each new request at time now: drop all timestamps older than now − W (they've slid out of the rolling window), then count what remains. This is a true rolling window — no boundary artifact at all.

Every request's timestamp is stored; those older than now − W are evicted, and the survivors are counted exactly.
# log = sorted set of timestamps for this key
remove all t from log where t ≤ now − W # evict what slid out
if size(log) < L: add now to log ; ALLOW
else: REJECT (429)
Pros
  • Perfectly accurate — no boundary burst ever
  • Enforces "no more than L in any window of length W"
Cons
  • Stores up to L timestamps per key → ~10× the memory
  • Heavier per-request work (evict + count)
When to use

When exactness matters and L is small (e.g. "5 login attempts per hour"). In Redis this maps to a sorted set (ZADD / ZREMRANGEBYSCORE / ZCARD).

3.5 Sliding Window Counter — the practical best balance

Combine the cheapness of fixed windows with a smoothing estimate that kills most of the boundary burst. Keep just two counters — the current fixed window and the previous one — and estimate the rolling count by weighting the previous window by how much it still overlaps the rolling window.

Only two counters. The rolling window borrows a fraction of the previous window equal to how much it still overlaps it.

The exact weighted-estimate formula

Let W = window length, t = time elapsed since the current window started (so 0 ≤ t < W). The rolling window [now − W, now] reaches back into the previous window by an amount (W − t), i.e. it covers a fraction (W − t)/W of it. So:

estimated_count = curr_count + prev_count × (W − t) / W
# equivalently: curr_count + prev_count × (1 − t/W)

if estimated_count < L: ALLOW (then curr_count += 1)
else: REJECT (429)

Worked example (matches the figure above): limit L = 7 per minute, prev_count = 5, curr_count = 3, and we are 60% into the current minute (t/W = 0.60, so the previous window's overlap weight is 1 − 0.60 = 0.40):

estimated = 3 + 5 × (1 − 0.60) = 3 + 5 × 0.40 = 3 + 2 = 5
5 < 7 ⇒ ALLOW
Pros
  • Just two integers per key — nearly as cheap as fixed window
  • Smooths the boundary burst well (assumes even spread in the previous window)
  • Great accuracy/cost balance — the common production choice
Cons
  • An estimate, not exact — assumes uniform arrival in the previous window
  • Slight over/under-count if traffic was very skewed within a window
When to use

The pragmatic default when fixed-window's boundary burst is unacceptable but you can't afford the log's memory. Cloudflare's public writeup reports the approximation is accurate to within a fraction of a percent on real traffic.

4. Data Model & Where State Lives

Whatever the algorithm, the limiter keeps a small piece of state per key. The key is what you limit on; the value is the algorithm's counters.

FieldExampleNotes
keyratelimit:{user_id}:{endpoint}Namespaced; include the rule scope so limits don't collide
value (fixed/sliding counter){ count, window_start }One or two integers
value (token bucket){ tokens, last_refill_ts }Refill computed lazily on read
TTLEXPIRE = W (or bucket refill time)Auto-reclaim memory for idle keys

In-memory (per node) vs. centralized store

Local in-memory

  • Counter in the process's own RAM (a hash map).
  • Fastest (nanoseconds, no network hop), simplest.
  • But each node only sees its own traffic → the global limit is effectively multiplied by the number of nodes. Fine for a single instance or a coarse per-node cap.

Centralized store (Redis)

  • All nodes read/write the same counter in a shared store — usually Redis (in-memory, single-threaded, atomic ops).
  • Gives a single source of truth so the global limit is honored no matter which node serves the request.
  • Costs a network round-trip (~0.5 ms same-DC) per check and makes the store a dependency you must scale and protect.

Redis is the near-universal answer because it is in-memory (fast), single-threaded (operations are atomic — see §5), and ships primitives (INCR, EXPIRE, sorted sets, Lua) that map directly onto every algorithm above.

5. Distributed Rate Limiting

This is where the interview gets deep. The moment you have more than one limiter node, "just increment a counter" hides several hard problems.

Centralized model: all limiter nodes share one atomic counter store, so the global limit holds no matter which node a request lands on.

Single source of truth vs. per-node counting

  • Per-node (local) counting: each node keeps its own counter. Zero network cost and no shared dependency, but N nodes means the effective global limit is roughly N × L. Acceptable only if you set each node's limit to L / N — which breaks when load is uneven or nodes scale up/down.
  • Centralized counting: one shared store (Redis) is the single source of truth. Exact global limit, at the cost of a round-trip and a dependency.

The read-modify-write race condition

The naive "read counter, add one, write it back" is a classic race. Two nodes both read count = 99 (limit 100), both compute 100, both write 100, and both allow — so 101 requests slip through. Under high concurrency this under-counts and lets the limit be exceeded.

Root cause

Read and write are two separate operations; another node interleaves between them. The fix is to make check-and-increment a single atomic operation.

Atomicity in Redis

Fixed window: INCR + EXPIRE

Redis INCR is atomic and returns the new value in one step — no read-then-write gap — so the race above disappears. Set the TTL only when the key is first created:

# Redis is single-threaded: each command runs to completion atomically
count = INCR(key)              # atomic increment, returns new value
if count == 1:
    EXPIRE(key, W)          # first request in this window → start the TTL
if count > L:
    return REJECT           # 429
return ALLOW
The INCR/EXPIRE gap

INCR and EXPIRE are two commands. If the process crashes between them, the key has a count but no TTL — it lives forever and permanently blocks that key. Fix by making the pair atomic: run both in a Lua script (or MULTI/EXEC), or use SET key val NX EX W to initialize. This gap is a common interviewer probe.

Token bucket / sliding-window via a Lua script

Token bucket needs read tokens → compute refill → check → decrement, and sliding-window-counter needs to read two counters and compute the weighted estimate. Those are multiple steps, so wrap them in a Lua script: Redis runs a script atomically (its single thread executes the whole script before anything else), giving you a safe read-modify-write with one round-trip.

-- token_bucket.lua  (KEYS[1]=bucket, ARGV: now, rate r, capacity C, cost, ttl)
local now, r, C, cost, ttl = tonumber(ARGV[1]), tonumber(ARGV[2]), tonumber(ARGV[3]), tonumber(ARGV[4]), tonumber(ARGV[5])
local b = redis.call('HMGET', KEYS[1], 'tokens', 'ts')
local tokens = tonumber(b[1]) or C
local ts     = tonumber(b[2]) or now
tokens = math.min(C, tokens + (now - ts) * r)   -- lazy refill
local allowed = tokens >= cost
if allowed then tokens = tokens - cost end
redis.call('HSET', KEYS[1], 'tokens', tokens, 'ts', now)
redis.call('EXPIRE', KEYS[1], ttl)
return allowed        -- whole script runs atomically → no race

Strict vs. approximate: local counting + async sync

Centralized checks add latency to every request. A common optimization trades a little accuracy for speed: each node keeps a local counter and only periodically syncs to the shared store (or nodes gossip). This is fast and survives brief store hiccups, but during the sync interval nodes can collectively overshoot the limit — an approximate limiter. Choose strict (centralized, exact, slower) vs. approximate (local + sync, fast, may overshoot) based on whether the limit is a hard cap (billing) or a soft guard (abuse).

Clock issues

Time is not free in distributed systems

Any algorithm using timestamps (token bucket refill, sliding windows) depends on time. If each node uses its own wall clock and clocks drift (or jump on NTP correction), refill amounts and window boundaries disagree across nodes. Mitigations: compute time inside the store (Redis TIME) so there's one clock, keep clocks tight with NTP, and prefer monotonic clocks for elapsed-time math to avoid backward jumps.

The CAP / latency trade-off, restated as fail-open vs. fail-closed

The shared counter store is a dependency, so the limiter inherits its availability. During a partition or Redis outage you must choose (this is the CAP choice showing up concretely):

  • Fail-open (favor availability, "AP"): if the store is unreachable, allow requests. Your service stays up; the risk is a burst gets through unlimited. The usual choice for public APIs — a limiter outage shouldn't cause a full outage.
  • Fail-closed (favor protection, "CP"): if you can't verify the limit, reject. Protects a fragile downstream or a hard security/billing gate, at the cost of rejecting legitimate traffic during the outage.
"I'd keep the counters in Redis for a single source of truth and make the check atomic with a Lua script. If Redis is unavailable I'd fail-open for our public API — a limiter outage shouldn't take the whole service down — while falling back to a coarse per-node local limit so we're not completely unprotected."

6. Response Behavior — 429 and the Headers

Rejecting is only half the job; a good limiter tells the client what happened and when to come back so well-behaved clients can back off instead of hammering.

  • 429 Too Many Requests — the standard HTTP status for "you exceeded the rate limit."
  • Retry-After — how long to wait before retrying, in seconds (e.g. Retry-After: 30) or as an HTTP date. Standardized and understood by many clients/CDNs.
  • X-RateLimit-Limit — the ceiling for the window (e.g. 100).
  • X-RateLimit-Remaining — requests left in the current window.
  • X-RateLimit-Reset — when the window resets (epoch seconds or seconds-until).
# A rejected response
HTTP/1.1 429 Too Many Requests
Retry-After: 12
X-RateLimit-Limit: 100
X-RateLimit-Remaining: 0
X-RateLimit-Reset: 1737000060
Content-Type: application/json

{ "error": "rate_limit_exceeded", "retry_after": 12 }
Client-side manners

Return the X-RateLimit-* headers on successful responses too, so clients can self-pace before hitting the wall. Pair Retry-After with exponential backoff + jitter on the client to avoid a synchronized retry stampede. The X-RateLimit-* names are a de-facto convention (GitHub, Twitter/X, etc.), not an RFC; Retry-After is the standardized one.

The 30-second decision

Need bursts allowed? → token bucket. Need perfectly smooth output? → leaky bucket. Need exactness & L is small? → sliding window log. Want cheap + smooth without the log's memory? → sliding window counter. Truly don't care and want the simplest thing? → fixed window (and accept the 2× boundary burst).

8. Interview Framing

How to drive the conversation

  1. Clarify (1–2 min): What key do we limit on (user/IP/API key)? What's the rule (e.g. 100/min)? Client-side, gateway, or per-service? Strict cap or best-effort? Single region or global?
  2. Estimate: QPS and memory (§2) → decide single Redis vs. sharded.
  3. Pick an algorithm and justify with the burst/accuracy dials (§3, §7).
  4. Go distributed: centralized Redis as source of truth, atomicity via INCR/Lua, and the race you're preventing (§5).
  5. Cover failure & response: fail-open vs. fail-closed; 429 + Retry-After (§6).

What interviewers probe (with one-liners)

Q: How do you make it exact across N nodes?
Keep counters in a single shared store (Redis) as the source of truth and make check-and-increment atomic — INCR for fixed window, a Lua script for token bucket / sliding window — so no two nodes can both read-modify-write the same value.

Q: Burst vs. smoothness — how do you choose?
Token bucket allows bursts up to capacity C while holding the average to r; leaky bucket forces a constant, smooth outflow with no bursts. Choose bursts if clients are naturally spiky and downstream tolerates it; choose smoothing if the downstream melts under spikes.

Q: What's wrong with a fixed window?
The boundary burst: up to 2L requests within one window length W, because L can land at the end of one window and L at the start of the next. Sliding window counter or log fixes it.

Q: How does the sliding window counter estimate the count?
estimated = curr_count + prev_count × (W − t)/W, where t is time elapsed into the current window — it weights the previous window by how much the rolling window still overlaps it. Cheap (2 counters) and accurate if arrivals are roughly uniform.

Q: What happens if Redis goes down?
Decide fail-open (allow — protect availability, the usual public-API choice) vs. fail-closed (reject — protect a hard cap). Ideally fall back to a coarse local per-node limit so you're not fully unprotected.

Q: What about the race condition on the counter?
Naive read-then-write lets two nodes both see 99 and both allow at limit 100. Atomic INCR (returns the post-increment value in one step) or a Lua script eliminates the read-modify-write gap.

Q: Any subtle bugs to watch for?
The INCR-then-EXPIRE gap (key with no TTL lives forever if you crash between them — make it atomic), and clock drift across nodes for timestamp-based algorithms (compute time in the store; use monotonic clocks for elapsed math).

One-line summary

Rate limiting = a small atomic counter per key. Token bucket is the sensible default; sliding-window counter is the best accuracy-for-memory balance; keep the counter in Redis for a global source of truth, make the check atomic to avoid races, and decide fail-open vs. fail-closed up front.
