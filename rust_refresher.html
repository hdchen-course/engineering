Rust Refresher

Rust's distinctive model and the syntax around it — ownership, borrowing, lifetimes, sum types, the Option/Result error model, traits, iterators, and fearless concurrency — a tight brush-up for a programmer coming from another language

Ownership & move semantics — the core model

Rust has no garbage collector and no manual free. Instead, every value has exactly one owner; when the owner goes out of scope the value is dropped (its memory freed) automatically. Assigning or passing a value that lives on the heap moves ownership — the source binding is invalidated, and using it afterward is a compile error, not a runtime crash. Small, fixed-size types (integers, bool, char, f64) instead implement Copy: they are duplicated bit-for-bit, so the original stays valid.

let s1 = String::from("hello");
let s2 = s1;              // MOVE: the heap buffer now belongs to s2
// println!("{}", s1);   // would not compile — s1 was moved
println!("{}", s2);      // ok

let x = 5;
let y = x;               // i32 is Copy — x is still valid
println!("x={x} y={y}");   // inline captures (Rust 1.58+, all editions)
// → output:
hello
x=5 y=5

The rule "one owner, dropped at end of scope" is what lets Rust free memory deterministically without a GC and without free. Passing a value into a function moves it too — so a function signature tells you, at a glance, whether it consumes its argument (fn f(s: String)) or merely borrows it (fn f(s: &str), next section).

Use-after-move is caught at compile time (E0382)

Touching a binding after its value has moved is rejected by the compiler with a precise diagnostic — the whole class of use-after-free / double-free bugs is gone before the program ever runs.

let s1 = String::from("hello");
let s2 = s1;             // s1 moved into s2
println!("{}", s1);      // ← use after move
// → rustc output (does not compile):
error[E0382]: borrow of moved value: `s1`
 |
2 |     let s2 = s1;
 |              -- value moved here
3 |     println!("{}", s1);
 |                    ^^ value borrowed here after move
 = note: move occurs because `s1` has type `String`,
         which does not implement the `Copy` trait

Two escape hatches when you genuinely need both: s1.clone() makes a deep copy (explicit, so the cost is visible), or borrow instead of moving (&s1). Reach for clone() deliberately, not reflexively — an unnecessary .clone() to "make the borrow checker happy" is a common beginner smell.

Borrowing & references

Instead of moving a value, you can lend a reference to it. Two kinds exist, and the borrow checker enforces one iron rule between them: at any given time you may have either any number of shared references &T (read-only) or exactly one mutable reference &mut T (read-write) — never both. "Many readers XOR one writer" is what makes data races impossible.

let mut v = vec![1, 2, 3];
let r1 = &v;             // shared borrow
let r2 = &v;             // many shared borrows are fine
println!("{:?} {:?}", r1, r2);
let m = &mut v;         // exclusive borrow (r1/r2 no longer used)
m.push(4);
println!("{:?}", m);
// → output:
[1, 2, 3] [1, 2, 3]
[1, 2, 3, 4]

Since Rust 2018, borrows end at their last use, not at the end of the enclosing block ("non-lexical lifetimes"). That is why the shared borrows above can coexist with the later &mut v: r1 and r2 are done being read before m is created.

A shared and a mutable borrow at once won't compile (E0502)

let mut s = String::from("hi");
let r = &s;              // immutable borrow starts
let w = &mut s;          // ← mutable borrow while r is still live
println!("{r} {w}");       // both used here
// → rustc output (does not compile):
error[E0502]: cannot borrow `s` as mutable because it is
              also borrowed as immutable
 |
2 |     let r = &s;
 |             -- immutable borrow occurs here
3 |     let w = &mut s;
 |             ^^^^^^ mutable borrow occurs here
4 |     println!("{r} {w}");
 |               --- immutable borrow later used here

This is the rule people mean by "fighting the borrow checker." The fix is almost never clone() — it is to shorten a borrow (compute the read result, then mutate), split the data into disjoint pieces, or restructure so a value isn't read and written through two aliases simultaneously. The compiler is pointing at a real aliasing hazard.

Lifetimes — why they exist

A reference must never outlive the data it points to. A lifetime is the compiler's name for "the region of code during which a reference is valid"; annotations like 'a don't change how long anything lives — they relate the lifetimes of inputs and outputs so the compiler can prove no reference dangles. When a function returns a reference derived from its arguments, you often must say which argument it borrows from.

// 'a ties the result's lifetime to BOTH inputs:
// the returned &str lives no longer than the shorter of x, y.
fn longest<'a>(x: &'a str, y: &'a str) -> &'a str {
    if x.len() >= y.len() { x } else { y }
}

fn main() {
    let a = String::from("long string");
    let b = String::from("short");
    println!("{}", longest(&a, &b));
}
// → output:
long string

The check has teeth: dangling references are rejected

Returning a reference to a local is a classic C trap (a pointer to freed stack memory). Rust rejects it — there is no lifetime that could make it sound.

fn dangle() -> &String {   // no input to borrow from
    let s = String::from("oops");
    &s                        // s is dropped when the fn returns
}
// → rustc output (does not compile):
error[E0106]: missing lifetime specifier
error[E0515]: cannot return reference to local variable `s`
 |
3 |     &s
 |     ^^ returns a reference to data owned by the
 |        current function

Elision keeps most code annotation-free. When there is exactly one input reference, its lifetime is given to all output references automatically — so fn first_word(s: &str) -> &str needs no 'a. You only write lifetimes when the compiler genuinely can't tell which input an output borrows from (as in longest above). Most day-to-day Rust has none.

Structs, enums & pattern matching

structs group related data; enums are true sum types — a value is exactly one of several variants, and each variant can carry its own data. match destructures them and is exhaustive: the compiler forces you to handle every variant (or add a _ catch-all), so adding a case later can't be silently forgotten.

#[derive(Debug)]
struct Point { x: i32, y: i32 }

enum Shape {
    Circle(f64),               // tuple-like variant
    Rect { w: f64, h: f64 },     // struct-like variant
}

fn area(s: &Shape) -> f64 {
    match s {
        Shape::Circle(r) => std::f64::consts::PI * r * r,
        Shape::Rect { w, h } => w * h,
    }
}

fn main() {
    let p = Point { x: 1, y: 2 };
    println!("{:?}", p);          // Debug print via derive
    let shapes = [Shape::Circle(1.0),
                  Shape::Rect { w: 2.0, h: 3.0 }];
    for s in &shapes {
        println!("{:.3}", area(s));
    }
    let maybe = Some(7);
    if let Some(n) = maybe {   // match just one variant
        println!("got {n}");
    }
}
// → output:
Point { x: 1, y: 2 }
3.142
6.000
got 7

if let is sugar for a match with one interesting arm and an ignored rest — ideal when you care about a single variant. Its cousin while let loops until a pattern stops matching. When you do want the compiler to enforce total coverage, prefer a full match: add a variant to the enum and every non-exhaustive match becomes a compile error pointing you at what to update.

Option<T>, Result<T,E> & the ? operator

Rust has no null. Absence is modeled by the enum Option<T> = Some(T) | None, and recoverable failure by Result<T, E> = Ok(T) | Err(E). Because these are ordinary enums, the compiler forces you to acknowledge the empty / error case — you cannot accidentally dereference a "null." The ? operator makes propagation ergonomic: on Ok/Some it unwraps the value; on Err/None it returns early from the function with that error.

use std::num::ParseIntError;

fn parse_sum(a: &str, b: &str) -> Result<i32, ParseIntError> {
    let x: i32 = a.parse()?;   // ? returns early on Err
    let y: i32 = b.parse()?;
    Ok(x + y)
}

fn main() {
    match parse_sum("2", "40") {
        Ok(n)  => println!("sum = {n}"),
        Err(e) => println!("error: {e}"),
    }
    match parse_sum("2", "oops") {
        Ok(n)  => println!("sum = {n}"),
        Err(e) => println!("error: {e}"),
    }
    let v = vec![10, 20, 30];
    println!("{:?}", v.get(1));   // Some(20) — no panic
    println!("{:?}", v.get(9));   // None    — out of range
}
// → output:
sum = 42
error: invalid digit found in string
Some(20)
None

.unwrap() and .expect("…") extract the inner value but panic on None/Err — fine in tests, examples, and prototypes, a liability in production paths. Prefer ? to propagate, match/if let to handle, or .unwrap_or(default) / .unwrap_or_else(..) to supply a fallback. In real code, model your own error type (or use crates like anyhow/thiserror) and let ? convert into it.

Traits & generics

A trait is a set of behavior (like an interface); types impl it. Generics with trait bounds give you polymorphism with zero runtime cost — the compiler monomorphizes a specialized copy per concrete type (static dispatch). When you need a heterogeneous collection or to erase the type, a dyn Trait object dispatches through a vtable (dynamic dispatch).

trait Greet {
    fn hello(&self) -> String;
}
struct En;
struct Fr;
impl Greet for En { fn hello(&self) -> String { "Hello".into() } }
impl Greet for Fr { fn hello(&self) -> String { "Bonjour".into() } }

fn greet_static<T: Greet>(g: &T) { println!("{}", g.hello()); }  // bound
fn greet_impl(g: &impl Greet)   { println!("{}", g.hello()); }  // impl Trait
fn greet_dyn(g: &dyn Greet)    { println!("{}", g.hello()); }  // trait object

fn main() {
    greet_static(&En);
    greet_impl(&Fr);
    let langs: Vec<Box<dyn Greet>> = vec![Box::new(En), Box::new(Fr)];
    for l in &langs { greet_dyn(l.as_ref()); }
}
// → output:
Hello
Bonjour
Hello
Bonjour

Static vs dynamic: generics / impl Trait compile to concrete, inlinable code (fast, larger binary, type known at compile time); dyn Trait stores a pointer + vtable and resolves the method at run time (one code copy, needed when the concrete type varies at run time, e.g. a Vec<Box<dyn Trait>>). #[derive(Debug, Clone, PartialEq, …)] auto-implements common traits so you rarely write that boilerplate by hand.

Collections & iterators

The everyday collections are the growable Vec<T> and the HashMap<K, V>. Iterators are lazy and zero-cost: adapters like map, filter, and take build a pipeline that does nothing until a consumer such as collect, sum, or a for loop drives it — and the whole chain compiles down to roughly the same machine code as a hand-written loop.

use std::collections::HashMap;

fn main() {
    let nums = vec![1, 2, 3, 4, 5, 6];
    let evens_sq: Vec<i32> = nums.iter()
        .filter(|&&n| n % 2 == 0)   // keep evens
        .map(|&n| n * n)             // square them
        .collect();                    // materialize into a Vec
    println!("{:?}", evens_sq);
    let sum: i32 = nums.iter().sum();
    println!("sum = {sum}");

    let mut counts: HashMap<&str, i32> = HashMap::new();
    for w in ["a", "b", "a", "c", "b", "a"] {
        *counts.entry(w).or_insert(0) += 1;   // upsert
    }
    println!("a = {}", counts["a"]);
}
// → output:
[4, 16, 36]
sum = 21
a = 3

The entry(k).or_insert(default) pattern is the idiomatic "insert-or-update" — it avoids a double lookup and returns a &mut V you can modify in place. Note iter() yields shared references (&T); use into_iter() to consume the collection by value, or iter_mut() to get &mut T.

Strings: String vs &str

There are two string types for the same reason there are owned values and borrows. String is an owned, growable, heap-allocated buffer; &str is a borrowed slice — a view (pointer + length) into string data owned by someone else (a String, or a "literal" baked into the binary). Both are guaranteed UTF-8, which is why indexing is by byte offset, not character.

// Take &str at API boundaries: it accepts both a
// borrowed String and a literal without allocating.
fn shout(s: &str) -> String { s.to_uppercase() }

fn main() {
    let owned: String = String::from("héllo");
    let slice: &str = &owned[0..1];   // byte range, not char index
    println!("slice = {slice}");
    println!("bytes = {}, chars = {}",
             owned.len(), owned.chars().count());
    for c in "ab".chars() { print!("[{c}]"); }
    println!();
    println!("{}", shout(&owned));   // &String coerces to &str
}
// → output (é is 2 bytes in UTF-8: 6 bytes, 5 chars):
slice = h
bytes = 6, chars = 5
[a][b]
HÉLLO

Because indices are byte offsets, slicing in the middle of a multi-byte character (e.g. &owned[0..2] here, which would split the é) panics at run time — Rust won't hand you invalid UTF-8. Iterate with .chars() for Unicode scalar values or .bytes() for raw bytes; there is deliberately no s[i] integer indexing on strings.

API rule of thumb: accept &str (most flexible — a String derefs to it for free), return or store String when you need ownership. This mirrors the owned-vs-borrowed distinction from collections (Vec<T> vs &[T]).

Concurrency — data races caught at compile time

Rust's headline concurrency claim ("fearless concurrency") falls straight out of the ownership rules plus two marker traits. Send means a type is safe to move to another thread; Sync means it is safe to share by reference across threads. The compiler auto-derives them and refuses to compile a program that would share mutable state unsafely — a data race becomes a type error, not a Heisenbug.

To share mutable state across threads you combine two pieces: Arc<T> (atomically reference-counted shared ownership) around a Mutex<T> (mutual exclusion). This Arc<Mutex<T>> pattern is the standard building block.

use std::sync::{Arc, Mutex};
use std::thread;

fn main() {
    let counter = Arc::new(Mutex::new(0));
    let mut handles = vec![];
    for _ in 0..8 {
        let c = Arc::clone(&counter);   // bump refcount, share owner
        handles.push(thread::spawn(move || {
            let mut n = c.lock().unwrap();   // lock guard; unlocks on drop
            *n += 1;
        }));
    }
    for h in handles { h.join().unwrap(); }
    println!("total = {}", *counter.lock().unwrap());
}
// → output (deterministic — the Mutex serializes the increments):
total = 8

Try to remove the Arc/Mutex and share a plain &mut across threads, and the code simply won't compile — thread::spawn requires the borrowed data to outlive the thread (a 'static bound a stack borrow can't meet), and an exclusive &mut can't be aliased into more than one thread anyway. The lock guard returned by lock() releases the mutex automatically when it goes out of scope (RAII), so there is no "forgot to unlock" bug. For lock-free counters, std::sync::atomic types are the lighter-weight choice.

Common pitfalls (and their fixes)

1 · Fighting the borrow checker with clone()

The reflex when an E0502/E0382 appears is to sprinkle .clone() until it compiles. That works but hides the design: you're paying for a deep copy to dodge an aliasing question. Usually the right fix is to shorten a borrow — read what you need into a local, then mutate — or to split the data so the reads and writes touch disjoint parts. Clone when you genuinely need a second owned copy, not as a borrow-checker silencer.

2 · Moving out of a borrow

You can't take ownership of something you've only borrowed. Trying to move a field out of a & reference is rejected.

fn take(p: &(String, i32)) -> String {
    p.0                     // ← tries to MOVE the String out of a &borrow
}
// → rustc output (does not compile):
error[E0507]: cannot move out of `p.0` which is behind
              a shared reference

Fix by borrowing or copying the piece instead: &p.0, p.0.clone(), or p.1 (an i32 is Copy, so reading it is fine).

3 · Indexing vs .get()

Indexing a Vec out of range panics; .get() returns an Option you can handle. Prefer .get() whenever the index might be out of bounds.

let v = vec![1, 2, 3];
// v[10]  →  panics: "index out of bounds: the len is 3 but the index is 10"
match v.get(10) {
    Some(x) => println!("{x}"),
    None    => println!("no element at 10 (get returns None)"),
}
// → output:
no element at 10 (get returns None)

4 · unwrap() in production

Every .unwrap() / .expect() is a potential panic. They're perfectly idiomatic in tests and quick scripts, but on a request path they turn a recoverable Err into a crash. Propagate with ?, or handle explicitly. clippy can be configured to deny unwrap in a crate.

5 · String vs &str at API boundaries

Taking a String parameter forces every caller to hand over ownership (often an extra allocation via .to_string()). Take &str instead — a String coerces to it automatically, and so does a literal. Same idea for slices: prefer &[T] over &Vec<T>.

A meta-pitfall: treating the borrow checker as an adversary. Its errors are almost always pointing at a genuine ownership/aliasing question you haven't answered yet. The fastest way out of the "fighting" phase is to read the diagnostic (rustc's messages are unusually good, often with a suggested fix) and let it teach the model, rather than reaching for clone() / unwrap() / unsafe to make the red text disappear.

Tooling & editions

Rust ships a famously integrated toolchain. You install and switch versions with rustup, and almost everything else goes through cargo, the build tool and package manager.

CommandWhat it does
cargo new / cargo initScaffold a new project (or initialize the current directory).
cargo build / --releaseCompile (debug, fast build) or optimize (--release).
cargo runBuild then run the binary.
cargo testRun #[test] functions and doc-tests.

clippy catches idiom problems the compiler allows

Code can compile cleanly yet still be non-idiomatic. clippy flags those with an explanation and usually a fix.

// compiles fine, but clippy objects:
let v = vec![1, 2, 3];
if v.len() == 0 { println!("empty"); }
# → cargo clippy
warning: length comparison to zero
 |
 |     if v.len() == 0 {
 |        ^^^^^^^^^^^^ help: using `is_empty` is clearer
 |                    and more explicit: `v.is_empty()`
 = note: `#[warn(clippy::len_zero)]` on by default

Editions

An edition (2015, 2018, 2021, 2024) is an opt-in language epoch set per crate in Cargo.toml. It lets Rust make small breaking syntax changes — new keywords, new defaults — without splitting the ecosystem: crates on different editions interoperate, so upgrading is per-crate and never forced. For example, the 2018 edition added the async/await and dyn keywords and changed module-path rules; the 2021 edition made closures capture disjoint fields and arrays implement IntoIterator by value. (The inline "{var}" format captures used throughout this chapter are not edition-gated — they are a Rust 1.58+ compiler feature available in every edition.)

Interview angle. A strong "why Rust?" answer connects the pieces: ownership + borrowing give memory safety and data-race freedom with no garbage collector, checked at compile time; Option/Result replace null and exceptions with values the type system forces you to handle; traits + generics give zero-cost abstraction. The cost is a steeper learning curve and longer compiles — worth it where safety and predictable performance both matter (systems code, infrastructure, embedded, high-scale services).

Wire cargo fmt --check and cargo clippy -- -D warnings into CI, and install rust-analyzer in your editor for inline types, jump-to-definition, and quick fixes — it turns the compiler's rich diagnostics into a fast feedback loop while you type.
