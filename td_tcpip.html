TCP/IP & Packet Analysis — a Practical Deep-Dive

What actually happens on the wire when two programs talk: how a byte stream is wrapped into segments, packets, and frames; the exact layout of the IPv4, UDP, and TCP headers; how the 3-way handshake, teardown, reliability, flow control, and congestion control work; how ports, sockets, and NAT identify a connection; and how to read all of it with tcpdump and Wireshark. Every header field size and command flag below is checked against the RFCs.
Read this like a story

The sections build from "how does a byte stream become framed packets" up to "capture a handshake and spot a retransmission." If you already know the layered model, skip to §4 (the TCP header) and §5 (the handshake) — those, plus §7–8 on reliability and congestion control, are what interviewers actually probe. Header layouts are drawn to match RFC 791 (IPv4), RFC 768 (UDP), and RFC 9293 (TCP, which obsoletes the original RFC 793). This chapter is generic, public networking knowledge.

1. The Layered Model & Encapsulation

Two processes on different machines want to exchange bytes. Between "write() some bytes into a socket" and "electrons/photons on a link" sit a handful of layers, each adding its own header and each solving one problem: the link layer moves a frame across one physical hop, the internet layer (IP) routes a packet across many hops, the transport layer (TCP/UDP) gives processes a conversation, and the application layer (HTTP, DNS, …) gives that conversation meaning. This is the TCP/IP model — four layers, more practical than the 7-layer OSI reference model it is usually mapped onto.

The four TCP/IP layers

LayerUnitJobAddressing
ApplicationmessageWhat the bytes mean: HTTP, DNS, TLS, gRPCURLs, names
Transportsegment (TCP) / datagram (UDP)Process-to-process delivery; TCP adds reliability & orderingport numbers
Internetpacket (datagram)Route across networks, host to host, hop by hopIP addresses (32-bit v4 / 128-bit v6)
LinkframeMove a frame across one physical segmentMAC addresses

Encapsulation: how a byte stream becomes framed packets

Each layer treats the layer above as opaque payload and prepends its own header (the link layer also appends a trailer, e.g. an Ethernet CRC). Sending is wrap-wrap-wrap; receiving is the mirror — each layer strips its header and hands the payload up. The names people say ("segment," "packet," "frame") are just "the payload plus this layer's header."

Encapsulation: application bytes gain a TCP header (segment), then an IP header (packet), then an Ethernet header + CRC (frame). The receiver strips each header in reverse.

MTU: the size limit that shapes everything

A link imposes a Maximum Transmission Unit — the largest payload one frame may carry. On classic Ethernet that is 1500 bytes. IP must fit a packet inside the MTU; if a packet is too big it is either fragmented (IPv4, §2) or rejected so the sender can retry smaller. TCP avoids fragmentation by negotiating a Maximum Segment Size (MSS) — on a 1500-byte Ethernet MTU with 20-byte IPv4 and 20-byte TCP headers, that is 1500 − 20 − 20 = 1460 bytes of data per segment (§10 covers MTU/MSS/PMTUD in depth).

Model vs. reality

The 7-layer OSI model (physical, data-link, network, transport, session, presentation, application) is a teaching reference; real stacks are TCP/IP's four layers. When someone says "layer 4" they mean transport (TCP/UDP); "layer 7" means application (HTTP). Knowing the mapping — and that TLS lives between L4 and L7 — is enough.

2. The IPv4 Header

IP is the internet layer: it carries a packet from a source IP to a destination IP, hop by hop, with no delivery guarantee, no ordering, and no connection — it is best-effort. The IPv4 header (RFC 791) is 20 bytes without options and up to 60 bytes with them. Every row below is 32 bits (4 bytes) wide.

The IPv4 header (RFC 791). Each row is 32 bits. The first five 32-bit words (20 bytes) are the fixed header; the Options word appears only when IHL > 5.

The fields that matter in interviews

TTL (Time To Live)8 bitsDecremented by 1 at each router; at 0 the packet is dropped and an ICMP "time exceeded" is returned — this is exactly what traceroute exploits.

Fragmentation

If a packet is larger than the next link's MTU and DF is not set, an IPv4 router may fragment it: split the payload across several packets that share the same Identification, each with its Fragment Offset set (in 8-byte units) and MF=1 on all but the last. The destination reassembles them; a lost fragment loses the whole packet. If DF=1 and the packet is too big, the router drops it and returns ICMP "fragmentation needed" — the mechanism Path MTU Discovery relies on (§10).

A note on IPv6

IPv6 in one paragraph

IPv6 (RFC 8200) uses 128-bit addresses and a fixed 40-byte header. It drops the header checksum (trusting L2 and L4 to catch errors), removes in-network fragmentation (only the source may fragment, guided by PMTUD), and replaces variable options with a chain of extension headers via the Next Header field. Hop Limit replaces TTL; Traffic Class + Flow Label replace ToS. The transport layer above (TCP/UDP) is unchanged.

3. UDP — the Minimal Transport

UDP (RFC 768) is the thinnest possible transport: it adds ports (so bytes reach the right process) and an optional checksum, and nothing else. It is connectionless — no handshake, no acknowledgements, no ordering, no retransmission, no flow or congestion control. If you want any of those, you build them yourself on top. The header is exactly 8 bytes.

The UDP header (RFC 768): four 16-bit fields, 8 bytes total, followed immediately by the payload.

The four fields

  • Source Port / Destination Port (16 bits each) — which process sent it and which should receive it.
  • Length (16 bits) — the length of the UDP header plus data, so the minimum value is 8.
  • Checksum (16 bits) — computed over a pseudo-header (source/dest IP, protocol, UDP length), the UDP header, and the data. It is optional in IPv4 (a zero value means "not computed") but mandatory in IPv6.

When UDP is the right choice

UDP wins when low latency beats reliability, or when the app does its own reliability. Real-time media (voice/video) would rather drop a late packet than wait for a retransmit. DNS uses a single small request/response where a connection setup would dominate the cost. And QUIC — the transport under HTTP/3 — runs on top of UDP precisely so it can implement its own streams, ordering, and congestion control in user space without being locked into the kernel's TCP.

Interview signal

"TCP vs. UDP" is really "do I want the transport to handle reliability/ordering/flow control, or will the application?" Naming a concrete UDP user that rebuilds reliability itself (QUIC, or a game netcode layer) shows you understand it is a deliberate trade, not just "UDP is faster."

4. The TCP Header

TCP (RFC 9293, which obsoletes RFC 793) turns IP's unreliable packets into a reliable, ordered, connection-oriented byte stream. It does this with sequence numbers, acknowledgements, windows, and a set of control flags — all carried in a header that is 20 bytes without options and up to 60 bytes with them.

The TCP header (RFC 9293). Data Offset gives the header length in 32-bit words, exactly like IPv4's IHL. The Options word appears only when Data Offset > 5.

5. The 3-Way Handshake

Before any data flows, TCP opens a connection by synchronizing sequence numbers in both directions — three segments, hence "3-way." Each side picks a random Initial Sequence Number (ISN) and learns the other's. Randomizing the ISN (RFC 6528) matters for security: a predictable ISN lets an off-path attacker forge segments into the stream.

The 3-way handshake. Each SYN carries a random ISN and consumes one sequence number, so the reply acknowledges ISN + 1. After the third segment, both sides are ESTABLISHED.

Step by step

  1. SYN — the client picks ISN x, sends a segment with SYN set and seq = x, and moves CLOSED → SYN-SENT. The server was in LISTEN.
  2. SYN-ACK — the server picks its own ISN y, replies with SYN and ACK set, seq = y and ack = x + 1 (acknowledging the client's SYN), and moves LISTEN → SYN-RECEIVED.
  3. ACK — the client replies with ACK set, seq = x + 1, ack = y + 1, and moves to ESTABLISHED. When the server sees this ACK it too becomes ESTABLISHED.

Because SYN "consumes" one sequence number, the very next data byte the client sends has seq = x + 1. The same +1 rule applies to FIN at teardown.

Why three, not two

Two segments could open the connection in one direction, but TCP is full-duplex: both sides must announce and have their ISN acknowledged. The middle SYN-ACK serves two purposes — it acknowledges the client's SYN and carries the server's SYN — which is why the exchange collapses to three segments rather than four.

6. Connection Teardown

Closing is also sequenced, but because each direction of the stream closes independently it normally takes four segments (a FIN and an ACK each way). One side calls close() first — the active closer — but the other can keep sending until it closes too (a "half-close").

Four-segment teardown. The active closer ends in TIME-WAIT for 2·MSL before finally reaching CLOSED; the passive closer goes CLOSE-WAIT → LAST-ACK → CLOSED.

Why TIME_WAIT exists

After sending the final ACK, the active closer does not immediately vanish — it sits in TIME_WAIT for twice the Maximum Segment Lifetime (2·MSL; Linux fixes this at 60 s). This looks wasteful but does two essential jobs:

  • Guarantee the final ACK arrives. If that ACK is lost, the peer will retransmit its FIN; only a socket still in TIME_WAIT can answer with another ACK. Vanish too early and the peer is stuck in LAST-ACK, keeps retransmitting its FIN, and — finding no socket on the other side — gets an RST back.
  • Let old duplicates die out. Waiting 2·MSL ensures any straggling segments from this connection have expired in the network, so they cannot be misread as belonging to a new connection that happens to reuse the same 4-tuple.
TIME_WAIT is on the side that closes first

A server that initiates the close accumulates many sockets in TIME_WAIT under high connection churn, which can exhaust local ports. The fix is architectural — use persistent/keep-alive connections, or arrange for the client to close first — not to blindly shorten the timeout, which reintroduces the stale-segment hazard. Options like SO_REUSEADDR / tcp_tw_reuse help within safe limits.

RST — the abrupt close

A RST tears the connection down immediately, with no FIN/ACK exchange. It is sent when a segment arrives for a connection that does not exist (e.g. a SYN to a closed port, which yields RST), when an application sets SO_LINGER to 0, or when a stack gives up on a broken connection. In a capture, an unexpected RST mid-stream usually means one side crashed, a firewall injected it, or a process closed a socket that still had unread data.

7. Reliability & Flow Control

IP can drop, duplicate, or reorder packets. TCP layers reliability on top using sequence numbers (label every byte), acknowledgements (confirm receipt), retransmission (resend what wasn't acked), and a sliding window (keep many bytes in flight without waiting for each one).

Sequence numbers & cumulative ACK

Every byte in the stream has a sequence number. The receiver's Acknowledgment Number is cumulative: ack = N means "I have every byte up to N−1; send me N next." A single ACK therefore confirms a whole run of bytes, and a lost ACK is harmless if a later one covers the same range. If segments arrive out of order, the receiver buffers them but keeps ACKing the last in-order byte — producing duplicate ACKs that signal a gap.

Retransmission: timeout vs. fast

  • Retransmission Timeout (RTO). Each connection estimates the round-trip time and derives a timeout. Per RFC 6298 it keeps a smoothed RTT (SRTT) and its variation (RTTVAR) and sets RTO = SRTT + 4 × RTTVAR (with a 1 s floor). If an ACK doesn't arrive within the RTO, the segment is resent and the RTO is doubled (exponential backoff).
  • Fast retransmit. Waiting for a timeout is slow. If the sender receives three duplicate ACKs (RFC 5681) for the same sequence number, it infers that segment was lost and resends it immediately, without waiting for the RTO.
# RTO estimation (RFC 6298), per round-trip sample R'
RTTVAR = (1 − 1/4)·RTTVAR + (1/4)·|SRTT − R'| # computed first, using the old SRTT
SRTT = (1 − 1/8)·SRTT + (1/8)·R'
RTO = SRTT + 4 × RTTVAR # clamped to a 1 s minimum

The sliding window & flow control

To keep the pipe full, TCP allows many unacknowledged bytes "in flight" at once — up to the current window. As ACKs arrive, the window slides forward and new bytes may be sent. Flow control prevents a fast sender from overwhelming a slow receiver: every ACK advertises the receiver's free buffer space in the 16-bit Window field (the receive window, rwnd). The sender must never have more unacknowledged data outstanding than the smaller of the two limits:

bytes in flight ≤ min( rwnd , cwnd )
# rwnd = receiver's advertised free buffer (on the wire, flow control)
# cwnd = sender's congestion window (local, never transmitted — §8)
Zero window & the persist timer

If the receiving application stops reading, its buffer fills and it advertises a zero window — "send nothing more." The sender then stalls. To avoid deadlock if the later window-update ACK is lost, the sender runs a persist timer and periodically sends a 1-byte zero-window probe to re-elicit the current window. Seeing repeated TCP Zero Window then Window Update in a capture points squarely at a slow/stuck consumer, not the network.

SACK — acknowledge the holes

Plain cumulative ACKs can't say "I got 1–1000 and 2001–3000 but not 1001–2000." With Selective Acknowledgment (RFC 2018, negotiated on the SYN) the receiver reports the exact non-contiguous blocks it holds, so the sender retransmits only the missing 1001–2000 instead of everything after the gap. This is a big win on links with sporadic loss.

8. Congestion Control

Flow control protects the receiver; congestion control protects the network. The sender maintains a private congestion window (cwnd) — never sent on the wire — and treats packet loss as the network's signal that it is sending too fast. The standard algorithm (RFC 5681) has four intertwined phases.

Slow start → congestion avoidance

  • Slow start. Begin with a small initial window (commonly 10 MSS, RFC 6928) and increase cwnd by 1 MSS for every ACK — which roughly doubles it each RTT. Exponential growth probes for capacity quickly. It continues until cwnd reaches the slow-start threshold ssthresh or a loss occurs.
  • Congestion avoidance. Above ssthresh, growth turns linear: roughly +1 MSS per RTT. This is the cautious probing phase.

The AIMD idea

Together these give AIMD — Additive Increase, Multiplicative Decrease: grow the window by a constant each RTT while things are fine, but on loss halve it. Additive increase is gentle and fair; multiplicative decrease backs off hard enough to relieve congestion fast. Iterated across many flows, AIMD converges to a roughly fair, stable share of the link — the property that makes the internet's congestion control work at all.

# AIMD, per round trip
no loss: cwnd += 1 MSS # additive increase (linear)
on loss: cwnd = cwnd / 2 # multiplicative decrease
# timeout (worse than dup-ACKs) → ssthresh = cwnd/2, cwnd resets to 1 MSS, slow start again

Fast retransmit & fast recovery

How TCP reacts depends on how it learned of the loss. Three duplicate ACKs (fast retransmit, §7) mean packets are still flowing — mild congestion — so TCP does fast recovery: halve cwnd and continue in congestion avoidance rather than crashing back to slow start. A full timeout is a worse sign (nothing is getting through): ssthresh drops to half, cwnd resets to 1 MSS (the loss window), and slow start begins again.

Modern algorithms: CUBIC & BBR

Classic AIMD (Reno/NewReno) underuses fast, long-distance links. CUBIC — the Linux default — grows the window along a cubic curve of time-since-last-loss, filling high bandwidth-delay-product pipes far better while staying loss-based. BBR (developed at Google) takes a different approach: instead of treating loss as the signal, it models the path's bottleneck bandwidth and round-trip propagation time and paces sending to that estimate — which can sidestep the throughput collapse loss-based schemes suffer on links with random (non-congestion) loss. Naming CUBIC as today's default and BBR as the model-based alternative is the senior touch.

9. Ports, Sockets & NAT

The 4-tuple identifies a connection

A single server IP:port (say :443) handles thousands of simultaneous connections. What distinguishes them is the full 4-tuple: (source IP, source port, destination IP, destination port). (Include the protocol and it is a 5-tuple.) Two connections may share three of the four fields; as long as one differs, they are distinct entries in the kernel's connection table. A socket is the OS handle to one endpoint of such a connection.

# two browser tabs to the same server — same server side, different source ports
conn A: 10.0.0.5 : 51514 → 93.184.216.34 : 443
conn B: 10.0.0.5 : 51520 → 93.184.216.34 : 443
# identical dst IP:port; the source port disambiguates them

Ephemeral ports

Servers listen on well-known ports (80, 443, 22, 53…). The client's source port is an ephemeral port the OS picks from a high range for the life of the connection (IANA suggests 49152–65535; Linux defaults to roughly 32768–60999). Because a source port is 16-bit, one client IP can hold at most ~64K simultaneous connections to the same server IP:port — a real limit for busy proxies.

NAT / PAT

IPv4 addresses are scarce, so a home or office network shares one public IP via NAT (Network Address Translation). The common form is PAT (Port Address Translation, a.k.a. "NAT overload" or masquerading): the router rewrites each outbound packet's source IP+port to its public IP and a chosen port, records the mapping in a table, and reverses the rewrite on the replies.

# NAT/PAT rewriting an outbound connection
inside : 192.168.1.20 : 51514 → 93.184.216.34 : 443
# router rewrites source, stores the mapping
outside: 203.0.113.9 : 40001 → 93.184.216.34 : 443
# reply to 203.0.113.9:40001 is rewritten back to 192.168.1.20:51514

Why NAT complicates peer-to-peer

NAT mappings are created by outbound traffic and, for a strict NAT, only accept replies from the same remote endpoint. So two peers who are both behind NAT can't simply connect: neither has an inbound mapping the other can reach, and neither knows its own public IP:port. The workarounds are STUN (a peer asks a public server "what public IP:port do you see me as?"), hole punching (both peers send outbound packets at once so each NAT opens a mapping the other's packets then match), and, when those fail (symmetric NATs), TURN — relaying all traffic through a public server. This is exactly the machinery WebRTC's ICE framework orchestrates.

Interview signal

"How would two clients behind NAT talk directly?" is a common probe. The crisp answer: you can't rely on inbound connections, so use a rendezvous/signaling server plus STUN to discover public mappings, hole-punch to open them, and fall back to a TURN relay for symmetric NATs.

10. Packet Analysis in Practice

The theory above is only useful if you can see it. tcpdump (CLI capture) and Wireshark / tshark (GUI + CLI with deep dissection) let you watch handshakes, read flags, follow a stream, and spot retransmissions, resets, and zero-windows. Live capture needs root/admin privileges and is out of scope for this chapter — the commands below are the ones you would run on a host you own; the sequences they would produce are described, not fabricated.

tcpdump — a correct filter cheat-set

# --- capture basics ---
tcpdump -i eth0 -nn                     # -n: no DNS, -nn: no port-name lookup either
tcpdump -i any -nn -c 100               # all interfaces, stop after 100 packets
tcpdump -i eth0 -w capture.pcap         # write raw packets to a file (open later in Wireshark)
tcpdump -r capture.pcap -nn             # read/replay from a file
tcpdump -i eth0 -s0 -X                  # full snap length + hex/ASCII payload dump

# --- host / net / port filters (BPF syntax) ---
tcpdump -nn host 93.184.216.34          # traffic to OR from this host
tcpdump -nn src net 10.0.0.0/8          # source in this network
tcpdump -nn tcp port 443                # TCP on port 443, either direction
tcpdump -nn 'tcp port 443 and host 93.184.216.34'   # combine with and/or/not

# --- match by TCP flags (byte 13 of the TCP header) ---
tcpdump -nn 'tcp[tcpflags] & tcp-syn != 0'           # any SYN (includes SYN-ACK)
tcpdump -nn 'tcp[tcpflags] == tcp-syn'               # SYN only (a pure connection open)
tcpdump -nn 'tcp[tcpflags] & (tcp-syn|tcp-ack) == (tcp-syn|tcp-ack)'  # SYN-ACK
tcpdump -nn 'tcp[tcpflags] & tcp-rst != 0'           # resets
tcpdump -nn 'tcp[tcpflags] & tcp-fin != 0'           # FINs (orderly close)

The tcp-syn, tcp-ack, tcp-fin, tcp-rst, tcp-push, and tcp-urg names are tcpdump macros for the flag bits (0x02, 0x10, 0x01, 0x04, 0x08, 0x20) in the flags byte at TCP offset 13 — the same values from §4. tcp[tcpflags] and the older tcp[13] are interchangeable.

tshark / Wireshark — display filters

Capture filters (BPF, above) decide what is recorded; display filters decide what is shown from an already-captured set and are far richer because Wireshark has fully dissected each packet.

# tshark reads the same .pcap and applies a DISPLAY filter with -Y
tshark -r capture.pcap -Y 'tcp.flags.syn==1 && tcp.flags.ack==0'   # connection opens
tshark -r capture.pcap -Y 'tcp.analysis.retransmission'            # retransmits
tshark -r capture.pcap -Y 'tcp.analysis.zero_window'               # receiver stalled
tshark -r capture.pcap -Y 'tcp.analysis.duplicate_ack'             # the dup-ACKs before a fast retransmit
tshark -r capture.pcap -Y 'tcp.flags.reset==1'                     # RSTs

# follow one TCP stream's payload as text (stream index 0)
tshark -r capture.pcap -q -z follow,tcp,ascii,0

# live capture with a CAPTURE filter (-f), needs privileges
tshark -i eth0 -f 'tcp port 443'

The equivalents typed into the Wireshark GUI filter bar are identical: tcp.flags.syn==1, tcp.analysis.retransmission, tcp.analysis.zero_window, tcp.flags.reset==1. Right-click a packet → Follow → TCP Stream is the GUI form of the follow,tcp command.

Reading it: packet 1 is the pure SYN carrying the client's options (MSS, window scale, SACK-permitted); packet 2 is the combined SYN-ACK; packet 3 is the bare ACK that opens the connection. After this, data segments carry [PSH, ACK] and the sequence/ack numbers climb by the bytes exchanged.

Interview framing — probe Q&As

Q: Why does TIME_WAIT exist, and why is it on the closing side?
After the final ACK, the active closer waits 2·MSL for two reasons: so it can re-ACK a retransmitted FIN if that final ACK was lost, and so any stale segments from this connection expire before the 4-tuple could be reused. It sits on whichever side closed first, which is why a server that initiates closes can pile up TIME_WAIT sockets — the fix is keep-alive/persistent connections or having the client close, not just shrinking the timer.

Q: What is a SYN flood, and how do SYN cookies defend against it?
An attacker sends many SYNs with spoofed sources and never completes the handshake. Each half-open connection normally consumes an entry in the server's SYN backlog queue; flood it and legitimate SYNs are dropped. SYN cookies remove the need to store that state: the server encodes the connection parameters into the ISN it returns in the SYN-ACK and allocates nothing. Only when a valid final ACK comes back (echoing ISN+1) does it reconstruct and create the connection — so there is no queue to exhaust.

Q: Nagle vs. delayed ACK — why can they interact badly?
Nagle's algorithm (RFC 896) reduces tiny-packet overhead by holding a small write until the previously-sent data is ACKed. Delayed ACK (RFC 1122) holds an ACK up to ~200 ms hoping to piggyback it on a reply. Put them together on a request/response with small writes and each waits for the other: the sender withholds the next small segment until an ACK arrives, while the receiver delays that ACK — adding up to ~200 ms of latency. Disabling Nagle with TCP_NODELAY is the usual fix for latency-sensitive, small-message protocols.

Q: What problem does window scaling solve?
The Window field is only 16 bits, capping the receive window at 65535 bytes. On a high bandwidth-delay-product link (fast + long RTT) that is far less than one RTT's worth of data, so throughput is throttled by the window, not the link. The window scale option (RFC 7323), negotiated on the SYN, applies a left-shift of up to 14 to the advertised window, raising the ceiling to about 1 GiB so the pipe can be kept full.

Q: MTU vs. MSS vs. PMTUD?
MTU is the largest frame payload a link carries (1500 on Ethernet). MSS is the largest TCP segment payload, advertised on the SYN — MTU minus the IP and TCP headers (1460 for classic IPv4/Ethernet). Path MTU Discovery finds the smallest MTU along the whole path: the sender sets DF, and any router that can't forward without fragmenting drops the packet and returns ICMP "fragmentation needed" with the next-hop MTU, so the sender shrinks its segments. If those ICMP messages are filtered, PMTUD black-holes — large packets vanish silently — which is why an unhelpful firewall can cause "small requests work, big ones hang."

One-line summary

TCP/IP is a stack of headers each solving one problem: IP routes best-effort packets by 32-bit address; UDP adds only ports; TCP adds a reliable, ordered byte stream via sequence/ack numbers, a 3-way handshake, sliding-window flow control, and AIMD congestion control; ports and NAT identify and multiplex connections by 4-tuple; and tcpdump/Wireshark let you read every bit of it on the wire. Know the header field sizes from memory, be able to draw the handshake, and explain TIME_WAIT, SYN cookies, and PMTUD, and you can reason about almost any connectivity or performance question.

Terminology & Acronyms

Quick reference for the key terms in this chapter.

TermMeaning
MTU (Maximum Transmission Unit)Largest payload one link-layer frame may carry — 1500 bytes on classic Ethernet.
MSS (Maximum Segment Size)Largest TCP segment payload a side accepts, advertised on the SYN — 1460 on Ethernet.
IHL (Internet Header Length)IPv4 header length in 32-bit words: 5 (20 bytes) to 15 (60 bytes).
DSCP (Differentiated Services Code Point)6-bit field marking a packet's QoS class; upper part of the former ToS byte.
ECN (Explicit Congestion Notification)2 bits letting routers signal congestion without dropping packets; paired with TCP's CWR/ECE flags.
TTL (Time To Live)Hop counter decremented at each router; at 0 the packet is dropped — how traceroute works.
PMTUD (Path MTU Discovery)Finds the smallest MTU along a path using DF and ICMP "fragmentation needed" replies.
SACK (Selective Acknowledgment)Lets a receiver acknowledge non-contiguous blocks so the sender resends only the true gaps (RFC 2018).
ISN (Initial Sequence Number)Randomized sequence number each side picks on its SYN when opening a connection.
MSL (Maximum Segment Lifetime)Assumed maximum time a segment survives in the network; TIME_WAIT lasts 2·MSL.
RTO (Retransmission Timeout)Time to wait for an ACK before resending; derived from RTT (RFC 6298).
rwnd (receive window)Receiver's advertised free buffer space, carried in the TCP Window field (flow control).
cwnd (congestion window)Sender's private limit on unacknowledged bytes, never sent on the wire (congestion control).
AIMD (Additive Increase, Multiplicative Decrease)Grow the window linearly while healthy, halve it on loss — the basis of TCP fairness.
BBR (Bottleneck Bandwidth and Round-trip propagation time)Model-based congestion control (developed at Google) that paces to estimated bandwidth rather than reacting to loss.
NAT (Network Address Translation)Rewrites packet addresses so a private network shares one public IP.
PAT (Port Address Translation)NAT variant that also rewrites ports, multiplexing many hosts behind one IP ("NAT overload").
STUN (Session Traversal Utilities for NAT)Lets a peer discover the public IP:port a NAT maps it to.
TURN (Traversal Using Relays around NAT)Relays all traffic through a public server when direct NAT traversal fails (symmetric NATs).
BPF (Berkeley Packet Filter)The filter syntax tcpdump uses to select which packets to capture.
