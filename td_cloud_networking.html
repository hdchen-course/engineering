Cloud & Data-Center Networking: Multi-Tenant Overlays, BGP & Network Automation

1. Why Cloud Networking Is Its Own Problem

In a single-tenant world, "the network" is plumbing: cables, switches, and IP addresses you mostly ignore. In a cloud, the network is the product. One physical fabric must simultaneously host thousands of tenants who each believe they own a private network — with overlapping IP ranges, their own subnets and firewall rules, and zero visibility into each other. That is the same multi-tenancy problem a database solves with per-tenant schemas or row-level isolation, except now it must hold at line rate for every packet.

The three forces: scale, isolation, and change

  • Scale. A large data center is hundreds of thousands of servers, each with multiple virtual machines or containers, each with one or more virtual NICs. The number of endpoints dwarfs anything a traditional enterprise network was designed for, and east-west (server-to-server) traffic vastly exceeds north-south (in/out of the building).
  • Isolation. Tenant A must never see tenant B's packets, even though both ride the same wires and may use the same 10.0.0.0/8 addresses. Isolation must be enforced in the data path, not by trust.
  • Change. Endpoints appear and vanish constantly as VMs and containers are scheduled. A control plane driven by humans typing on switches cannot keep up; the network's desired state has to be described in code and continuously reconciled.

"The network became software"

The response to all three forces is the same: move intelligence off fixed-function hardware and into software you can program, version, and automate. The physical switches become a fast, simple underlay whose only job is to move IP packets between servers. Everything a tenant cares about — their virtual network, addresses, routing, and policy — lives in a software-defined overlay built on top. This split is the single most important idea in the chapter, and every later section is a consequence of it.

Bridge from what you know

An overlay network is a per-tenant namespace over shared infrastructure — exactly like multi-tenancy in a database or the way a VPC gives each customer a private view of a shared cloud. Encapsulation (the next big idea) is the network's version of tunneling one tenant's traffic inside the provider's own packets, much like a per-tenant VPN. If you can hold "shared physical substrate, per-tenant virtual view, reconciled by a control loop" in your head, you already understand the shape of cloud networking.

2. The Data-Center Fabric: Clos / Spine-Leaf

Before any overlay exists, packets need a physical network to cross. Modern data centers almost universally build that underlay as a Clos fabric — a multi-stage network first described by Charles Clos in 1953 for telephone switching — realized today as a spine-leaf (a folded fat-tree) topology.

Leaves, spines, and why not a big core switch

Every server connects to a leaf switch (the top-of-rack, or ToR). Every leaf connects to every spine switch; leaves never connect to leaves, and spines never connect to spines. The result: any server reaches any server on a different rack in the same number of hops — leaf → spine → leaf (two servers on the same leaf stay local and are even closer) — so inter-rack latency is uniform and predictable, and there is no single congested "core."

The older design put a giant, expensive chassis switch at the center of a tree. That "big-iron core" is a scaling dead end: it is a single failure domain, it can only be upgraded by replacing the whole box (a "forklift upgrade"), and it caps total bandwidth at what one box can switch. Spine-leaf instead scales horizontally — need more bandwidth between racks? add spines. Need more racks? add leaves. It is built from many identical, cheap, fixed-function switches, which is exactly the commodity-hardware, scale-out philosophy backend engineers know from stateless service fleets.

A spine-leaf (folded fat-tree) Clos fabric. Servers attach to leaf (ToR) switches; each leaf connects to every spine. Bandwidth scales by adding spines; capacity by adding leaves.

ECMP: many equal paths at once

Because a leaf reaches every other leaf through any spine, there are multiple equal-cost paths for every flow. ECMP (Equal-Cost Multi-Path) spreads traffic across them. A switch hashes each packet's flow tuple — typically the 5-tuple (source IP, destination IP, protocol, source port, destination port) — and picks an uplink from that hash. Hashing on the flow keeps every packet of a given flow on one path (so no reordering), while different flows spread across all spines. This is how a fabric aggregates many modest links into enormous bisection bandwidth (the total bandwidth available between the two halves of the fabric — a measure of how much any-to-any traffic it can carry at once).

Oversubscription

# oversubscription ratio at a leaf oversubscription = (downlink bandwidth to servers) : (uplink bandwidth to spines) # e.g. 48 server ports at 25G = 1200G down, 8 uplinks at 100G = 800G up 1200G : 800G = 1.5 : 1 # 1.5x oversubscribed

A leaf usually has more capacity facing its servers than facing the spines, because not every server bursts at once. The oversubscription ratio quantifies that bet. 1:1 is non-blocking (full line rate even if everyone bursts) but expensive; 3:1 or higher is common where traffic is bursty and averages low. Getting this ratio wrong is a classic capacity-planning failure: too aggressive and the fabric congests under load; too conservative and you have paid for idle optics.

Bridge from what you know

ECMP across spines is load balancing — the same idea as spreading requests across a stateless service fleet, but done per-packet-flow in hardware. Oversubscription is capacity planning under statistical multiplexing: you provision for the aggregate, not the sum of worst cases, exactly like sizing a connection pool or a thread pool.

3. Underlay vs Overlay & Encapsulation

The fabric of §2 moves IP packets between servers. But tenants want their own networks — their own L2 segments, their own IP ranges, isolated from everyone else. The answer is to run a virtual network on top of the physical one. The physical IP network is the underlay; each tenant's virtual network is an overlay; the glue between them is encapsulation.

The core trick: a packet inside a packet

When a VM sends a frame, the software switch on its host does not put that frame on the wire as-is. It encapsulates it — wraps the tenant's original ("inner") frame inside a new ("outer") IP/UDP packet addressed from this host to the destination host. The underlay only ever sees the outer packet and routes it like any other IP traffic; it neither knows nor cares about the tenant frame hidden inside. At the destination host, the software switch strips the outer header (decapsulation) and delivers the original frame to the target VM. The two hosts form the endpoints of a tunnel — commonly called VTEPs (VXLAN Tunnel Endpoints).

This is the mechanism that delivers multi-tenancy: a tenant identifier carried in the encapsulation header tells the receiving host which virtual network the inner frame belongs to, so two tenants can use the identical 10.0.0.5 address and never collide — their packets carry different tenant IDs and are decapsulated into different virtual networks.

VXLAN — the go-to standard

VXLAN (Virtual Extensible LAN, RFC 7348) encapsulates an Ethernet frame inside UDP (destination port 4789). Its tenant identifier is the VNI (VXLAN Network Identifier), which is 24 bits wide — allowing roughly 16 million segments, versus the mere 4094 usable VLANs of the old 12-bit 802.1Q tag. That jump from ~4K to ~16M is the whole reason VXLAN exists: VLANs simply cannot number a hyperscale multi-tenant cloud.

VXLAN packet layout: the tenant's original Ethernet frame is wrapped in outer Ethernet + IP + UDP + an 8-byte VXLAN header carrying the 24-bit VNI. Total added overhead is about 50 bytes for IPv4.

Geneve — the extensible successor

Geneve (Generic Network Virtualization Encapsulation, RFC 8926) was designed to fix VXLAN's rigidity. VXLAN's header is fixed: 24 bits of VNI and little else. Geneve adds a variable-length options field built from TLVs (Type-Length-Value), so control planes can attach metadata — security tags, telemetry, service-chaining hints — to each packet without inventing a new protocol. Geneve also runs over UDP (assigned port 6081) and carries a 24-bit VNI, but its extensibility is why many modern SDN stacks and DPUs default to it.

GRE and FoU, briefly

GRE (Generic Routing Encapsulation) is the older, simpler tunnel: it wraps almost any payload directly in IP (protocol number 47) with a small header and an optional 32-bit key. It predates the multi-tenant cloud and is common for point-to-point tunnels. Its weakness in a Clos fabric is that it is not UDP, so ECMP hardware — which hashes on UDP/TCP ports — sees no port entropy and tends to pin all GRE traffic to a single path. FoU (Foo-over-UDP) fixes exactly that: it wraps GRE (or another protocol) inside UDP so the outer UDP source port can be varied per flow, restoring ECMP spread. This "wrap it in UDP so ECMP works" motivation is the same reason VXLAN and Geneve chose UDP in the first place.

The MTU / PMTUD caveat — a classic trap

Common mistake — the encapsulation MTU black hole

Every ~50 bytes of VXLAN/Geneve overhead comes out of the underlay's MTU. If the underlay MTU is 1500 and a tenant sends a full 1500-byte frame, the encapsulated packet is ~1550 bytes — too big. If the "don't fragment" bit is set (as it is for most TCP), a router drops it and should return an ICMP "fragmentation needed" message so the sender lowers its packet size — this is Path MTU Discovery (PMTUD). But cloud fabrics and firewalls frequently block that ICMP, so the sender never learns; large packets vanish silently while small ones (pings, TCP handshakes) succeed. The signature is maddening: "the connection opens but hangs on the first big transfer." The fix is to raise the underlay to jumbo frames (e.g. 9000-byte MTU) so encapsulation fits with room to spare, and/or clamp the tenant TCP MSS so inner segments stay small enough after wrapping. This one is a strong probe because it tests whether you actually understand encapsulation overhead.

Bridge from what you know

Encapsulation is tunneling: the tenant packet is the "message," the outer header is the "envelope," and the fabric is a courier that only reads the envelope. It is conceptually identical to a per-tenant VPN, or to wrapping an application message in an RPC/HTTP frame — a header the transport understands, carrying an opaque payload the transport ignores.

4. BGP in the Data Center

The fabric can forward packets, and overlays can carry tenants — but something has to tell every switch and host where every address lives. That job belongs to a routing protocol, and the modern data center has largely standardized on one: BGP (Border Gateway Protocol), the same protocol that stitches the public internet together, repurposed for the inside of a building.

BGP as distributed reachability

BGP is fundamentally a way for routers to advertise "I can reach these prefixes" to their neighbors, who re-advertise onward. Think of it as a controlled gossip of reachability that converges on a consistent picture of the network — a distributed agreement about who can reach what, built from peer-to-peer announcements rather than a central authority. Each router applies policy to decide which advertisements to accept, prefer, and propagate.

eBGP vs iBGP

  • eBGP (external BGP) runs between routers in different autonomous systems (ASes). It is the internet's inter-domain protocol, and in the data center it is the popular choice for the fabric: each leaf and each spine is given its own AS number, and every leaf-spine link is an eBGP session. eBGP's loop prevention (it rejects routes whose AS-path already contains its own AS) and its natural per-hop behavior make it clean for a Clos fabric.
  • iBGP (internal BGP) runs between routers within the same AS. iBGP has a catch: to prevent loops it does not re-advertise a route learned from one iBGP peer to another iBGP peer, so a naive iBGP network needs a full mesh of sessions between all routers — which explodes at scale.

Route reflectors

The fix for the iBGP full-mesh explosion is a route reflector: a designated router that is allowed to re-advertise (reflect) iBGP routes between clients, so each router peers only with the reflector instead of with every other router. It turns an O(n²) mesh into an O(n) hub-and-spoke of control-plane sessions. (In pure-eBGP fabric designs there is no full-mesh problem to solve, so reflectors appear more often in the overlay/EVPN control plane described below.)

ECMP comes for free

Because a leaf learns the same destination prefix from every spine with an equal AS-path length, BGP installs all of those next-hops and the fabric load-balances across them via ECMP (§2). With a unique AS number per switch, the paths differ in AS-path content, so this needs multipath-relax (accept equal-length paths even when the AS numbers differ) — or a design where every spine shares one AS so the paths are truly identical and multipath works by default. Routing protocol and load balancing become the same mechanism.

BGP to the host

A striking modern pattern is running BGP all the way down to the server. The host runs a lightweight BGP speaker and peers with its ToR leaf, advertising the addresses it owns — including the virtual IPs of the services or containers it hosts. When a container moves, the new host simply advertises that address and the old one withdraws it; the fabric reconverges with no manual reconfiguration. This makes service and pod mobility a routing event rather than an orchestration special-case, and it is why "BGP to the host" shows up constantly in container-networking designs.

MP-BGP / EVPN — the VXLAN control plane

VXLAN (§3) defines how to encapsulate, but not how a VTEP learns which remote host owns which tenant MAC/IP. The early answer was flood-and-learn (multicast the unknown traffic and learn from replies) — noisy and hard to scale. The modern answer is EVPN (Ethernet VPN) carried over MP-BGP (Multiprotocol BGP).

MP-BGP extends BGP to carry address families beyond plain IPv4 routes. EVPN is one such family: it lets every VTEP advertise, via BGP, the tenant MAC and IP addresses sitting behind it, tagged with their VNI. Now a VTEP learns all remote endpoints from BGP updates — a proper control plane — instead of flooding. This MP-BGP/EVPN as the control plane for VXLAN combination is the backbone of the standards-based multi-tenant data center.

# the clean separation EVPN gives you data plane = VXLAN encapsulation (how bytes are wrapped & tunneled) control plane = MP-BGP / EVPN (how VTEPs learn remote MAC/IP ↔ VNI ↔ host)

A note on internet-edge BGP

The same protocol also does its original job at the edge: the routers connecting the data center to the outside world speak eBGP with other providers to exchange internet reachability. This is where route leaks and hijacks live — accidentally (or maliciously) advertising prefixes you shouldn't, drawing in traffic that isn't yours. Google's publicly documented Espresso edge and B4 WAN work are well-known examples of applying SDN principles (§5) to this edge/WAN routing at scale, moving path selection into software rather than leaving it purely to per-router BGP policy.

Bridge from what you know

BGP is eventually consistent, policy-driven reachability gossip: peers exchange "I can reach X," apply local policy, and converge — much like an anti-entropy/gossip protocol converging on membership, but for routes. EVPN then uses that same distribution mechanism as a publish/subscribe bus for endpoint locations, exactly the way a service mesh uses a control plane to tell every proxy where every service instance currently lives.

5. Network Virtualization & SDN

Everything so far implies a division of labor that deserves its own name. Software-Defined Networking (SDN) is the deliberate separation of the control plane (the logic that decides where traffic should go) from the data plane (the fast machinery that actually forwards packets).

Control plane vs data plane

  • Data plane (forwarding plane). Per-packet work: match this packet against a table, rewrite headers, encapsulate, forward, drop, count. It must run at line rate, so it lives in ASICs, NIC/DPU hardware, or tightly optimized software switches.
  • Control plane. The decision-making: compute routes, program the forwarding tables, distribute tenant/endpoint state, enforce policy. It can run in general-purpose software — even centrally — because it operates at the timescale of changes, not of individual packets.

Traditional networking baked both planes into every switch, each running its own distributed routing algorithm. SDN pulls the control plane out into software — often a logically centralized SDN controller — that has a global view and programs the many simple, fast data-plane elements beneath it. This is the same architectural move as separating a database's query planner from its storage engine, or a scheduler's placement logic from the nodes that run the work.

VRFs: many routing tables in one box

A VRF (Virtual Routing and Forwarding) instance is an independent routing table living inside a single physical router or host. Each tenant gets its own VRF, so tenant A's routes are invisible to tenant B even on shared hardware — the routing-table equivalent of the per-tenant isolation encapsulation provides in the data path. VRFs plus VXLAN/EVPN are how a shared fabric presents each tenant a fully private L3 network.

Programmable data planes

The data plane itself has become programmable. Languages and interfaces for describing packet-processing pipelines let engineers define how a switch or NIC parses and acts on packets rather than accepting fixed vendor behavior — pushing new encapsulations, telemetry, or load-balancing logic into the hardware fast path. Combined with a software control plane, this makes the entire network a programmable, testable system rather than a box of static configuration.

A public reference point: network virtualization at scale

Google's publicly published Andromeda is a well-documented example of a large network-virtualization stack: it provides each tenant a virtual network over a shared physical fabric, doing the encapsulation, virtual routing, firewalling, and load balancing largely in software on the hosts, orchestrated by a centralized control plane — with a deliberate design principle of moving as much per-packet work as possible onto a fast path (and, increasingly across the industry, offloading that fast path to hardware, §7). It is a useful concrete illustration of the control/data-plane split applied to multi-tenant networking; Google's Jupiter data-center fabric papers similarly document the Clos-fabric ideas of §2 at hyperscale.

Bridge from what you know

The SDN controller reconciling forwarding tables against a desired network state is precisely a Kubernetes-style controller reconciling actual pods against a desired spec — a control loop watching declared intent and driving the data plane toward it. Hold that analogy; §8 makes it the center of the job.

6. Secure Communication in the Fabric

Isolation (§3) keeps tenants from seeing each other's packets, but it does not make the packets confidential or authenticated against a compromised host, a rogue admin, or a tapped link. For that you need cryptography, and two families dominate: mutual TLS at the application layer and IPsec at the network layer.

Mutual TLS (mTLS)

Ordinary TLS authenticates the server to the client (the padlock in a browser). Mutual TLS makes both ends present certificates, so the client authenticates the server and the server authenticates the client. In a service mesh, every service has an identity (a certificate), and every connection is mutually authenticated and encrypted — a workload cannot talk to another workload without proving who it is. mTLS operates per-connection at the application/transport boundary, is identity-aware (the certificate names the workload), and is the natural fit for service-to-service traffic.

IPsec

IPsec secures IP packets themselves, below the application, and is the standard for network-to-network or host-to-host tunnels (site-to-site VPNs, encrypting overlay traffic across an untrusted underlay or WAN). Its pieces are worth knowing precisely:

  • ESP (Encapsulating Security Payload) provides encryption plus integrity/authentication of the payload. This is what you almost always use, because it actually encrypts.
  • AH (Authentication Header) provides integrity and authentication but no encryption. It is largely of historical interest — it also breaks with NAT because it authenticates parts of the IP header that NAT rewrites.
  • IKE (Internet Key Exchange) is the handshake that authenticates the peers and negotiates the keys and parameters (the "security associations") that ESP/AH then use. IKE is the control plane; ESP is the data plane.

Transport mode vs tunnel mode — get this right

Transport modeTunnel mode
What's protectedOnly the IP payload; the original IP header stays exposed.The entire original IP packet, header and all, is encrypted and wrapped in a new outer IP header.

Common mistake

Confusing "tunnel vs transport" with "ESP vs AH." They are orthogonal: mode (transport/tunnel) decides how much of the packet is protected and whether a new outer header is added; protocol (ESP/AH) decides what protection (encryption+auth vs auth-only). You pick one from each column — e.g. "ESP in tunnel mode" is the classic site-to-site VPN.

Which one, and where

Reach for mTLS when…
  • Securing service-to-service (east-west) app traffic.
  • You want per-workload identity, not just an encrypted pipe.
  • Policy is "which service may call which," enforced with certificates.
Reach for IPsec when…
  • Encrypting whole networks or the overlay across an untrusted underlay/WAN.
  • Endpoints are gateways/hosts, and apps are unaware of crypto.
  • You need transparent, application-agnostic packet encryption.

They are not mutually exclusive — a cloud commonly runs mTLS between services and encrypts inter-data-center links with IPsec (or link-layer encryption). Both are the cryptographic backbone of zero trust: the network location of a peer grants it nothing; every connection must be authenticated and encrypted regardless of which side of any perimeter it is on. That is the bridge from "isolation by topology" to "trust by verified identity."

Isolation stops tenants from seeing each other's packets; it doesn't make a packet trustworthy. So I'd layer identity on top — mTLS for service-to-service, where I want per-workload certificates and policy, and IPsec (ESP, tunnel mode) to encrypt overlay or inter-site links transparently. Under zero trust, network position grants nothing; every hop is authenticated.

7. Host Networking & Hardware Offload

All the encapsulation, virtual routing, firewalling, and crypto above has to happen somewhere for every packet entering and leaving a server. Do it on the host CPU and you burn cores that customers are paying to run their workloads, and you add latency and jitter. The modern answer is to push that work down into the network hardware. This section follows the packet's path onto the wire and the offloads along the way.

The NIC datapath and SR-IOV

A NIC (Network Interface Card) traditionally hands packets to the OS kernel, which copies and processes them before the application sees them. In a virtualized host that means the hypervisor's software switch touches every packet — flexible but CPU-hungry.

SR-IOV (Single-Root I/O Virtualization) lets one physical NIC present itself as many. It exposes one PF (Physical Function) — the full-featured device the host manages — and many lightweight VFs (Virtual Functions), each of which can be assigned directly to a VM or container. That VM's packets flow straight between its VF and the wire, bypassing the hypervisor software switch entirely — near-bare-metal throughput and latency. The trade-off: the packet skips the host's software switch, so the overlay/policy work that switch used to do must now be done somewhere else — which is exactly the case for a smarter NIC.

The DPU / SmartNIC

A DPU (Data Processing Unit) — also called a SmartNIC — is a NIC with its own general-purpose CPU cores, memory, and programmable packet-processing engines. It runs the host's networking data plane on the card instead of on the host CPU: VXLAN/Geneve encapsulation, the virtual switch and firewall rules, load balancing, telemetry, and encryption are all offloaded. The host CPU is freed to run tenant workloads, and — importantly for a cloud provider — the networking/security software runs on the DPU in a domain the tenant's compromised VM cannot reach.

NVIDIA's BlueField DPU is a public, concrete example of this class of device; NVIDIA's ConnectX is the corresponding high-speed NIC line and Spectrum the Ethernet switch line. Naming them is just to make the category tangible — the concept (offload the data plane off the CPU onto a programmable NIC) is general.

Bridge from what you know

A DPU is the network's version of offloading blocking work off your main thread: the host CPU is the application thread, and the DPU is a dedicated I/O co-processor / sidecar that handles packets asynchronously so the CPU never blocks on them. "Move the data plane off the CPU" is the same instinct as async I/O, a sidecar proxy, or a dedicated I/O thread pool.

RDMA and RoCEv2 — the GPU-cluster fast path

Training large models needs GPUs across many servers to exchange gradients constantly, and the network can easily become the bottleneck. RDMA (Remote Direct Memory Access) lets one machine read/write another machine's memory directly, with the NICs doing the transfer and the CPU and OS kernel out of the loop — zero-copy, kernel-bypass, ultra-low latency. RoCEv2 (RDMA over Converged Ethernet, version 2) carries RDMA over a routable UDP/IP Ethernet network, so it runs across an ordinary IP Clos fabric.

RDMA was born on lossless fabrics and performs badly if packets are dropped, so RoCEv2 needs the Ethernet fabric to behave as near-lossless. Three mechanisms cooperate:

  • PFC (Priority Flow Control, 802.1Qbb) lets a congested switch tell the upstream sender to pause a specific traffic class rather than dropping its packets — per-priority backpressure so RDMA traffic isn't lost.
  • ECN (Explicit Congestion Notification) lets switches mark packets (instead of dropping them) as congestion builds, signaling the endpoints to slow down before queues overflow.
  • DCQCN (Data Center Quantized Congestion Notification) is the end-to-end congestion-control algorithm for RoCEv2 that reacts to those ECN marks, ramping each flow's rate up and down to hold the fabric just below the loss point. PFC is the emergency brake; ECN+DCQCN is the smooth throttle that keeps you from needing it.

On top of RDMA, GPUDirect RDMA lets the NIC move data straight into and out of GPU memory without a bounce through host RAM, and collective-communication libraries such as NCCL use these paths to implement fast all-reduce/all-gather across a cluster. This is the networking half of the interconnect story in Part XV · Chapter 4; the fabric here (RoCEv2 over Clos, made lossless by PFC/ECN/DCQCN) is what those collectives run on.

Why lossless is hard

PFC prevents drops but introduces its own hazards at scale — pause frames can propagate backward and cause congestion spreading or even PFC deadlock across a topology. Tuning ECN thresholds and DCQCN so the fabric rarely has to fire PFC is a genuinely hard operational problem, and a good signal in an interview that you understand the trade-off rather than just the acronyms.

Provisioning and host security (tie-ins)

Before a host can join the fabric it must be brought up and trusted. Provisioning typically bootstraps over the network: DHCP hands the machine an address and boot info, PXE network-boots an installer, and Redfish gives a standardized out-of-band API to the server's management controller for power, firmware, and boot control — the mechanics covered in Part XV · Chapter 1.

Trust is established by a chain of measured or verified boot steps:

  • Secure Boot verifies each stage of the boot chain against signatures before executing it, so unsigned/modified firmware or bootloaders won't run — a static, signature-based root of trust.
  • TPM (Trusted Platform Module) is a hardware chip that stores keys and accumulates measurements (hashes) of the boot components into PCRs, enabling remote attestation — a host can prove to a control plane what software it actually booted.
  • DRTM / measured launch establishes a dynamic root of trust: it can measure and launch a trusted environment at runtime, from a known hardware-enforced starting point, without depending on every earlier boot stage being trusted. The distinction worth knowing: Secure Boot is a static chain verified from power-on, whereas DRTM creates a fresh, measured trust anchor at launch time (a "late launch"), reducing how much earlier code you must trust.

8. Network & Systems Automation

This is the part a cloud-platform engineer actually lives in. A fabric with hundreds of switches, thousands of hosts, and constantly churning tenant state cannot be operated by logging into devices and typing. The network must be described as data and driven by software loops — and doing that safely across a shared, multi-tenant fabric is the core of the job.

Intent / declarative configuration

The foundational shift is from imperative ("SSH to switch, run these commands") to declarative / intent-based configuration: you describe the desired end state — these tenants, these VNIs, these routes, this policy — and let a system compute and apply the steps to get there. This is infrastructure as code (IaC) for the network: the desired state lives in version control, is code-reviewed, and is the single source of truth.

The reconciliation loop

Declared intent is only half of it; something must continuously make reality match. A reconciliation loop repeatedly (1) reads desired state, (2) reads observed/actual state from the devices, (3) computes the diff, and (4) applies the minimum changes to converge — then repeats forever, correcting drift whenever reality wanders (a switch reboots to defaults, someone makes a manual change, a device is replaced).

# the network control loop, in pseudocode — a reconciler
while True:
    desired = load_intent()          # from version-controlled source of truth
    actual  = fetch_device_state()   # stream telemetry / read configs
    diff    = compute_diff(actual, desired)
    if diff:
        if validate(diff):           # dry-run / model-check BEFORE touching prod
            apply_incrementally(diff, canary=True)   # small blast radius first
        else:
            alert("intent rejected by validation")
    sleep(interval)                  # steady-state drift correction
Bridge from what you know

This is exactly a Kubernetes controller: watch desired spec, observe actual, reconcile the difference, loop. The network is just another resource whose "pods" are VNIs, routes, and ACLs. If you have written or reasoned about a controller/operator, you already understand fabric automation — the control theory is identical, only the nouns change.

Network state machines & safe rollout

A shared fabric multiplies the blast radius: one bad push can black-hole traffic for many tenants at once. So the automation is built around safety, not just convenience:

  • Config validation before apply. Model or dry-run the change against a representation of the network to catch a route leak, a loop, or a lost prefix before it reaches hardware — the network equivalent of a type-checker and unit tests in CI.
  • Staged / canary rollout. Apply to one device, one rack, one failure domain first; verify health (§9) against SLOs; only then widen. Never change everything at once.
  • Immutability & versioned artifacts. Treat a device's config as an immutable, versioned artifact rendered from intent, not a thing you hand-edit in place. Every change is a new version with a known diff.
  • Fast, automatic rollback. Because each version is known and diffable, a failed rollout reverts to the last-good version automatically when health checks fail — bounded time-to-recovery instead of a frantic manual undo.
  • State machines for multi-step changes. A migration (say, moving a tenant to a new VNI) is modeled as an explicit state machine with safe, resumable transitions, so a failure mid-way leaves the fabric in a known, recoverable state rather than a half-applied mess.
Interview signal

Asked "how would you safely roll out a fabric-wide change," the strong answer is a loop, not a command: intent in version control → validate/dry-run → canary one failure domain → verify against SLOs → widen → auto-rollback on regression, with every config an immutable versioned artifact. That framing — reconcile, validate, canary, roll back — signals you think about blast radius on a shared multi-tenant fabric, which is the whole point of the role.

9. Operating the Network

A built network still has to be run: observed, held to objectives, and debugged when — not if — it misbehaves. The failure modes here are a common source of interview questions because they test whether you truly understand the mechanisms of the earlier sections.

Observability

  • Flow logs record per-connection metadata (who talked to whom, ports, bytes, accept/drop) — invaluable for security forensics, debugging reachability, and capacity analysis.
  • Streaming telemetry replaces old-style polling (SNMP every 30s) with devices pushing a high-frequency stream of counters and state (queue depths, drops, interface errors, ECN marks). It is the "observed state" feeding the reconciliation loop of §8 and the raw material for detecting congestion or drift in near-real-time.
  • Active probing — synthetic packets that traverse real paths — measures actual latency, loss, and reachability continuously, catching black holes that passive counters miss.

SLOs and error budgets

Network health is expressed the same way as any service's: SLOs (Service Level Objectives) on latency, packet loss, and availability, with an error budget that governs how much risk (and change velocity) is acceptable. A rollout (§8) that burns error budget is halted and rolled back. This ties the automation and the operations together: the same SLOs that gate a canary are the ones on the operator's dashboard.

Classic failure modes

Common mistake — blaming the app for a network black hole

"The API works from my laptop but times out from the new subnet, and only on large responses." That is almost never the application — it is the §3 MTU/PMTUD black hole: something on the new path added encapsulation, the resulting packets exceed the underlay MTU, and the ICMP that would fix it is filtered. The tell-tale sign is size-dependent failure (handshake fine, bulk transfer hangs). Reach for MTU/MSS before you reach for the app logs.

10. Common Interview Questions

These pull the whole chapter together. Each answer is written the way you'd say it out loud — mechanism first, then the trade-off.

Q: Walk a packet from VM-A on one host to VM-B on another, across an overlay.
VM-A emits an Ethernet frame to VM-B's (tenant) IP. The source host's virtual switch / DPU looks up VM-B's location and VNI, encapsulates the frame in outer Ethernet + IP + UDP + a VXLAN header carrying the 24-bit VNI, with the outer IP addressed from this host (VTEP) to VM-B's host. The Clos underlay routes that outer packet purely on its outer IP — spreading it across spines via ECMP — knowing nothing of the tenant inside. The destination VTEP receives it, strips the outer headers, reads the VNI to pick the right tenant network (bridge domain), and delivers the original frame to VM-B. The VTEP knew VM-B's MAC/IP-to-host mapping because it was advertised via MP-BGP/EVPN, not flooded. And the whole thing only works if the underlay MTU has room for the ~50 bytes of encapsulation.

Q: VXLAN vs Geneve — when and why?
Both wrap an Ethernet frame in UDP with a 24-bit VNI (~16M tenants, versus ~4K VLANs), and both route over a plain L3 underlay. The difference is extensibility: VXLAN's header is fixed; Geneve adds variable-length TLV options so the control plane can carry metadata — security tags, telemetry, service-chaining — per packet. Pick VXLAN for maximum interop as the de facto standard; pick Geneve when you need that programmable metadata, which is why many SDN stacks and DPUs default to it.

Q: Why run BGP inside the data center?
Because a Clos fabric is many equal-cost paths that change as links and hosts come and go, and BGP is a mature, policy-rich, massively scalable way to distribute reachability and load-balance over ECMP — the same protocol proven on the internet. eBGP-per-switch gives clean loop prevention and per-hop behavior; MP-BGP/EVPN then rides the same protocol to distribute tenant MAC/IP-to-VTEP mappings as the VXLAN control plane; and BGP-to-the-host turns container/service mobility into a routing event. One protocol, underlay and overlay.

Q: mTLS vs IPsec — which and where?
mTLS secures service-to-service traffic at the application/transport layer with per-workload identity (both ends present certificates) — ideal for a zero-trust service mesh where policy is "which service may call which." IPsec secures IP packets below the app — ideal for encrypting whole networks or the overlay across an untrusted underlay/WAN, transparently to applications. Remember the two orthogonal IPsec choices: ESP (encrypt+auth) vs AH (auth only, effectively legacy), and transport mode (payload only) vs tunnel mode (whole packet + new outer header, the site-to-site VPN). You often run both: mTLS east-west, IPsec between sites.

Q: What does a DPU actually offload?
The host's networking data plane: VXLAN/Geneve encapsulation, the virtual switch and firewall, load balancing, telemetry, and crypto — all run on the NIC's own cores instead of the host CPU. That frees CPU for tenant workloads, cuts latency/jitter, and isolates the networking/security software in a domain a compromised guest VM can't reach. It's the "move the data plane off the CPU" instinct — the packet-world equivalent of offloading blocking I/O to a co-processor. With SR-IOV giving VMs a direct NIC path, the DPU is where the overlay/policy work that used to sit in the host software switch now lives.

Q: Design the control plane for a multi-tenant virtual network.
Separate control and data planes (SDN). The data plane is host virtual switches / DPUs doing VXLAN or Geneve encapsulation with a per-tenant VNI, each tenant in its own VRF for L3 isolation. The control plane distributes endpoint state — a VTEP-to-MAC/IP mapping per VNI — via MP-BGP/EVPN (or an equivalent centralized controller like the publicly documented Andromeda model), so hosts learn locations without flooding. Drive the whole thing from declarative intent in version control, reconciled by a control loop that validates changes (dry-run/model-check), canaries them one failure domain at a time against SLOs, and auto-rolls back on regression. Secure it with per-workload mTLS and encrypt inter-site links with IPsec; offload the data plane to DPUs; and instrument it with streaming telemetry and flow logs so the reconciler and the on-call see the same truth. Call out the blast-radius danger of a shared fabric and the MTU headroom the overlay needs — that's the difference between reciting acronyms and having operated one.

One-line summary

Cloud networking makes one physical Clos fabric (§2) look like thousands of private tenant networks by wrapping tenant packets in VXLAN/Geneve overlays over a shared L3 underlay (§3), distributing reachability and endpoint state with BGP and MP-BGP/EVPN (§4) under an SDN control/data-plane split (§5), securing it with mTLS and IPsec toward zero trust (§6), offloading the per-packet data plane to SR-IOV/DPUs and running GPU clusters over lossless RoCEv2 (§7), all provisioned and changed safely by declarative intent and reconciliation loops (§8), then observed and debugged against SLOs where the classic killers are black holes, asymmetric routing, MTU/PMTUD, ECMP polarization, and BGP leaks (§9).
