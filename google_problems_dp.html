Dynamic Programming

Six Google-style dynamic-programming problems • original framing, execution-tested solutions, and interviewer probes

Note: Representative big-tech-style problems — not sourced from Google. The “Google-style” badge denotes the flavor of question, not its source.

How to read this chapter: every worked example uses inputs invented for this book, and each stated output was produced by compiling and running the accompanying Java. Beyond hand-picked edge cases (all-negative arrays, arrays with zeros, strictly-decreasing prices, impossible coin targets, single characters, and the two split-array extremes m = 1 and m = n) each solution was cross-checked against an independent brute force over hundreds of thousands of random inputs, and the two split-array methods were differentially tested against each other. The recurring idea below is to define a state, find the recurrence that links it to smaller states, and either scan once carrying a rolling optimum (Kadane-style) or fill a table bottom-up — and, when the answer itself is monotone, to binary-search on the answer instead.

Maximum Subarray

Medium Google-style

Problem

Given an integer array, find the contiguous non-empty subarray with the largest sum and return that sum. Values may be negative.

  • The subarray must be non-empty, so a single element is a valid answer.
  • When every value is negative the best sum is the single least-negative element — you are never forced to add a second number that can only make the sum worse.

Example: for [3, -4, 5, -1, 2, -8, 6] the answer is 6 (computed by running the code). The best window is [5, -1, 2], summing 5 - 1 + 2 = 6; it dips through the -1 because the surrounding positives more than pay for it. The lone [6] at the end also reaches 6, but never more. An all-negative array such as [-5, -2, -8] returns -2 — the least-negative single element.

Approach & Intuition

This is the canonical one-dimensional DP known as Kadane’s algorithm. Define cur as the largest sum of a subarray that ends at the current index. The recurrence is a single decision at each element: either extend the previous best-ending-here (cur + nums[i]) or restart a fresh subarray at the current element (nums[i]) — whichever is larger. Because a negative running sum can only hurt a later extension, restarting whenever cur + nums[i] < nums[i] is exactly the right move. Keep a separate best as you scan, to remember the largest cur ever seen; the ending index that maximises the sum need not be the last one.

public int maxSubArray(int[] nums) {
    int best = nums[0], cur = nums[0];   // seed BOTH at the first element, not 0
    for (int i = 1; i < nums.length; i++) {
        cur = Math.max(nums[i], cur + nums[i]);  // extend, or restart at nums[i]
        best = Math.max(best, cur);           // remember the best window seen
    }
    return best;
}

Complexity: Time O(n) — one pass, constant work per element. Space O(1) — two scalars, no table.

Common pitfalls / interviewer probes: Seed with the first element, not 0. Initialising best = 0 silently returns 0 on an all-negative array, since no real subarray beats the empty one — but the problem forbids empty subarrays, so the least-negative element must win. Take the max before adding, not after. The decision is max(nums[i], cur + nums[i]); writing cur = max(0, cur) + nums[i] is an equivalent reset but only if you never let best initialise to 0. Track best separately from cur. The maximal window may end in the middle of the array, so returning cur (the best ending at the last index) is wrong. Follow-up: return the indices. Interviewers often ask you to also report the subarray’s bounds — track a candidate start that moves whenever you restart, and commit it when cur beats best.

Maximum Product Subarray

Medium Google-style

Problem

Given an integer array, find the contiguous non-empty subarray whose elements multiply to the largest product, and return that product. The array may contain negatives and zeros.

  • A single element is a valid subarray, so the answer is at least the largest single value.
  • Two negatives multiply to a positive, so the biggest product can hide behind a pair of negatives — you cannot simply track the running maximum.

Example: for [2, -3, -2, 4, -1] the answer is 48 (computed by running the code): the window [2, -3, -2, 4] gives 2 × -3 × -2 × 4 = 48 — the two negatives cancel. Extending to include the final -1 would flip the sign to -48, so the scan stops there. With a zero, [-2, 0, -1] returns 0: the zero severs the array and the best any window can reach is 0 itself.

Approach & Intuition

The twist over Maximum Subarray is that sign matters: multiplying by a negative turns the largest product into the smallest and vice-versa, so a running maximum alone is blind to the “two negatives make a positive” case. Carry both a curMax and a curMin (the largest and most-negative products ending at the current index). When the current value is negative, swap them before multiplying, because the old minimum × a negative becomes the new candidate maximum. Each is then max/min of “start fresh at v” versus “extend”; the max(v, …) also handles a zero for free — a zero drags both products to 0, and the fresh-start term restarts the window at the next element.

public int maxProduct(int[] nums) {
    int best = nums[0], curMax = nums[0], curMin = nums[0];
    for (int i = 1; i < nums.length; i++) {
        int v = nums[i];
        if (v < 0) {                       // a negative flips max <-> min roles
            int t = curMax; curMax = curMin; curMin = t;
        }
        curMax = Math.max(v, curMax * v);  // best product ending here (v = restart)
        curMin = Math.min(v, curMin * v);  // worst (most negative) ending here
        best = Math.max(best, curMax);
    }
    return best;
}

Complexity: Time O(n) — one pass, constant work per element. Space O(1) — three scalars.

Common pitfalls / interviewer probes: Track the minimum too. Keeping only curMax misses products like -3 × -2 that turn positive; the most-negative running product is a live candidate the moment the next negative arrives. Swap before multiplying, on a negative. When v < 0, exchange curMax and curMin first — multiplying by a negative sends the old min to the top and the old max to the bottom. Zeros reset naturally. Because each update takes max/min against a bare v, a 0 zeroes both running products and the window restarts at the next element — no special case needed. Seed from nums[0], not 1. Initialising the products to 1 invents a phantom empty prefix and breaks a single-element or leading-negative array. Overflow. On worst-case input the product can exceed int range; an interviewer may ask you to switch to long.

Best Time to Buy and Sell Stock

Easy Google-style

Problem

You are given daily prices of a single asset. Choose one day to buy and a later day to sell, maximising your profit. Return the maximum profit, or 0 if no profitable transaction is possible. Exactly one buy and one sell are allowed.

  • You must buy before you sell, so the sell day’s index is strictly greater than the buy day’s.
  • If prices only fall, the best you can do is not trade — the answer is 0.

Example: for [8, 3, 6, 2, 9, 5] the answer is 7 (computed by running the code): buy at the 2 on day 4 and sell at the 9 on day 5, for 9 - 2 = 7. Note the global minimum 2 comes after the earlier dip to 3, and the best sell price 9 follows it — a single left-to-right pass captures this. A strictly-decreasing series like [9, 7, 4, 1] returns 0: no later day ever exceeds an earlier buy.

Approach & Intuition

Frame it as a rolling DP over one pass. Sweep left to right tracking minSoFar, the cheapest price seen up to (and including) today — the best day to have bought. For each day, the best profit achievable by selling today is price - minSoFar; fold the largest such value into a running best. Because minSoFar only ever considers earlier days, the buy-before-sell constraint holds automatically. Seeding best = 0 encodes the “don’t trade” option, so a market that only falls yields 0.

public int maxProfit(int[] prices) {
    int minSoFar = Integer.MAX_VALUE, best = 0;
    for (int p : prices) {
        if (p < minSoFar) minSoFar = p;                 // cheapest buy day so far
        else if (p - minSoFar > best) best = p - minSoFar;  // best sale if we sell today
    }
    return best;
}

Complexity: Time O(n) — a single pass. Space O(1) — two scalars.

Common pitfalls / interviewer probes: Don’t pair the global min with the global max blindly. The max must occur after the min; tracking minSoFar as you go enforces the ordering, whereas max(prices) - min(prices) can pick a sell day that precedes the buy day. Seed best = 0, not MIN_VALUE. The “no transaction” fallback is a profit of 0; a strictly-decreasing series should return 0, never a negative “loss.” The else if is fine. On a day that sets a new minimum there is no sale worth considering (selling at your own buy price yields 0), so updating the min and skipping the profit check in one branch is correct. Follow-ups. Unlimited transactions (sum every upward step) and at-most-k transactions (a genuine 2-D DP) are the usual escalations.

Coin Change

Medium Google-style

Problem

Given coin denominations and a target amount, return the fewest coins that sum exactly to the amount. You may use each denomination any number of times. If the amount cannot be made, return -1.

  • An amount of 0 needs 0 coins.
  • Greedily taking the largest coin can fail — e.g. with [2, 5, 7] for 27, grabbing sevens first is not optimal — so a DP over every sub-amount is required.

Example: for coins [2, 5, 7] and amount 27 the answer is 5 (computed by running the code): 5 + 5 + 5 + 5 + 7 = 27 uses five coins, and no combination uses fewer. A greedy “largest first” would take 7 + 7 + 7 = 21, then grab the largest coin ≤ the remaining 6 — a 5 — leaving 1, which no coin can make, so greedy dead-ends entirely. That failure is exactly why a DP over every sub-amount is needed. For coins [3, 5] and amount 4 the code returns -1: no multiset of 3s and 5s sums to 4.

Approach & Intuition

This is an unbounded-knapsack DP. Let dp[a] be the minimum number of coins that sum to exactly a. Build the table bottom-up: dp[a] = 1 + min over coins c of dp[a - c] for every coin that fits (c ≤ a). Because each denomination may repeat, we simply reuse the already-computed dp[a - c] for the same coin set — no “used-up” bookkeeping. Initialise every entry to a sentinel INF = amount + 1 (strictly larger than any real coin count, which is at most amount) and set dp[0] = 0. If dp[amount] is still above amount at the end, the target is unreachable, so return -1.

public int coinChange(int[] coins, int amount) {
    int INF = amount + 1;              // sentinel: bigger than any real coin count
    int[] dp = new int[amount + 1];
    Arrays.fill(dp, INF);
    dp[0] = 0;                       // zero coins make amount 0
    for (int a = 1; a <= amount; a++)
        for (int c : coins)
            if (c <= a && dp[a - c] + 1 < dp[a])
                dp[a] = dp[a - c] + 1;
    return dp[amount] > amount ? -1 : dp[amount];  // untouched -> impossible
}

Complexity: Time O(amount × coins) — every sub-amount tries every denomination. Space O(amount) for the table.

Common pitfalls / interviewer probes: Return -1 for the impossible case. Guard with a sentinel and test whether dp[amount] was ever lowered; returning the raw INF or 0 is a classic bug. Choose the sentinel so it can’t overflow or be mistaken for a real answer. Using amount + 1 (rather than Integer.MAX_VALUE) keeps dp[a - c] + 1 from overflowing while staying strictly above any legitimate count of at most amount one-value coins. Greedy is wrong. Taking the largest coin first fails on sets like [2, 5, 7]; the DP is what guarantees optimality. Amount 0. dp[0] = 0 both answers the trivial case and anchors the recurrence. Follow-up: count the ways. Coin Change II asks for the number of combinations instead of the minimum count — same table shape, but loop coins on the outside to avoid counting permutations.

Longest Palindromic Substring

Medium Google-style

Problem

Given a string, return a longest substring that reads the same forwards and backwards. If several share the maximum length, returning any one of them is acceptable.

  • A single character is a palindrome, so the answer is never empty for a non-empty input.
  • Palindromes come in two shapes: odd length (a single centre character, like aba) and even length (a centre between two characters, like abba). Both must be considered.

Example: for "abaxyzzyxf" the answer is "xyzzyx" (computed by running the code) — a length-6 even palindrome centred between the two zs. The shorter "aba" (an odd palindrome) also appears but loses on length. A single character like "z" returns "z", and a string with no repeats such as "abcd" returns a length-1 substring (the code returns "a").

Approach & Intuition

Expand around every centre. A palindrome is symmetric about its centre, so treat each index as a potential centre and grow outward while the mirrored characters match. There are two centre kinds: odd-length palindromes centred on a character (start the two pointers at i, i) and even-length ones centred between two characters (start at i, i + 1). For each of the n indices we run both expansions, giving 2n - 1 centres in all, and keep the longest span found. The index arithmetic start = i - (len - 1) / 2, end = i + len / 2 recovers the substring bounds correctly for both parities. (A table DP where dp[i][j] marks whether s[i..j] is a palindrome is the textbook alternative — same O(n²) time but O(n²) space.)

public String longestPalindrome(String s) {
    if (s == null || s.length() < 1) return "";
    int start = 0, end = 0;
    for (int i = 0; i < s.length(); i++) {
        int odd  = expand(s, i, i);       // odd-length centre ON i
        int even = expand(s, i, i + 1);   // even-length centre BETWEEN i, i+1
        int len = Math.max(odd, even);
        if (len > end - start + 1) {      // found a longer palindrome
            start = i - (len - 1) / 2;
            end   = i + len / 2;
        }
    }
    return s.substring(start, end + 1);
}
// Grow outward while the mirrored ends match; return the matched length in chars.
private int expand(String s, int l, int r) {
    while (l >= 0 && r < s.length() && s.charAt(l) == s.charAt(r)) { l--; r++; }
    return r - l - 1;                 // pointers overshot by one on each side
}

Complexity: Time O(n²) — 2n - 1 centres, each expanding up to O(n). Space O(1) beyond the output (the DP variant costs O(n²) space; Manacher’s algorithm reaches O(n) time).

Common pitfalls / interviewer probes: Check both centre parities. Expanding only from i, i misses every even-length palindrome (like "xyzzyx"); you must also expand from i, i + 1. The even seed can be out of range — that’s fine. When i is the last index, i + 1 is past the end, so expand matches nothing and returns length 0; the r < s.length() guard handles it. Get the return-length formula right. After the loop the pointers have moved one step too far on each side, so the matched length is r - l - 1, not r - l. Recover bounds for both parities with the same math. start = i - (len - 1) / 2 and end = i + len / 2 work whether len is odd or even. Compare lengths, not raw expand results. Update the answer only when the new span strictly exceeds the stored one so the first maximal palindrome is kept.

Split Array Largest Sum

Hard Google-style

Problem

Given an array of non-negative integers and an integer m, split the array into m non-empty contiguous subarrays so that the largest subarray sum among them is as small as possible. Return that minimised largest sum.

  • With m = 1 there is no choice — the answer is the sum of the whole array.
  • With m = n (one element per part) the answer is the single largest element.

Example: for [4, 3, 2, 6, 7, 1] with m = 3 the answer is 8 (computed by running the code). The split [4, 3] | [2, 6] | [7, 1] yields subarray sums 7, 8, 8, so the largest is 8, and no 3-way split does better. As sanity checks, m = 1 returns the full sum 23 and m = 6 returns the largest element 7 — both matched by an independent DP.

Approach & Intuition

Binary-search on the answer. The quantity we want — the largest allowed subarray sum, call it the capacity — is monotone: if a capacity cap lets us fit the array into ≤ m pieces, then any larger cap does too. So binary-search the smallest feasible cap. The search range is pinned: the low bound is max(arr) (a single element must fit inside one piece, so no cap below the largest element can ever work) and the high bound is sum(arr) (one piece holding everything, the m = 1 case). Feasibility is a greedy O(n) check: walk left to right adding to the current piece, and start a new piece whenever adding the next element would exceed cap; if that needs more than m pieces, cap is too small. (A DP with state “minimum possible largest sum splitting the first i elements into k parts” also solves it in O(m · n²); we used it only as a cross-check.)

public int splitArray(int[] nums, int m) {
    int lo = 0, hi = 0;
    for (int n : nums) { lo = Math.max(lo, n); hi += n; }  // max(arr) .. sum(arr)
    while (lo < hi) {
        int mid = lo + (hi - lo) / 2;
        if (feasible(nums, m, mid)) hi = mid;   // mid works -> try smaller
        else lo = mid + 1;                      // too small -> raise the cap
    }
    return lo;                                   // lo == hi == smallest feasible cap
}
// Greedy: can nums be split into <= m contiguous pieces, each summing to <= cap?
private boolean feasible(int[] nums, int m, int cap) {
    int pieces = 1, cur = 0;
    for (int n : nums) {
        if (cur + n > cap) {                     // n won't fit -> open a new piece
            pieces++; cur = n;
            if (pieces > m) return false;
        } else cur += n;
    }
    return true;
}

Complexity: Time O(n · log(sum - max)) — each of O(log range) binary-search steps runs an O(n) feasibility scan. Space O(1). The DP alternative is O(m · n²) time and O(m · n) space.

Common pitfalls / interviewer probes: Set the search bounds precisely. The low end must be max(arr), not 0 — any cap below the largest element can never hold that element, so the greedy feasibility check would mis-report (accepting a piece whose running sum exceeds the cap); the high end is sum(arr). The answer is monotone — that’s why binary search applies. Feasibility only ever flips from false to true as the cap grows, so you can search for the boundary. Start the piece count at 1. You already have one open piece before the scan; counting from 0 is off by one. Contiguous, not any subset. The pieces must be consecutive slices, which is exactly what the left-to-right greedy produces — reordering elements changes the problem. Use lo + (hi - lo) / 2. Writing (lo + hi) / 2 can overflow when the sum is near Integer.MAX_VALUE. Non-negativity matters. The greedy feasibility argument relies on a piece’s running sum only ever increasing as you add elements; with negative numbers the problem needs the DP instead.
