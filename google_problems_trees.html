Trees — Recursion, DFS & Tree DP

Six Google-style tree & recursion problems • original framing, execution-tested solutions, and interviewer probes

Note: Representative big-tech-style problems — not sourced from Google. The “Google-style” badge denotes the flavor of question, not its source.

How to read this chapter: every worked example uses inputs invented for this book, and each stated output was produced by compiling and running the accompanying Java against a suite of edge cases (empty tree, single node, all-negative values, perfect vs. skewed shapes, multi-digit counts, deep nesting) and, wherever practical, a brute-force differential check over tens of thousands of random inputs. The recurring idea below is post-order DFS: solve each child first, combine the children’s answers at the parent, and thread a running global optimum through the recursion — the backbone of tree DP.

Binary Tree Maximum Path Sum

Hard Google-style

Problem

A path in a binary tree is any sequence of nodes where each adjacent pair is connected by an edge; a node appears at most once and the path need not pass through the root. The path sum is the total of the node values along it. Return the maximum path sum over every non-empty path in the tree. Values may be negative.

  • A single node is itself a valid path, so the answer for a one-node tree is just that node’s value.
  • When every value is negative the best path is the single least-negative node — you are never forced to add a second, only-hurtful node.

Example: for the tree below the answer is 32 (computed by running the code). The optimal path bends through the root: 9 → 11 → 4 → -3 → 6 → 5, summing 9 + 11 + 4 - 3 + 6 + 5 = 32. Note it dips through the negative -3 because the 6-subtree on the far side pays for it. An all-negative tree such as [-10, [-2], [-13, [-1]]] returns -1 — the least-negative single node.

// node values (root at top)
        4
       / \
      11  -3
     / \     \
    9   2     6
             / \
            5   1        // -> max path sum 32

Approach & Intuition

This is tree DP via post-order DFS. For each node define its downward gain: the largest sum of a path that starts at the node and descends into exactly one of its subtrees. That gain is node.val + max(gain(left), gain(right)), but any child gain that is negative is clamped to 0 — a subtree that only subtracts is simply not entered. Separately, the best path that bends at a node (using both children) is node.val + max(0, gain(left)) + max(0, gain(right)); we fold that value into a running global maximum at every node. The gain a node returns to its parent can only continue up one side, so it uses a single child; the global best is where a full “Λ-shaped” path is closed off. Carrying the global maximum in a one-element array lets the recursion update it in place.

public int maxPathSum(TreeNode root) {
    int[] best = { Integer.MIN_VALUE };   // best full path seen so far
    gain(root, best);
    return best[0];
}
// Downward gain: best path that STARTS at n and descends one side only.
private int gain(TreeNode n, int[] best) {
    if (n == null) return 0;
    int l = Math.max(0, gain(n.left, best));    // clamp: skip a negative branch
    int r = Math.max(0, gain(n.right, best));
    best[0] = Math.max(best[0], n.val + l + r);  // path bending through n
    return n.val + Math.max(l, r);              // straight path to extend upward
}

Complexity: Time O(n) — each node is visited exactly once and does constant work. Space O(h) for the recursion stack, where h is the tree height (O(log n) if balanced, O(n) for a degenerate chain).

Common pitfalls / interviewer probes: Clamp negative child gains, not the node itself. Wrapping each child in max(0, …) lets you drop a harmful subtree, but the node’s own value is always included — that is what keeps an all-negative tree returning the least-negative node instead of 0. Seed the global with Integer.MIN_VALUE, not 0. Initialising to 0 silently reports 0 for an all-negative tree, since no real path ever beats it. Return one side, record both. The value handed to the parent may only continue up a single branch (a path cannot fork), yet the answer considered at a node uses both branches; conflating the two is the classic bug. Watch for overflow on adversarial input. With tens of thousands of large-magnitude nodes the sum can exceed int range — an interviewer may ask you to switch the accumulator to long.

Count Complete Tree Nodes

Medium Google-style

Problem

Given the root of a complete binary tree, count its nodes. In a complete tree every level is fully filled except possibly the last, and the last level’s nodes are packed as far left as possible. A trivial O(n) traversal works, but the completeness guarantee lets you do far better — aim for O(log² n).

  • An empty tree has 0 nodes; a single node has 1.
  • A perfect tree of height h (all levels full) has exactly 2^h - 1 nodes — no traversal needed.

Example: a complete tree with 12 nodes (levels of size 1, 2, 4, and a last level of 5 packed left) returns 12 (verified by running the code). The code never visits all 12 nodes: it measures the left and right spine heights, sees they differ, and recurses — touching only O(log² n) nodes.

Approach & Intuition

Walk the leftmost spine and the rightmost spine of the current subtree, counting their lengths. If they are equal, every level is full, so the subtree is perfect and holds exactly 2^h - 1 nodes — return immediately without descending. If they differ, the last level is only partly filled; recurse into both children and add 1 for the current node. The key insight is that in a complete tree, at each level of recursion at most one of the two children is not perfect, so the recursion follows a single root-to-leaf path of length O(log n), and each step spends O(log n) measuring a spine — hence O(log² n) overall, not O(n).

public int countNodes(TreeNode root) {
    if (root == null) return 0;
    int lh = leftHeight(root), rh = rightHeight(root);
    if (lh == rh) return (1 << lh) - 1;   // perfect subtree: 2^h - 1 nodes
    // last level partly filled -> count each side, plus this node
    return 1 + countNodes(root.left) + countNodes(root.right);
}
private int leftHeight(TreeNode n)  { int h = 0; while (n != null) { h++; n = n.left;  } return h; }
private int rightHeight(TreeNode n) { int h = 0; while (n != null) { h++; n = n.right; } return h; }

Complexity: Time O(log² n) — the recursion descends one root-to-leaf path (O(log n) levels) and each level measures a spine in O(log n). Space O(log n) for the recursion stack. A plain traversal would be O(n) time.

Common pitfalls / interviewer probes: Measure heights in the right directions. The left height follows .left repeatedly and the right height follows .right; swapping them breaks the perfect-subtree test. The 2^h - 1 shortcut is the whole point. Reaching for it only when lh == rh is what avoids the linear scan; if you always recurse you have merely written an O(n) count with extra height work. Use 1 << h carefully. For very tall trees 1 << h can overflow a 32-bit int; interviewers may ask you to guard with 1L << h. Only valid for complete trees. The shortcut assumes completeness — on an arbitrary tree equal spine heights do not imply perfection, so the method would overcount (2^h − 1 is the maximum node count for that height — a non-perfect tree has fewer). Empty tree. The null guard returns 0 and also terminates the recursion at absent children.

Diameter of Binary Tree

Easy Google-style

Problem

The diameter of a binary tree is the length of the longest path between any two nodes, where length is counted in edges. The path may or may not pass through the root. Return that edge count.

  • A single node has diameter 0 — there is no edge to traverse.
  • The longest path need not touch the root; it can lie entirely within one subtree.

Example: for the tree below the diameter is 6 edges (verified by running the code). The longest path runs 7 → 4 → 2 → 1 → 3 → 6 → 8 — seven nodes, so six edges — passing through the root. Counting nodes instead would give 7; the problem asks for edges, so 6 is correct.

// node values (root at top)
          1
        /   \
       2     3
      / \      \
     4   5      6
    /            \
   7              8      // -> diameter 6 edges (7-4-2-1-3-6-8)

Approach & Intuition

Another post-order DFS. For each node compute its height in nodes — 1 + max(height(left), height(right)), with a null child contributing 0 (so a leaf has height 1). The longest path that bends at a node uses both subtrees fully, so its edge count is exactly height(left) + height(right). Fold that quantity into a running global maximum at every node; the height returned upward continues along only one side. The pattern mirrors Maximum Path Sum: combine two children for the local answer, return one child upward. The diameter is where the widest “Λ” closes.

public int diameterOfBinaryTree(TreeNode root) {
    int[] best = { 0 };        // longest path length, measured in EDGES
    height(root, best);
    return best[0];
}
// Height of the subtree at n, in nodes; updates best (a path's edge count) bending at n.
private int height(TreeNode n, int[] best) {
    if (n == null) return 0;
    int l = height(n.left, best), r = height(n.right, best);
    best[0] = Math.max(best[0], l + r);   // edges on the path bending through n
    return 1 + Math.max(l, r);            // height (nodes) of this subtree
}

Complexity: Time O(n) — one visit per node. Space O(h) for the recursion stack (O(log n) balanced, O(n) for a degenerate chain).

Common pitfalls / interviewer probes: Edges vs. nodes. The diameter here is edges, so a null child returns height 0 and the bending path is l + r; if the problem instead asked for the number of nodes on the longest path the answer would be l + r + 1. State which convention you are using. Combine both children, return one. The path through a node spans both subtrees, but the height propagated to the parent may follow only one — the same two-value discipline as Maximum Path Sum. Don’t recompute heights. A naive version calls a separate height() inside a diameter recursion, giving O(n²); folding the update into a single post-order pass keeps it O(n). Single node / empty. One node yields 0 (no edges); an empty tree also yields 0.

Flip Equivalent Binary Trees

Medium Google-style

Problem

A flip swaps the left and right child of a node. Two binary trees are flip equivalent if one can be turned into the other by any number of flips at any set of nodes. Given the roots of two trees, decide whether they are flip equivalent.

  • Two empty trees are flip equivalent; an empty tree and a non-empty tree are not.
  • Node values must match at corresponding positions — flipping only reorders children, never changes values.

Example: the two trees below are flip equivalent, so the code returns true (verified by running it). Tree A has root 1 with children 2 (left) and 3 (right); tree B has the same root with 3 and 2 swapped, node 2’s children 4, 5 swapped, and the 5-node’s children 7, 8 swapped too. Flipping those three nodes (root, node 2, and node 5) turns A into B. If B’s 8 were instead a 9, the code returns false — no sequence of flips can change a value.

// Tree A                     Tree B  (flip root, node 2 & the "5" node)
      1                             1
     / \                           / \
    2   3                         3   2
   / \                               / \
  4   5                             5   4
     / \                           / \
    7   8                         8   7     // -> flip equivalent: true

Approach & Intuition

Recurse in lock-step over both trees. At each pair of nodes, first dispose of the base cases: if both are null they match; if exactly one is null, or the values differ, they cannot match. Otherwise the two children can align in one of two ways — without a flip (A.left with B.left, A.right with B.right) or with a flip (A.left with B.right, A.right with B.left). The trees are flip equivalent here iff either alignment recurses to true. Because the value check happens before recursing, a mismatch prunes immediately, so each node is effectively examined once.

public boolean flipEquiv(TreeNode a, TreeNode b) {
    if (a == null && b == null) return true;          // both empty -> match
    if (a == null || b == null || a.val != b.val) return false;
    // children line up as-is, OR after flipping a's two children
    return (flipEquiv(a.left, b.left)  && flipEquiv(a.right, b.right))
        || (flipEquiv(a.left, b.right) && flipEquiv(a.right, b.left));
}

Complexity: Time O(n) where n is the size of the smaller tree — a value mismatch stops a branch early, so each surviving node pair is compared once. Space O(h) for the recursion stack.

Common pitfalls / interviewer probes: Handle the three null cases in order. Both-null must be checked before the one-null test; otherwise a.val dereferences a null pointer. Values compared before children. Confirming a.val == b.val up front both prunes and prevents the null dereference on the following line. Short-circuit is what keeps it linear. Java’s &&/|| stop early, so the first workable alignment ends the comparison; forgetting the flipped alternative (the second || clause) wrongly rejects trees that differ only by a swap. Flips reorder, never relabel. A common follow-up asks you to also return the set of nodes that were flipped, or to canonicalise each tree (sort children by a hash) and compare — a useful cross-check but O(n log n) rather than O(n).

Decode String

Medium Google-style

Problem

Decode a string encoded with the rule k[substring], meaning the bracketed substring repeats exactly k times. Encodings may nest, k is a positive integer that can have multiple digits, and the input outside brackets is plain lowercase letters. The input is always well-formed — brackets balance and every [ is preceded by a count.

  • There are no stray digits: a number always introduces a bracket group.
  • k may exceed a single digit, e.g. 12[z] expands to twelve z’s.

Example: running the code, "2[pq3[r]]" decodes to "pqrrrpqrrr": the inner 3[r] becomes rrr, giving pqrrr, which the outer 2[…] doubles. The multi-digit case "12[z]" yields a 12-character run of z, and "3[a2[bc]]" yields "abcbcabcbcabcbc" — all three outputs were produced by executing the function.

Approach & Intuition

Scan left to right with two stacks: one of pending repeat counts, one of partially-built strings. Accumulate digits into an integer k so multi-digit counts work. On '[', push the current count and the text built so far, then start a fresh buffer for the bracket body. On ']', the current buffer is a completed body: pop the enclosing text and the matching count, and append the body to that text k times. Plain letters just extend the current buffer. When the scan ends, the current buffer holds the fully decoded string. The stacks encode exactly the nesting, so arbitrarily deep encodings unwind correctly.

public String decodeString(String s) {
    Deque<Integer> counts = new ArrayDeque<>();       // pending repeat factors k
    Deque<StringBuilder> segs = new ArrayDeque<>();   // text built before each '['
    StringBuilder cur = new StringBuilder();
    int k = 0;
    for (char c : s.toCharArray()) {
        if (Character.isDigit(c)) {
            k = k * 10 + (c - '0');          // accumulate a MULTI-digit count
        } else if (c == '[') {
            counts.push(k);                    // stash k and the text so far
            segs.push(cur);
            cur = new StringBuilder();
            k = 0;
        } else if (c == ']') {
            StringBuilder inner = cur;         // finished bracket body
            cur = segs.pop();
            int rep = counts.pop();
            for (int i = 0; i < rep; i++) cur.append(inner);
        } else {
            cur.append(c);                     // plain letter
        }
    }
    return cur.toString();
}

Complexity: Time O(N) where N is the length of the decoded output — each output character is appended once (the input scan itself is O(|s|), dominated by the expansion). Space O(N) for the output plus O(d) stack depth, where d is the nesting depth.

Common pitfalls / interviewer probes: Accumulate multi-digit counts. The k = k*10 + (c - '0') idiom is essential; treating each digit as a separate count misreads 12[z] as 1[2[z]]. Reset k after pushing. Zero it on '[' so the next count starts clean. Push the buffer, then start empty. On '[' you must save the outer buffer and begin a fresh one for the body; reusing the same buffer merges the body into its own prefix. Pop order on ']'. The completed body is the current buffer; the enclosing text is what you pop — append body to popped, not the reverse. A recursive-descent parser is the natural alternative and often reads more cleanly; interviewers may ask you to write both and compare stack usage against recursion depth.

Cracking the Safe

Hard Google-style

Problem

A safe is opened by the correct sequence of n digits, each drawn from {0, 1, …, k-1}. The lock checks only the most recent n digits entered, so a long input string tries a new candidate password with every keypress. Return any shortest string that is guaranteed to contain all k^n possible passwords as contiguous substrings. Such a string has length k^n + n - 1.

  • With n = 1 the answer is simply every digit once, e.g. k = 2 gives a length-2 string.
  • Every one of the k^n length-n combinations must appear exactly once at minimum length — this is a de Bruijn sequence.

Example: for n = 2, k = 2 the code returns "01100" (length 2² + 2 - 1 = 5, verified by running it). Its length-2 windows are 01, 11, 10, 00 — all four 2-digit binary passwords, each present. For n = 3, k = 2 the output has the expected length 2³ + 2 = 10 and contains all eight 3-bit codes; the test harness confirmed completeness for every case up to k = 4.

Approach & Intuition

Model the problem as an Euler circuit on a de Bruijn graph. Each node is a string of the last n-1 digits (there are k^(n-1) of them); each of the k^n possible length-n codes is a directed edge from its first n-1 digits to its last n-1 digits. A walk that uses every edge exactly once (an Euler circuit — one exists because every node has equal in- and out-degree k) spells out a string in which every code appears exactly once. Build that walk with Hierholzer’s algorithm: from the current node, greedily take each unused outgoing edge, recurse, and append the edge’s digit after the recursion returns (post-order). Finally append the starting node’s n-1 digits to complete the final wrap-around windows.

private Set<String> seen = new HashSet<>();   // length-n codes (edges) already used
private StringBuilder ans = new StringBuilder();
private int k;

public String crackSafe(int n, int k) {
    this.k = k;
    if (n == 1 && k == 1) return "0";          // single self-loop edge case
    StringBuilder start = new StringBuilder();
    for (int i = 0; i < n - 1; i++) start.append('0');   // start node = n-1 zeros
    dfs(start.toString(), n);
    ans.append(start);                    // append the start node's digits to close the wrap-around
    return ans.toString();
}
// Hierholzer: consume unused edges out of `node`, appending digits post-order.
private void dfs(String node, int n) {
    for (int x = 0; x < k; x++) {
        String edge = node + (char) ('0' + x);   // a length-n code
        if (seen.add(edge)) {                    // add() is false if already used
            dfs(edge.substring(1), n);        // next node = drop the first digit
            ans.append((char) ('0' + x));
        }
    }
}

Complexity: Time O(n · k^n) — the walk traverses all k^n edges once, and each step builds and hashes an O(n)-length key. Space O(n · k^n) for the seen set of edges, and the output has length k^n + n - 1.

Common pitfalls / interviewer probes: Append the edge digit after recursing. Hierholzer appends in post-order; appending before the recursive call produces a string that is not a valid Euler walk and drops codes. Append the start node. The post-order walk emits one digit per edge (k^n digits); the start node's n-1 digits must be appended so the final wrap-around windows are real codes and the length reaches k^n + n - 1. Nodes are the last n-1 digits, edges the length-n codes. Mixing these up (e.g. treating full codes as nodes) breaks the degree balance the Euler argument relies on. Recursion depth. This DFS recurses once per edge, so depth reaches k^n; on large inputs an interviewer may push you toward an explicit stack (iterative Hierholzer) to avoid overflow. Handle n = 1, k = 1. A single digit with one symbol is the degenerate self-loop that the up-front guard returns directly.
