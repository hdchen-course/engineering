Automated QA Scoring Overview

What it does, why it matters, and what interviewers evaluate.

The Old Way vs The New Way

Traditionally, a QA manager listens to ~20 random calls per agent per month and scores them on a rubric. This means only 2-5% of conversations are ever reviewed — riddled with sampling bias, expensive in human hours, and feedback arrives weeks late.

Automated QA scores every single conversation within minutes of it ending, across multiple quality dimensions. Every agent gets complete, timely, objective feedback.

The Core Idea

This is test automation for human conversations. Just as CI runs assertions against every code commit, this system runs quality checks against every conversation — some deterministic (rules), some judgment-based (LLM-as-judge).

What Gets Scored

Quality Dimensions

  • Compliance: did the agent verify identity, read required disclosures?
  • Tone: was the agent empathetic and professional?
  • Resolution: was the customer's issue actually solved?
  • Efficiency: unnecessary transfers, excessive hold time?
  • Knowledge accuracy: did the agent give correct information?

Peak Is Not the 24h Average

The ~6/sec figure is the 24h average. Real contact-center volume concentrates in business hours, so the daytime arrival rate is more like 12-15/sec with short bursts above 20/sec. Because scoring is async and queue-backed, I don't size ML workers to the instantaneous peak — but I also don't size to the 24h average, because a queue can only absorb transient bursts (seconds to a minute), not sustained overload. So I size steady-state ML capacity to the sustained business-hours rate (~12-15/sec) plus burst headroom, and let the queue smooth only the short spikes above 20/sec, trading a little extra latency (still well within the 5-minute SLO) for far cheaper capacity than provisioning for the instantaneous peak. Autoscaling that tracks the diurnal curve lets me shed workers overnight when the true rate drops toward the ~6/sec average.

The Cost Bomb

$3.6M/year in raw LLM cost is a non-starter. The entire scaling story of this system is cost optimization — batching, prompt caching of the shared rubric, and tiered scoring (cheap model for obvious cases, expensive only for ambiguous ones). Bring this up early; it's the defining constraint.

"At 500K conversations a day, naive LLM scoring costs about $3.6M a year. So cost isn't an afterthought — it's the central design constraint. I'll batch requests, exploit prompt caching for the shared rubric, and use a tiered cascade where an expensive model only handles the genuinely ambiguous cases. I'll be careful not to cache the score itself by conversation similarity — that behavioral variation is exactly the signal I'm measuring."

Why Rules and ML Run in Parallel

Rules are fast (<50ms) and local; ML is slow (~1s) and remote. Run them concurrently, not sequentially — the aggregator waits for both, so total latency is max(rule, ML), not sum. And if ML is down, rules still produce a compliance verdict immediately.

Key APIs

Ingestion is event-driven, not synchronous request/response — a completed-conversation event lands on a queue and scoring runs asynchronously (that's what buys the 5-minute SLO and natural backpressure).

// Enqueue a conversation for scoring. Idempotent on conversation_id
// so queue redeliveries / retries never double-score.
POST /v1/score-requests
  { conversation_id, tenant_id, agent_id, transcript_ref, category }
  -> 202 Accepted { score_request_id }

// Read the merged (rule + ML) score once ready
GET  /v1/scores/{conversation_id}
  -> { overall_score, compliance_passed, dimensions[],
       rule_version_set, model_version, status }   // status: pending|complete

GET  /v1/scorecards/{agent_id}?period=weekly
  -> AgentScorecard

// Rule admin — config-driven, used by non-engineers via an admin UI
GET  /v1/rules?tenant_id=...
POST /v1/rules            // creates a NEW version; never mutates in place
PUT  /v1/rules/{id}       // supersede with a new version (audit-preserving)
Idempotency & Exactly-Once Scoring

A queue-based pipeline gives at-least-once delivery, so the same conversation can arrive twice (redelivery, retry after a worker crash). Dedup on conversation_id. Because the score table is partitioned by scored_at, a UNIQUE(conversation_id) can't be enforced across partitions, so the uniqueness lives outside the partitioned table — a small non-partitioned dedup table keyed on conversation_id. The worker inserts the conversation_id into that dedup table in the same transaction as the score write, so the id counts as consumed only once the score is durably committed; a redelivered event that finds it already present is dropped rather than creating a duplicate scorecard entry (and a worker that crashes mid-scoring leaves no row, so the retry re-scores cleanly). Without this, retries silently inflate an agent's conversation count and skew every aggregate. (A Redis processed-ids set is faster to check but can't join the Postgres transaction, so on its own it is only best-effort — pair it with a transactional outbox / idempotency key if you go that route.)

Scoring Dimensions Design

The critical distinction: deterministic rules vs probabilistic ML.

Two Fundamentally Different Score Types

Rule-Based (Deterministic)

  • Binary pass/fail
  • High precision, zero false positives
  • Auditable — "you didn't verify ID at 0:45"
  • Used for compliance (must be defensible)

ML-Based (Probabilistic)

  • Score 1-5, nuanced
  • Captures tone, empathy, clarity
  • Tolerates some noise
  • Used for coaching (improvement, not punishment)

The Design Decision That Wins Points

Don't use ML for everything. Compliance MUST be a rule — a probabilistic "87% likely the agent verified identity" is legally useless. You need a defensible binary answer with evidence. Reserve ML for the subjective dimensions where nuance matters and some noise is acceptable.

Rule Engine Deep Dive

Config-driven rules that non-engineers can change without a deploy.

Why Configurable Matters

Compliance requirements change constantly — new regulations, new products, new scripts. If every rule change needs an engineer and a deploy, the system can't keep up. Rules must be data, not code.

Rule Versioning & A/B Testing

Rules are immutable versions, never edited in place. This gives you a full audit trail (which rule version scored this call?) and lets you A/B test a new rule against the old one before full rollout. A non-engineer edits rules through an admin UI with dropdowns — never raw JSON.

Evidence Is Non-Negotiable

Every rule result stores the exact transcript excerpt and timestamp. When an agent disputes "you didn't verify identity," you show them 0:45 in the transcript. Without evidence, the score is unauditable and agents won't trust it.

LLM-as-Judge Integration

Using AI to evaluate soft dimensions — reliably and affordably.

PII Redaction Before the Judge (Non-Negotiable)

The judge scores behavior — empathy, clarity, resolution — none of which needs the customer's real name, card number, or address. So a raw transcript must never reach the LLM judge, especially when the judge is a third-party model. Insert a PII-redaction stage between transcript ingestion and every LLM call, and score only the redacted text.

Compliance Critical — Redact Before the Judge

Sending raw conversation transcripts to an LLM-as-judge (potentially an external provider) is a PII exposure. Redact first. This mirrors the two-pass redaction in the Conversation Analytics pipeline: a fast regex pass for structured PII, then an NER pass for unstructured PII, replacing every match with a placeholder token. The judge sees [NAME], never "Jane Doe".

Raw transcript
  │  Pass 1 — regex (fast, high precision): SSN, credit card, phone, email
  │           "4111 1111 1111 1111" → [CREDIT_CARD], "555-12-3456" → [SSN]
  │  Pass 2 — NER model (thorough): names, addresses, account numbers
  │           "Jane Doe at 12 Oak St" → [NAME] at [ADDRESS]
  ▼
Redacted transcript   // placeholders/tokens only — no raw PII
  ▼
LLM-as-judge          // prompt operates on the REDACTED transcript
  ▼
Score + redacted evidence span
Reuse, Don't Rebuild

The transcript is already redacted upstream in the analytics/transcript-processing pipeline. QA scoring should consume that already-redacted transcript rather than re-fetching the raw one — one redaction stage, applied once, before any model (rule engine included) touches the text. If QA scoring ingests transcripts on its own path, it runs the same two-pass redactor before the judge; regex-only is the fallback if NER is unavailable, and the conversation is flagged for re-processing.

{{redacted_transcript}}

// Quote only from the REDACTED text; never reconstruct or infer PII.

Stored Evidence Must Be Redacted & Minimized

The "evidence" excerpt persisted on the score record (Sections 5, 7 & 10) must be a redacted, minimal span — a short quote from the already-redacted transcript with placeholders in place of PII, never raw customer data. Store the smallest span that justifies the score plus a timestamp/offset pointer back to the transcript store; if a reviewer needs the full un-redacted context, they resolve the pointer through an access-controlled, audited path. Persisting verbatim PII in the score row turns an auditable 2-year score table into a 2-year PII liability.

Third-Party Judge — Data Handling

When the judge is an external / third-party model, redaction is necessary but not sufficient. Only send transcripts under data-processing terms that guarantee no training on your data and no retention beyond the request, and route requests to a region consistent with each tenant's data-residency requirements. Prefer a provider (or a self-hosted/in-VPC model) that contractually meets these terms; if none does, keep the judge in-house. The redacted transcript is the payload either way — a double safeguard.

LLMs Fail Confidently, Not Gracefully

A subtly-wrong transcript produces a confidently-wrong score, which produces wrong coaching. Never trust a single LLM judgment blindly. Mitigate with confidence scoring, human review of edge cases, and the calibration loop (Section 9).

Cost Optimization (The Whole Game)

Three Levers to Kill the $3.6M Bill

  • Batch: score several conversations (or all dimensions of one) in a single call — amortizes the shared rubric/system prompt and per-request overhead. The saving is bounded by input tokens: you still pay for every transcript's tokens, so batching is a modest lever, not a single fix
  • Prompt caching: the rubric and instructions are byte-identical on every call — use provider-side prompt/prefix caching so those static tokens are billed at a steep discount. Also cache deterministic sub-results (e.g. the correct KB answer a knowledge-accuracy check verifies against). Do NOT cache the empathy/quality score by conversation similarity: two calls on the same topic can have opposite agent behavior, and that variation is precisely the signal you exist to measure
  • Tiered (cascade): a cheap model handles obvious cases (clear 1 or clear 5); the expensive model only judges the ambiguous middle (2-4). This is the biggest lever
Tiered Scoring in Practice

Run a cheap, fast classifier first. If it's highly confident the call is clearly great or clearly bad, accept that score. Only escalate the uncertain 20-30% to the expensive model. This alone can cut LLM cost by 60-70%.

Score Aggregation & Scorecards

From per-conversation scores to per-agent scorecards.

Per-Conversation Score

Combine rule results and ML scores into one number with a weighted formula:

conversation_score = 0.40 * compliance_score   (from rules)
                   + 0.30 * quality_score      (from ML)
                   + 0.30 * efficiency_score   (hybrid)

// CRITICAL OVERRIDE: any failed critical rule caps the total.
if anyCriticalRuleFailed {
    conversation_score = min(conversation_score, 50)  // cap at 50%
}
The Critical-Rule Cap

A conversation where the agent was warm, efficient, and helpful but forgot to verify identity cannot score well — that's a compliance failure regardless of everything else. The cap enforces this: critical rules are gates, not just weighted factors.

Per-Agent Scorecard

type AgentScorecard struct {

Statistical Significance

Don't Rank on Tiny Samples

An agent with 5 conversations shouldn't be ranked against one with 200 — the small sample is noise. Require a minimum (say 30 conversations) before generating a reliable scorecard or percentile ranking. Otherwise a single bad call tanks a new agent unfairly.

Coaching Recommendations

Auto-generate from pattern analysis: "Agent X scores low on empathy specifically on billing calls — recommend empathy training for billing scenarios." The value isn't the score; it's the actionable, specific next step.

Alert Fatigue Prevention

Too Many Alerts = No Alerts

If supervisors get 200 alerts a day, they ignore all of them. Group related alerts (5 agents missed the same new disclaimer → one alert about the disclaimer, not five). Support snoozing and de-duplication. An alert system nobody reads is worse than none.

Compliance Audit Trail

Every compliance alert and its resolution is logged immutably. When a regulator asks "how do you ensure agents verify identity?", you show the rule, the 100% coverage, the violation alerts, and the remediation — a complete, defensible record.

Calibration & Drift Detection

Keeping LLM judges accurate as they drift over time.

The Drift Problem

LLM judges drift — model updates, prompt tweaks, or subtle distribution shifts change how they score. A "4/5 empathy" today might be a "3/5" next month for identical behavior. Undetected, this corrupts every downstream scorecard and coaching decision.

The Human Calibration Loop

Ongoing
Maintain a golden set
A fixed set of conversations with expert human-assigned scores — the ground truth.
Periodic
Re-score the golden set
Run the LLM judge against the golden set regularly and compare to human scores.
On divergence
Humans win, re-tune the judge
When agreement drops below threshold, the human scores are truth — re-tune the prompt/model until agreement stabilizes.
"Humans Win, The Judge Gets Re-Tuned"

This one line captures the whole philosophy. The LLM is a scalable approximation of human judgment, continuously validated against real human judgment. When they disagree, humans are the ground truth and the judge is corrected — never the reverse.

A/B Testing Scoring Models

Before rolling out a new judge model, run it in shadow mode against the current one on live traffic. Compare their scores and their agreement with the golden set. Only promote the new model if it matches humans better than the incumbent.

Evidence Excerpts Are Redacted, Not Raw

The evidence stored in dimensions (and rule Evidence) is a short, PII-redacted span from the already-redacted transcript, plus a timestamp/offset pointer into the transcript store — never verbatim customer PII. This keeps the score record auditable without turning it into a long-lived PII store. Full un-redacted context, if ever needed, is reached only by resolving the pointer through an access-controlled, audited path. See the LLM-as-Judge section for the upstream redaction stage.

Score Schema

CREATE TABLE conversation_scores (
    id                UUID NOT NULL,
    conversation_id   UUID NOT NULL,
    tenant_id         UUID NOT NULL,
    agent_id          UUID NOT NULL,
    scored_at         TIMESTAMPTZ NOT NULL,
    overall_score     REAL,
    compliance_passed BOOLEAN,       -- did all critical rules pass?
    dimensions        JSONB,          -- per-dimension scores + REDACTED evidence spans
    rule_version_set  JSONB,          -- which rule versions were applied
    model_version     VARCHAR(50),    -- which judge model scored it
    -- PK must include the partition key on a partitioned table
    PRIMARY KEY (id, scored_at)
) PARTITION BY RANGE (scored_at);
CREATE INDEX idx_scores_agent_time ON conversation_scores(agent_id, scored_at DESC);
-- Partition-local index for the read API and per-conversation lookups
CREATE INDEX idx_scores_conv ON conversation_scores(conversation_id);

-- Dedup / idempotency lives OUTSIDE the time-partitioned table: a unique
-- constraint on conversation_id is not enforceable across scored_at partitions,
-- so exactly-once is enforced here, in the same transaction as the score write
-- (a Redis processed-ids set is best-effort only -- it can't join this transaction).
CREATE TABLE score_dedup (
    conversation_id   UUID PRIMARY KEY,   -- global uniqueness, no partitioning
    score_id          UUID NOT NULL,
    scored_at         TIMESTAMPTZ NOT NULL
);
Store the Version Set

Recording rule_version_set and model_version on every score is what makes the system auditable and reproducible. Six months later you can answer "why did this call score 45?" by replaying the exact rules and model that scored it.

Partitioning

Partition scores by time (monthly) and cluster by tenant_id. Recent partitions stay hot for dashboards; old partitions move to cheaper storage but remain queryable for audits.

Scaling & Cost

Handling 500K/day and keeping the LLM bill sane.

Scaling the Pipeline

  • Rule engine: trivially parallel, stateless workers — scale horizontally, cheap
  • ML scoring: the bottleneck. Batch, cache, and tier to control both latency and cost
  • Queue-based: completed conversations land in a queue; workers pull and score. Backpressure is natural — if scoring falls behind, the queue absorbs it (score-later, never drop)

The Cost Optimization Stack

TechniqueSavingsTrade-off
Batching (several/call)~10-20%Latency increase; harder evidence attribution
Prompt/prefix caching~20-40% of input costOnly the static rubric is reused, never scores
Tiered cascade (cheap→expensive)~60-70%Cheap model must be well-calibrated on the easy tail
Stack Them

These compound. A tiered cascade on prompt-cached, batched requests can take the naive $3.6M/year down to roughly $600K-900K/year — the difference between a viable product and a money pit. The tiered cascade does most of the work (it removes ~70% of calls from the expensive model); caching and batching trim what's left. This is the single most important scaling conversation for this system.

Failure Handling

LLM service down

  • Rules still produce compliance verdict immediately
  • ML scores marked pending, retried later
  • Compliance never blocks on ML

Scoring falls behind

  • Queue absorbs backlog
  • Prioritize compliance-critical conversations first
  • Score-later beats score-never

Pitfalls & Follow-ups

Mistakes to avoid and how to answer the hard questions.

Common Pitfalls

Pitfall 1 — LLM for everything

Using an LLM to check compliance. A probabilistic "87% likely verified" is legally useless. Compliance MUST be deterministic rules with evidence. LLM is for subjective coaching dimensions only.

Pitfall 2 — Ignoring cost

Designing the scoring pipeline without addressing the $3.6M/year LLM bill. Cost IS the design here — batch, cache, tier. If you don't bring it up, the interviewer likely will — and skipping it looks naive.

Pitfall 3 — Ignoring drift

Assuming the LLM judge scores consistently forever. It drifts. Without a human calibration loop, every scorecard silently corrupts over time.

Pitfall 4 — Ranking on tiny samples

Generating a percentile ranking for an agent with 5 calls. Statistical noise. Require a minimum sample (~30) before ranking or the scores are unfair and untrusted.

Likely Follow-up Questions

Q: How do you keep the LLM cost under control?▶

Three stacked techniques. The big one is a tiered cascade: a cheap model handles the obvious ~70% (clear pass / clear fail), and the expensive model only judges the ambiguous 20-30% (~65% saving). On top of that, prompt caching bills the byte-identical rubric at a steep discount (~20-40% of input cost), and batching amortizes shared prompt tokens and per-request overhead (~10-20%). Stacked, this takes $3.6M/year down to roughly $600K-900K. Note what I deliberately do NOT do: cache the score by conversation similarity — that would erase the per-agent behavioral signal the whole system exists to measure.

Q: Why not use ML for compliance too?▶

Compliance needs a defensible, auditable binary answer. "87% likely the agent verified identity" is useless to a regulator or in a dispute. A deterministic rule with a cited transcript excerpt is defensible. Reserve ML for subjective dimensions where nuance beats precision.

Q: How do you know the LLM judge is still accurate?▶

A golden set of human-scored conversations. Periodically re-run the judge against it and measure agreement. When agreement drops below threshold, humans are truth — re-tune the judge until it stabilizes. New models run in shadow mode against the golden set before promotion.

Q: An agent disputes their score. What happens?▶

Every score stores evidence — the exact transcript excerpt and timestamp — plus the rule versions and model version used. You show the agent "at 0:45 you discussed the account before verifying identity." Reproducible and auditable, which is why agents trust it.

Q: What if the ML scoring service goes down?▶

Rules and ML run in parallel, so rules still produce the compliance verdict immediately — the critical path is unaffected. ML scores get marked pending and retried when the service recovers. Compliance never blocks on the availability of the coaching-oriented ML.
