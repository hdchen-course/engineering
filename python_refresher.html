The object model — names, objects, and references

Start with the one sentence that unlocks Python: everything is an object — integers, strings, functions, classes, modules, even types themselves. And a variable is not a box that holds a value; it is a name tag stuck onto an object that lives somewhere else.

Analogy: a name is a sticky label, an object is a balloon. a = b doesn't copy the balloon — it puts a second label on the same balloon. Whether you can change what's inside the balloon depends on whether the balloon is mutable.

Tiny runnable example

import sys
x = 256
y = 256
print(x is y)        # True  — small ints are cached & shared
print(x == y)        # True  — equal values

a = [1, 2, 3]
b = a                # b is a SECOND name for the SAME list
b.append(4)
print(a)             # [1, 2, 3, 4]  — aliasing: a sees b's change
print(a is b)        # True  — same object

Names vs objects (the picture)

Names live in a namespace and point at objects on the heap. Assignment rebinds a name; it never copies the object. This single idea explains aliasing, the mutable-default-argument trap, and why is differs from ==.

Mutable vs immutable — the dividing line

Immutable (can't change contents)Mutable (can change in place)
int, float, bool, str, bytes, tuple, frozensetlist, dict, set, bytearray, most custom classes

What lets an object be a dict key / set member is hashability, not immutability. Most immutable built-ins are hashable and can be safely shared; the mutable built-in containers (list, dict, set, bytearray) are unhashable and can't be keys; a tuple is hashable only if everything inside it is (a tuple holding a list is not); and custom objects are hashable by default (identity-based) and can be keys even though they're mutable. Mutable containers are also the source of most aliasing surprises. A tuple is just an immutable list — reach for it when the collection shouldn't change.

Note for Java/C++ folks: Python has no primitives-vs-objects split — 3 is a full object. There is nothing like a C++ copy constructor on plain assignment: b = a is always a pointer copy (reference), like assigning a Java reference. To actually copy, use list(a), a.copy(), or copy.deepcopy(a). And == is like Java's .equals() (value), while is is Java's == (identity).

Interview angle: Expect "what does this print?" aliasing puzzles and "difference between == and is?". Answer crisply: == compares values (calls __eq__); is compares identity (same object, same id()). Never use is to compare values — the sole idiomatic uses are x is None, is True/is False. Mention that assignment binds names and never copies; copies are explicit.

Core data structures — and the dict that runs everything

Four built-ins cover almost every coding problem. If you internalize their operations and Big-O, you can implement most interview solutions on reflex.

The four, at a glance

nums   = [3, 1, 2]                 # list  — ordered, mutable, dupes OK
point  = (4, 5)                    # tuple — ordered, immutable, hashable
seen   = {1, 2, 3}                 # set   — unordered, unique, O(1) membership
counts = {"a": 1, "b": 2}         # dict  — key -> value, O(1) avg lookup

dict — the go-to structure

The dict is the most important structure in Python. It backs objects (__dict__), keyword args, namespaces, and JSON. Since 3.7 it preserves insertion order as a language guarantee. Master these idioms:

d = {}
d["x"] = 1                       # insert / overwrite
d.get("y", 0)                    # safe read with default (no KeyError)
d.setdefault("z", []).append(9)  # get-or-create pattern
for k, v in d.items(): ...        # iterate pairs
"x" in d                         # membership test on KEYS, O(1)
d.pop("x", None)                 # remove without KeyError
merged = {**d1, **d2}             # merge (3.5+); or d1 | d2 (3.9+)

# counting — a common interview idiom
freq = {}
for c in text:
    freq[c] = freq.get(c, 0) + 1
# ...or just: from collections import Counter; Counter(text)

When a solution feels O(n²) because of an x in list check inside a loop, swap the list for a set or dict → membership drops to O(1) and the whole thing becomes O(n). This one move fixes a large share of "too slow" problems.

list vs tuple

  • list — mutable, use for a growing/changing homogeneous sequence.
  • tuple — immutable, use for fixed records (a coordinate, a return of several values), and anywhere you need a hashable key: seen.add((r, c)), dp[(i, j)].
r, c = divmod(idx, cols)     # tuple unpacking
visited = set()
visited.add((r, c))          # tuple as set member — lists can't do this

set — dedup and math

a, b = {1,2,3}, {2,3,4}
a & b     # {2, 3}   intersection
a | b     # {1,2,3,4} union
a - b     # {1}      difference
a ^ b     # {1, 4}   symmetric difference

Note for Java/C++ folks: list ≈ ArrayList/std::vector, dict ≈ HashMap/unordered_map, set ≈ HashSet/unordered_set, tuple ≈ an immutable struct/record. There's no built-in ordered tree map — use a sorted list plus bisect, or a heap, when you need ordering.

Interview angle: Say the Big-O out loud as you code ("membership on a set is O(1) average, so this loop is O(n)"). Reaching for a dict/set to collapse a nested loop is a strong signal. Know the average-vs-worst nuance: hash operations are O(1) average, O(n) worst under pathological collisions — fine to mention, rarely the bottleneck.

Comprehensions & generators — build fast, evaluate lazily

Comprehensions are Python's signature way to build a collection in one readable expression. Generators are their lazy cousins: they produce items one at a time instead of materializing the whole thing in memory.

Comprehensions

squares  = [x*x for x in range(10)]              # list
evens    = [x for x in range(20) if x % 2 == 0]   # with filter
by_len   = {w: len(w) for w in words}          # dict comprehension
uniq     = {c for c in text}                     # set comprehension
grid     = [[0]*cols for _ in range(rows)]      # 2-D grid, one list per row

Trap: grid = [[0]*cols]*rows makes rows references to one shared inner list — mutating grid[0][0] changes every row. Use the comprehension form above instead. (Same aliasing rule from the object-model section.)

Generator expressions & lazy evaluation

Swap the brackets for parentheses and you get a generator: nothing is computed until you iterate, and only one item exists at a time. This is how you process a 10 GB file with a few KB of memory.

# list comp: builds ALL 10 million ints in memory (~400 MB)
total = sum([x*x for x in range(10_000_000)])

# generator expr: computes one at a time, ~constant memory
total = sum(x*x for x in range(10_000_000))   # note: no inner brackets

Generator functions with yield

def read_lines(path):
    with open(path) as f:
        for line in f:          # the file object is itself lazy
            yield line.rstrip()   # pauses here, resumes on next()

def countdown(n):
    while n > 0:
        yield n
        n -= 1

for x in countdown(3):     # 3, 2, 1  — state is preserved between yields
    print(x)

Each yield suspends the function, handing a value to the caller and freezing all local state; the next next() resumes right after the yield. A generator is a one-shot iterator — once exhausted, it's done.

Idiom: chain lazy steps into a pipeline that never materializes intermediates: total = sum(len(line) for line in read_lines(path) if line). Reads the file, filters blanks, sums lengths — in constant memory.

Note for Java folks: generators are like a lazily-evaluated Stream / Iterator that you write imperatively with yield. There's no separate "stream" type — laziness is built into the iterator protocol itself.

Interview angle: When asked to "process a huge/infinite stream" or "reduce memory," reach for a generator and say "lazy evaluation — constant memory, one item at a time." Know that a generator can only be consumed once, that sum()/any()/max() accept generator expressions directly (drop the brackets), and that yield from subgen delegates to a sub-generator.

Functions & closures — first-class, flexible, and full of traps

Functions are objects: you can pass them, return them, and store them in data structures. That power brings two of the most common traps in Python.

Arguments: positional, keyword, defaults

def connect(host, port=443, *, timeout=30):   # * → timeout is keyword-only
    ...
connect("api")                       # port=443, timeout=30
connect("api", 80, timeout=5)         # timeout must be named

*args and **kwargs

def log(*args, **kwargs):
    # args   → tuple of extra positional args
    # kwargs → dict of extra keyword args
    print(args, kwargs)

log(1, 2, level="warn")          # (1, 2) {'level': 'warn'}

# unpacking at the call site (the mirror image)
nums = [1, 2, 3]
print(*nums)                     # same as print(1, 2, 3)
opts = {"sep": "-"}
print(*nums, **opts)             # 1-2-3

Gotcha #1: the mutable default argument

def bad(item, bucket=[]):        # default list is created ONCE, at def time
    bucket.append(item)
    return bucket

bad(1)   # [1]
bad(2)   # [1, 2]  ← surprise! same list persists across calls

def good(item, bucket=None):     # the correct pattern
    if bucket is None:
        bucket = []
    bucket.append(item)
    return bucket

Default argument values are evaluated once, when the def statement runs — not on each call. A mutable default (list/dict/set) is therefore shared by every call. Default to None and build the real object inside.

Gotcha #2: late binding in closures

funcs = [lambda: i for i in range(3)]
[f() for f in funcs]           # [2, 2, 2]  — NOT [0, 1, 2]

A closure captures the variable i, not its value at creation time. By the time the lambdas run, the loop has finished and i == 2. Fix by binding the current value as a default argument (evaluated eagerly):

funcs = [lambda i=i: i for i in range(3)]
[f() for f in funcs]           # [0, 1, 2]

Closures done right

def make_counter(start=0):
    count = start
    def tick():
        nonlocal count       # rebind the enclosing variable
        count += 1
        return count
    return tick               # tick "closes over" count

c = make_counter()
c(); c(); c()                # 1, 2, 3 — state lives in the closure

Without nonlocal, assigning count inside tick would create a new local variable and shadow the outer one. Reading is fine without it; rebinding needs it.

Note for Java/C++ folks: closures capture variables by reference to the enclosing scope, unlike a Java lambda's effectively-final capture or a C++ [=] value capture. That reference semantics is exactly why the late-binding trap exists. nonlocal is the "I really mean the outer one" keyword; global is its module-level sibling.

Interview angle: The mutable-default and late-binding traps are classic trick questions — be able to predict the output and explain the mechanism (def-time evaluation; capture of the variable, not the value). Bonus points for knowing * forces keyword-only args and / forces positional-only (3.8+).

Decorators & iterators — wrapping behavior, producing sequences

Decorators: a function that wraps a function

A decorator takes a function and returns a replacement, usually adding behavior around the original. Because functions are objects, this is just higher-order functions plus the @ sugar.

import functools, time

def timed(func):
    @functools.wraps(func)          # preserve name/docstring of func
    def wrapper(*args, **kwargs):
        t0 = time.perf_counter()
        result = func(*args, **kwargs)
        print(f"{func.__name__} took {time.perf_counter()-t0:.4f}s")
        return result
    return wrapper

@timed
def work(n):
    return sum(range(n))
# @timed is exactly:  work = timed(work)

Always use @functools.wraps(func) on the wrapper — without it, the decorated function loses its __name__, docstring, and signature, which breaks introspection, logging, and debuggers.

Decorators that take arguments

Add one more layer: a factory that returns the actual decorator.

def retry(times):
    def decorator(func):
        @functools.wraps(func)
        def wrapper(*args, **kwargs):
            for attempt in range(times):
                try:
                    return func(*args, **kwargs)
                except Exception:
                    if attempt == times - 1:
                        raise
        return wrapper
    return decorator

@retry(3)
def flaky(): ...

Handy built-in decorators worth knowing: @property, @staticmethod, @classmethod, @functools.lru_cache (memoization — huge for recursive DP (dynamic-programming) interview problems), and @dataclasses.dataclass.

@functools.lru_cache(maxsize=None)
def fib(n):
    return n if n < 2 else fib(n-1) + fib(n-2)   # memoized → O(n)

Iterables vs iterators (the protocol)

  • An iterable can produce an iterator: it defines __iter__(). (Lists, dicts, strings, files.)
  • An iterator produces the next item: it defines __next__() and raises StopIteration when exhausted. It's also its own iterable (__iter__ returns self).
# what a for-loop actually does under the hood:
it = iter([10, 20])     # calls list.__iter__() → an iterator
next(it)               # 10
next(it)               # 20
next(it)               # raises StopIteration → loop ends

class Countdown:
    def __init__(self, n): self.n = n
    def __iter__(self): return self
    def __next__(self):
        if self.n <= 0:
            raise StopIteration
        self.n -= 1
        return self.n + 1

In practice you rarely hand-write __next__ — a generator function gives you the whole protocol for free, which is why generators are the go-to way to build custom iterators.

Interview angle: Be able to explain "iterable vs iterator" and sketch the for-loop desugaring (iter() then repeated next() until StopIteration). For decorators, explain that @d is sugar for f = d(f), why functools.wraps matters, and reach for @lru_cache to memoize recursive solutions on the spot.

The GIL and choosing a concurrency model

The Global Interpreter Lock is a mutex in CPython that lets only one thread execute Python bytecode at a time. It makes the interpreter's memory management simple and single-threaded code fast, but it means threads don't give you parallel CPU speedup.

Analogy: the GIL is a single microphone in a meeting room. Many people (threads) are present, but only the one holding the mic can speak (run Python). It gets passed around quickly, so it looks concurrent — but two people can never speak at the same instant. To truly speak in parallel, you need separate rooms (processes).

The picture

Pick the right tool

ModelBest forParallel CPU?Cost / notes
threadingI/O-bound (network, disk, DB calls)No (GIL)Cheap; GIL is released during blocking I/O, so threads overlap waits
multiprocessingCPU-bound (crunching, image/number work)Yes — separate interpretersHeavier; data crosses processes via pickling/IPC (inter-process communication)

# I/O-bound → threads (GIL released while waiting on the network)
from concurrent.futures import ThreadPoolExecutor
with ThreadPoolExecutor() as ex:
    results = list(ex.map(fetch_url, urls))

# CPU-bound → processes (true parallelism across cores)
from concurrent.futures import ProcessPoolExecutor
with ProcessPoolExecutor() as ex:
    results = list(ex.map(crunch, chunks))

# high-concurrency I/O → asyncio
import asyncio
async def main():
    results = await asyncio.gather(*(fetch(u) for u in urls))
asyncio.run(main())

The rule of thumb: I/O-bound → threads or asyncio; CPU-bound → multiprocessing. Using threads for a CPU-bound loop gives near-zero speedup (often slightly slower, due to GIL contention).

Note for Java/C++ folks: unlike JVM threads or C++ std::thread, Python threads can't run CPU work in parallel because of the GIL. The workaround is processes, not threads. (CPython 3.13 ships an experimental free-threaded "no-GIL" build, and 3.12+ adds per-interpreter GILs via sub-interpreters — worth mentioning as "the GIL is being chipped away," but the mental model above is still what you code to today.)

Interview angle: Expect "what is the GIL and why does it matter?" Answer: one thread runs Python bytecode at a time, so threads help I/O-bound work (GIL is released during blocking calls) but not CPU-bound work — for that, use multiprocessing. Then name asyncio as the single-threaded cooperative option for very high I/O concurrency. Showing you match the model to the workload is the whole point.

Stdlib power tools & typing hints

"Batteries included" is real. Three modules win coding rounds; typing hints make real-world code maintainable.

collections

from collections import Counter, defaultdict, deque, namedtuple

Counter("mississippi")          # {'i':4,'s':4,'p':2,'m':1}
Counter(words).most_common(3)   # top-3 (value, count) pairs

g = defaultdict(list)          # missing key auto-creates []
g[u].append(v)                 # no setdefault needed — great for graphs

dq = deque([1,2,3])            # O(1) at BOTH ends — use for BFS queues
dq.appendleft(0); dq.popleft()   # list.pop(0) is O(n); deque is O(1)

Point = namedtuple("Point", "x y")
p = Point(1, 2); p.x          # lightweight immutable record

itertools — lazy combinatorics

from itertools import (product, permutations, combinations,
                       accumulate, groupby, chain, count, cycle, islice)

permutations([1,2,3])          # all orderings
combinations([1,2,3], 2)       # all 2-subsets
product([0,1], repeat=3)         # all 3-bit tuples
list(accumulate([1,2,3,4]))     # running sums → [1, 3, 6, 10]
list(chain([1,2], [3,4]))       # flatten → [1, 2, 3, 4]
list(islice(count(), 5))         # take 5 from an infinite counter

heapq — the priority queue for interviews

import heapq
h = [3, 1, 2]
heapq.heapify(h)               # O(n), in place → MIN-heap
heapq.heappush(h, 0)
heapq.heappop(h)               # 0  — smallest first
heapq.nlargest(3, data)          # top-3 without full sort
heapq.nsmallest(3, data)

# max-heap trick: negate the values
maxh = []
for x in data: heapq.heappush(maxh, -x)
largest = -heapq.heappop(maxh)

heapq is a min-heap only. For a max-heap, push negated values (numbers) or wrap items in a (priority, item) tuple with negated priority. This is the standard trick for "top-K" and Dijkstra (shortest-path algorithm) questions.

Typing hints

Hints are optional and don't affect runtime, but they document intent and let tools (mypy, pyright, IDEs) catch bugs before you run the code.

from typing import Optional, Callable
from dataclasses import dataclass

def total(nums: list[int]) -> int:         # 3.9+ builtin generics
    return sum(nums)

def find(key: str) -> Optional[str]:        # same as str | None; in 3.10+ you can write the annotation as str | None
    ...

handler: Callable[[int], bool]           # takes int, returns bool

@dataclass
class User:
    name: str
    age: int = 0                        # auto __init__/__repr__/__eq__

Note for Java/C++ folks: type hints are not enforced at runtime — Python stays dynamically typed. They're closer to documentation checked by a separate tool. A @dataclass is the Python answer to a POJO (plain old Java object) / struct with boilerplate generated for you (like a Java record).

Interview angle: Knowing Counter, defaultdict(list) for graphs, deque for BFS, and heapq for top-K/Dijkstra lets you skip boilerplate and go straight to the algorithm — a strong signal of Python fluency. Mention type hints + dataclasses when asked about writing maintainable production code.

The integer / identity caching gotcha in detail

a = 256; b = 256
a is b        # True  — 256 is in CPython's small-int cache (−5..256)
x = 257; y = 257
x is y        # typically False — outside the cache, two distinct objects
x == y       # True — always compare VALUE with ==

This is a CPython implementation detail, not a language guarantee. The lesson isn't the boundary number — it's never use is to compare values. It only ever seems to work because of caching.

Interview Q&A

"What's the difference between a list and a tuple?"

Lists are mutable and ordered; tuples are immutable and hashable. Use a tuple for fixed records and as dict keys / set members; use a list for a collection that changes. Tuples are also slightly lighter and signal "don't modify this."

"Explain the GIL."

A mutex allowing one thread to run Python bytecode at a time in CPython. It helps I/O-bound threading (the GIL releases during blocking I/O) but prevents CPU-bound parallelism in threads — use multiprocessing for that, or asyncio for high-concurrency I/O on one thread.

"How do generators save memory?"

They're lazy: values are produced one at a time via yield, and local state is frozen between yields. Nothing is materialized, so you can process huge or infinite streams in near-constant memory. A generator is consumed once.

"Why does def f(x=[]) misbehave?"

The default list is created once when the def runs and reused across calls, so it accumulates state. Default to None and create the list inside the function.

"== vs is?"

== compares values via __eq__; is compares object identity (same id()). Use is only for singletons like None. Small-int/string caching can make is appear to work on values — don't rely on it.

"What is a decorator?"

A callable that takes a function and returns a replacement, adding behavior around it. @d above a function is sugar for f = d(f). Use functools.wraps to preserve metadata; @lru_cache to memoize.

"How do you make a shallow vs deep copy?"

Shallow: list(a), a.copy(), or a[:] — copies the top level, nested objects stay shared. Deep: copy.deepcopy(a) — recursively copies everything.

Interview angle / closing: Python interviews reward fluency more than trivia — reach for the right data structure, name the Big-O, use comprehensions and the stdlib idioms, and be ready to explain the object model, the GIL, and the mutable-default / late-binding traps from first principles. If you come from Java/C++, highlight that systems depth and treat Python's dynamic, reference-based model and rich stdlib as the fast part to pick up.
