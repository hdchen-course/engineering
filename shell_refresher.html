Shell / Bash Scripting Refresher

The syntax, idioms, and pitfalls of Bash — a tight, practical brush-up for someone who already programs and wants to write scripts that don't silently do the wrong thing

The safe-scripting preamble

Bash's defaults are forgiving in exactly the wrong way: a typo'd variable expands to the empty string, a failing command in the middle of a script is ignored, and a broken pipeline still reports success. The near-universal fix is a two-line preamble at the top of every non-trivial script.

#!/usr/bin/env bash
set -euo pipefail
FlagWhat it doesWhy you want it
set -eExit immediately if any command returns non-zero (with exceptions).A failed step no longer silently falls through to the next.
set -uTreat an expansion of an unset variable as an error.Catches an unset $dir in rm -rf "$dir/" before it silently becomes rm -rf /.
set -o pipefailA pipeline fails if any stage fails, not just the last.curl … | tar x no longer "succeeds" when curl died.

The shebang #!/usr/bin/env bash finds bash on PATH rather than hard-coding /bin/bash — important on macOS, where /bin/bash is a frozen 3.2, and modern Bash lives elsewhere.

-u catches unset variables

set -euo pipefail
echo "before"
echo "value=[${missing}]"   # never defined
echo "after"
# → output (script aborts on line 3, exit status 1):
before
script.sh: line 3: missing: unbound variable

When set -e trips you up

set -e is not magic; it has surprising blind spots. The classic trap is arithmetic that evaluates to zero — (( )) returns exit status 1 when its result is 0, and that trips set -e.

set -euo pipefail
count=0
echo "start"
(( count++ ))          # post-increment yields the OLD value 0 → status 1
echo "count is now $count"
# → output (aborts before the second echo!):
start

The fix is to make the arithmetic's status irrelevant: (( count++ )) || true, or better, count=$(( count + 1 )). The same idiom rescues any command whose non-zero exit is expected:

# grep exits 1 when there is no match; that would abort under set -e
matches=$(grep -c "nobody" /etc/passwd || true)
echo "nobody lines: $matches"
# → output:
nobody lines: 1

set -e is also disabled inside a command that is part of an if/while condition, a &&/|| chain (except the last), or a function called in those contexts. Rely on it as a safety net, not as your error handling — check the exit codes that matter explicitly.

Variables, quoting & substitution

There are no types — everything is a string (arrays and integers are shallow conveniences on top). Assignment has no spaces around =. The single most important habit in all of shell scripting: always quote your expansions — "$var", not $var.

name="Ada Lovelace"          # no spaces around =
echo "name is: $name"       # always quote expansions

today=$(date -u +%Y-%m-%d)     # command substitution: $(...) nests cleanly
echo "date: $today"

n=7
echo "sum: $(( n * 6 ))"      # arithmetic expansion
echo "pow: $(( 2 ** 10 ))"
# → output:
name is: Ada Lovelace
date: 2026-08-17
sum: 42
pow: 1024

Prefer $(...) over backticks for command substitution: it nests without escaping and reads better. Use $(( )) for integer math — bash has no floats; reach for awk or bc when you need them.

"$@" vs "$*" — a real difference

Both hold the positional parameters, but quoted they behave differently: "$@" expands to one word per argument (what you almost always want); "$*" joins them all into a single word separated by the first char of IFS (a space by default).

show() {
  echo "count = $#"
  echo '"$*" ->'; for a in "$*"; do echo "  [$a]"; done
  echo '"$@" ->'; for a in "$@"; do echo "  [$a]"; done
}
show one "two three" four
# → output:
count = 3
"$*" ->
  [one two three four]
"$@" ->
  [one]
  [two three]
  [four]

Rule of thumb: to forward a script's arguments to another command intact, write cmd "$@". Reaching for $* (or unquoted $@) is almost always a bug when any argument can contain spaces.

Word-splitting & globbing — why unquoted expansion is dangerous

When you leave an expansion unquoted, bash performs two extra steps on the result: word-splitting (on the characters in IFS — space, tab, newline) and filename expansion / globbing (*, ?, […]). This is why a filename with a space, or a value that happens to contain *, silently turns one argument into many.

count() { echo "received $# argument(s)"; }
var="a b c"
count $var       # UNQUOTED: word-splits into 3 args
count "$var"     # QUOTED:   stays 1 arg
# → output:
received 3 argument(s)
received 1 argument(s)

Globbing fires on unquoted values too

pattern='*.txt'           # dir contains a.txt and b.txt
echo $pattern            # unquoted: the glob is expanded
echo "$pattern"          # quoted: stays literal
# → output:
a.txt b.txt
*.txt

The danger is data-dependent: the same script works for months, then a file named my report.pdf or a variable holding * quietly corrupts a loop or a rm. Quote everything, and let shellcheck flag what you miss.

IFS — controlled splitting when you actually want it

Splitting is a feature when scoped tightly. Prefix a command with IFS=… to change the separator for that command only, and pair it with read -r to parse structured lines.

line="root:x:0:0:root:/root:/bin/bash"
IFS=':' read -r user _ uid _ <<< "$line"   # split on ':' just here
echo "user=$user uid=$uid"
# → output:
user=root uid=0

read -r should be your default: without -r, read treats backslash as an escape and mangles paths like C:\temp. The _ is a conventional throwaway name for fields you don't need.

Conditionals & tests: [[ ]] vs [ ]

[ ] is the old POSIX test builtin; [[ ]] is a bash keyword that is safer and more capable. Prefer [[ ]] in bash: it doesn't word-split or glob its operands (so an empty variable can't break the syntax), and it adds == glob matching and =~ regex.

x=10; y=9
[[ $x -gt $y ]] && echo "numeric: 10 > 9"       # -gt/-eq compare as NUMBERS
[[ "$x" > "$y" ]] || echo "string: '10' < '9'"  # > compares lexicographically!
s="hello.txt"
[[ $s == *.txt ]] && echo "glob match: ends in .txt"   # == does glob matching
[[ $s =~ ^h.*t$ ]] && echo "regex match: ^h.*t$"     # =~ regex
# → output:
numeric: 10 > 9
string: '10' < '9'
glob match: ends in .txt
regex match: ^h.*t$

Use numeric operators (-eq -ne -lt -gt) for numbers and string operators (== != < >) for strings — never mix them. [[ 10 > 9 ]] is false because it compares character by character. Inside [[ ]], < and > are comparison, not redirection.

File tests

[[ -e $f ]] && echo "-e exists"
[[ -f $f ]] && echo "-f regular file"
[[ -s $f ]] || echo "-s false: file is empty"
[[ -d /tmp ]] && echo "-d /tmp is a directory"
# → output (f is a fresh empty temp file):
-e exists
-f regular file
-s false: file is empty
-d /tmp is a directory

Loops and case

for i in 1 2 3; do printf '%s ' "$i"; done; echo
n=0; while (( n < 3 )); do printf 'w%d ' "$n"; (( n++ )) || true; done; echo
for f in one two; do
  case $f in
    one)       echo "matched one";;
    two|three) echo "matched two-or-three";;
    *)         echo "default";;
  esac
done
# → output:
1 2 3
w0 w1 w2
matched one
matched two-or-three

Reading a stream line by line

The canonical safe reader: IFS= read -r line. Clearing IFS preserves leading/trailing whitespace; -r keeps backslashes literal.

printf 'alpha\nbeta gamma\n' | while IFS= read -r line; do
  echo "line: [$line]"
done
# → output:
line: [alpha]
line: [beta gamma]

Functions, local, and return codes

Functions take arguments positionally ($1, $2, "$@") — you don't declare a parameter list. Two things to internalize: declare working variables local (bash has one global namespace otherwise), and know the two ways a function "returns" a result.

  • A status (0–255, where 0 = success/true) via return — test it with if or $?.
  • A value/string by echo-ing it and capturing with $(func …).
# Return a STRING: echo it, capture with $(...)
join_path() {
  local dir=$1 file=$2       # local: invisible to the caller
  echo "${dir%/}/$file"
}

# Return a STATUS: the exit code of the last command is the return code
is_even() {
  (( $1 % 2 == 0 ))          # (( )) status becomes the function's status
}

p=$(join_path /var/log "app.log")
echo "path: $p"

if is_even 4; then echo "4 is even"; fi
if is_even 7; then echo "7 is even"; else echo "7 is odd (returned non-zero)"; fi
# → output:
path: /var/log/app.log
4 is even
7 is odd (returned non-zero)

return only accepts a number 0–255; it is not for returning data. And $? is fragile — it reflects only the immediately preceding command, so capture it right away (rc=$?) if you need it after other commands run.

Interview angle. "How does a shell function return a value?" — distinguish the exit status (small integer, meant for success/failure) from output captured via command substitution. Mixing them up (e.g. return 42 to hand back a count) is a common bug.

Arrays & associative arrays

Bash has real indexed arrays, and — since bash 4 — associative arrays (hash maps). The one rule you must not forget: expand them as "${arr[@]}" (quoted, with @) so each element stays one word.

# Indexed array
fruits=(apple "dragon fruit" cherry)
echo "count: ${#fruits[@]}"          # length
echo "first: ${fruits[0]}"
for f in "${fruits[@]}"; do          # ALWAYS quote [@]
  echo "  - $f"
done
fruits+=(pear)                        # append
echo "after append: ${#fruits[@]}"
# → output:
count: 3
first: apple
  - apple
  - dragon fruit
  - cherry
after append: 4

Associative arrays (declare -A, bash 4+)

declare -A caps=( [France]=Paris [Japan]=Tokyo )
caps[Kenya]=Nairobi
echo "France -> ${caps[France]}"
echo "keys: ${!caps[@]}"              # ${!arr[@]} = the keys
echo "size: ${#caps[@]}"
# → output (key order is unspecified — it's a hash):
France -> Paris
keys: Kenya France Japan
size: 3

declare -A is required before assigning an associative array — without it, caps[France]=Paris is treated as an indexed array subscripted by the arithmetic value of France (0), silently wrong. Associative arrays don't exist at all in bash 3.2 (macOS's default) or in POSIX sh.

Traps: a bare $arr is just ${arr[0]}, not the whole array. "${arr[@]}" gives elements as separate words; "${arr[*]}" joins them into one string. Iteration order of an associative array is not the insertion order.

Parameter expansion — string surgery without extra processes

Bash can slice, trim, default, and substitute inside ${…} directly — no sed/cut subprocess needed. Learning these makes scripts both faster and clearer.

name=${1:-anon}                 # default if $1 is unset or empty
echo "name: $name"

path="/usr/local/bin/tool.tar.gz"
echo "basename:      ${path##*/}"     # strip longest leading */
echo "dirname:       ${path%/*}"      # strip shortest trailing /*
echo "strip .gz:     ${path%.gz}"     # % = shortest trailing match
echo "strip .tar.gz: ${path%%.*}"     # %% = longest trailing match

csv="a,b,c,b"
echo "replace first: ${csv/b/X}"      # / = first match
echo "replace all:   ${csv//b/X}"     # // = every match

s="hello world"
echo "substring 0:5: ${s:0:5}"        # offset:length
echo "length:        ${#s}"
# → output:
name: anon
basename:      tool.tar.gz
dirname:       /usr/local/bin
strip .gz:     /usr/local/bin/tool.tar
strip .tar.gz: /usr/local/bin/tool
replace first: a,X,c,b
replace all:   a,X,c,X
substring 0:5: hello
length:        11

Mnemonic for the trim operators: # is on the left of most keyboards, so #/## trim from the front; % is on the right, so %/%% trim from the back. Single = shortest match, doubled = longest.

Requiring a variable: ${x:?message}

: "${API_TOKEN:?must be set}"    # abort with a message if unset/empty
echo "token present"
# → output when API_TOKEN is unset (exit status 1):
script.sh: line 1: API_TOKEN: must be set

The leading : is the no-op builtin — it does nothing but expand its arguments, which is exactly what triggers the :? check. This is the cleanest way to assert required inputs at the top of a script.

Pipes, redirection & here-documents

Every process has three standard streams: stdin (0), stdout (1), stderr (2). Redirection wires them to files or to each other; pipes wire one command's stdout to the next's stdin.

echo "first line"  > log.txt     # > truncates/creates
echo "second line" >> log.txt    # >> appends
cat log.txt

# 2>&1 merges stderr into stdout so a pipe/redirect sees both
ls log.txt nope.txt 2>&1 | sort
# → output:
first line
second line
log.txt
ls: nope.txt: No such file or directory

Order matters: >file 2>&1 sends both streams to the file, but 2>&1 >file sends stderr to the old stdout (the terminal) and only stdout to the file — because 2>&1 copies wherever stdout points at that moment.

Here-documents and here-strings

# here-doc: a multi-line block fed to stdin; $vars expand unless the tag is quoted
release="1.2.0"
cat <<EOF
version=$release
literal=\$release
EOF

# here-string: one string fed to stdin
wc -w <<< "count these five little words"
# → output:
version=1.2.0
literal=$release
       5

Quote the delimiter (<<'EOF') to disable all expansion inside the body — essential when the block contains literal $ or backticks (e.g. embedding another script).

Process substitution <(…)

<(cmd) makes a command's output look like a file, so tools that want file arguments can read a stream — no temp file needed.

# diff two command outputs directly
diff <(printf 'a\nb\nc\n') <(printf 'a\nB\nc\n')
# → output:
2c2
< b
---
> B

The text toolbelt: high-value one-liners

The real power of shell is gluing together small tools. The following operate on this sample (fruit + count per line), piped in via echo "$data":

data='apple 3
banana 5
apple 2
cherry 9
banana 1'

sort by a numeric column, take the top 3

echo "$data" | sort -k2 -nr | head -3
# → output:
cherry 9
banana 5
apple 3

sum a column with awk

echo "$data" | awk '{ sum += $2 } END { print "total:", sum }'
# → output:
total: 20

count occurrences (the classic sort | uniq -c)

echo "$data" | cut -d' ' -f1 | sort | uniq -c
# → output:
   2 apple
   2 banana
   1 cherry

uniq only collapses adjacent duplicate lines, so it must be preceded by sort. sort -u is a shortcut for "sort then drop duplicates" but does not give you the counts.

substitute with sed, filter with grep

echo "$data" | sed 's/apple/APPLE/' | grep '^banana'
# → output (sed replaces first match per line; grep keeps banana lines):
banana 5
banana 1

xargs: turn a stream into arguments

printf 'a\nb\nc\n' | xargs -n1 echo "item:"
printf 'x\ny\n'    | xargs -I{} echo "wrap [{}]"
# → output:
item: a
item: b
item: c
wrap [x]
wrap [y]

For filenames that may contain spaces or newlines, pair find … -print0 with xargs -0 (NUL-delimited) so nothing gets word-split. -n1 runs the command once per input; -I{} substitutes each input into a template.

Traps & cleanup

Bash has no finally, but trap … EXIT is better: the handler runs on every exit path — normal return, set -e abort, or a signal. Combine it with mktemp for leak-free temp files.

work=$(mktemp -d)
cleanup() { rm -rf "$work"; echo "cleaned up temp dir"; }
trap cleanup EXIT          # runs on ANY exit: normal, error, or signal

echo "working in a temp dir..."
echo data > "$work/file"
# no explicit rm needed — the trap handles it even on early exit
# → output:
working in a temp dir...
cleaned up temp dir

Always create temp files with mktemp (or mktemp -d for a directory) — never a fixed path like /tmp/mytmp, which is a race condition and a symlink-attack vector. Register the cleanup trap immediately after creating the temp file.

Common pitfalls (and their fixes)

1 · [ $x = yes ] when $x is empty

With the old single-bracket test, an empty unquoted $x vanishes and the shell sees [ = yes ] — a syntax error.

x=""
if [ $x = yes ]; then echo "unreachable"; fi
# → output:
script.sh: line 2: [: =: unary operator expected

Fix: quote the variable, or use [[ ]] (which doesn't split its operands):

x=""
if [ "$x" = yes ]; then …; else echo "quoted [ ]: not yes (no error)"; fi
if [[ $x == yes ]]; then …; else echo "[[ ]]: safe even unquoted"; fi
# → output:
quoted [ ]: not yes (no error)
[[ ]]: safe even unquoted

2 · A variable set inside a pipe is lost

Each stage of a pipeline runs in a subshell, so a variable modified in … | while read reverts once the pipe ends. Feed the loop with process substitution or a here-string instead, so it runs in the current shell.

count=0
printf 'a\nb\nc\n' | while read -r _; do (( count++ )) || true; done
echo "after pipe:    count=$count"   # 0 — the while ran in a subshell

count=0
while read -r _; do (( count++ )) || true; done < <(printf 'a\nb\nc\n')
echo "after procsub: count=$count"   # 3 — same shell keeps the value
# → output:
after pipe:    count=0
after procsub: count=3

3 · cd without a guard

If a cd fails and the script keeps going, the next commands run in the wrong directory — occasionally catastrophically (cd build; rm -rf ./*). Guard it.

cd /no/such/dir || { echo "cd failed, aborting"; exit 1; }
echo "unreachable"
# → output (exit status 1):
script.sh: line 1: cd: /no/such/dir: No such file or directory
cd failed, aborting

Other common traps: parsing ls (for f in $(ls) breaks on spaces/newlines — glob directly with for f in *); forgetting -r on read; and unquoted expansions everywhere. A linter catches most of these mechanically — see below.

Tooling & portability

shellcheck — run it on every script

shellcheck is a static analyzer that flags the exact mistakes above with links to explanations. Wire it into CI and your editor.

# bad.sh
#!/usr/bin/env bash
for f in $(ls *.log); do
  rm $f
done
# → shellcheck bad.sh
In bad.sh line 2:
for f in $(ls *.log); do
         ^---------^ SC2045 (error): Iterating over ls output is fragile. Use globs.
              ^-- SC2035 (info): Use ./*glob* or -- *glob* so names with dashes won't become options.

In bad.sh line 3:
  rm $f
     ^-- SC2086 (info): Double quote to prevent globbing and word splitting.

Did you mean:
  rm "$f"

bash vs POSIX sh

Not every machine has bash, and #!/bin/sh may be a minimal POSIX shell (e.g. dash on Debian/Ubuntu). Bash-only features — arrays, [[ ]], local, ${var//…}, process substitution — are "bashisms" that break under a strict sh. The same array script run under dash:

# arr.sh:  arr=(one two three); echo "${arr[1]}"
# → under bash:
two
# → under dash (a POSIX sh):
arr.sh: 1: Syntax error: "(" unexpected

Decide up front: if you need arrays and the niceties, write #!/usr/bin/env bash and own it. If the script must run anywhere (init systems, containers, embedded), target POSIX sh and let shellcheck -s sh enforce it. Don't write #!/bin/sh at the top and then use bashisms — that's the combination that breaks mysteriously on another host.

Interview angle. Good answers to "how do you write a robust shell script?" hit: the set -euo pipefail preamble, quoting every expansion, [[ ]] over [ ], mktemp + trap … EXIT for cleanup, checking exit codes, and running shellcheck. Bonus: knowing when to stop and reach for Python — shell is superb glue but a poor place for data structures and real logic.
