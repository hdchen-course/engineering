Go Refresher

Go's radical simplicity + concurrency built into the language — a fast way in from C++/Java/Python, then interview-grade depth

Go's design philosophy (why it feels different)

Go was built at Google to make large teams productive on large codebases. The guiding instinct is radical simplicity: a small language you can hold in your head, one obvious way to do most things, and a compiler + tooling fast enough to feel like a scripting language while producing a single static binary.

The classic mental model: "Go is C for the 21st century — with garbage collection, memory safety, and concurrency built in." A high-schooler can read idiomatic Go on day one; the depth is in the runtime and the concurrency model.

  • Simplicity over features. No inheritance, no exceptions, no operator overloading, no implicit conversions. Fewer ways to be clever = easier to read someone else's code.
  • Composition over inheritance. You build behavior by embedding structs and satisfying interfaces, not by deep class trees.
  • Errors are values. Functions return an error; you check it. No hidden control flow.
  • Concurrency is a language feature. Goroutines and channels, not an add-on library.
  • Tooling is opinionated. gofmt ends every formatting argument; go test, go vet, the race detector, and modules are all included.
  • Fast compiles. The dependency model and lack of headers make builds fast even at scale.

Slogan worth quoting: "Don't communicate by sharing memory; share memory by communicating." That is the philosophy of channels in one line — pass data between goroutines rather than guarding shared state with locks.

A note for people coming from C++, Java, or Python

You know…In Go…
C++: manual memory / RAII, templates, exceptions, pointer arithmeticGarbage-collected (no delete); pointers exist but no pointer arithmetic; generics arrived in 1.18; no exceptions — errors are returned; goroutines instead of threads.
Java: classes + inheritance, checked exceptions, JVM startup, threads/executorsNo classes/inheritance — structs + methods + interfaces (satisfied implicitly); no exceptions; instant startup, single binary; goroutines are far cheaper than threads.
Python: dynamic types, the GIL, asyncioStatic + compiled + genuinely parallel; explicit types (with inference); goroutines give real multicore parallelism — no GIL.

The fastest way to feel at home: run gofmt constantly, read the standard library source (it is the style guide), and internalize "return the error, don't throw it." Most of your existing algorithmic and systems knowledge transfers directly.

Types & basics

Go is statically typed with type inference. Every variable has a well-defined zero value, so there is no "uninitialized garbage" like in C/C++.

package main

import "fmt"

func main() {
    var i int = 42       // explicit type
    f := 3.14             // := short declaration, inferred as float64
    s := "héllo"          // string: immutable, UTF-8 bytes
    ok := true            // bool
    var r rune = '世'     // rune = int32, one Unicode code point
    var b byte = 'A'     // byte = uint8

    fmt.Println(i, f, s, ok, r, b)
    fmt.Println(len(s))       // 6: byte length, not rune count (é is 2 bytes)
}

:= only works inside functions and declares a new variable; use = to assign to an existing one. Declaring a variable you never read is a compile error — Go refuses to build code with unused locals or unused imports.

Pointers (no arithmetic)

x := 10
p := &x            // *int, address of x
*p = 20           // dereference and set; x is now 20
// p++ is a COMPILE ERROR — Go has no pointer arithmetic.

// new(T) returns a *T pointing at a zero value
q := new(int)      // *int -> 0

Pointers give you shared, mutable references without unsafe arithmetic. There is no dangling-pointer problem: the garbage collector keeps memory alive as long as any pointer references it, even if you return the address of a local variable (Go moves it to the heap — called escape analysis).

Control flow — small surface area

// The ONLY loop keyword is `for`.
for i := 0; i < n; i++ { }        // C-style
for cond { }                       // while-style
for { break }                       // infinite loop
for i, v := range xs { use(i, v) }  // range over slice/map/string/channel

// if can carry an init statement; no parentheses, braces required
if v, err := doThing(); err != nil {
    return err
}

switch {                            // tagless switch = clean if/else-if chain
case score >= 90:
    grade = "A"
default:
    grade = "?"
}                                    // no fall-through by default

Interview angle. The "unused variable/import is an error" rule and the single for keyword are good talking points: they show Go trades a little friction for codebases that stay clean and uniform. Mention gofmt — style is not a code-review topic in Go.

Slices — the go-to type (know the header by heart)

An array in Go has a fixed size baked into its type ([3]int) and is rarely used directly. The everyday type is the slice ([]int): a lightweight view onto a backing array. A slice value is a tiny 3-word header:

  • ptr — pointer to the first element in the backing array
  • len — how many elements the slice currently exposes
  • cap — how many elements exist from ptr to the end of the backing array

Slices in code

nums := []int{2, 3, 5}          // literal: len 3, cap 3
buf := make([]int, 0, 8)         // len 0, cap 8 (preallocate to avoid regrows)

nums = append(nums, 7)          // may reallocate; ALWAYS reassign the result
sub := nums[1:3]              // [3 5] — shares the SAME backing array as nums
fmt.Println(len(sub), cap(sub)) // 2 5 (append grew cap to 6; cap(sub)=6-1)

Aliasing trap. Because a slice shares its backing array, writing through sub[0] mutates nums too. And append into a sub-slice can silently overwrite elements of the parent if there is spare cap. When you need an independent copy, use copy(dst, src) or a full-slice expression s[low:high:max] to cap it.

Maps

m := make(map[string]int)     // or map literal: map[string]int{"a": 1}
m["a"] = 1
m["z"]++                    // missing key reads as zero value, then increments to 1

v, ok := m["b"]              // comma-ok: ok is false if key absent
if !ok { fmt.Println("missing") }
delete(m, "a")

for k, v := range m {         // iteration order is RANDOMIZED on purpose
    fmt.Println(k, v)
}

Maps are not safe for concurrent read+write — a concurrent write crashes the program with a fatal error ("fatal error: concurrent map writes") that recover() cannot catch. Guard with a sync.Mutex or use sync.Map. Also: you can't take the address of a map element (&m["k"] is illegal) because the backing store can move on growth.

Interview angle. The classic question is "what does append return and why must you reassign?" Answer with the header: append may allocate a new backing array and give you a new header; the old variable would still point at the old array. Bonus points for the sub-slice aliasing trap and s[low:high:max] to bound capacity.

Structs & methods

A struct groups fields. You attach behavior with methods — functions with a receiver. There are no classes; a method can be defined on any named type you own.

type Point struct {
    X, Y int
}

// Value receiver: gets a COPY, cannot mutate the caller's Point.
func (p Point) Add(q Point) Point {
    return Point{p.X + q.X, p.Y + q.Y}
}

// Pointer receiver: can mutate; use for big structs or in-place changes.
func (p *Point) Scale(f int) {
    p.X *= f
    p.Y *= f
}

func main() {
    p := Point{X: 1, Y: 2}
    p.Scale(10)                // Go auto-takes &p for the pointer method
    fmt.Println(p.Add(Point{1, 1})) // {11 21}
}

Receiver rule of thumb: be consistent per type. If any method needs a pointer receiver (mutation, or the struct is large), give all its methods pointer receivers. Structs are value types — assigning or passing one copies every field, unlike Java objects which are references.

Composition via embedding (not inheritance)

type Logger struct{ prefix string }
func (l Logger) Log(msg string) { fmt.Println(l.prefix, msg) }

type Server struct {
    Logger          // embedded: Server "has-a" Logger and promotes its methods
    Addr string
}

s := Server{Logger: Logger{prefix: "[srv]"}, Addr: ":8080"}
s.Log("up")              // promoted: calls s.Logger.Log

Interfaces — satisfied implicitly

An interface is a set of method signatures. A type satisfies it automatically by having those methods — there is no implements keyword and no declared relationship. This is structural (duck) typing checked at compile time.

type Stringer interface {
    String() string
}

type Temp float64

// Temp now satisfies Stringer just by having this method.
func (t Temp) String() string {
    return fmt.Sprintf("%.1f°C", float64(t))
}

var s Stringer = Temp(21.5)   // works — no "implements" needed
fmt.Println(s.String())        // 21.5°C

Implicit satisfaction means you can write an interface after the fact to describe types you don't own (e.g. define a small interface that *os.File happens to satisfy). Idiomatic Go favors tiny interfaces — often one method (io.Reader, io.Writer). "Accept interfaces, return structs."

The empty interface, any, and type assertions

var x any = 42            // any == interface{}; holds any value (Go 1.18+ alias)

n, ok := x.(int)          // type assertion with comma-ok (no panic if wrong)
if ok { fmt.Println(n * 2) }

switch v := x.(type) {     // type switch
case int:    fmt.Println("int", v)
case string: fmt.Println("string", v)
default:     fmt.Println("other")
}

The nil-interface trap. An interface value holds a (type, value) pair. A non-nil interface wrapping a nil pointer is not == nil. Returning a concrete *MyError that is nil through an error return makes err != nil true unexpectedly. Return a literal nil for the no-error case.

Generics (Go 1.18+)

// Type parameter with a constraint (a union of allowed types).
func Max[T int | int64 | float64 | string](a, b T) T {
    if a > b {
        return a
    }
    return b
}

fmt.Println(Max(3, 7))          // 7 (T inferred as int)
fmt.Println(Max("a", "b"))      // b

Interview angle. Explain the difference from Java/C++: Go interfaces are satisfied structurally, so coupling is looser and interfaces stay small. Expect "how do interfaces work under the hood?" — answer: an interface value is two words, a pointer to a type descriptor (itable) and a pointer to the data. Method calls go through the itable.

Error handling — errors are values

Go has no exceptions for ordinary failures. A function that can fail returns an error as its last result; nil means success. You handle it right there. This makes control flow explicit and local.

import (
    "fmt"
    "os"
)

func readConfig(path string) ([]byte, error) {
    data, err := os.ReadFile(path)
    if err != nil {
        // %w WRAPS err, preserving it for errors.Is / errors.As.
        return nil, fmt.Errorf("read config %q: %w", path, err)
    }
    return data, nil
}

error is just an interface: type error interface { Error() string }. Anything with an Error() string method is an error.

Sentinels, wrapping, errors.Is / errors.As

import "errors"

var ErrNotFound = errors.New("not found")   // a sentinel error

// A custom error type carries structured detail.
type ValidationError struct {
    Field string
}
func (e *ValidationError) Error() string {
    return "invalid field: " + e.Field
}

// errors.Is compares against a sentinel, unwrapping the chain.
if errors.Is(err, ErrNotFound) { /* handle 404 */ }

// errors.As extracts a concrete type from the chain.
var ve *ValidationError
if errors.As(err, &ve) {
    fmt.Println("bad field:", ve.Field)
}

Idiom: wrap with context as an error travels up (fmt.Errorf("doing X: %w", err)), and only compare/inspect at the boundary that can act on it. Wrap with %w (keeps the chain) vs %v (flattens to text, breaks Is/As).

defer, panic, recover

defer schedules a call to run when the surrounding function returns — LIFO order. It's Go's cleanup mechanism (the RAII substitute): close files, unlock mutexes, right next to where you acquired them.

func process(path string) error {
    f, err := os.Open(path)
    if err != nil {
        return err
    }
    defer f.Close()          // runs no matter how we return below

    mu.Lock()
    defer mu.Unlock()        // deferred calls run in reverse: Unlock, then Close
    // ... work ...
    return nil
}

panic is for truly exceptional, unrecoverable situations (programmer bugs, impossible states) — not routine errors. It unwinds the stack running deferred calls. recover, called inside a deferred function, stops the unwind and lets you convert a panic into an error at a boundary.

// Convert a panic into an error at an API boundary.
func safeDivide(a, b int) (result int, err error) {
    defer func() {
        if r := recover(); r != nil {
            err = fmt.Errorf("recovered: %v", r) // named return set here
        }
    }()
    return a / b, nil          // b == 0 panics; deferred func catches it
}

Don't use panic/recover as exceptions for flow control — idiomatic Go returns errors. recover only works inside a deferred function and only catches a panic in the same goroutine. An unrecovered panic in any goroutine crashes the whole program.

Interview angle. "Errors vs panic?" — errors are expected outcomes you return and handle; panic is for unrecoverable bugs. "What does defer guarantee?" — it runs on every return path (including during a panic), in LIFO order, and its arguments are evaluated when defer is reached, not when it runs (a common trick question).

Goroutines & channels — the headline feature

A goroutine is a function running concurrently, started with the go keyword. It's not an OS thread: it starts with a tiny ~2 KB stack that grows on demand, and the Go runtime multiplexes millions of them onto a handful of OS threads. Starting one is nearly free.

go doWork()                 // runs concurrently; main does NOT wait
go func(id int) {          // anonymous goroutine
    fmt.Println("worker", id)
}(7)

Channels are typed pipes that let goroutines communicate and synchronize. A send blocks until a receiver is ready (and vice-versa) on an unbuffered channel — so the channel itself provides the handshake.

ch := make(chan int)        // unbuffered: send blocks until someone receives
go func() { ch <- 42 }()     // send
v := <-ch                    // receive (blocks until value arrives)

buf := make(chan int, 2)     // buffered: send blocks only when the buffer is full
close(buf)                   // closing signals "no more values"; receives still drain the buffer

// range over a channel receives until it is closed.
for v := range ch {
    use(v)
}

// comma-ok on receive detects a closed channel
v, ok := <-ch                // ok == false once closed and drained

Rules that prevent panics: only the sender closes a channel, and never close it twice. Sending on a closed channel panics. A receive from a nil channel blocks forever. Leaked goroutines blocked on a channel that never sends are the most common Go "memory leak."

select — wait on multiple channels

select is like a switch for channel operations: it blocks until one case can proceed, then runs it. If several are ready it picks one at random. A default makes it non-blocking; time.After adds a timeout.

select {
case v := <-ch1:
    fmt.Println("got from ch1:", v)
case ch2 <- x:
    fmt.Println("sent x to ch2")
case <-time.After(2 * time.Second):
    fmt.Println("timed out")
default:
    fmt.Println("nothing ready right now") // makes select non-blocking
}

Interview angle. Expect "goroutine vs thread" (cheap, user-space scheduled, growable stack vs OS thread ~1 MB), "buffered vs unbuffered channel," and "how do you cancel/timeout work?" — answer context.Context + select on ctx.Done(). Be ready to spot a deadlock (all goroutines blocked → the runtime aborts with a fatal error, "all goroutines are asleep - deadlock!", which is not a recoverable panic).

The scheduler (G–M–P), at a high level

Goroutines are cheap because Go schedules them in user space. The runtime uses the G–M–P model:

  • G — a goroutine (its stack + state).
  • M — a "machine," i.e. an OS thread that actually runs code.
  • P — a "processor," a scheduling context holding a run queue of Gs. The number of P's is GOMAXPROCS (defaults to the number of logical CPUs (runtime.NumCPU()); since Go 1.25 the default also respects the container's cgroup CPU limit, so in a CPU-capped container it can be lower).

An M must hold a P to run Gs. Each P has a local run queue; when it empties, that P steals work from another P's queue (work-stealing) to stay busy. When a goroutine makes a blocking syscall, the M can detach from its P so another M can keep the P's queue running — so one blocked goroutine doesn't stall the others.

Since Go 1.14 the scheduler is asynchronously preemptive: a goroutine in a tight loop can be preempted at safe points, so it can't starve others. Earlier versions only switched at function-call/channel/allocation points.

Garbage collection, at a high level

Go uses a concurrent, tri-color mark-and-sweep collector tuned for low latency rather than peak throughput. Most GC work runs concurrently with your program; stop-the-world pauses are tiny (sub-millisecond in typical services).

  • Tri-color: objects are white (unvisited), grey (reachable, children not yet scanned), or black (fully scanned). Marking finishes when no grey objects remain; anything still white is unreachable and freed.
  • Write barrier: while marking runs concurrently, a write barrier catches pointer writes so the mutator can't hide a reachable object from the collector.
  • Non-generational, non-compacting: unlike the JVM, Go's GC doesn't move objects or use generations. Escape analysis puts many objects on the stack, reducing heap pressure in the first place.
  • GOGC (default 100) trades memory for CPU: it triggers the next GC when the heap has grown ~100% since the last one. Higher = less frequent GC, more memory.

Interview angle. "How does Go's GC differ from Java's?" — Go optimizes for short, predictable pause times with a concurrent mark-sweep, non-generational, non-compacting collector; the JVM offers multiple tunable generational/compacting collectors optimized more for throughput. "How do you reduce GC pressure?" — preallocate slices with make(…, 0, n), reuse buffers via sync.Pool, avoid needless pointers, and let value types stay on the stack.

Standard tooling (batteries included)

Go ships one binary, go, that builds, tests, formats, and manages dependencies. No third-party build system needed.

# Build & run
go run .                  # compile + run the current package
go build ./...            # produce a static binary (cross-compile via GOOS/GOARCH)
GOOS=linux GOARCH=arm64 go build   # cross-compile, no toolchain juggling

# Test (files named *_test.go, funcs TestXxx(t *testing.T))
go test ./...             # run all tests
go test -race ./...       # run with the data-race detector — use in CI
go test -bench=. -cover   # benchmarks + coverage

# Format & lint (non-negotiable in Go culture)
go fmt ./...              # canonical formatting; zero style debates

# Modules = dependency management (go.mod / go.sum)

A tiny table test (idiomatic)

func TestMax(t *testing.T) {

        a, b, want int
    }{
        {1, 2, 2},

Concurrency patterns worth knowing

Worker pool (bounded parallelism)

Fixed number of goroutines pull jobs off a channel — caps concurrency and reuses goroutines.

func worker(jobs <-chan int, results chan<- int, wg *sync.WaitGroup) {
    defer wg.Done()
    for j := range jobs {          // drains until jobs is closed
        results <- j * j
    }
}

func main() {
    jobs := make(chan int, 100)
    results := make(chan int, 100)
    var wg sync.WaitGroup

    for w := 0; w < 3; w++ {         // 3 workers
        wg.Add(1)
        go worker(jobs, results, &wg)
    }
    for j := 1; j <= 9; j++ {
        jobs <- j
    }
    close(jobs)                    // tell workers no more jobs

    go func() { wg.Wait(); close(results) }() // close results once all workers done
    for r := range results {
        fmt.Println(r)
    }
}

Note the directional channel types in the signature: <-chan int (receive-only) and chan<- int (send-only). They document intent and let the compiler stop a worker from accidentally closing the jobs channel.

Fan-out / fan-in

Fan-out: start several goroutines reading the same input channel to parallelize. Fan-in: merge their outputs back into one channel.

// fanIn merges many input channels into one output channel.
func fanIn(ins ...<-chan int) <-chan int {
    out := make(chan int)
    var wg sync.WaitGroup
    wg.Add(len(ins))
    for _, in := range ins {
        go func(c <-chan int) {   // pass c as arg (pre-1.22 loop-var capture safety)
            defer wg.Done()
            for v := range c {
                out <- v
            }
        }(in)
    }
    go func() { wg.Wait(); close(out) }()
    return out
}

Prefer synchronization primitives that fit: channels for handing off data and signaling; sync.WaitGroup to wait for a set of goroutines; sync.Mutex/sync.RWMutex for protecting shared state; context.Context for cancellation/timeouts across a call tree. Always run CI with -race.

Interview angle. Be able to write a worker pool from scratch and explain who closes which channel and why (sender closes; close signals completion; WaitGroup coordinates the "all done, close results" step). A frequent follow-up: "add cancellation" → thread a context.Context and select on ctx.Done() in the worker loop.

Interview Q&A — likely Go questions

"What is a goroutine and how is it different from an OS thread?"

A goroutine is a function scheduled by the Go runtime in user space. It starts with a ~2 KB growable stack and is multiplexed onto a small pool of OS threads (G–M–P model), so you can run hundreds of thousands cheaply. OS threads are ~1 MB and switched by the kernel. Starting a goroutine is go f(); you coordinate with channels or sync primitives.

"Explain slices: what happens on append?"

A slice is a header of {ptr, len, cap}. append writes into spare capacity if len < cap; otherwise it allocates a new, larger backing array (~2× small, ~1.25× large), copies, and returns a new header — which is why you must reassign the result. Sub-slices share the backing array, so appends and writes can alias the parent.

"How do interfaces work / how is satisfaction determined?"

Structurally and implicitly: a type satisfies an interface simply by having the required methods — no implements keyword. At runtime an interface value is two words: a pointer to a type/itable descriptor and a pointer to the data. Idiomatic Go uses small interfaces and "accepts interfaces, returns structs."

"Value receiver vs pointer receiver?"

Value receivers operate on a copy (can't mutate the original, fine for small immutable types). Pointer receivers can mutate and avoid copying large structs. Keep it consistent per type. Note a subtlety: a non-pointer value's method set excludes pointer-receiver methods, so a T value boxed in an interface can't satisfy an interface that needs them — you must store *T.

"How does Go handle errors, and what is wrapping?"

Errors are ordinary values returned as the last result; you check if err != nil. fmt.Errorf("...: %w", err) wraps an error to preserve the chain; errors.Is tests for a sentinel and errors.As extracts a concrete type, both unwrapping. Panic/recover is reserved for unrecoverable bugs, not routine failures.

"Buffered vs unbuffered channels? When does a send block?"

Unbuffered: a send blocks until a receiver is ready (a synchronous handshake). Buffered (make(chan T, n)): a send blocks only when the buffer is full; a receive blocks only when empty. Closing signals no more values; receives still drain remaining buffered values, then return the zero value with ok == false.

"What causes a Go deadlock, and how do you avoid goroutine leaks?"

Deadlock: every goroutine is blocked (e.g. sending on an unbuffered channel with no receiver) — the runtime detects the all-asleep case and aborts with a fatal error (not a recoverable panic). Leaks: a goroutine blocked forever on a channel that's never sent to/closed. Avoid with clear ownership (sender closes), select with ctx.Done() for cancellation, and buffering or draining appropriately.

"Describe Go's garbage collector."

Concurrent tri-color mark-and-sweep, tuned for low pause times; non-generational and non-compacting. A write barrier keeps concurrent marking correct. GOGC tunes the memory/CPU trade-off. Escape analysis keeps many allocations on the stack, cutting heap pressure.

"How do you detect and prevent data races?"

Run tests/binaries with the built-in race detector (go test -race, go run -race). Prevent by not sharing mutable state across goroutines without synchronization — communicate over channels, or guard with sync.Mutex/atomics. Maps and slices aren't safe for concurrent writes.

"Why choose Go? What are its trade-offs?"

Pros: simple to read/learn, first-class concurrency, fast compiles, single static binary, great tooling, predictable GC latency — ideal for network services, CLIs, and infrastructure. Trade-offs: less expressive than C++/Rust (generics are newer and limited), no manual memory control, error handling is verbose, and it's not built for hard-real-time or manual-SIMD workloads.

Positioning to lead with: "I like Go for services where clarity, predictable latency, and easy deployment matter. I'm comfortable with the concurrency model — goroutines, channels, select, and context for cancellation — and I lean on the tooling (gofmt, go vet, -race) to keep things safe and uniform." Then be ready to whiteboard a worker pool.
