Low-Level Observability & Hardware Diagnostics

The layer below application APM: how to see what a server is actually doing at the kernel and hardware boundary. Kernel tracepoints and the PMU, perf and flame graphs, eBPF and the verifier, ftrace, the user-space profilers, and how to read the machine's own error channels — MCE, ECC/EDAC, PCIe AER, thermal events, and the BMC's System Event Log (SEL) — then scale that reading across a fleet with the USE method and a differential-diagnosis workflow. You already instrument services with traces, metrics, and logs. This chapter takes that same instinct and sinks it beneath the process boundary. §1 frames the layers and the mental bridge (kernel events are spans; hardware errors are structured log events). §2 is the instrumentation substrate every tool sits on — tracepoints, the PMU, kprobes/uprobes, USDT. §3–§6 are the tools: perf and flame graphs, eBPF (and why its verifier makes it safer than a kernel module), ftrace, and the user-space/protocol profilers. §7 turns to the hardware's own confessions — how to read MCE, ECC/EDAC, PCIe AER, thermal, and the BMC SEL. §8 scales all of it to a fleet: correlating faults, telling a flaky node from a systemic bug. §9 gives you a method (USE) and a differential-diagnosis playbook. §10 is the interview-question treatment. 1. The Layers Below the App

Application performance monitoring (APM) — request traces, RED/USE dashboards, structured logs — answers "which service, which endpoint, which query is slow?" But some problems live below that line: a NUMA-remote allocation, a syscall storm, a NIC dropping packets in the ring, a DIMM throwing correctable ECC errors, a CPU quietly throttling on a thermal limit. To see those you need system-level observability — instrumentation in the kernel and readouts from the hardware itself.

The observability stack. APM sits on top; this chapter is everything beneath it — kernel instrumentation, the PMU, the platform's hardware error channels, and the always-on BMC you reach over Redfish/IPMI.

The bridge: it's tracing and logging, one floor down

Nothing here is conceptually new to a backend engineer — the vocabulary maps almost one-to-one:

A metric counter (Prometheus)A PMU hardware counter (cycles, cache-misses) or an eBPF map histogram

The one idea to carry

Hardware and kernel events are signals you read the same way you read distributed traces and log events — they have a timestamp, a source, a type, and a severity. The skill is knowing which channel carries which signal, and how to correlate them. Everything in this chapter is a way of turning the machine's internal state into events you can query.

2. The Instrumentation Substrate

Before the tools, understand what they attach to. There are two orthogonal axes: where the instrumentation point lives (kernel vs user space) and whether it was placed there ahead of time (static) or injected at runtime (dynamic).

MechanismStatic / DynamicWhereWhat it is
TracepointStaticKernelA named, stable hook the kernel authors placed at meaningful events (sched:sched_switch, block:block_rq_issue, syscall enter/exit). Low overhead, documented fields.
kprobe / kretprobeDynamicKernelAttach to (almost) any kernel function's entry (kprobe) or return (kretprobe) at runtime by patching the instruction stream. Powerful but tied to internal symbol names that can change between kernels.
uprobe / uretprobeDynamicUser spaceSame idea, but on a user-space binary's functions — trace a libc call or your own function without recompiling.
USDTStaticUser spaceUser Statically-Defined Tracepoints: markers a developer compiled into the app (e.g. via DTRACE_PROBE) that stay stable across builds — the app's own "official" trace points.
PMU counterHardwareCPUThe Performance Monitoring Unit: dedicated hardware registers that count micro-architectural events. The ground truth for CPU behavior.

The PMU: hardware performance counters

Every modern CPU core has a Performance Monitoring Unit — a small bank of counter registers you can program to count events like retired instructions, core cycles, cache misses, branch mispredictions, and TLB misses. They run in hardware at full speed, so reading them is nearly free. The single most useful derived metric is IPC — Instructions Per Cycle:

IPC = instructions_retired / core_cycles # higher is better; modern cores can retire 3–4+/cycle low IPC (< ~1) usually means the core is stalled — waiting on memory, mispredicting branches, or serializing — not doing useful work

A hot loop with an IPC of 0.3 is not "CPU-bound" in the useful sense — it is memory-bound, stalled waiting for cache lines. IPC plus the cache/branch-miss counters tell you why a core is busy, which raw CPU% never can.

Counters are shared and finite

A PMU has only a handful of programmable counters (often 4–8 general-purpose per core). Ask perf to measure more events than there are counters and it multiplexes — time-slices the counters and scales the results, which introduces sampling error. In VMs and containers the PMU may be partially or fully virtualized, restricted, or unavailable; confirm counter access before trusting the numbers.

3. perf — the Swiss-Army Profiler

perf is the standard Linux profiler, built on the kernel's perf_event subsystem. It can read PMU counters, sample stacks, and consume tracepoints. Two modes cover most work: counting (perf stat) and sampling (perf record / perf report).

perf stat — the counting mode

perf stat runs a command (or attaches to a running one) and reports aggregate counter totals. It is the fastest way to answer "is this workload memory-bound, branch-bound, or genuinely compute-bound?"

# count key PMU events for a command
$ perf stat -e cycles,instructions,cache-references,cache-misses,\
             branches,branch-misses ./my_server --bench

# abridged, illustrative output — read the ratios, not the digits:
   1,200,000,000  cycles
     360,000,000  instructions     # IPC = instructions / cycles = 0.30  -> STALLED
     150,000,000  cache-references  # loads/stores that consulted the cache
      45,000,000  cache-misses      # 45M / 150M = ~30% miss rate -> memory-bound
       9,000,000  branch-misses     # a few % mispredict rate

The interpretation flow: low IPC + high cache-miss rate ⇒ memory-bound (fix data layout / locality); low IPC + high branch-miss rate ⇒ misprediction-bound (fix branchy hot code); high IPC but still slow ⇒ genuinely doing too much work (fix the algorithm).

perf record / report — the sampling mode

perf record interrupts the program at a set frequency (e.g. 997 Hz — a prime, to avoid aliasing with periodic work) and captures the call stack each time. Over thousands of samples, the functions that appear most often are where time is spent. perf report then shows a ranked, foldable breakdown.

# sample on-CPU stacks at 997 Hz, whole process tree, with call graph
$ perf record -F 997 -g --call-graph dwarf -p $(pgrep my_server) -- sleep 30
$ perf report --stdio           # ranked by self / children time
Sampling vs tracing

perf record is a statistical sampler: cheap, always-on-safe, but it only sees what it happened to catch — rare events can be missed. Tracepoint/probe-based tools (§4, §5) trace every occurrence: exact, but higher overhead. Reach for sampling to find where time goes; reach for tracing to answer exactly how often / how long a specific event takes.

Flame graphs, and on-CPU vs off-CPU

A flame graph turns thousands of sampled stacks into one picture: the x-axis is the fraction of samples (not time-ordered), the y-axis is stack depth. A wide box means that function (and its children) was on-CPU in many samples — a hotspot. You read it top-down for "what's running" and look for the widest plateaus.

A flame graph: width is the share of samples, not wall-clock order. The widest leaf box is the biggest self-time consumer — the first thing to optimize.
On-CPU graphs make waiting invisible

A standard perf flame graph only shows time on-CPU. If your latency comes from waiting — blocked on a lock, a disk read, or a network reply — the thread is off-CPU and produces no samples, so it's invisible. For that you need an off-CPU flame graph: trace scheduler sched_switch/wakeup events (via eBPF or perf sched) to measure how long threads were descheduled and why. On-CPU answers "what burned the cycles?"; off-CPU answers "what were we stuck waiting on?" You often need both.

4. eBPF — Safe Programmable Kernel Tracing

If perf is a rich readout, eBPF (extended Berkeley Packet Filter) is a way to run your own small programs inside the kernel, attached to tracepoints, kprobes, uprobes, or USDT, that aggregate data in-kernel and hand back only the summary. It is the foundation of modern Linux observability (and of a lot of networking and security tooling too).

Why eBPF instead of a kernel module?

Historically, to run custom code in the kernel you wrote a kernel module — a loadable plugin with full kernel privileges. A bug in a module can panic or corrupt the whole system. eBPF trades that danger for safety: before an eBPF program is allowed to load, the in-kernel verifier statically checks it.

eBPF program
  • Verifier proves it terminates (bounded loops only; no arbitrary back-edges)
  • Verifier proves every memory access is in bounds — no wild pointers
  • Runs in a restricted sandbox; can only call a fixed allowlist of helper functions
  • Can't crash the kernel; load is rejected if unsafe
  • Attach/detach at runtime, no reboot, no recompile of the kernel
Kernel module
  • Full, unchecked kernel privileges
  • A bug can panic the machine or corrupt memory silently
  • No sandbox, no verifier — you are trusted completely
  • Appropriate for real drivers/functionality, overkill and risky for observability
The bridge

eBPF is your familiar APM/tracing agent, but compiled down into the kernel and proven safe before it runs. You attach a probe (like adding a span), aggregate in a map (like a metric counter), and export a histogram — all without leaving the kernel, so overhead stays low and you never ship raw events over the wire.

bcc and bpftrace

You rarely write eBPF bytecode by hand. Two front-ends dominate: bcc (a toolkit and Python/C++ library with a large set of ready-made tools like execsnoop, biolatency, tcpconnect) and bpftrace (a high-level, awk-like language for one-liners and short scripts). A histogram of syscall latency in bpftrace is a few lines:

# histogram of read() syscall latency, in nanoseconds
tracepoint:syscalls:sys_enter_read { @start[tid] = nsecs; }

tracepoint:syscalls:sys_exit_read
/@start[tid]/                       # only if we saw the entry
{
    @ns = hist(nsecs - @start[tid]); # power-of-two bucket histogram
    delete(@start[tid]);
}
# on exit, bpftrace prints @ns as an ASCII histogram of the distribution

Notice the shape: store a per-thread start timestamp on entry, compute the delta on exit, and accumulate into an in-kernel histogram map. Only the compact histogram crosses into user space — not one event per syscall. Tracing a specific function is the same pattern with a kprobe: or uprobe: attach point.

When to reach for eBPF

Use eBPF when you need to trace every occurrence of a kernel or app event with custom aggregation and near-production-safe overhead, on a running system, without a reboot: syscall latency distributions, off-CPU analysis, per-PID network flows, block-I/O latency, "who is calling this function and with what argument." Use perf record instead when a cheap statistical sample of "where is CPU time going" is enough.

eBPF is safe, not free

The verifier prevents crashes and unbounded loops — it does not prevent you from attaching an expensive probe to an extremely hot path and adding measurable overhead. High-frequency probes (e.g. on every packet or every scheduler switch) still cost cycles. Measure the observer's own impact, and prefer tracepoints (stable, low-overhead) over kprobes (tied to internal symbols) when a suitable one exists.

5. ftrace — the Kernel's Built-in Tracer

ftrace is the tracing framework built directly into the kernel, driven through the tracefs filesystem (usually /sys/kernel/tracing). It needs no external agent and is often the first thing available on a bare or minimal system. Its two signature tracers:

  • function tracer — records every kernel function as it is entered. A firehose; you narrow it with a function filter.
  • function_graph tracer — records entry and exit, drawing a C-like nested call graph with per-function durations. This is the one that shows you where time goes inside a kernel path (e.g. what a slow syscall does step by step).

ftrace also consumes the same tracepoints as everything else, and can do latency tracers (e.g. tracking the longest interrupts-disabled region). Driving the virtual files by hand is tedious, so trace-cmd is the standard CLI front-end (and KernelShark a GUI over its output).

# function_graph a single syscall path with trace-cmd, then view it
$ trace-cmd record -p function_graph -g __x64_sys_read ./do_one_read
$ trace-cmd report | head

# illustrative shape — durations in µs, nesting shows the call tree:
 __x64_sys_read() {
   vfs_read() {
     ext4_file_read_iter() {  ...  }   1.83 us
   }                                   2.10 us
 }                                     2.44 us
perf vs ftrace vs eBPF — how to choose

ftrace: always present, best for tracing kernel function call graphs and durations with zero install. perf: best for PMU counters and statistical CPU profiling / flame graphs. eBPF: best for custom in-kernel aggregation (histograms, per-key maps) and correlating across events. They overlap and share the tracepoint/probe substrate (§2); pick by what you need to produce.

6. User-Space Profilers & Protocol Tools

Not everything lives in the kernel. A family of user-space tools answers narrower questions, and knowing which one fits saves hours.

strace attaches with ptrace and stops the target on every syscall — it can slow a busy process by an order of magnitude and change its timing enough to hide or distort the very problem you're chasing. It is a superb diagnostic on a reproducer or a stuck process, a poor choice for a latency-sensitive service under load. For "syscall behavior in production," prefer an eBPF tool (e.g. bcc's syscount/execsnoop) which aggregates in-kernel at far lower cost.

7. Reading Hardware Logs & Errors

Software tools tell you what code did; the platform's error channels tell you what the silicon did. These are structured events — treat each like a log record with a source, a type, and a severity. First, the inventory tools that tell you what hardware is even present:

ToolReadsTypical question
dmidecodeThe firmware's SMBIOS/DMI tables — board, BIOS version, DIMM part numbers/slots, CPU info."What DIMM is in slot A1? What BIOS version is this box on?"
lspciThe PCIe device tree, config space, link speed/width, capabilities."Is the NIC linked at the expected Gen/width? Is the accelerator even enumerated?"
ipmitoolThe BMC over the IPMI protocol — sensors, and the SEL (System Event Log)."What does the out-of-band controller say happened — power, thermal, hardware faults?"
Redfish (HTTPS/JSON)The BMC over the modern Redfish REST API — same data as IPMI, plus richer inventory and telemetry.Same as IPMI, but scriptable/automatable at fleet scale over a clean JSON API.
IPMI vs Redfish, in one line

Both are ways to talk to the BMC — the always-on management sidecar. IPMI is the older, low-level binary standard (still ubiquitous, e.g. ipmitool sel list). Redfish is its modern successor: a RESTful HTTPS + JSON API (DMTF standard) designed for automation and fleet-scale tooling. New tooling should prefer Redfish; you'll still meet IPMI everywhere in the field.

Machine-Check Architecture (MCA / MCE)

The CPU's Machine-Check Architecture (MCA) is its hardware mechanism for reporting detected errors — a bad cache line, an uncorrectable memory error, a bus/interconnect error, an internal parity error. The CPU records details in machine-check bank MSRs; the kernel decodes them (on Linux, the mcelog daemon or the kernel's EDAC/tracepoint path; rasdaemon is the modern collector). The critical distinction is whether the error was corrected — and only one of the two paths actually raises the CPU exception:

  • Corrected error (CE) — the hardware detected and fixed the error (e.g. ECC corrected a single-bit flip). No #MC exception is raised; it is logged in the MCA banks and signaled via CMCI (or polled by the kernel). The machine keeps running. These are informational, but a rising rate on one component predicts failure.
  • Uncorrected error (UC) — the error could not be corrected. This is what raises the actual Machine-Check Exception (#MC, vector 18). Depending on type and whether the bad data was consumed, it triggers recovery, a process kill, or a kernel panic / machine shutdown to prevent using corrupt data.

ECC & EDAC memory errors

ECC (Error-Correcting Code) memory adds redundancy so the memory controller can correct single-bit errors and detect (but not correct) double-bit errors (this is standard SECDED — single-error-correct, double-error-detect). On Linux, the EDAC subsystem surfaces these under /sys/devices/system/edac/… and via rasdaemon, attributing counts to a specific DIMM/rank:

  • CE (Correctable Error) count climbing on one DIMM ⇒ that DIMM is degrading. It's still correct, but it's the early-warning signal — schedule the DIMM for replacement before it produces a UE.
  • UE (Uncorrectable Error) ⇒ data was lost; typically surfaces as an uncorrected MCE and can crash the affected workload or the box. This DIMM must be replaced.
Bridge

An ECC/EDAC record is exactly a structured log event: {timestamp, component: DIMM slot A1, type: correctable, count: N}. Reading it is querying that event stream — and a rising correctable-error rate on one component is a classic leading indicator, the hardware equivalent of an error-rate SLO burning down.

PCIe AER (Advanced Error Reporting)

PCIe AER is the PCI Express error-reporting facility. Errors on the PCIe link/devices are classified as:

  • Correctable — recovered by the link automatically (e.g. a replayed TLP, an 8b/10b/128b/130b receiver error). Occasional ones are normal; a high or rising rate suggests a marginal link — reseat/replace the card or riser, check signal integrity.
  • Uncorrectable — Non-Fatal — a transaction failed but the link still works; the affected transaction is lost.
  • Uncorrectable — Fatal — the link itself is unreliable; usually requires a link reset and can take the device offline.

On Linux these appear in dmesg/kernel log tagged pcieport … AER: with the device's PCI address (matchable to lspci) and the decoded error bits. A device that keeps dropping off the bus, or an accelerator that "disappears," is very often an AER story.

Thermal, power, and the BMC SEL

When a CPU or accelerator approaches its thermal limit it throttles — drops frequency to shed heat — which shows up as a mysterious performance regression with no code change. Thermal and power events are visible in several places: CPU MSRs / /sys thermal zones, RAPL power counters, and — authoritatively — the BMC's SEL (System Event Log), which records sensor threshold crossings, power events, fan failures, and hardware faults with timestamps, independent of the OS.

# read the BMC's system event log over IPMI
$ ipmitool sel list
   1 | 08/19/2026 | 14:03:11 | Temperature #0x30 | Upper Critical going high | Asserted
   2 | 08/19/2026 | 14:03:12 | Processor #0x01    | Proc Automatically Throttled | Asserted
   3 | 08/19/2026 | 14:07:44 | Memory  #0x1a      | Correctable ECC | Asserted

# check PCIe link + AER, and correlate an accelerator that "vanished":
$ lspci -vvv -s 0000:65:00.0 | grep -iE 'lnksta|aer|uncorr|corr'
The reading discipline

For any hardware symptom, gather the same three attributes you'd pull from a log: which component (DIMM slot, PCI address, CPU/socket), what type (correctable vs uncorrectable, thermal, power), and what rate/trend (one-off vs climbing). A single corrected error is noise; a rising correctable rate on one component is a prediction; an uncorrectable error is an incident.

The OS log and the BMC can disagree — trust the BMC for hardware

If the kernel logged nothing but the box rebooted, the OS may have died before it could write anything. The BMC SEL survives OS crashes and power events because the BMC is a separate always-on computer. For "why did this machine go down with no kernel panic in the logs?", the SEL (over IPMI/Redfish) is often the only witness — check it before concluding "no evidence."

8. Fleet-Scale Diagnosis

One box you can log into and poke. A fleet of thousands you cannot — you must turn every machine's kernel and hardware signals into a stream you can query centrally, exactly like application logs and metrics. The building blocks are familiar: structured logging, aggregation, and correlation.

From per-node signals to a queryable stream

  • Collect structured, not free-text. Have rasdaemon (RAS events: MCE, ECC/EDAC, AER), the BMC (SEL/sensors via Redfish), and PMU/eBPF summaries emit structured records with stable fields: node_id, component (DIMM slot / PCI address / socket), error_type, severity, count, timestamp, plus hardware identity (serial, board, firmware version).
  • Aggregate centrally. Ship those to the same kind of log/metric pipeline you already run for the application tier, so you can compute rates and group by component and by hardware model/firmware/rack/power-domain.
  • Correlate. Now hardware faults become just more spans/events in the same query surface as request traces — you can join a p99 latency regression on a service to a thermal-throttle event on the nodes it was scheduled on.

Flaky node vs systemic issue

The central fleet question: is this one bad box (pull it, replace the part) or a systemic problem (a firmware bug, a bad component batch, a rack cooling failure) that will keep spreading? The answer is in the grouping:

Grouping / signalPoints toAction
Errors isolated to one node_id, others fineA flaky node / a failing partDrain, replace the specific DIMM/card, RMA
Correctable ECC concentrated on one component type / vendor lot across many nodesA bad component batchFleet-wide identify by part/serial, proactive replacement campaign
Errors correlate with one firmware/BIOS versionA firmware regressionHalt that firmware rollout, roll back / patch
Thermal events correlate with a rack / power domain / rowCooling or facility issueEscalate to datacenter ops, not to server repair
Broad, uncorrelated, low-rate correctable errorsExpected background rateAlert on rate and trend, not single events
Bridge

This is precisely the "flaky instance vs bad deploy" reasoning from distributed systems, moved to hardware. You group by every dimension you have (node, component, part, firmware, rack) and ask "what do the failing units share that the healthy ones don't?" — the same differential you'd run to decide whether a canary failure is the canary or the change.

Alert on rates and trends, never single events

At fleet scale, some box always has a corrected error right now — that's normal physics, not an incident. Paging on every corrected MCE/ECC event drowns you in noise and trains everyone to ignore alerts. Alert on rate (errors/hour on one component crossing a threshold), trend (accelerating), and any uncorrectable event. Aggregate the corrected ones into a predictive-replacement signal, not a page.

9. Method: USE & Differential Diagnosis

Tools without a method make you waste effort. Two frameworks keep a diagnosis disciplined: the USE method for resource health, and a differential-diagnosis workflow for a specific incident.

The USE method

The USE method — a standard resource-health framework — says: for every resource, check three things —

Utilization # % of time the resource was busy (or % of capacity used) Saturation # how much extra work is queued/waiting for it (the backlog) Errors # count of error events from it

Apply it to each resource in turn — CPU, memory (capacity and bandwidth), disks, network interfaces, and interconnects/buses. The power of USE is that saturation catches what utilization misses: a CPU at 100% utilization with a near-zero run-queue is fully used but not saturated (fine — it's doing work), whereas a CPU at 70% with a deep run-queue is saturated by scheduling latency. And the errors axis is exactly the hardware channels of §7.

ResourceUtilizationSaturationErrors
CPUbusy % (and IPC — is it doing work or stalling?)run-queue length; scheduler waitMCE / thermal throttle
Memoryused capacity; bandwidth usedswapping / page-fault stalls; reclaimECC/EDAC CE & UE
Disk / SSDbusy %; IOPS vs limitI/O queue depth / awaitI/O errors, SMART, media errors
Network / NICbandwidth usedring/qdisc drops, backlogCRC/RX errors, PCIe AER on the NIC

A differential-diagnosis workflow

When something is wrong, resist jumping to the tool you like best. Work top-down, and let each answer narrow the next question.

A differential-diagnosis flow: characterize the symptom, sweep resources with USE, then drop to the right tool (profiling, hardware channels, or tracing), confirm one hypothesis at a time, fix, and verify — including across the fleet.

Worked mini-playbooks

  • Boot failure / no OS. The main OS never came up, so software tools are useless — go out-of-band. Read the BMC SEL and sensors over IPMI/Redfish (power-on self-test progress / POST codes, memory-training failure, power fault, thermal trip). Confirm hardware is enumerated (does the BMC even see all DIMMs and the boot device?). This is the pre-OS "init" failing (covered in the firmware chapters); the BMC is your only witness.
  • Recurring hardware errors. Pull the structured stream (§8): is it correctable (predictive — schedule replacement) or uncorrectable (incident — drain now)? Is it one component, one part lot, or one firmware version? Group before you act.
  • Performance regression, no code change. USE sweep first. If CPU utilization is high but IPC dropped, suspect memory/locality or throttling: check perf stat cache-miss rate and thermal/power events (a throttling CPU regresses with zero code change). If off-CPU time grew, chase the wait (lock, I/O, network) with an off-CPU flame graph or eBPF.

10. Common Interview Questions

Low-level observability is a common focus for systems, performance, and firmware roles because you can't fake it: the answer is a method (classify, then drill down with the right tool), not a memorized command. Say the tool, but always say why you reach for it and what the next step is if it comes up empty.

Q: A box is slow. Walk me through finding out why with perf.
Start with perf stat to classify the bottleneck: read cycles, instructions (compute IPC), cache-misses, and branch-misses. Low IPC with a high cache-miss rate ⇒ memory-bound (fix data layout/locality); low IPC with high branch-misses ⇒ misprediction-bound; high IPC but still slow ⇒ genuinely too much work (algorithm). Then perf record -F 997 -g and render a flame graph to find the hottest self-time functions. If the flame graph looks idle but latency is high, the time is spent waiting — switch to an off-CPU analysis (scheduler tracing / eBPF) to find the blocking. I'd also glance at hardware channels: a throttling CPU (thermal) looks like a slowdown with no code change.

Q: What is eBPF, and when would you use it over a kernel module?
eBPF runs small, sandboxed programs inside the kernel, attached to tracepoints/kprobes/uprobes/USDT, aggregating in in-kernel maps. Before loading, the verifier statically proves the program terminates (bounded loops) and never accesses memory out of bounds — so, unlike a kernel module (full privilege, a bug can panic the box), eBPF can't crash the kernel. For observability, security, and networking data-collection on a live production system with no reboot, eBPF is the right tool; a kernel module is for actual driver/kernel functionality where you need capabilities eBPF doesn't grant. I'd still reach for perf record when a cheap statistical CPU sample is all I need.

Q: You see recurring ECC errors across the fleet. How do you triage?
First split correctable vs uncorrectable: correctable = predictive (schedule the DIMM for replacement before it fails), uncorrectable = incident (drain the node now, data was at risk). Then I group the structured EDAC/rasdaemon stream by dimensions — node_id, DIMM slot, part/vendor lot, BIOS/firmware version, rack/power-domain — to tell a flaky node (isolated → replace the part) from a systemic issue (a bad component batch → replacement campaign; a firmware regression → halt the rollout; a rack thermal problem → datacenter ops). And I alert on rate and trend, plus any uncorrectable event — never page on single corrected errors, which are normal background at scale.

Q: dmesg shows a "pcieport … AER: Corrected error" repeating on one device. What does it mean and what do you do?
PCIe Advanced Error Reporting caught a correctable link error — the link recovered automatically (e.g. a replayed TLP), so no data was lost. One-off is normal; a repeating/rising rate on one device means a marginal link. I'd map the PCI address to the physical card with lspci, check the negotiated link speed/width (LnkSta) against expected, and treat it as a physical-layer problem: reseat the card/riser, check the slot/cable, and if it persists replace the card or move slots. If it escalates to uncorrectable/fatal AER, expect the device to drop off the bus or need a link reset — that's an incident, not a warning.

Q: The machine rebooted but the kernel log shows nothing. Where do you look?
The OS may have died before it could write anything, so the on-disk log isn't the source of truth. I go to the BMC SEL over IPMI/Redfish — the BMC is a separate always-on controller that logs power events, thermal trips, and uncorrectable hardware faults independent of the OS. A thermal trip, a power fault, or an uncorrectable MCE recorded there explains a silent reboot the kernel never got to log.

Q: How do you decide between perf, ftrace, and eBPF?
They share the same tracepoint/probe substrate but produce different things. perf for PMU counters and statistical CPU profiling / flame graphs. ftrace (via trace-cmd) for kernel function-graph call trees and durations with zero install — great on a minimal box. eBPF for custom in-kernel aggregation (latency histograms, per-key maps) and correlating across events at low, production-safe overhead. I pick by whether I need a sample, a call-graph trace, or custom aggregation.

"Utilization tells me the resource is busy; saturation tells me work is waiting for it; errors tell me it's failing. I run that USE triad across CPU, memory, disk, and network before I open a single profiler — it stops me from optimizing a resource that was never the bottleneck."
One-line summary

Low-level observability is your APM instinct sunk beneath the process boundary: the PMU and IPC tell you why a core is busy (§2), perf/eBPF/ftrace let you sample or trace the kernel safely — with eBPF's verifier making it safer than a kernel module (§3–§5), the user-space and packet tools cover the rest (§6), and the hardware's own channels — MCE, ECC/EDAC, PCIe AER, thermal, and the always-on BMC SEL — are structured error events you read like logs (§7); scale that reading across a fleet by grouping structured signals to separate a flaky node from a systemic fault (§8), and keep it disciplined with the USE method and a differential-diagnosis workflow (§9).

Terminology & Acronyms

Quick reference for the key terms in this chapter.

TermMeaning
APMApplication Performance Monitoring — request traces, RED metrics, and logs answering "which service or endpoint is slow?"
TracepointA named, stable static hook the kernel authors placed at meaningful events, with documented fields and low overhead.
kprobe / uprobeDynamic probes attached at runtime to (almost) any kernel function (kprobe) or user-space function (uprobe); ret variants fire on return.
USDTUser Statically-Defined Tracepoints — stable trace markers a developer compiles into an application.
PMUPerformance Monitoring Unit — per-core hardware registers that count micro-architectural events (cycles, cache-misses).
IPCInstructions Per Cycle — instructions retired divided by core cycles; low IPC (< ~1) signals a stalled core.
perfThe standard Linux profiler on the perf_event subsystem; counts PMU events (perf stat) and samples stacks (perf record).
Flame graphA visualization of thousands of sampled stacks: x-axis is the share of samples (not time), y-axis is stack depth; the widest leaf is the biggest self-time hotspot. An on-CPU graph shows only running time; an off-CPU graph traces descheduled/waiting time.
eBPFExtended Berkeley Packet Filter — sandboxed programs run inside the kernel to aggregate trace data safely at low overhead.
VerifierThe in-kernel checker that statically proves an eBPF program terminates and never accesses memory out of bounds before load.
bcc / bpftraceThe two dominant eBPF front-ends: bcc's ready-made tool suite, and bpftrace's awk-like language for one-liners.
ftraceThe kernel's built-in tracer, driven via tracefs; its function_graph tracer shows nested call trees with per-function durations.
USE methodA resource-health framework: for each resource check Utilization, Saturation, and Errors.
MCA / MCEMachine-Check Architecture — the CPU's hardware error-reporting mechanism; a Machine-Check Exception (#MC) is raised on an uncorrected error.
CMCICorrected Machine-Check Interrupt — signals corrected machine-check errors without raising the #MC exception.
ECCError-Correcting Code memory — redundancy that corrects single-bit and detects double-bit memory errors.
SECDEDSingle-Error-Correct, Double-Error-Detect — the standard ECC scheme: fix one flipped bit, catch two.
EDACError Detection and Correction — the Linux subsystem that surfaces memory errors and attributes them to a DIMM/rank.
PCIe AERPCI Express Advanced Error Reporting — classifies link/device errors as correctable, uncorrectable non-fatal, or uncorrectable fatal.
TLPTransaction Layer Packet — the PCIe transaction unit; a replayed TLP is a recovered correctable link error.
BMCBaseboard Management Controller — an always-on management sidecar that reports box health even when the OS is down.
SELSystem Event Log — the BMC's timestamped record of sensor threshold crossings, power, thermal, and hardware faults.
IPMIIntelligent Platform Management Interface — the older low-level binary standard for talking to the BMC.
RedfishThe modern RESTful HTTPS + JSON successor to IPMI for BMC access, designed for fleet-scale automation.
