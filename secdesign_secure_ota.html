Secure OTA Updates

Updating software over-the-air across a whole fleet — without bricking devices or letting an attacker push malicious code
📚 Google Security Systems — Overview  ›  Part VII · Chapter 10 — Secure OTA Updates

What is OTA, and why is it dangerous?

OTA = "over-the-air." It just means pushing a new version of the software to a device remotely, over the network, instead of plugging in a cable. Your phone does it. Your car does it. A smart thermostat, a payment terminal, a Wi-Fi router, a warehouse robot — all pull down new firmware from the internet.

Analogy: OTA is like mailing every household in a country a new front-door lock and trusting them to install it themselves — all on the same day, unsupervised. If the lock is good, great, everyone is safer. If the lock is broken, you just jammed a million front doors shut at once. And if a crook can slip a fake lock into the mail, they now have a key to every house.

The tiny concrete example

Imagine a company ships 2 million smart doorbells. They push an update at 2pm. The update has a bug that crashes the device on boot. By 2:15pm, 2 million doorbells are dead bricks — and because they can't boot, they can't download a fix either. There is no "just redeploy." Someone may have to physically touch every unit. That is a company-ending event.

The two reasons OTA is the most dangerous code path on a device

DangerWhy it's uniquely bad
A bad update can brick the whole fleetUnlike a web server you can roll back in seconds, a bricked embedded device is unreachable. The damage is physical and often irreversible at scale.
The update channel is an attack vectorWhoever controls "what code runs next" controls the device. If an attacker can push firmware, they own every device — silently, permanently, remotely. It's the ultimate backdoor.

The mental model for the whole chapter: two enemies at once — your own bugs (reliability: never brick) and a malicious pusher (security: only authentic code runs). A serious OTA design must beat both, and the techniques are different: crypto stops the attacker, staged rollout + rollback stop your own mistakes.

Interview angle: When asked "design secure OTA," open by naming the stakes in one line: "An update mechanism is the most powerful and most dangerous code path on a device — it can brick the entire fleet or, if abused, hand an attacker full control. So I'm optimizing for two things at once: only authentic code ever runs, and a bad release can never take down more than a tiny slice before we catch it." That framing signals seniority immediately.

Signed updates & the chain of trust

The single most important rule: a device must never run code it can't prove came from the real vendor. The tool for that is a digital signature, also called code signing.

Analogy: think of a wax seal on a royal letter. Anyone can read the letter (it's not secret), and anyone can carry it — but only the king has the ring that makes the seal. If the seal matches the king's ring, you know two things: the letter really came from the king (authenticity) and nobody edited it on the way (integrity). A digital signature is that wax seal, done with math.

The tiny concrete example

The vendor's build server produces firmware-v42.bin. It runs a hash over the file (say SHA-256) to get a short fingerprint, then signs the fingerprint with its private key. It ships firmware-v42.bin + signature. The device recomputes the hash and checks the signature against the vendor's public key, which was burned into the device at the factory. Match → run it. No match → refuse and stay on the old version.

# On the build server (trusted; private key lives in an HSM —
# a Hardware Security Module, a tamper-resistant chip that holds keys)
hash = sha256(firmware_v42.bin)
signature = sign(hash, private_key)      # only the vendor can do this
publish(firmware_v42.bin, signature, version=42)

# On the device (untrusted network in between)
if verify(sha256(image), signature, public_key):  # public key baked in at manufacture
    install(image)
else:
    reject("unauthentic image — refusing to run")

Why asymmetric keys, not a shared password?

  • Public/private (asymmetric) signing means the device only ever holds a public key. A public key can verify a signature but cannot create one. Crack open one device, dump its memory, and you learn nothing that lets you forge updates.
  • A shared secret (like an HMAC key — HMAC is a keyed hash that both sides compute with the same secret to check authenticity) would have to live on every device. Extract it from a single unit and you can now sign malicious firmware for the entire fleet. Fatal.

The chain of trust — and the link to Chapter 9

A signature is only as trustworthy as the key you check it against, and that key is only trustworthy if the thing checking it is trustworthy. So trust chains downward to something unforgeable in hardware:

This is exactly where OTA consumes the work from Chapter 9 (Device Provisioning & Identity): provisioning is what burned the vendor's public key (and the device's own identity) into the hardware at the factory. OTA reuses that same root of trust to verify every future update. Device identity also lets the fleet server authenticate which device is asking, using the provisioned identity (e.g., a mutual-TLS client certificate — mutual TLS means both ends prove who they are, not just the server) — the natural sequel to giving the device an identity is safely evolving the code it runs.

Privacy note: a per-device identity plus continuous check-ins is powerful, but it also makes every device (and by extension its user) individually trackable, and health/crash payloads can carry sensitive data. So minimize and aggregate: collect only the signals the health gate actually needs, prefer coarse or anonymized telemetry over per-device records, and treat the update identifier as sensitive rather than a convenient tracking handle.

Integrity & authenticity vs. confidentiality

A common beginner mistake is to reach for encryption first. But encryption solves the wrong problem here:

PropertyQuestion it answersToolNeeded for OTA?
Integrity"Was it changed in transit?"HashYes — always
Authenticity"Did it really come from the vendor?"SignatureYes — always
Confidentiality"Can eavesdroppers read it?"EncryptionOptional

Key point: Sign always; encrypt only if you must. The firmware blob can be fully public — sitting on a CDN (content delivery network — a mesh of edge servers that cache files close to users), cached, visible to anyone — and it's still safe, because tampering breaks the signature and the device refuses to run it. You only add encryption when the firmware contents are a secret worth hiding (anti-reverse-engineering, protecting IP), and that adds key-distribution complexity. Confidentiality is a bonus; authenticity+integrity are the requirement.

Interview angle: Say the exact sentence "sign the hash on the server, verify against a built-in public key on the device, before running anything." Then pre-empt the follow-up: "the image itself can be public on a CDN — authenticity comes from the signature, not from keeping the blob secret." Naming the integrity/authenticity/confidentiality split out loud is a strong senior signal.

Anti-rollback & version pinning

Here's the subtle attack that confuses people. A signature proves an image is authentic — but an old vendor image is also authentic. Its signature is perfectly valid.

Analogy: imagine a bank accepts any check that carries a genuine signature — even a real check you wrote and cashed last year. An attacker fishes an old, already-used check out of the trash and re-deposits it. The signature is real; the check is stale. That's a downgrade (rollback) attack: replaying a genuinely-signed old version.

The tiny concrete example

Version 41 of your firmware had a serious security hole. Version 42 patched it. An attacker intercepts the update and feeds the device the real, signed v41 instead. The device checks the signature — valid! — installs v41, and is now vulnerable again. The attacker didn't need to forge anything; they just rewound time.

The fix — anti-rollback / version pinning: the device must reject any version lower than what it has already run. It keeps a monotonic (only-ever-increases) version counter, ideally stored in write-once hardware such as a fuse or a secure counter, so even physical tampering can't rewind it. Rule: accept only if new_version >= min_allowed_version. Crucially, the version must be inside the signed payload — sign the hash of version || image together, not the image bytes alone. If the version rides as unsigned metadata, an attacker replays an old, still-validly-signed image with a relabeled high version number and passes both the signature check and the floor check, silently defeating anti-rollback.

# Signature valid AND version not a downgrade
if verify(image, signature, public_key)
   and image.version >= device.min_allowed_version:   # anti-rollback
    install(image)                                      # write to spare slot; floor NOT raised yet
else:
    reject("downgrade or unauthentic — refused")

# ...later, only after a healthy trial boot is confirmed:
def commit(image):
    device.min_allowed_version = image.version          # monotonic bump, in a fuse/secure counter

Version pinning vs. legitimate rollback — the nuance

But wait — didn't we say rollback is how we recover from a bad update? Yes. So there are two different "rollbacks," and confusing them is a classic trap:

Recovery rollback (good)Downgrade attack (bad)
Who triggers itThe device / bootloader, locally, when a new boot fails its health checkAn attacker on the network, forcing an old signed image
What it reverts toThe previous known-good slot the device just came fromAn arbitrary old, vulnerable version
Version counterStays put — you never committed the new version, so the floor didn't riseWould need to move the floor down — which anti-rollback forbids

Resolution: the anti-rollback floor only rises when an update is committed (confirmed healthy). A trial boot that fails reverts to the slot you were already on — that isn't a downgrade because you never accepted the new version in the first place. So local recovery and anti-rollback coexist cleanly.

Interview angle: Raise the downgrade attack before the interviewer asks — "signature alone isn't enough; I need anti-rollback, because an old signed image is still validly signed." Then immediately distinguish it from recovery rollback. A common follow-up probes "an attacker replays an old signed firmware with a known bug — stop it?" Having the monotonic-counter-in-hardware answer ready is a differentiator.

Staged & canary rollouts

Crypto stops the malicious pusher. But it does nothing about your own bug — a perfectly signed, perfectly authentic update that happens to crash on boot. The defense against that is to never ship to everyone at once.

Analogy: a chef tasting a new recipe doesn't cook it for all 500 dinner guests at once. They make one plate, taste it, then a table of four, then a section of the room — checking after each step. If it's bad, at most a few plates are wasted, not the whole banquet. That first tiny taste is the canary; growing it table-by-table is the staged (phased) rollout.

The tiny concrete example

You have 2 million devices. Instead of "push to all," you push to 0.1% (2,000 devices) first and watch. Do they check back in healthy? Crash rate normal? If yes, go to 1%, then 10%, then 50%, then 100% — each step gated on health metrics. If the canary looks sick, you auto-halt: new devices simply stop being offered the bad version. Worst case you harmed 2,000 devices, not 2 million.

What makes a rollout "staged" well

  • Cohorts / rings: split the fleet by ring (internal → beta → production) or by model, region, or hardware revision. This catches model-specific breakage before wide release.
  • Health gates: advance only when telemetry (install-success rate, crash rate, check-in rate, key device metrics) stays within thresholds. Automate the gate where you can.
  • Auto-halt & pause/abort controls: if the failure rate crosses a limit, the rollout pauses itself. Operators can also pause or abort manually — an emergency stop button.
  • Emergency lane: a critical security patch may roll faster (higher starting %, push instead of poll) — but still staged. A bad emergency patch that bricks the fleet is worse than the bug you were fixing.

Tie to the Operational Excellence chapter: this is the exact same discipline as canary deployments and progressive delivery for services — deploy to a small blast radius, watch signals, automate rollback on regression, and gate promotion on health. OTA just raises the stakes because the "servers" are millions of physical devices you can't SSH into. The Op-Ex habits (canary, monitoring-driven gates, automatic rollback) map straight across.

Staged rollout is a SECURITY property too, not just reliability. It bounds the blast radius. Even if a signing mistake or a compromised build slips through, phased delivery + auto-halt means it reaches a tiny fraction of devices before you stop it. Same "limit the damage of any single failure" theme that runs through all of security design.

Interview angle: Frame staged rollout as defending against your own fallibility: "Crypto assumes the vendor is honest and correct — but I might ship a bug. Canary + phased rollout + automatic halt means a bad release, malicious or merely buggy, can never harm more than a small, bounded slice of the fleet." Connecting it explicitly to canary deploys from operational excellence shows breadth.

A/B partitions, atomic apply & auto-rollback

Staged rollout limits how many devices get a bad update. But what protects the individual device — so that even a device that did get the bad update, or lost power mid-install, still survives? The answer is A/B (dual-slot) partitions.

Analogy: a trapeze artist doesn't let go of one bar until they've got a firm grip on the next. The device keeps its current, working firmware untouched (bar A) while it prepares the new one (bar B). Only when B is fully written, verified, and confirmed healthy does it truly let go of A. Miss the grab? Swing back to A. No fall, no brick.

The tiny concrete example

The device has two storage slots. It's running Slot A. The new firmware is downloaded and written entirely into Slot B — A is never touched. Its signature is verified in place. Then the bootloader is told "next boot, try B." The switch is a single atomic flag flip. If power dies mid-download, B is just garbage and the device boots A as if nothing happened. No half-installed, no brick.

The three ideas that make it "never brick"

  • Atomic apply: the change from A to B is a single instantaneous flag flip that either fully happens or doesn't. There is no in-between, half-updated state that could leave the device unbootable.
  • Trial boot + health check: the device boots B once, on probation. It must actively confirm it's healthy (check in with the server, pass a self-test, or pet a watchdog timer). If it doesn't confirm, the bootloader assumes the worst.
  • Automatic rollback on failure: a failed trial boot → the bootloader flips back to A on the next reboot, with zero human involvement. The device self-heals to the last known-good version.

The cost: A/B needs roughly 2× the firmware storage. That's the price of "never brick." Very constrained microcontrollers may instead keep a tiny immutable recovery image that can always re-download — cheaper storage, but a failed update means downtime until recovery completes. Know both, and state the trade-off.

Supply-chain concerns — signing a compromised build

One more threat: what if the attacker doesn't break the crypto at all, but instead poisons the software before it gets signed — a malicious dependency, a tampered build server, a rogue commit? Then you'd faithfully sign and ship malware. Signing proves who built it, not that it's safe.

  • Provenance / build integrity: only artifacts produced by the trusted, reproducible build pipeline get signed — akin to Binary Authorization in BeyondProd. "Signed" then also means "built and reviewed properly," not just "came from us."
  • Protect the signing key: keep the private key in an HSM; use offline / quorum control for the root key so no single person or compromised host can mint firmware.
  • Key rotation & a key set: devices trust a set of keys (or a key hierarchy) so you can rotate the signing key or revoke a compromised one without bricking devices that only knew the old key.
  • Dependency & SBOM hygiene: track what goes into the image (software bill of materials) so a compromised third-party component can be found and rebuilt fast.

Interview angle: The follow-up "what if the signing key is compromised?" is common. Answer with layers: rotate to a new key devices also trust, revoke the old one, and note that anti-rollback + provenance (only trusted-pipeline builds get signed) + staged rollout all limit the damage even during the window of compromise. Then add: "and the root key is offline/quorum-controlled, so this is rare in the first place." Layered defense, not a single fix.

The secure update flow, end to end

Now let's put every piece in order and watch it run. Step through the flow below — from the vendor signing a build all the way to the device either committing the new version or rolling back to safety.

Step 0 / 7 — ready
Ready. Press Step to walk the secure OTA flow: sign → distribute → verify → stage/canary → trial-boot → commit or rollback.

The same flow as a timeline

  1. Sign (vendor): the trusted build pipeline builds the image, an HSM signs its hash, and it's published with version + metadata. Provenance ensures only genuine builds get signed.
  2. Distribute: the signed image lands on a CDN — public, cacheable, cheap to serve to millions. The origin only serves signed metadata and rollout decisions, never the mass of downloads.
  3. Verify (device): the device checks the signature against its built-in public key and confirms the version isn't a downgrade. Fail either → discard, stay put, report failure.
  4. Stage / canary: the server only offers the update to the current rollout cohort, starting tiny. Blast radius is bounded from the first byte.
  5. Install & trial-boot: written to the inactive Slot B (A untouched), then booted on probation with a health check.
  6. Commit or rollback: healthy → commit (bump the anti-rollback floor, advance the rollout). Unhealthy → automatic revert to Slot A, and the rollout auto-halts.

Interview angle: Draw this flow as your backbone diagram, then hang each defense on the matching step: signature+provenance on sign/verify, anti-rollback on verify, CDN+delta+poll+jitter on distribute, canary+auto-halt on stage, A/B+atomic+trial-boot on install, health-gated commit/auto-revert on the final step. One picture, every requirement accounted for.

Interview angle system design

"Design a secure OTA update system for millions of devices" is a rich prompt because it forces you to balance security (only authentic code runs) against reliability (never brick), at scale. Lead with the one-sentence model, then layer the defenses.

The one-sentence model

Say this: "The vendor signs every image; each device verifies that signature against a key provisioned at manufacture and refuses any downgrade before running it; updates roll out gradually with health checks; and each device applies atomically to a spare slot with automatic rollback — so a bad or malicious image can never brick the fleet or run unverified."

Likely questions & how to answer

Q: "How do you stop an attacker from pushing malicious firmware?"

Asymmetric code signing: server holds the private key in an HSM, devices hold only the public key (provisioned at manufacture, Ch 9), and verify before running. A public key can't forge anything, so cracking one device teaches an attacker nothing.

Q: "An attacker replays a genuinely-signed old version with a known bug?"

Anti-rollback: the device keeps a monotonic version floor (ideally a hardware fuse/secure counter) and refuses anything below it. A valid signature isn't enough — old signed images are still validly signed.

Q: "Power dies mid-update — do you brick the device?"

No. A/B slots: the running Slot A is never touched; the new image goes to Slot B and the switch is a single atomic flag. Power loss just boots A again. Trial boot + health check + auto-revert handle a bad-but-complete image.

Q: "A buggy (but authentic) update slips through — limit the damage?"

Staged/canary rollout with health-gated promotion and automatic halt — same discipline as canary service deploys. A bad release reaches a small, bounded cohort before it's stopped; affected devices self-heal via auto-rollback.

Q: "Millions of devices, limited bandwidth?"

Put the public signed blob on a CDN (authenticity is by signature, not secrecy); ship delta/diff images; have devices poll with jitter and concurrency caps to avoid a thundering herd; ingest status reports via a queue.

Q: "Signing key compromised, or a poisoned build?"

Key rotation over a trusted key set + revocation; root key offline/quorum in an HSM; and build provenance (only trusted-pipeline artifacts get signed) so "signed" means "built properly." Anti-rollback + staged rollout limit the blast radius during any window of compromise.

Closing line: "The through-line is layered defense: authenticity by signature (never a shared secret), verify-before-boot chained to a hardware root of trust, no downgrades, never overwrite the running image, and roll out gradually with automatic rollback — so both a malicious push and a merely buggy release are contained. It's the natural sequel to giving the device its identity in Chapter 9."
