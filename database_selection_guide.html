The Decision Framework

In a system-design interview, "which database?" is never answered by naming a favorite product. It is answered by deriving the store from the workload. The signal an interviewer is grading is whether you can state requirements, translate them into properties a datastore must have, and then justify a choice against explicit trade-offs. A great answer sounds like: "Reads are 100:1 over writes, we need single-digit-millisecond point lookups by key at 500k RPS, the data is a self-contained document, and we can tolerate reading data that is a few seconds stale — so I'll use a partitioned key-value/document store and front it with a cache."

🧮 The funnel: requirements → properties → store
  1. Enumerate access patterns first. List every read and write the feature performs, keyed by how it looks data up (by primary key? by secondary attribute? by range? full-text? aggregation?). The access pattern, not the data, dictates the store — especially for non-relational engines where you model the table around the query.
  2. Quantify. Read/write ratio, peak QPS, object size, total dataset size, growth rate, and the latency budget (p50 and p99).
  3. Fix the correctness bar. Do you need strong consistency and multi-item transactions, or is eventual consistency acceptable? What must survive a region failure?
  4. Match to a data model. Relational, key-value, document, wide-column, columnar-analytical, search, or blob.
  5. Check it scales & costs out. Can it partition to your data size and QPS? What is the $ and the operational burden (managed vs self-run, failover, backups, schema changes)?
  6. Consider polyglot. The right answer is frequently more than one store — a system of record plus a cache, an index, and an analytics sink.
Interview meta-tip: Say "it depends" only if you immediately name what it depends on. "It depends on the read/write ratio and whether we need cross-item transactions" is a strong sentence; "it depends" alone is a non-answer. Always close with a concrete recommendation and one sentence naming what you gave up.
OLTP vs OLAP is the first fork. If the workload is many small, latency-sensitive point operations serving live traffic, you are in OLTP territory (MySQL, Postgres, DynamoDB, Cassandra, MongoDB, Redis). If it is a few large scans that aggregate over huge historical datasets for dashboards/ML, you are in OLAP territory (BigQuery, Redshift, Snowflake, ClickHouse). Trying to serve OLAP from an OLTP row-store — or user-facing reads from a columnar warehouse — is the single most common mismatched answer.

The Seven Decision Dimensions

Every datastore choice is a point in this seven-axis space. Walk them explicitly and the recommendation writes itself.

1 · Access patterns — model around the query▶
  • Point lookup by key (get value for id) → key-value / document / any indexed store. Cheapest possible operation.
  • Lookup by non-key attribute → you need a secondary index (relational secondary index, DynamoDB GSI, MongoDB secondary index).
  • Range / ordered scan (latest N per key, time windows) → a store that keeps data sorted: relational B+tree, Cassandra clustering columns, DynamoDB sort key.
  • Ad-hoc joins across entities → relational (MySQL/Postgres). NoSQL forces you to denormalize or do client-side joins.
  • Full-text / relevance search → a search engine (Elasticsearch/OpenSearch), not LIKE '%term%'.
  • Large aggregations over history → a columnar warehouse (BigQuery).
NoSQL rule: in relational you design the schema, then write queries. In DynamoDB/Cassandra you start from the queries and design a table (partition key + sort key) that answers each one with a single partition read. If a new query needs a different key, you add a new table/index — you do not JOIN.
2 · Consistency vs availability (CAP / PACELC)▶

How fresh must a read be, and what happens during a network partition or region failure? A store that chooses availability will keep serving (possibly stale) data during a partition; a store that chooses consistency may reject requests to avoid divergence. See the CAP / PACELC section for the full treatment. Money movement and inventory decrements usually need strong consistency and transactions; a "likes" counter or a feed can tolerate eventual consistency.

3 · Read/write ratio & throughput▶
  • Read-heavy (e.g. 100:1): add read replicas and a cache (Redis). Reads scale horizontally cheaply; the hard part is cache invalidation and replica lag.
  • Write-heavy (ingest, metrics, chat): favor LSM-tree engines (Cassandra, ScyllaDB, RocksDB-backed stores) that turn random writes into sequential appends, versus B+tree stores that do random-write-in-place. Also consider buffering writes through a log (Kafka).
  • Throughput ceiling of a single primary: a single well-tuned MySQL/Postgres primary handles thousands to low-tens-of-thousands of write TPS. Beyond that you shard or move to a natively-partitioned store (DynamoDB/Cassandra) that scales writes linearly with nodes.
B+tree vs LSM in one line: B+tree = read-optimized, write-amplifies via in-place random page writes. LSM = write-optimized for incoming random writes (sequential appends), but pays read amplification and its own write amplification from background compaction (hence compaction tuning). Match the tree to your dominant operation.
4 · Data-model fit▶

Force-fitting a model is expensive forever. Relational for highly-related, normalized entities with ad-hoc queries; document for self-contained aggregates with flexible schema; wide-column for massive time-ordered/partitioned data; key-value for pure lookups; columnar for analytics; graph for deep relationship traversal; search for text. See Data Models.

5 · Scale & partitioning▶
  • Vertical scaling (bigger box) is the simplest lever and buys a lot; use it before sharding.
  • Partitioning/sharding key choice is the highest-leverage decision. A good key spreads load evenly and keeps each query on one partition. A bad key creates a hot partition (e.g. partitioning chat by date so all of today's traffic hits one node).
  • Natively-sharded stores (DynamoDB, Cassandra, MongoDB sharded clusters, BigQuery) rebalance for you; manually-sharded relational (via Vitess or app-level routing) puts that burden on you, and cross-shard transactions/joins get expensive (distributed 2PC).
  • Consistent hashing minimizes data movement when adding/removing nodes.

7 · Cost & operational burden▶
  • Managed vs self-hosted: managed (DynamoDB, BigQuery, Aurora, Atlas) trades $ for far less operational toil — no patching, backups, or failover to run yourself. In interviews, prefer managed unless there's a reason not to, and say why.
  • Pricing model shapes design. DynamoDB bills read/write capacity (and storage) — a hot-partition or full-scan pattern is directly a cost bug. BigQuery on-demand bills by bytes scanned, so partitioning, clustering, and SELECT-only-needed-columns are cost controls, not just perf tuning.
  • Operational burden includes schema migrations, resharding, version upgrades, backup/restore, and on-call. A store your team can actually run beats a theoretically-superior one they can't.

CAP and PACELC — Say It Precisely

Vague, imprecise CAP answers hurt you in interviews — be precise.

⚖ CAP theorem (Brewer)

During a network partition (P), a distributed store must choose between Consistency (C) — every read sees the latest write (linearizability) — and Availability (A) — every request gets a non-error response. You cannot have both while partitioned. Crucially, P is not optional in a real distributed system (networks fail), so the meaningful choice is CP vs AP during a partition. "CA" describes a single node, not a distributed system.

  • CP (consistency during partition): reject/limit requests on the minority side to avoid divergence. Examples: MongoDB (primary-based), HBase, ZooKeeper/etcd, Spanner.
  • AP (availability during partition): keep accepting reads/writes on all sides, reconcile later. Examples: Cassandra, Riak, and the original 2007 Amazon Dynamo paper (vector clocks + client-side conflict merge + sloppy quorums). Note the managed DynamoDB service is different: each partition uses a single leader + quorum replication (leaning CP for writes), but defaults to eventually-consistent reads and is engineered to prioritize availability operationally. The "accept on all sides, reconcile later" model applies to multi-region Global Tables (last-writer-wins) and the classic Dynamo paper, not to single-region writes.
⏱ PACELC — the more useful model

CAP only describes behavior during a partition, which is rare. PACELC (Abadi) adds the common case: if Partition, choose Availability or Consistency; Else (normal operation), choose Latency or Consistency. Even with no partition, replication forces a trade — waiting for replicas to acknowledge (consistency) costs latency.

StorePACELC classificationMeaning
DynamoDB / CassandraPA / EL (tunable)Favor availability under partition; favor low latency normally (eventual consistency by default). Both can be tuned toward consistency per request (strongly-consistent read / QUORUM).
MongoDBPC / EC (tunable)Primary-based: consistency-leaning, but read preference / read & write concern let you relax it.
MySQL / Postgres (async replica)PC / ELPrimary is the consistent source of truth; async replicas are lower-latency but stale (replica lag).
Google SpannerPC / ECChooses consistency in both cases (TrueTime + Paxos); pays latency to stay externally consistent.
Tunable consistency is the pragmatic reality. Cassandra and DynamoDB aren't strictly "AP" — they let you dial consistency per operation. Cassandra: choose ONE, QUORUM, or ALL for reads and writes; if R + W > RF (replication factor) the read and write quorums overlap, so a read is guaranteed to see the latest acknowledged write (strong consistency). DynamoDB: default reads are eventually consistent (cheaper, lower latency); request a strongly consistent read for the latest value within a region. Global Tables replicate across regions with last-writer-wins and are eventually consistent between regions.
Don't claim "strong consistency" for free. If you say a design is strongly consistent, be ready to name the mechanism (single primary, quorum, consensus like Raft/Paxos) and the cost you pay (write latency, reduced availability during failover, or a leader bottleneck).

Data-Model Fit

Relational (MySQL, Postgres)
  • Normalized tables, foreign keys, ad-hoc JOINs, ACID transactions.
  • Best when relationships and consistency matter and query shapes evolve.
  • Cost: single-primary write ceiling; sharding is manual and joins/txns break across shards.
Key-Value (Redis, DynamoDB)
  • Get/put by key; O(1) lookups; trivially partitionable.
  • Best for caches, sessions, and any "fetch this blob by id" path.
  • Cost: no ad-hoc queries; secondary access needs extra indexes/tables.
Document (MongoDB)
  • Self-contained JSON/BSON aggregates; flexible schema; nested arrays.
  • Best when one read returns one whole entity (product, profile, order).
  • Cost: cross-document joins are weak; unbounded document growth is an anti-pattern.
Wide-Column (Cassandra)
  • Partition key + clustering columns keep rows sorted within a partition.
  • Best for write-heavy, time-ordered, per-key data at massive scale.
  • Cost: query-first modeling, no joins, must denormalize; beware unbounded partitions.
Columnar / OLAP (BigQuery)
  • Column-oriented storage + vectorized execution; scans billions of rows fast.
  • Best for aggregations, reporting, ML feature generation.
  • Cost: not for row-level point reads/writes or live user traffic.
Search / Graph / Blob
  • Search (Elasticsearch): inverted index for text/relevance.
  • Graph (Neo4j/Neptune): fast pointer-following traversals — Neo4j's native engine uses index-free adjacency (O(1) per hop); managed Neptune resolves hops via index lookups rather than true index-free adjacency.
  • Blob (S3): the bytes; DB holds the pointer.

Eight Classic Interview Scenarios

Each maps a prompt to a recommended store via the framework. State the deciding dimension, then commit.

1 · URL shortener▶

Access pattern: write once (create short code → long URL), read many by exact key. Extremely read-heavy, tiny objects, no joins, no range scans.

Recommend: Key-value store — DynamoDB or Cassandra keyed on the short code, fronted by a Redis cache for the most-requested links. A single MySQL/Postgres table also works fine at moderate scale and gives you a free auto-increment counter for base62 code generation.

Why: the workload is a pure point lookup by primary key — the simplest, most partitionable operation. There is nothing relational here, so a KV store scales reads and writes linearly and stays sub-10 ms; the cache absorbs the viral-link read spikes. Choose a strongly-consistent read only on create to avoid duplicate codes; reads can be eventually consistent.

2 · Social feed / timeline▶

Access pattern: read a user's timeline (latest N posts from people they follow) with very low latency; writes fan out to many followers. Read-dominated, staleness of a few seconds is fine.

Recommend: Redis (sorted set / list per user) as the precomputed timeline cache, backed by a durable wide-column/KV store (Cassandra or DynamoDB) for posts and the follow graph. Media in object storage.

Why: fan-out-on-write pushes each new post into followers' Redis timelines so reads are O(1) list slices. Eventual consistency is acceptable for a feed. Use fan-out-on-read (query at read time) for celebrity accounts with millions of followers to avoid write amplification — a hybrid is the mature answer.

3 · Chat / messaging▶

Access pattern: very high write throughput; read recent messages per conversation in time order; effectively infinite history.

Recommend: Cassandra (or DynamoDB) with partition key = conversation_id and clustering key = message_ts (descending). Recent conversations/unread counts in Redis.

Why: LSM-tree write path suits the write-heavy ingest; partitioning by conversation keeps all of one chat's messages co-located and sorted, so "last 50 messages" is a single-partition sorted range read. Watch the hot/large partition: a hugely active group could create an unbounded partition — bucket by (conversation_id, month) to cap partition size.

4 · Metrics / time-series▶

Access pattern: huge volume of timestamped writes; queries are range scans over time windows plus downsampling/retention.

Recommend: a purpose-built time-series DB (Prometheus, InfluxDB, TimescaleDB) for live monitoring; among the matrix stores, Cassandra partitioned by (series_id, time_bucket) serves as a scalable TSDB. Pipe raw events through Kafka and land history in BigQuery for long-range analysis.

Why: time-series needs write-optimized storage, time-bucketed partitioning, retention/TTL, and downsampling — exactly what TSDBs specialize in and what a B+tree OLTP store handles poorly. Keep hot recent data in the TSDB; roll up cold data into the warehouse.

5 · Analytics / reporting dashboards▶

Access pattern: large aggregations (GROUP BY, joins, window functions) over months of historical data; few concurrent analysts; latency of seconds is fine.

Recommend: BigQuery (or Redshift/Snowflake/ClickHouse). Ingest via streaming or batch load; partition and cluster tables on the common filter columns.

Why: columnar storage reads only the referenced columns and compresses aggressively; vectorized/distributed execution scans billions of rows in seconds — 10–100× faster than a row-store for scans. Never run these on the OLTP primary — a heavy analytical scan can starve live user traffic. Replicate/ETL into the warehouse instead. On-demand BigQuery bills by bytes scanned, so partition pruning and column selection are cost controls.

6 · Session store▶

Access pattern: read/write a small session blob by session id on nearly every request; must be fast; entries expire.

Recommend: Redis with a per-key TTL (or DynamoDB with TTL for a fully-managed, durable option).

Why: in-memory sub-millisecond get/set with native expiry is exactly the session workload. Losing a session on a rare cache flush is usually acceptable (user re-logs in); if not, enable AOF persistence or use DynamoDB. Do not keep sessions in a relational DB — it's needless disk I/O on the hottest path.

7 · Leaderboard / ranking▶

Access pattern: update a score, then read top-N and a player's rank in real time.

Recommend: Redis sorted set (ZSET): ZADD board score member, ZREVRANGE board 0 9 WITHSCORES for top-10, ZREVRANK board member for a player's rank.

Why: a sorted set keeps members ordered by score with O(log N) updates and O(log N + M) range reads — computing rank in any other store means an expensive sort/scan per read. Persist the authoritative scores in a durable store and treat Redis as the fast ranking index.

ZADD game:leaderboard 4820 "player:42"
ZINCRBY game:leaderboard 150 "player:42"
ZREVRANGE game:leaderboard 0 9 WITHSCORES   # top 10
ZREVRANK  game:leaderboard "player:42"       # 0-based rank
8 · Shopping cart▶

Access pattern: read/write a cart by user id; must stay available (an unavailable cart loses sales); writes are frequent; data is self-contained per user.

Recommend: DynamoDB keyed on user_id (the canonical Amazon Dynamo use case), optionally cached in Redis.

Why: availability > strict consistency here — you'd rather accept an "add to cart" than reject it, and a stale cart read is tolerable. A KV store keyed by user gives a single-partition read of the whole cart and scales horizontally. Managed DynamoDB delivers the high availability you want (and defaults to eventually-consistent reads). It was the classic 2007 Dynamo paper — not today's managed DynamoDB — that let all replicas accept writes and tolerated conflicting versions, merging them client-side via vector clocks (a re-added item reappearing beats losing the sale). Checkout, however, moves to a strongly-consistent, transactional path (inventory decrement + payment), e.g. DynamoDB transactions or a relational store.

Polyglot Persistence

Real systems rarely use one store. Polyglot persistence means using the right tool per access pattern and keeping them in sync. The senior move in an interview is to name a system of record (SoR) — the single source of truth — and treat every other store as a derived view fed from it.

Fig 1: Writes hit the system of record; derived stores (cache, search, warehouse, blob) are kept in sync via change-data-capture / an event log.
🔁 Keeping derived stores in sync
  • Cache-aside for Redis: on read miss, load from SoR and populate; on write, update SoR then invalidate/update the cache. Set TTLs to bound staleness.
  • Change Data Capture (CDC): tail the SoR's write log (e.g. MySQL binlog via Debezium) into Kafka, then fan out to the search index and warehouse. Decouples producers from consumers and gives replay.
  • Dual writes are an anti-pattern: writing to two stores from application code has no atomicity — a crash between writes leaves them inconsistent. Prefer CDC or the transactional outbox pattern.
Interview framing: "MySQL is my system of record for orders (ACID, transactions). I stream its binlog through Kafka into Elasticsearch for product search and into BigQuery for analytics, and I cache hot product reads in Redis. Each store owns a job it's best at; the SoR owns the truth." That one paragraph demonstrates polyglot thinking, CDC, and clear ownership.

Interview Q&A

Q: "SQL or NoSQL?" — what's the real answer?
Reject the false binary. The question is the access pattern and consistency need. Use relational when you need ad-hoc joins, multi-row ACID transactions, and evolving query shapes over related entities. Use a NoSQL store when your access patterns are known and narrow, and you need horizontal write scale or a specific model (KV, document, wide-column). Many systems use both. Name the deciding factor rather than picking a camp.
Q: When do you introduce a cache, and what breaks?
Introduce a cache when reads dominate and the latency budget is tight (sub-ms to low-ms) or the backing store is getting hot. What breaks: cache invalidation (stale reads), the thundering herd on a popular key expiring (mitigate with request coalescing / staggered TTLs), and cache stampede after a flush. Decide the pattern (cache-aside is default) and a staleness bound (TTL). Never let the cache become the source of truth unless you've made it durable on purpose.
Q: How do you pick a partition/shard key?
Pick a key with high cardinality that both (a) spreads writes/reads evenly and (b) co-locates data that's read together. Test it against your top queries: does each land on one partition? Then stress the worst case — is there a value (today's date, a celebrity user, one giant tenant) that concentrates load into one partition? If so, add a bucket/salt to the key. A hot partition caps your whole cluster at one node's throughput regardless of node count.
Q: Strong vs eventual consistency — how do you decide per feature?
Ask "what's the cost of a client reading slightly stale data?" For money, inventory, and uniqueness (usernames), the cost is high → strong consistency and transactions. For feeds, counts, recommendations, and analytics, brief staleness is invisible → eventual consistency buys availability and latency. On tunable stores, dial it per operation (DynamoDB strongly-consistent read on the critical path only; Cassandra QUORUM where correctness matters, ONE elsewhere).
Q: Why not just use one big relational database for everything?
It's a fine default and scales further than people think (replicas + caching + vertical scale). It stops fitting when: writes exceed a single primary's ceiling and sharding breaks your joins/transactions; the workload is analytical scans that starve OLTP; you need sub-ms in-memory access; the data is genuinely schema-less or text-search-shaped; or you need multi-region availability during partitions. Reach for a specialized store only when a measured requirement forces it — premature polyglot adds operational cost.
Q: How would you serve an OLTP app that also needs heavy analytics?
Separate the workloads. Keep the OLTP store (MySQL/Postgres/DynamoDB) for live traffic, and replicate changes via CDC/ETL into an analytical system (BigQuery/Redshift/ClickHouse). Analysts and dashboards query the warehouse; users never touch it. This is HTAP (Hybrid Transactional/Analytical Processing)-by-composition and avoids one workload degrading the other. Mention CDC (binlog → Kafka → warehouse) to show how the sync stays near-real-time.
Q: Interviewer says "1M writes/sec of telemetry." First move?
Don't point that firehose straight at a database. Buffer it through a partitioned log (Kafka) to absorb spikes and decouple producers, then consume into a write-optimized store: a TSDB or Cassandra (LSM-tree, partitioned by series + time bucket) for recent queryable data, and batch into object storage / BigQuery for history. Apply TTL/retention and downsampling. The key insights: LSM over B+tree for write-heavy, time-bucketed partitioning to avoid hot/unbounded partitions, and a log as a shock absorber.
