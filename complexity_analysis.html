Complexity Analysis

Big-O math foundations • Summation techniques • Recurrences • Master Theorem • Amortized analysis

Why analyze precisely instead of "going by feel"

The most common judgment call when working through problems is "will this solution time out / overflow?". Complexity analysis turns that "feel" into something "computable": given the upper bound on n, work out the order of magnitude of the operation count and compare it against the roughly 10^8 ~ 10^9 operations per second a machine can do — then you can tell whether it will TLE (Time Limit Exceeded).

Core mindset: complexity = "how the operation count grows as the input n gets large." We only care about the order of growth, not constants or lower-order terms — because once n is large enough, the highest-order term dominates everything.

The three asymptotic notations

NotationMeaningIn plain terms
O(f)Upper bound"at most" on the order of f — the one used most often
Ω(f)Lower bound"at least" on the order of f
Θ(f)Tight boundupper and lower bounds match — "exactly" on the order of f

The formal definition of Big-O

T(n) = O(f(n))  ⟺  there exist constants c > 0, n₀ such that for all n ≥ n₀,  T(n) ≤ c · f(n)

In plain terms: beyond some n₀, T(n) is forever held below c·f(n). The constant c lets us ignore coefficients, and n₀ lets us ignore the noise from small n.

Example: prove 3n² + 5n + 100 = O(n²)

We need to find c, n₀ such that 3n² + 5n + 100 ≤ c·n²
For n ≥ 1: 5n ≤ 5n², 100 ≤ 100n²
So 3n² + 5n + 100 ≤ 3n² + 5n² + 100n² = 108n²
Take c = 108, n₀ = 1 and it holds → it is O(n²) ✓

In practice you don't prove it like this. Just remember the rules: drop constant coefficients, keep only the highest-order term. 3n² + 5n + 100 → O(n²). The formal proof above explains "why you're allowed to drop them."

Simplification rules

  • Drop constant coefficients: O(3n) = O(n), O(n/2) = O(n)
  • Keep only the highest order: O(n² + n) = O(n²)
  • Addition takes the larger: two segments run back to back → O(f) + O(g) = O(max(f,g))
  • Multiplication multiplies: nesting → O(f) × O(g) = O(f·g)
  • The log base doesn't matter: log₂n and log₁₀n differ only by a constant factor → both written as O(log n)

Growth hierarchy — which beats which

From slow to fast (fewest to most operations as n grows). Memorize it — judging TLE relies entirely on it.

O(1) < O(log n) < O(√n) < O(n) < O(n log n) < O(n²) < O(n³) < O(2ⁿ) < O(n!)

For example, LC 1359 Count Orders with n ≤ 500 (O(n²) tabulation) and LC 1316 Echo Substring with n ≤ 2000 (O(n²)) are both judged this way.

Why log n shows up so often

log n = "how many times n can be divided by 2 until it reaches 1." Whenever each operation halves the problem size, you get O(log n):

n → n/2 → n/4 → ... → 1
After halving k times you reach 1: n / 2ᵏ = 1 → 2ᵏ = n → k = log₂n

That's why binary search, balanced trees, heap height, and fast exponentiation are all O(log n) — what they have in common is "halving at every step."

Summation techniques — the mathematical core of loop complexity

Analyzing a loop is essentially about adding up how many times each loop level runs. Master a handful of common series sums and you can compute it instantly.

1. Arithmetic series

1 + 2 + 3 + ... + n = n(n+1)/2 = Θ(n²)

Derivation (Gauss pairing):

S = 1 + 2 + ... + (n-1) + n
S = n + (n-1) + ... + 2 + 1  (written in reverse)
Add the two: 2S = (n+1) + (n+1) + ... + (n+1) = n copies of (n+1)
2S = n(n+1) → S = n(n+1)/2

This is why "a nested loop running a triangle" is O(n²). For example, the inner loop of LC 1359 Count Orders Σj = (2i-1)(2i)/2 = i(2i-1), and the double loop of LC 2563 Fair Pairs, both come down to this arithmetic sum.

2. Sum of squares

1² + 2² + ... + n² = n(n+1)(2n+1)/6 = Θ(n³)

3. Geometric series

1 + 2 + 4 + ... + 2ᵏ = 2^(k+1) − 1 = Θ(2ᵏ)

General form: 1 + r + r² + ... + rᵏ = (r^(k+1) − 1)/(r − 1)

Key insight: the sum of a geometric series ≈ its largest term. 1+2+4+...+n = 2n−1 ≈ 2n = O(n). So "the total work when the size halves each time" is O(n), not O(n log n) — the last level (the largest) already accounts for half of it. This counterintuitive fact is key in the Master Theorem and in build-heap analysis.

4. Harmonic series

1 + 1/2 + 1/3 + ... + 1/n = Θ(log n)

Use: analyzing loops like "for each i, mark its multiples." If you do it for every i (the naive marking method), the cost is Σ n/i = n·(1+1/2+...+1/n) = n·Θ(log n) = Θ(n log n). The real Sieve of Eratosthenes only marks for primes, so the sum becomes n·Σ_{p prime} 1/p = O(n log log n) — smaller. The difference is exactly "only iterate over primes" versus "iterate over every number."

Loop analysis — from code to Big-O

Method: work from the innermost level outward, count how many times each level runs, and multiply. Use summation when the bounds vary.

Example 1: fixed nesting → multiply

for (int i = 0; i < n; i++)       // n times
    for (int j = 0; j < n; j++)   // n times
        sum++;                    // O(1)
// total n × n = O(n²)

Example 2: triangular nesting → arithmetic sum

for (int i = 0; i < n; i++)       // i = 0..n-1
    for (int j = i; j < n; j++)   // runs (n-i) times
        sum++;
Total count = Σ(n−i) for i=0..n-1 = n + (n−1) + ... + 1
= n(n+1)/2 = Θ(n²)

Common misjudgment: seeing "the inner loop starts at i" and panicking that it's O(n·something). In fact triangular nesting is still O(n²) — the constant just becomes 1/2, and constants get dropped.

Example 3: size halving → log

for (int i = n; i > 1; i = i / 2)   // halve until 1
    sum++;
// n → n/2 → n/4 → ... → 1, log₂n times → O(log n)

Example 4: inner variable tied to the outer → multiply then sum

for (int i = 1; i < n; i *= 2)      // log n times
    for (int j = 0; j < i; j++)      // i times
        sum++;
i = 1, 2, 4, ..., n → inner loop runs 1 + 2 + 4 + ... + n times
= geometric series ≈ 2n = Θ(n)  (not O(n log n)!)

Trap: the outer loop runs log n times and the inner runs at most n times, so intuition says O(n log n). But the inner counts are the geometric series 1,2,4,...,n, whose sum ≈ its largest term = 2n = O(n). The power of "sum ≈ largest term" for geometric series.

Example 5: two segments back to back → take the larger

sort(arr);                    // O(n log n)
for (int x : arr) process(x);   // O(n)
// O(n log n) + O(n) = O(n log n)  ← take the larger

while + two pointers → amortized O(n)

int j = 0;
for (int i = 0; i < n; i++) {
    while (j < n && cond) j++;   // j only increases, never decreases
}
// looks nested, but j moves at most n steps overall → O(n) total, not O(n²)

Common pattern: sliding window, the stack in LC 2434 robotWithString, LC 2197 merging non-coprime numbers — all cases of "looks nested, but the inner pointer moves only O(n) steps overall" → amortized O(n). The key test: does the inner variable "reset" between outer iterations? If it doesn't reset → amortized.

Recurrence relations

The complexity of recursive / divide-and-conquer algorithms is written as a recurrence: T(n) expressed in terms of smaller T. Solving it gives you the complexity.

How to write a recurrence

A divide-and-conquer algorithm usually looks like this:

T(n) = a · T(n/b) + f(n)
  • a = how many recursive calls (into how many subproblems)
  • n/b = the size of each subproblem (divided by what)
  • f(n) = the cost of splitting + combining (the non-recursive part)

Method 1: recursion tree

Draw the work at each level as a tree and sum over all levels. Take Merge Sort T(n) = 2T(n/2) + n as an example:

level 0:            n                    work = n
level 1:       n/2     n/2               work = n/2 + n/2 = n
level 2:    n/4 n/4   n/4 n/4            work = 4 × n/4 = n
  ...                                every level is n
level k:   1  1  1  ...  1  (n leaves)   work = n
Work at every level is n
Number of levels = tree height = log₂n (halving each level)
Total work = n × log₂n = Θ(n log n)

Method 2: substitution (unrolling)

Repeatedly unroll T(n) = 2T(n/2) + n:

T(n) = 2T(n/2) + n
= 2[2T(n/4) + n/2] + n = 4T(n/4) + 2n
= 8T(n/8) + 3n
= 2ᵏT(n/2ᵏ) + k·n  (after unrolling k times)
When n/2ᵏ = 1 → k = log₂n, T(1)=1
= n·T(1) + n·log₂n = n + n log n = Θ(n log n)

Common recurrences at a glance

RecurrenceSolutionTypical algorithm
T(n) = T(n/2) + O(1)O(log n)Binary search
T(n) = T(n−1) + O(1)O(n)Linear recursion
T(n) = 2T(n/2) + O(n)O(n log n)Merge Sort, quicksort (average)
T(n) = 2T(n/2) + O(1)O(n)Tree traversal
T(n) = 2T(n/2) + O(log n)O(n)Build heap (Floyd's bottom-up)
T(n) = T(n−1) + O(n)O(n²)Quicksort (worst), selection sort
T(n) = 2T(n−1) + O(1)Θ(2ⁿ)Tower of Hanoi
T(n) = T(n−1) + T(n−2) + O(1)Θ(φⁿ) ≈ Θ(1.618ⁿ)Naive recursive Fibonacci (exponential, but not tightly 2ⁿ)

Note the huge difference between T(n/2) and T(n−1): T(n−1)+O(1) is O(n), but T(n/2)+O(1) is O(log n). The former subtracts 1 each time (a linear number of steps), the latter halves each time (a logarithmic number of steps). This is also why "halving" algorithms are so much faster.

Master Theorem — the shortcut formula for divide-and-conquer recurrences

For recurrences of the form T(n) = a·T(n/b) + f(n), skip the unrolling and plug straight into the formula. This is the master key to divide-and-conquer complexity.

T(n) = a·T(n/b) + f(n),  a ≥ 1, b > 1

Comparing f(n) with n^(log_b a)

The key is comparing which is larger: the "combine cost f(n)" or the "total number of leaves n^(log_b a)." Let c* = log_b a:

CaseConditionResultWho dominates
Case 1f(n) = O(n^(c*−ε))Θ(n^c*)Leaves (recursion) dominate
Case 2f(n) = Θ(n^c*)Θ(n^c* · log n)The two are balanced
Case 3f(n) = Ω(n^(c*+ε))Θ(f(n))The root (combine) dominates

Intuition: n^(log_b a) is the recursion tree's "total number of leaves" = the pure recursion work. f(n) is the combine work at each level. Whichever grows faster decides the total complexity; if they grow equally fast you get an extra log n factor (every level contributes the same amount, over log levels).

How to compute log_b a

log_b a = "b raised to what power equals a"
log₂2 = 1 (2¹=2),   log₂4 = 2 (2²=4),   log₂8 = 3
log₃9 = 2 (3²=9),   log₄2 = 0.5 (4^0.5=2)

Three classic applications

Merge Sort: T(n) = 2T(n/2) + n

a=2, b=2, f(n)=n → c* = log₂2 = 1
f(n) = n = Θ(n¹) = Θ(n^c*) → Case 2
Result = Θ(n · log n) ✓

Binary search: T(n) = T(n/2) + 1

a=1, b=2, f(n)=1 → c* = log₂1 = 0
f(n) = 1 = Θ(n⁰) = Θ(n^c*) → Case 2
Result = Θ(n⁰ · log n) = Θ(log n) ✓

Naive matrix multiplication subproblem: T(n) = 8T(n/2) + n²

a=8, b=2, f(n)=n² → c* = log₂8 = 3
f(n) = n² = O(n^(3−ε)) (ε=1) → Case 1 (leaves dominate)
Result = Θ(n³) ✓ (this is also why Strassen uses a=7 to bring it down to n^2.81)

Limitations of the Master Theorem: it only applies to "even-split" recurrences of the form a·T(n/b)+f(n). T(n)=T(n/3)+T(2n/3)+n (uneven split) and T(n)=T(n−1)+n (subtractive) can't use it — use a recursion tree or substitution instead. There's also a well-known "gap": when f(n) falls exactly between Case 2 and Case 3 (e.g. f(n) = n^c* · log n, such as T(n)=2T(n/2)+n log n), none of the three cases apply and you must solve it with a recursion tree — that example's answer is Θ(n log²n), not Θ(n log n). Case 3 also carries an implicit "regularity condition" (a·f(n/b) ≤ c·f(n), c<1), which the vast majority of polynomial f(n) satisfy automatically.

Amortized analysis

Some operations are occasionally expensive but mostly cheap. Amortized analysis computes "the average cost over a sequence of operations" rather than the worst-case cost of a single operation.

The core distinction: amortized ≠ average case. Average takes the expectation over "random inputs"; amortized guarantees an upper bound on the total cost over "a sequence of operations," without relying on probability — it holds even for the worst-case input.

Classic example: push on a dynamic array (ArrayList)

When the array is full it must "grow" = allocate a new array twice as large + copy all elements (O(n)). A single push is O(n) worst case, but amortized it is O(1).

Aggregate method: compute the total cost of n pushes

Growth happens at size = 1, 2, 4, 8, ..., n
Total copy cost = 1 + 2 + 4 + ... + n = geometric series ≈ 2n
Total cost of n pushes = n (each write) + 2n (copies) = 3n
Average per operation = 3n / n = O(1) amortized ✓

Once again "the sum of a geometric series ≈ its largest term" is at work: all the growth copies together add up to only 2n, not n × n. So normal growth of a dynamic array is actually cheap; what really blows up memory is "pre-allocating a large capacity for every node up front" (see space complexity below).

Three methods of amortized analysis

MethodApproach
AggregateCompute the total cost T(n) of n operations, amortized = T(n)/n
AccountingCheap operations "prepay" credit, expensive ones "withdraw" it
PotentialDefine a potential function Φ, amortized cost = actual + ΔΦ

Common amortized examples

  • Monotonic stack (robotWithString, merging non-coprime numbers, min-product): each element is pushed at most once and popped at most once → n elements make 2n stack operations total → amortized O(n), even if one while loop pops many at once.
  • Sliding window (longest nice subarray): the left and right pointers each advance monotonically, moving n steps each overall → O(n).
  • Union-Find with path compression and union by rank/size: a single operation is amortized O(α(n)) (inverse Ackermann function, essentially constant). Note that either optimization alone gives only O(log n).

Interview heuristic: when "the inner loop looks O(n) but the variable only increases, never decreases or resets" → use an amortized argument that "the total number of steps is O(n)," don't report O(n²). The theoretical name for this argument is exactly amortized analysis.

Worked examples — practice on classic problems

Apply the techniques above to a few common LeetCode problems.

1. Count Orders (LC 1359) — tabulation DP

for (int i = 2; i <= n; i++)
    for (int j = 1; j <= 2*i-1; j++)
        dp[i] += dp[i-1] * j;
Inner-loop count = Σ(2i−1) for i=2..n ≈ Σ 2i = 2·Σi = 2·n²/2 = n²
→ O(n²). n≤500 → 250,000 operations, well below 10⁸ → passes comfortably
(Optimizable: the inner arithmetic sum has a closed form i(2i−1) → O(n))

2. Echo Substring (LC 1316) — brute force with pruning

Enumerate half-length len × start i × compare len characters
= Σ_len Σ_i len ≈ n × n × n / constant = O(n³)
n≤2000 → 8×10⁹ blows up in theory, but the while rarely runs to the full length → passes in practice
Robust version: lcp DP or rolling hash → O(n²) = 4×10⁶

3. Fair Distribution of Cookies (LC 2305) — subset enumeration

Enumerate submasks of each subset: Σ_{mask} 2^(popcount(mask))
= each bit has three states (out / in the large set / in the small set) = 3ⁿ
n≤8 → 3⁸ = 6561 → extremely fast

Derivation of "enumerating submasks = 3ⁿ": for each element it can be (a) not in the mask, (b) in the mask but not in the submask, or (c) in the submask. One of three choices, n independent elements → 3ⁿ. This is a common complexity in bitmask DP.

4. Binary-search-on-answer type (LC 2861 Alloys) — n × binary search

Binary search the answer for each machine: log(upper bound) iterations
Each binary-search step checks every metal: O(n)
k machines → O(k · n · log(upper bound))
Everything ≤ 10⁵ scale → about 10⁵ × 30 = 3×10⁶ → passes comfortably

5. Tarjan's bridge finding (LC 1192) — graph traversal

DFS visits each node once and looks at each edge twice (undirected)
= O(V + E)
V,E ≤ 10⁵ → 2×10⁵ → passes comfortably

Estimation SOP: (1) identify the dominant loop / recursion structure → (2) compute the order using summation / recurrences / the Master Theorem → (3) plug in the upper bound on n to get the actual operation count → (4) compare against 10⁸/sec to judge TLE → (5) if it exceeds, think about whether you can lower the order (closed-form arithmetic sum, binary search, monotonic stack, amortization).

Don't forget space complexity

  • Extra space: excludes input and output, counts only the auxiliary structures you allocate.
  • A DP table dp[n][m] → O(n·m); a rolling array can compress it to O(m) (as in LC 1335 minDifficulty).
  • Hidden space of recursion: the call stack depth. A DFS on a chain-shaped graph has depth O(n) and may overflow the stack.
  • new ArrayList(n) × n of them → O(n²) space → MLE (Memory Limit Exceeded — a common trap: pre-allocating a large capacity for every node).
