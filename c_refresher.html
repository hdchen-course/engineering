C Refresher

The machine-close language — how your code becomes bytes, where variables live, and why pointers and manual memory are both C's superpower and its biggest hazard

What C really is

Think of C as a thin, honest layer over the hardware. If a higher-level language is a self-driving car — it parks, brakes, and refuels for you — C is a manual transmission with the hood open. Nothing happens that you didn't ask for: no garbage collector sweeping up behind you, no bounds-checking guardrail, no hidden allocations. That's exactly why C is fast and predictable, and exactly why it will let you drive off a cliff.

Here is the whole language in one runnable program:

/* hello.c — compile: cc hello.c -o hello   run: ./hello */
#include <stdio.h>

int main(void) {
    int answer = 42;
    printf("the answer is %d\n", answer);
    return 0;   // 0 = success, by convention
}

No classes, no exceptions, no strings-as-objects. A handful of types (int, char, double, pointers), functions, structs, and a preprocessor. The whole ISO C standard fits in a book you can read on a flight. The difficulty isn't the surface area — it's that C trusts you completely.

Note for readers coming from higher-level languages

If your instincts come from Python, Java, JavaScript, Go, or C#, retrain these reflexes:

You're used to…In C…
Garbage collectionYou free() every heap allocation yourself, or it leaks.
Arrays that know their length & bounds-checkAn array is just a base address. Reading past the end is undefined behavior, not an exception.
Strings as first-class objectsA "string" is a char array ending in a '\0' byte. Length is computed by scanning.
Pass-by-reference / everything's an objectEverything is pass-by-value. To mutate a caller's variable you pass a pointer to it.
Rich standard libraryTiny stdlib. You often write your own data structures.
Runtime that catches errorsNo runtime. A bad pointer corrupts memory silently and crashes (or worse, doesn't) later.

The mental shift: in higher-level languages a variable is its value. In C, a variable is a named box at an address, and much of the language is about those addresses. Once "everything is bytes at an address" clicks, the rest of C follows.

Interview angle

Interviewers use C to probe whether you understand what's actually happening under any language. Expect: "what does this pointer expression do," "walk me through the memory," "why is this undefined behavior," "where's the leak." You rarely need obscure syntax — you need a crisp mental model of the stack, the heap, and pointers. The rest of this chapter builds exactly that model.

Compilation & linking — from text to a running program

Analogy: publishing a book from many chapters. Each chapter (.c file) is written and typeset independently (compiled to an object file). A shared style guide (header) tells every chapter what the others' functions look like without reprinting them. Finally a binder (linker) stitches all chapters plus the pre-printed appendix (libraries) into one book (the executable).

The four stages

# See each stage explicitly:
cc -E main.c        # 1. Preprocess: expand #include / #define, output pure C
cc -S main.c        # 2. Compile:    C -> assembly (main.s)
cc -c main.c        # 3. Assemble:   assembly -> object file (main.o)
cc main.o util.o -o app   # 4. Link: combine objects + libs -> executable
  1. Preprocess — a text step. #include literally pastes the header in; #define macros are substituted. The compiler proper never sees a #.
  2. Compile — each translation unit (one .c plus its included headers) becomes assembly, then
  3. Assemble — an object file (.o): machine code with a symbol table and unresolved references.
  4. Link — the linker resolves every symbol (matches each call foo to the one definition of foo) and produces the final binary.

Declaration vs definition — why headers exist

A declaration promises a function/variable exists somewhere ("here's its shape"). A definition actually creates it. Each .c is compiled alone, so it needs declarations of anything defined elsewhere — that's what a header provides.

/* math_util.h — the shared "style guide" (declarations only) */
#ifndef MATH_UTIL_H       // include guard: prevents double-inclusion
#define MATH_UTIL_H
int add(int a, int b);    // declaration (a promise)
#endif

/* math_util.c — the definition (the real thing) */
#include "math_util.h"
int add(int a, int b) { return a + b; }

/* main.c — a user of it */
#include "math_util.h"       // gets the declaration only
int main(void) { return add(2, 3) == 5 ? 0 : 1; }

The two classic linker errors: undefined reference to 'add' means a declaration was used but no definition was linked (forgot to compile math_util.c). multiple definition of 'add' means a function/global was defined in a header and included by several files. Definitions go in .c; headers hold declarations.

Static vs dynamic linking

cc main.o -o app -lm           # link the math library (libm)
cc main.o -static -o app -lm   # bake the lib INTO the binary
  • Static (.a): library code is copied into your executable. Bigger binary, no runtime dependency, self-contained.
  • Dynamic (.so / .dll): the binary references a shared library loaded at run time. Smaller binaries, shared across processes, but the library must be present and compatible.

Interview angle: "Explain what happens between saving main.c and running ./app." A strong answer names the four stages, distinguishes declaration from definition, explains why an undefined reference is a link-time (not compile-time) error, and contrasts static vs dynamic linking. Bonus: mention that each .c is compiled independently, which is why headers and the linker exist at all.

The memory model — where variables actually live

A running C program's address space is divided into regions. Analogy: an office building. The code/text is the fixed blueprint. Globals are permanent fixtures bolted to the floor. The heap is a big warehouse you rent lockers from and must return. The stack is a stack of scratch desks — each function call grabs the top desk and returns it the instant it finishes.

Stack vs heap — the distinction that matters most

How variables live — a walk-through

int g = 10;            // global -> data segment, lives whole program
static int s;          // zero-initialized global -> BSS

void f(void) {
    int local = 5;       // stack: born here, dies when f returns
    int *p = malloc(sizeof *p);  // p is on the stack; *p is on the heap
    *p = 7;
    free(p);            // heap block returned; p itself dies at return
}

The #1 stack bug — dangling stack pointer. Never return the address of a local: its desk is reclaimed the moment the function returns.

int *broken(void) {
    int x = 42;
    return &x;   // BUG: x dies at return; caller holds a dangling pointer (UB)
}
// Fix: return by value, or malloc the storage, or take a caller-provided buffer.

Interview angle: "Where does this variable live, and when does it die?" is the memory question in disguise. Be able to point at any variable and say stack / heap / data / BSS / text and give its lifetime. The killer follow-up — "what's wrong with returning &x?" — is really "do you understand stack frames?"

Pointers & pointer arithmetic

A pointer is just a variable whose value is an address. Analogy: a house has contents (the value) and a street address. A pointer holds the address on a slip of paper. &x = "the address of x." *p = "go to that address and look inside" (dereference).

int  x = 42;
int *p = &x;     // p holds the address of x
printf("%d\n", *p);   // 42  — dereference: read through p
*p = 99;          // writes THROUGH p into x; now x == 99

Why pointers exist: mutating a caller's variable

Because C is pass-by-value, a function gets a copy of its arguments. To change the caller's variable, pass its address:

void swap(int *a, int *b) {   // receive addresses
    int t = *a; *a = *b; *b = t;   // operate through them
}
int main(void) {
    int x = 1, y = 2;
    swap(&x, &y);   // pass addresses; now x==2, y==1
}

Pointer arithmetic — it's typed, and it scales

Adding 1 to a pointer advances it by sizeof(*p) bytes, not one byte. p + i means "the i-th element after p." In fact arr[i] is defined as *(arr + i).

int a[] = {10, 20, 30};
int *p = a;         // points at a[0]; array name decays to &a[0]
printf("%d\n", *(p + 2));   // 30  — advanced by 2*sizeof(int) bytes
p++;                // now points at a[1]
printf("%d\n", p[1]);      // 30  — p[1] == *(p+1)

The types int * vs char * matter precisely because arithmetic scales by element size. That's why void * (untyped) can't be dereferenced or incremented — the compiler doesn't know the step size.

Arrays & C-strings

An array in C is not a smart object — it's a contiguous block of elements, and its name decays to a pointer to the first element in almost every expression. There is no stored length and no bounds checking.

int a[5] = {1, 2, 3};   // a[3], a[4] auto-zeroed -> 0, 0
size_t n = sizeof a / sizeof a[0];  // 5 — works ONLY where a is a real array
a[7] = 99;   // out of bounds: no error, silently corrupts adjacent memory (UB)

When you pass an array to a function it decays to a pointer — the length is lost. Inside void f(int a[]), sizeof a is the size of a pointer, not the array. Always pass the length alongside: void f(int *a, size_t n).

C-strings: a char array ending in '\0'

C has no string type. A string is a char array whose end is marked by a null terminator byte '\0' (value 0). Every string function relies on that byte being present.

char s[] = "hi";   // actually 3 bytes: 'h','i','\0'
size_t len = strlen(s);   // 2 — scans until it hits '\0' (O(n), not O(1)!)

char dst[4];
strcpy(dst, "abc");       // copies 'a','b','c','\0' — exactly fits
// strcpy(dst, "abcd");    // BUFFER OVERFLOW: 5 bytes into a 4-byte buffer (UB)

The null terminator is load-bearing. Lose it and strlen/printf("%s") run off the end of the buffer scanning for a zero that isn't there. strncpy notoriously may not null-terminate if the source fills the buffer — always ensure termination yourself.

Safer copying

char dst[8];
snprintf(dst, sizeof dst, "%s", src);  // bounded; always null-terminates

Prefer bounded functions (snprintf) and always pass buffer sizes. The unbounded classics — gets (removed from the standard), strcpy, sprintf, strcat — are the source of countless buffer-overflow vulnerabilities.

Interview angle: "Implement strlen" / "reverse a C-string in place" / "why is strlen O(n)?" all test whether you truly get the null-terminator model. Mention that char *s = "literal" points at read-only memory (writing to it is UB), whereas char s[] = "literal" is a writable copy on the stack — a classic trap.

Structs & unions

A struct groups related fields into one type — like a small record. Fields are laid out in memory in order (with padding for alignment).

struct Point { int x; int y; };

struct Point a = { 3, 4 };   // aggregate init
struct Point b = { .x = 3, .y = 4 };  // designated init (C99+)
printf("%d\n", a.x);              // dot: access on a value

struct Point *p = &a;
printf("%d\n", p->y);              // arrow: access through a pointer  (p->y == (*p).y)

obj.field when you hold the value; ptr->field when you hold a pointer. p->y is pure sugar for (*p).y.

typedef — dropping the struct keyword

typedef struct { int x, y; } Point;   // now just "Point", no "struct"
Point c = { 1, 2 };

Alignment & padding

The compiler inserts padding so each field sits on its natural alignment boundary. Field order affects sizeof:

struct Bad  { char c; int i; char d; };  // often 12 bytes (padding around c, d)
struct Good { int i; char c; char d; };  // often 8 bytes (fields packed better)

Unions — one storage, many interpretations

A union overlays all its members in the same memory. Its size is the largest member. You store one member at a time; reading a different one reinterprets the bytes.

union Value {
    int   i;
    float f;
    char  bytes[4];
};                       // sizeof == 4 (all share the same 4 bytes)

union Value v;
v.i = 1;                  // store as int
// reading v.f now reinterprets those bytes as a float — you must track which is active

The idiomatic use is a tagged union — a struct pairing a union with an enum saying which member is live:

struct Var {
    enum { INT, FLT } tag;   // which member is valid
    union { int i; float f; } as;
};
// This is how interpreters/JSON parsers store "a value of one of N types".

Reading a union member other than the one last written is only well-defined for the "type punning" cases the standard blesses; in general it's a portability trap. The tag field exists precisely so you never do it by accident.

Interview angle: "Difference between a struct and a union?" — struct = sum of sizes (fields coexist); union = max of sizes (fields overlap). Follow-ups: "why does struct field order change sizeof?" (alignment/padding) and "how would you represent a value that's one of several types?" (tagged union). Being able to draw the byte layout wins the question.

Manual memory management

The heap is yours to manage. Four functions from <stdlib.h> do it all:

FunctionWhat it does
malloc(n)Allocate n bytes, uninitialized (contains garbage). Returns NULL on failure.
calloc(count, size)Allocate count*size bytes, zeroed. Also checks the multiplication for overflow.
realloc(p, n)Resize a block to n bytes, preserving contents; may move it (returns the new address).
free(p)Return a block to the allocator. Every malloc needs exactly one free.
int *a = malloc(10 * sizeof *a);   // 10 ints; sizeof *a adapts if type changes
if (!a) { /* handle allocation failure */ return 1; }
for (int i = 0; i < 10; i++) a[i] = i;

int *bigger = realloc(a, 20 * sizeof *a);
if (!bigger) { free(a); return 1; }   // realloc failed: original 'a' still valid
a = bigger;                              // commit only on success

free(a);      // done
a = NULL;     // prevent accidental reuse

The realloc trap: never write a = realloc(a, n);. If it fails it returns NULL but the original block is not freed — you've just leaked it and lost the only pointer. Assign to a temporary first.

The four classic heap bugs

// 1. LEAK — allocation with no matching free
void leak(void) { int *p = malloc(100); }  // p dies, block stays allocated forever

// 2. USE-AFTER-FREE — touch memory after freeing it
free(p); *p = 5;                          // UB: block may be reused

// 3. DOUBLE FREE — free the same block twice
free(p); free(p);                          // UB: corrupts allocator bookkeeping

// 4. BUFFER OVERFLOW — write past the allocated size
char *buf = malloc(8);
strcpy(buf, "this is way too long");       // UB: heap corruption

Discipline that eliminates most of these: (1) pair every malloc with a free at the same "ownership level"; (2) set pointers to NULL after freeing — free(NULL) is a safe no-op, so this also neutralizes double frees; (3) never let two pointers think they own the same block; (4) always allocate/copy with an explicit size. Tools like Valgrind and AddressSanitizer (cc -fsanitize=address) catch these at run time.

Ownership — the concept C forces you to design

For every allocation, answer: who is responsible for freeing it, and when? C won't track this for you. Document it (e.g. "caller owns the returned buffer"). This is the same ownership discipline that later languages formalize with RAII or borrow checkers — in C it lives in your head and your comments.

Interview angle: Given a snippet, "find the memory bug" is a staple. Scan for: allocation paths with no free (leak), any use after free, free called twice, writes without a size check (overflow), and the a = realloc(a, …) anti-pattern. State the ownership contract of any function that returns a pointer — that's the senior signal.

Undefined behavior

The C standard defines behavior only for correct programs. Cross certain lines and the standard imposes no requirements at all — the compiler may do anything: crash, produce garbage, or (worst) appear to work until it doesn't. This is undefined behavior (UB), and it's the root of most C security bugs.

Common UB: reading uninitialized memory, out-of-bounds access, dereferencing NULL or a dangling pointer, signed integer overflow, dividing by zero, data races.

int x;               // uninitialized
if (x == 0) ...      // UB: reading indeterminate value

int i = INT_MAX;
i = i + 1;           // UB: signed overflow (NOT guaranteed to wrap)

Modern compilers optimize assuming UB never happens. Because signed overflow is UB, a compiler may delete an overflow check entirely, or assume a loop terminates. "It worked on my machine" is meaningless with UB — a new compiler version can silently change the result. Treat UB as a bug even when it seems to work.

The preprocessor

A pure text-substitution pass that runs before compilation. It doesn't understand C — it just manipulates text.

#define PI 3.14159            // object-like macro
#define SQUARE(x) ((x) * (x))   // function-like macro — parenthesize everything!
#include <stdio.h>              // paste a header

#ifdef DEBUG                    // conditional compilation
    printf("debug: %d\n", x);
#endif

Macro pitfalls (why they're text, not functions): #define SQUARE(x) x*x makes SQUARE(a+b) expand to a+b*a+b — wrong. And SQUARE(i++) increments twice. Parenthesize every argument and the whole body, and avoid side effects in macro arguments. In modern C, prefer const/enum for constants and static inline functions over function-like macros.

Include guards (#ifndef X / #define X / #endif) stop a header being pasted twice into one translation unit — which would cause redefinition errors.

const, static, volatile

const — "this won't change through this name"

const int MAX = 100;               // read-only value
void print(const char *s);          // promise: won't modify *s (documents intent)

// Pointer const-ness — read right to left:
const int *p;        // pointer to const int   (can't change *p, can change p)
int *const q = &x;    // const pointer to int   (can change *q, can't change q)

static — two very different meanings

// 1. At file scope: internal linkage — symbol is private to this .c file
static int counter = 0;     // not visible to the linker in other files
static void helper(void);      // file-private function

// 2. Inside a function: persistent local — one instance, retains value across calls
int next_id(void) {
    static int id = 0;      // initialized once; lives in static storage (BSS), not the stack
    return ++id;             // 1, 2, 3, ... across calls
}

volatile — "the compiler must not assume"

Tells the compiler this variable can change outside the visible program flow (hardware register, memory-mapped I/O, a variable touched by a signal handler). The compiler must re-read it from memory every time and never optimize accesses away.

volatile int *reg = (volatile int *)0x40021000;   // a hardware register
while (*reg == 0) { }   // re-reads *reg each iteration; without volatile, may loop forever

volatile is not for thread safety — it gives no atomicity and no ordering guarantees. For concurrency use _Atomic / <stdatomic.h> or a mutex. Its real domains are memory-mapped hardware and sig_atomic_t flags.

Function pointers

Functions have addresses too, so you can store one in a variable and call through it — C's mechanism for callbacks, plugin tables, and dispatch.

int add(int a, int b) { return a + b; }
int sub(int a, int b) { return a - b; }

int (*op)(int, int);   // op: pointer to "function taking (int,int) returning int"
op = add;                 // function name decays to its address
printf("%d\n", op(2, 3));   // 5 — call through the pointer

// Callback: qsort takes a comparator function pointer
int cmp(const void *a, const void *b) {
    int x = *(const int *)a, y = *(const int *)b;
    return (x > y) - (x < y);   // overflow-safe: subtraction could overflow (UB)
}
int arr[] = {3, 1, 2};
qsort(arr, 3, sizeof arr[0], cmp);   // generic sort via callback

An array of function pointers is a dispatch table — how you replace a big switch, and conceptually how C++ virtual dispatch (the vtable) works under the hood: an object carries a pointer to a table of function pointers.

Interview angle: Reading a tricky declaration like int (*(*f)(int))[3] tests your grasp of C's declarator syntax (use the right-left rule, or cdecl). More practically: "how does qsort stay generic?" (a void* comparator function pointer) and "how would you implement runtime dispatch in C?" (a struct of function pointers — a hand-rolled vtable).

Where C still rules

Decades on, C remains the default where you must be close to the metal, dependency-free, and predictable:

  • Operating-system kernels — Linux, the BSDs, and most RTOSes are C. Kernels can't assume a runtime, a garbage collector, or even a heap; C's "nothing hidden" model fits.
  • Embedded-adjacent & firmware — microcontrollers, device drivers, bootloaders. Tiny RAM, direct hardware registers (that's where volatile proves its worth), sometimes no OS at all.
  • Language runtimes & interpreters — the reference implementations of Python (CPython), Ruby (MRI), Lua, and many VMs are C. Tagged unions and function-pointer dispatch (both above) are exactly how a bytecode interpreter is built.
  • Systems software & infrastructure — databases, network stacks, codecs, compilers, and the C standard library itself. Anywhere a few percent of performance or a stable ABI matters.
  • The universal ABI — nearly every language can call C ("FFI"). C is the common language that lets ecosystems interoperate.

Where C is not the right reach today: application logic, web services, and most business software — the manual-memory cost isn't worth it when a higher-level language (or C++/Rust for systems work) buys you safety.

Interview Q&A — likely C questions

"What's the difference between the stack and the heap?"

Stack: automatic lifetime tied to function calls, fast (bump a pointer), small, freed on return — the compiler manages it. Heap: manual lifetime via malloc/free, larger, slower to allocate, lives until you free it. Prefer the stack; use the heap when size is dynamic or the object must outlive the current frame.

"What does *(p + 2) do, and why isn't it p + 2 bytes?"

Pointer arithmetic is scaled by sizeof(*p). p + 2 advances by two elements, then * reads that element. It's identical to p[2], because p[i] is defined as *(p + i).

"Find the memory bug in this function."

Scan for: allocations with no matching free (leak), use of a pointer after free (use-after-free), freeing the same pointer twice (double free), writes without a bounds/size check (buffer overflow), returning the address of a local (dangling stack pointer), and a = realloc(a, n) (leak on failure). State the ownership contract too.

"Why is a C-string O(n) to get the length?"

There's no stored length — a string is a char array ending in '\0'. strlen scans byte by byte until it finds the terminator. Lose the terminator and it reads off the end of the buffer (UB / overflow).

"struct vs union?"

A struct's size is (roughly) the sum of its fields — they coexist. A union's size is its largest member — all members share the same storage, so only one is valid at a time. The idiomatic safe use is a tagged union (a struct with an enum tag plus a union).

"What is undefined behavior, and why care if it 'works'?"

UB means the standard imposes no requirements — the compiler may do anything. Optimizers assume UB never occurs, so they can delete your checks or change behavior between versions. Code that relies on UB is a latent bug even when it currently produces the right answer.

"When would you use volatile?"

When a value can change outside the normal program flow: memory-mapped hardware registers, a variable modified in a signal handler, or a spin on a flag another context updates. It forces the compiler to re-read from memory and not optimize accesses away. It is not a concurrency primitive — use atomics or locks for threads.

"What's the difference between malloc and calloc?"

malloc(n) returns n uninitialized bytes (garbage). calloc(count, size) returns zeroed memory and checks count*size for multiplication overflow. Use calloc when you need zeroed memory or are allocating an array by count.

"How do you do a callback / runtime dispatch in C?"

Function pointers. Store a function's address in a variable typed ret (*)(args) and call through it — that's how qsort takes a comparator. A struct or array of function pointers is a dispatch table, the same idea as a C++ vtable.

Positioning for coming-from-higher-level candidates: lead with the mental model — "in C, a variable is a named box at an address; the language is mostly about the stack, the heap, and pointers between them." Show you can name where any variable lives and when it dies, state ownership for any pointer you return, and spot the classic UB. That model, not syntax trivia, is what a C interview is really checking.
