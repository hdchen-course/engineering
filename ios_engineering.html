Swift Essentials

Three ideas power almost every Swift design decision: value vs reference types, optionals, and protocols. Get these and the rest of the language reads cleanly.

Analogy first. A value type is like emailing someone a photocopy of a document — they can scribble on their copy and yours is untouched. A reference type is like emailing a shared Google Doc link — everyone edits the same underlying thing. Swift makes you choose which one you mean, and that single choice removes a huge class of "who changed my data?" bugs.

Value types vs reference types

struct, enum, and the standard collections (Array, Dictionary, String) are value types: assigning or passing them copies the value. class is a reference type: assigning shares one instance, and multiple variables can mutate it.

struct Point { var x: Int; var y: Int }   // value type — copied
class  Node  { var value = 0 }            // reference type — shared

var a = Point(x: 1, y: 2)
var b = a          // COPY: b is independent of a
b.x = 99           // a.x is STILL 1

let n1 = Node()
let n2 = n1        // SAME instance, two names
n2.value = 99      // n1.value is now 99 too
INSIGHT

Swift's standard library is value-type-first, made cheap by copy-on-write: an Array shares its buffer until someone mutates it, then it copies. So "everything copies" is the mental model, and the runtime avoids the cost until a write actually happens. Value semantics are what make Swift concurrency safe — a copied struct can't be mutated out from under you by another thread.

When to reach for which

  • Prefer struct by default — models, DTOs, small state. Local reasoning, no shared mutation, thread-friendly.
  • Use class when you need identity or shared mutable state — a view controller, a cache, an object that must be the same object everywhere (compared with ===), or one that inherits from a UIKit class.
  • enum with associated values models "one of N shapes" precisely — e.g. enum LoadState { case idle, loading, loaded([Post]), failed(Error) }.

Optionals — nil made explicit

Analogy: an Optional is a box that is either empty or holds a value. The type system forces you to open the box before using what's inside, so "null pointer" surprises become compile-time checks. A String is always a string; a String? might be a string or nothing.

var name: String? = nil              // may hold a String, or nothing

// 1. Optional binding — safest
if let real = name { greet(real) }

// 2. guard — bind and exit early; keeps the happy path un-indented
func greetIfPossible() {
    guard let real = name else { return }
    greet(real)                        // `real` is a non-optional String here
}

// 3. Optional chaining + nil-coalescing
let len = name?.count ?? 0          // count if present, else 0

// 4. Force-unwrap — crashes if nil. Reserve for "impossible to be nil".
let forced = name!                    // code smell in most places
TRAP

The force-unwrap operator ! and implicitly-unwrapped optionals (String!) are the iOS equivalent of a landmine. In interviews, reaching for ! to "make the compiler happy" reads as junior. Show you default to guard let / if let and can explain the one legitimate ! case: a value that is genuinely guaranteed non-nil after initialization (e.g. an @IBOutlet).

Protocols — capability, not hierarchy

Analogy: a protocol is a job description ("anything that can draw()"), not a family tree. A type can adopt many protocols, so Swift favors composition of capabilities over deep inheritance chains. This is "protocol-oriented programming".

protocol Drawable {
    func draw()
}

// Protocol EXTENSION gives a default implementation — free for adopters
extension Drawable {
    func draw() { print("default shape") }
}

struct Circle: Drawable {
    func draw() { print("○") }   // override the default
}
struct Blank: Drawable {}              // uses the default draw()

func renderAll(_ shapes: [Drawable]) {   // program to the protocol, not a class
    for s in shapes { s.draw() }
}
  • Protocol extensions provide shared default behavior without a base class — how the standard library gives every Collection a map/filter.
  • Generics + protocol constraints (func max<T: Comparable>(...)) give type-safe reuse; associated types (associatedtype Element) let a protocol be generic.
  • Delegation, the go-to UIKit pattern, is just a protocol: a view controller adopts UITableViewDataSource and the table asks it for rows.
INTERVIEW ANGLE

Expect "struct or class here, and why?" The strong answer names value semantics, thread-safety, and copy-on-write — then picks struct unless identity, inheritance, or shared mutable state is required. On optionals, show you treat nil as a modeled state, not an error, and avoid !. On protocols, contrast protocol-oriented composition with classical inheritance and mention protocol extensions as the "default method" mechanism.

UIKit vs SwiftUI — Imperative vs Declarative

The same screen, two philosophies. UIKit: you hold references to views and mutate them step by step. SwiftUI: you describe what the UI should look like for a given state, and the framework figures out the changes.

Analogy. UIKit is giving turn-by-turn driving directions ("set the label text, now change its color, now hide the spinner"). SwiftUI is handing over the destination address ("the screen shows this count") — the framework computes the route. When state changes, you don't touch the views; you change the state and SwiftUI re-renders.

UIKit — imperative
class CounterVC: UIViewController {
    let label = UILabel()
    var count = 0

    // YOU mutate the view by hand
    @objc func tapped() {
        count += 1
        label.text = "\(count)"
    }
}
SwiftUI — declarative
struct CounterView: View {
    @State private var count = 0

    // UI is a function of state
    var body: some View {
        VStack {
            Text("\(count)")
            Button("Tap") { count += 1 }
        }
    }
}
INSIGHT

The mental shift: in SwiftUI you never write "update this label." You write body as a pure-ish function state → view tree. When an @State/@Published value changes, SwiftUI re-invokes body, diffs the returned tree against the previous one, and mutates only the underlying UIKit/AppKit views that actually changed. It's the same core idea as React's render + reconciliation.

When to use which

Reach for SwiftUI

New screens, rapid iteration, cross-Apple-platform UI, live previews, simple-to-moderate state.

Key: default for greenfield

WATCH

SwiftUI's declarative model is not free of imperative escape hatches, and misusing them is the classic beginner error: mutating @State from inside body (infinite re-render), or getting model ownership wrong. For a legacy ObservableObject view-model, own it with @StateObject (not @ObservedObject, which is re-created when the parent re-renders) so its @Published changes are observed; for a modern @Observable model, own it with @State (@StateObject can't be used with it — it requires ObservableObject conformance). Know the ownership rules for the wrappers above.

INTERVIEW ANGLE

Be able to state the imperative-vs-declarative distinction in one sentence and back it with the counter example. Then go deeper: how SwiftUI re-renders (invalidate → recompute body → diff → minimal mutation), why value-type views make that cheap, and the ownership semantics of @State vs @StateObject vs @Binding. Senior signal: knowing when UIKit is still the right tool and how to bridge the two.

The View-Controller Lifecycle

A UIViewController is born, its view loads, appears, disappears, and dies — on a fixed, ordered set of callbacks. Knowing which work belongs in which callback is essential iOS knowledge.

Analogy. Think of a stage actor. viewDidLoad is the one-time dress rehearsal (set up the set). viewWillAppear/viewDidAppear fire every time they walk on stage (refresh what the audience sees, start the spotlight). viewWillDisappear/viewDidDisappear fire every time they exit (pause, save). deinit is when the actor leaves the building for good.

What goes where

CallbackFiresPut here
viewDidLoad()Once, after the view is loaded into memoryOne-time setup: subviews, static config, initial data request wiring
viewWillAppear(_:)Every time the view is about to showRefresh data that may have changed, update UI to current state
viewDidAppear(_:)Every time, after it's on screenStart animations, analytics "screen viewed", begin location/camera
viewWillDisappear(_:)Every time it's about to hideSave edits, resign first responder, pause work
viewDidDisappear(_:)Every time, after it's hiddenStop timers/observers, release expensive resources
deinitWhen the VC is deallocatedFinal cleanup; a deinit that never prints is your leak alarm
TRAP

Doing one-time setup in viewWillAppear. It fires on every return-to-screen, so adding subviews or observers there duplicates them each time (stacked views, double callbacks). Rule of thumb: build once in viewDidLoad, refresh in viewWillAppear. And layout math belongs in viewDidLayoutSubviews — frames are not final in viewDidLoad.

INTERVIEW ANGLE

Classic question: "Where would you start/stop a location manager or a timer, and why?" Start in viewDidAppear / stop in viewDidDisappear so you don't hold hardware or fire callbacks while off-screen. A senior answer connects this to memory: a timer or observer not torn down keeps the VC alive — verify by checking deinit actually runs. SwiftUI's analog is onAppear/onDisappear and the task modifier, which auto-cancels when the view leaves.

ARC & Retain Cycles

iOS has no tracing garbage collector. Instead the compiler inserts retain/release calls at compile time — Automatic Reference Counting. It's deterministic and pause-free, but it can't detect cycles: two objects that hold each other never reach zero and leak forever.

Analogy. Each object keeps a tally of how many people are "holding its hand" (its retain count). When the last person lets go (count hits 0), the object is freed immediately — no waiting for a garbage collector to sweep. The catch: if object A holds B's hand and B holds A's hand, then even after everyone else lets go, the two of them keep each other alive. Nobody can leave. That's a retain cycle.

class Person {
    let name: String
    var apartment: Apartment?         // strong → Apartment
    init(_ name: String) { self.name = name }
    deinit { print("\(name) freed") }
}

class Apartment {
    let unit: String
    var tenant: Person?               // strong → Person  ← this closes the cycle
    init(_ unit: String) { self.unit = unit }
    deinit { print("Apt \(unit) freed") }
}

var alice: Person?    = Person("Alice")
var u4a:   Apartment? = Apartment("4A")
alice?.apartment = u4a          // Alice —strong→ 4A
u4a?.tenant      = alice        // 4A —strong→ Alice   (cycle!)

alice = nil                     // external ref gone…
u4a   = nil                     // …both gone, but NEITHER deinit prints. Leaked.

See it leak, then see weak break it

Step through the exact scenario. Watch each object's retain count. Steps 1–3 build the cycle and orphan it (leak); steps 4–5 apply the weak fix and free both. Press Step; Reset replays it.

Step 0 / 5 Ready. Two objects created; each held once by a local variable.

The fix: weak and unowned

A weak reference does not increase the retain count and automatically becomes nil when its target is freed — so it must be an Optional (weak var tenant: Person?). An unowned reference also doesn't retain, but is assumed to always be valid while used (non-optional); accessing it after the target is freed crashes.

class Apartment {
    weak var tenant: Person?          // weak breaks the cycle — no retain
}

// Closures capture self strongly too — the #1 real-world cycle:
class ViewModel {
    var onDone: (() -> Void)?
    func setup() {
        onDone = { [weak self] in   // capture list breaks VM ⇄ closure cycle
            self?.finish()
        }
    }
    func finish() {}
}
weakunowned
Retains target?NoNo
TypeOptional (auto-nils)Non-optional

Use whenReference can outlive/be nil (delegates, parent from child)Reference is guaranteed to live as long (tight, same-lifetime pairs)
RULE OF THUMB

The "child" or "back" reference is the one you make weak: a delegate is weak, a child's pointer back to its parent is weak, and closures that outlive their owner capture [weak self]. Pick unowned only when you can prove the two objects share a lifetime (e.g. a value and its own helper created together and never separated).

INTERVIEW ANGLE

"What is ARC and how does it differ from garbage collection?" — deterministic, compile-time-inserted retain/release, immediate deallocation at count 0, no GC pauses, but no cycle collector. Then: "What's a retain cycle and how do you find/fix one?" Walk the two-object example, name weak vs unowned, and mention closures capturing self as the most common production leak. Bonus: Xcode's Memory Graph Debugger and a non-firing deinit as detection tools.

Concurrency — GCD, async/await & Actors

Two eras coexist. GCD (Grand Central Dispatch) is the callback-and-queues model that has run iOS for a decade. Swift Concurrency (async/await + actors) is the modern, structured, compiler-checked model. You'll use both.

Analogy. A queue is a line at a service desk. The main queue is the one desk that's allowed to touch the screen — keep it moving or the UI freezes. Global (background) queues are extra desks for slow work (network, parsing) so the main desk stays free. The golden move: do the slow work on a background desk, then hop back to the main desk to update the UI.

GCD — the classic model

DispatchQueue.global(qos: .userInitiated).async {
    let data = heavyParse()                 // off the main thread — UI stays smooth
    DispatchQueue.main.async {               // hop back to touch UI
        self.label.text = data
    }
}
  • QoS (quality of service) tells the system how to prioritize: .userInteractive > .userInitiated > .utility > .background.
  • Serial vs concurrent queues: a serial queue runs one task at a time (great for protecting shared state); a concurrent queue runs many.
  • DispatchQueue.main is a serial queue bound to the main thread — the only safe place for UI.

async / await — the modern model

Same idea, but the "hop back" and the callback nesting vanish. await suspends the function without blocking the thread; the code reads top-to-bottom like synchronous code but runs asynchronously.

func loadUser() async throws -> User {
    let (data, _) = try await URLSession.shared.data(from: url)
    return try JSONDecoder().decode(User.self, from: data)
}

Task { @MainActor in                          // bridge sync → async, pinned to the main actor
    do {
        let user = try await loadUser()
        name = user.name                     // safe: this Task is explicitly @MainActor-isolated
    } catch { showError(error) }
}

// Structured concurrency: run two fetches in parallel, await both
async let a = loadUser()
async let b = loadSettings()
let (user, settings) = try await (a, b)

Actors & @MainActor

An actor is a reference type that serializes access to its own mutable state — the compiler guarantees no two tasks touch it at once, eliminating data races. @MainActor is a special actor tied to the main thread; annotate UI code with it and the compiler enforces the main-thread rule for you.

actor Counter {
    private var value = 0
    func increment() { value += 1 }     // runs serially — no locks needed
    func get() -> Int { value }
}
let c = Counter()
await c.increment()                        // cross-actor access is awaited

@MainActor
class ProfileVM: ObservableObject {           // all members run on the main thread
    @Published var name = ""            // safe to update UI-bound state directly
}
WATCH

Don't DispatchQueue.main.sync { ... } from the main thread — instant deadlock. And never block the main thread with synchronous network or disk I/O; that's the classic beach-ball/frozen-UI bug. In async/await land, avoid mixing raw GCD hops with actors — let @MainActor do the hopping.

INTERVIEW ANGLE

Be fluent in both: "How would you fetch data without freezing the UI?" — background queue / async function, hop to main / @MainActor for UI. Deeper: contrast GCD callbacks with structured concurrency (cancellation propagation, no callback pyramids, compile-time data-race safety), and explain what an actor guarantees and why it removes manual locks. Name the deadlock trap and the main-thread rule.

App Lifecycle & Scene Phases

Above individual screens sits the app's own lifecycle: launching, foreground/active, inactive, background, and (maybe) termination. Modern iOS also splits an app into scenes (windows) for multitasking.

Analogy. Your app is a shop. Active = open and serving customers. Inactive = briefly interrupted (a phone call overlays, the app switcher is open) — lights on, no transactions. Background = shutters down but staff still tidying up for a few seconds (save the till, finish the receipt). Suspended/terminated = closed; the system may quietly demolish the shop to reclaim land (memory).

SwiftUI: scenePhase

@main
struct MyApp: App {
    @Environment(\.scenePhase) private var phase
    var body: some Scene {
        WindowGroup { ContentView() }
            .onChange(of: phase) { _, newPhase in
                switch newPhase {
                case .active:     resume()      // visible & receiving events
                case .inactive:   pauseTimers() // transitioning / interrupted
                case .background: saveState()   // last chance to persist
                @unknown default: break
                }
            }
    }
}

UIKit: AppDelegate + SceneDelegate

  • AppDelegate — process-level events: application(_:didFinishLaunchingWithOptions:), push-notification registration, background fetch.
  • SceneDelegate — per-window UI state (since multi-window/iPad): sceneDidBecomeActive, sceneWillResignActive, sceneDidEnterBackground, sceneWillEnterForeground, sceneDidDisconnect.
  • A single app can have multiple scenes (windows) alive at once; the app delegate is shared, scene delegates are per-window.

What to do in each phase

PhaseDoDon't
LaunchMinimal setup; get to first frame fast (launch-time budget)Heavy sync work — it delays the launch and can trigger a watchdog kill
ActiveResume timers/animations, refresh live dataAssume you were never backgrounded — state may be stale
InactivePause games/media, dim sensitive contentStart long work — you may be about to background
BackgroundPersist state, flush, request extra time via a background task if neededExpect unlimited time — you get seconds, then suspension
TRAP

Assuming applicationWillTerminate always runs. When the system reclaims a suspended app's memory, it usually kills it without calling terminate. So persistence must happen on entering background, not on termination. Treat "entered background" as "I might never wake up here again."

INTERVIEW ANGLE

"Where do you save user state so nothing is lost?" — on backgrounding (scenePhase == .background / sceneDidEnterBackground), because termination isn't guaranteed. Follow-ups probe launch performance (why heavy work at launch is dangerous) and multi-scene apps (AppDelegate is process-wide, SceneDelegate is per-window). Bonus: background execution limits and background tasks/modes.

Memory Management & Common Leaks

ARC handles the routine work, but a handful of patterns reliably leak. Knowing the usual suspects — and the tools that catch them — is a strong practical signal.

Analogy. ARC is a diligent janitor who throws out anything nobody is holding. But it can't throw out two objects clutching each other, and it can't see a note you pinned to the bulletin board (a global/observer) that still points at something. Leaks are almost always "someone is still holding on when they shouldn't be."

The usual suspects

Closures capturing self

  • A stored closure that references self keeps self alive.
  • Fix: [weak self] (then guard let self else { return }).
  • The single most common production leak.

Strong delegates

  • A delegate should be weak var delegate: FooDelegate?.
  • Strong delegate + child holding parent = cycle.

Timers & observers

  • A target-action Timer retains its target (the VC), so deinit won't fire until it's invalidated — invalidate it from a lifecycle callback like viewDidDisappear. Only a block-based timer capturing [weak self] can safely be invalidated in deinit.
  • Block-based NotificationCenter observers capture strongly — use [weak self] and remove them.

Unbounded caches

  • A growing dictionary cache is a "leak" in effect (memory climbs).
  • Use NSCache (auto-evicts under pressure) or a bounded LRU.

Detection toolkit

  • A deinit that never prints — the cheapest leak detector. Add one to suspect classes.
  • Memory Graph Debugger (Xcode) — pause and see who still references an object; purple ! flags cycles.
  • Instruments → Leaks & Allocations — track live bytes and abandoned memory over time.
  • Malloc Stack Logging — capture allocation backtraces to find where a leaked object was created.
// Autorelease pool: in a tight loop that creates many temporaries,
// drain per-iteration so peak memory doesn't balloon.
for url in imageURLs {
    autoreleasepool {
        let img = UIImage(contentsOfFile: url.path)
        process(img)                          // temporaries freed each pass
    }
}
WATCH

Not every memory growth is a "leak" ARC can see. Abandoned memory (still referenced but never used again — e.g. an ever-growing array) won't show up in the Leaks instrument because it's technically reachable. Use Allocations/Memory Graph to catch those.

INTERVIEW ANGLE

Expect "your app's memory climbs over time — how do you debug it?" Structure the answer: reproduce → add deinit logging / Memory Graph to find retained objects → identify the cycle or unbounded structure → fix with weak/removal/eviction → verify deinit now fires. Naming the closure-capture cycle and the strong-delegate cycle unprompted is what marks a senior answer.

SwiftData / Core Data

Core Data is Apple's mature object-graph persistence framework (an ORM-like layer, usually backed by SQLite) with contexts, fetch requests, and relationships. SwiftData is the modern Swift-native wrapper over the same engine: declare a model with the @Model macro and query with @Query.

import SwiftData

@Model
final class TodoItem {
    var title: String
    var done: Bool
    var createdAt: Date
    init(title: String, done: Bool = false) {
        self.title = title
        self.done = done
        self.createdAt = .now
    }
}

struct TodoList: View {
    @Query(sort: \TodoItem.createdAt) private var items: [TodoItem]
    @Environment(\.modelContext) private var context
    var body: some View {
        List(items) { Text($0.title) }
            .toolbar {
                Button("Add") { context.insert(TodoItem(title: "New")) }
            }
    }
}

Networking with URLSession

URLSession is the built-in HTTP client. It is asynchronous by design — its work never runs on the main thread, and its completion handlers historically ran on a background queue. With async/await it reads cleanly:

struct Post: Codable { let id: Int; let title: String }

func fetchPosts() async throws -> [Post] {
    var req = URLRequest(url: URL(string: "https://api.example.com/posts")!)
    req.httpMethod = "GET"
    let (data, resp) = try await URLSession.shared.data(for: req)
    guard let http = resp as? HTTPURLResponse,
          (200..<300).contains(http.statusCode) else {
        throw URLError(.badServerResponse)
    }
    return try JSONDecoder().decode([Post].self, from: data)   // Codable parsing
}
TIP

Standard production touches: set timeouts and caching policy on the URLSessionConfiguration, decode JSON with Codable, surface typed errors, and for uploads/downloads that must survive backgrounding use a background URLSession. Update UI only after hopping to the main actor.

INTERVIEW ANGLE

"Design the data layer for a feed screen." Then the storage decision matrix: why not UserDefaults for a feed, why Keychain for the auth token, and where the offline cache lives.

Performance & the Main-Thread Rule

On iOS, performance is mostly one discipline: keep the main thread free so every frame ships on time. Everything else — scrolling, memory, launch — flows from that.

Analogy. The screen redraws like a flip-book: 60 (or 120) pages a second. Each page must be drawn within its slot — about 16 ms at 60fps, 8 ms at 120fps. If the main thread is busy parsing JSON or resizing a giant image when the page is due, that page is skipped: the user sees a stutter (a "dropped frame" or "hitch"). So the rule is blunt: do slow work off the main thread; only touch UI on it.

THE ONE RULE

UIKit and SwiftUI are not thread-safe. All view reads and writes must happen on the main thread. Network, disk, image decoding, JSON parsing, and heavy computation must happen off it, then hop back (DispatchQueue.main.async / @MainActor) for the UI update. Violating this causes intermittent crashes and corrupted layout that are miserable to reproduce.

  • Time Profiler — where CPU time goes; find the main-thread hot path.

WATCH

The most common self-inflicted jank: doing image decode/resize or JSON parsing inside cellForRowAt / a SwiftUI body. Both run on the main thread and both run per visible cell during a scroll — guaranteeing dropped frames. Precompute off-thread and cache.

INTERVIEW ANGLE

"Your table view scrolls poorly — how do you fix it?" Structure it: confirm cell reuse, move image decode/resize and any IO off the main thread, cache decoded images, and profile with the Time Profiler + Animation Hitches instruments to prove the fix. Tie every point back to the 16 ms frame budget and the main-thread rule — that framing is what separates a senior answer from a list of tips.

The one thing that's genuinely different: memory

NOTE

Android (JVM) and the web (JS) both use a tracing garbage collector: a background collector periodically finds unreachable objects, so mutual references get cleaned up automatically — but you pay unpredictable GC pauses. iOS uses ARC: deallocation is deterministic and pause-free, but there is no cycle collector. Two objects that strongly reference each other leak forever unless you break the cycle with weak/unowned. This is the habit web/Android devs must build on iOS — see the ARC tab.

Things that transfer directly

  • Declarative UI intuition from React/Compose maps almost 1:1 onto SwiftUI — state drives the view, the framework diffs and re-renders.
  • Structured concurrency from Kotlin coroutines maps onto Swift's async/await, Task, and TaskGroup, including cooperative cancellation.
  • The main-thread UI rule is identical across all three platforms — only the main thread touches the UI; everything slow goes elsewhere.
  • MVVM / unidirectional data flow patterns carry over; the wrappers change names, not shape.
INTERVIEW ANGLE

If you're crossing over, lead with the analogy ("SwiftUI is React; coroutines are async/await") to show transfer, then pivot to the delta that matters: "The big adjustment is memory — iOS is ARC, not GC, so I actively watch for retain cycles with weak/unowned, especially in closures and delegates." Naming that difference unprompted signals you understand iOS on its own terms, not just by translation.

Terminology & Acronyms

Quick reference for the key terms in this chapter.

TermMeaning
Value typeA type (struct, enum) copied on assignment or passing, so each holder owns an independent value.
Reference typeA type (class) shared on assignment, so multiple names point at the same mutable instance.
Copy-on-write (COW)Optimization where a value type shares its buffer until a mutation, then copies — making value semantics cheap.
OptionalA type that either holds a value or nil, forcing the absence case to be handled explicitly.
ProtocolA capability contract a type can adopt; basis of protocol-oriented programming (composition over inheritance).
UIKitApple's imperative UI framework: you hold references to views and mutate them step by step.
SwiftUIApple's declarative UI framework: the view is a function of state, re-rendered when state changes.
@State / @ObservableSwiftUI's state model: @State owns view-local state; @Observable marks a reference-type model whose property changes trigger re-render. Older code uses ObservableObject + @Published.
deinitA class's deallocation callback; a deinit that never runs is a telltale sign of a leak.
ARCAutomatic Reference Counting — compiler-inserted retain/release that frees an object when its count hits zero.
Retain cycleTwo objects strongly referencing each other, so neither's count reaches zero — a leak ARC can't collect.
weak referenceA non-retaining, optional reference that auto-nils when its target is freed; used to break cycles.
unowned referenceA non-retaining, non-optional reference assumed always valid; crashes if used after the target is freed.
GCDGrand Central Dispatch — the queue-based API for dispatching work across threads via serial/concurrent queues.
QoSQuality of Service — a priority hint (.userInteractive down to .background) for how the system schedules work.
async / awaitSwift syntax for asynchronous code that suspends without blocking the thread and reads top-to-bottom.
actorA reference type that serializes access to its own mutable state, eliminating data races without manual locks.
@MainActorA global actor tied to the main thread; annotating UI code enforces the main-thread rule at compile time.
scenePhaseSwiftUI environment value reporting the app's phase: active, inactive, or background.
URLSessionThe built-in asynchronous HTTP client; its work runs off the main thread by design.
CodableProtocol for encoding and decoding Swift types to and from formats like JSON.
Core Data / SwiftDataApple's object-graph persistence; SwiftData is the modern @Model-based wrapper over the same engine.
