Objective-C Refresher

Objective-C's distinctive model and the syntax around it — Smalltalk-style message passing and dynamic dispatch, classes and designated initializers, properties and ARC memory management, blocks, protocols and delegation, categories, and the Foundation types — a practical brush-up for a programmer reading or maintaining legacy iOS/macOS code

Message passing — the core model

Objective-C is C with a thin Smalltalk-style object layer added on top. The single idea that everything else follows from is that you don't call methods — you send messages. The syntax is [receiver selector:arg], not receiver.method(arg). A selector is the name of the message (e.g. length, stringByAppendingString:); the runtime looks it up on the receiver's class at run time and dispatches dynamically. Two consequences a newcomer feels immediately: method names read as interleaved label:value pairs, and sending a message to nil is legal and does nothing — it returns 0/nil instead of crashing.

// import Foundation — the base framework (NSString, NSArray, …)
#import <Foundation/Foundation.h>

int main(void) {
    @autoreleasepool {
        NSString *s = @"hello";
        // message send: [receiver selector] — NOT s.uppercaseString()
        NSString *up = [s uppercaseString];
        NSUInteger n  = [up length];
        // keyword message: one label per argument
        NSString *joined = [s stringByAppendingString:@" world"];
        printf("%s %lu %s\n", [up UTF8String], (unsigned long)n, [joined UTF8String]);

        // messaging nil is SAFE: returns 0 / nil, no crash
        NSString *nothing = nil;
        NSUInteger z = [nothing length];        // 0
        id r = [nothing uppercaseString];          // nil
        printf("nil length = %lu\n", (unsigned long)z);
        printf("nil object message -> %s\n", r == nil ? "nil" : "obj");
    }
    return 0;
}
// → output:
HELLO 5 hello world
nil length = 0
nil object message -> nil

Dispatch is dynamic: [obj doThing] compiles to objc_msgSend(obj, @selector(doThing)), which finds the implementation on obj's class at run time. That is why the language supports selectors as first-class values, respondsToSelector: introspection, categories, and swizzling — the binding is a runtime lookup, not a compile-time address. The flip side is that a typo in a selector is not a compile error unless the compiler can see a declaration for it.

nil-messaging is a feature, not a bug: it removes most of the defensive if (x != null) checks a Java or C++ developer expects. A message to nil returns nil for object returns, 0 for numeric returns, and a zeroed struct only for structs small enough to be returned in registers (larger struct returns — e.g. >16 bytes on arm64, returned via an indirect pointer — are left undefined, so don't rely on them). The cost is that a silently-swallowed nil can mask a logic error — see the Pitfalls section.

Classes — @interface / @implementation & initializers

A class is split into a public @interface (the declaration, historically in a .h header) and an @implementation (the code, in a .m file). Methods are prefixed by their receiver kind: - for instance methods and + for class methods. Objects are created in two steps — alloc grabs zeroed memory, then an init method sets it up: [[Vec2 alloc] initWithX:3 y:4]. The designated initializer is the one that does the real work (calls [super init] and assigns every ivar); convenience initializers funnel into it. Return instancetype from initializers and factory methods so the static type is the actual subclass.

#import <Foundation/Foundation.h>

@interface Vec2 : NSObject
@property (nonatomic) double x;
@property (nonatomic) double y;
// designated initializer — returns instancetype, not id
- (instancetype)initWithX:(double)x y:(double)y;
- (double)distanceTo:(Vec2 *)other;
+ (instancetype)origin;                    // + = class (factory) method
@end

@implementation Vec2
- (instancetype)initWithX:(double)x y:(double)y {
    self = [super init];              // always chain to super's init
    if (self) {
        _x = x;                       // assign the auto-synthesized ivar _x
        _y = y;
    }
    return self;
}
- (double)distanceTo:(Vec2 *)other {
    double dx = self.x - other.x;     // dot-syntax = a getter message
    double dy = self.y - other.y;
    return sqrt(dx*dx + dy*dy);
}
+ (instancetype)origin {
    return [[self alloc] initWithX:0 y:0];
}
@end

int main(void) {
    @autoreleasepool {
        Vec2 *a = [[Vec2 alloc] initWithX:3 y:4];
        Vec2 *o = [Vec2 origin];
        printf("a = (%.0f, %.0f)\n", a.x, a.y);
        printf("distance = %.1f\n", [a distanceTo:o]);
    }
    return 0;
}
// → output:
a = (3, 4)
distance = 5.0

The self = [super init] assignment is not a ritual: an initializer is allowed to return a different object (or nil on failure), so you must capture and test what super hands back before touching ivars. Note that inside the initializer we assign the ivar _x directly rather than the property self.x — a common convention, because a subclass could override the setter and you don't want that running against a half-built object.

Do not name a class Point, Rect, Size, Fixed, or other identifiers that collide with C typedefs in the SDK's MacTypes.h — you'll get a "redefinition as a different kind of symbol" error. Real code sidesteps this with a class prefix (Objective-C has no namespaces): Foundation uses NS, and your app might use a two- or three-letter prefix of its own.

Properties — @property, attributes & the synthesized ivar

A @property declares a getter/setter pair (and, by default, a backing ivar named _name) in one line. The parenthesized attributes control the accessors: memory policy (strong / weak / copy / assign), atomicity (nonatomic for the common single-threaded case; the default atomic adds locking), and mutability (readonly vs the default readwrite). Dot-syntax (obj.name) is pure sugar for the accessor messages [obj name] / [obj setName:…] — it is not a field access.

@interface Person : NSObject
@property (nonatomic, copy)     NSString *name;     // copy: snapshot against mutable strings
@property (nonatomic)           NSInteger age;
@property (nonatomic, readonly) NSString *summary;  // getter only
@end

@implementation Person
- (NSString *)summary {                       // custom getter for the readonly prop
    return [NSString stringWithFormat:@"%@ (%ld)", self.name, (long)self.age];
}
@end

int main(void) {
    @autoreleasepool {
        Person *p = [Person new];           // new = alloc + init
        NSMutableString *m = [NSMutableString stringWithString:@"Ann"];
        p.name = m;                        // dot-syntax setter; copy takes a snapshot
        [m appendString:@"XYZ"];             // mutate the ORIGINAL afterwards
        p.age = 30;
        printf("name=%s\n", [p.name UTF8String]);   // still "Ann" — copy protected us
        printf("summary=%s\n", [p.summary UTF8String]);
    }
    return 0;
}
// → output:
name=Ann
summary=Ann (30)

Why copy on NSString? A caller can hand you an NSMutableString where an NSString is expected. With strong you'd retain their mutable instance and it could change under you; copy takes an immutable snapshot at assignment time. The rule of thumb: use copy for value-like types that have a mutable subclass (NSString, NSArray, NSDictionary, blocks), and strong for genuine reference objects.

Modern Objective-C auto-synthesizes the ivar and accessors, so you rarely write @synthesize. The backing ivar is _name by default. You reach it directly (_name) inside initializers and dealloc; everywhere else prefer self.name so custom accessors and KVO notifications fire.

Memory management — ARC, strong / weak & retain cycles

Objective-C manages object lifetime with reference counting. Under ARC (Automatic Reference Counting) — the default in every modern project — the compiler inserts the retain/release calls for you at compile time; an object is deallocated when its retain count hits zero. You never call retain/release by hand. What you do control is the ownership qualifier on each reference: strong keeps the target alive (the default for object properties); weak does not, and is automatically set to nil when the target is deallocated; unsafe_unretained is like weak but is not zeroed (a dangling pointer risk — avoid it unless targeting very old runtimes).

The classic leak is a retain cycle: two objects that hold each other with strong references keep each other's count above zero forever. You break the cycle by making one direction weak — canonically, a child's back-reference to its parent, or a delegate reference.

@class Parent;

@interface Child : NSObject
@property (nonatomic, weak) Parent *parent;    // weak → breaks the cycle
@end
@implementation Child
- (void)dealloc { printf("Child dealloc\n"); }
@end

@interface Parent : NSObject
@property (nonatomic, strong) Child *child;  // parent strongly OWNS child
@end
@implementation Parent
- (void)dealloc { printf("Parent dealloc\n"); }
@end

int main(void) {
    @autoreleasepool {
        Parent *p = [Parent new];
        Child  *c = [Child new];
        p.child  = c;      // strong
        c.parent = p;      // weak → no cycle
        printf("wired up\n");
    }   // scope ends: both deallocate because nothing strongly retains them
    printf("after pool\n");
    return 0;
}
// → output (build with clang -fobjc-arc):
wired up
Parent dealloc
Child dealloc
after pool

Make both directions strong and neither dealloc ever prints — the objects leak. That is the retain cycle. The fix is exactly the weak back-reference above; delegates and parent pointers are weak for this reason, and blocks capturing self need the weakSelf pattern (see Blocks).

Autorelease pools & the historical MRC note

The @autoreleasepool { … } block drains objects that were autoreleased (returned by convenience constructors like stringWithFormat:) when the block exits. In an app the run loop wraps each iteration in a pool for you; you add an explicit one around tight loops that create many temporaries, or in a plain command-line main. Before 2011, code used Manual Reference Counting (MRC): you balanced every alloc/retain/copy with a matching release/autorelease by hand, following the "you own what you alloc/copy/new/retain" rule.

Legacy (MRC) code you may still meet: explicit [obj retain], [obj release], [obj autorelease], and [super dealloc] at the end of a dealloc. Under ARC these are compile errors (the compiler owns them). A file can opt out with -fno-objc-arc, which is how mixed old/new codebases keep a few MRC files alive — but new code is always ARC.

Foundation types — strings, collections & literals

Foundation supplies the everyday value types, and nearly all come in an immutable class plus a mutable subclass: NSString / NSMutableString, NSArray / NSMutableArray, NSDictionary / NSMutableDictionary. Collections hold objects only, so scalars are boxed into NSNumber. Compiler literals make this bearable: @"…" for strings, @[…] for arrays, @{…} for dictionaries, and @(expr) to box a number or BOOL. Subscripting (arr[i], dict[key]) works on both.

int main(void) {
    @autoreleasepool {
        NSArray *arr = @[@"a", @"b", @"c"];              // array literal
        NSDictionary *dict = @{@"one": @1, @"two": @2};  // dictionary literal
        NSNumber *n = @(3 + 4);                        // boxed int → NSNumber
        BOOL flag = YES;
        NSNumber *b = @(flag);                          // boxed BOOL

        printf("arr[1] = %s\n", [arr[1] UTF8String]);      // subscripting
        printf("count = %lu\n", (unsigned long)arr.count);
        printf("two = %ld\n", (long)[dict[@"two"] integerValue]);
        printf("n = %d, b = %d\n", [n intValue], [b boolValue]);

        NSMutableArray *ma = [@[@1, @2] mutableCopy];
        [ma addObject:@3];
        printf("ma.count = %lu\n", (unsigned long)ma.count);
    }
    return 0;
}
// → output:
arr[1] = b
count = 3
two = 2
n = 7, b = 1
ma.count = 3

The literals are pure compiler sugar: @[a, b] lowers to [NSArray arrayWithObjects:(id[]){a, b} count:2] (a counted C-array call), and @42 to [NSNumber numberWithInt:42]. That counted call raises an exception on a nil element, so a nil inside an @[…] literal is a runtime crash, not a truncation — use NSNull as an explicit placeholder (next section) when a slot may be empty.

%@ is the format specifier for "any object" — it sends description (or debugDescription) to the argument. It works in NSLog and +stringWithFormat:, not in C's printf; that's why these runnable snippets convert to a C string with UTF8String before printf. In real code you'd typically write NSLog(@"%@", obj).

Blocks — closures, capture & __block

A block is Objective-C's closure: an anonymous function that captures variables from its enclosing scope. The type syntax uses a caret: returnType (^name)(paramTypes), and the literal is ^returnType(params){ … } (the return type is usually inferred and omitted). By default a block captures a copy of each referenced local (by value at creation time); to mutate a captured local and share it back, mark it __block. Blocks are used throughout Foundation's enumerate…UsingBlock:, completion handlers, and GCD (Grand Central Dispatch).

int main(void) {
    @autoreleasepool {
        // block literal: ^returnType(params){…}; here the return type is inferred
        int (^square)(int) = ^(int n){ return n * n; };
        printf("square(6) = %d\n", square(6));

        int captured = 10;
        void (^printCaptured)(void) = ^{ printf("captured = %d\n", captured); };
        captured = 99;              // block copied the VALUE at creation time
        printCaptured();             // prints 10, not 99

        __block int total = 0;      // __block → mutable & shared with the block
        NSArray *nums = @[@1, @2, @3, @4];
        [nums enumerateObjectsUsingBlock:^(NSNumber *x, NSUInteger i, BOOL *stop){
            total += [x intValue];
        }];
        printf("total = %d\n", total);
    }
    return 0;
}
// → output:
square(6) = 36
captured = 10
total = 10

The retain-cycle-with-self pitfall. A block that references self (or an ivar, which implicitly captures self) strongly retains self. If self also retains the block — e.g. a stored @property (copy) completion handler — you have a cycle and both leak. The fix is the weakSelf / strongSelf pattern: capture a __weak reference, then re-pin it to a local strong inside the block so it can't vanish mid-body.

typedef void (^Task)(void);

@interface Worker : NSObject
@property (nonatomic, copy) Task task;   // self retains the block…
@property (nonatomic) NSInteger jobs;
@end

@implementation Worker
- (void)dealloc { printf("Worker dealloc\n"); }
- (void)setup {
    __weak typeof(self) weakSelf = self;      // …so capture self WEAKLY
    self.task = ^{
        typeof(self) strongSelf = weakSelf;   // pin for the block body
        if (strongSelf) {
            printf("jobs = %ld\n", (long)strongSelf.jobs);
        }
    };
}
@end

int main(void) {
    @autoreleasepool {
        Worker *w = [Worker new];
        w.jobs = 5;
        [w setup];
        w.task();
    }   // Worker deallocates — block held self weakly, so no cycle
    printf("done\n");
    return 0;
}
// → output:
jobs = 5
Worker dealloc
done

Note the "Worker dealloc" fires before "done": with weakSelf the block does not keep the Worker alive, so it is released at the end of the pool. Replace weakSelf with a direct self reference and the stored block would retain the Worker forever — the cycle. This exact pattern shows up in every completion-handler-heavy iOS codebase.

Protocols — interfaces & the delegation pattern

A @protocol is Objective-C's interface: a named list of methods a class can promise to implement. Methods are @required by default or explicitly @optional. A class adopts protocols in angle brackets after its superclass (@interface Foo : NSObject <Bar, Baz>), and you type a value by capability with id<Protocol> — "any object conforming to Protocol". Before calling an optional method you must probe with respondsToSelector:, because it may not be there.

@protocol Formatter <NSObject>
@required
- (NSString *)format:(NSInteger)value;
@optional
- (NSString *)prefix;
@end

@interface HexFormatter : NSObject <Formatter>
@end
@implementation HexFormatter
- (NSString *)format:(NSInteger)value {
    return [NSString stringWithFormat:@"0x%lX", (unsigned long)value];
}
@end

// accept ANY object that conforms to Formatter
NSString *describe(id<Formatter> f, NSInteger v) {
    NSString *body = [f format:v];
    if ([f respondsToSelector:@selector(prefix)]) {  // guard the optional method
        return [[f prefix] stringByAppendingString:body];
    }
    return body;
}

int main(void) {
    @autoreleasepool {
        HexFormatter *h = [HexFormatter new];
        printf("%s\n", [describe(h, 255) UTF8String]);
        printf("conforms = %d\n", [h conformsToProtocol:@protocol(Formatter)]);
    }
    return 0;
}
// → output:
0xFF
conforms = 1

Delegation is the pattern that made protocols famous across Cocoa. Instead of subclassing a view or a data source, an object exposes a @property (nonatomic, weak) id<SomeDelegate> delegate; and calls back into it ([self.delegate didFinish:result]) at key moments. The delegate is weak to avoid the classic view↔controller retain cycle, and optional callbacks are guarded with respondsToSelector:. This is how UITableView, UITextField, and countless APIs hand control back to your code.

Categories & class extensions

A category adds methods to an existing class you don't own — even a Foundation class — without subclassing. The syntax is @interface ClassName (CategoryName). A class extension is an anonymous category — @interface ClassName () — placed in the .m file to declare private ivars, properties, and methods, and (a common trick) to redeclare a publicly readonly property as readwrite internally.

// Category: add a method to NSString (a class you don't own)
@interface NSString (Shout)
- (NSString *)shout;
@end
@implementation NSString (Shout)
- (NSString *)shout {
    return [[self uppercaseString] stringByAppendingString:@"!"];
}
@end

@interface Counter : NSObject
@property (nonatomic, readonly) NSInteger count;   // public: read-only
- (void)tick;
@end

// Class extension: private surface, declared in the .m
@interface Counter ()
@property (nonatomic, readwrite) NSInteger count;  // redeclare as writable internally
@end

@implementation Counter
- (void)tick { self.count += 1; }
@end

int main(void) {
    @autoreleasepool {
        printf("%s\n", [[@"hi" shout] UTF8String]);
        Counter *c = [Counter new];
        [c tick]; [c tick];
        printf("count = %ld\n", (long)c.count);
    }
    return 0;
}
// → output:
HI!
count = 2

Category caveats. A category cannot add stored properties/ivars (only methods), and if two categories define the same selector on the same class, which one wins is undefined. Because categories can also override existing methods with no compile-time warning, prefix category method names in shipping code (e.g. myapp_shout) to avoid silently clobbering a framework method or colliding with a future SDK addition.

nil / Nil / NULL / NSNull, BOOL & errors

Objective-C has four distinct "nothing" values, and mixing them up is a classic source of bugs. nil is a null object pointer; Nil is a null Class pointer; NULL is the C null pointer (for non-object C pointers); and NSNull is a real singleton object ([NSNull null]) used as a placeholder inside collections, which cannot store a bare nil. BOOL is a C type with the values YES (1) and NO (0).

int main(void) {
    @autoreleasepool {
        // NSNull is a real object placeholder — collections can't hold bare nil
        NSArray *a = @[@"x", [NSNull null], @"z"];
        id middle = a[1];
        printf("is NSNull = %d\n", middle == [NSNull null]);

        NSString *s1 = [NSString stringWithFormat:@"ab%@", @"c"];
        NSString *s2 = @"abc";
        printf("== (identity) : %d\n", s1 == s2);        // pointer compare — may be 0
        printf("isEqual (value): %d\n", [s1 isEqualToString:s2]);

        BOOL yes = YES;
        printf("BOOL yes = %d\n", yes);                // YES is 1, NO is 0
    }
    return 0;
}
// → output:
is NSNull = 1
== (identity) : 0
isEqual (value): 1
BOOL yes = 1

== compares pointers, so it is true only when two references point at the exact same object. For value equality you must send isEqual: (or a typed variant like isEqualToString:). The == (identity) line prints 0 here because the runtime-built string and the literal are different instances — never compare object contents with ==.

Error handling — NSError ** out-parameter

Objective-C uses exceptions (@throw/@try) only for programmer errors; recoverable/runtime failures use the NSError convention: the method returns a BOOL (or nil object) to signal success, and writes details into an NSError ** out-parameter. Callers pass the address of a local NSError * and inspect it only when the return value indicates failure.

// BOOL return signals success; details flow out via NSError **
BOOL parsePositive(NSString *text, NSInteger *out, NSError **error) {
    NSInteger v = [text integerValue];
    if (v <= 0) {
        if (error) {                       // always null-check the out-param
            *error = [NSError errorWithDomain:@"AppErrorDomain"
                                         code:42
                                     userInfo:@{NSLocalizedDescriptionKey: @"not positive"}];
        }
        return NO;
    }
    if (out) *out = v;
    return YES;
}

int main(void) {
    @autoreleasepool {
        NSError *err = nil;
        NSInteger value = 0;
        if (parsePositive(@"7", &value, &err)) {
            printf("ok: %ld\n", (long)value);
        }
        if (!parsePositive(@"-3", &value, &err)) {   // test the RETURN, not err
            printf("failed: %s (code %ld)\n",
                   [err.localizedDescription UTF8String], (long)err.code);
        }
    }
    return 0;
}
// → output:
ok: 7
failed: not positive (code 42)

The golden rule: decide success from the return value, not from whether error is non-nil. A method may leave *error untouched (or set) even on success, so reading it after a YES return is undefined-behavior territory. This is the same shape Swift bridges into throws — a Swift try foo() maps onto exactly this NSError ** pattern.

Common pitfalls (and their fixes)

1 · nil-messaging silently no-ops

The same feature that removes null-checks can hide a bug: [obj doWork] on a nil obj does nothing and returns 0/nil, so a method that "isn't running" is often a silently-nil receiver. When a value must not be nil, assert it (NSParameterAssert(obj)) rather than letting the message vanish. Watch especially for nil arithmetic: [array count] on a nil array is 0, which can mask a failed load.

2 · == vs isEqual:

As shown in the nil & errors section, == compares pointers. Comparing string or number contents with == works only by accident (interned literals) and breaks the moment one side is built at runtime. Always use isEqual: / isEqualToString: for value equality — and if you override isEqual: on your own class, override hash to match, or the object misbehaves as a dictionary key.

3 · Mutable vs immutable copy

Sending copy to an immutable object may return the same instance (a valid optimization — there's nothing to copy), whereas mutableCopy always returns a distinct mutable object. Don't assume copy gives you a fresh, mutable object.

NSString *imm = @"abc";
NSString *c = [imm copy];                // immutable copy → may be the SAME object
NSMutableString *mc = [imm mutableCopy];  // always a distinct instance
printf("copy same ptr = %d\n", imm == c);
printf("mutableCopy same ptr = %d\n", imm == (NSString *)mc);
[mc appendString:@"d"];
printf("mc = %s, imm = %s\n", [mc UTF8String], [imm UTF8String]);
// → output:
copy same ptr = 1
mutableCopy same ptr = 0
mc = abcd, imm = abc

4 · Retain cycles in blocks & delegates

A stored block that captures self, or a strong delegate reference, is the two most common leaks. Blocks: use the weakSelf/strongSelf pattern (Blocks section). Delegates: declare @property (nonatomic, weak) id<…> delegate;. Both come down to the same rule — the "back" or "callback" pointer should be weak so it doesn't form a cycle with the owner.

5 · KVC / KVO pitfalls

Key-Value Coding (valueForKey: / setValue:forKey:) and Key-Value Observing resolve keys as strings at run time, so a mistyped key is not a compile error — it throws NSUnknownKeyException at run time. For KVO to fire, changes must go through the accessor (self.name = … or setValue:forKey:); assigning the ivar _name directly bypasses the notification. And every addObserver:… must be balanced by removeObserver:… before the observer deallocates, or you crash on the next notification to a dead object.

A meta-pitfall for newcomers: treating Objective-C as "C++ with brackets". The dynamic runtime changes the mental model — dispatch is by selector at run time (so there is no compile-time devirtualization to lean on), nil receivers are silent, equality and copying are message-based, and object lifetime is reference-counted (mind cycles), not scope-based like C++ RAII. Idiomatic Objective-C leans on the runtime (protocols, categories, KVC/KVO, delegation) rather than fighting it.

Tooling & interop

Objective-C is compiled by clang (the LLVM C-family front end), links against Foundation (and, on Apple platforms, UIKit/AppKit), and is edited in Xcode. A single-file program builds and runs from the command line:

# compile one .m file against Foundation, with ARC enabled
clang -fobjc-arc -framework Foundation prog.m -o prog
./prog
Tool / flagWhat it does
clangThe compiler; treats .m as Objective-C, .mm as Objective-C++.
-fobjc-arcEnable ARC. Xcode turns this on by default; the bare CLI does not, so add it (or use -fno-objc-arc for a legacy MRC file).
-framework FoundationLink the Foundation framework (NSString, collections, NSError, …).
Xcode / xcodebuildThe IDE and its build tool; the Static Analyzer catches leaks and misuse.

Bridging to Swift

Objective-C and Swift interoperate in the same target. Swift imports Objective-C via a bridging header; Objective-C sees Swift classes through a generated -Swift.h header (Swift symbols must be marked @objc / @objcMembers or inherit NSObject). Nullability annotations (nullable / nonnull, usually via the NS_ASSUME_NONNULL_BEGIN/_END region) tell Swift which Objective-C references become optionals, and NSError ** methods bridge to Swift throws. For plain C / Core Foundation pointers, ownership is transferred across the ARC boundary with __bridge, __bridge_retained, and __bridge_transfer casts.

Interview angle. A crisp "what makes Objective-C distinctive?" answer: it is C plus a dynamic messaging runtime. Dispatch is by selector at run time (enabling categories, delegation, KVC/KVO, and introspection); messaging nil is safe; memory is reference-counted with ARC, so the real skill is spotting retain cycles and reaching for weak. Its whole design optimizes for the dynamic, framework-heavy Cocoa style — which is also why Swift, its successor, kept full two-way interop rather than a clean break.

Every runnable snippet in this chapter was compiled and executed with clang -fobjc-arc -framework Foundation on macOS; the // → output blocks are the real program output. Output is printed with C's printf (via -UTF8String) purely to keep it deterministic and prefix-free — production code logs with NSLog(@"%@", …), which adds a timestamp and process prefix.

strong / weakOwnership qualifiers: strong keeps the target alive; weak does not and auto-nils when it is deallocated.
Retain cycleTwo objects retaining each other strongly so neither's count reaches zero — a leak, broken with weak.
Autorelease poolA @autoreleasepool { … } scope that releases autoreleased objects when it exits.
MRC (Manual Reference Counting)Legacy pre-ARC model where you balanced retain/release/autorelease calls by hand.
FoundationThe base framework supplying NSString, the collections, NSNumber, NSError, and other value types.
BlockObjective-C's closure: an anonymous function that captures variables from its enclosing scope.
__blockQualifier letting a block mutate a captured local and share the change back with the enclosing scope.
weakSelf / strongSelfPattern for capturing self weakly then re-pinning it inside a block to avoid a retain cycle.
ProtocolA named list of @required/@optional methods a class can promise to implement — an interface.
DelegationPattern where an object calls back into a weak delegate that conforms to a protocol.
Category / class extensionA category adds methods to an existing class; an anonymous category (class extension) declares a class's private surface.
NSNullSingleton object ([NSNull null]) used as a placeholder inside collections, which cannot hold a bare nil.
BOOL / YES / NOObjective-C's boolean type and its two values, YES (1) and NO (0).
NSError **Out-parameter error convention: the return value signals success, and error details flow out through the pointer.
KVC / KVO (Key-Value Coding / Observing)String-keyed property access and change observation, resolved by name at run time.
