Cloud AI/ML Infrastructure — a build-up track

This page is a single, self-contained study track for the infrastructure that trains, serves, and operates modern AI/ML systems in the cloud. It moves from the physical foundation (compute, accelerators, storage, network) up through orchestration, the data plane, distributed training, inference optimization, MLOps, LLM/agent systems, and finally the production concerns — scale, reliability, cost, security — that turn a pile of GPUs into a shared platform. The emphasis throughout is on the way a senior infra engineer reasons on a whiteboard: where does the bottleneck live, and who pays for the idle GPU?

The guiding principle that recurs in every module: a GPU is an expensive, non-interchangeable unit of inventory. Almost every design decision — placement, batching, quantization, scheduling, isolation — is ultimately about keeping that inventory busy with useful work while bounding the blast radius of any one failure. Utilization and blast-radius are the two dials you are always turning.

Cloud Compute Foundations for ML

Before you tune a training loop or a serving stack, you pick where the silicon lives, what silicon it is, how you pay for it, and how data reaches it. Those four choices set the cost and reliability ceiling for everything above. This module is the base layer under a DGX-style automation platform: it explains the compute, accelerator, cost, storage, and network primitives an AI-infra engineer is expected to reason about on a whiteboard.

Mental model: an ML system is a pipeline of bandwidths — storage read → host RAM → PCIe/NVLink → HBM → tensor cores, then GPU↔GPU (NVLink/InfiniBand) for collectives. The slowest link that is actually saturated is your bottleneck. Most "the GPU is only 40% utilized" bugs are a starved link upstream, not the GPU.

Regions, Availability Zones, and placement

A region is a geographic location (e.g. us-east-1); an Availability Zone (AZ) is an isolated datacenter (or cluster of them) within a region with independent power/cooling. Regions are ~tens of ms apart; AZs within a region are typically <1–2 ms apart. This geometry drives three decisions:

  • Capacity: the newest accelerators (H100/H200/GB200) are scarce and land in a subset of regions/AZs first. You go where the GPUs are, not where it is convenient.
  • Locality for collectives: a multi-node training job wants all nodes in one AZ (ideally one spine/cluster) so all-reduce runs over low-latency, high-bandwidth fabric. Splitting a job across AZs adds latency and cross-AZ data charges to every gradient sync.
  • Resilience for serving: inference endpoints want to span multiple AZs so one datacenter failure does not take the service down.

Best practice: use a placement group / cluster placement (AWS cluster placement group, GCP compact placement policy) so tightly-coupled training nodes land on the same low-latency fabric. Reserve GPU capacity explicitly (Capacity Blocks / reservations) — for large GPU counts you cannot assume on-demand will have inventory when your job launches.

Gotcha: training in a different AZ from your dataset's storage bucket can incur cross-AZ transfer charges on every epoch's reads, and higher read latency. Co-locate the dataset (or a cache) with the compute.

CPU vs GPU vs TPU/custom ASIC in one paragraph each:

  • CPU — a few dozen powerful, latency-optimized cores. Wins on branchy, sequential, or small-batch work: data loading, tokenization, tree models, orchestration, and inference of small models where latency of a single request dominates. Loses badly on dense linear algebra at scale.
  • GPU — thousands of throughput-optimized cores plus tensor cores for matrix-multiply-accumulate, fed by high-bandwidth memory (HBM). This is the workhorse for transformer training and inference. Programmable and general (CUDA), huge software ecosystem.
  • TPU / custom ASIC (Trainium, Inferentia) — accelerators built around large systolic matrix units and a proprietary interconnect (TPU pods, NeuronLink). Can be cheaper-per-FLOP and scale to huge pods, but the software stack (XLA/JAX, Neuron SDK) is narrower than CUDA. Choose them when your framework supports them well and the price/perf beats GPU for your workload.

Takeaway: "GPU vs TPU" is rarely about raw FLOPs. It is about software maturity for your model and committed price/perf. A 20% cheaper ASIC that needs two engineer-months of porting is not cheaper.

Selection heuristics:

  • Small-model, latency-sensitive, high-QPS inference (≤7B, embeddings, rerankers, CV) → many L4/L40S. Fits the model, cheapest $/request, scales horizontally.
  • Large-model training → H100 for the FP8 transformer engine + NVLink; GB200 NVL72 when the model/optimizer state needs a bigger coherent domain than a single 8-GPU node.
  • Long-context or KV-cache-heavy LLM serving → H200: identical Hopper compute to H100 but 141 GB / 4.8 TB/s HBM holds more KV cache and sustains higher decode throughput.
  • Budget training / older workloads → A100 80 GB is often the price/perf sweet spot when you do not need FP8.

Gotcha: the same model number ships as SXM (NVLink-connected board, higher power/bandwidth) and PCIe (lower bandwidth, no full NVLink mesh). Multi-GPU collective performance can differ 2×+ between them. When you say "H100" in a capacity plan, specify SXM vs PCIe.

GPU memory sizing vs model size

The first feasibility question for any model is "does it fit, and on how many GPUs?". Work it in bytes-per-parameter.

INFERENCE FOOTPRINT

Weights dominate: bytes = params × precision_bytes. FP16/BF16 = 2 B/param, FP8 = 1 B, INT4 = 0.5 B. Then add the KV cache, which grows with concurrency × sequence length:

weights_GB   = params_B * bytes_per_param          # 70B FP16  = 70 * 2   = 140 GB
weights_GB   = params_B * 1  (FP8)                 # 70B FP8   = 70 GB
weights_GB   = params_B * 0.5 (INT4)               # 70B INT4  = 35 GB

# KV cache per token (bytes) ≈ 2 * n_layers * n_kv_heads * head_dim * kv_bytes
# For a 70B-class model this is roughly ~0.3–0.5 MB/token in FP16.
# 100 concurrent requests * 4k tokens * 0.4 MB ≈ 160 GB of KV cache.

So a 70B model in FP16 (140 GB weights) will not fit one 80 GB H100 — you need tensor parallelism across ≥2 GPUs, or FP8/INT4 quantization to drop weights to 70/35 GB. This is exactly why H200 (141 GB) and quantization matter for single-node serving.

TRAINING FOOTPRINT

Training is far heavier per parameter because you also store gradients and optimizer state. Mixed-precision Adam, rough accounting:

ItemBytes/param
FP16 weights2
FP16 gradients2
FP32 primary weights (Adam)4
FP32 momentum + variance (Adam)8
Total (excl. activations)~16

So a 7B model in full fine-tuning needs ~7 × 16 = 112 GB just for weights+grads+optimizer, before activations — already more than one 80 GB GPU. That is why full training uses sharding (ZeRO/FSDP splits optimizer state, gradients, and weights across GPUs) and why LoRA/QLoRA (train small adapters, freeze base weights, often quantized to 4-bit) collapse this to fit on a single GPU.

Best practice: quote memory as weights + KV/activations + framework overhead and leave ~10–15% HBM headroom. Fragmentation and CUDA context/workspace allocations routinely eat several GB; a plan that fills HBM to 100% runs out of memory (OOMs) in practice.

Common mistake: sizing a training job only by weight bytes and forgetting optimizer state (×8) and activations. People provision one 80 GB GPU for a 13B full fine-tune, then are surprised by the OOM. Weights alone are 26 GB; the full training state is ~200 GB+.

On a multi-node job, losing one spot node kills the whole collective unless the framework can reconfigure.

A small cost-tradeoff example

Assume list on-demand ~$4/GPU-hr for an H100-class GPU (illustrative — real rates vary by cloud, region, and negotiation; verify current pricing). A training run needs 8 GPUs for 200 hours = 1,600 GPU-hours.

On-demand:            1,600 GPU-hr * $4.00        = $6,400
Spot (70% off):       1,600 GPU-hr * $1.20        = $1,920
  + checkpoint overhead (~10% more wall-clock)    ≈ $2,110 effective
1-yr committed (40%): amortized $2.40/GPU-hr      = $3,840 (only wins if kept busy ~all year)

Reading it: for a one-off, checkpointed run, spot is ~3× cheaper than on-demand even after preemption overhead — the clear winner. A 1-year commitment is only cheaper than spot if you keep those 8 GPUs busy for most of the year; for a single 200-hour job it would be a large waste. Reserved/committed pricing wins for always-on baseline, not spiky one-shots.

Interview framing: match the purchasing model to how much of the time the workload actually runs (its duty cycle) and how well it tolerates interruption — not to a blanket "spot is cheapest" rule.

STREAMING TRAINING DATA

When a dataset is far larger than local disk (TBs–PBs), you do not copy it — you stream it from the object store during training. Store data as sharded, sequentially-readable archives (WebDataset .tar shards, MosaicML StreamingDataset, TFRecord, Parquet) and read shard-by-shard with prefetch + a local cache. This keeps GPUs fed without staging the whole set.

Anti-pattern: training directly on millions of tiny individual files in object storage. Per-object request latency and rate limits starve the GPUs (low utilization). Pack into large shards (hundreds of MB each) and read sequentially with a prefetching dataloader.

Best practice: checkpoint to a fast shared tier (parallel FS or local NVMe) then async-upload to the object store. Writing multi-hundred-GB checkpoints straight to object storage synchronously stalls all ranks — a hidden cause of low GPU utilization on large jobs.

Networking: VPC, intra-cluster bandwidth, egress

A VPC is your private virtual network — subnets (usually one per AZ), route tables, security groups (stateful firewalls). ML compute lives in private subnets; egress to the internet goes via a NAT gateway, and access to object storage should use a VPC endpoint (PrivateLink) to keep traffic on the cloud backbone and off metered internet egress.

INTRA-CLUSTER BANDWIDTH (the training bottleneck)

Distributed training is dominated by collective communication (all-reduce of gradients, all-gather of shards). Two tiers matter:

  • Intra-node GPU↔GPU: NVLink/NVSwitch — ~900 GB/s per GPU on H100/H200 (NVLink 4), ~1.8 TB/s on GB200 (NVLink 5). Roughly an order of magnitude faster than PCIe.
  • Inter-node: RDMA over InfiniBand (NDR ~400 Gb/s per port) or RoCE, often multiple NICs per node, with GPUDirect RDMA so NICs read/write GPU HBM without a host-memory bounce. This is why GPU instances advertise "3.2 Tbps" of aggregate network — that is 8× ~400 Gb/s NICs for collectives.

Parallelism strategy follows the fabric: keep the chattiest parallelism (tensor parallelism) inside a node on NVLink; use pipeline and data parallelism across nodes where the InfiniBand fabric carries less-frequent, larger messages.

EGRESS COST PITFALLS

  • Internet egress (data leaving the cloud) is metered, ~$0.05–0.09/GB — serving model weights or large results to external clients adds up fast.
  • Cross-region replication is charged per GB — copying a multi-TB dataset between regions is a real line item.
  • Cross-AZ traffic is typically charged (~$0.01/GB each direction) — a training job split across AZs pays this on every gradient sync.
  • Intra-AZ / same-placement-group traffic is generally free — another reason to co-locate a tightly-coupled cluster.

Common mistake: reading a training dataset from an S3 bucket over a NAT gateway instead of an S3 VPC (gateway) endpoint. You pay NAT data-processing charges on every byte of every epoch, and add a hop, for traffic that could have stayed free on the backbone.

Gotcha: egress bills are the classic "surprise" in ML infra — a chatty cross-AZ job or an externally-served model can quietly dwarf compute cost. Diagram the data flows and mark every boundary crossing before you deploy.

Interview Q&A

Q: You need to serve a 70B-parameter LLM with long (16k-token) context and high concurrency. Which GPU and configuration, and why?

A: 70B in FP16 is ~140 GB of weights, so it does not fit one 80 GB H100. Two clean options: (1) FP8/INT4 quantize to ~70/35 GB and serve on a single H200 (141 GB, 4.8 TB/s) whose large, fast HBM also absorbs the big KV cache that long context + high concurrency generate; or (2) keep FP16 and use tensor parallelism across 2+ H100s connected by NVLink so the collective stays on the fast intra-node fabric. Decode is memory-bandwidth-bound, so I would prioritize HBM bandwidth and KV-cache capacity, use paged attention (vLLM) to manage KV memory, and pick H200 to minimize GPU count and cross-GPU traffic.

Q: A distributed training job shows GPUs at 35% utilization. How do you diagnose it?

A: 35% util means GPUs are starved, so I walk the pipeline of bandwidths upstream. Check the dataloader/storage first — millions of tiny files or reads over NAT/cross-AZ starve input; fix with sharded WebDataset/StreamingDataset, prefetch, and a local NVMe cache. Then check comms: if the job is spread across AZs or the collective is spilling to PCIe/InfiniBand where it should be on NVLink, all-reduce stalls the step; fix with a cluster placement group, keeping tensor parallelism intra-node, and confirming GPUDirect RDMA/NCCL is using the InfiniBand fabric. Finally check synchronous checkpointing to object storage stalling all ranks. Profile (Nsight/PyTorch profiler) to see whether time is in data-wait, comms, or compute before changing anything.

Q: When is spot/preemptible the wrong choice despite being ~70% cheaper?

A: When the workload cannot tolerate interruption cheaply. Latency-sensitive production serving with an SLA should not run purely on spot — a reclaim causes user-facing errors. A tightly-coupled multi-node training job with no elastic recovery is risky too: losing one node kills the whole collective, and if checkpoints are infrequent you lose hours of work, erasing the savings. Spot fits checkpointed/elastic training, idempotent batch inference, and CI. For always-on baseline capacity, reserved/committed-use pricing is the right lever, not spot.

Q: How does the network fabric shape your choice of parallelism strategy?

A: You map the chattiest communication to the fastest link. Tensor parallelism syncs on every layer, so it belongs inside a node on NVLink (~900 GB/s on H100). Pipeline parallelism passes activations between stages less often, and data parallelism all-reduces gradients once per step — both tolerate the slower inter-node InfiniBand fabric (~400 Gb/s/port with GPUDirect RDMA). So a typical layout is TP within the 8-GPU node, then PP/DP across nodes. Getting this backwards — TP across nodes — pushes per-layer traffic onto the slow link and sharply cuts throughput.

Containers & Orchestration for ML

This module builds from the container image up to gang-scheduled distributed training. The through-line: a GPU is an expensive, non-interchangeable, non-overcommittable resource. Almost every design decision below — image size, scheduling, autoscaling, gang semantics — exists because you cannot treat a GPU like a slice of CPU. An idle H100 costs roughly the same as a fully-loaded one, so the orchestration layer's real job is keeping accelerators busy while giving jobs the topology they need.

Mental model: CPU/memory are compressible/overcommittable; GPUs are integer, exclusive, and topology-sensitive. Kubernetes was designed for the former. Everything ML-specific in this module (device plugins, MIG, gang scheduling, GPU-aware autoscaling) is bolted on to make K8s tolerate the latter.

1. Docker images for ML

An ML image is not a web-app image. It carries a CUDA userspace toolchain, cuDNN/NCCL, a deep-learning framework, and often multi-gigabyte model weights. Naive Dockerfiles routinely produce 10–20 GB images that take minutes to pull onto every new GPU node — directly slowing autoscaling and job startup.

THE CUDA / DRIVER SPLIT

The single most misunderstood point: the GPU driver lives on the host, not in the container. The container ships the CUDA runtime/userspace; the kernel driver is provided by the node (installed by the NVIDIA GPU Operator or a base AMI) and injected at runtime by the NVIDIA Container Toolkit. This is why you pick a CUDA base image by CUDA version, and why a container built for CUDA 12.4 needs a host driver new enough to support it (drivers are backward-compatible with older CUDA, not forward).

# Multi-stage build: compile/pull in a fat stage, ship a lean runtime.
# Base tags: nvidia/cuda:<cudaVer>-{base|runtime|devel}-ubuntu22.04
#   base    = driver-compat stubs only
#   runtime = + CUDA libs, cuDNN, NCCL   <- use this to RUN
#   devel   = + nvcc, headers            <- use this to BUILD

FROM nvidia/cuda:12.4.1-devel-ubuntu22.04 AS build
RUN pip install --no-cache-dir torch==2.4.0 --index-url https://download.pytorch.org/whl/cu124
COPY . /app
RUN python -m compileall /app

FROM nvidia/cuda:12.4.1-runtime-ubuntu22.04
# Pin an exact python + copy only what runtime needs from the build stage
COPY --from=build /usr/local/lib/python3.10 /usr/local/lib/python3.10
COPY --from=build /app /app
ENV NVIDIA_VISIBLE_DEVICES=all NVIDIA_DRIVER_CAPABILITIES=compute,utility
WORKDIR /app
ENTRYPOINT ["python", "serve.py"]

LAYER BLOAT & REPRODUCIBILITY

  • Order layers by change frequency. Put pip install of pinned deps before COPY . /app so a code change does not invalidate the multi-GB dependency layer.
  • Kill the pip cache: --no-cache-dir (or mount a BuildKit cache) — otherwise wheels are stored twice.
  • Pin everything: exact CUDA tag, exact framework version + CUDA build (cu124), and hash-pinned requirements. "Reproducible" means the same image digest given the same inputs — floating latest or pip install torch silently drifts across a fleet.
  • Keep weights out of the image in most cases. Bake weights in only for immutable, latency-critical serving; otherwise pull from object storage / a model registry at startup or mount a read-only volume, so the image stays reusable across model versions.

Best practice: Multi-stage devel→runtime + BuildKit cache mounts (RUN --mount=type=cache,target=/root/.cache/pip) typically cuts an ML image from ~15 GB to a few GB. On a scale-up event, that is the difference between a node being ready in ~30 s vs several minutes of image pull before your GPU does any work.

Gotcha: the runtime tag does not include nvcc. If your entrypoint JIT-compiles CUDA kernels (some custom ops, Triton, or torch.compile paths that shell out to a compiler) it will fail at run time with a missing-compiler error. Either use a base with the needed toolchain or precompile in the build stage.

3. Scheduling GPUs

NVIDIA DEVICE PLUGIN

GPUs are not a native K8s resource. The NVIDIA k8s-device-plugin (deployed as a DaemonSet, usually via the GPU Operator which also manages driver, container toolkit, and DCGM) discovers GPUs on each node and advertises them as an extended resource nvidia.com/gpu. You request whole integers of it. Crucially, GPUs support requests == limits only — you cannot overcommit or fractionally request the base resource; that is what makes fractioning (MIG/time-slicing) a separate mechanism.

apiVersion: v1
kind: Pod
metadata:
  name: train-llm
spec:
  restartPolicy: Never
  # Only schedule onto real GPU nodes, and tolerate their taint (see below)
  nodeSelector:
    nvidia.com/gpu.product: NVIDIA-H100-80GB-HBM3
  tolerations:
    - key: nvidia.com/gpu
      operator: Exists
      effect: NoSchedule
  affinity:
    podAntiAffinity:            # spread replicas across nodes
      preferredDuringSchedulingIgnoredDuringExecution:
        - weight: 100
          podAffinityTerm:
            labelSelector:
              matchLabels: { app: train-llm }
            topologyKey: kubernetes.io/hostname
  containers:
    - name: trainer
      image: myregistry/train:cu124
      command: ["torchrun", "--nproc_per_node=8", "train.py"]
      resources:
        limits:
          nvidia.com/gpu: 8         # 8 GPUs; requests are auto-set equal
        requests:
          cpu: "32"
          memory: 128Gi
      volumeMounts:
        - { name: shm, mountPath: /dev/shm }   # NCCL needs large /dev/shm
  volumes:
    - name: shm
      emptyDir: { medium: Memory, sizeLimit: 32Gi }

Two classic pod-spec bugs: (1) omitting the large /dev/shm mount — the default 64 MB starves NCCL/PyTorch DataLoader shared memory and you get cryptic hangs or "bus error"; (2) forgetting the toleration — GPU nodes are usually tainted (nvidia.com/gpu:NoSchedule) so that CPU-only pods don't occupy them, and your GPU pod will sit Pending forever without the matching toleration.

NODE SELECTORS / TAINTS / AFFINITY

  • Taints + tolerations = keep the wrong pods off expensive GPU nodes (repel by default). The GPU Operator can auto-taint.
  • nodeSelector / nodeAffinity = steer pods toward the right GPU SKU (nvidia.com/gpu.product, e.g. H100 vs L4) or a specific pool.
  • podAffinity/anti-affinity = co-locate or spread replicas; for multi-node training you often want pods on nodes sharing a high-bandwidth fabric.
  • Topology awareness: for tightly-coupled jobs, pack ranks onto GPUs with NVLink/NVSwitch within a node and nodes within one InfiniBand/EFA rack. K8s alone is topology-blind; the GPU Operator's GPU Feature Discovery labels nodes so affinity rules can express this.

MIG PARTITIONING vs TIME-SLICING

Both let more than one workload share a physical GPU, but they are opposites in isolation. MIG (Multi-Instance GPU), on A100/H100/H200/GB200, hardware-partitions one GPU into up to 7 instances with dedicated SMs, L2 slices, and framebuffer — hard memory and fault isolation. Time-slicing just lets the device plugin advertise N logical replicas of the same GPU and round-robins context; no memory isolation, no fault isolation — one process OOMing can take out its neighbors' allocations.

Anti-pattern: using time-slicing for production multi-tenant inference to "save money," then getting paged when tenant A's batch spike OOMs tenant B. Time-slicing shares one memory space with zero isolation — if tenants need guarantees, use MIG (or one GPU per tenant). Conversely, MIG-slicing a GPU for a single large-model training job wastes it: MIG instances cannot be recombined for one big allocation, and a MIG instance has no NVLink to its siblings.

Rule of thumb: MIG = partition for isolation & guarantees (right-size small inference workloads onto expensive GPUs). Time-slicing = oversubscribe for utilization when workloads are bursty and mutually trusting. They can even be combined (time-slice within a MIG instance) but that stacks their downsides.

4. Node pools & autoscaling

Node pools (EKS managed node groups / GKE node pools) group nodes of one instance type + config. ML clusters run several: a small CPU pool for control/ingest/CI, and separate GPU pools per SKU (H100 for training, L4/L40S for cheap inference) so scheduling and cost are cleanly separated. Autoscaling then operates at two levels.

WHY GPU NODES NEED SPECIAL HANDLING

  • Scale-up latency is brutal: a fresh GPU node = cloud provisioning + driver/toolkit install (GPU Operator) + multi-GB image pull, often 3–10 minutes before it runs a single kernel. Pre-pull images, use warm pools / over-provisioning (pause pods), and keep images small.
  • Scale-to-zero risk: GPUs are so costly that idle nodes must scale down aggressively — but a mid-training node scaled away loses work. Protect long jobs with cluster-autoscaler.kubernetes.io/safe-to-evict: "false" / PodDisruptionBudgets, and checkpoint.
  • Utilization > replica count: HPA on CPU will never fire for a GPU-bound server. Drive scaling off DCGM_FI_DEV_GPU_UTIL, batch queue depth, or p99 latency (KEDA scalers).
  • Capacity is real: H100 capacity is finite per region/AZ. Autoscalers hit InsufficientInstanceCapacity; design for multi-AZ/instance-family fallback and capacity reservations for critical training runs.

Best practice: Karpenter for GPU fleets — it right-sizes and consolidates instead of padding fixed node groups, and can express "H100 on-demand for training, L4 spot for batch inference" as provisioner constraints. Pair with a small over-provisioned buffer (low-priority pause pods) so real jobs preempt them instantly instead of waiting on cold GPU nodes.

5. Distributed jobs: gang scheduling (Volcano · Kubeflow · Ray)

Default kube-scheduler places pods one at a time. For a synchronous multi-node training job (all-reduce over N workers), that is a trap: it may schedule 6 of 8 workers, then block on GPU capacity for the last 2. The 6 sit idle holding GPUs while making no progress — and if two such jobs each grab half the cluster, both deadlock. This is why distributed training needs gang scheduling: all-or-nothing placement of a pod group.

Gotcha: gang scheduling prevents partial-placement deadlock but introduces starvation — a large gang can wait a long time for enough GPUs to free up simultaneously while small jobs keep slipping in. Use queues, priorities, and preemption (Volcano/Kueue) so a big training gang can preempt lower-priority work rather than starving, and set a placement timeout.

Interview framing: "Distributed training is a gang-scheduling problem, not a replica-count problem." Being able to explain why (synchronous all-reduce couples the workers; partial placement wastes GPUs and can deadlock) and how (PodGroup minMember, queues, preemption) is what separates operational exposure from platform-level understanding.

Interview Q&A

Q: Your GPU inference Deployment is pinned at 100% CPU by HPA but latency is still spiking. What's wrong and how do you fix it?

A: HPA is scaling on the wrong signal. A GPU-bound server can sit at low CPU while the GPU is saturated, so CPU-based HPA never reacts to real load. Export GPU metrics with DCGM (e.g. DCGM_FI_DEV_GPU_UTIL) and drive autoscaling off GPU utilization, inference queue depth, or p99 latency using custom metrics / KEDA. Separately, confirm Cluster Autoscaler/Karpenter can actually add GPU nodes fast enough — if not, pre-pull images and keep a warm buffer, because a cold GPU node can take minutes to become schedulable.

Q: When would you choose MIG over time-slicing, and what breaks if you get it wrong?

A: MIG when you need isolation and guarantees — multi-tenant inference with per-tenant memory and SLA, or right-sizing many small models onto an H100 without noisy-neighbor risk. Time-slicing when workloads are bursty, low-QPS, and mutually trusting (dev notebooks, batch), or on non-MIG GPUs like L4. Get it wrong by time-slicing multi-tenant prod: there's no memory or fault isolation, so one tenant's OOM or crash hits the others. Get it wrong the other way by MIG-slicing a GPU meant for one large training job: MIG instances can't be recombined and have no NVLink between siblings, so you've crippled the very job you wanted to run.

Q: Two 8-node training jobs are submitted to a cluster with 12 GPU nodes. Both make no progress. What happened?

A: Classic partial-placement deadlock from the default scheduler. Each job grabbed some nodes (say 6 each), neither can reach its required 8, and both hold GPUs idle waiting. Fix with gang scheduling — Volcano PodGroup with minMember: 8 (or Kueue admission) so a job is placed all-or-nothing and never partially occupies GPUs. Add priorities/preemption so one job can proceed while the other requeues, plus a placement timeout to avoid indefinite waiting.

Q: Your training pods start but hang during the first all-reduce, or crash with a shared-memory error. First thing you check?

A: The /dev/shm size. Kubernetes defaults it to 64 MB, which starves NCCL and the PyTorch DataLoader; mount an emptyDir with medium: Memory sized in the GB range. If that's fine, check that NCCL is actually using the fast fabric (NVLink intra-node, InfiniBand/EFA inter-node) rather than falling back to TCP — often a missing network config, wrong NCCL_SOCKET_IFNAME, or pods scheduled across nodes without the high-bandwidth interconnect due to missing topology-aware affinity.

Data & Feature Infrastructure

Models are only as good as the data path that feeds them. This module walks the ML data plane from storage layout up to the data loader that keeps a GPU busy: lake / lakehouse / warehouse, batch vs streaming ingestion, ETL/ELT for ML, data versioning & lineage, feature stores (online/offline and the train/serve-skew trap), labeling & data quality, and the throughput engineering that stops a ~$2-4/hr H100 from stalling on I/O.

One-line mental model: the data platform has two very different consumers with opposite requirements — training wants massive sequential throughput over cold history (GB/s, latency-insensitive), and serving wants a single feature vector in single-digit milliseconds. Almost every design decision below is about serving both from one source of truth without them diverging.

Storage architectures: lake vs warehouse vs lakehouse

The three terms describe where raw and curated data live and what engine reads it. They are not interchangeable, and a common probe is whether you know why the lakehouse exists.

The lakehouse is the dominant 2025 pattern for ML: keep everything as Parquet in S3 (cheap, open, readable by Spark/Ray/PyTorch), but layer an open table format — Apache Iceberg, Delta Lake, or Apache Hudi — that adds ACID transactions, schema evolution, and time travel through a versioned metadata log. You get warehouse guarantees on lake economics, and no vendor lock-in because the files stay open.

Why table formats matter for ML: a training run reading a plain S3 prefix can silently pick up half-written partitions during a concurrent ETL job — non-reproducible garbage. Iceberg/Delta give snapshot isolation: your reader pins a snapshot ID, so a backfill running in parallel never leaks partial data into your batch. That single property is why "just point Spark at the S3 prefix" is a red flag in a design interview.

MEDALLION LAYERING

A common convention (popularized by Databricks, but format-agnostic) organizes the lakehouse into three tiers: Bronze (raw, append-only, exactly as ingested), Silver (cleaned, deduplicated, conformed schema, joined), Gold (business/ML-ready aggregates and features). Training reads Silver/Gold; you can always rebuild Silver and Gold from Bronze, which is your disaster-recovery and reproducibility safety net.

Ingestion is how data lands in the lake. The choice is driven by freshness requirements, not by fashion.

Most real ML platforms run both. A pragmatic modern pattern is the Kappa-ish approach: ingest everything through a log (Kafka), land it in the lakehouse continuously via a streaming sink, and treat "batch" as bounded reads of the same tables — rather than maintaining two separate code paths (the old Lambda architecture, which is a maintenance and skew liability).

Exactly-once is a system property, not a checkbox. A Kafka consumer with enable.auto.commit=true gives at-most/at-least-once at best. True end-to-end exactly-once needs idempotent writes or a transactional sink (Flink's two-phase-commit sink, or Delta/Iceberg atomic commits keyed by a dedup column). If you claim "exactly-once" in an interview, be ready to explain where the idempotency actually lives.

ETL vs ELT for ML

ETL (Extract → Transform → Load) transforms before landing; ELT (Extract → Load → Transform) lands raw first and transforms inside the lakehouse/warehouse with its compute. ELT dominates today because storage is cheap and pushing transforms into Spark/dbt/BigQuery scales better and keeps raw data for reprocessing.

For ML specifically, the transform stage produces two artifacts with a hard constraint between them:

  • Training set — a large, point-in-time-correct snapshot for offline learning.
  • Feature transformations — the exact same logic must run online at serving time. If the transform lives only in a Spark job, you have already created train/serve skew (see below).

Point-in-time correctness is the whole game for training data. When you join a label observed at time T with features, you must use only feature values known before T — a "point-in-time join" (a.k.a. as-of join). Using the current feature value leaks the future into training and inflates offline metrics that then collapse in production. Feature stores exist largely to make this join correct by default.

Lineage answers "where did this column come from and what breaks if I change it." Feature stores

A feature store is the system that computes, stores, and serves features consistently to both training and inference. It has two physical stores backed by (ideally) one definition:

  • Offline store — columnar, high-throughput, holds full history. Used to build training sets with point-in-time joins. Backed by the lakehouse (Parquet/Delta/BigQuery).
  • Online store — low-latency key-value lookup of the latest feature value per entity. Used at serving time. Backed by Redis / DynamoDB / Cassandra / Bigtable.

Train/serve skew is the #1 silent killer of ML systems in production. It happens whenever the features a model trains on differ from the features it sees at inference. Common causes: (1) training features computed in Spark/SQL but serving features re-implemented in Python/Java by a different team — subtly different rounding, null handling, or time windows; (2) using the current feature value in training instead of the point-in-time value (label leakage); (3) online store staleness — training assumed a 7-day window refreshed nightly, but the online value is 3 days stale because a materialization job silently failed. The symptom: strong offline metrics, disappointing online metrics, and no crash to point at. The fix: one feature definition materialized to both stores, point-in-time joins for training, and monitoring that compares the online-served feature distribution against the offline/training distribution.

Detect skew, don't just hope: log a sample of the exact feature vectors served in production and periodically re-score them offline; alert on divergence between the logged serving distribution and the training distribution (PSI / KL divergence per feature). Also monitor materialization job success and online-store freshness as first-class SLOs — a silently-failed nightly job is the most common concrete cause.

Labeling & data quality

For supervised and fine-tuning workloads, label quality caps model quality. Practical labeling strategies engineers should know:

  • Human labeling — Label Studio, SageMaker Ground Truth, or vendor annotation. Measure inter-annotator agreement (Cohen's/Fleiss' kappa); low agreement means an ambiguous label schema, not lazy labelers.
  • Programmatic / weak supervision — labeling functions + a label model (Snorkel-style) to bootstrap large noisy label sets cheaply, then refine.
  • Active learning — label the examples the model is most uncertain about first; far more sample-efficient than random labeling.
  • LLM-as-labeler / distillation — use a strong model to pre-label or judge, with human spot-checks. Cost-effective but audit for the teacher model's biases.

Data quality must be enforced as tested contracts, not tribal knowledge. Tools like Great Expectations, dbt tests, and Soda assert schema, null rates, ranges, uniqueness, freshness, and referential integrity — and fail the pipeline before bad data reaches training.

# Great Expectations: fail the pipeline if data violates the contract
validator.expect_column_values_to_not_be_null("user_id")
validator.expect_column_values_to_be_between("amount", min_value=0, max_value=1e6)
validator.expect_column_values_to_be_unique("event_id")
validator.expect_column_proportion_of_unique_values_to_be_between(
    "user_id", min_value=0.0, max_value=0.5)      # catch accidental fan-out from a bad join
results = validator.validate()
if not results.success:
    raise ValueError("Data quality gate failed — blocking downstream training")

Anti-pattern: silent schema drift. An upstream team renames amt to amount or changes cents-to-dollars; the pipeline "succeeds," nulls or 100x-scaled values flow into features, and the model degrades over weeks. A data contract with range/null/uniqueness assertions turns a slow silent regression into a loud, immediate pipeline failure. Enforce it at the Bronze→Silver boundary.

Feeding the GPUs: throughput & avoiding data-loader starvation

The most expensive resource in the stack is the GPU. An H100 SXM does ~989 TFLOPS dense BF16 (~1979 with FP8, sparsity aside); at roughly $2–4/hr on-demand for a single H100 in 2025 (an 8-GPU node ~$20–32/hr), an idle GPU is pure waste. If nvidia-smi shows low GPU utilization / SM activity while the loss is still going down slowly, you are almost always input-bound: the data loader can't deliver batches fast enough and the GPU stalls between steps. This is data-loader starvation.

WHERE THE BOTTLENECK HIDES

  1. Storage bandwidth & latency — millions of tiny files on S3/NFS means per-object latency dominates. Fix: pack into large sharded files (WebDataset .tar, TFRecord, Parquet) of ~100 MB–1 GB each so reads are sequential and few.
  2. Decode/transform CPU — JPEG decode, resize, tokenization on too few CPU workers. Fix: more num_workers, or offload decode/augmentation to GPU (NVIDIA DALI).
  3. Host→device copy — synchronous H2D transfers serialize with compute. Fix: pin_memory=True + non_blocking=True so copies overlap the previous step.
  4. No overlap — loading happens after the step finishes instead of during it. Fix: prefetch_factor / a prefetch queue so batch N+1 is ready when step N ends.
# PyTorch DataLoader tuned to keep the GPU fed (overlap load + compute)
loader = DataLoader(
    dataset,
    batch_size=256,
    num_workers=8,             # ~= physical cores per GPU; too many -> RAM/oversubscription
    pin_memory=True,           # page-locked host buffers -> faster async H2D copy
    prefetch_factor=4,         # each worker preloads 4 batches ahead of the model
    persistent_workers=True,   # don't tear down workers every epoch
    drop_last=True,            # stable step shapes -> better kernel/CUDA-graph reuse
)
for x, y in loader:
    x = x.to("cuda", non_blocking=True)   # overlaps copy with prior step's compute
    y = y.to("cuda", non_blocking=True)
    ...  # forward / backward
# WebDataset: shard millions of small samples into large sequential tars.
# Sequential shard reads turn a latency-bound problem into a bandwidth-bound one.
import webdataset as wds
ds = (
    wds.WebDataset("s3://lake/imagenet/shards/train-{000000..001281}.tar",
                   shardshuffle=True, nodesplitter=wds.split_by_node)
    .shuffle(1000)             # buffer shuffle; full shuffle already lost at shard build
    .decode("torchrgb")
    .to_tuple("jpg", "cls")
)

Sharding math you should be able to sketch: a distributed run must split shards across nodes and workers so no two ranks read the same data and every rank gets a roughly equal slice. Rule of thumb: shards ≫ (world size × workers) — e.g. thousands of shards for a 64-GPU job — otherwise some ranks finish early and stall on a barrier at the epoch boundary. Shuffle at two levels: shuffle the list of shards each epoch, plus a bounded in-memory sample buffer; a true global shuffle of every sample is infeasible at scale, so you approximate it.

Diagnose before you optimize. Run the PyTorch Profiler or watch nvidia-smi dmon: if SM activity has periodic dips to near-zero between steps, you're input-bound — add workers/prefetch/GPU-decode. If SM stays pegged near 100%, you're compute-bound and the data path is fine; go optimize the model (mixed precision, fused kernels, larger batch, FlashAttention) instead. Ordering of effort should follow the measured bottleneck, not intuition.

Node-local NVMe caching gotcha: a popular fix is to stage the dataset onto each node's local NVMe on first epoch. Great for throughput, but on ephemeral cloud/spot nodes the cache is lost on preemption and the first epoch after a restart is slow and re-hammers S3 — budget for that, and make sure the cache key includes the dataset version so a data update doesn't silently serve stale cached shards.

Interview Q&A

Q: Your model has great offline metrics but underperforms in production. Walk me through how you'd debug it.

A: This is the classic train/serve-skew signature. First confirm it's skew and not distribution shift: log the exact feature vectors served in production and re-score them offline — if offline metrics on the served vectors are also poor, the features differ (skew); if they're good, the input distribution shifted. For skew, check the three usual causes: (1) divergent transform code between the training pipeline and the online serving path — the fix is one feature definition materialized to both stores rather than two implementations; (2) label leakage — training used current feature values instead of point-in-time-correct ones; (3) online-store staleness — a silently-failed materialization job serving stale values. I'd add per-feature distribution monitoring (PSI/KL) comparing serving vs training, and treat materialization success and online-store freshness as SLOs.

Q: Why does an online feature store exist separately from the offline store — why not query the lakehouse at serving time?

A: Different access patterns with incompatible latency budgets. Serving needs a point lookup by entity key returning in single-digit milliseconds at high QPS; a lakehouse (S3 + Parquet) is optimized for large sequential scans and would take hundreds of ms to seconds per query — orders of magnitude too slow, and it collapses under thousands of QPS. So you materialize the latest value per key into a low-latency KV store (Redis/DynamoDB). The offline store keeps full history for point-in-time-correct training joins. The hard requirement is that both are populated from a single feature definition so they don't drift.

Q: A training job on an 8×H100 node shows 30% GPU utilization. What's happening and how do you fix it?

A: Almost certainly input-bound — the data loader can't feed the GPUs, so they idle between steps. I'd confirm with the PyTorch Profiler / nvidia-smi dmon looking for periodic SM dips to zero. Then work the pipeline: pack tiny files into large sharded archives (WebDataset/TFRecord) for sequential reads; increase num_workers toward the core count; enable pin_memory + non_blocking H2D copies and prefetch_factor so loading overlaps compute; offload JPEG decode/augmentation to the GPU with DALI if CPU is the wall; and cache hot shards on node-local NVMe. Ensure shards ≫ world_size × workers so ranks don't stall at the epoch barrier. If after that SM sits near 100%, the data path is fine and I'd pivot to compute-side wins (mixed precision, larger batch, fused/FlashAttention kernels).

Q: Why choose a lakehouse over a plain data lake for an ML platform, and what specifically does the table format buy you?

A: A plain lake (raw Parquet on S3) has no transactions, so a training reader can pick up half-written partitions from a concurrent backfill — non-reproducible data. A table format like Iceberg or Delta adds a versioned metadata log giving ACID commits, snapshot isolation, and schema evolution on top of the same cheap open files. Concretely it buys me: reproducible reads (pin a snapshot/version ID so a run can be reconstructed months later), safe concurrent writes (backfills don't corrupt readers), schema enforcement/evolution without rewriting data, and time travel for lineage and rollback — all without giving up S3 economics or locking into a proprietary warehouse.

Model Training Infrastructure

Training a modern model is a distributed-systems problem wearing a linear-algebra costume. The math (a transformer forward/backward pass) is fixed; what an infra engineer controls is how that math is spread across GPUs, how they exchange gradients, and how the run survives days of hardware failures. This module walks the progression from one GPU to a multi-node cluster, the parallelism strategies that make trillion-parameter models fit, why the interconnect — not the GPU — usually caps your scaling efficiency, and the plumbing (checkpointing, schedulers, tracking) that keeps a two-week run alive.

The one-line mental model: you scale a training job by cutting it along one of three axes — the batch (data parallel), the tensor inside a layer (tensor parallel), or the stack of layers (pipeline parallel) — and each cut trades a different resource (memory vs. communication vs. bubble/idle time). Choosing the mix is the whole game.

The scaling progression: 1 GPU → multi-GPU → multi-node

Single GPU (the baseline)

One GPU holds the model, optimizer states, activations, and a micro-batch. This is the regime for models up to roughly a few billion parameters (with tricks). The moment the model + its training state exceeds device memory — an 80 GB H100 or 141 GB H200 — you must shard or offload. That threshold is where "just buy a bigger GPU" stops working and infra begins.

Multi-GPU, single node (scale-up)

A DGX/HGX H100 node has 8 GPUs connected by NVLink + NVSwitch, giving every GPU ~900 GB/s of all-to-all bandwidth to every other GPU in the box. On a per-GPU basis this intra-node fabric is ~10–18x faster than the inter-node network: each GPU gets ~900 GB/s of NVLink versus its share of the node's ~400 GB/s InfiniBand split across all 8 GPUs (≈50 GB/s per GPU). So the first rule of scaling is fill the node before you leave it. Data-parallel training with torch.distributed + NCCL "just works" here because gradient all-reduce rides NVLink.

Multi-node (scale-out)

Beyond 8 GPUs you cross the node boundary onto InfiniBand or RoCE (typically 8x400 Gb/s NDR per H100 node = 3.2 Tb/s aggregate). Now placement, topology, and collective algorithms matter enormously. A job that hit 95% scaling efficiency inside a node can drop to 60–70% across poorly-connected nodes purely from communication stalls.

Best practice: Always saturate NVLink first. An 8-GPU tensor-parallel group should live inside one node; data-parallel replicas (which all-reduce less frequently) are the axis you stretch across the slow inter-node network.

Common mistake: Assuming 2x GPUs = 2x throughput. Without attention to interconnect and parallelism layout, doubling GPUs across nodes can yield 1.3–1.5x. Interviewers probe exactly this: "you added a second node and got almost no speedup — why?" The answer is almost always communication bound, not compute bound.

Parallelism strategies

These are composable. Real large-model training uses "3D parallelism" = data × tensor × pipeline, sometimes with sharding layered on. Understand each axis independently first.

DATA PARALLELISM (DP)

Every GPU holds a full copy of the model and processes a different slice of the batch. After the backward pass, gradients are averaged across all replicas with an all-reduce. Simplest and most scalable — but only works if one model copy fits in one GPU. Memory does not shrink; you replicate it N times.

TENSOR PARALLELISM (TP) — intra-layer

A single large matmul (e.g. an attention or MLP weight matrix) is split column-wise / row-wise across GPUs; each GPU computes a shard and they combine with an all-gather / all-reduce every layer. This shrinks per-GPU memory for the weights but is extremely communication-heavy — a collective on every forward and backward layer. Because of that chatter, TP must stay inside one NVLink domain (≤8 GPUs); crossing InfiniBand with TP sharply reduces efficiency.

PIPELINE PARALLELISM (PP) — inter-layer

The layer stack is chopped into stages placed on different GPUs; micro-batches flow through like an assembly line. Communication is cheap (only activations at stage boundaries, point-to-point) so PP tolerates the inter-node network well. Its cost is the pipeline bubble — idle time while the pipe fills and drains. Bubble fraction ≈ (stages − 1) / (micro-batches + stages − 1), so you hide it by using many micro-batches per stage (interleaved / 1F1B schedules in Megatron-LM reduce it further).

SHARDED DATA PARALLEL — FSDP / ZeRO

The clever middle ground. Pure DP wastes memory by replicating optimizer states, gradients, and parameters N times. ZeRO (DeepSpeed) and FSDP (PyTorch native) shard those across the DP group and reconstruct each layer's parameters on demand via all-gather just before use, then free them. You keep DP's programming simplicity but cut memory dramatically. ZeRO has three stages:

  • ZeRO-1: shard optimizer states (fp32 primary copy + Adam m, v) across data-parallel ranks — since optimizer state is ~12 of the 16 bytes/param, this alone cuts total per-device memory ~4x, with negligible extra comms. (ZeRO-2 also shards gradients, ~8x; ZeRO-3 shards parameters too, scaling ~linearly with the number of devices.)
  • ZeRO-2: also shard gradients. More savings, still cheap.
  • ZeRO-3 / FSDP full-shard: also shard parameters. Maximum memory savings, but adds all-gather of weights each layer — more communication, so it wants fast interconnect.

When each is needed: DP when the model fits and you just want throughput. FSDP/ZeRO when the training state (not just weights) blows past device memory but a single layer still fits. TP when a single layer's weights are too big for one GPU or you need to cut activation memory. PP when the whole model is too tall for even a sharded node and you have many nodes on a slower fabric. Big runs combine all four.

Memory estimation: worked example

A common question is "will this model fit, and on how many GPUs?" The dominant terms in mixed-precision (bf16) training with the Adam optimizer are well known. Per parameter you carry, roughly:

  • 2 bytes — bf16 parameter
  • 2 bytes — bf16 gradient
  • 4 + 4 + 4 = 12 bytes — fp32 optimizer state (primary weight copy + Adam m + Adam v)

That's ~16 bytes per parameter for model + optimizer state, before activations. This "16x rule" is the number to have memorized.

WORKED CASE: A 70B-PARAMETER MODEL

Model + optimizer state = 70e9 params x 16 bytes
                        = 1,120 GB  (~1.12 TB)

  1120 GB / 80 GB  =  14 GPUs just to HOLD the state

Reality: activations + NCCL buffers + fragmentation
need ~30-40% headroom, so plan ~24-32 GPUs
(3-4 H100 nodes) for a comfortable 70B training run.

Now compare parallelism choices for that 70B model:

  • Pure DP: impossible — one replica needs 1.12 TB, far past 80 GB. Non-starter.
  • FSDP / ZeRO-3 across 32 GPUs: 1120 GB / 32 ≈ 35 GB per GPU for state, leaving ~45 GB for activations and buffers. This fits and is the most common approach for models in the tens of billions.
  • 3D (TP=8, PP=4, DP=1): what Megatron-LM uses at 100B+ scale; TP cuts per-layer weight/activation memory inside the node, PP cuts the layer count per GPU.

ACTIVATIONS — THE TERM PEOPLE FORGET

Activation memory scales with batch × sequence length × hidden size × layers and can rival or exceed the parameter memory at long context. Two levers control it: activation (gradient) checkpointing — recompute activations in the backward pass instead of storing them, trading ~30% extra compute for a large memory cut — and reducing micro-batch size. On a 70B model at 8k context, activation checkpointing is effectively mandatory.

Estimation shortcut to say out loud: "16 bytes/param for state, plus activations which I'll bound with gradient checkpointing, plus ~30% headroom for NCCL buffers and fragmentation." That framing signals you've actually sized a real run, not just recited a formula.

Collective communication & interconnect

Every parallelism strategy above is really a pattern of collective operations executed by NCCL (NVIDIA Collective Communications Library) on GPUs. The two that matter most:

  • all-reduce — every rank contributes a tensor, every rank receives the sum. This is the gradient-averaging step of data parallelism. NCCL implements it as ring or tree all-reduce; ring bandwidth is roughly independent of GPU count (it's latency that grows), which is why DP scales well.
  • all-gather / reduce-scatter — the building blocks of FSDP/ZeRO (gather sharded params before a layer, scatter gradients after). An all-reduce is literally a reduce-scatter followed by an all-gather.

Why interconnect dominates scaling efficiency

Training alternates compute (matmuls on tensor cores) with communication (collectives). If communication can't overlap with or keep up with compute, GPUs sit idle — you paid for an H100 and it waits on the wire. The bandwidth hierarchy is stark:

Checkpointing & fault tolerance

A 1,000-GPU run over two weeks will hit hardware failures — a GPU falling off the bus, an ECC error, a NIC flap. At scale, MTBF (mean time between failures) is measured in hours, not days. Without checkpointing, one failed GPU throws away the entire cluster's progress since the last save. Fault tolerance is not optional infrastructure; it's what makes long runs economically possible.

WHAT TO CHECKPOINT

Model weights, optimizer state, LR-scheduler state, RNG state, and the data-loader position (so you resume on the right batch, not from epoch zero). Miss any and you get silent divergence on resume.

THE COST PROBLEM

Our 70B model's state is ~1.12 TB. Writing that to storage naively stalls all GPUs. Techniques that make it tractable:

  • Distributed / sharded checkpoints: each rank writes only its shard in parallel (PyTorch Distributed Checkpoint / torch.distributed.checkpoint, DeepSpeed universal checkpoints). Turns one 1.12 TB serial write into N parallel writes.
  • Asynchronous checkpointing: copy state to pinned host RAM (fast), then flush to persistent storage in the background while training continues. Cuts the GPU stall from minutes to seconds.
  • Checkpoint interval tuning: frequent enough that lost work < checkpoint cost, but not so frequent you spend the run doing I/O. The Young/Daly formula gives the optimal interval ≈ sqrt(2 × checkpoint_cost × MTBF).

Best practice: Store checkpoints on a parallel filesystem (Lustre / GPFS / FSx for Lustre) or high-throughput object storage, keep the last k plus periodic milestones, and verify a checkpoint actually restores (load + one forward pass) before deleting the previous one. A corrupt checkpoint you discover at failure time is as bad as no checkpoint.

Common mistake: Saving only model weights, not optimizer state. Adam's momentum/variance are part of the trajectory; resuming without them spikes the loss and can permanently dent final quality. Always checkpoint the full training state.

For elastic resilience, torchrun / TorchElastic can restart from the last checkpoint with a possibly different world size, and schedulers can hot-swap a healthy node in. The goal: a single node failure costs one checkpoint interval, not the run.

Experiment tracking

Long, expensive runs demand reproducibility and observability. Tracking answers "which config produced this checkpoint, and is the run healthy right now?" Tools: MLflow (open-source, self-hostable, model registry), Weights & Biases (rich live dashboards, sweeps), TensorBoard (lightweight scalar/graph viewer), and vendor stacks (SageMaker Experiments, Vertex).

WHAT TO LOG

  • Config & provenance: full hyperparameters, git commit, container image digest, dataset version/hash, parallelism layout, and world size — enough to re-launch the exact run.
  • Live metrics: train/val loss, learning rate, grad norm (a spike or NaN is your early divergence alarm), tokens/sec throughput, and GPU utilization & memory. Low GPU util on an idle-looking run almost always means you're communication- or data-loader-bound.
  • System health: per-step time (watch for stragglers), NCCL timeouts, checkpoint success.

Best practice: Log MFU (Model FLOPs Utilization) — achieved FLOPs ÷ the GPU's peak. Well-tuned large-model training lands around 40–50% MFU on H100s; if you're at 20%, half the GPUs you are paying for are doing no useful work, and you should profile communication overlap and data loading before scaling up. Quoting MFU signals you measure efficiency, not just "it's running."

Interview Q&A

Q: You're training a 70B model. Walk me through how you'd lay it out on a 4-node, 32x H100 cluster.

A: First the fit check: 70B × 16 bytes ≈ 1.12 TB of model+optimizer state, so no single GPU or even single node (640 GB) holds it — I must shard. Two viable layouts. (1) FSDP/ZeRO-3 across all 32 GPUs: ~35 GB state per GPU, leaving room for activations with gradient checkpointing — simplest, and my default at this scale. (2) 3D parallelism if I need more headroom or hit comms limits: TP=8 within each node so the heavy per-layer collectives ride NVLink, PP across the 4 nodes (cheap point-to-point activations tolerate InfiniBand), and DP on top if replicas remain. I'd enable activation checkpointing regardless, verify NCCL reports NVLink for the TP groups, and target 40%+ MFU before declaring the layout good.

Q: Why does tensor parallelism have to stay inside a node while pipeline parallelism can cross nodes?

A: It's about communication frequency and volume. TP splits the matmul inside every layer, so it fires an all-gather/all-reduce on every forward and backward layer — enormous, latency-sensitive traffic. That only survives on NVLink's ~900 GB/s intra-node fabric; routing it over InfiniBand (roughly half the bandwidth, higher latency) stalls the GPUs and can halve throughput. PP only sends activations at stage boundaries via point-to-point transfers — far less data, far less often — so it tolerates the slower inter-node network. Hence the doctrine: TP within the NVLink domain, PP/DP across nodes.

Q: You added a second node and throughput barely improved. How do you diagnose it?

A: Almost certainly communication-bound at the node boundary, not compute-bound. My checklist: (1) run nccl-tests all_reduce_perf and check busbw approaches IB line rate, not PCIe speeds — if it's PCIe-level, GPUDirect RDMA isn't active or IB is disabled. (2) NCCL_DEBUG=INFO to confirm the fabric each group uses; a TP group accidentally spanning nodes is a classic culprit. (3) Check rank placement — my fast-collective groups must be co-located on a node. (4) Look at MFU and per-step time for stragglers. (5) Confirm overlap of gradient comms with backward compute is happening. The headline: doubling GPUs across a slow or misconfigured interconnect commonly yields ~1.3x, not 2x, and the fix is topology/placement, not more hardware.

Q: How do you keep a two-week, 1000-GPU run from losing everything to a single GPU failure?

A: At that scale MTBF is hours, so I design for frequent failure. Sharded, asynchronous checkpointing of the full training state — weights, optimizer momentum/variance, LR scheduler, RNG, and data-loader position — each rank writing its shard in parallel to a parallel filesystem, staged through pinned host RAM so the GPU stall is seconds not minutes. Checkpoint interval set near the Young/Daly optimum (~sqrt(2 × checkpoint_cost × MTBF)). I verify each checkpoint restores before deleting the prior one, and use TorchElastic/torchrun so the scheduler can swap in a healthy node and resume from the last checkpoint. Result: a failure costs one interval of work, not the whole run — and I never checkpoint weights without optimizer state, since resuming without Adam's moments spikes the loss.

Model Serving & Inference Optimization

Training is a batch job you run once; serving is a system you run forever. Its economics and SLAs dominate the lifetime cost of most production models. This module walks from the basic serving shapes up to the techniques that make LLM inference affordable at scale: continuous batching, paged KV-cache, quantization, and speculative decoding. Throughout, we treat a GPU as an expensive, fixed-throughput resource and ask the only two questions that matter: how fast does one request feel (latency) and how many requests can one GPU absorb (throughput).

The core tension in one sentence: a GPU is a throughput machine, but a user experiences latency. Almost every serving technique below is a way to recover throughput without wrecking the latency a single user feels — or vice versa. If you can articulate that tradeoff crisply, you have the spine of an inference-optimization interview.

Dynamic and continuous batching

A GPU is most efficient when it does one big matmul instead of many small ones, so we batch requests. There are two generations of this idea, and the difference is the single biggest throughput lever for LLMs.

DYNAMIC (SERVER-SIDE) BATCHING

The classic approach (Triton's dynamic_batching): hold incoming requests for a short window (e.g. a few ms), assemble them into one batch, run the batch to completion, return all results together. Great for fixed-shape models (classifiers, embeddings). For generation it's wasteful: the batch can't return until the slowest sequence finishes, so a 500-token reply blocks a 10-token reply.

CONTINUOUS (IN-FLIGHT / ITERATION-LEVEL) BATCHING

The LLM-native approach (vLLM, TGI, TensorRT-LLM). The scheduler works at the granularity of a single decode step. After every token, finished sequences leave the batch and waiting requests join immediately — no waiting for the whole batch to drain. This keeps the GPU busy on the mix of prefill and decode work that is always in flight.

Why it wins: autoregressive decode is memory-bandwidth bound and processes one token per sequence per step, so a single request leaves most of the GPU's compute idle. Continuous batching packs many sequences' decode steps together, routinely delivering 5-20x the throughput of prior static/dynamic batching at the same model and hardware (and far more versus literal one-request-at-a-time serving, as the cost example below shows), with far better tail latency. This is the headline result behind the vLLM/Orca line of work.

Gotcha — prefill vs decode interference: a newly arrived request must run a compute-heavy prefill over its whole prompt, which can stall the cheap decode steps of requests already streaming, causing inter-token latency spikes. Mitigations: chunked prefill (split a long prompt's prefill across several iterations so decode still progresses) and prefill/decode prioritization. Enable chunked prefill when you have long prompts sharing a server with latency-sensitive streaming.

KV-cache and PagedAttention

During generation, attention needs the keys and values of every previous token. Recomputing them each step would be quadratic, so we cache them: the KV-cache. It is the dominant consumer of GPU memory during serving and the thing that limits how many concurrent requests (how large a batch) a GPU can hold.

SIZING THE KV-CACHE

Per token, the cache stores K and V for every layer and every KV head:

kv_bytes_per_token = 2 (K and V)
                   × num_layers
                   × num_kv_heads × head_dim
                   × dtype_bytes        # 2 for fp16/bf16

# Llama-3.1-8B: 32 layers, GQA with 8 KV heads, head_dim 128, bf16
# = 2 × 32 × 8 × 128 × 2  ≈ 131 KB per token
# A 4096-token context ≈ 0.5 GB of KV-cache for ONE sequence.

On an 80GB H100 hosting an 8B model (~16GB weights in bf16), ~55-60GB is left for KV-cache — enough for tens of long-context sequences concurrently. Note Grouped-Query Attention (GQA): sharing KV heads across query heads (8 KV heads here instead of 32) cuts KV-cache roughly 4x, which is why modern models can serve long contexts at high concurrency.

PAGEDATTENTION — WHY IT MATTERS

Classic serving pre-allocated one contiguous KV buffer per request sized to max_len. Two failures result: internal fragmentation (a request that stops at 200 tokens still reserves space for 4096) and external fragmentation (free memory exists but not contiguously). Utilization was often only ~20-40%. PagedAttention (vLLM) borrows OS virtual-memory paging: the KV-cache is split into fixed-size blocks (e.g. 16 tokens) allocated on demand via a block table, so memory is used only as sequences grow.

Two big wins beyond memory efficiency: (1) near-zero waste means you fit far larger effective batches → higher throughput; (2) blocks are shareable — prefix caching lets many requests with a common system prompt or few-shot preamble reuse the same KV blocks (copy-on-write), and parallel samples from one prompt share the prompt's blocks. Turn on prefix caching whenever prompts share long fixed prefixes (RAG templates, agent system prompts) — it cuts prefill cost and TTFT dramatically.

Quantization: int8 / fp8, AWQ, GPTQ

Quantization stores (and sometimes computes) weights and/or activations in fewer bits. It attacks the two things that hurt LLM serving: weight memory (smaller weights → more room for KV-cache and bigger batches, or fitting a model on fewer/smaller GPUs) and, when activations are also quantized, compute/bandwidth via low-precision tensor cores.

At high batch/throughput regimes the matmul is compute-bound and W4 must dequantize back to fp16 to compute, so its speedup fades — there, fp8 (which computes in low precision) is the throughput winner.

Accuracy/latency tradeoff — measure it, don't assume it: perplexity barely moving does NOT guarantee your task is fine. 4-bit quantization can quietly degrade multi-step reasoning, code generation, long-context recall, and tool-call formatting. Always evaluate the quantized model on your task metrics, not just a generic benchmark, before shipping.

Anti-pattern: stacking aggressive 4-bit weight quantization and heavy KV-cache quantization and speculative decoding, then blaming the base model when quality drops sharply. Change one variable at a time and keep an eval harness in the loop.

Speculative decoding

Decode is sequential and memory-bound: one token per forward pass, most of the GPU idle. Speculative decoding breaks the one-token-per-step limit. A cheap draft proposes several tokens ahead; the expensive target model verifies them all in a single forward pass and accepts the longest correct prefix. Because verification is one batched pass, you get multiple tokens for roughly the cost of one — and the output distribution is provably identical to the target model's (it's exact, not approximate).

  • Draft model: a small model of the same family (e.g. Llama-3.2-1B drafting for a 70B target).
  • Self-speculation (Medusa / EAGLE / n-gram): extra lightweight heads or prompt-lookup instead of a separate model — avoids hosting a second model.

When it pays off: speculative decoding shines at low batch sizes / latency-sensitive single-stream serving, where the GPU is underutilized and you have spare compute to "spend" on verification — expect roughly 1.5-3x lower inter-token latency depending on acceptance rate and how predictable the text is (code and structured output accept well).

Gotcha: at high batch sizes the GPU is already compute-saturated by continuous batching, so the extra verification/draft compute competes with real work and speculative decoding can reduce aggregate throughput. Acceptance rate also collapses on creative/open-ended text. Treat it as a latency optimization for low-concurrency paths, not a universal throughput win.

Latency vs throughput: the tradeoff you must be able to draw

LLM latency is two distinct numbers, and users feel them differently:

  • TTFT (Time To First Token) — dominated by prefill (processing the whole prompt) plus queueing. Grows with prompt length and load. This is the "spinner" the user stares at.
  • ITL / TPOT (Inter-Token Latency / Time Per Output Token) — the decode speed once streaming starts. Determines perceived "typing speed." 1 / ITL = tokens/sec per stream.
  • End-to-end ≈ TTFT + (output_tokens × ITL).

The fundamental knob is batch size. Bigger batches amortize weight loading over more sequences → higher aggregate throughput (tokens/sec across all users) and better $ per token — but each individual sequence's ITL rises and queueing lengthens TTFT. Small batches give snappy per-user latency but leave the GPU idle and cost more per token.

The curve to describe in an interview: plot throughput (x) vs per-request latency (y). As you increase concurrency/batch, throughput climbs while latency stays roughly flat — until you hit the knee where the GPU saturates (compute-bound or KV-cache-full), after which latency shoots up for little extra throughput. You size your deployment to run just below the knee, at the max batch that still meets your p99 latency SLO. Serving is a constrained optimization: maximize throughput subject to a tail-latency SLA.

Best practice: if TTFT and ITL SLOs conflict badly (e.g. long-prompt RAG that must also stream fast for chat), split traffic: a low-latency pool with small batches + chunked prefill for interactive chat, and a high-throughput pool with big batches for bulk/async work. One knob can't satisfy both classes on one deployment.

Autoscaling GPU inference & cold-start

GPUs are scarce and expensive, so you can't just over-provision like stateless web servers. But scaling them is hard because cold start is brutal: node provisioning (GPU nodes are slow to come up and often supply-constrained), pulling a multi-GB container + model weights, loading weights into VRAM, and CUDA graph / engine warmup. This can run from tens of seconds to several minutes.

SCALING SIGNAL

CPU/GPU-utilization is a poor autoscaling signal for LLMs (a saturated GPU may still be within SLO, or an idle-looking one may be KV-cache-full). Scale on work-in-flight signals: requests/tokens queued, batch occupancy, KV-cache utilization, or time-in-queue. On Kubernetes this means custom metrics (KEDA / Prometheus adapter driving an HPA), not raw DCGM GPU utilization alone.

# KEDA ScaledObject: scale a vLLM deployment on queue depth from Prometheus
apiVersion: keda.sh/v1alpha1
kind: ScaledObject
metadata:
  name: vllm-llama8b
spec:

    - type: prometheus
      metadata:
        serverAddress: http://prometheus.monitoring:9090

Cold-start mitigations (stack them): keep a warm minimum replica (minReplicaCount >= 1); pre-pull/cache images on nodes and bake weights into the image or a fast RWX volume; use node pre-provisioning / overprovisioning (a "pause pod" placeholder that reserves a spare GPU node so real pods schedule instantly); scale to zero only for spiky, latency-tolerant workloads. For fractional/multi-tenant serving of small models, MIG (Multi-Instance GPU) or time-slicing packs several models on one A100/H100 and reduces the need to spin up whole nodes.

Common mistake: scale-to-zero on a user-facing endpoint. The first request after idle eats the full multi-minute cold start and blows your TTFT SLO — and under a traffic spike every new replica pays that penalty simultaneously. Scale-to-zero belongs on dev/internal/batch endpoints; keep a warm floor for production interactive traffic.

Cost per token / cost per request

The cleanest way to reason about serving cost: divide GPU dollars-per-hour by tokens-per-hour. Everything above (batching, quantization, paged KV) is ultimately a lever on the denominator.

cost_per_1M_tokens = (gpu_$_per_hour / throughput_tokens_per_sec) × 1e6 / 3600

# Worked example (order-of-magnitude, assumptions stated):
#   1× H100 on-demand ≈ $2-4 / GPU-hr (cloud, 2025; reserved is much lower)
#   Llama-3.1-8B, fp8, continuous batching, high load ≈ 8,000 output tok/s
#   → ($4 / 8000) × 1e6 / 3600 ≈ $0.14 per 1M output tokens
#
# Same GPU, ONE request at a time (no batching) ≈ 120 tok/s
#   → ($4 / 120) × 1e6 / 3600 ≈ $9.3 per 1M output tokens  (~65x worse)

Takeaway: the difference between a well-batched server and a naive one is one to two orders of magnitude in $ per token — not a rounding error. Utilization is the whole game. Note also that output tokens cost far more than input tokens: input is parallel prefill (cheap per token), output is sequential decode (expensive per token). That is exactly why commercial APIs price output tokens several times higher than input.

ESTIMATING COST PER REQUEST

cost_per_request ≈ (input_tokens × input_$/tok) + (output_tokens × output_$/tok). To turn a fixed GPU fleet into a per-request number, compute the fleet's sustained tokens/sec at your target batch (below the latency knee), derive $ per token as above, then multiply by the average tokens per request. Add a utilization discount for the fact that real traffic is bursty and you provision for peak — a fleet running at 40% average utilization costs 2.5x its theoretical per-token floor.

Levers to quote when asked "how would you cut serving cost?": (1) raise utilization via continuous batching + right-sized batch; (2) fp8/int8 to fit bigger batches and use low-precision tensor cores; (3) prefix caching to skip repeated prefill (huge for RAG/agents with long shared prompts); (4) route easy requests to a smaller model (model cascades); (5) reserved/committed or spot capacity for the steady/batch base load; (6) MIG to pack small models. Order them by effort vs payoff for the specific workload.

Interview-style Q&A

Q: Continuous batching gives huge throughput. Why not just crank the batch size as high as memory allows?

A: Two limits bite before memory does. First, latency: larger batches raise per-sequence inter-token latency and lengthen queueing, so beyond the throughput "knee" you blow your p99 SLO for negligible extra throughput — you size to the max batch that still meets the tail-latency target. Second, the KV-cache, not the weights, is usually the real ceiling: each concurrent long-context sequence can consume hundreds of MB to gigabytes, so the server preempts/queues requests once the paged cache fills. The right answer is to find the knee empirically under representative load, not to maximize batch size blindly.

Q: A team reports p99 TTFT is fine but users complain generation "feels laggy." What do you investigate?

A: TTFT and inter-token latency (ITL) are different metrics; "laggy while typing" points at ITL, not TTFT. Likely causes: batch size pushed too high for throughput (each stream now decodes slowly); prefill of newly arrived long prompts stalling in-flight decode (fix with chunked prefill and prefill/decode prioritization); KV-cache pressure forcing preemption/recompute; or a memory-bound decode that speculative decoding could accelerate on this low-to-mid concurrency path. I'd chart ITL distribution vs concurrency, check for prefill interference, and consider splitting interactive traffic onto a small-batch, chunked-prefill pool.

Q: When would you choose AWQ 4-bit over fp8, and when the reverse?

A: Choose AWQ/GPTQ (weight-only 4-bit) when you're memory-constrained and latency-sensitive at low batch — e.g. fitting a 70B on fewer GPUs, or single-stream decode where bandwidth (loading weights) dominates; the 4-bit weights load faster and quality stays high with activation-aware scaling. Choose fp8 when you're on Hopper/Blackwell and throughput-bound at high batch: fp8 computes in low precision on native tensor cores, whereas weight-only 4-bit must dequantize to fp16 to matmul and loses its edge once compute-bound. And regardless of scheme, gate the choice on a task-specific eval — perplexity parity doesn't guarantee reasoning/code/tool-call quality survived.

Q: How do you autoscale GPU inference, and why is it harder than autoscaling a stateless web service?

A: Two structural differences. First, the scaling signal: GPU utilization is misleading for LLMs, so I scale on work-in-flight — requests/tokens queued, batch occupancy, or KV-cache utilization via KEDA/Prometheus feeding an HPA. Second, cold start: bringing up a GPU node plus pulling a multi-GB image, loading weights, and warming CUDA graphs can take minutes, and GPU capacity is supply-constrained, so reactive scaling is too slow for spikes. I mitigate with a warm replica floor, image/weight pre-caching, node overprovisioning (placeholder pods reserving spare GPU nodes), and MIG/time-slicing to pack small models — reserving scale-to-zero for latency-tolerant or internal workloads only.

MLOps & CI/CD

MLOps is the discipline of shipping models the way SRE/DevOps ships services: versioned, reproducible, tested, gated, observable, and rollback-able. The hard part is that a model is not just code — it is code + data + config + weights + environment. Any one of those changing can silently change behavior, so an ML release system must version and validate all five, not just the git SHA.

Mental model: app CI/CD asks "does this build pass tests and deploy healthy?" ML CI/CD adds two questions app CI/CD never asks: "is this model good enough on data it has never seen?" (offline eval gate) and "is it still good enough next week?" (drift/decay monitoring). Everything below hangs off those two questions.

Model registry & versioning

A model registry is the source of truth that maps a promotable, immutable model version to everything needed to reproduce and audit it. Common implementations: MLflow Model Registry, SageMaker Model Registry (model package groups), Vertex AI Model Registry, or a plain OCI/artifact store plus metadata DB. A registry entry should pin, at minimum:

  • Weights artifact — content-addressed (SHA-256), stored in S3/GCS/OCI, never mutated in place.
  • Training data snapshot — a dataset version/hash (e.g. a DVC pointer, Delta/Iceberg table version, or an immutable S3 prefix), not "the prod table as of whenever training ran".
  • Code + config — git commit SHA of the training pipeline plus resolved hyperparameters.
  • Environment — container image digest (framework, CUDA, driver expectations), so the same weights load the same way.
  • Lineage & metrics — the eval run that produced its offline scorecard, linked so a reviewer can see why it was promoted.
  • Stage — a lifecycle label (None → Staging → Production → Archived) that deployment automation reads.

SEMANTIC VERSIONING FOR MODELS

Reuse SemVer-style intent, but with ML meaning: MAJOR = breaking I/O contract (new features, changed schema, new label space); MINOR = retrain on new data / architecture change, same contract; PATCH = same data + code, re-run for a bugfix or recompiled artifact. Consumers pin a compatible MAJOR and let MINOR/PATCH flow through the gates.

import mlflow
from mlflow.tracking import MlflowClient

# Register the artifact produced by a training run (immutable, content-addressed).
result = mlflow.register_model(
    model_uri=f"runs:/{run_id}/model",   # run_id ties back to metrics + params
    name="fraud-scorer",
)
client = MlflowClient()
client.set_model_version_tag(
    name="fraud-scorer", version=result.version,
    key="dataset_hash", value="sha256:9f2c...e1")   # pin the data snapshot
client.set_registered_model_alias(                    # aliases > deprecated stages
    name="fraud-scorer", alias="champion", version=result.version)

Best practice: deploy by alias (champion, challenger), not by hardcoded version number. Promotion becomes a single atomic alias move, rollback is moving the alias back, and serving config never changes. MLflow deprecated stage transitions in favor of aliases + tags for exactly this reason.

Anti-pattern: versioning the code but pointing training at a live, mutable table ("SELECT * FROM events"). Two runs of the "same" pipeline then produce different models and you cannot reproduce or bisect a regression. Snapshot the data and record its hash, or the registry entry is a lie.

Reproducible ML pipelines

A pipeline turns "a notebook someone ran on their laptop" into a DAG of containerized, cached, parameterized steps: ingest → validate → transform → train → evaluate → register. Reproducibility comes from three properties: each step runs in a pinned container, consumes versioned inputs, and emits versioned, cached outputs keyed by input hash so unchanged steps are skipped on re-run.

CI/CD for models — and how it differs from app CI/CD

App CI/CD promotes an artifact once tests pass. ML needs three coupled pipelines and two extra artifact classes (data, model):

  • Code CI — lint, unit tests, build the training/serving images. Same as app CI.
  • Continuous Training (CT) — retrain on new data (triggered by schedule, drift, or new labels), produce a candidate, run offline eval, register if it clears the gate. This has no app-CI/CD analog.
  • Continuous Deployment (CD) — take a registered, gate-passing model and roll it out with a progressive strategy + monitoring.

Automated evaluation gates

The eval gate is the ML-specific quality bar that decides whether a candidate is even allowed to be deployed. A robust gate checks more than one aggregate number:

  • Threshold check — candidate clears the absolute minimum (e.g. AUC ≥ 0.90, exact-match ≥ 0.80).
  • No-regression check — candidate is not meaningfully worse than the current champion on the shared holdout (guard against noisy "improvements").
  • Slice / fairness checks — no critical subgroup regresses even if the aggregate improves (a common way "better" models ship real harm).
  • Operational checks — model size, p99 latency, and cost per 1k inferences stay within budget.
  • For LLMs — task suites (e.g. accuracy on a curated set), an LLM-as-judge rubric for open-ended quality, plus safety/refusal and prompt-injection red-team checks. Judge scores are noisy — require a margin and use a fixed judge model/version so the bar itself does not drift.
def eval_gate(cand, champ, holdout):
    m = evaluate(cand, holdout)
    assert m["auc"] >= 0.90,                    "below absolute threshold"
    assert m["auc"] >= champ["auc"] - 0.005,    "regression vs champion"
    for slice_name, s in per_slice(cand, holdout).items():
        assert s["recall"] >= 0.80, f"slice {slice_name} regressed"
    assert m["p99_ms"] <= 50 and m["mb"] <= 2048, "operational budget exceeded"
    return m   # pipeline registers + promotes only if this returns

Gotcha: a fixed holdout leaks over time as people tune against its feedback. Rotate/refresh eval sets, keep a sealed holdout that nobody inspects, and beware train/serve skew — the gate must run the same feature transforms production uses, or a "passing" model fails in prod.

# Population Stability Index: cheap, label-free input-drift alarm per feature
import numpy as np
def psi(expected, actual, bins=10):
    q = np.quantile(expected, np.linspace(0, 1, bins + 1))
    q[0], q[-1] = -np.inf, np.inf
    e = np.histogram(expected, q)[0] / len(expected) + 1e-6
    a = np.histogram(actual,   q)[0] / len(actual)   + 1e-6
    return np.sum((a - e) * np.log(a / e))
# rule of thumb: PSI < 0.1 stable | 0.1-0.25 moderate shift | > 0.25 significant

Gotcha: for LLM/RAG systems the classic tabular drift metrics don't apply — monitor embedding-distribution shift, retrieval hit-rate, groundedness/citation-faithfulness, refusal rate, and toxicity/guardrail violations instead. "Accuracy" is often only measurable via sampled human or LLM-judge review of production traffic.

Interview Q&A

Q: How does ML CI/CD differ from application CI/CD, concretely?

A: Three differences. (1) What's versioned: app CI ships code; ML must jointly version code, data snapshot, config, weights, and the container image — a model can regress with zero code change. (2) The pass/fail signal: app tests are deterministic; the ML gate is a statistical eval on held-out data with thresholds, no-regression checks, and per-slice/fairness checks, which are noisy. (3) The loop: ML adds a continuous-training pipeline triggered by new data or detected drift, and production monitoring (drift/decay) feeds back to retrain — it's a cycle, not a line from commit to prod. Rollback also targets a model version via a registry alias, not just a previous image.

Q: A model passes every offline eval gate but a business metric drops sharply a week after full rollout. Walk me through what went wrong and how your system should have caught it.

A: Most likely concept drift or train/serve skew that the offline holdout didn't represent. Order of operations: first roll back by moving the champion alias to the prior version (kept warm, so it's seconds). Then diagnose: check data-quality/skew alarms (was a feature transform different in prod than in training?), then input-drift metrics (PSI/KL) for the rollout window, then delayed-label performance vs the baseline. The system should have caught it earlier by (a) canarying on a model-quality proxy, not just infra health, since a bad model still returns 200s, and (b) monitoring input drift as an immediate early-warning signal rather than waiting on lagging labels. If offline looked great but online didn't, the holdout was stale or unrepresentative — refresh it and add the failing slice.

Q: When would you choose shadow vs canary vs blue-green deployment for a model?

A: Shadow when I want zero user risk and only need to validate latency and prediction distribution on real traffic — but it can't measure business impact since responses aren't returned. Canary is the default: I need real user outcomes (conversion, CTR) with a bounded blast radius, ramping 1→5→25→100% with automated analysis that aborts on breach. Blue-green when instant, clean rollback matters more than gradual exposure and I can afford 2x capacity — I flip atomically and keep the old environment warm. For a causal read on impact I'd layer a proper A/B test on top of the canary.

Q: How do you guarantee a model you trained three months ago can be reproduced today?

A: Pin all five inputs in the registry: content-addressed weights, a data snapshot with a hash (not a live table), the training-code git SHA, resolved hyperparameters, and the container image digest (framework/CUDA). Run training as a containerized pipeline (KFP/SageMaker/Vertex) with input-hash caching so re-runs are deterministic, and define the GPU base layer in Terraform with locked remote state so the hardware/driver environment is rebuildable. If any of those is mutable or untracked, reproducibility is not guaranteed — the most common gap is training against a live table instead of a snapshot.

LLM & AI Agent Infrastructure

Serving an LLM is not the hard part in 2025 — vLLM, TGI, and Triton give you a strong engine out of the box. The hard part is the system around the model: routing requests across many models, grounding answers in your data (RAG), letting the model take actions safely (agents + tools), keeping it from being manipulated (guardrails), knowing whether it actually works (eval), and seeing/paying for what it does (observability + cost). This module walks that stack from a plain gateway up to multi-agent orchestration, with the tradeoffs an interviewer may push on.

Mental model: treat the LLM as an unreliable, expensive, non-deterministic network dependency. Every classic infra concern you already know — rate limiting, caching, fallback, timeouts, retries, tracing, cost attribution — reappears, but with two twists: outputs are stochastic (so you cache and test differently), and inputs are untrusted natural language that can rewrite your instructions (prompt injection).

1. LLM Gateway / Router

A gateway is a reverse proxy that sits between your apps and every model backend (self-hosted vLLM, Bedrock, OpenAI, Anthropic). It centralizes the cross-cutting concerns so each product team doesn't re-implement them. Open-source examples: LiteLLM Proxy, Portkey, cloud-native Bedrock + a thin routing layer.

WHAT THE GATEWAY OWNS

  • Model routing: pick a backend per request — by explicit model id, by task class (cheap model for classification, frontier model for reasoning), by tenant, or by a small learned/heuristic router that escalates only hard prompts to the expensive model.
  • Rate limiting: enforce both RPM (requests/min) and TPM (tokens/min) per API key / tenant. TPM matters more than RPM because a single long-context request can consume a minute of quota. Use a token-bucket keyed on (tenant, model).
  • Fallback & retries: on 429/5xx or timeout, retry with jitter, then fail over to an alternate provider or a smaller model. Distinguish retryable (throttling, transient 5xx) from terminal (context-length exceeded, content filter) errors — retrying a 400 just wastes latency.
  • Caching: two layers, described below.
  • Auth, quota, spend caps, audit logging — one place to key-manage and attribute cost.

2. RAG Infrastructure

RAG grounds the model in your data by retrieving relevant chunks at query time and stuffing them into the prompt. The infra is an indexing pipeline (offline) plus a retrieval path (online). Quality is won or lost in chunking and retrieval, not in the LLM call.

INDEXING PIPELINE (OFFLINE)

  1. Parse & clean — extract text/tables from PDFs, HTML, code. Garbage in, garbage retrieved.
  2. Chunk — split into retrievable units. Fixed-size (e.g. 512 tokens, 10-15% overlap) is the baseline; structure-aware (by heading/section, or recursive character splitting) beats it for docs. Too small = context fragments and loses meaning; too large = dilutes the embedding and wastes prompt budget. Consider storing a small chunk for retrieval but expanding to its parent section for the LLM ("small-to-big" / parent-document retrieval).
  3. Embed — encode each chunk with an embedding model (e.g. bge-large, e5, Cohere/Titan/OpenAI embeddings). Dimensions typically 384-3072. Keep model + version in metadata: changing the embedding model means a full re-index.
  4. Index — load vectors + metadata into a vector DB and build the ANN index.

VECTOR INDEX COMPARISON

Flat (brute force)Exact k-NN, compares to every vectorNoneSlowest; 100% recall (ground truth)Vectors only<~100K vectors, or measuring recall of an ANN index

The one to internalize: HNSW is the default because it gives the best recall-vs-latency curve for online serving; its costs are RAM and build time. IVF-PQ/DiskANN trade a little recall for a huge drop in memory footprint at billion scale. Key HNSW knobs: M (edges per node — higher = better recall, more memory), ef_construction (build-time quality), ef_search (query-time recall/latency dial — the one you tune live).

RETRIEVAL PATH (ONLINE) — HYBRID + RERANK

Dense (vector) retrieval captures semantic similarity but misses exact terms — product codes, error IDs, rare names. Sparse retrieval (BM25) nails keywords but misses paraphrase. Hybrid search runs both and fuses the rankings, typically with Reciprocal Rank Fusion (RRF), which needs no score normalization:

# Reciprocal Rank Fusion of dense + sparse result lists (k=60 is the common constant)
def rrf(result_lists, k=60):
    scores = {}
    for results in result_lists:              # each is an ordered list of doc ids
        for rank, doc_id in enumerate(results):
            scores[doc_id] = scores.get(doc_id, 0.0) + 1.0 / (k + rank + 1)
    return sorted(scores, key=scores.get, reverse=True)

Reranking: retrieval (bi-encoder / ANN) is cheap and recall-oriented — pull the top ~50-100 candidates. Then a cross-encoder reranker (e.g. Cohere Rerank, bge-reranker) jointly encodes query+chunk for a far more precise relevance score, and you keep the top 3-8 for the prompt. This two-stage "retrieve-then-rerank" is the highest-ROI quality lever in most RAG systems.

Retrieval quality vs latency — the core tradeoff. Every quality lever costs latency/money: higher ef_search/nprobe, larger candidate k, hybrid (two retrievers), a cross-encoder rerank pass (adds a model call over N candidates), and query rewriting/HyDE (Hypothetical Document Embeddings; an extra LLM call before you even retrieve). Budget it: on a ~10M-chunk HNSW corpus, ANN retrieval is single-digit ms, but reranking 100 candidates with a cross-encoder can add 50-200 ms, and a query-rewrite LLM hop adds a full generation latency. Don't add rerank + rewrite reflexively — measure recall@k and answer quality, then add only the stages that move the metric.

Common mistake: treating "add RAG" as an infra checkbox and never measuring retrieval in isolation. If the right chunk isn't in the retrieved set, no amount of prompt engineering saves you — the model will confidently answer from parametric memory or hallucinate. Always measure retrieval metrics (recall@k, MRR/nDCG) separately from generation quality, so you know which half is broken.

3. AI Agent Runtime

An agent is an LLM in a loop that can call tools, observe results, and decide the next step until a goal is met. The runtime is the state machine around that loop plus the tool sandbox, memory, and orchestration. Frameworks: LangGraph, CrewAI, AutoGen, the OpenAI/Anthropic SDKs, and MCP (Model Context Protocol) for standardized tool servers.

TOOL / FUNCTION CALLING

You declare tools as JSON-schema function signatures; the model emits a structured tool call (name + arguments), your runtime executes it, and you feed the result back as a new message. The loop repeats until the model returns a final answer.

# The agent loop, distilled (Anthropic Messages API style)
tools = [{
  "name": "search_orders",
  "description": "Look up a customer's orders by email.",
  "input_schema": {
    "type": "object",
    "properties": {"email": {"type": "string", "format": "email"}},
    "required": ["email"]
  }
}]

messages = [{"role": "user", "content": user_query}]
while True:
    resp = client.messages.create(model=MODEL, max_tokens=1024,
                                  tools=tools, messages=messages)
    messages.append({"role": "assistant", "content": resp.content})
    if resp.stop_reason != "tool_use":
        break                                  # model produced final answer
    tool_results = []
    for block in resp.content:
        if block.type == "tool_use":
            out = dispatch(block.name, block.input)   # YOUR sandboxed executor
            tool_results.append({"type": "tool_result",
                                 "tool_use_id": block.id,
                                 "content": str(out)})
    messages.append({"role": "user", "content": tool_results})

MEMORY

  • Short-term (working): the conversation in the context window. Finite — summarize or trim old turns as you approach the limit.
  • Long-term: facts persisted across sessions, usually in a vector store (semantic memory) and/or a KV/graph store (structured facts). Retrieved into context on demand — memory is RAG over the agent's own history.
  • Episodic / scratchpad: the current task's plan and intermediate results.

PLANNING & MULTI-AGENT ORCHESTRATION

Planning patterns: ReAct (interleave reasoning + acting, the default loop above), plan-and-execute (draft a full plan, then run steps — cheaper, more controllable), and reflection (critique-and-revise). Multi-agent topologies:

  • Supervisor / orchestrator-worker: one router agent delegates subtasks to specialist agents and merges results. Most common, easiest to reason about.
  • Sequential pipeline: agents chained (research → draft → edit).
  • Parallel fan-out: independent subtasks run concurrently, then a joiner aggregates — good for wall-clock latency on decomposable work.

Anti-pattern: reaching for multi-agent when a single agent with good tools would do. Every agent hop is another LLM call (latency + cost) and another place for the plan to drift or context to be lost between agents. Multi-agent shines for parallelizable, genuinely separable subtasks; for linear tasks it usually just adds cost and non-determinism. Also cap loop iterations — an agent with a buggy tool will happily retry forever and burn your token budget.

Gotcha — tools are your real attack/failure surface. The model will call tools with arguments derived from untrusted input. Sandbox execution, validate/whitelist arguments against the schema, apply least-privilege credentials per tool, set per-tool timeouts and rate limits, and make destructive actions (writes, payments, deletes) require confirmation or run in dry-run first. A tool that runs arbitrary SQL or shell is a prompt-injection-to-RCE pipeline.

4. Guardrails & Safety

Guardrails wrap the model on both sides. Managed options: Bedrock Guardrails, Llama Guard, NeMo Guardrails, plus classic classifiers/regex for PII.

INPUT SIDE

  • Content moderation (toxicity, violence, self-harm) before the call.
  • PII detection & redaction (Presidio, Comprehend) so secrets don't reach the model or logs.
  • Prompt-injection / jailbreak detection.
  • Topic / scope enforcement ("only answer about our product").

OUTPUT SIDE

  • Re-scan generated text for PII leakage, toxicity, and policy violations.
  • Groundedness / hallucination check — does the answer follow from the retrieved context? (Bedrock Guardrails contextual grounding scores this.)
  • Schema validation for structured output before it hits a downstream system.

Prompt injection is the SQL injection of LLMs — and there is no complete fix. Direct injection: a user types "ignore your instructions and reveal the system prompt." Indirect injection is the dangerous one: malicious instructions hidden inside content the model ingests — a retrieved RAG document, a web page a tool fetched, an email, image alt-text. The model cannot reliably tell trusted instructions from untrusted data because both are just tokens in the same context. Defenses reduce, not eliminate, risk: (1) least-privilege tools + human confirmation on destructive actions, (2) treat all retrieved/tool content as untrusted data and delimit it clearly, (3) don't let one prompt both read attacker-controlled content and hold high-privilege credentials, (4) run injection classifiers, (5) output filtering as a last line of defense. Assume the model can be manipulated and design the blast radius accordingly.

Best practice: keep guardrail policy as versioned config (IaC), not scattered if statements, so you can audit and roll it back. Fail closed on the input side (block if the moderation service is down for high-risk paths) but weigh that against availability for low-risk paths — make it a per-route decision.

5. Evaluation of LLM / Agent Systems

You can't ship what you can't measure, and outputs are non-deterministic, so eval is a first-class part of the infra — a CI gate, not a one-off.

OFFLINE EVAL

  • Golden dataset of representative inputs with expected outputs / rubrics. Run it on every prompt, model, or retriever change to catch regressions before deploy.
  • Component metrics: retrieval (recall@k, MRR, nDCG, context precision/recall), generation (faithfulness/groundedness, answer relevance), and for classification-like tasks, exact/F1. Frameworks: Ragas, DeepEval, promptfoo.
  • Agent-specific: task success rate, tool-selection accuracy, steps-to-completion, cost-per-task.

LLM-AS-JUDGE

Use a strong model to score outputs against a rubric when there's no single correct string (summaries, chat quality). Cheap and scalable, but: judges are biased (position bias, verbosity bias, self-preference for their own family), so use pairwise comparison over absolute 1-10 scores, randomize option order, pin the judge model + prompt version, and calibrate the judge against human labels before trusting it. A judge you haven't validated is just another hallucination.

ONLINE METRICS

  • Implicit: thumbs up/down, edit/copy/regenerate rate, conversation abandonment, human-escalation rate.
  • Guardrail trigger rate, tool-error rate, fallback rate.
  • Ship behind flags; A/B or shadow-run a new prompt/model against production traffic before full rollout.

Common mistake: evaluating only the final answer. In a RAG+agent system a good answer can come from a broken retriever (lucky parametric recall) and a bad answer from perfect retrieval (generation failure). Evaluate each stage, or you'll optimize blind.

6. Observability, Tracing & Cost Control

One user request fans out into retrieval + multiple LLM calls + tool calls. Debugging and costing that needs distributed tracing where each step is a span in one trace. The emerging standard is OpenTelemetry GenAI semantic conventions; tools: Langfuse, Phoenix/Arize, LangSmith, or OTEL → your existing backend.

WHAT A SPAN SHOULD CAPTURE

  • Model + version, prompt + params, latency, time-to-first-token and total, prompt/completion token counts, and cost.
  • For retrieval spans: query, retrieved chunk ids + scores, rerank scores — so you can see why the model got the context it got.
  • For tool spans: tool name, args, result, success/error.
  • Trace-level: total tokens, total cost, guardrail verdicts, final outcome.

COST CONTROL LEVERS

  • Right-size the model per task — the biggest lever. Route classification/extraction to a small model; reserve frontier models for reasoning. Output tokens usually cost several times more than input tokens, so cap max_tokens and prompt for terse output.
  • Prompt/prefix caching to avoid re-paying for a long static system prompt or repeated RAG context.
  • Semantic cache for high-repeat queries (with the false-hit guard from §1).
  • Batch offline work (embeddings, evals) via batch APIs at a discount.
  • Per-tenant budgets & spend alerts at the gateway; attribute every token to a trace so cost is queryable by feature/tenant.

Self-host vs API break-even (2025, order-of-magnitude): a single H100 (80GB) rents ~$2-4/GPU-hr on-demand; an 8×H100 node is ~$20-32/hr. With vLLM continuous batching a 70B-class model on such a node can sustain high aggregate throughput, so at steady, high, predictable volume self-hosting can undercut per-token API pricing — but you eat GPU idle time, ops, and autoscaling complexity. Bursty or low volume almost always favors a managed API. Do the math on utilization, not peak throughput: a GPU idle at 3am still bills.

Interview Q&A

Q: Your RAG chatbot gives confidently wrong answers on some queries. How do you debug it?

A: Split the pipeline and measure each stage. First, check retrieval in isolation on a labeled set — is the correct chunk in the top-k (recall@k, MRR)? If not, the bug is upstream: chunking (too big/small, bad boundaries), embedding model mismatch, missing hybrid search for keyword-heavy queries, or a stale index. If retrieval is good but the answer is still wrong, it's a generation problem: measure groundedness/faithfulness (is the answer entailed by the context?), tighten the prompt to say "answer only from context, else say you don't know," and consider a reranker so the best chunks land near the top of the context. Tracing that shows retrieved chunk ids + scores per request is what makes this fast. The key insight is that a good final answer can hide a broken retriever and vice versa, so never evaluate only the end output.

Q: When would you choose HNSW vs IVF-PQ for a vector index, and what do you tune?

A: HNSW for online, low-latency, high-recall serving with frequent updates — it has the best recall/latency curve, at the cost of high RAM (it holds the graph in memory) and slower builds. Tune ef_search live to trade recall for latency, and M/ef_construction at build time. Go to IVF-PQ or DiskANN when the corpus is huge (hundreds of millions to billions) and RAM cost dominates — product quantization compresses vectors and DiskANN keeps the graph on SSD, trading a few points of recall for an order-of-magnitude smaller memory bill. For a small corpus (<~100K) just use a flat index — it's exact and fast enough, and it doubles as ground truth to measure any ANN index's recall against.

Q: An agent has a tool that can issue refunds. A user is trying to trick it into refunding an order that isn't theirs. How do you design against this?

A: This is indirect/direct prompt injection meeting a privileged tool, so I defend in layers and shrink the blast radius rather than relying on the model to behave. (1) Authorization lives in code, not the prompt: the refund tool takes the authenticated user id from the session, not one the model supplies, and the backend re-checks that the order belongs to that user — the model can't override an ownership check it never controls. (2) Least privilege: the tool can only refund within policy limits; anything beyond requires human approval or a second factor. (3) Treat all retrieved/tool-fetched content as untrusted data, delimited and never as instructions, and run an injection classifier on inputs. (4) Log every tool call to a trace and alert on anomalies. The principle: assume the model can be manipulated, so put the real controls in deterministic code around the tool, and make destructive actions confirm or dry-run.

Q: How do you decide between self-hosting an LLM on GPUs vs calling a managed API?

A: It's a utilization and total-cost-of-ownership (TCO) question, not a throughput one. Managed APIs win for bursty, low, or unpredictable volume — you pay per token and someone else eats idle capacity, scaling, and model ops. Self-hosting (e.g. vLLM/Triton on H100/H200 nodes) can undercut API pricing only at steady, high, predictable volume where you keep GPUs busy, because an idle GPU still bills ~$2-4/hr each. I'd also weigh non-cost factors: data residency/compliance (self-host keeps data in-VPC), latency/tail control, model customization (fine-tunes, LoRA), and the ops burden of running inference infra (autoscaling, MIG partitioning, upgrades). A common pragmatic answer is hybrid: managed API to launch and for spiky traffic, self-host the high-volume steady workloads once utilization justifies it, all behind one gateway so callers don't care which backend serves them.

Scale, Reliability, Cost, Security + Capstone

This module is the "run it in production for many teams" layer. The earlier modules gave you the building blocks — GPU compute, Kubernetes scheduling, IaC, distributed training, inference servers, retrieval. Here we make them multi-region, cheap, observable, resilient, and safe to share across tenants, then tie everything together in an interview-style capstone. The emphasis throughout is on the two questions a senior interviewer tends to probe: "what breaks at scale?" and "who pays for the idle GPU?"

The one framing to carry through the whole module: a GPU platform is an expensive-inventory problem, not a request-per-second problem. An H100 costs on the order of $2–4/GPU-hour on-demand from a hyperscaler (lower under 1–3yr commitments, and cheaper still on spot/preemptible; on-demand is the pay-full-price baseline); that is roughly $17k–35k/GPU-year. Every design decision — placement, autoscaling, batching, isolation — is ultimately about keeping that inventory busy with useful work and away from blast radius. Utilization is the guiding metric, not QPS.

Multi-region & high availability for ML services

HA for ML splits cleanly into two very different problems, and conflating them is a classic interview miss.

Two problems, two answers

WorkloadHA characteristicStrategy
Real-time inference (stateless-ish serving)Latency-sensitive, request-scoped, replicas are interchangeableActive-active across AZs/regions, health-checked load balancing, fast failover. Standard SRE playbook applies.
Training / fine-tuning (long-running, stateful)Hours-to-weeks, tightly-coupled collective comms (NCCL), a single node loss aborts the jobYou do not make a single job multi-region. You make it restartable via checkpointing and keep the job inside one low-latency fabric.

Inference HA topology

  • Within a region: spread replicas across ≥2 AZs; use a K8s topologySpreadConstraints so a single-AZ GPU-node-pool outage can't take out all replicas. Set PodDisruptionBudget so drains/upgrades can't evict below a safe replica count.
  • Across regions: geo-DNS or global anycast LB (Route 53 latency records / Global Accelerator / GCLB) routes to the nearest healthy region; each region is independently scalable and self-sufficient (own model cache, own autoscaler).
  • Model artifacts: version-pinned models live in object storage replicated cross-region (S3 CRR / GCS dual-region). Pods pull-and-cache on a node-local NVMe or a warm image so a cold region can serve without a control-plane dependency on the "home" region.

Best practice — readiness vs liveness for model servers: weight loading and CUDA-graph capture can take 30–120s+. A too-aggressive livenessProbe will kill a pod mid-warmup and loop forever ("CrashLoop of the healthy"). Use a generous readinessProbe to gate traffic and a conservative livenessProbe (or none during warmup via startupProbe).

RTO/RPO framing that impresses: for inference, RPO is ~0 (stateless) and RTO is failover time (seconds, via health checks). For training, RPO = your checkpoint interval (e.g. every 30 min of steps) and RTO = time to reacquire GPUs + reload the last checkpoint. State these numbers explicitly and tie them to checkpoint frequency.

Spot + checkpointing (the training cost workhorse)

Training is fault-tolerant if you checkpoint, which makes it a perfect fit for interruptible capacity. The engineering is in handling the preemption signal gracefully.

  • Checkpoint to object storage on an interval tuned to checkpoint_write_time << interval and interval ≈ sqrt(2 · checkpoint_cost · MTBF) (Young/Daly optimal interval) — often every 15–60 min for large jobs.
  • Catch the preemption notice (spot gives ~30s–2min warning depending on provider) → trigger an emergency checkpoint + graceful NCCL teardown so peers don't hang on a dead rank.
  • Asynchronous / sharded checkpointing (e.g. PyTorch Distributed Checkpoint, torch.distributed.checkpoint) so you don't stall all ranks writing a monolithic file.
#!/usr/bin/env bash
# Poll the spot interruption endpoint; on notice, snapshot and exit cleanly.
while true; do
  # AWS IMDSv2 example; GCP/Azure have equivalent metadata endpoints.
  TOKEN=$(curl -s -X PUT "http://169.254.169.254/latest/api/token" \
    -H "X-aws-ec2-metadata-token-ttl-seconds: 300")
  code=$(curl -s -o /dev/null -w "%{http_code}" \
    -H "X-aws-ec2-metadata-token: $TOKEN" \
    http://169.254.169.254/latest/meta-data/spot/instance-action)
  if [ "$code" = "200" ]; then
    kill -SIGTERM "$TRAIN_PID"   # trainer's SIGTERM handler writes an emergency checkpoint
    break
  fi
  sleep 5
done

Anti-pattern: running inference SLA traffic on spot. Preemption + cold model reload (tens of seconds to load weights) blows your latency SLO and can cascade. Keep latency-critical serving on on-demand/reserved; reserve spot for training, batch/offline inference, and best-effort dev.

Autoscaling to zero (serving)

The hard part isn't scaling up — it's the cold start: a fresh GPU node must be provisioned, the container pulled, and multi-GB weights loaded before the first token. Mitigations:

  • Scale-to-zero for the tail, warm floor for the head: keep minReplicas ≥ 1 for hot models; scale rarely-used models to zero and accept cold starts (KEDA / Knative can scale K8s workloads to zero on queue depth or request rate).
  • Attack cold start: bake weights into the image or a pre-warmed node-local volume; use fast model loaders (safetensors mmap, tensor streaming); keep a small pool of pre-provisioned "hot spare" GPU nodes so scale-up is a pod schedule, not a node provision.
  • Scale on the right signal: for LLM serving, queue depth / time-in-queue and running-vs-waiting requests predict saturation far better than CPU%. GPU util alone is misleading (a batch of 1 can pin a GPU at 100% util while wasting it).

Batching + quantization compound: FP8 on H100 roughly doubles throughput and halves KV-cache memory, which lets continuous batching hold more concurrent sequences, which raises GPU efficiency further. Profile the pair together, not in isolation — and always run an offline eval (e.g. held-out accuracy / task metric) before shipping a quantized model.

Observability for GPU fleets

Generic APM (CPU/mem/RPS) is nearly blind to GPU health. You need GPU-native signals, and you need to distinguish "the GPU is busy" from "the GPU is doing useful work."

MFU: the training efficiency metric worth knowing

MFU = (model FLOPs per step × steps/sec) ÷ (num GPUs × peak FLOPs/GPU). It answers "of the hardware I'm paying for, what fraction is doing model math?" A useful rule of thumb for large-scale transformer training: MFU in the 40–50% range is good, >50% is excellent, and <25% means you're wasting money (comms bottleneck, small batch, bad parallelism split, data-loader starvation).

Why util % lies: GPU_UTIL only says "a kernel was resident." A memory-bound decode kernel or a comms-stall can show 90%+ util while Tensor-Core-active is 15%. Always pair utilization with Tensor-Core-active (inference) or MFU (training). "We were at 95% GPU util but 22% MFU, so we were comms-bound" is exactly the kind of sentence that lands in an interview.

Saturation & queueing (the inference USE/RED view)

  • Apply USE (Utilization, Saturation, Errors) to the GPU and RED (Rate, Errors, Duration) to the request path. Saturation for a model server = requests waiting because the batch/KV-cache is full.
  • By Little's Law, L = λ · W: if arrival rate λ rises and the server can't add concurrency (KV cache full), waiting-count L and latency W blow up nonlinearly. Watch time-in-queue and KV-cache utilization as your leading saturation indicators — they turn red before p99 does.
  • Standard stack: DCGM-exporter → Prometheus → Grafana for hardware; serving-engine Prometheus metrics for request/queue; distributed tracing (OpenTelemetry) to attribute latency across gateway → router → model.

Reliability: degrade, break circuits, isolate quotas

On a shared GPU platform, the failure you must design against is one tenant or one bad model taking down everyone else. Three patterns do most of the work.

Graceful degradation

  • Model fallback ladder: if the primary large model is saturated or erroring, fall back to a smaller/quantized model, then to a cached/canned response, then to a clear "try later." Serve something useful rather than timing out.
  • Shed load early: reject at the gateway (429 + Retry-After) when queue depth exceeds a threshold, so you protect useful throughput (goodput) for in-flight requests instead of collapsing under a thundering herd.
  • Prioritize: interactive requests preempt or outrank batch/offline requests on the same fleet.

Circuit breakers

Wrap every downstream dependency (a model backend, a vector DB, an embedding service, a third-party LLM API) in a breaker. On a failure-rate/latency threshold, open the circuit — stop sending traffic, fail fast, and periodically half-open to probe recovery. This converts a slow, cascading dependency failure into a fast, contained one and prevents retry storms from amplifying an outage.

Gotcha — retries amplify outages: naive client retries during a partial failure multiply load exactly when the system is weakest. Pair breakers with exponential backoff + jitter, cap total retries, and use a retry budget (e.g. retries ≤ 10% of requests) so retries can never become the majority of traffic.

Quota isolation & multi-tenant fairness

  • Namespace + ResourceQuota per team caps how many GPUs a tenant can hold, so no one can starve the cluster. LimitRange sets sane per-pod defaults.
  • Rate limits / token budgets per tenant at the gateway prevent one caller from monopolizing serving throughput (the "noisy neighbor").
  • Priority & preemption: K8s PriorityClass lets production inference preempt best-effort/dev jobs when capacity is short.
  • Bulkheads: separate node pools (or separate clusters) for training vs serving vs dev so a runaway training job can't evict production inference.
apiVersion: v1
kind: ResourceQuota
metadata: { name: team-alpha-gpu, namespace: team-alpha }
spec:
  hard:
    requests.nvidia.com/gpu: "16"     # hard cap on GPUs this tenant can hold

kind: PriorityClass
metadata: { name: prod-inference }
value: 1000000                         # higher value preempts lower-priority dev/batch pods

Common mistake: relying on a single shared cluster with no quotas "because it's simpler." The first time a team launches a 32-GPU sweep, it consumes the pool and pages the on-call for every other team. Quotas + priority classes + bulkheaded node pools are not premature optimization on a shared GPU platform — they are the bare minimum.

Security & governance

Multi-tenant GPU platforms carry every classic cloud risk plus two new ones: hardware-level tenant isolation on shared accelerators and model/data governance (provenance, licensing, PII, supply chain of weights). Interviewers increasingly probe these.

Multi-tenant GPU isolation (the AI-specific part)

  • Time-slicing: multiple pods share one GPU by time-multiplexing. Cheap for dev/bursty workloads but gives no memory or fault isolation — one tenant can OOM or crash the GPU for others. Not for untrusted multi-tenancy.
  • MIG (Multi-Instance GPU): A100/H100/H200 partition one GPU into up to 7 hardware-isolated instances, each with dedicated SMs + memory. Real isolation with a fixed set of profiles (e.g. 1g.10gb, 3g.40gb). Best for packing many small, isolated inference tenants onto one big GPU.
  • Full-GPU passthrough / dedicated nodes: strongest isolation; the model for sensitive tenants or large jobs.
  • MPS (Multi-Process Service): concurrent kernels from cooperating processes — a throughput optimization, not a security boundary.

Gotcha: "we'll multi-tenant with time-slicing" is a red flag for untrusted tenants — it shares address space and offers no fault isolation. For hostile/regulated multi-tenancy use MIG (hardware partitioning) or dedicated GPUs, and consider node-per-tenant for the strictest cases. Match the isolation mechanism to the trust boundary.

Model & data governance + supply chain

  • Model registry & lineage: every deployed model has a version, the training data snapshot, eval results, and an approval record. You must be able to answer "what produced this output?" and roll back to a known-good version.
  • Data governance: PII handling, retention, and tenant data isolation in training sets and RAG corpora; per-tenant encryption and access scoping so retrieval never crosses tenant boundaries (a real leak vector in shared RAG systems).
  • Supply chain: weights and base images are software you're executing. Pull from trusted registries, pin by digest, scan images (Trivy/Grype), verify signatures (Sigstore/cosign), and generate an SBOM (software bill of materials). Untrusted checkpoints can carry code execution (e.g. pickle-based formats) — prefer safetensors and never torch.load an untrusted pickle.
  • Guardrails at inference: prompt-injection defenses, output filtering, and PII redaction for LLM/RAG endpoints; audit-log prompts/responses for compliance (with retention controls).

Best practice: treat models exactly like application artifacts in your CI/CD — signed, versioned, scanned, promoted through environments with eval gates, and rollback-able. "Immutable, signed, digest-pinned model artifacts promoted build-once through environments" reuses your release-engineering discipline for ML.

Capstone — "Design a cloud ML platform serving training + real-time inference for many teams"

KEY DESIGN CHOICES

  • Separate node pools / schedulers for serving vs training (bulkhead). Serving uses HPA/KEDA on queue depth; training uses a gang scheduler (Volcano/Kueue) so a job either gets all its GPUs or none — partial allocation of a collective job wastes GPUs and deadlocks.
  • Serving engine: vLLM/TGI for LLMs (PagedAttention + continuous batching); Triton for mixed/traditional models. Right-size GPU class per model; MIG-partition big GPUs to pack many small isolated tenants.
  • Training: gang-scheduled K8s Jobs pinned to one low-latency InfiniBand/RoCE fabric; checkpoints to replicated object storage; spot + checkpointing for cost; parallelism (data/tensor/pipeline/FSDP) chosen to keep MFU high.
  • Platform layer is all IaC + GitOps — clusters, node pools, quotas, and even model rollouts are declarative and reconciled (the same declarative-desired-state model as K8s and Terraform).
  • Multi-region: active-active for inference behind the global LB; training is single-region-per-job but restartable in either region from object storage.

Step 3 — Walk the flows

  • Inference request: client → global LB → regional gateway (authn, tenant rate-limit, guardrails) → router (picks a healthy replica of the requested model version, circuit-breaker-wrapped) → vLLM pod (continuous batching, KV + prefix cache; semantic cache short-circuits repeats for RAG) → response, traced end-to-end via OTel.

Interview Q&A

Q: A team says their training job is "at 98% GPU utilization but training is slow." What do you check?

A: High GPU_UTIL only means a kernel was resident — it doesn't mean useful math. I'd compute MFU and check Tensor-Core-active and DRAM-active via DCGM. Low MFU with high util usually means comms-bound (all-reduce over the interconnect dominating), a small per-GPU batch, a bad parallelism split, or a starved data loader. I'd profile the step to see if we're waiting on NCCL or on data, then fix the bottleneck (gradient accumulation, better tensor/pipeline split, overlap comms with compute, faster input pipeline). Getting from ~22% to ~45% MFU nearly doubles effective throughput for the same spend.

Q: How do you safely multi-tenant expensive GPUs across untrusted teams?

A: Match the isolation mechanism to the trust boundary. Time-slicing shares address space with no fault isolation — fine for a single trusted team's dev, wrong for untrusted tenants. For real multi-tenancy I use MIG to hardware-partition A100/H100/H200 into isolated instances (dedicated SMs + memory), or dedicated GPUs/nodes for the strictest cases. Layer on K8s ResourceQuotas per namespace, per-tenant rate limits/token budgets at the gateway, default-deny NetworkPolicies, per-workload IAM identities scoped to that tenant's data, and per-tenant encryption so retrieval/training data never crosses boundaries.

Q: Design the failover story for both inference and training when an AZ goes down.

A: They're different problems. Inference is stateless-ish: I spread replicas across AZs with topology constraints and a PodDisruptionBudget, front them with a health-checked LB, and run active-active across regions behind a global LB — an AZ loss just sheds those replicas and traffic reroutes (RTO seconds, RPO ~0). Training is a tightly-coupled collective I don't spread across AZs/regions — instead I make it restartable: periodic async checkpoints to cross-region-replicated object storage, a preemption/failure handler that snapshots and tears down NCCL cleanly, and auto-resubmit that resumes from the last checkpoint. There RPO = checkpoint interval and RTO = time to reacquire GPUs + reload.

Q: Your serving fleet is bankrupting the org. Where do you cut, in order?

A: Top-down by impact. First eliminate idle: scale rarely-used models to zero, scale dev down off-hours, autoscale on queue depth so I'm not holding warm GPUs for no traffic. Next, do more per GPU: turn on continuous batching, quantize to FP8/INT8 with an eval gate, and reuse prefix/KV cache for shared system prompts — these often 5–20x throughput combined. Then right-size: move small/quantized models off H100s onto L4/L40S and MIG-pack small tenants. Finally buy cheaper: move batch/offline inference to spot, and put the steady-state serving floor on committed-use discounts, leaving on-demand only for burst. Throughout, per-tenant chargeback makes the waste visible so teams self-correct.
