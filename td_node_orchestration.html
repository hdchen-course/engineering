Node-Level Orchestration & Fleet Bring-up

The system-software view of how a single server becomes a scheduling target and how a rack full of them becomes a fleet: what a container actually is (cgroups v2 + namespaces, not a VM), how a workload gets handed a specific accelerator or high-speed NIC, how bare metal goes from power-on to "healthy node in the cluster," and why bringing up hardware is really CI/CD for physical machines. The control-plane view of Kubernetes lives in Part XIII; here we stay on the node, close to the kernel and the metal.
Read this like a story

We start at the node and zoom out to the fleet. §1 frames the two altitudes (control plane vs node) so we don't retread Part XIII. §2 dissects what a container is — a process wearing cgroups and namespaces. §3 is the kubelet + CRI + OCI runtime chain that turns a pod spec into running processes. §4 is how special hardware becomes schedulable (device plugins, Topology Manager, Node Feature Discovery). §5 is bare-metal bring-up: power-on → firmware → NetBoot OS → join → burn-in, treated as declarative, idempotent CI/CD. §6 is fleet telemetry and hardware health. §7 is interconnect topology as background context (PCIe, NVLink, InfiniBand/RDMA) and why topology-aware scheduling matters. §8 is validation and regression-gating firmware/kernel/driver changes. §9 collects the interview questions. Read it as one arc: a process becomes a container, a box becomes a node, a rack becomes a fleet.

1. Two Altitudes: Control Plane vs the Node

Cluster orchestration is usually taught from the top — the API server, the scheduler, controllers reconciling desired state. That is the control-plane altitude, and it is Part XIII's subject. This chapter lives one level down, at the node: the single machine that actually runs the work, and the Linux kernel primitives that make "a container" more than a marketing word. If the control plane is the distributed database that decides what should run where, the node is the execution engine that makes it real on one box.

The clean mental split: the control plane decides and records intent (this pod should exist, on a node with these resources); the node realizes that intent (create the cgroups, set up the namespaces, pull the image, start the process, report back health). The contract between them is small and deliberate — the scheduler places a pod onto a node, and from there the node's agent takes over. Everything in this chapter is about that second half plus the physical layer beneath it.

The two altitudes. The control plane decides where work goes; the node makes it run. Bring-up is what produces a node the control plane can schedule onto.
Interview signal

If asked "how does Kubernetes run a container," a weak answer stops at "the scheduler picks a node." A strong answer continues down: "the kubelet on that node calls the container runtime over the CRI, which creates cgroups and namespaces and hands the OCI image's root filesystem to a runtime like runc." Knowing the handoff point between control plane and node is the whole game here.

2. What a Container Actually Is

The single most clarifying fact for a backend engineer: a container is not a virtual machine. There is no guest kernel, no hypervisor, no emulated hardware. A container is just one (or more) ordinary Linux processes running on the host kernel, with two kernel features applied to them: namespaces (which control what the process can see) and cgroups (which control what the process can use). That's it. Everything else — images, layers, the runtime — is packaging and plumbing around those two primitives.

The one-sentence bridge

A container is a process with namespace isolation (its own view of PIDs, mounts, network, etc.) plus cgroup limits (a cap on CPU, memory, and I/O) — sharing the host's single kernel. A VM virtualizes the hardware and runs a whole second kernel; a container virtualizes only the OS-level view and shares the kernel.

Namespaces — what the process can see

A namespace partitions a global kernel resource so that processes inside it see their own isolated instance. When you create a process in a fresh set of namespaces, it believes it has the machine to itself. The kernel provides several, and a typical container uses most of them:

NamespaceIsolatesEffect inside the container
pidProcess IDsIts main process is PID 1; it can't see host processes.
mntMount pointsIts own filesystem tree (the image's root fs), not the host's.
netNetwork stackOwn interfaces, routes, ports, firewall rules.
utsHostname / domainCan set its own hostname without touching the host's.
ipcSysV IPC / POSIX msg queuesOwn shared-memory and semaphore namespace.
userUID/GID mappingsCan be root (UID 0) inside while unprivileged on the host.
cgroupcgroup root viewSees its own cgroup tree rooted at its slice, not the host root.

Under the hood these are created with the clone()/unshare() syscalls (a process asks the kernel for a new namespace) and joined with setns(). You can even watch this happen by hand:

# run a shell in fresh PID + mount + UTS + net namespaces
# (unshare is the user-space front-end to the unshare() syscall)
# --mount-proc remounts /proc for the new PID ns; without it, ps still reads the host's procfs
sudo unshare --pid --mount --uts --net --fork --mount-proc bash
# inside: hostname is ours to set, and:
ps aux            # sees almost nothing — its own PID view
ip link           # only loopback — its own empty net namespace
Bridge for distributed-systems folks

A namespace is like giving a tenant its own view of a shared multi-tenant system — its own schema, its own visible rows — without spinning up a separate database. The data plane (the kernel) is shared; only the visibility is partitioned.

cgroups v2 — what the process can use

Control groups (cgroups) are the kernel's resource-accounting-and-limiting mechanism. Where namespaces answer "what can I see," cgroups answer "how much can I consume." cgroups v2 is the current unified hierarchy: a single tree under /sys/fs/cgroup where each node is a directory, and controllers (cpu, memory, io, pids) are enabled per subtree. A container is placed in its own cgroup, and the runtime writes limits into that directory's control files.

# cgroups v2 unified hierarchy — a container's slice is just a directory
/sys/fs/cgroup/<slice>/<container>/
  cpu.max        # "<quota> <period>", e.g. "20000 100000" = 0.2 CPU
  cpu.weight     # relative share under contention (default 100)
  memory.max     # hard memory cap; exceeding it triggers the OOM killer
  memory.high    # soft cap — throttles/reclaims before the hard max
  io.max         # per-device IOPS / bandwidth ceilings
  pids.max       # cap on number of processes (fork-bomb guard)

The mapping to a pod spec is direct. A Kubernetes CPU limit becomes cpu.max (a hard quota per period); a CPU request becomes cpu.weight (a proportional share when the node is busy). A memory limit becomes memory.max — and here is the asymmetry candidates trip on:

CPU throttles, memory kills

Exceeding a CPU limit does not kill the process — the scheduler simply throttles it (it gets no more slices until the next period), which shows up as latency, not a crash. Exceeding memory.max is different: memory can't be "given back" the way CPU time can, so the kernel's OOM killer terminates a process in the cgroup. That's why a memory-limited pod dies with OOMKilled while a CPU-limited one just runs slowly. Confusing the two is a classic misdiagnosis of a "slow" vs "crashing" workload.

Both containers are just processes on one shared kernel. Namespaces isolate their view; cgroups cap their consumption. Contrast a VM, which would run a second full kernel on emulated hardware.
Interview signal

"What is a container?" — the answer that lands is "a process (tree) with namespace isolation and cgroup limits, sharing the host kernel — not a VM." Bonus points for naming the split: namespaces = visibility, cgroups = resource limits, and that CPU limits throttle while memory limits OOM-kill.

3. The Node Agent: kubelet, CRI & OCI

Given those primitives, who actually assembles them into a running pod? On each node a daemon called the kubelet is the local agent. It watches the control plane for pods bound to its node, and for each one it drives the container lifecycle: pull images, create the sandbox, start containers, run health probes, and continuously report status back. The kubelet does not create containers itself — it delegates to a container runtime through a stable gRPC interface called the CRI (Container Runtime Interface).

The runtime stack, layer by layer

  • CRI — a gRPC API with two services: RuntimeService (sandboxes, containers, exec) and ImageService (pull/list/remove images). It decouples the kubelet from any specific runtime, the way a driver interface decouples a kernel from a specific device.
  • containerd (a common high-level runtime that implements the CRI) — manages images, snapshots (the layered filesystem), and container lifecycle. It hands the actual process creation to a low-level runtime.
  • runc (the OCI reference low-level runtime) — the small program that does the raw kernel calls: set up namespaces, apply the cgroup, pivot into the image's root filesystem, drop capabilities, and exec the entrypoint. This is where the primitives from §2 are actually invoked.
The node runtime stack. The kubelet speaks CRI to a high-level runtime (containerd), which invokes an OCI low-level runtime (runc), which makes the kernel calls that build the container.

OCI images: the artifact

What gets pulled and run is an OCI image — an open, vendor-neutral format. An image is a manifest (JSON pointing to a config + a list of layers) plus layers (each a tarball of filesystem changes, content-addressed by digest) plus a config (entrypoint, env, working dir). The layers stack into the container's root filesystem via a union/overlay filesystem, so shared base layers are pulled and stored once. Content-addressing (a layer is named by the SHA-256 of its bytes) gives free deduplication and integrity checking.

Bridge

Think of an OCI image like an immutable, content-addressed build artifact in an artifact repository: layers are cached by digest exactly like dependency jars keyed by hash, and the overlay filesystem is a copy-on-write merge of those read-only layers plus one writable top layer for the running container.

CRI vs the control plane — don't conflate

The CRI is a node-local interface between the kubelet and a runtime. It is unrelated to the control-plane APIs (the scheduler, controllers, etcd) from Part XIII. A common interview slip is to say "the scheduler creates the container" — it doesn't; it only binds the pod to a node. The node's kubelet, via CRI, does the creating.

4. Exposing Special Hardware to Workloads

A stock node advertises CPU and memory, and the scheduler places pods against those. But accelerators, high-speed NICs, and other specialized devices are invisible to the base scheduler — the kernel sees a PCIe device, but Kubernetes has no built-in concept of "one inference accelerator." The device-plugin API is how a node teaches the cluster to see and allocate such hardware.

The one-sentence bridge

A device plugin is how the cluster "sees" special hardware: it is a small daemon on the node that discovers devices, advertises them to the kubelet as a countable, schedulable resource (e.g. example.com/accel: 8), and — when a pod is granted one — tells the runtime exactly which device nodes and environment to inject.

The device-plugin flow

  1. Register. The plugin (usually a DaemonSet, one per node) connects to the kubelet over a gRPC socket and registers under a resource name like example.com/accel.
  2. Advertise (ListAndWatch). It streams the list of healthy device IDs to the kubelet, which surfaces them as extended resources in the node's capacity. Now a pod can request resources.limits: example.com/accel: 2 and the scheduler treats it like any countable resource.
  3. Allocate. When the kubelet assigns devices to a pod, it calls the plugin's Allocate; the plugin returns the concrete device files, mounts, and environment variables the runtime must inject so the container can open exactly those devices — and no others.
# a pod requesting a specialized accelerator as an extended resource
resources:
  limits:
    example.com/accel: 2      # scheduler only places this on a node
                             # whose plugin advertises >= 2 free devices
Device-plugin lifecycle: the plugin advertises devices to the kubelet as a countable resource; the scheduler places pods against that count; Allocate injects the concrete device files into the granted container.

Topology matters: NUMA, Topology Manager & NFD

Advertising a device by count is not enough for performance. On a multi-socket server, an accelerator hangs off a particular PCIe root complex attached to one NUMA node; the CPU cores and memory that feed it should be on that same NUMA node, or every transfer pays a cross-socket hop. (NUMA is RAM data-locality — the same locality/sharding instinct you already apply to data, applied to which socket owns which memory and device.)

  • Topology Manager — a kubelet component that coordinates the CPU Manager, Memory Manager, and device plugins so a pod's cores, memory, and devices are all allocated from the same NUMA node when possible. Policies range from best-effort (try, but don't block) to single-numa-node (refuse to admit the pod unless it fits on one node).
  • Node Feature Discovery (NFD) — a daemon that inspects each node's hardware and kernel (CPU flags, PCIe devices, kernel version, NIC capabilities) and publishes them as node labels. Workloads then use node affinity to land only where a required capability exists — e.g. "schedule only where an RDMA-capable NIC is present."
Interview signal

"How does a pod get a specific accelerator?" → the device plugin advertises the device to the kubelet as an extended resource; the scheduler places the pod against that count; the kubelet calls Allocate, which injects the concrete device files. Then raise the bar yourself: "and for performance you want the Topology Manager to co-locate the pod's CPU, memory, and device on one NUMA node, with NFD labeling nodes by capability." That shows you understand allocation and locality.

5. Bare-Metal Bring-up: CI/CD for Physical Hardware

Before any of the above can happen, a physical machine has to become a node. Bring-up is the pipeline that takes a rack of powered-off, bare hardware and produces validated, cluster-joined nodes — repeatably, for hundreds or thousands of boxes. The guiding principle is that this is CI/CD for physical hardware: declarative desired state, idempotent steps, automated validation gates, and no manual, hand-crafted configuration.

The bring-up pipeline

The bare-metal bring-up pipeline: power-on through health-validated cluster join. Each stage is idempotent and gated; a failure routes the node to repair rather than into service.

1 — Power-on via the BMC (out-of-band)

You can't press a button on a thousand machines. Each server has a BMC (Baseboard Management Controller) — a tiny always-on computer on the motherboard, on its own management network, that can power the box on/off, read sensors, and mount virtual media even when the main OS is down or the box is "off." Fleet tooling drives it programmatically, historically via IPMI and increasingly via Redfish (a modern HTTPS/JSON REST API — structured resources instead of IPMI's opaque byte commands).

Bridge

The BMC is an always-on out-of-band admin sidecar: a separate little computer that manages the box independently of the main OS — the same pattern as a sidecar/agent that stays up to administer a service even when the service itself has crashed. Redfish is its clean REST API; IPMI is the older binary protocol it's replacing.

2 — Firmware configuration

UEFI/BIOS is the pre-OS "init" (covered in Chapter 1). Bring-up applies a declarative firmware profile: enable virtualization and the IOMMU (VT-d/AMD-Vi), set boot order to network-first, configure Secure Boot state, memory and NUMA options, and power/thermal policy. The goal is that every node of a given type has byte-identical firmware settings — configuration drift here causes maddening one-off failures later.

3 — OS install via NetBoot (ties to Chapter 1)

With network-first boot, the machine does a PXE / network boot: firmware gets an address over DHCP, is pointed at a boot server, downloads a bootloader and an installer/provisioning image over TFTP/HTTP, and installs (or boots a live provisioning environment). This is exactly the NetBoot mechanism from Chapter 1, now used as the OS-delivery step of bring-up. The installed image is standardized and version-pinned so every node starts from the same known-good baseline.

4 — Config: drivers, agents, kernel

Post-install, a declarative config step installs the pinned kernel, device drivers/firmware for accelerators and NICs, the container runtime, the node agent, and telemetry exporters (§6). Everything is versioned and idempotent — re-running converges to the same state rather than stacking changes.

5 — Burn-in & health validation

Before a node carries real work it must earn trust. Burn-in runs stress tests for a sustained period to surface infant-mortality failures (defective parts that fail soon after first being switched on): CPU/memory stressors, a full memory pass to surface bad DIMMs, storage I/O, thermal soak, and interconnect/link checks. Only a node that passes every gate proceeds.

6 — Join & go Ready

The validated node registers with the control plane, the node agent starts, and once its health checks pass the node is marked schedulable. It is now a first-class member of the fleet — and the loop from §1–§4 can begin placing pods on it.

Idempotent & declarative — why it's non-negotiable

At fleet scale, imperative "SSH in and run these commands" bring-up is unreproducible and drifts. Declarative desired-state provisioning (describe the target; let the tool converge) plus idempotency (re-running is safe and lands the same state) is what makes bring-up a pipeline and not a craft. It's the same reason infrastructure-as-code beat hand-clicked consoles.

"I'd model bring-up as a declarative, gated pipeline — power-on over the BMC via Redfish, apply a firmware profile, NetBoot a version-pinned OS image over PXE, converge drivers and agents idempotently, run burn-in stress and hardware validation as a gate, then join the cluster and go Ready. A failed gate quarantines the box for repair; nothing enters service unvalidated. It's CI/CD, but the artifact is a physical machine."

6. Fleet Telemetry & Hardware Health

A node that joined healthy doesn't stay healthy forever. Fleet operation depends on continuous telemetry — both the software-level metrics you know and the hardware health signals that a backend engineer rarely sees but that dominate physical-fleet reliability. This ties directly into the observability stack of Chapter 3; here we focus on what's node- and hardware-specific.

The exporter model

The prevailing pattern is a small exporter process per node that reads local counters and exposes them over HTTP for a time-series scraper to pull. A host node exporter surfaces OS-level metrics (CPU, memory, filesystem, network); additional exporters surface hardware sensors and device-specific counters. Because it's pull-based scraping of a plain HTTP endpoint, adding a node just means the scraper discovers one more target.

Hardware health signals that matter

Temperature (CPU, board, device, inlet)BMC sensors / deviceThermal excursions cause throttling (silent slowdown) or shutdown; a hot inlet can indicate a cooling failure across a rack.

Why ECC is the canary

ECC (Error-Correcting Code) memory detects and corrects single-bit errors transparently. The value for fleet health is the correctable error stream: a DIMM that starts logging a rising rate of corrected errors is usually on its way to an uncorrectable error (which crashes the machine or corrupts data). Watching correctable-ECC trends lets you drain and replace a DIMM on a maintenance schedule instead of eating an unplanned node crash — the hardware equivalent of acting on a rising error-rate metric before it pages you.

Closing the loop: health-driven remediation

Telemetry only helps if it drives action. A mature fleet ties these signals to automated remediation: a node crossing a health threshold is cordoned (marked unschedulable) and drained (its pods evicted and rescheduled elsewhere), then routed to an automated repair workflow — reseat/replace the flagged component, re-run burn-in (§5), and only re-admit on a pass. The out-of-band BMC path is essential here: it lets tooling power-cycle or reimage a stuck node whose main OS is unresponsive.

Interview signal

Mentioning hardware health — ECC error trends, thermal throttling, link flaps — and tying it to automated cordon/drain/repair shows you think about a physical fleet, not just pods. The phrase that lands: "correctable ECC errors are a leading indicator; we drain and replace proactively rather than wait for an uncorrectable crash."

7. Interconnect Topology as Context

This section is background, not the chapter's core — but you can't reason about topology-aware scheduling (§4) without a working picture of how devices and nodes are wired together. The theme: bandwidth and latency depend on the physical path, so where two things sit relative to each other changes performance by an order of magnitude.

Inside the box: PCIe and device-to-device links

  • PCIe topology. Devices attach through a tree of PCIe switches rooted at the CPU's root complex. Two devices under the same switch can talk with low latency; two devices on different root complexes (different NUMA nodes) must route through the CPU interconnect. This tree structure is exactly why the Topology Manager cares which NUMA node a device is on.
  • Device-to-device fabric (NVLink / NVSwitch). For accelerator-dense servers, NVIDIA's NVLink provides direct high-bandwidth links between accelerators, and NVSwitch is a switch chip that lets many accelerators in a box communicate at full bandwidth without funneling through the slower PCIe/CPU path. The scheduling consequence: a multi-device job runs far faster when its devices are mutually NVLink-connected than when traffic must fall back to PCIe.

Across boxes: InfiniBand, RDMA & RoCE

Between servers, high-performance fleets use RDMA (Remote Direct Memory Access): one machine reads or writes another machine's memory directly, with no involvement from the remote CPU and no copies through the kernel network stack.

The one-sentence bridge

RDMA = remote direct memory access with no CPU and zero copy: the NIC on one host transfers data straight into a pre-registered buffer in another host's memory, bypassing both kernels — the network analogue of DMA (a device writing memory directly, past the CPU) that you met in Chapter 2.

  • Transports. RDMA runs natively over InfiniBand (a purpose-built low-latency fabric) or over Ethernet via RoCE (RDMA over Converged Ethernet), which needs a lossless/well-configured Ethernet fabric to perform.
  • Verbs. Applications use the verbs API: register memory regions, create queue pairs (send/receive queues), and post work requests directly to the NIC. Completed transfers land in a completion queue the app polls — no syscall on the data path, the same "keep the kernel off the hot path" idea from low-latency systems.
  • GPUDirect RDMA lets a NIC DMA data straight into (or out of) an accelerator's memory over PCIe, skipping a bounce through host CPU memory entirely — so a distributed training/inference job can move tensors between accelerators on different servers with minimal CPU involvement and minimal copies.

The practical upshot for scheduling: a distributed job's collective operations (all-reduce and friends, e.g. via NCCL) are bottlenecked by the slowest link in the group. Placing the job's workers so they share fast intra-node NVLink and a common high-bandwidth RDMA fabric — rather than scattering them across distant nodes — is why topology-aware scheduling exists.

Keep this in proportion

Interconnect details are context for topology-aware placement, not the node-orchestration core. In an interview, one or two accurate sentences — "RDMA is zero-copy, no-remote-CPU memory access over InfiniBand or RoCE; collectives are gated by the slowest link, so you place workers to share NVLink and a common fabric" — is the right depth unless the role is specifically about networking hardware.

8. Validation & CI/CD for System Software

System software — firmware, kernel, drivers — sits underneath every workload, so a regression there can take down a whole fleet at once. The discipline that prevents this is the same one application teams use, applied to the lowest layers: automated validation and staged, gated rollout of every firmware/kernel/driver change.

The validation layers

LayerWhat it checksAnalogy
Component unit testsA driver or firmware module behaves correctly in isolation.Unit tests in a code CI pipeline.
Hardware validation suiteEvery device, link, and sensor on a node functions to spec (device enumerates, links train to expected width/speed, ECC works, thermals sane).Integration tests against real dependencies.
Stress / burn-inSustained load surfaces marginal hardware and thermal/power limits (§5).Load/soak testing before release.
Regression suiteA new kernel/driver/firmware doesn't lose performance or break a previously-working device.Regression tests gating a merge.

Regression-gating a fleet-wide change

You never push a new firmware or kernel to the whole fleet at once. The rollout is staged exactly like a well-run deployment pipeline:

  1. Lab / hardware-in-the-loop. Validate the change on every affected hardware SKU in a lab, running the full validation + regression suite. Firmware/driver behavior is SKU-specific, so coverage across hardware variants matters as much as code coverage.
  2. Canary. Roll to a small, representative slice of the production fleet and watch the telemetry from §6 (thermals, ECC rates, link errors, workload performance) for regressions.
  3. Staged expansion. Widen in waves, with automated health gates between stages — any regression halts the rollout.
  4. Automated rollback. Keep the previous known-good firmware/kernel image and a fast path back to it, because a bad low-level change can render nodes unbootable — which is exactly where the out-of-band BMC (§5) proves its worth, letting you reimage a node whose OS won't come up.
Why firmware/driver rollout is scarier than app rollout

A bad application deploy usually fails safely — the pod crash-loops and the control plane keeps the old version running. A bad firmware or kernel change can leave a node unbootable or subtly corrupt data, and it affects hardware you can't just "roll back" with a redeploy. That's why the gates are stricter, the canary is mandatory, per-SKU validation is essential, and out-of-band recovery is designed in from the start.

Interview signal

Framing firmware/kernel/driver changes as "CI/CD with hardware-in-the-loop validation, per-SKU coverage, canary + staged rollout gated on hardware telemetry, and out-of-band rollback for unbootable nodes" shows you'd treat the riskiest layer with the most rigor — the opposite of the naive "just flash all the nodes" answer.

9. Common Interview Questions

Q: What are cgroups and namespaces, really — and how do they make a container?
Namespaces isolate what a process can see (its own PID/mount/network/UTS/IPC/user/cgroup views), created via clone()/unshare(). cgroups (v2) limit and account what it can use (CPU, memory, I/O, pids) via a unified hierarchy under /sys/fs/cgroup. A container is just a process (tree) with both applied, sharing the host kernel — no guest kernel, no hypervisor. Key nuance: a CPU limit throttles, a memory limit OOM-kills.

Q: Walk me from a pod spec to a running process on the node.
The scheduler binds the pod to a node (control plane). The node's kubelet sees it and calls the container runtime over the CRI (gRPC). A high-level runtime like containerd pulls the OCI image (content-addressed layers → overlay root fs) and asks an OCI low-level runtime like runc to create the container: set up namespaces, apply the cgroup, pivot root into the image fs, drop capabilities, and exec the entrypoint. The kubelet then runs probes and reports status.

Q: How does a pod get a specific accelerator or high-speed NIC?
A device plugin (DaemonSet) discovers the devices and advertises them to the kubelet as an extended resource (e.g. example.com/accel: 8). A pod requests a count in its resource limits; the scheduler places it on a node with enough free devices; the kubelet calls the plugin's Allocate, which injects the concrete device files, mounts, and env into the container. For performance, the Topology Manager co-locates CPU, memory, and device on one NUMA node, and NFD labels nodes by hardware capability.

Q: Design a bare-metal bring-up pipeline.
Treat it as CI/CD for hardware, declarative and idempotent: (1) power-on via the BMC out-of-band using Redfish/IPMI; (2) apply a firmware profile (IOMMU, boot order, Secure Boot); (3) NetBoot a version-pinned OS over PXE (Chapter 1); (4) converge drivers, runtime, and agents idempotently; (5) run burn-in stress + a hardware-validation gate; (6) join the cluster and go Ready. A failed gate quarantines the box for repair; nothing unvalidated enters service. Keep a fast out-of-band reimage/rollback path.

Q: Why does NUMA / topology-aware scheduling matter?
Because memory, CPU cores, and devices attached to different sockets/root complexes are slower to reach across the interconnect. A pod whose cores, memory, and accelerator all sit on one NUMA node avoids cross-socket hops; a distributed job whose workers share fast NVLink and a common RDMA fabric avoids being bottlenecked by the slowest link. Count-based allocation isn't enough — locality is a first-order performance factor.

Q: What does RDMA buy a distributed job?
RDMA moves data directly between machines' memory with no remote CPU involvement and no copies through the kernel network stack (zero-copy, over InfiniBand or RoCE), using the verbs API with no syscall on the data path. GPUDirect RDMA extends this straight into device memory. For collective operations (all-reduce, etc.), that means dramatically lower latency and CPU overhead — and since collectives are gated by the slowest link, it's why you place workers to share the fastest interconnect.

Q: How would you safely roll out a firmware or kernel change to a fleet?
Validate on every affected hardware SKU in a lab (hardware-in-the-loop) with full validation + regression suites; canary on a small production slice watching hardware telemetry (ECC, thermals, link errors); expand in waves behind automated health gates; and keep a known-good image with out-of-band (BMC) rollback because a bad low-level change can leave nodes unbootable. Never flash the whole fleet at once.

One-line summary

Node-level orchestration is where intent becomes execution: a container is a process wearing namespaces (visibility) and cgroups (limits) on the shared host kernel (§2); the kubelet realizes pod specs by calling a runtime over the CRI to run OCI images (§3); device plugins plus the Topology Manager and NFD let workloads see and locally place special hardware (§4); bare-metal bring-up is declarative, idempotent, gated CI/CD that turns a powered-off box into a validated node — power-on over the BMC, firmware profile, NetBoot, converge, burn-in, join (§5); fleet health leans on hardware telemetry like ECC-error trends and thermals driving automated cordon/drain/repair (§6); interconnect topology (PCIe, NVLink/NVSwitch, InfiniBand/RDMA) is the context that makes topology-aware scheduling worthwhile (§7); and every firmware/kernel/driver change ships through hardware-in-the-loop validation, canary, and staged rollout with out-of-band rollback (§8).

TermMeaning
Control planeThe cluster layer that decides and records intent — API server, scheduler, controllers, etcd (Part XIII).
NodeA single machine that runs the work and realizes the control plane's intent close to the kernel.
NamespaceKernel feature that isolates what a process can see — its own PID, mount, network, UTS, IPC, user, and cgroup views.
cgroups v2Control groups, unified hierarchy — the kernel mechanism that limits and accounts what a process can use (CPU, memory, I/O, pids).
OOM killerOut-of-memory killer: the kernel terminates a process when its cgroup exceeds memory.max.
kubeletThe per-node agent that watches for bound pods and drives their container lifecycle.
CRIContainer Runtime Interface — the gRPC API between the kubelet and a container runtime.
containerdA high-level container runtime that implements the CRI, managing images, snapshots, and lifecycle.
runcThe OCI reference low-level runtime that makes the raw kernel calls to build a container.
OCI imageOpen Container Initiative image — a vendor-neutral manifest plus content-addressed layers plus config.
Device pluginA node daemon that discovers special hardware and advertises it to the kubelet as a countable, schedulable resource.
NUMANon-Uniform Memory Access — memory and devices attached to a given socket are faster to reach from that socket's cores.
Topology ManagerA kubelet component that co-locates a pod's CPU, memory, and devices on the same NUMA node.
NFDNode Feature Discovery — a daemon that inspects node hardware/kernel and publishes capabilities as node labels.
BMCBaseboard Management Controller — an always-on out-of-band controller that manages the box even when the main OS is down.
IPMI / RedfishOut-of-band management protocols: IPMI (Intelligent Platform Management Interface) is the older binary protocol; Redfish is the modern HTTPS/JSON REST API replacing it.
IOMMUInput-Output Memory Management Unit (VT-d / AMD-Vi) — enables safe device pass-through and DMA remapping.
PXEPreboot Execution Environment — network boot: firmware gets an address over DHCP and loads an OS image over TFTP/HTTP.
Burn-inSustained stress testing of a new node to surface infant-mortality hardware failures before it carries work.
ECC memoryError-Correcting Code memory — detects/corrects single-bit errors; rising correctable errors are a leading DIMM-failure indicator.
PCIePeripheral Component Interconnect Express — the tree of switches, rooted at the CPU, through which devices attach.
NVLink / NVSwitchNVIDIA's direct high-bandwidth accelerator-to-accelerator links (NVLink) and the switch chip connecting many (NVSwitch).
RDMARemote Direct Memory Access — one host reads/writes another's memory directly, with no remote CPU and zero copies.
InfiniBand / RoCERDMA transports: InfiniBand is a purpose-built low-latency fabric; RoCE is RDMA over Converged Ethernet.
GPUDirect RDMALets a NIC DMA data straight into or out of an accelerator's memory, skipping a bounce through host CPU memory.
