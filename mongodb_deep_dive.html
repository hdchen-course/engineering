The Document & BSON Model

MongoDB stores data as documents grouped into collections inside databases. A document is a set of field/value pairs — conceptually a JSON object — but on the wire and on disk it is encoded as BSON (Binary JSON), a length-prefixed binary format that adds types JSON lacks and makes traversal/skip fast.

📄 Why BSON, not plain JSON?
  • Richer types: BSON adds ObjectId, Date, Decimal128 (IEEE-754 128-bit decimal, exact for money), 32/64-bit ints, Binary, Timestamp, and Double — JSON only has number/string/bool/null/array/object.
  • Traversable: Each element is length-prefixed, so the server can skip a subdocument or array without parsing every byte.
  • Compact for numbers: integers and doubles are stored in fixed binary form instead of as text.
The 16 MB rule: a single BSON document is capped at 16 MB. This is the most important physical constraint driving schema design — it bounds how much you can embed. For larger blobs, use GridFS (which chunks files across documents) or object storage with a reference.
The _id field and ObjectId▶
  • Every document has a unique _id. If you don't supply one, the driver generates an ObjectId. It is the primary key and is automatically indexed with a unique index.
  • An ObjectId is 12 bytes: a 4-byte Unix timestamp (seconds), a 5-byte random value per process, and a 3-byte incrementing counter. It is roughly monotonic (ordered by creation second), which matters for insert locality and sharding.
  • You may use your own _id (e.g. a natural key or UUID) — but a monotonically increasing _id creates a write hotspot on the last B-tree page, and is a poor shard key for the same reason.
{
  "_id": ObjectId("665f0c1a9b3e2a0c1d4e5f60"),
  "sku": "TSHIRT-BLK-M",
  "name": "Black T-Shirt (M)",
  "price": NumberDecimal("19.99"),
  "tags": ["apparel", "unisex"],
  "attrs": { "color": "black", "size": "M" },
  "createdAt": ISODate("2026-01-15T10:30:00Z")
}
Storage engine: WiredTiger▶

WiredTiger has been the default storage engine since MongoDB 3.2. Key properties an interviewer expects you to know:

  • Document-level concurrency: writers take a lock at the document level (via optimistic MVCC), so concurrent writes to different documents in the same collection don't block each other.
  • MVCC + snapshots: readers see a consistent point-in-time snapshot without blocking writers — this underpins snapshot read concern and transactions.
  • Compression: block compression on by default (snappy; zstd and zlib available) plus prefix compression on indexes.
  • Journaling / durability: a write-ahead journal makes committed writes crash-recoverable; checkpoints flush a consistent snapshot to disk (roughly every 60s or by log size).

Schema Design: Embedding vs Referencing

MongoDB is "flexible schema," but that does not mean "no schema" — it means the schema lives in your access patterns. The core modeling decision is whether related data is embedded in one document or referenced across documents. Model for how you read and write, not for how the entities relate on paper.

Embed when…
  • Data is read together ("one round trip serves the screen").
  • The relationship is one-to-few and bounded (an order's line items, a user's addresses).
  • The child has no independent lifecycle — it doesn't need to be queried on its own.
  • You want atomicity: a single-document update is always atomic, giving you all-or-nothing for the whole embedded tree with no transaction.
Reference when…
  • The child set is unbounded or large (a product's reviews, a user's events) — embedding risks the 16 MB limit.
  • The entity is shared / queried independently (a product referenced by many orders).
  • Data changes at very different rates (avoid rewriting a huge document to update one hot counter).
  • You'd otherwise duplicate large data many times.
The unbounded-array anti-pattern. Embedding an ever-growing array (comments, events, IoT readings) into one document is the classic mistake: the document grows toward 16 MB, updates rewrite more and more data, and indexes on the array bloat. Cap embedded arrays, or reference/bucket instead.
Design patterns that make document modeling work▶
PatternWhat it doesUse when
SubsetEmbed only the "hot" few (e.g. last 5 reviews) in the parent; keep the full set in a referenced collection.You show a preview but rarely need the whole child set.
Extended referenceDuplicate a few frequently-read fields from a referenced doc (e.g. copy productName into the order line) instead of joining.Read-heavy paths where a $lookup per read is too costly. Accept controlled duplication.
ComputedStore pre-aggregated results (counts, sums, rollups) rather than recomputing on every read.Reads vastly outnumber the writes that change the value.
BucketGroup many small time-series events into one document per time window/device.High-volume time-series/IoT; avoids one-doc-per-reading overhead. (See also native time-series collections, 5.0+.)
OutlierHandle the rare "celebrity" document (millions of children) with an overflow flag/collection so the common case stays simple.Skewed distributions where a few parents are huge.
Tradeoff to state out loud in an interview: denormalization/duplication trades write complexity and consistency risk for read speed and fewer round trips. Because MongoDB gives you atomicity only within a single document for free, embedding is also a way to get atomic multi-field updates without a transaction.
Modeling relationship cardinalities▶
  • One-to-few: embed as an array of subdocuments.
  • One-to-many: reference — store the parent's _id on each child, index it.
  • One-to-squillions (unbounded): reference from the child to the parent only; never embed. Consider the outlier/bucket patterns.
  • Many-to-many: store an array of references on the side you query from (often both), or a dedicated join collection when you need attributes on the relationship itself.

Indexes & the ESR Rule

MongoDB indexes are B-trees. Without a supporting index a query does a collection scan (COLLSCAN in explain); with one it does an IXSCAN. Use db.coll.explain("executionStats") and watch totalDocsExamined vs nReturned — a healthy indexed query keeps them close.

Index types you must be able to name▶
TypeWhat it indexesNotes
Single fieldOne field, asc/desc.Direction is irrelevant for a single-field index (it can be scanned either way).
CompoundMultiple fields in order.Serves queries on any left prefix; order matters — see ESR below.
MultikeyAn array field.Created automatically when a field holds an array; one index entry per array element. A compound index may contain at most one array field.
TextString content for keyword search.Tokenizes + stems; one text index per collection. For real relevance search, Atlas Search (Lucene) is the modern option.
Geospatial2dsphere (GeoJSON on a sphere) / 2d (legacy planar).Powers $near, $geoWithin, $geoIntersects.
HashedHash of a field's value.Used for hashed sharding to spread writes evenly; supports equality, not range.
Wildcard$** or a subtree.For unpredictable/arbitrary field names; not a substitute for designed indexes.
TTLA date field, with expireAfterSeconds.A background thread deletes expired docs — sessions, caches, ephemeral data.
Partial / SparseOnly documents matching a filter (partial) or only docs that contain the field (sparse).Smaller, cheaper indexes; partial is the more general, preferred option.
UniqueEnforces uniqueness on the key.Can be combined with partial to enforce uniqueness only on a subset.
The ESR rule — compound index field order▶

The canonical MongoDB compound-index heuristic — worth committing to memory. Order the fields of a compound index as Equality → Sort → Range:

  1. Equality fields first — the exact-match predicates (field: value, $in). These narrow the scan to a contiguous slice of the index.
  2. Sort fields next — so the index already returns rows in the requested sort() order and MongoDB can skip an in-memory sort (avoiding a blocking SORT stage, which is limited to 100 MB unless allowDiskUse — since MongoDB 4.4 this is the shared blocking-sort limit for both find() and aggregation, and 6.0+ spills to disk past it by default).
  3. Range fields last — inequalities ($gt, $lt, $gte, ranges). A range "opens up" the scan, so anything after it can't be used to seek or to satisfy a sort.
// Query: orders for a customer, shipped, newest first, within a date range
db.orders.find({
  customerId: 1234,           // Equality
  status: "SHIPPED",          // Equality
  createdAt: { $gte: start, $lt: end }   // Range
}).sort({ createdAt: -1 })    // Sort

// ESR-ordered index:
db.orders.createIndex({ customerId: 1, status: 1, createdAt: -1 })
//   E: customerId, status   S/R: createdAt (serves both the sort and the range)
Why order matters: a compound index only serves a query if the query uses a left prefix of its keys. Putting a range field before a sort field forces MongoDB to do a separate sort. Equality-then-sort-then-range keeps the whole operation index-driven.
Covered queries: if every field the query needs (filter + returned projection) lives in the index, MongoDB answers from the index alone (totalDocsExamined: 0) — never touching documents. Exclude _id in the projection if it isn't in the index. This is the document-DB analogue of a covering index.

The Aggregation Pipeline

Aggregation processes documents through an ordered array of stages; each stage transforms the stream and feeds the next — like a Unix pipe. It is how MongoDB does group-bys, joins, reshaping, and analytics.

Common stages▶
StagePurpose
$matchFilter documents (like find). Put it first so it can use an index and shrink the stream early.
$groupGroup by an expression and accumulate ($sum, $avg, $push, $addToSet, …).
$project / $addFields / $setReshape: include/exclude/compute fields.
$sort / $limit / $skipOrder and paginate. $sort + $limit together let the engine keep only top-N.
$lookupLeft outer join to another collection.
$unwindFlatten an array into one document per element.
$facet / $bucketRun multiple sub-pipelines in one pass; bucket into ranges (histograms).
$merge / $outWrite results back to a collection (materialized views / ETL).
 
// Revenue per product category for shipped orders in 2026 Q1, top 5
db.orders.aggregate([
  { $match: { status: "SHIPPED",
              createdAt: { $gte: ISODate("2026-01-01"), $lt: ISODate("2026-04-01") } } },
  { $unwind: "$items" },
  { $group: { _id: "$items.category",
              revenue: { $sum: { $multiply: ["$items.qty", "$items.price"] } },
              orders:  { $addToSet: "$_id" } } },
  { $addFields: { orderCount: { $size: "$orders" } } },
  { $project: { orders: 0 } },
  { $sort: { revenue: -1 } },
  { $limit: 5 }
])
Performance rules for pipelines▶
  • Filter and sort early. A leading $match/$sort can use an index; the optimizer also tries to push a $match before a $project/$lookup automatically, but writing it early is clearer and safe.
  • Memory limit: each blocking stage (notably $group and $sort) holds up to 100 MB of RAM. In MongoDB 6.0+ a stage exceeding that spills to disk automatically (allowDiskUseByDefault=true); pre-6.0 it errored unless you passed allowDiskUse: true. Spilling is slower, and you can force the old error-instead-of-spill behavior per operation with allowDiskUse: false. $sort feeding a small $limit avoids the cap entirely.
  • $lookup is a join — index the foreign field (localField/foreignField or the joined pipeline's $match) and it uses a fast indexed nested-loop join. Without such an index, MongoDB 5.1+ may use a hash join (given enough memory) rather than a per-document collection scan, but an index on the foreign field is still the recommended fast path. On large datasets, denormalizing (extended reference) often beats $lookup.
  • Only the first $match/$sort (before any transforming stage) can leverage indexes; after a $group/$unwind the stream is synthetic.

Replica Sets & Elections

A replica set is MongoDB's HA unit: a group of mongod processes holding the same data. One is the primary (takes all writes); the rest are secondaries that replicate from it. This is how MongoDB provides redundancy and automatic failover.

Fig 1: A 3-member replica set. Secondaries tail the primary's oplog; members heartbeat to detect failure.
The oplog — how replication works▶
  • The primary records every write as an idempotent operation in the oplog (local.oplog.rs), a capped collection (fixed-size, rolls over).
  • Each secondary tails the oplog and applies operations in order, converging to the same state. Replication is asynchronous by default.
  • Idempotency matters: an update like "set x=5" is stored so it can be re-applied safely, which makes recovery and re-sync robust.
  • Oplog window = how far back the oplog reaches. If a secondary falls behind further than the window, it can no longer catch up incrementally and needs a full initial sync. Size the oplog for your peak write rate and maintenance windows.
Elections & failover▶
  • Members exchange heartbeats (default every 2 seconds). If the primary is unreachable past the election timeout (electionTimeoutMillis, default 10 seconds), secondaries call an election.
  • MongoDB uses a Raft-inspired protocol (replication protocol version 1). A candidate must win votes from a strict majority of voting members to become primary — this prevents split-brain (two primaries).
  • Majority math: a set of N voting members tolerates the loss of floor((N-1)/2) members and still elects a primary. So 3 members tolerate 1 failure; 5 tolerate 2. Use an odd number of voting members.
  • Member roles: priority biases which node becomes primary; hidden/delayed members serve backups/analytics without taking traffic; an arbiter votes but holds no data (use sparingly — it can't provide a w:majority data copy).
  • A former primary that rejoins with writes the new primary never received will roll back those un-replicated writes — the reason to use w:majority (below).
Arbiter caution: an arbiter lets you form a majority cheaply (e.g. 2 data + 1 arbiter) but holds no data, so it can't satisfy w:majority acknowledgment if a data node is down, and it weakens durability guarantees. Prefer three full data-bearing members.

Sharding — Horizontal Scale

Sharding partitions a collection's documents across multiple shards (each itself a replica set) so the dataset and throughput exceed one machine. Applications talk to a mongos router; config servers (their own replica set) hold the metadata mapping ranges of the shard key to shards.

Fig 2: mongos routes queries using config-server metadata; each shard is a replica set owning a set of chunks.
Choosing a shard key — what matters most▶

The shard key determines how documents distribute and which queries stay fast. A good key balances three properties:

  • High cardinality — many distinct values, so data can split into many chunks. (A boolean or a country field can't split beyond a handful of chunks.)
  • Low frequency / even distribution — no single value dominates, so no shard gets a disproportionate share.
  • Non-monotonic — an ever-increasing key (timestamp, ObjectId, auto-increment) sends every new insert to the same "max" chunk on one shard: a hot shard. Use a hashed shard key, or a compound key that leads with a well-distributed field, to spread writes.
StrategyDistributionRange queries
RangedBy contiguous key ranges. Can hotspot if the key is monotonic or skewed.Efficient — a range query is targeted to the few shards holding that range.
HashedEven, by hash of the key — great for write scaling.Poor — a range on the key must scatter-gather to all shards.
CompoundLead with a distributing field, add a field that queries target (e.g. { tenantId: 1, orderId: 1 }).Targeted when the query includes the leading prefix.
Targeted vs scatter-gather: if a query includes the shard key (or its prefix), mongos routes it to just the relevant shard(s) — a targeted query. If it does not, mongos must broadcast to every shard and merge results — a scatter-gather query, whose latency tracks the slowest shard and which doesn't scale with cluster size. Design the shard key so your highest-QPS queries are targeted.
Chunks, balancing, and hot shards▶
  • Sharded data is divided into chunks — contiguous shard-key ranges. Default chunk size is 128 MB (configurable). Modern MongoDB (6.0+) distributes data based on data size per shard rather than raw chunk count, and no longer auto-splits chunks the way older versions did.
  • The balancer runs in the background and migrates chunks between shards to keep them balanced, throttling to limit impact on live traffic.
  • Jumbo chunks: if too many documents share one shard-key value, a chunk can't split and grows unbounded — it's marked "jumbo" and can't be migrated, creating imbalance. This is a direct symptom of a low-cardinality/high-frequency key.
  • Hot shard: a monotonic shard key funnels all new writes to one shard regardless of how many shards you add — the classic sharding failure. Fix with hashed or compound keys.
  • Zone sharding pins key ranges to specific shards (e.g. by region for data-locality/compliance).
Evolving the key: since 4.4 you can refine a shard key by appending fields (refineCollectionShardKey); since 5.0 you can fully reshard a collection online (reshardCollection). Historically the shard key was immutable, so this used to be irreversible — worth mentioning that it's now recoverable but expensive.

Consistency: Write/Read Concern, Read Preference, Causal

MongoDB lets you tune the consistency/latency/durability tradeoff per operation with three independent (orthogonal) knobs. Interviewers may probe how the three knobs interact.

Write concern — durability of a write▶
Write concernAcknowledged when…Guarantee
w: 0Fire-and-forget (no ack).None — write may be lost. Rarely appropriate.
w: 1The primary has applied it.Durable on primary only — can be rolled back if the primary fails before replicating.
w: "majority" default (5.0+)A majority of data-bearing members have it.Survives failover — never rolled back. This is the safe default.
j: trueWritten to the on-disk journal (not just memory).Survives a process/power crash on the acknowledging nodes.
  • Add wtimeout so a write doesn't block forever if a majority can't be reached.
  • Since MongoDB 5.0 the default write concern is w: "majority" — a deliberate shift toward safety over raw speed. Before 5.0 it was w: 1.
Read concern — what you're allowed to see▶
Read concernReturns
local defaultThe node's most recent data — may include writes that could still be rolled back.
availableLike local but on sharded clusters may return orphaned docs; lowest latency, weakest guarantee.
majorityOnly data acknowledged by a majority — i.e. durable, won't be rolled back.
linearizableReflects all majority-acknowledged writes that completed before the read began; single-document, primary-only. Strongest, slowest.
snapshotA consistent point-in-time view across the operation — used by multi-document transactions.
Pairing for read-your-own-writes durability: w:"majority" writes + readConcern:"majority" reads guarantees you never see (nor lose) a write that later disappears. Combine with a causally consistent session to also get monotonic ordering across a secondary read.
Read preference — which member serves the read▶
Read preferenceRoutes reads toUse for
primary defaultPrimary only.Strong consistency / read-your-writes.
primaryPreferredPrimary, or a secondary if none.Availability during failover.
secondarySecondaries only.Offloading reads; tolerates staleness.
secondaryPreferredSecondaries, else primary.Read scaling with a fallback.
nearestLowest network latency member.Geo-distributed low-latency reads.
Secondary reads are eventually consistent. Because replication is async, a secondary can lag the primary. Reading from a secondary can return stale data and even non-monotonic results across requests. If you need "read my own write," read from the primary or use a causally consistent session.
Causal consistency▶
  • A causally consistent session guarantees that operations respect their causal order: read-your-writes, monotonic reads, monotonic writes, and writes-follow-reads — even when reading from secondaries.
  • It works by tracking a logical cluster time / operation time token in the session and having each operation wait until the target node has advanced past it.
  • Available since MongoDB 3.6 via client sessions. It's the right tool when you want to scale reads onto secondaries without exposing users to their own stale reads.

Multi-Document Transactions

A single-document write in MongoDB is always atomic, including updates to embedded arrays/subdocuments — which is why good document design removes the need for many transactions. When you genuinely must update several documents (or collections) atomically, MongoDB supports ACID multi-document transactions.

🔒 What you get, and when it arrived
  • Replica-set transactions since 4.0; sharded-cluster (distributed) transactions since 4.2.
  • Snapshot isolation: a transaction reads from a single consistent snapshot; other clients see none of its writes until commit (all-or-nothing).
  • Transactions use readConcern:"snapshot" and commit with a write concern (use w:"majority" for durability across failover).
  • Default time limit: a transaction that runs longer than transactionLifetimeLimitSeconds (default 60 seconds) is aborted — to bound the resources pinned by its snapshot.
const session = client.startSession();
try {
  session.startTransaction({ readConcern: { level: "snapshot" },
                             writeConcern: { w: "majority" } });
  await accounts.updateOne({ _id: from }, { $inc: { balance: -100 } }, { session });
  await accounts.updateOne({ _id: to   }, { $inc: { balance:  100 } }, { session });
  await session.commitTransaction();
} catch (e) {
  await session.abortTransaction();   // then retry on transient errors
} finally {
  session.endSession();
}
Use transactions sparingly. They add locking, coordination, and (on sharded clusters) two-phase-commit overhead, and long transactions pin snapshots and stress the storage engine. Prefer to design them away by embedding related data in one document. When you do use them: keep them short, touch few documents, and implement retry-on-transient-error logic (the driver marks retryable transient/commit errors with labels).
Retryable writes (default-on in modern drivers) are a lighter-weight guarantee: the driver safely retries a single write once through a brief network interruption without duplicating it, using a unique operation id. This covers many cases people reach for transactions to solve.

Worked Data Model: E-Commerce Orders

A concrete example that exercises every earlier decision. Requirements: show an order (with its line items) in one read; a product is referenced by many orders and has an unbounded stream of reviews; the storefront filters products by category and lists a customer's recent orders.

1. products — reference target, subset pattern for reviews
// products: queried on its own and referenced by orders → its own collection.
{
  _id: ObjectId("..."),
  sku: "TSHIRT-BLK-M",
  name: "Black T-Shirt (M)",
  category: "apparel",
  price: NumberDecimal("19.99"),
  attrs: { color: "black", size: "M" },
  ratingAvg: 4.6,           // COMPUTED pattern: pre-aggregated, updated on write
  ratingCount: 812,
  recentReviews: [          // SUBSET pattern: only the last few embedded for preview
    { user: "jdoe", stars: 5, text: "Great fit", at: ISODate("2026-02-01") }
  ]
}
// Full, unbounded review history lives in its own collection (referenced):
// reviews: { _id, productId, userId, stars, text, createdAt }
2. orders — embed line items, extended reference for product fields
// An order's items are one-to-few, bounded, and always read WITH the order → EMBED.
// We copy name/price into each item (EXTENDED REFERENCE) so rendering the order
// needs no $lookup, and the historical price is frozen at purchase time.
{
  _id: ObjectId("..."),
  customerId: ObjectId("...C1..."),
  status: "SHIPPED",
  createdAt: ISODate("2026-03-14T09:00:00Z"),
  total: NumberDecimal("59.97"),          // COMPUTED: denormalized for fast listing
  items: [
    { productId: ObjectId("...P1..."), name: "Black T-Shirt (M)",
      qty: 3, price: NumberDecimal("19.99"), category: "apparel" }
  ],
  shipTo: { line1: "...", city: "...", country: "US" }   // EMBED: no independent life
}
3. Indexes (ESR-driven) and shard key
// "a customer's recent shipped orders": E=customerId,status  S/R=createdAt
db.orders.createIndex({ customerId: 1, status: 1, createdAt: -1 })

// storefront filter "products in a category, cheapest first"
db.products.createIndex({ category: 1, price: 1 })

// reviews looked up by product, newest first
db.reviews.createIndex({ productId: 1, createdAt: -1 })

// SHARDING: customerId leads → a customer's orders are co-located (targeted reads),
// and customerId is high-cardinality & non-monotonic (no hot shard).
sh.shardCollection("shop.orders", { customerId: 1, _id: 1 })
Why this shape: the order screen is one document read (embedded items + copied product fields, no join). Products stay separate because they're shared and their reviews are unbounded. The compound index follows ESR so "recent orders" needs no in-memory sort. The shard key co-locates each customer's data so the hottest query is targeted, not scatter-gather — and it isn't monotonic, so writes spread across shards.

When to Use MongoDB — and When to Avoid It

Good fit
  • Evolving / semi-structured schemas; per-record variation (product catalogs, CMS, user profiles).
  • Data naturally shaped as documents read together (an order, a page, an event).
  • Need horizontal write scale with built-in sharding & HA replica sets.
  • High-volume ingest / time-series (native time-series collections, 5.0+).
  • Geospatial queries, and integrated full-text search via Atlas Search.
Reach for something else
  • Heavily relational, many-to-many with ad-hoc joins → a relational DB. $lookup exists but isn't a JOIN-first engine.
  • Complex multi-entity transactions as the norm → an RDBMS where transactions are the default, not the exception.
  • Large-scale OLAP / columnar analytics → ClickHouse / BigQuery / a warehouse.
  • Graph traversal (social graphs, recommendations) → a graph DB.
  • Pure key-value cache at sub-ms latency → Redis/Memcached.

Interview Q&A

Q: Embed or reference — how do you decide?
Model for access patterns. Embed one-to-few, bounded data that's read together and has no independent lifecycle (it also gives you free single-document atomicity). Reference when the child set is unbounded or large (16 MB doc limit), when the entity is shared or queried on its own, or when parts change at very different rates. Name the tradeoff: referencing costs a join/second round trip; embedding/duplicating costs write complexity and consistency maintenance.
Q: What is the ESR rule and why does field order matter?
Order compound-index fields Equality → Sort → Range. Equality predicates narrow to a contiguous index slice; sort fields next let the index return rows already ordered (no blocking 100 MB in-memory SORT); range fields last because an inequality opens the scan and nothing after it can seek or satisfy a sort. A compound index only helps queries using a left prefix of its keys.
Q: How do you pick a shard key, and what goes wrong?
Want high cardinality, low frequency, and non-monotonic values, and ideally include it in the hottest queries so they're targeted rather than scatter-gather. Failure modes: a monotonic key (timestamp/ObjectId) creates a hot shard because all inserts hit the max chunk on one shard; a low-cardinality key can't split, producing un-migratable jumbo chunks and imbalance. Fixes: hashed shard key (even writes, but range queries scatter) or a compound key leading with a distributing field. Since 5.0 you can reshard online if you got it wrong.
Q: Targeted vs scatter-gather query?
If the query carries the shard key (or its prefix), mongos routes it to only the shard(s) owning that range — targeted, scales with the cluster. If not, mongos broadcasts to every shard and merges — scatter-gather, bounded by the slowest shard and not scalable. Design the shard key so the highest-QPS queries are targeted.
Q: Walk me through an election.
Members heartbeat every ~2s. If the primary is unreachable past electionTimeoutMillis (default 10s), an eligible secondary becomes a candidate and requests votes under a Raft-inspired protocol (PV1). It needs a strict majority of voting members to win, which prevents split-brain. Priority biases who wins; use an odd number of voting members so N tolerates floor((N-1)/2) failures. A rejoining old primary rolls back any writes the new primary never received — which is why w:"majority" matters.
Q: How do write concern, read concern, and read preference differ?
They're independent. Write concern = durability of a write (w:1 primary-only and roll-back-able vs w:"majority" durable; j:true for journal). Read concern = what a read may see (local default, majority = won't-be-rolled-back, linearizable, snapshot for transactions). Read preference = which member serves the read (primary vs secondary/nearest). Note the 5.0 default write concern is majority; the default read concern is local and default read preference is primary.
Q: If I read from a secondary, can I read my own write?
Not guaranteed by default — replication is async so a secondary may lag. Either read from the primary, or use a causally consistent session, which tracks cluster/operation time so reads wait for the target node to catch up (read-your-writes + monotonic reads), even on secondaries.
Q: When do you actually need a multi-document transaction?
Rarely, if the schema is designed well — a single-document update (including embedded arrays) is already atomic. Reach for a transaction only for genuine cross-document/cross-collection invariants (e.g. money transfer between two accounts). Then keep it short, touch few docs, use w:"majority", mind the 60s default lifetime limit, and retry on transient/commit-error labels. Replica-set transactions landed in 4.0, sharded in 4.2. Consider retryable writes first for single-write resilience.
Q: What's the significance of the 16 MB document limit?
It's the hard cap on a single BSON document and the reason you can't embed unbounded data. It pushes you toward referencing, the subset pattern, and bucketing for growing collections (comments, events, time-series). For large binaries, use GridFS or external object storage with a reference.

Terminology & Acronyms

Quick reference for the key terms in this chapter.

TermMeaning
BSONBinary JSON — the length-prefixed binary format MongoDB uses to encode documents on the wire and on disk.
Document / CollectionA document is a set of field/value pairs (a JSON-like record); a collection is a group of documents, akin to a table.
ObjectIdThe 12-byte default _id: 4-byte timestamp + 5-byte random + 3-byte counter; roughly monotonic.
Decimal128IEEE-754 128-bit decimal BSON type; stores exact decimals, used for money.
WiredTigerThe default storage engine — document-level concurrency, MVCC snapshots, compression, and journaling.
MVCCMulti-Version Concurrency Control — readers see a point-in-time snapshot without blocking writers.
GridFSSpec for storing files larger than the 16 MB document limit by chunking them across documents.
ESR ruleEquality → Sort → Range — the recommended field order for a compound index.
Compound indexAn index over multiple fields; serves queries that use any left prefix of its keys.
Multikey indexAn index on an array field — one entry per element; a compound index may hold at most one array field.
Covered queryA query answered entirely from an index, examining zero documents (totalDocsExamined: 0).
COLLSCAN / IXSCANCollection scan vs index scan, as reported by explain.
Aggregation pipelineAn ordered array of stages that transform a document stream — group-bys, joins, reshaping, analytics.
$lookupAggregation stage that performs a left outer join to another collection.
Replica setA group of mongod processes holding the same data, providing redundancy and automatic failover.
OplogA capped collection of idempotent write operations that secondaries tail to replicate the primary.
ElectionA Raft-inspired majority vote among voting members that selects a new primary, preventing split-brain.
ShardingHorizontal partitioning of a collection's documents across multiple shards to scale beyond one machine.
Shard keyThe field(s) that determine how documents distribute across shards and which queries stay targeted.
mongosThe query router that directs operations to shards using config-server metadata.
Config serversA dedicated replica set holding the chunk-range-to-shard mapping metadata.
ChunkA contiguous shard-key range; the unit the balancer migrates (default 128 MB).
BalancerBackground process that migrates chunks between shards to keep data evenly distributed.
Targeted vs scatter-gatherA query carrying the shard key routes to specific shard(s) (targeted); one without it broadcasts to all shards (scatter-gather).
Write concernThe durability a write must reach before acknowledgment (w:1, w:"majority", j:true).
Read concernThe visibility guarantee for a read (local, majority, linearizable, snapshot).
Read preferenceWhich replica-set member serves a read (primary, secondary, nearest).
Causal consistencyA session guarantee that operations respect causal order (read-your-writes, monotonic reads) even on secondaries.
Multi-document transactionACID, snapshot-isolated update spanning multiple documents/collections; commits all-or-nothing.
