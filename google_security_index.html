Google Security Systems

Deep-dive reading guide & interview prep — for Security Backend / Silicon

In one picture — the big idea

Picture a giant, ultra-secure office building where every employee is a program and every room holds someone's data. The old way to stay safe was a strong wall around the whole building: get past the front door (the network) and you're trusted everywhere. That fails the moment one door is forced. Google's answer is the opposite — trust nothing by location; prove everything on every step.

Read from the ground up, the five systems are just the parts of that building:

  • Titan is a tamper-resistant ID chip welded into each machine at the factory, so a computer can prove it's a genuine, un-tampered Google box (not an impostor).
  • ALTS makes every hallway conversation happen inside a sealed, verified tube: both sides show ID and the talk is encrypted — even though they're inside the "safe" building.
  • BeyondProd is the guard who checks not just who you are but what job you're running and that your code was approved before letting you in a room.
  • KMS keeps every document in a locked safe, with the safe's key locked in a bigger vault, and that vault's key locked in an offline master vault.
  • Zanzibar is the master directory that, in a few milliseconds, answers one question for the whole planet: "Is this person allowed in this specific room?"

Tiny concrete example: you click "open" on a shared photo. Behind that one click, the machine proves it's genuine (Titan), the frontend calls the photo service over a sealed, mutually-verified channel (ALTS), the guard confirms the caller is approved code carrying your credential (BeyondProd), Zanzibar confirms you are on that photo's share list — the deciding check — and only then is the stored key unwrapped from its vault chain (KMS) so the bytes can be returned. (These five are a conceptual stack; walking them bottom-to-top explains the layers, but in practice the permission check runs before any data is decrypted.)

Jargon, decoded (you'll meet these below): root of trust = the one thing you trust absolutely because it's baked into hardware; attestation = a machine cryptographically proving "here is exactly what I am and what I'm running"; RPC = one program calling another over the network (a "remote procedure call"); zero-trust = verify identity on every call instead of trusting the network; provenance = proof of where a binary came from and that it was approved; envelope encryption = encrypt data with a key, then encrypt that key with another key (DEK wrapped by KEK); quorum = an action needs several trusted people together, never one; ReBAC = relationship-based access ("Alice is an editor of Doc 7"); QPS / p95 = queries per second / the latency 95% of requests beat.

How to use this guide

Five of Google's public security systems, each in its own deep-dive: what it is, where it's used, how it's designed, why that way, its hard problems, and how to reason about it in an interview. They're best read as one coherent story, not five isolated papers. Start with the one-diagram map below, then read in the suggested order.

Each doc closes with an Interview angle tab — reusable talking points and likely questions, framed as general principles you can reason from.

The system-of-systems map

These aren't five separate things — they stack. Hardware anchors machine identity; identity secures every RPC; a policy layer authorizes services and verifies their code; the data those services touch is encrypted with keys rooted in the same hardware/quorum discipline; and on top, a global service decides — at planet scale — whether a given user is actually allowed to touch a given object.

The common thread: "don't trust the network — trust hardware-rooted identity + provenance, and encrypt everything." Titan makes machine identity real; ALTS turns it into per-RPC service identity; BeyondProd authorizes services and verifies provenance; KMS keeps the data safe; Zanzibar decides whether the end user is allowed to touch the object — at planet scale. Being able to narrate this stack top-to-bottom is a staff-level signal.

Follow one request up the stack

One click ("open this shared file") touches every layer, bottom to top. Step through what each one contributes.

Interview angle: the highest-signal move here is to narrate the stack as one defense-in-depth story rather than five gadgets. A strong answer names what each layer would still protect if the layer below it were breached — e.g. "even if the network is fully owned, ALTS means the attacker can't impersonate a service; even with a valid service identity, BeyondProd still demands approved code provenance and a real end-user credential; even reading raw disk gives only ciphertext without KMS." That "assume breach, show the next line of defense" framing is exactly the zero-trust mindset interviewers probe for.

The five deep-dives

SYSTEM 01 · start here

Titan — Hardware Root of Trust

Google's custom secure chip. Secure boot via SPI-bus interposition, per-chip key at fabrication, offline quorum CA, remote attestation, firmware-identity-hashed-into-keys. The foundation the other four build on — read this first.
SYSTEM 02

ALTS — Application Layer Transport Security

Mutual auth + encryption for ~1010 internal RPCs/sec. Identity over hostname, Protobuf certs, 1-RTT DH handshake, boundary-aware encryption modes, session resumption, CRL revocation. The connective tissue of Google's production security.
SYSTEM 03

BeyondProd — Zero-Trust for Production Services

"BeyondCorp for services." Trust by code provenance + hardware + identity, not network location. Borg, Binary Authorization for Borg (BAB), GFE ingress, EUC tickets, gVisor. Ties ALTS + Titan into a coherent zero-trust model.
SYSTEM 04

Key Management & Encryption at Rest

Cloud KMS + Keystore. Envelope encryption (DEK wrapped by KEK), the master-key wrapping chain to an offline root, software/HSM/external protection levels, rotation without rewriting petabytes. A canonical key-hierarchy design.
SYSTEM 05 · security + backend scale

Zanzibar — Global Authorization at Scale

Google's planet-scale permission system: relation tuples (ReBAC), userset rewrite rules, zookies for consistency (the "new enemy problem"), Spanner, Leopard indexing, hot-spot handling, request hedging. >10M QPS, <10ms p95. The one doc that is both a security system and a large-scale backend — highest interview ROI.
BRIDGE NOTE · optional

Content Protection & Broadcast Encryption (AACS ↔ Titan)

Beginner primer: symmetric vs asymmetric/ECC, how Blu-ray/AACS lets many device keys open one disc (Media Key Block + subset-difference tree + revocation), and why "shared software key" is fragile vs "per-device hardware key." A career bridge from content-protection key management to hardware roots of trust.
TALKING POINT · optional

Memory-Safe Languages (Rust & the ~70% stat)

A "what's your view?" tech-chat card, not a whiteboard question: what memory safety means, the bug classes (buffer overflow, use-after-free), the striking stats (~70% of Microsoft CVEs, ~70% of Android high-severity vulns — peaking ~76% in 2019), why Rust matters (safety without a GC), the pragmatic trade-offs, and an honest interview framing. Covers a preferred-qualification topic.
DESIGN · Chapter 9

Device Provisioning & Identity

How a device earns a hardware-rooted identity and keys at the factory before it ever talks to the cloud: per-device PKI, attestation, factory trust models, and revocation. The manufacture-time root of trust that secure OTA later consumes.
DESIGN · Chapter 10

Secure OTA Updates

Updating software over-the-air across a whole fleet without bricking devices or letting an attacker push malicious code: signed images + chain of trust, anti-rollback, staged/canary rollouts, A/B atomic apply, and automatic recovery. The natural sequel to device identity.

Suggested reading order

  1. Titan — start here; it's the hardware root of trust everything else anchors on.
  2. ALTS — how hardware identity becomes service identity on every RPC.
  3. BeyondProd — how identity + provenance become an authorization model.
  4. KMS — how the data those services touch is protected, via a layered key hierarchy.
  5. Zanzibar — how authorization ("is this user allowed?") is served at planet scale with strong consistency. The security-meets-backend-scale capstone.

TermMeaning

BeyondProdGoogle's zero-trust model for production services — trust by code provenance, identity, and hardware, not network location.
KMS (Key Management Service)Google's system for creating, storing, and rotating encryption keys (Cloud KMS / Keystore).
ZanzibarGoogle's planet-scale authorization system that answers "is this user allowed?" from relation tuples.
