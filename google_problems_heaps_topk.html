Heaps, Top-K & Greedy — Google-style Problems

Six Google-style heap, top-K & greedy problems • original framing, execution-tested solutions, and interviewer probes

Note: Representative big-tech-style problems — not sourced from Google. The “Google-style” badge denotes the flavor of question, not its source.

Jump Game

Medium Google-style

Problem

You start at index 0 of an integer array nums. Each element is the maximum forward jump length from that position — standing on a value v lets you move to any index from the current one up to v steps ahead. Decide whether it is possible to reach the last index.

  • A zero means you cannot move at all from that seat; you are stranded unless an earlier jump already carried you past it.
  • The array is non-empty; a single-element array is trivially "already at the end."

Example: for nums = [3, 1, 2, 0, 4] the answer is true — from index 0 (value 3) you can reach index 3 directly, but that seat is a 0; instead jump 0→2 (value 2), then 2→4, landing on the last index. For nums = [2, 1, 0, 0, 4] the answer is false: the furthest you can ever reach is index 2 (0→1→2 gives reach 2); index 3 (a 0) is never landed on, so index 4 is unreachable → false.

Approach & Intuition

You never need to try individual jump lengths. Sweep left to right tracking a single number, reach — the furthest index reachable using everything seen so far. At each index i, if i has already slipped past reach, a gap of unreachable seats separates you from the goal, so return false. Otherwise standing on i extends your horizon to i + nums[i]; keep the maximum. If the sweep finishes without ever falling behind, the last index was reachable. This greedy frontier works because reachability is contiguous: if you can reach i, you can reach every index below it too.

// reach = furthest index reachable with the jumps seen so far.
public boolean canJump(int[] nums) {
    int reach = 0;
    for (int i = 0; i < nums.length; i++) {
        if (i > reach) return false;          // gap: index i is unreachable
        reach = Math.max(reach, i + nums[i]);   // extend the frontier
    }
    return true;                              // never fell behind -> last index reached
}

Complexity: Time O(n) — one pass, constant work per index. Space O(1) — a single running frontier.

Common pitfalls / interviewer probes: Greedy beats DP here — a memoised "can I reach the end from i?" recursion is O(n²) (each state scans its jump targets) and uses O(n) space; the greedy frontier collapses it to a single O(n) pass with one scalar. The i > reach guard must come first — check reachability of i before using nums[i], or you extend the frontier from a seat you could never stand on. Zeros are only fatal at the frontier — a 0 you have already jumped over is harmless; a 0 exactly at reach with more array ahead is what strands you. Single element — reach starts at 0 and the loop never trips, correctly returning true. A classic follow-up (Jump Game II) asks for the minimum number of jumps, which needs a second frontier tracking the current jump's boundary.

Meeting Rooms II

Medium Google-style

Problem

Given a list of meeting time intervals [start, end) (start inclusive, end exclusive), return the minimum number of rooms required so that no two overlapping meetings ever share a room. Equivalently, this is the maximum number of meetings that are simultaneously in progress at any instant.

  • Two meetings that merely touch — one ends exactly when the next begins — do not overlap and can reuse the same room.
  • The list may be empty (zero rooms) and intervals arrive in no particular order.

Example: for [[1, 9], [2, 5], [6, 8], [10, 12]] the answer is 2. The [1, 9] meeting spans the whole morning; [2, 5] overlaps it (2 rooms), then [6, 8] also overlaps [1, 9] (still 2, since [2, 5] has ended); [10, 12] starts after everything else is done and reuses a room. Peak concurrency is 2.

Approach & Intuition

Overlap only cares about when things start versus when things end, not which start pairs with which end. So split the intervals into a sorted list of start times and a sorted list of end times, then merge them chronologically with two pointers. Walk the starts: if the next meeting begins before the earliest not-yet-finished meeting ends (start[i] < end[j]), it needs a fresh room, so bump the room count. Otherwise a meeting has already freed up — advance the end pointer to reuse that room. Because the count is only ever incremented (never decreased), it settles on the highest concurrency ever reached, which is exactly the rooms needed. This is a min-heap of end times in disguise, with the sorted-end array playing the heap's role.

public int minMeetingRooms(int[][] intervals) {
    int n = intervals.length, rooms = 0;
    int[] start = new int[n], end = new int[n];
    for (int i = 0; i < n; i++) {          // split into start / end streams
        start[i] = intervals[i][0];
        end[i]   = intervals[i][1];
    }
    Arrays.sort(start);                     // process events in time order
    Arrays.sort(end);
    for (int i = 0, j = 0; i < n; i++) {
        if (start[i] < end[j]) rooms++;    // starts before earliest end -> new room
        else j++;                          // a meeting ended first -> reuse its room
    }
    return rooms;
}

Complexity: Time O(n log n) — dominated by the two sorts; the merge is a single linear pass. Space O(n) for the two extracted arrays. The heap variant is the same O(n log n) time but O(k) extra space where k is the peak concurrency.

Common pitfalls / interviewer probes: Half-open intervals — the strict start[i] < end[j] (not <=) is what lets a meeting ending at 5 hand its room to one starting at 5; using <= would over-count on back-to-back meetings. Why never decrement — the else branch consumes one start and one end together (both pointers advance), so it leaves concurrency unchanged; only the if branch raises it, so rooms naturally records the peak. Don't pair each start with its own end — decoupling the two sorted streams is the key insight; keeping intervals whole and comparing them pairwise is the O(n²) trap. Empty input — n = 0 skips the loop and returns 0; the end pointer j is only read when i < n, so it never runs off the array. A common follow-up is the min-heap formulation (push each end time, pop when a room frees) or returning the actual room assignment per meeting.

K Closest Points to Origin

Medium Google-style

Problem

Given an array of points on the plane, points[i] = [x, y], and an integer k, return the k points closest to the origin (0, 0) by Euclidean distance. The answer may be returned in any order, and when distances tie any valid choice is accepted.

  • Compare by squared distance x² + y² — the monotonic square root is unnecessary and only invites floating-point error.
  • Assume 1 ≤ k ≤ points.length; when k equals the length, every point is returned.

Example: for points = [[2, 3], [-1, 1], [4, 0], [0, -1]] and k = 2, the squared distances are 13, 2, 16, 1. The two smallest are [0, -1] (distance 1) and [-1, 1] (distance 2), so the answer is [[-1, 1], [0, -1]] (order irrelevant). With k = 1 only [0, -1] is returned.

Approach & Intuition

Maintain a bounded max-heap of size k, keyed on squared distance so the farthest of the current candidates sits at the top. Offer each point; whenever the heap grows past k, poll off the top to evict the current farthest. After processing every point, the heap holds exactly the k nearest. Because the heap never exceeds k elements, each insert/evict costs O(log k) rather than O(log n) — a real win when k ≪ n, and the reason a size-k heap is preferred over sorting all points.

// Squared distance to the origin; use long so large coordinates can't overflow.
private long dist(int[] p) { return (long) p[0] * p[0] + (long) p[1] * p[1]; }

public int[][] kClosest(int[][] points, int k) {
    // Max-heap: the farthest candidate seen so far is at the top.
    PriorityQueue<int[]> heap = new PriorityQueue<>(
        (a, b) -> Long.compare(dist(b), dist(a)));
    for (int[] p : points) {
        heap.offer(p);
        if (heap.size() > k) heap.poll();     // over capacity: drop the farthest
    }
    int[][] res = new int[heap.size()][2];
    for (int i = 0; i < res.length; i++) res[i] = heap.poll();
    return res;
}

Complexity: Time O(n log k) — n points, each an O(log k) heap operation. Space O(k) for the heap. A quickselect (Hoare partition) alternative reaches O(n) average time but degrades to O(n²) worst case and reorders the input in place.

Common pitfalls / interviewer probes: Max-heap, not min-heap — to keep the k smallest you evict the largest, so the comparator must put the farthest on top (dist(b) vs dist(a)); flipping it keeps the k farthest points instead. Skip the square root — ordering by x² + y² gives the same ranking as true distance and avoids double precision bugs on ties. Overflow — compute the squared distance in long: although the classic ±10⁴ coordinate bound keeps x² + y² (≤ 2×10⁸) within a 32-bit int, coordinates beyond roughly ±3.3×10⁴ make x² + y² exceed Integer.MAX_VALUE — using long is the safe default and also avoids comparator-subtraction overflow. k = n — the heap never exceeds n, nothing is evicted, and all points are returned. Interviewers often push toward the quickselect solution for O(n) average time, or ask how you would handle a stream of points, where the bounded heap shines because it holds only k at a time.

Kth Largest Element in an Array

Medium Google-style

Problem

Given an integer array nums and an integer k, return the k-th largest element — the value that would sit at position k counting down from the maximum. This is the k-th largest by rank, not the k-th distinct value: duplicates each occupy their own rank, so in [5, 5, 5] the 2nd largest is still 5. Aim for better than a full sort.

  • 1 ≤ k ≤ nums.length; k = 1 asks for the maximum, k = n for the minimum.
  • Values may repeat and may be negative; the array is not sorted.

Example: for nums = [7, 4, 10, 2, 10, 8] and k = 3 the answer is 8. Sorted ascending the array is [2, 4, 7, 8, 10, 10]; the two 10s are the 1st and 2nd largest, so the 3rd largest is 8 — note the duplicate 10 consumes a rank rather than collapsing.

Approach & Intuition

The k-th largest element is exactly the element that lands at ascending index n - k once the array is ordered. Rather than fully sorting, use Quickselect: partition around a pivot, which drops the pivot into its final sorted slot p and puts all smaller-or-equal values to its left. If p equals our target index n - k we are done; otherwise recurse into just the side that contains the target. Choosing a random pivot keeps the expected work linear on distinct-valued inputs; on duplicate-heavy arrays a two-way partition still degrades, so a three-way (Dutch-national-flag) partition is what keeps it linear there.

public int findKthLargest(int[] nums, int k) {
    // The k-th largest sits at ascending index n - k.
    int n = nums.length, target = n - k;
    int lo = 0, hi = n - 1, p;
    while (target != (p = partition(nums, lo, hi))) {
        if (target < p) hi = p - 1;   // pivot too big: search left
        else            lo = p + 1;   // pivot too small: search right
    }
    return nums[target];
}

// Lomuto partition around a RANDOM pivot. Returns the pivot's
// final index; every value <= pivot ends up on its left.
private final Random rand = new Random();
private int partition(int[] nums, int lo, int hi) {
    int p = lo + rand.nextInt(hi - lo + 1);  // pick pivot
    swap(nums, hi, p);                        // park it at hi
    int small = lo - 1;
    for (int i = lo; i < hi; ++i)
        if (nums[i] <= nums[hi]) swap(nums, ++small, i);
    swap(nums, ++small, hi);                  // pivot to its slot
    return small;
}

// plain temp swap: idiomatic, and a self-swap (i == j) is a harmless no-op
private void swap(int[] nums, int i, int j) {
    int t = nums[i];
    nums[i] = nums[j];
    nums[j] = t;
}

Complexity: Time expected O(n) with a random pivot (each round shrinks the search range by a constant fraction on average); worst case O(n²) if pivots repeatedly split off just one element — a random pivot makes that vanishingly unlikely for distinct values, but a two-way (Lomuto) partition still hits O(n²) on duplicate-heavy input, where a three-way partition is needed to restore linear expected time. Space O(1): the selection is iterative and in place, with no recursion stack. A heap-based alternative is O(n log k) time and O(k) space.

Common pitfalls / interviewer probes: (1) Rank, not distinct value — the target index is n - k, and duplicates each hold a rank; folding them together silently returns the wrong answer on inputs like [10, 10, 8]. (2) Self-swap must be safe — the random pivot can already sit at hi, so swap(i, i) happens; a plain temp swap makes it a harmless no-op (an XOR swap would instead zero the slot, which is why the idiomatic temp swap is preferred here). (3) Random, not fixed, pivot — a first/last-element pivot degrades to O(n²) on already-sorted input, a classic worst case interviewers reach for. (4) Recurse into only the side holding the target; scanning both sides re-derives a full sort and forfeits the linear expected time.

Minimum Cost to Hire K Workers

Hard Google-style

Problem

There are n workers; worker i has a quality[i] and a minimum acceptable wage[i]. You must hire exactly K workers and form one pay group under two rules: (1) within the group every worker is paid in proportion to their quality, and (2) every worker is paid at least their minimum wage. Return the least total amount needed to hire any valid group of K.

  • A group's pay rate (money per unit quality) is forced to be at least max(wage[i] / quality[i]) over its members — the most "expensive per quality" worker sets the rate.
  • Total cost of a group is therefore rate × (sum of qualities).

Example: for quality = [3, 5, 8, 2], wage = [15, 20, 40, 12], K = 2 the answer is 30.0. The wage/quality ratios are 5.0, 4.0, 5.0, 6.0. Pairing the workers with quality 3 and quality 2 fixes the rate at max(5.0, 6.0) = 6.0, giving 6.0 × (3 + 2) = 30.0 — and each is paid at least their minimum (18 ≥ 15, 12 ≥ 12). No other pair is cheaper.

Approach & Intuition

Fix the pay rate by fixing which worker has the highest ratio in the group. Sort workers by wage / quality ascending and sweep; the current worker's ratio is the group rate for any group whose members all appear at or before it. Among those candidates we want the K with the smallest total quality (cost is rate × sumQuality). Keep a running max-heap of qualities of size K: whenever it overflows, evict the largest quality. Each time the heap holds exactly K qualities, the current ratio is a valid rate and sumQuality × rate is a candidate answer.

public double mincostToHireWorkers(int[] quality,
                                   int[] wage, int K) {
    int n = quality.length;
    // Each worker as [ wage/quality ratio, quality ].
    double[][] worker = new double[n][2];
    for (int i = 0; i < n; ++i)
        worker[i] = new double[]{
            (double) wage[i] / quality[i], quality[i] };
    // Ascending by ratio: the current worker fixes the group's
    // pay rate (the largest ratio seen so far in the window).
    Arrays.sort(worker, (a, b) -> Double.compare(a[0], b[0]));

    // Max-heap of qualities: shed the largest to retain the K
    // smallest-quality members under the current rate.
    PriorityQueue<Integer> heap =
        new PriorityQueue<>(Collections.reverseOrder());
    double best = Double.MAX_VALUE;
    int sumQ = 0;
    for (double[] r : worker) {
        double rate = r[0];
        int q = (int) r[1];
        sumQ += q;
        heap.offer(q);
        if (heap.size() > K) sumQ -= heap.poll();  // drop worst
        if (heap.size() == K)
            best = Math.min(best, sumQ * rate);
    }
    return best;
}

Complexity: Time O(n log n) — the ratio sort dominates; the sweep does n heap operations, each O(log K), for O(n log K). Space O(n) for the paired ratio/quality array plus O(K) for the heap.

Common pitfalls / interviewer probes: (1) Why sorting by ratio works — fixing the group's highest-ratio worker fixes the rate; because we sweep ratios ascending, every earlier worker is affordable at that rate, so we are free to pick the cheapest-quality K among them. (2) Max-heap, evict the largest quality — the rate is fixed by the ratio, so cost falls with total quality; a min-heap or keeping the largest qualities inverts the optimisation. (3) Only score when the heap is full — a group must have exactly K members; scoring before the heap reaches size K undercounts the quality sum. (4) Use floating-point comparison for the ratio sort and beware integer division — compute (double) wage[i] / quality[i], not integer wage[i] / quality[i], or ties and ordering collapse. A common follow-up asks for the actual roster, or to stream workers online.

Merge k Sorted Lists

Hard Google-style

Problem

You are given an array of k singly-linked lists, each already sorted in ascending order. Merge them into one sorted linked list and return its head. The lists may be empty, the array itself may be empty, and values may repeat across lists.

  • An empty input array returns null; an array of all-empty lists also yields an empty result.
  • Total node count N can be large, so an approach better than repeatedly scanning all k heads is expected.

Example: for lists [2→7], [1→5→9], [], [3→4→8] the merged result is 1→2→3→4→5→7→8→9. The empty third list contributes nothing, and values interleave across the remaining three.

Approach & Intuition

Merging two sorted lists is a linear zipper. To combine k of them cheaply, merge in a bottom-up, pairwise tournament: first merge neighbours (0,1), (2,3), …, then merge the results (0,2), (4,6), …, doubling the stride each round. After about log₂k rounds everything has collapsed into slot 0. Reusing the input array as scratch keeps it fully in place — no priority queue and no recursion. Each node is touched once per round, and there are log₂k rounds.

/* ListNode: int val; ListNode next; -- standard singly-linked node. */
public ListNode mergeKLists(ListNode[] lists) {
    if (lists.length == 0) return null;
    int n = lists.length;
    // Bottom-up merge, doubling the stride each round:
    // merge (0,1),(2,3)...  then (0,2),(4,6)...  in place.
    for (int step = 1; step < n; step <<= 1)
        for (int i = 0; i + step < n; i += step << 1)
            lists[i] = merge(lists[i], lists[i + step]);
    return lists[0];
}

// Zip two sorted lists onto a dummy-headed chain.
private ListNode merge(ListNode a, ListNode b) {
    ListNode dummy = new ListNode(), tail = dummy;
    while (a != null && b != null) {
        if (a.val <= b.val) { tail.next = a; a = a.next; }
        else               { tail.next = b; b = b.next; }
        tail = tail.next;
    }
    tail.next = (a != null) ? a : b;   // attach the remainder
    return dummy.next;
}

Complexity: Time O(N log k) where N is the total number of nodes and k the number of lists — each of the log₂k rounds re-touches every node once. Space O(1) auxiliary: merging is iterative (no recursion stack) and the input array is reused, so only the dummy handles and a few pointers are allocated. This beats the naive O(Nk) of merging one list at a time and matches the O(N log k) of a k-way heap while using constant extra space.

Common pitfalls / interviewer probes: (1) Odd counts and stragglers — the guard i + step < n leaves an unpaired list untouched this round; it is correctly absorbed in a later, wider round. Getting the loop bounds wrong drops or double-merges a list. (2) Empty and null cases — an empty array must return null, and merge must accept empty (null) operands; the dummy head plus the final tail.next attach handle both uniformly. (3) Terminate the tail — the surviving list is already null-terminated, so attaching the remainder finishes the chain; forgetting the attach truncates the result. (4) The naive alternative — merging list 2 into list 1, then list 3, … — is O(Nk); the doubling schedule is what buys the log k. A frequent follow-up compares this against a min-heap of the k current heads.
