Handling Ambiguity in Design Rounds

These prompts are ambiguous by design. Here is the pattern and the framework that turns emptiness into signal.

A typical data-platform loop has one signature: the design rounds give you almost nothing to work with on purpose — that emptiness is the question. The coding round is usually lost not to the algorithm but to communication. Below is the failure-mode breakdown, then the reusable machinery so the loop doesn't feel like guessing.

INSIGHT

Data-platform design loops grade a specific muscle: can you convert a vague wish into a concrete, defensible spec — out loud, in real time. The "right answer" is rarely a system; it's the path you take to define the system. Whoever fills the silence with structured questions is the one who reads as senior (L5/L6).

Round-by-round breakdown

SD1Extreme-ambiguity dashboard: "leadership just wants a dashboard"SYSTEM DESIGN▶

The prompt: essentially one sentence — the boss wants to see a dashboard — and "what would you put in it?" No audience, no product, no metric, no decision. Total ambiguity. The instinct is to start naming charts. That instinct is the trap: a dashboard is a decision surface, and you cannot pick metrics before you know whose decision they serve.

The concrete lesson

  • Drive, don't receive: immediately reframe from "what charts" to "who acts on this, and what action changes based on the number."
  • Anchor on one persona: an on-call SRE, a PM, and a VP need three different dashboards. Force a choice, state it, move.
  • Metrics follow decisions: every tile must map to a decision or it's decoration. "If this goes red, someone does X" is the acceptance test for each metric.
  • Name the plumbing last: serving from Bigtable/BigQuery, metrics via Monarch, freshness SLO, pre-aggregated rollups vs. live queries — but only after the "what" is nailed.
TIP

Say the audience and the decision back to the interviewer as a stated assumption, then ask them to confirm or redirect. That single move converts ambiguity into a contract and shows you drive, not stall.

SD2Scalable mobile-data pipeline + the "swap the algorithm" twistSYSTEM DESIGN▶

The prompt: design a pipeline that ingests mobile data, computes/aggregates it, and scales. Thin context by design. Then the twist: "today we change the method/algorithm — how do you add a new pipeline?" The specific algorithm is deliberately never given, and that is the point. The round isn't testing whether you know a particular computation; it tests whether the design is algorithm-agnostic — whether swapping or adding a computation is cheap.

The concrete lesson — design for the swap before you're asked

  • Separate transport from logic: ingest (Pub/Sub) → durable log → pluggable compute stage → sink (Colossus/BigQuery). The computation is a strategy behind a stable interface, not built into the DAG (directed acyclic graph — the pipeline's task graph).
  • Algorithm as a versioned plugin: a new algorithm is a new Dataflow/Beam transform implementing the same (input schema) → (output schema) contract; adding one is config + deploy, not a rewrite.
  • Fan-out for A/B and backfill: because logic is decoupled, you can run algo v1 and v2 in parallel off the same source log, compare outputs, and backfill by replaying the log — no re-ingest.
  • Stable contracts at the seams: schema versioning + a registry so old and new pipelines coexist; that's what makes "add a new pipeline" a bounded change.
  • Then talk scale/quality/cost: partition mobile data by device/region, late-arrival + watermarks, dedup on at-least-once delivery, and the cost of storing raw vs. aggregated.
INSIGHT

The "change the algorithm" twist is a rigged test: if your first design already isolates computation behind an interface, the twist is a five-second answer. If you hardcoded the algorithm into the DAG, the twist forces a redesign in front of the interviewer. Build extensibility in from minute one so the twist rewards you instead of exposing you.

DSUUnion-Find coding — and the communication breakdown that can cost itCODING▶

The failure mode: the problem is Disjoint Set Union / Union-Find — very learnable. But a classic way to lose it is a comm breakdown: audio drops mid-round, the interviewer can't hear you and doesn't acknowledge, and the channel silently dies. Without the two-way loop it's easy to misread the direction and code the wrong thing. That is a communication loss, not an algorithm loss — and it is entirely preventable.

The concrete lesson — the channel is a graded axis

  • Silence is a signal, not a green light: if the interviewer goes quiet for more than a beat, assume the channel is broken, not that you're doing great.
  • Fall back to the shared editor instantly: if audio might be down, type your approach in the code pane — "Can you hear me? I'll restate my plan here in comments." The editor is the one channel that can't silently fail.
  • Confirm the problem before coding: restate the input/output and the approach in one line and get an explicit "yes" before writing the algorithm. A 20-second confirm would have saved the whole round.
  • Pre-flight the setup: test mic, screen-share, and editor in the first minute; keep a phone dial-in number ready as a backup line.
"I want to confirm you can hear me — if not, tell me in the doc and I'll drive everything in the editor. Before I code: input is X, output is Y, approach is Union-Find with path compression + union by rank. Good to start?"

The ambiguity-driving framework

Run this in order on any underspecified prompt. Say each layer out loud; state assumptions instead of waiting for permission.
1 · Audience

Who literally opens this and how often? SRE at 3am, PM weekly, VP quarterly — each implies a different artifact. Pick one and name them.

Key: "Who is this for?" before anything else.
2 · Decisions

What action does that person take from it? No decision → no feature. This is the guiding principle every metric answers to.

Key: Every tile ties to a decision or it's cut.
3 · Metrics

The smallest set of numbers that drive those decisions — plus their freshness, granularity, and "what does red mean" threshold.

Key: Metrics are derived, not brainstormed.
4 · Scope & scale

Volume, latency SLO, real-time vs. batch, data quality (dedup, late arrival), and cost of the chosen freshness. Bound the problem explicitly.

Key: State the SLO; it forces the architecture.
5 · Assumptions aloud

Voice every gap-fill as "I'm assuming X — correct me." Turns ambiguity into a contract and invites the interviewer to steer.

Key: Stated assumption > silent guess.
TRAP

The #1 failure mode: passively waiting to be told what to build. When the prompt is empty, candidates freeze or ask "what do you want?" — which reads as "I can't operate without a spec," the exact opposite of the L5 signal. Ambiguity is not missing information; it is the interviewer handing you the pen. Fill the void with structured, stated decisions and let them redirect. Driving the wrong direction confidently and correcting on feedback beats standing still.

Say-this openers for ambiguous prompts

"Let me drive this: who looks at this dashboard, and what decision do they make from it? I'll assume it's an on-call SRE deciding whether to page — tell me if the real audience is leadership instead."
"Before I pick metrics, I'll define the one decision this surface exists to support. Everything on it earns its place by feeding that decision."
"I'll design the compute step as a pluggable stage behind a fixed input/output contract — so when we swap the algorithm later, adding a pipeline is a new transform plus config, not a redesign. Let me state that interface now."
"I'm going to state my assumptions as I go and keep moving — stop me the moment one is wrong so I'm driving in your direction, not mine."
NOTE

Both design rounds reward the same instinct — convert vagueness into an explicit, extensible contract — and the coding round is a reminder that the contract with the interviewer (that you're heard and aligned) is the one you can't afford to let fail silently. Same skill, three surfaces.

Driving the Ambiguity

Turn "leadership wants a dashboard" into a requirement set before drawing a single box.
NOTE

Three vague asks — "a dashboard," "a scalable pipeline," "the algorithm will change" — are withheld on purpose in two flavors: the dashboard is under-specified on purpose (no audience/decision/metric), the pipeline is under-specified on substance & stability (no schema, no number, and the method-change is buried). The exam is whether you treat the vagueness as the work.

The signature move: reframe "build a dashboard" as "who decides what, from which number, how fresh?" and reframe "scalable pipeline" as "the method is the one guaranteed change, so it is the one thing behind an interface." Being wrong about the metric must be cheap.

WATCH

Tricky follow-up incoming: "Leadership loves it — now the growth PM wants the same dashboard per-experiment and hourly." If you built the exec view into the pipeline, this is a rewrite. Answer it in advance: audience is a serving-layer concern (role-scoped views + a granularity dimension), never a pipeline concern.

What Goes in the Dashboard

Layered views off one source of truth — exec KPIs on top, trust signals underneath.

I don't build "a dashboard." I build layers, because the exec and the on-call engineer ask different questions. Every tile carries metric_name @ method_version so a reader always knows which definition they're seeing.

L1Business / Leadership KPIsEXEC▶
  • Active users: DAU / WAU / MAU and the DAU/MAU stickiness ratio.
  • Retention curve: D1/D7/D30, sliced by app_version and country.
  • Sessions: session length / sessions-per-user — only after sessionization is agreed.
  • Version tag: e.g. "Retention · v3 (official)". Non-negotiable.
L2Pipeline Health / Freshness / VolumeON-CALL▶
  • Freshness SLO: "data complete through <timestamp>"; target exec tables complete by 06:00 local (lag < 6h).
  • Ingest: events/sec vs. 7-day baseline; Pub/Sub oldest-unacked-message age.
  • Compute: Dataflow system lag, autoscaling worker count, backlog depth, dead-letter size.
L3Data QualitySCIENCE + ON-CALL▶
  • Duplicate rate (dropped by event_id): expect ~1–3% from client retries.
  • Late-arrival distribution: % arriving >24h / >72h after event-time — drives restatement.
  • Null/malformed rate per field; clock-skew (event-time vs. ingest-time) p50/p99.
  • Method-vs-method delta: when v4 is shadowed, show |v4−v3| per metric, flag if >5%.
L4Infra / CostFINOPS▶
  • BigQuery bytes scanned/day and $/day; Colossus/GCS storage by tier; backfill job cost.
  • This is how you answer "spend doubled" before finance asks.
TRAP

Retention is not a cheap slice. "Cluster by app_version, country so exec queries scan MBs" is true for a DAU rollup but not for D1/D7/D30 retention — retention is a self-join of a cohort day against a return day over per-user history. Clustering doesn't bound that compute; you need pre-materialized cohort tables (cohort_date × return_day × slice), not raw scans. Name the materialization or the cost claim is vague.

TRAP

Slice cardinality can explode the DQ panel. app_version (hundreds live in the wild) × country (~200) × day × metric × method_version is easily millions of rows; a naive "null rate per field per slice" tile becomes its own expensive query. Cap cardinality (top-N versions + "other" bucket) and pre-aggregate DQ, or the trust layer costs more than the KPI layer.

TIP

Exec sees L1; on-call sees L2–L4; science lives in L3's method-delta panel. One pipeline, role-scoped views — that sentence alone answers the "second audience" trap.

Pipeline Architecture

Fixed backbone, Google-flavored primitives, one pluggable stage — built for mobile reality.

The backbone

Pub/Sub (ingest) → immutable raw (Colossus / BigQuery raw) → normalize + sessionize (Dataflow/Beam) → [Metric Compute — PLUGGABLE] → versioned output tables → serving (BigQuery + dashboard).

1Ingestion — absorb the burstPUB/SUB▶
  • Edge collector → Pub/Sub. A push tripling ingestion for 10 min is just a deeper backlog, not dropped data — backpressure becomes queue depth.
  • Every event carries a client-generated event_id (idempotency key) and a device-set event-time distinct from server ingest-time.
  • Malformed events → dead-letter topic, never silently dropped.
2Land raw, immutablyCOLOSSUS▶

Append-only, partitioned by ingest-date, keyed by event_id. Never mutated or deleted (except sanctioned privacy deletion). Raw immutability is why backfill under a new method is possible at all.

3Normalize + sessionizeDATAFLOW▶

Dedup by event_id, parse the JSON blob to a typed schema, resolve identity (device_id → user_id), sessionize. Event-time windowing + watermarks for late data; autoscaling for bursts.

4Metric compute — the pluggable stagePLUGGABLE▶

The one stage designed to change. Each metric definition is a versioned plugin behind a stable (events, params) → rows contract, tagged with method_version. This is the crux of the round — detailed in the Extensibility & Algorithm-Swap tab.

5Versioned output + servingBIGQUERY▶

Output partitioned by metric-date, clustered by app_version, country, tagged with method_version. Rollup tables sit on top so dashboards never scan raw. Exec reads rollups pinned to the official version; science reads any version incl. shadow.

Scale sanity check

5B events/day ≈ 58k events/sec average. Pub/Sub + Dataflow autoscaling scale ~linearly; the cost lever is partitioning + rollups, not just more workers.

TRAP

The peak/average ratio is badly understated. "3× at push-peak ≈ 180k/sec" only reprices the specific trap. Real mobile traffic follows a day-night cycle and is timezone-clustered and push-driven; a coordinated push into a dense timezone can spike 5–10× the daily mean for minutes. Design the buffer and autoscaling headroom against the true peak (and its ramp rate — Dataflow can't add workers instantly), not against 3×. Also state a Pub/Sub retention window long enough to survive a compute outage, or the "buffer absorbs it" claim is unbounded.

TRAP

Dedup and late data are unbounded-state problems in streaming. A retry that arrives 3 days after the original can't be de-duplicated by an in-flight streaming window — you'd need days of event_id state. In practice dedup-across-days and the 3-day-late event are resolved by the batch reprocess over immutable raw, not by the streaming watermark. Be explicit that streaming gives provisional numbers with bounded allowed-lateness, and the T+1 batch is the correcting source of truth — otherwise you're claiming watermarks do something they can't afford to.

WATCH

Tricky follow-up: "Where's your backpressure / dead-letter path when compute can't keep up?" Answer: Pub/Sub retention = the buffer; dead-letter topic = poison messages; Dataflow system-lag alert = the trigger to scale or shed to batch. Say all three.

Extensibility & Algorithm-Swap

The exam. If the compute stage is behind an interface, "add a new pipeline" is a non-event.
INSIGHT

Name the ONE axis of change — the method — and push it behind an interface. Keep raw immutable to enable reprocessing. Version outputs so a new method writes alongside, never over, the old. Then "add a new pipeline" collapses to "add a plugin + config + bounded backfill."

The backbone, with the one swappable stage

The contract

Every method is a plugin implementing one interface:

Metric.compute(events_in_window, params) → rows tagged {metric_name, method_version}

A new method = new class/module + config/registry entry + Beam template deploy. Zero changes to ingest, raw storage, or serving.

Walk-through — "science ships retention v4 today"

  1. Deploy: register RetentionV4 in the plugin registry; the DAG picks it up. Plumbing untouched.
  2. Backfill: registration triggers a bounded reprocess over immutable raw (e.g. last 90 days), writing a new logical output tagged method_version=v4 alongside v3. v3's numbers do not move.
  3. Shadow / canary: v4 runs in parallel, lands in the method-delta panel. Leadership stays pinned to v3 (official).
  4. Gate: schema/contract test + DQ gate (row counts, null rates, |v4−v3| anomaly) must pass before promotion.
  5. Promote: flip one config flag — official_version = v4. The version tag answers the "which is right?" question cleanly.
TRAP

The interface boundary is drawn too narrow. The constraints say the science team changes metric definitions AND sessionization AND identity resolution — but sessionization and identity live in the "fixed backbone" (stage 3), upstream of the pluggable compute. So a sessionization change is exactly the monolithic-rewrite scenario you claimed to avoid. Fix: make normalize/sessionize also versioned plugins (session_version), and tag outputs with the full lineage {session_version, method_version}. Otherwise "the method is behind an interface" is only two-thirds true.

TRAP

Backfill cost is under-owned. 90 days × 5B/day = ~450B events reprocessed per method change, several times a quarter, plus each shadow run. That is a large recurring Dataflow + BigQuery bill you dismissed with "storage is cheap." Bound it explicitly: reprocess only affected metrics, sample-then-full for the gate, cache normalized/sessionized intermediates so a metric-only change doesn't re-run identity resolution, and put a cost budget on shadow runs.

WATCH

Anti-signal to avoid naming out loud: a single monolithic Dataflow job with the formula wired inline, where a method change edits + redeploys the whole pipeline and overwrites history. State that this is the no-hire design and why yours isn't it.

Data Quality, Scale & Trade-offs

Mobile is dirty by nature — dedup, late data, clock skew, restatement, cost — plus the rubric and interview tips.

Data quality

  • Duplicates: dedup by event_id — idempotent by construction. In streaming, bounded by allowed-lateness; cross-day retries caught by the batch reprocess.
  • Late data: event-time windowing + watermarks. A device offline 3 days syncing 50k last-Tuesday events lands in Tuesday's window; that day was already published, so I restate — recompute the affected partition, bump data_version, dashboard shows "Tue updated — late data" rather than silently mutating a screenshotted number.
  • Clock skew: trust event-time within a bound; surface p50/p99 skew in L3.
TRAP

Unbounded restatement destroys trust. "Any past day can silently update forever" means leadership's Q2 number can move in Q3. Define a freeze horizon (e.g. day N is official and immutable after 7 days; later-arriving events land in a labeled "corrections" bucket, not a rewrite). Without a cutoff, "official numbers stay stable" contradicts "we restate on late data."

TRAP

Falling back to ingest-time corrupts cohorts. Reassigning a skewed-clock event from its true Tuesday to "today" mis-buckets retention/DAU cohorts — mixing event-time and ingest-time inside one metric is a silent correctness bug. Better: quarantine events whose skew exceeds the bound into a DQ bucket and exclude them from cohort metrics, don't relabel their day.

TRAP

You built a Lambda architecture, then claimed one source of truth. A same-day streaming path and a T+1 batch path running "the same" plugin still diverge (different windowing, watermark, dedup horizon). Either explicitly own reconciliation (batch is authoritative; streaming is labeled provisional and gets overwritten by batch), or go Kappa (one path, replay from raw). Saying "same source of truth, two freshness paths" without the reconciliation rule is the classic vague answer.

Reliability, cost, privacy

  • Freshness SLO: exec tables complete by 06:00 (lag < 6h); monitored via Monarch — freshness lag, row-count anomaly, DLQ depth. "Blank at 2am": freshness metric distinguishes no data (Pub/Sub unacked age) from stuck (Dataflow system lag climbing).
  • Backfill: always a bounded window over immutable raw, emitting a new version. Never full-history on a tweak.
  • Cost: partition by date + cluster by app_version/country; rollup/materialized tables; tiered raw (hot 30d → nearline/coldline); incremental compute + targeted backfill windows.
  • Privacy: device_id/user_id are PII — access-controlled datasets, retention limits, deletion propagating through raw + all derived versions (the one sanctioned mutation of the immutable layer).
TRAP

"Raw is immutable forever" collides with privacy retention limits and cost. 5B/day × 20% YoY, never deleted, is petabytes/year — and GDPR-style deletion + retention limits legally require purging raw, not just derived. Reconcile it: raw is immutable for its retention window (e.g. 18 months) then tiered/expired; user-deletion is a first-class exception with a documented propagation job. "Except privacy deletion" as a parenthetical isn't a plan.

Coding & Remote Communication — Don't Lose a Round You Can Solve

A candidate who knows DSU cold can still lose the round when audio fails, the interviewer goes silent, and they code the wrong thing. This is how to prevent it.

Part A — Remote-Comm Playbook: When the Channel Breaks, Stop Coding

The failure mode isn't the algorithm. It's coding forward into silence. Silence is a signal, not a green light.
INSIGHT

This kind of lost round is a protocol failure, not a skill failure. When audio drops and you keep typing, you solve the problem you imagine was asked. The fix is a rule: the shared editor is your fallback channel, and no line of solution code gets written before the approach is confirmed in text.

The recovery sequence — run it the moment comm degrades

  1. STOP coding immediately: the instant you can't hear or aren't sure you're heard, freeze. Do not "keep making progress" — progress on the wrong problem is negative.
  2. Confirm the channel out loud AND in text: say it and simultaneously type it at the top of the editor, so it lands even if your audio is gone.
  3. Declare your fallback: announce that you'll drive everything through the editor until audio is restored, so the interviewer knows silence from you is a tool issue, not you being stuck.
  4. Narrate approach in TEXT before implementing: write a short plan as editor comments — restated problem, approach, complexity — and pause for a thumbs-up.
  5. Get explicit confirmation, then code: "Does this match what you're asking?" Wait for a yes (verbal or typed) before the first real line.
  6. Treat interviewer silence as a re-sync trigger: if they go quiet for ~20–30s after you asked something, assume a comm gap and re-confirm in text rather than filling the void with code.
"I'm having trouble hearing you — can you hear me? To be safe I'll type my approach and questions directly in the editor so we stay in sync, and I'll read the top of the file for any replies from you."
"Before I implement, here's my plan as a comment block: [restate] [approach] [complexity]. Can you confirm this is the direction you want — a quick 'yes' in the editor works if audio is choppy."
TRAP

Pushing forward silently. When audio breaks, the instinct is to demonstrate momentum by coding — but you're now guessing at the spec with no correction loop. Every minute of confident wrong code is a minute you'll spend rewriting, and it reads to the interviewer as "doesn't notice when he's off track." Momentum into ambiguity is the anti-signal. Explicit re-sync is the pro signal.

TIP

Keep a permanent scratch region at the top of the editor: // PROBLEM: ... // APPROACH: ... // Q FOR YOU: .... It doubles as your think-aloud transcript and your degraded-audio lifeline — and it shows structured thinking even when everything works.

WATCH

Don't over-apologize or fixate on the tech glitch — one calm sentence, switch to text, keep solving. Panic about the tooling is itself a negative signal. Composure under a broken channel is exactly what a remote-heavy data team is screening for.

Part B — DSU / Union-Find Crib: The Template to Know Cold

Know it well enough to type it with a dead mic and narrate it in comments.
DSUInterview-quality template — path compression + union by rankTEMPLATE▶
  • find(x): path compression (here the path-halving variant) flattens the tree so future lookups are near-constant.
  • union(a,b): attach the smaller-rank root under the larger; returns false if already connected (that return value is your cycle detector).
  • count: track number of components, decrement on every successful union — free "connected components" answer.
MethodJava (clean, interview style)
fieldsint[] parent, rank; int count;
initparent[i]=i; rank[i]=0; count=n;
findwhile(parent[x]!=x){parent[x]=parent[parent[x]]; x=parent[x];} return x;
unionsee full block below — union by rank, returns boolean
 
class DSU {
    private final int[] parent, rank;
    private int count;

    DSU(int n) {
        parent = new int[n];
        rank = new int[n];
        for (int i = 0; i < n; i++) parent[i] = i;
        count = n;
    }

    int find(int x) {                       // iterative + path halving
        while (parent[x] != x) {
            parent[x] = parent[parent[x]];  // compress
            x = parent[x];
        }
        return x;
    }

    boolean union(int a, int b) {           // false => already connected (cycle)
        int ra = find(a), rb = find(b);
        if (ra == rb) return false;
        if (rank[ra] < rank[rb]) { int t = ra; ra = rb; rb = t; }
        parent[rb] = ra;
        if (rank[ra] == rank[rb]) rank[ra]++;
        count--;
        return true;
    }

    int components() { return count; }
    boolean connected(int a, int b) { return find(a) == find(b); }
}
NOTE

Iterative find with path halving avoids recursion-stack risk on large inputs and is one fewer thing to explain. State both optimizations aloud (or in comment): "path compression + union by rank gives amortized inverse-Ackermann, effectively constant."

Classic problems — pattern → DSU mapping

Number of Connected Components

Union every edge, answer is components().

Key: component count = distinct roots
Redundant Connection

Process edges; the first edge whose union returns false is the answer.

Key: union false = cycle-closing edge
Accounts Merge

Union accounts sharing any email; group emails by root, sort per group.

Key: map email→id, union on shared key
Number of Islands (via DSU)

Union each land cell with its right/down land neighbor; count land roots. (BFS/DFS also valid — say why you'd pick which.)

Key: 2D index = r*cols+c
INSIGHT

Complexity to state without hesitating: with both path compression and union by rank, m operations on n elements run in O(m · α(n)), where α is the inverse-Ackermann function — ≤ 4 for any input that fits in the universe. So: amortized near-constant per op. Space is O(n).

TIP

Four Golden Signals

From the Google SRE book — the four metrics that matter most for any service. If you can only measure four things, measure these.
"The Four Golden Signals from the Google SRE book are my starting point for any monitoring system: latency, traffic, errors, and saturation. They cover both the user experience and the system's capacity."

1. Latency

The time it takes to serve a request. Critical insight: track success and error latency separately. A fast error (500ms) and a slow success (5s) tell very different stories.

Why Percentiles, Not Averages

  • Average is misleading: If 99 requests take 10ms and 1 takes 10,000ms, the average is ~110ms (109.9ms) — hides the pain of that 1 user
  • p50 (median): The "typical" user experience
  • p95: 1 in 20 users sees at least this latency — good engineering target
  • p99: 1 in 100 users — important for large-scale services
  • p99.9: Matters when you have millions of requests (1 in 1000 = thousands of users/day)
WARNING

You CANNOT average percentiles. If service A has p99=100ms and service B has p99=200ms, the combined p99 is NOT 150ms. You must merge the underlying histograms.

# Good: Histogram with meaningful buckets
http_request_duration_seconds_bucket{le="0.05"}   -- 50ms
http_request_duration_seconds_bucket{le="0.1"}    -- 100ms
http_request_duration_seconds_bucket{le="0.25"}   -- 250ms
http_request_duration_seconds_bucket{le="0.5"}    -- 500ms
http_request_duration_seconds_bucket{le="1.0"}    -- 1s
http_request_duration_seconds_bucket{le="+Inf"}   -- catch-all

2. Traffic

A measure of how much demand is being placed on the system. The specific metric depends on the system type.

  • Web service: HTTP requests per second, QPS
  • Streaming: Concurrent sessions, bandwidth utilization
  • Key-value store: Reads/sec, writes/sec
  • Message queue: Messages produced/sec, messages consumed/sec
  • Business-specific: Orders/min, transactions/sec, searches/sec

3. Errors

The rate of requests that fail. Three categories to track:

  • Explicit errors: HTTP 5xx responses — system failures
  • Implicit errors: HTTP 200 but wrong content (e.g., search returns stale data, empty results for a valid query)
  • Policy violations: Responses slower than SLO threshold count as "errors" for error budget (e.g., any response > 1s = "error")
ERROR BUDGET CONCEPT

If your SLO is 99.9% availability, your error budget is 0.1% — about 43 minutes of downtime per 30-day window. This budget is "spent" on deployments, experiments, and inevitable failures. When the budget runs out, freeze changes and focus on reliability.

4. Saturation

How "full" the service is. Saturation is the ONLY golden signal that predicts future problems (the others are reactive).

  • CPU utilization: Consistently above 70%? Time to scale.
  • Memory: How close to OOM? GC pressure increasing?
  • Disk I/O: Approaching IOPS limits?
  • Network: Bandwidth utilization nearing NIC capacity?
  • Queue depth: Growing queues = consumers can't keep up
  • Thread pool: All threads busy = requests start queuing
  • Connection pool: No available connections = requests blocked
"Saturation is unique among the four signals because it's predictive rather than reactive. A growing queue depth tells you the system WILL fail soon, even if it hasn't yet."

RED & USE Methods

Two complementary frameworks: RED for services (request-driven), USE for resources (infrastructure-driven).

RED Method (for Services)

Created by Tom Wilkie (Grafana Labs). Use RED for any component that processes requests — microservices, APIs, web servers.

Rate

  • Requests per second
  • Segmented by endpoint
  • Shows traffic patterns
  • Detects traffic drops

Errors

  • Failed requests per second
  • Error rate as percentage
  • By error code/type
  • Tracks user impact

Duration

  • Latency distribution
  • p50, p95, p99
  • By endpoint/method
  • Histogram preferred

USE Method (for Resources)

Created by Brendan Gregg. Use USE for any physical or virtual resource — CPU, memory, disk, network, GPUs.

Utilization

  • % time resource is busy
  • Or: % of capacity used
  • Example: CPU 85%
  • High = approaching limit

Saturation

  • Extra work that is queued
  • Or: work not being serviced
  • Example: run queue length
  • Any saturation = problem

Errors

  • Count of error events
  • Hardware errors (ECC)
  • Retransmissions
  • Disk errors, CRC failures

When to Use Which

ContextMethodWhy
Microservice dashboardREDServices process requests — measure from the consumer's perspective
Kubernetes node monitoringUSENodes are resources — measure capacity and saturation
Database monitoringBothRED for query serving (latency, errors, QPS) + USE for resources (disk, CPU, connections)
API GatewayREDGateway's purpose is handling requests
Message brokerRED + USERED for message throughput + USE for broker resource utilization
Top-level service healthREDDirectly maps to user experience
Root cause investigationUSEPinpoints which resource is the bottleneck
"I'd apply the RED method at the service layer — rate, errors, duration for each microservice — and the USE method at the infrastructure layer for CPU, memory, disk, and network. RED tells me if users are affected; USE tells me why."

Relationship to Four Golden Signals

CONNECTION

The Four Golden Signals = RED + Saturation. RED covers Latency (Duration), Traffic (Rate), and Errors. Adding Saturation from USE gives you the complete picture. In an interview, mention all three frameworks to show breadth.

SLI / SLO / SLA

The foundation of reliability engineering. These three concepts form a hierarchy from measurement to target to contract.
"I'd start by defining SLIs for the core user journeys, then set SLOs that align with business requirements. The SLA is a business contract — it should be looser than our SLO so we have breathing room."

Definitions

SLI Service Level Indicator — What You Measure FOUNDATION ▶

A carefully defined quantitative measure of some aspect of the level of service provided. It must be something you can measure reliably.

Good SLI Formula

SLI = (good events / total events) * 100%

Example:
SLI = (requests completing in < 200ms) / (total requests) * 100%
SLI = (successful non-5xx responses) / (total responses) * 100%

Good vs Bad SLI Examples

Ratio of requests without errorsNumber of 5xx errorsRaw count depends on traffic volume
KEY PRINCIPLE

A good SLI measures the user's experience, not the system's internals. "Was the user's request handled correctly and quickly?" not "Is CPU below 80%?"

SLO Service Level Objective — Your Target TARGET ▶

A target value or range for an SLI. Example: "99.9% of requests complete in < 200ms over a 30-day rolling window."

SLO Anatomy

SLO = SLI + Target + Time Window

COMMON MISTAKE

Don't set SLO at 100%. It's impossible, and it means zero error budget — no deployments, no experiments, no maintenance windows.

SLA Service Level Agreement — Business Contract CONTRACT ▶

A formal contract with customers that specifies consequences (usually financial) for not meeting the agreed service level.

Hierarchy

SLO (internal, tighter)  >  SLA (external, looser)

Example:
  Internal SLO: 99.95% availability
  External SLA: 99.9% availability

  If SLO breaches → internal alert, freeze changes
  If SLA breaches → customer refund/credits

Why SLO Must Be Tighter Than SLA

  • SLO breach = early warning → fix before customers are contractually affected
  • Gives you a buffer to react before money is lost
  • Example: AWS S3's SLA is 99.9%, and providers generally run their internal SLO tighter than the SLA they contract to

Metrics Design

How to design metrics that scale: naming conventions, types, cardinality management, and dimensional data.

Metric Types

TypeDescriptionExampleOperations
CounterMonotonically increasing value. Only goes up (or resets to 0).http_requests_totalrate(), increase()
GaugeValue that can go up or down. A snapshot.temperature_celsiusDirect value, min/max/avg

HISTOGRAM vs SUMMARY

Prefer Histogram in almost all cases. Histograms can be aggregated across instances (sum the buckets), while Summaries cannot. Summaries are only useful when you need exact quantiles from a single instance.

Naming Conventions

# Pattern: {service}_{component}_{what}_{unit}_{suffix}

# Good examples:
payment_checkout_duration_seconds_bucket    # histogram bucket
payment_checkout_requests_total             # counter
payment_checkout_errors_total               # counter
inventory_stock_level_items                 # gauge
search_query_duration_seconds_sum           # histogram sum
order_queue_depth_messages                  # gauge

# Bad examples:
latency                    # no context, what service? what unit?
request_time               # is it seconds? milliseconds?
errors                     # for what? total or rate?
cpu                        # utilization? time? cores?
PROMETHEUS CONVENTIONS

Suffix with unit (_seconds, _bytes, _total). Use _total for counters. Use base units (seconds not milliseconds, bytes not megabytes). Snake_case always.

Cardinality — The Silent Killer

Cardinality = number of unique time series. Each unique combination of metric name + label values = one time series.

# This is FINE (low cardinality):
http_requests_total{method="GET", status="200", service="payment"}
# Labels: ~5 methods × ~10 status codes × ~20 services = 1,000 series

# This KILLS your monitoring system (high cardinality):
http_requests_total{method="GET", status="200", user_id="abc123"}
# Labels: ~5 methods × ~10 codes × 10,000,000 users = 500,000,000 series !!!
CARDINALITY EXPLOSION

NEVER use unbounded labels: user_id, email, request_id, session_id, IP address. Each unique value creates a new time series. 10M users = 10M time series per metric = your monitoring system OOMs and dies.

Percentile Calculation Pitfall

Why You Cannot Average Percentiles

  • Scenario: 3 instances, each reports p99 = 100ms, 150ms, 200ms
  • Wrong: Average them → p99 = 150ms
  • Right: Merge the underlying histograms, then compute p99 from the merged data
  • Why: Percentiles are not linear; the 99th percentile of combined traffic depends on the distribution, not the average of individual percentiles
  • Solution: Use Prometheus histograms with histogram_quantile() — it merges bucket counts across instances before calculating

Alerting Strategy

Alert fatigue kills on-call engineers. The key principle: alert on SYMPTOMS not CAUSES, and every alert must be actionable.
"Rather than alert on individual host CPU, I'd alert on user-facing symptoms — if error rate exceeds our error budget burn rate, that's a page. CPU alerts become informational, not paging."

Symptoms vs Causes

Alert on Symptoms (Good)

  • Error rate > 1% for 5 minutes
  • p99 latency > 2s for 10 minutes
  • Checkout success rate below SLO
  • Zero orders for 3 minutes
  • Error budget burn rate > 14.4x

Alert on Causes (Bad)

  • Memory > 90% (might be normal for JVM)
  • CPU > 80% (self-corrects; not user-visible on its own)
  • Disk > 70% as a static threshold (too early) — but note disk is the exception: it doesn't self-heal, so DO page on projected time-to-full (e.g. <4h at current growth)
  • 1 node down (might be normal in k8s)
  • GC pause > 200ms (might not affect users)
KEY PRINCIPLE

Cause-based alerts have too many false positives. CPU at 85% with autoscaling enabled? Not a problem. But error rate at 2%? ALWAYS a problem regardless of which resource caused it. Alert on what users experience.

Multi-Window / Multi-Burn-Rate Alerting

From Google's Site Reliability Workbook, the "Alerting on SLOs" chapter. Combines fast detection with low false-positive rate.

Burn Rate Concept

  • Burn rate 1x: Budget consumed exactly on pace — exhausts by end of the 30-day window. Normal consumption, no action.
  • Burn rate 14.4x: Exhausts the budget in ~2 days — fast burn, page immediately
  • Burn rate 6x: Exhausts in ~5 days — page during business hours
  • Burn rate 3x: Exhausts in ~10 days — slow burn, ticket
Burn RateShort WindowLong WindowSeverityAction
14.4x5 minutes1 hourP1 — PageImmediate response, likely outage
6x30 minutes6 hoursP2 — Page (business hours)Significant issue, investigate soon
3x2 hours1 dayP3 — TicketSlow burn, address within 24h
1x6 hours3 daysP5 — ReviewMonitor trend, plan capacity
WHY TWO WINDOWS

Short window: Ensures the problem is currently happening (not just a spike from 30 min ago). Long window: Ensures it's sustained and not a momentary blip. Both conditions must be true to fire.

Alert Fatigue Prevention

  • Every alert must be actionable: If no one does anything when it fires, delete it
  • Every page-level alert needs a runbook: Link in the alert → "what to do first"
  • Review alert volume weekly: >2 pages/week per person = burnout and ignoring alerts
  • Snooze / auto-resolve: Alerts that auto-resolve in <2 min should be downgraded
  • Aggregate related alerts: "5 hosts high CPU" should be 1 alert, not 5
  • Silence during maintenance: Scheduled deploys should auto-silence related alerts
"I'd follow Google's multi-window, multi-burn-rate approach. A 14.4x burn rate over a 5-minute window AND 1-hour window means we'll exhaust our monthly error budget in 2 days — that's a P1 page. A 3x burn rate over 2 hours is a ticket for the next business day."

Monitoring Architecture

Push vs Pull Collection

Pull-Based (Prometheus)

  • Server scrapes /metrics endpoints
  • Knows which targets exist (service discovery)
  • Can detect DOWN targets (scrape fails)
  • Simple: just expose an HTTP endpoint
  • Challenge: ephemeral targets, firewalls
  • Good for: Kubernetes, known infrastructure

Push-Based (StatsD, Datadog, CloudWatch)

  • Agents push data to central collector
  • Works behind NAT/firewalls
  • Good for ephemeral (Lambda, batch jobs)
  • Challenge: can't detect "silent failure" (not pushing = dead or just quiet?)
  • Good for: serverless, short-lived processes

Scaling Prometheus

# Single Prometheus → 10M time series, ~1-2 weeks retention
# Beyond that, you need horizontal scaling:

Option 1: Thanos
  Prometheus (short-term) → Thanos Sidecar → Object Store (S3)
  Thanos Query (unified view across all Prometheus instances)

Option 2: Cortex / Mimir
  All writes → Cortex Distributor → Cortex Ingester → Object Store
  (No local Prometheus storage needed)

Option 3: Victoria Metrics
  Drop-in Prometheus replacement, better compression and performance
  Supports both push and pull

# Rule of thumb: up to ~100 microservices + k8s cluster
# → single Prometheus is usually fine with 2-week retention
"For the monitoring architecture, I'd use Prometheus with pull-based scraping for metrics, OpenTelemetry for distributed traces stored in Tempo, and Fluentd shipping structured logs to Elasticsearch. Grafana provides unified dashboards across all three. For alerting, Prometheus Alertmanager evaluates recording rules and routes notifications through PagerDuty with runbook links."
