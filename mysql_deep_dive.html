MySQL Architecture Overview

MySQL uses a layered architecture that separates concerns between client connections, query processing, and data storage. Understanding these layers is essential for diagnosing performance issues.

Fig 1: MySQL Three-Layer Architecture

Query Execution Path

▶ SQL Query Lifecycle
  1. Client sends SQL over TCP (port 3306) or Unix socket
  2. Parser — Lexical analysis + syntax validation, produces AST (Abstract Syntax Tree)
  3. Preprocessor — Validates table/column existence, permission checks, resolves aliases
  4. Optimizer — Cost-based optimizer (CBO) evaluates access paths, join orders, index selection. Produces execution plan.
  5. Executor — Calls storage engine API (handler interface) to fetch/modify rows
  6. Storage Engine — InnoDB reads from buffer pool or disk, applies locks, returns results
Interview Insight: The optimizer is key. It decides whether to use an index, which join algorithm (nested loop, hash join in 8.0.18+), and in what order to join tables. Understanding EXPLAIN output is critical.

Why InnoDB won: MyISAM's table-level locking means any write blocks all reads on that table — unacceptable for concurrent web workloads. InnoDB's row-level locking + MVCC allows readers and writers to coexist without blocking each other.

InnoDB Internals

InnoDB is a high-performance, transactional storage engine. Its design is heavily influenced by IBM DB2 and Oracle. Understanding its internals helps diagnose performance issues and design better schemas.

Page Structure

16KB Pages — The Fundamental Unit of I/O ▶
  • Every read/write to disk happens in 16KB page units (configurable: 4KB, 8KB, 16KB, 32KB, 64KB)
  • Pages are organized as B+ tree nodes: leaf pages contain actual row data, internal pages contain keys + page pointers
  • Page structure: File Header (38B) + Page Header (56B) + Infimum/Supremum + User Records + Free Space + Page Directory + File Trailer (8B)
  • The page directory provides binary search within a page using slot pointers
  • Fill factor: InnoDB leaves 1/16 of each page free for future updates to avoid page splits
Interview Insight: Page size affects B+ tree fan-out. With 16KB pages and 8-byte keys + 6-byte pointers, an internal node can hold ~1170 entries, and a leaf page holds ~100 full rows (assuming rows of roughly 160 bytes). A 3-level B+ tree can index ~1170 x 1170 x ~100 = ~137 million rows with just 3 I/O operations.

Buffer Pool

Buffer Pool — The Heart of InnoDB Performance ▶

The buffer pool is an in-memory cache for both data pages and index pages. Typically set to 70-80% of available RAM on dedicated database servers.

LRU with Young/Old Sublists

  • Young sublist (5/8 of buffer pool) — Hot pages, recently accessed
  • Old sublist (3/8 of buffer pool) — Pages that might be evicted
  • New pages are inserted at the midpoint (head of old sublist), not the head of the full list
  • If a page in the old sublist is accessed again after innodb_old_blocks_time (default 1000ms), it moves to the young sublist
  • This prevents full-table scans from flushing the entire buffer pool (scan resistance)

Dirty Page Flushing

  • Modified pages are marked "dirty" — they differ from their on-disk version
  • Flushing strategies: innodb_io_capacity controls background flush rate
  • Adaptive flushing adjusts rate based on redo log generation speed
  • Checkpoint: the LSN up to which all dirty pages have been flushed to disk

Redo Log (WAL)

Write-Ahead Logging — Durability Guarantee ▶
  • WAL principle: Write the log record BEFORE the dirty page is flushed. This ensures crash recovery can replay committed transactions.
  • Redo log is a circular buffer of fixed-size files (default: 2 files x 48MB in 5.7, dynamically sized in 8.0.30+)
  • Each log record has an LSN (Log Sequence Number) — monotonically increasing
  • innodb_flush_log_at_trx_commit:
    • = 1 (default): Flush to disk on every commit. Full durability. ACID compliant
    • = 2: Write to OS buffer on commit, flush every second. Lose ~1s on OS crash.
    • = 0: Write + flush every second. Lose ~1s on any crash. Unsafe
  • Group commit: multiple transactions flush their redo in a single fsync call for throughput

Crash Recovery Process

  1. Read last checkpoint LSN from redo log header
  2. Scan redo log forward from checkpoint, redo all changes (even uncommitted ones)
  3. Apply undo log to rollback uncommitted transactions
  4. Result: database is consistent without manual intervention

Undo Log

Undo Log — MVCC + Rollback ▶
  • Stored in the undo tablespace (separate from data tablespace since 5.6+)
  • Each row modification creates an undo record with the previous version of the row
  • Undo records form a version chain — linked list of previous versions for MVCC reads
  • Two types: INSERT undo (only needed for rollback, discarded after commit) and UPDATE undo (needed for MVCC, kept until no active read view needs it)
  • Purge thread: background cleanup of undo records no longer needed by any active transaction
Long-running transactions prevent purge of undo records, causing undo tablespace bloat and degraded MVCC read performance (longer version chain traversal).

Doublewrite Buffer

Doublewrite Buffer — Torn Page Protection ▶
  • Problem: OS writes in 4KB blocks, InnoDB pages are 16KB. A crash mid-write produces a "torn page" — partially written, partially old data.
  • Solution: Before writing dirty pages to their final location, InnoDB writes them sequentially to a shared doublewrite buffer (2MB area in system tablespace or dedicated files in 8.0.20+).
  • Recovery: If a torn page is detected (via page checksum), InnoDB reads the intact copy from the doublewrite buffer.
  • Performance impact: ~5-10% write overhead, but sequential writes are cheap
  • Can be disabled on filesystems with atomic writes (e.g., ZFS, FusionIO)

Change Buffer

Change Buffer — Optimizing Secondary Index Updates ▶
  • When a secondary index page is not in the buffer pool, the modification is buffered in the change buffer instead of reading the page from disk
  • Works for: INSERT, UPDATE (non-unique indexes), DELETE-mark operations
  • Does NOT work for: unique indexes (must read page to check uniqueness)
  • Merge happens when: the page is eventually read into buffer pool, or background merge thread runs
  • Defaults to 25% of the buffer pool, configurable up to 50% via innodb_change_buffer_max_size
Design implication: If your workload is write-heavy with many secondary indexes, change buffering reduces random I/O significantly. However, for read-heavy workloads where pages are always in memory, it provides less benefit. Note: change buffering is OFF by default since MySQL 8.4.0 (innodb_change_buffering=none) — see the Modern InnoDB section below; this classic benefit applies only where it is explicitly enabled or on older versions.

Modern InnoDB: Instant DDL, Change-Buffer Deprecation, Redo Capacity ▶
Why this matters in 2026: A lot of pre-8.0 MySQL "folk wisdom" is now stale. Three pillars have shifted: (1) most schema changes are metadata-only thanks to ALGORITHM=INSTANT, (2) the change buffer — long taught as the reason non-unique secondary index writes are cheap — is now off by default since MySQL 8.4.0 (the feature and its variable still exist), and (3) redo log sizing is now a single dynamic knob, innodb_redo_log_capacity. Online DDL algorithms

Every ALTER TABLE resolves to one of three algorithms. You can force one with ALGORITHM=INSTANT|INPLACE|COPY; if the requested algorithm can't satisfy the operation, MySQL errors out instead of silently downgrading — which is exactly why you specify it explicitly in production.

AlgorithmWhat it doesConcurrent DMLCost
INSTANT Data-dictionary metadata change only; no table rebuild, no data-file touch. Fully allowed — brief metadata-lock only. O(1), milliseconds regardless of table size.
INPLACE Rebuilds or reorganizes within the existing tablespace (e.g. add secondary index). Mostly allowed — short exclusive MDL at start/end, DML runs during the bulk phase. O(n) work, but no full external copy; changes buffered in an online log and reapplied.
COPY Builds a brand-new table and copies every row over. Blocks writes (reads permitted); table is effectively read-only for the duration. O(n) plus full disk space for a second copy; slowest, most disruptive.
OperationBest algorithmNotes
Add columnINSTANTMetadata-only since 8.0.12; can be placed in any position (not just last) since 8.0.29.
Drop columnINSTANTSupported instantly since 8.0.29.
Rename column / set-or-drop DEFAULT / rename tableINSTANTPure dictionary edits.
Add secondary indexINPLACERebuild-free but scans/sorts the table; DML stays online.
Add PRIMARY KEYINPLACERebuilds/reorganizes the table but supports ALGORITHM=INPLACE with concurrent DML — not COPY-only.

INSTANT is bounded — don't over-trust it. Instant column add/drop mutates rows lazily, and a table can only accumulate so many instant changes before you hit the row-version limit and the next such ALTER is rejected until you rebuild (ALGORITHM=INPLACE/COPY or OPTIMIZE TABLE). Instant column ops are also restricted to ROW_FORMAT ≠ COMPRESSED, tables without a full-text index, and not the sole/primary-key operations. Verify what actually happened via SHOW WARNINGS or the information_schema.INNODB_TABLES.TOTAL_ROW_VERSIONS counter.

When INSTANT can't help: external OSC tools

For operations that force COPY (data-type changes, big charset migrations) on a large, write-heavy table, native DDL would block writes for too long — especially on a replication topology where the ALTER also serializes down the replicas. Two proven-in-production tools sidestep this by building a shadow table and cutting over atomically:

ToolOrigin / LicenseMechanism
pt-online-schema-change (pt-osc)Percona Toolkit, GPL v2Trigger-based: triggers on the original table mirror live changes into a copy, then an atomic rename swaps them.
gh-ostGitHub, MIT licenseTriggerless: tails the binary log to replay changes onto the ghost table, so it adds no trigger overhead to the primary write path.

Change buffer: off by default since 8.4.0

Still present — but disabled by default. The change buffer merges writes to non-unique secondary indexes so that dirtying random secondary-index leaf pages doesn't require an immediate random read from disk. In MySQL 8.4.0 the default of the controlling variable innodb_change_buffering changed from all to none — i.e. change buffering is off by default. The feature and the variable (valid values none, inserts, deletes, changes, purges, all) still exist in 8.4 and are not removed or formally deprecated. Treat the old advice "change buffering speeds up non-unique secondary index inserts/deletes/updates" as a historical default: on modern instances with large buffer pools and fast NVMe/SSD storage it gave little benefit and complicated crash recovery, so it was turned off by default.

Redo log configuration

Since MySQL 8.0.30 the redo log is sized with a single dynamic variable, innodb_redo_log_capacity, defaulting to 104857600 bytes (100 MiB). It supersedes the old pair innodb_log_file_size × innodb_log_files_in_group, both of which are deprecated. InnoDB now manages a pool of 32 redo files internally, and you can resize capacity online with SET GLOBAL innodb_redo_log_capacity = <bytes>; without a restart. If you set both the new and old variables, the new one wins. 
-- Modern (8.0.30+): one knob, changeable at runtime, no restart
SET GLOBAL innodb_redo_log_capacity = 2147483648;  -- 2 GiB

-- Force-and-verify an online, metadata-only column add
ALTER TABLE orders
  ADD COLUMN promo_code VARCHAR(16) AFTER status,
  ALGORITHM=INSTANT, LOCK=NONE;
SHOW WARNINGS;
Interview one-liners:
  • INSTANT = metadata-only, O(1); add-column anywhere since 8.0.29, drop-column since 8.0.29, first shipped 8.0.12. Bounded by a per-table row-version limit.
  • INPLACE rebuilds but keeps DML online (add secondary index, add PRIMARY KEY, extend VARCHAR within its length-byte boundary); COPY blocks writes (data-type / charset changes) — reach for gh-ost (MIT) or pt-osc (GPLv2) when a COPY-only change hits a big hot table.
  • Change buffer is off by default since 8.4.0 (default innodb_change_buffering=none) but still exists and is not removed — the "cheap non-unique secondary index writes" story is now a legacy default.
  • Redo = innodb_redo_log_capacity (default 100 MiB, 8.0.30+, online-resizable), replacing innodb_log_file_size / innodb_log_files_in_group.

B+ Tree Fundamentals

Why B+ Tree? (Not B-Tree, Not Hash) ▶
B+ Tree Advantages
  • All data in leaf nodes only — internal nodes store only keys, maximizing fan-out
  • Leaf nodes form a doubly-linked list — efficient range scans
  • Consistent I/O: O(log N) for point lookups regardless of data position
  • High fan-out reduces tree height (3-4 levels handles billions of rows)
Why Not Others?
  • B-Tree: Data in ALL nodes reduces fan-out, deeper tree, more I/O
  • Hash Index: O(1) lookups but NO range queries, no ordering, not persistent in InnoDB
  • LSM-Tree: Better write throughput (sequential writes) but worse read amplification; compaction adds write amplification (used in RocksDB/LevelDB)

Clustered vs Secondary Index

Clustered Index — Primary Key IS the Data ▶
  • In InnoDB, every table MUST have a clustered index. The table data IS the clustered index's leaf nodes.
  • Priority: explicit PRIMARY KEY → first UNIQUE NOT NULL index → hidden 6-byte GEN_CLUST_INDEX
  • Leaf nodes contain the full row data
  • Rows are physically stored in PK order (sorted insert with AUTO_INCREMENT is optimal)
Design Rule: Always define an explicit PRIMARY KEY. Use AUTO_INCREMENT integer (or ordered UUID v7) to avoid random page splits from UUID v4 inserts.
Secondary Index — Stores PK, Requires Bookmark Lookup ▶
  • Leaf nodes store: indexed columns + PRIMARY KEY value
  • To get non-indexed columns: secondary index lookup → get PK → bookmark lookup into clustered index
  • This double-lookup is why covering indexes are so powerful
  • Wider PKs = wider secondary indexes = more space, more I/O
Fig 3: Secondary Index lookup requires a bookmark lookup back to the Clustered Index

Covering Index

Covering Index — Eliminate Bookmark Lookups ▶

When all columns needed by a query exist in the secondary index itself, no bookmark lookup is needed. EXPLAIN shows "Using index" in the Extra column.

-- Query: SELECT name, age FROM users WHERE name = 'Bob'
-- Covering index:
CREATE INDEX idx_name_age ON users(name, age);
-- Now both 'name' (search key) and 'age' (output) are in the index
-- No need to read the clustered index!
Trade-off: Covering indexes add write overhead (maintaining wider indexes) but can dramatically speed up reads by eliminating random I/O from bookmark lookups.

Composite Index & Leftmost Prefix Rule

Composite Index — Column Order Matters ▶

A composite index (a, b, c) sorts data by a, then by b within same a, then by c within same (a, b).

Index Skip Scan (MySQL 8.0.13+)

If the leading column has low cardinality, the optimizer can "skip scan" — internally treating it as multiple range scans for each distinct value of the leading column.

-- Index: (gender, age)
-- Query: WHERE age > 25
-- Skip scan internally does:
--   WHERE gender='M' AND age > 25
--   UNION
--   WHERE gender='F' AND age > 25

Index Condition Pushdown (ICP)

ICP — Filter at Storage Engine Level ▶
  • Without ICP: Storage engine returns ALL rows matching the index range to the server layer, which then filters
  • With ICP: The storage engine evaluates WHERE conditions that can be checked using index columns before returning rows
  • Reduces the number of full-row reads from the clustered index
  • EXPLAIN shows "Using index condition"
-- Index: (last_name, first_name)
-- Query: WHERE last_name LIKE 'Smith%' AND first_name LIKE 'J%'
-- Without ICP: Read all 'Smith%' rows, filter 'J%' at server
-- With ICP: Check 'J%' using index before fetching full row

MySQL 8.0 Index Features (often missed) ▶
Why this matters in interviews: most candidates stop at B+Tree and composite indexes. MySQL 8.0 shipped three new index capabilities that directly solve classic anti-patterns — functional, invisible, and descending indexes. Knowing them signals you actually track engine evolution rather than reciting MySQL 5.x lore. The fourth item below, the Adaptive Hash Index, is not an 8.0 feature — it is a long-standing InnoDB internal optimization (present well before 8.0), covered here because it is a common tuning pitfall. 8.0 GA: 2018-04-19

1. Functional / Expression Indexes 8.0.13+

The classic function-on-column anti-pattern — WHERE YEAR(created_at) = 2024 — is non-sargable: the index on created_at cannot be used because the column is wrapped in a function, forcing a full scan. Pre-8.0.13 the only fix was an explicitly declared (engine-maintained) generated column plus an index on it — you had to add the column to the schema by hand, though its values are computed automatically by the engine. Since 8.0.13 you can index the expression directly (internally implemented as a hidden virtual generated column). Note the double parentheses — they are what distinguishes a functional key part from an ordinary column key part.

-- Anti-pattern: index on created_at is IGNORED
SELECT * FROM orders WHERE YEAR(created_at) = 2024;   -- full scan

-- Fix (MySQL 8.0.13+): functional index. Note the (( )).
CREATE INDEX idx_order_year ON orders ((YEAR(created_at)));

-- Now the optimizer can use idx_order_year for:
SELECT * FROM orders WHERE YEAR(created_at) = 2024;

-- Expression in the query must MATCH the indexed expression to be used.
-- So range-friendly rewrites are still usually preferable:
--   WHERE created_at >= '2024-01-01' AND created_at < '2025-01-01'
Watch out: the query's expression must match the indexed expression for the optimizer to use it. A functional index does not help a range predicate on the raw column, and vice versa. Prefer a sargable range rewrite when possible; reach for functional indexes when the transformation is unavoidable (e.g. LOWER(email), JSON extraction).

2. Invisible Indexes 8.0.0+

An invisible index is fully maintained by the engine but ignored by the optimizer. This lets you safe-test a drop on a busy production table: flip it invisible, watch query plans and latency, and instantly flip it back if something regresses — no expensive rebuild if you were wrong.

ALTER TABLE orders ALTER INDEX idx_customer INVISIBLE;   -- soft-disable
-- observe: EXPLAIN, slow log, p99 latency ...
ALTER TABLE orders ALTER INDEX idx_customer VISIBLE;     -- instant revert

-- Session-scoped override to actually test WITH the invisible index:
SET SESSION optimizer_switch = 'use_invisible_indexes=on';
A brand-new index can even be created INVISIBLE to stage a rollout. Note: a table's primary key cannot be made invisible.

3. Descending Indexes 8.0.0+

Before 8.0, DESC in an index definition was parsed but silently ignored — the index was stored ascending, and a mixed-direction ORDER BY forced a filesort. In 8.0 descending indexes are stored physically in reverse order, so a composite index whose key-part directions match the sort can be scanned forward with no sort step.

-- Serves: ORDER BY a ASC, b DESC  without a filesort
CREATE INDEX idx_ab ON t (a ASC, b DESC);

4. Adaptive Hash Index (AHI) InnoDB, pre-8.0

Not an 8.0 feature and not something you create — it is a long-standing InnoDB optimization that has existed since the MySQL 5.x era and earlier. InnoDB watches access patterns on hot buffer-pool pages and automatically builds an in-memory hash index for frequently searched key prefixes, turning B+Tree traversals into O(1) point lookups. It is an internal mechanism, not a schema or query technique you apply. Controlled by innodb_adaptive_hash_index (default ON).

Double-edged: under highly concurrent workloads with many secondary-index lookups the AHI's internal latch (partitioned via innodb_adaptive_hash_index_parts, default 8) can itself become a contention bottleneck. A common tuning move for such workloads is SET GLOBAL innodb_adaptive_hash_index = OFF; and measuring throughput both ways.

Anomaly Definitions

  • Dirty Read: Reading uncommitted data from another transaction (data might be rolled back)
  • Non-Repeatable Read: Same SELECT returns different VALUES because another TX committed an UPDATE between our reads
  • Phantom Read: Same range query returns different ROWS because another TX committed INSERT/DELETE

MVCC Implementation

Read View + Undo Log Chain = Consistent Reads Without Locks ▶

How MVCC Works

  1. Every row has hidden columns: DB_TRX_ID (last TX that modified it), DB_ROLL_PTR (pointer to undo log for previous version)
  2. When a transaction starts a consistent read, it creates a Read View containing:
    • m_ids: list of active (uncommitted) transaction IDs at that moment
    • m_low_limit_id: next TX ID to be assigned (anything >= this is invisible)
    • m_up_limit_id: smallest active TX ID (anything < this is visible)
    • m_creator_trx_id: the TX creating this read view (own changes are visible)
  3. For each row, check DB_TRX_ID against the read view rules:
    • If trx_id < m_up_limit_id: visible (committed before read view)
    • If trx_id >= m_low_limit_id: invisible (started after read view)
    • If trx_id in m_ids: invisible (was active when read view created)
    • Otherwise: visible
  4. If current version is invisible, follow DB_ROLL_PTR to previous version in undo log, repeat check

Locking

Record Lock, Gap Lock, Next-Key Lock ▶
Lock TypeWhat It LocksPurposeExample
Record Lock Single index record Prevent concurrent modification of same row SELECT * FROM t WHERE id=5 FOR UPDATE locks record id=5
Gap Lock Gap BETWEEN index records (exclusive of endpoints) Prevent INSERT into the gap — prevents phantom reads If records exist for id=3,7: gap lock on (3,7) prevents INSERT id=5
Next-Key Lock Record lock + gap lock on the gap BEFORE the record Default lock in REPEATABLE READ — prevents phantoms Lock on record 7 = gap (3,7) + record 7 = (3, 7]
Insert Intention Lock Special gap lock for INSERT Signals intent to insert, doesn't block other insert intentions at different positions Two inserts at id=4 and id=6 don't block each other in gap (3,7)

Why Gap Locks Exist

Without gap locks, another transaction could INSERT a row into a range you just scanned, causing a phantom read in REPEATABLE READ. Gap locks prevent this by "sealing" the gaps between existing records.

Deadlock Detection

  • InnoDB maintains a wait-for graph of lock dependencies
  • When a cycle is detected, InnoDB picks the transaction with the least undo log (smallest cost to rollback) as the victim
  • The victim's transaction is rolled back and an error (1213) is returned to the client
  • Application must retry the failed transaction
Common deadlock causes: Accessing rows in different order across transactions, gap lock conflicts with INSERT, secondary index + clustered index lock ordering mismatch.
Internal 2-Phase Commit: Redo Log <-> Binlog ▶

Why two logs must agree InnoDB Server layer

A single transaction touches two independent, layered logs:
  • Redo log — owned by the InnoDB storage engine. It makes the change crash-durable on the local instance (physical/physiological WAL). Since MySQL 8.0.30 (2022) redo files live in the #innodb_redo/ subdirectory of the data dir as #ib_redo0 … #ib_redoN (32 files by default), sized by the single dynamic knob innodb_redo_log_capacity (default 100 MiB); the older innodb_log_file_size / innodb_log_files_in_group are deprecated and the pre-8.0.30 ib_logfile0/ib_logfile1 layout is legacy.
  • Binary log (binlog) — owned by the MySQL server layer, above the engine. It is the logical record of changes used for replication and point-in-time recovery (PITR).
These are written by different code layers, so a naive "write redo, then write binlog" would leave a window where a crash makes them disagree: the row change is durable locally but missing from the binlog (replicas/PITR lose it), or present in the binlog but not applied locally (replicas run a transaction the primary never committed). Either way the primary and its replicas diverge. MySQL closes this window with an internal XA two-phase commit (2PC) that keeps redo and binlog atomically consistent.
The contract that makes it work: the binlog is the coordinator / source of truth. On crash recovery, a transaction that InnoDB left in the PREPARE state is committed if and only if its complete event group exists in the binlog; otherwise it is rolled back. This single rule guarantees "durable locally" and "present in binlog" are the same event.

The internal XA 2PC sequence

Every committing transaction that writes to both logs goes through three ordered steps:
  • 1. InnoDB PREPARE — write the redo log prepare record (tagged with the transaction's XID) and fsync the redo log. Durability of this fsync is governed by innodb_flush_log_at_trx_commit. After this the change is recoverable but marked "prepared, not committed."
  • 2. Write + fsync BINLOG — the server writes the transaction's events to the binlog and fsyncs the binlog. Durability of this fsync is governed by sync_binlog. This is the commit point: once the binlog is safely on disk, the transaction is logically decided as committed.
  • 3. InnoDB COMMIT — write the redo log commit record and mark the transaction committed in InnoDB, release locks. This redo commit record does not need its own synchronous fsync for correctness, because recovery can re-derive the decision from the binlog (step 2).

Binlog group commit

Fsyncing the binlog on every transaction is expensive, so MySQL (since 5.6) batches concurrent committers into a group commit pipeline with three ordered stages. One thread acts as the leader for each stage and does the work on behalf of the whole queued group:
  • FLUSH — each session's binlog cache is written into the binlog file (still just page cache).
  • SYNC — a single fsync() flushes the whole group's binlog data to disk at once (amortizing the fsync cost across many transactions).
  • COMMIT — InnoDB commits the group in order (step 3 above); commit ordering is preserved so the binlog order matches the InnoDB commit order.
Tunables binlog_group_commit_sync_delay (microseconds to wait, gathering a bigger group) and binlog_group_commit_sync_no_delay_count (max transactions before firing early) trade a little latency for far higher throughput. Group commit does not weaken durability — with the settings below, no transaction returns success to the client until its binlog is fsynced.

Crash recovery (binlog as coordinator)

On restart InnoDB replays redo, then reconciles PREPAREd transactions against the binlog:
  • XID present as a complete event group in the binlog → commit the prepared transaction (finish step 3).
  • XID absent (crash happened before/while writing the binlog) → roll back the prepared transaction.
  • A partially-written trailing binlog event is truncated during recovery, so it counts as "absent" and is rolled back.
Result: what the primary keeps is exactly what the binlog contains, so replicas and PITR stay consistent with the primary.

Durability knobs — both must be crash-safe

For crash-safe replication you MUST set BOTH innodb_flush_log_at_trx_commit = 1 AND sync_binlog = 1 (the "double 1" configuration). If either is relaxed, a well-timed OS/power crash can drop the redo or the binlog for an acknowledged transaction, breaking the 2PC guarantee and letting the primary and its replicas silently diverge.
Setting Value Durability guarantee Performance
innodb_flush_log_at_trx_commit

2 Write redo to OS page cache each commit, fsync ~once/sec. Survives a mysqld crash, but an OS/power crash can lose ~1s of commits. Faster
0 Write + fsync redo only ~once/sec (not at commit). A crash can lose ~1s of committed transactions, even a mysqld crash. Fastest
sync_binlog
default = 1 since 5.7.7		 1 fsync binlog at every commit (every group in group commit). No committed transaction is ever missing from the binlog after a crash. Required for crash-safe replication. Slowest (one binlog fsync per group, amortized by group commit)
N > 1 fsync binlog once every N commit groups. A crash can lose up to N groups of binlog events. Faster

Binlog group commit landed in MySQL 5.6. Binary logging is enabled by default since MySQL 8.0 (log_bin was OFF by default pre-8.0; it can still be turned off with --skip-log-bin), and GTIDs are commonly used, but the redo↔binlog 2PC contract is unchanged.

Replication Topologies

Fig 5: Three replication modes — increasing durability guarantees

Replication Mechanisms

Async Replication (Traditional) ▶
  1. Primary writes changes to binary log (binlog)
  2. Replica I/O thread connects to primary, reads binlog events, writes them to local relay log
  3. Replica SQL thread reads relay log and replays events on replica data
  • Primary does NOT wait for replica — zero impact on write latency
  • Risk: if primary crashes before replica catches up, data is lost
  • GTID (Global Transaction Identifier): unique ID per transaction, simplifies failover
Semi-Synchronous Replication ▶
  • Primary waits for at least one replica to acknowledge receiving the binlog event before committing
  • Default AFTER_SYNC: primary waits for a replica to ACK receipt into its relay log after the primary flushes its binlog but before the commit is returned to the client (not necessarily applied). AFTER_COMMIT waits after the primary commits. The wait-point name refers to the primary's stage, set by rpl_semi_sync_source_wait_point (the legacy alias rpl_semi_sync_master_wait_point was deprecated in 8.0.26).
  • Guarantees: committed TX exists on at least 2 nodes
  • Trade-off: ~1 network RTT added to every commit (negligible within same DC)
  • Fallback: if no replica ACKs within timeout, degrades to async to avoid blocking
Group Replication (MySQL InnoDB Cluster) ▶
  • Built on Paxos-based Group Communication System (GCS)
  • Single-primary mode: One writer, automatic failover
  • Multi-primary mode: All nodes accept writes, conflict detection at commit time
  • Certification-based conflict resolution: if two nodes modify same row, first to be ordered wins; others are rolled back
  • Recommended 3+ (odd number) for fault tolerance; max 9 members, InnoDB tables with PK, GTID enabled
  • Used with MySQL Router for transparent failover to applications

Failover Strategies

Failover — Promoting a Replica ▶

Manual Failover

  1. Ensure target replica has applied all relay log events (STOP REPLICA; START REPLICA UNTIL...)
  2. Set read_only=OFF on promoted replica
  3. Point other replicas to new primary (change replication source)
  4. Update application connection strings / VIP / DNS

Automated Failover Options

  • MySQL InnoDB Cluster + Router: Built-in automatic failover with Group Replication
  • Orchestrator (open source): Topology-aware failover, handles complex chains
  • MHA (Master High Availability): Classic tool, applies differential relay logs to pick most up-to-date replica
  • ProxySQL + Orchestrator: Transparent failover without app-level changes
Data loss risk: In async replication, a promoted replica may be missing transactions that were committed on the failed primary but not yet replicated. Semi-sync or Group Replication minimizes this gap.

"Why Is This Query Slow?" — Systematic Approach

🔍 Step-by-Step Diagnosis
  1. EXPLAIN the query — Look at type (ALL=bad), rows estimate, Extra column
  2. Check indexes — Is the right index being used? Is it a covering index?
  3. Check data volume — How many rows does the table have? What's the selectivity?
  4. Check for locks — SHOW ENGINE INNODB STATUS, performance_schema.data_locks
  5. Check buffer pool hit rate — Low hit rate means excessive disk I/O
  6. Check query plan changes — Statistics stale? Run ANALYZE TABLE
  7. Profile the query — SET profiling=1; ... SHOW PROFILE; or performance_schema
-- Quick diagnosis commands
EXPLAIN ANALYZE SELECT ...;        -- MySQL 8.0.18+ (actual execution stats)
SHOW STATUS LIKE 'Handler_%';      -- Rows examined vs returned
SELECT * FROM sys.statements_with_full_table_scans;  -- sys schema

Index Design Methodology

From Queries to Indexes — A Framework ▶
  1. List all critical queries (top N by frequency or latency)
  2. For each query, identify:
    • Equality predicates (WHERE col = value) — these go FIRST in composite index
    • Range predicates (WHERE col > value) — at MOST ONE range column can use the index
    • ORDER BY / GROUP BY columns — put AFTER equality, BEFORE range for sort elimination
    • SELECT columns — include for covering index if feasible
  3. Apply ESR rule: Equality → Sort → Range
  4. Consolidate: Can one composite index serve multiple queries?
  5. Validate: EXPLAIN each query, confirm index usage
-- Example: Designing index for
-- SELECT * FROM orders WHERE user_id = ? AND status = 'shipped'
--   ORDER BY created_at DESC LIMIT 20;

-- Equality: user_id, status
-- Sort: created_at DESC
-- Range: none
-- Index: (user_id, status, created_at)
-- This gives: eq lookup + sorted output, no filesort needed!

Sharding Strategies

Range vs Hash Sharding ▶
Range Sharding
  • Split by value range (e.g., user_id 1-1M, 1M-2M, ...)
  • Pro: Range queries stay on one shard
  • Con: Hot spots (newest data = most active shard)
  • Con: Uneven distribution over time
  • Good for: time-series, archival patterns
Hash Sharding
  • shard = hash(key) % num_shards
  • Pro: Even distribution
  • Con: Range queries must scatter to ALL shards
  • Con: Resharding requires data movement (use consistent hashing)
  • Good for: key-value lookups, user data by user_id

Resharding Challenges

  • Data migration while serving traffic (online resharding)
  • Cross-shard transactions become much harder
  • Consistent hashing (virtual nodes) minimizes data movement
  • Vitess, ProxySQL, or application-level routing layer

Connection Pooling

Why and How Many Connections? ▶
  • Why: Each MySQL connection = 1 thread + memory (~1-10MB per connection for sort buffers, join buffers, etc.). Too many = OOM or context switch overhead.
  • Connection pool libraries: HikariCP (Java), pgbouncer-style proxies, ProxySQL
  • Sizing formula (rule of thumb): connections = (cores * 2) + effective_spindle_count
  • For SSD: ~(cores * 2) to (cores * 4) is the typical best balance
  • Example: 8-core server → 16-32 connections in the pool
  • More connections ≠ more throughput. Past that best balance, contention and context switches REDUCE performance.
Interview Insight: If asked "the database is slow," first check if there are too many connections (hundreds) with most in SLEEP state. This usually means the application is not using connection pooling properly.

Common Interview Questions

"Design the Schema for X" — Patterns ▶
  • User/Post/Comment: Classic normalized schema. user_id FK in posts, post_id FK in comments. Index on (post_id, created_at) for comment feeds.
  • Social graph: Adjacency list table: follows(follower_id, followee_id). Composite PK, reverse index for "who follows me?"
  • E-commerce orders: orders + order_items (1-to-many). Denormalize total into orders for fast listing. Index on (user_id, status, created_at).
  • Chat messages: Partition by conversation_id or time. Index on (conversation_id, sent_at). Consider TTL archival.
  • Inventory/counters: Use UPDATE inventory SET qty = qty - 1 WHERE id = ? AND qty > 0 for atomic decrement with optimistic check.
"How Would You Handle 10x Traffic Growth?" ▶
  1. Read replicas — Route reads to replicas (most workloads are read-heavy)
  2. Caching layer — Redis/Memcached for hot data, cache-aside pattern
  3. Connection pooling — ProxySQL or HikariCP to limit connection count
  4. Query optimization — Add covering indexes, eliminate N+1 queries
  5. Vertical scaling — More RAM (bigger buffer pool), faster SSDs
  6. Horizontal sharding — Split by user_id/tenant_id if above isn't enough
  7. Async processing — Move non-critical writes to message queue
When to Denormalize ▶
  • Read-heavy with expensive JOINs: Pre-compute and store aggregates (e.g., post_count in users table)
  • Hot path needs single-table lookup: Duplicate data to avoid JOIN in latency-critical path
  • Reporting/Analytics: Star schema with denormalized dimensions
  • Cross-shard queries: After sharding, denormalize to keep related data on same shard
Cost of denormalization: Write complexity increases (maintain consistency in multiple places), risk of stale data, larger storage. Always start normalized, denormalize only when you have measured evidence of a bottleneck.
