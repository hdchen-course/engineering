The Linux Kernel & the Hardware Boundary

A backend engineer's guided tour across the line where software meets silicon: how a syscall really works, how a loadable module plugs a driver into the kernel, how the kernel discovers and talks to PCIe devices, how DMA and the IOMMU let hardware touch memory safely, how interrupts and NUMA and the page cache shape performance, and how to read an oops when it all goes wrong. Every mechanism is bridged from the distributed-systems concepts you already know — syscalls as an API, DMA as async offload, interrupts as webhooks, NUMA as data locality.

1. The Great Divide: User Space vs Kernel Space

Every line of code on a running machine executes in one of two worlds. User space is where your applications live: sandboxed, unable to touch hardware directly, each process in its own virtual address space. Kernel space is the privileged core that owns the hardware, schedules threads, manages memory, and mediates every request to do anything real. The boundary between them is enforced by the CPU itself, and understanding it is the foundation for everything else in this chapter.

Privilege levels & the mode switch

x86-64 CPUs have four privilege rings (0–3), but in practice operating systems use only two: ring 0 for the kernel and ring 3 for user code. (Arm calls the equivalent concept exception levels: EL0 for apps, EL1 for the kernel.) The ring you are in is a hardware bit that gates privileged instructions — you cannot execute an I/O port access, load a page-table base register, or disable interrupts from ring 3. Attempting to does not silently fail; it traps into the kernel as a fault. A mode switch is the CPU transitioning ring 3 → ring 0 (and back). It is not the same as a context switch (swapping one thread/process for another) — a mode switch keeps running the same thread, just with more privilege.

Bridge

Think of the kernel as a managed runtime with a hard security boundary, like the way a serverless platform stands between your function and the raw machine. Your code never touches the disk, the NIC, or physical RAM directly — it asks the platform to, through a well-defined API. That API is the system-call interface, and the ring boundary is what makes "asks" the only option.

Why the divide exists

Three reasons, all of which come up in interviews: isolation (a buggy or malicious process can't corrupt another process or the kernel), abstraction (apps see files and sockets, not disk sectors and Ethernet frames), and arbitration (the kernel multiplexes finite hardware — CPU, RAM, devices — fairly among many processes). The cost is that any real work (I/O, memory from the OS, talking to a device) requires crossing into the kernel, and that crossing has a price we'll quantify next.

The user/kernel divide. Applications run unprivileged and reach the hardware only by trapping across the syscall boundary into the kernel, which alone runs privileged and owns the devices.

2. What Actually Happens on a Syscall

You call read(fd, buf, n). It looks like an ordinary function call, but a function call can't reach kernel code — that code lives on the other side of the ring boundary. What actually happens is a carefully coordinated hardware-assisted transition. Getting this sequence right in an interview is a strong signal.

Bridge

A syscall is your program calling the operating system's API — an RPC to the kernel that happens to run on the same machine. Like any RPC it has an ABI (a calling convention), it marshals arguments, it can block, and it returns a status. The difference from a network RPC is that the "transport" is a CPU instruction that flips privilege, and the "server" is the kernel running in your own thread's context.

The sequence, step by step

  1. libc wrapper. The read() you call is a thin glibc wrapper. It places the syscall number and arguments in the registers the ABI dictates, then executes the trap instruction.
  2. The trap instruction. On x86-64 this is the SYSCALL instruction (older code used the int 0x80 software interrupt; ARM64 uses SVC). It switches to ring 0, jumps to a fixed kernel entry point the kernel registered at boot, and saves the return address.
  3. Kernel dispatch. The entry handler reads the syscall number and indexes the syscall table (sys_call_table) to find the handler — e.g. sys_read. It validates arguments.
  4. Copy across the boundary. The kernel must never dereference a user pointer directly (it might be invalid, or an attack). It uses copy_from_user() / copy_to_user(), which check that the address really belongs to the caller's address space before moving bytes.
  5. Do the work & return. The handler runs (possibly sleeping if data isn't ready), puts the result in the return register, and executes SYSRET/ERET to drop back to ring 3. A negative value is mapped by libc to -1 plus errno.

The x86-64 syscall ABI

The System V calling convention for user functions and the syscall convention differ in one important register, which trips people up:

Syscall numberraxReturn value also comes back in rax.
Arg 1–6rdi, rsi, rdx, r10, r8, r9Note arg 4 is r10, not rcx — SYSCALL clobbers rcx (saves return RIP there).

# The classic "hello" via raw syscalls, no libc — x86-64 Linux (GNU as, AT&T syntax)
# write(1, msg, len); then exit(0);
    mov  $1, %rax        # syscall number for write
    mov  $1, %rdi        # fd = 1 (stdout)
    lea  msg(%rip), %rsi # buf
    mov  $13, %rdx       # count
    syscall              # trap into ring 0 → sys_write
    mov  $60, %rax       # syscall number for exit
    xor  %rdi, %rdi      # status = 0
    syscall
A syscall round-trip: libc marshals the number/args, the trap instruction switches to ring 0, the kernel dispatches through the syscall table and copies data across the boundary, then returns to ring 3.

Why syscalls are "expensive"

A syscall is far cheaper than a context switch, but it is not free: it flushes some pipeline state, may pollute caches/TLB, and modern speculative-execution mitigations (KPTI page-table isolation, retpolines) added real overhead. This is why high-throughput I/O designs batch syscalls: io_uring submits many operations with one crossing, sendmmsg/recvmmsg move many packets per call, and kernel-bypass avoids the crossing entirely (see Low-Latency C++, Part XIII).

Interview signal

If asked "what happens when you call read()?", narrate the five steps: libc marshals number+args → trap instruction switches ring → kernel dispatches via the syscall table → copy_to_user moves bytes safely → SYSRET back with the result. Mention copy_to/from_user specifically — it shows you know the kernel never trusts a raw user pointer.

"A syscall is an RPC to the kernel from within my own thread. The SYSCALL instruction flips to ring 0 and lands at a fixed entry point; the kernel indexes the syscall table, validates and copies my arguments with copy_from_user, does the work, and returns via SYSRET. The kernel never dereferences my pointers directly — that's the whole point of the boundary."

3. Loadable Kernel Modules & a Char Driver

The Linux kernel is monolithic, but not static: you can extend it at runtime with a loadable kernel module (LKM) — a chunk of code that links into the running kernel's address space and runs with full ring-0 privilege. Almost every device driver ships as a module.

Bridge

An LKM is a plugin loaded into the kernel process. Just like a plugin in an application server, it registers callbacks (an init hook, an exit hook, and per-operation handlers), gets access to the host's internal APIs, and can crash the whole host if it misbehaves — there is no sandbox around it. Loading one is dynamic-linking a shared object, except the "host" is the kernel and the "linker" is insmod.

Character devices, /dev nodes, major/minor

The classic driver interface is a character device — a byte-stream device exposed as a special file under /dev. Each device node carries a major number (which driver owns it) and a minor number (which instance/unit). When user space calls open/read/write/ioctl on /dev/mydev, the kernel routes those calls — via the major number — to the function pointers your driver registered in a struct file_operations.

Bridge

file_operations is an interface/vtable: a struct of function pointers the kernel calls polymorphically. Registering a char device is "implementing the FileLike interface and handing the kernel your implementation." ioctl is the catch-all method for device-specific commands that don't fit the read/write stream model — think of it as a typed control-plane RPC alongside the read/write data plane.

// Skeleton char driver — the shape every Linux driver interview expects.
// (Illustrative: error paths trimmed for space.)
#include <linux/module.h>
#include <linux/fs.h>
#include <linux/uaccess.h>   // copy_to_user / copy_from_user

static int     my_major;
static char    kbuf[256];

static int my_open(struct inode *ino, struct file *f) {
    printk(KERN_INFO "mydev: open\n");   // shows up in dmesg
    return 0;
}
static ssize_t my_read(struct file *f, char __user *ubuf,
                       size_t len, loff_t *off) {
    size_t n = min(len, sizeof(kbuf));
    if (copy_to_user(ubuf, kbuf, n))   // never memcpy to a user ptr!
        return -EFAULT;
    return n;                          // bytes delivered
}
static ssize_t my_write(struct file *f, const char __user *ubuf,
                        size_t len, loff_t *off) {
    size_t n = min(len, sizeof(kbuf));
    if (copy_from_user(kbuf, ubuf, n))
        return -EFAULT;
    return n;
}
static long my_ioctl(struct file *f, unsigned int cmd, unsigned long arg) {
    switch (cmd) { /* device-specific control commands */ }
    return 0;
}
static int my_release(struct inode *ino, struct file *f) { return 0; }

static const struct file_operations fops = {   // the vtable
    .owner   = THIS_MODULE,
    .open    = my_open,
    .read    = my_read,
    .write   = my_write,
    .unlocked_ioctl = my_ioctl,
    .release = my_release,
};

static int __init my_init(void) {   // runs on insmod/modprobe
    my_major = register_chrdev(0, "mydev", &fops);  // 0 = pick a major
    printk(KERN_INFO "mydev: loaded, major=%d\n", my_major);
    return 0;
}
static void __exit my_exit(void) {   // runs on rmmod
    unregister_chrdev(my_major, "mydev");
}
module_init(my_init);
module_exit(my_exit);
MODULE_LICENSE("GPL");   // non-GPL taints the kernel & hides symbols
Kernel C is not user-space C

Inside a module there is no libc, no printf (use printk with a log level like KERN_INFO), no floating point by default, and a tiny fixed stack (a few KiB — no deep recursion or big stack arrays). A null-pointer dereference doesn't segfault a process; it can take down the whole machine. MODULE_LICENSE("GPL") matters: a proprietary license "taints" the kernel and the module loses access to GPL-only symbols.

Common mistake: trusting user pointers

A classic driver bug to watch for: dereferencing the user buffer directly (memcpy(kbuf, ubuf, n)) instead of copy_from_user. A raw user pointer may be unmapped, may point into the kernel, or may race with another thread unmapping it — dereferencing it is a security hole and a crash. Always cross the boundary with the copy_*_user helpers, and always check their return value.

4. The Linux Device Model: How the Kernel Finds Hardware

Before a driver can drive anything, the kernel has to know the hardware exists. The Linux device model is the unifying framework that discovers devices, matches them to drivers, and manages their lifecycle. Its three nouns are bus, device, and driver.

Bus, device, driver, and probe()

  • A bus (PCI, USB, I²C, platform, …) is a namespace of devices and the rules for enumerating them. It maintains two lists: devices present, and drivers registered.
  • A device is a discovered piece of hardware, identified by IDs (for PCI: vendor ID + device ID).
  • A driver registers with a bus and declares an ID table of the devices it supports.
  • When a device and a matching driver are both present, the bus calls the driver's probe() function, handing it that device to initialize. On removal, remove() is called. This bind/unbind is the heart of hot-plug.
Bridge

This is exactly service discovery + dependency injection. The bus is a registry; devices register as they appear (hot-plug = a service coming online); drivers declare which "service types" they can handle via an ID table; and probe() is the wiring callback that fires when a compatible provider and consumer are both present. You've built this pattern in distributed systems — the kernel just does it for hardware.

// A PCI driver declares which devices it binds to, and a probe hook.
static const struct pci_device_id my_ids[] = {
    { PCI_DEVICE(0x10de, 0x1eb8) },   // vendor 0x10de, a device id
    { 0, }
};
MODULE_DEVICE_TABLE(pci, my_ids);   // lets modprobe autoload on match

static int my_probe(struct pci_dev *pdev, const struct pci_device_id *id) {
    pci_enable_device(pdev);          // power up, enable MMIO/IO space decoding
    pci_set_master(pdev);             // enable bus-mastering — required before the device can DMA
    pci_request_regions(pdev, "mydrv");  // claim its BAR regions
    // map BARs, request IRQ, register upper-layer device... (§5–§7)
    return 0;
}
static struct pci_driver my_driver = {
    .name = "mydrv", .id_table = my_ids,
    .probe = my_probe, .remove = my_remove,
};
module_pci_driver(my_driver);   // registers with the PCI bus

How devices are described: ACPI vs Device Tree

Some buses are self-describing — you can walk PCIe and ask each device what it is. But many devices (memory-mapped peripherals, clocks, GPIOs) are not discoverable; the kernel has to be told they exist and where. Two mechanisms do this, and which one you meet depends on the platform:

Rule of thumb

On a server, assume ACPI is describing the platform (and providing NUMA/topology tables the scheduler and allocator rely on). On an embedded board, assume a Device Tree. PCIe devices under either are still enumerated by walking the bus.

5. PCIe From the Kernel's Point of View

PCI Express is the backbone that attaches high-speed devices — NICs, NVMe drives, GPUs, and accelerators — to a server. From the kernel's view, three things matter: how you find a device (config space + enumeration), how you talk to it (BARs + MMIO), and how it notifies you (MSI/MSI-X interrupts, §7).

Configuration space

Every PCIe function has a standardized configuration space — 256 bytes in legacy PCI, extended to 4 KiB in PCIe. Its first 64 bytes are a fixed header the kernel reads to identify and set up the device: Vendor ID and Device ID (the pair drivers match on), Class code (NIC? storage? display?), the Command/Status registers (enable memory decoding, bus-mastering for DMA), and the Base Address Registers (BARs). Beyond the header sits a linked list of capabilities (MSI-X, power management, PCIe-specific features).

Bridge

Config space is the device's self-describing metadata endpoint — like hitting a service's /info plus /config. Enumeration is a topology crawl: the kernel walks the bus/device/function tree (a DFS across PCI-to-PCI bridges), reads each function's IDs, and builds the device graph — much like a service mesh discovering everything reachable from a root.

Enumeration & BDF

At boot (or hot-plug), firmware and/or the kernel enumerate the PCIe tree, addressing each function by its Bus:Device.Function (BDF) triple — the identifier you see in lspci (e.g. 0000:3b:00.0). Enumeration assigns bus numbers to bridges and, crucially, programs each BAR with a physical address range carved out of the system's MMIO space.

BARs & MMIO

A Base Address Register tells the system where to map a device's register block or memory into the CPU's physical address space. Once mapped, the driver reaches the device through Memory-Mapped I/O (MMIO): reading or writing those physical addresses is transparently routed to the device instead of DRAM. The driver maps the BAR into kernel virtual space with ioremap() and must use the accessor functions (readl/writel, or ioread32/iowrite32) — never a plain pointer dereference.

// Map BAR0 and poke a device register (inside probe/setup).
void __iomem *regs;
resource_size_t start = pci_resource_start(pdev, 0);  // BAR0 phys addr
resource_size_t len   = pci_resource_len(pdev, 0);
regs = pci_iomap(pdev, 0, len);        // = ioremap of the BAR

u32 id = ioread32(regs + DEV_ID_REG);   // MMIO read → goes to device
iowrite32(ENABLE_BIT, regs + CTRL_REG);  // MMIO write → device register
MMIO is not ordinary memory

An MMIO write can have side effects (starting a DMA, clearing an interrupt) and reads/writes must not be reordered or cached like RAM. That's why you use readl/writel (which include the right barriers and volatile semantics) rather than dereferencing the mapped pointer. Mapping is done with ioremap — the region is marked uncacheable/device memory, not write-back cacheable like normal RAM.

BARs carve device register/memory windows out of the CPU's physical address space. MMIO accesses to those addresses are routed to the device rather than to DRAM.

6. DMA and the IOMMU

MMIO lets the CPU poke a device one register at a time — fine for control, hopeless for bulk data. To move a 9 KB packet or a 1 MB block, the device does Direct Memory Access (DMA): it reads and writes system RAM itself, in bursts, while the CPU does other work. This is the single biggest performance mechanism at the hardware boundary — and the biggest source of subtle bugs.

Bridge

DMA is async I/O offload / zero-copy at the hardware level. Instead of the CPU copying bytes register-by-register (a blocking, synchronous drain), the CPU hands the device a memory address and says "put the data there and tell me when you're done" — then goes off to do other work and gets a callback (an interrupt, §7) on completion. It's the same idea as handing a task to a thread pool and awaiting a future, except the "worker" is the NIC or NVMe controller.

Coherent vs streaming mappings

You cannot just hand a device a random kernel pointer. Devices work in bus/DMA addresses (which may differ from CPU physical addresses, especially with an IOMMU), and CPU caches can hold stale copies of memory the device is about to overwrite. The DMA mapping API solves both. It offers two flavors:

Coherent (consistent) — dma_alloc_coherent
  • Long-lived buffer both sides poke often (descriptor rings, mailboxes).
  • Hardware/mapping keeps CPU and device views coherent — no manual cache management.
  • Allocated once at setup; may be uncached, so slower for CPU-heavy access.
Streaming — dma_map_single / dma_map_sg
  • One-shot buffer for a single transfer (a packet, a block).
  • You map before the transfer, unmap after; ownership passes to the device in between.
  • Cheaper & cacheable, but you must respect the direction and not touch the buffer while the device owns it.
// Streaming map for one outbound transfer (e.g. transmit a buffer).
dma_addr_t dma = dma_map_single(&pdev->dev, kbuf, len, DMA_TO_DEVICE);
if (dma_mapping_error(&pdev->dev, dma)) return -ENOMEM;
// ... program the device with 'dma' & 'len', kick off DMA, device owns buf ...
// (do NOT read/write kbuf here — the device does)
dma_unmap_single(&pdev->dev, dma, len, DMA_TO_DEVICE);  // syncs caches, returns ownership

Cache coherency & the direction argument

The DMA_TO_DEVICE / DMA_FROM_DEVICE / DMA_BIDIRECTIONAL argument is not decoration — on architectures without hardware-coherent DMA, it tells the kernel which cache operation to perform: flush/clean dirty CPU cache lines to RAM before an outbound transfer, or invalidate stale lines after an inbound one. Get the direction wrong and the device or CPU reads garbage — a classic, hard-to-debug driver defect.

Common mistake: touching a mapped buffer

While a buffer is DMA-mapped, the device owns it. Reading or writing it from the CPU in that window — or forgetting to unmap/sync — produces coherency bugs that appear as intermittent data corruption, not a clean crash. On coherent-DMA x86 you might get away with it; on a weakly-coherent Arm SoC you won't. Map, hand off, wait for completion, unmap, then touch it.

The IOMMU: an MMU for devices

Historically a DMA-capable device could read or write any physical address — a buggy driver or malicious device could scribble over the kernel or another VM's memory. The IOMMU (Intel VT-d, AMD AMD-Vi, Arm SMMU) fixes this. It sits between devices and memory and translates device (I/O virtual) addresses to physical addresses using per-device page tables — and it refuses any access outside what's been mapped.

Bridge

If the MMU is virtual memory for processes, the IOMMU is virtual memory for devices. It gives each device (or group of devices) its own address space, so a device sees only the pages explicitly granted to it — the same isolation guarantee the MMU gives a process, applied to DMA.

Why the IOMMU matters

  • Isolation / security. A device can only touch memory that's been mapped for it; a driver bug or a malicious peripheral (think a rogue Thunderbolt device) can't DMA over the whole system. This is the defense against classic DMA attacks.
  • Virtualization & passthrough. To give a VM direct ownership of a physical device (PCIe passthrough / SR-IOV virtual functions), the IOMMU remaps the device's DMA to the guest's memory, so the guest can drive real hardware at near-native speed while staying confined to its own RAM. This is what makes accelerator passthrough in the cloud safe.
  • 32-bit devices. The IOMMU can present a contiguous low address to a device with limited addressing while the real pages live anywhere in physical memory (replacing bounce-buffer copies).
The IOMMU translates a device's I/O virtual addresses to physical addresses via per-device page tables and blocks anything unmapped — an MMU for devices, giving DMA isolation and enabling safe passthrough.
Interview signal

"Coherent vs streaming DMA?" → coherent = long-lived, always-consistent buffers (descriptor rings) allocated once with dma_alloc_coherent; streaming = per-transfer buffers you map/unmap with a direction, cheaper and cacheable but device-owned in between. "What does the IOMMU protect against?" → a device DMAing over arbitrary physical memory — it gives per-device address spaces for isolation and makes VM device passthrough safe.

7. Interrupts: the Hardware's Callbacks

A device that finished a DMA needs to tell the CPU. Polling wastes cycles, so instead the device raises an interrupt: the CPU stops what it's doing, saves state, and jumps to the driver's registered handler. Interrupts are how asynchronous hardware events reach software.

Bridge

An interrupt is a hardware event callback — a webhook from a device. You register a handler ("subscribe"), and when the event fires the CPU invokes it out of band, preempting whatever was running. Like a webhook handler, an interrupt handler must be fast and non-blocking: do the minimum, acknowledge, and defer heavy work — because while you're in it, you're blocking other events.

Top half vs bottom half

Because a handler runs with interrupts disabled (or in a very restricted context) and delays everything else, Linux splits interrupt work in two:

  • Top half (the hard IRQ handler). Runs immediately, in interrupt context. Must be minimal: acknowledge the device, grab the data or note what happened, and schedule the rest. Cannot sleep.
  • Bottom half (deferred work). The heavy lifting, run later in a context that can be preempted. Three mechanisms:
    • softirq — high-frequency, high-performance, statically defined (the network stack's RX/TX runs here); runs in interrupt context, can't sleep.
    • tasklet — a simpler API built on softirqs; serialized per-tasklet; also can't sleep.
    • workqueue — runs in a kernel thread (process context), so it can sleep and take mutexes — use when the deferred work might block.
Bridge

Top/bottom half is the fast-ack + async-queue pattern you use for webhooks: the handler does the bare minimum to acknowledge receipt within the tight deadline, drops the payload on a queue, and returns; a worker drains the queue and does the real processing. Softirq/tasklet are "process it on a lightweight deferred context, no blocking calls"; a workqueue is "hand it to a real worker thread that's allowed to block."

Threaded IRQs

Modern drivers often use threaded IRQs (request_threaded_irq): a tiny top-half "quick check" decides if the interrupt is really ours and wakes a dedicated kernel thread that runs the handler in process context. This gives clean code (the handler can sleep) and helps real-time kernels, which push nearly all IRQ work into threads so scheduling stays predictable.

// Register a handler. In modern PCIe you request MSI/MSI-X vectors first.
pci_alloc_irq_vectors(pdev, 1, nvec, PCI_IRQ_MSIX);   // prefer MSI-X
request_irq(pci_irq_vector(pdev, 0), my_isr, 0, "mydrv", dev);

static irqreturn_t my_isr(int irq, void *dev) {   // TOP HALF
    u32 st = ioread32(regs + IRQ_STATUS);
    if (!(st & MINE)) return IRQ_NONE;   // not ours (shared line)
    iowrite32(st, regs + IRQ_ACK);      // ack fast
    schedule_work(&my_work);            // defer heavy work → bottom half
    return IRQ_HANDLED;
}

MSI / MSI-X: interrupts as memory writes

Legacy PCI used physical interrupt pins — few in number, often shared between devices (hence the "is it ours?" check above). PCIe replaced them with Message-Signaled Interrupts: to raise an interrupt the device simply performs a special memory write to an address the OS programmed. MSI-X extends this to many independent vectors per device (up to 2048), each routable to a specific CPU. This is what lets a modern multi-queue NIC give each RX queue its own interrupt pinned to its own core — essential for scaling.

Interrupt affinity

Which CPU handles a given interrupt is the IRQ affinity (/proc/irq/N/smp_affinity, or irqbalance). Steering a device's interrupt to the same core (and NUMA node, §8) that processes its data keeps caches warm and avoids cross-core traffic — a standard tuning lever for high-throughput networking and storage.

Common mistake: doing real work in the top half

Sleeping, taking a mutex, calling copy_to_user, or doing a long loop in the hard-IRQ handler stalls the whole system and can deadlock (you can't sleep in interrupt context). The top half acknowledges and defers; the bottom half (workqueue if it must block, softirq/tasklet if not) does the work. A common probe hands you a "handler" that does a big memcpy and asks what's wrong.

8. Memory & Locality: Virtual Memory, NUMA, the Page Cache

The kernel is, above all, a memory manager. Three pieces of that show up constantly at the hardware boundary and in performance interviews: virtual memory (and MMIO's place in it), NUMA, and the page cache.

Virtual memory & where MMIO lives

Every process (and the kernel) sees virtual addresses; the MMU translates them to physical using page tables, caching translations in the TLB. The kernel maps not just RAM but also device MMIO regions (via ioremap, §5) into its virtual space — but marks those pages uncacheable / device memory so writes reach the device in order and reads always hit the hardware. This is why you can't treat an ioremap'd pointer like a normal array: it lives in the virtual address space but obeys device, not RAM, rules.

NUMA: data locality for RAM

A multi-socket server is Non-Uniform Memory Access: each CPU socket has its own memory controller and local DRAM. A core can reach any RAM, but reaching memory attached to another socket costs extra latency and crosses a limited inter-socket link. The system is modeled as NUMA nodes (roughly, one per socket) with a distance matrix (from ACPI's SLIT table, §4) telling the kernel how far each node is from each other.

Bridge

NUMA is data-locality / sharding for RAM. It's the same principle as keeping a request's data on the shard (or in the region) that serves it: reaching across the inter-socket link is your "cross-region hop," slower and bandwidth-limited. The whole game is co-locating a thread and the memory it touches on the same node — just like pinning a workload near its data.

Working with NUMA

  • First-touch policy. By default Linux allocates a page on the node of the CPU that first writes it — so which thread initializes the data decides where it lands. Allocate-and-initialize on the thread that will use it.
  • numactl / libnuma. Bind a process's memory and CPUs to a node: numactl --cpunodebind=0 --membind=0 ./app. Inspect topology with numactl --hardware or lscpu.
  • Per-node allocation in the kernel. Drivers use kmalloc_node/alloc_pages_node to place DMA buffers and rings on the node local to the device (a device hangs off one socket's PCIe root complex). Pair that with IRQ affinity on the same node (§7).
NUMA: each socket has local DRAM reachable quickly; reaching the other socket's memory crosses the inter-socket link at higher latency. Co-locate threads with the memory they touch.

The page cache

Reading a file the second time is fast because the kernel keeps recently-used file pages in RAM — the page cache. Reads are served from it on a hit; writes go to it and are flushed to disk later (write-back). It's why "free" RAM on a busy server is misleading (much of it is reclaimable cache), why a warm cache makes a benchmark lie, and why O_DIRECT exists for apps (databases) that manage their own caching and want to bypass it. fsync is how you force durability past the page cache.

Interview signal

"How does NUMA affect a hot path?" → cross-node memory access adds latency and competes for the inter-socket link, so a thread touching remote memory can be far slower than one touching local. Fix by pinning the thread and allocating its data on the same node (first-touch, numactl --membind, kmalloc_node) and steering the device's IRQs to that node too. Name first-touch — it's the detail that separates people who've actually tuned NUMA from those who've only read about it.

9. When It Breaks: Reading an Oops, Panic & the Log

Kernel bugs don't throw catchable exceptions — they print a diagnostic and either limp on or halt. Being able to read that diagnostic is what turns "the box rebooted" into a root cause.

Oops vs panic

  • An oops is the kernel detecting an internal error (e.g. a null dereference in a driver). It kills the offending context and dumps state, but tries to keep the system alive. A tainted, unstable kernel — you should reboot soon.
  • A panic is unrecoverable (or an oops in a context that can't be killed, like an interrupt or with panic_on_oops set): the kernel stops the machine. It can be configured to reboot after N seconds or to capture a crash dump.

Decoding the dump

An oops/panic prints a rich snapshot to the kernel log: the reason ("BUG: unable to handle kernel NULL pointer dereference"), the faulting RIP (function+offset/size), the call trace (the stack, symbolized if symbols are available), the CPU registers, and the taint flags (was a proprietary or out-of-tree module loaded?). The single most useful line is usually RIP: — the function and offset where it died — followed by the call trace showing how it got there.

# A trimmed oops as it appears via dmesg / the console:
BUG: unable to handle kernel NULL pointer dereference at 0000000000000000
RIP: 0010:my_read+0x2a/0x80 [mydrv]        # faulting function+offset [module]
Call Trace:
 vfs_read+0x9d/0x150
 ksys_read+0x5f/0xe0
 do_syscall_64+0x38/0x90                    # came in via a syscall (§2)
Modules linked in: mydrv(OE)                # O=out-of-tree, E=unsigned → tainted

The everyday toolbox

ToolUse for
dmesg / journalctl -kRead the kernel ring buffer: oops, driver messages, printk output, OOM-killer events.

"Tainted" is a clue, not noise

The taint flags on an oops tell you the environment: O/E mean an out-of-tree/unsigned module was loaded, G/P distinguish GPL vs proprietary, D means a previous oops already occurred. If a crash shows a proprietary driver in "Modules linked in" and a taint flag, that's your first suspect. Upstream maintainers will ask you to reproduce without the tainting module.

Debug workflow

Start at dmesg. Read the RIP: line for the faulting function, the call trace for how you got there, and Modules linked in + taint for what to suspect. Reproduce with more printk/ftrace; for a hard hang or repeatable panic, capture a kdump vmcore and open it in crash. Escalate to kgdb when you need to single-step live.

10. Common Interview Questions

The kernel/hardware boundary is a common focus for systems-software and firmware roles because it's hard to fake: you either know how the pieces connect or you don't. Here are the questions that come up again and again, with the answers a strong candidate gives.

Q: Walk me through exactly what happens when a program calls read().
The libc wrapper puts the syscall number (read) in rax and args in rdi/rsi/rdx, then executes SYSCALL. The CPU switches to ring 0 and jumps to the kernel's registered entry point. The kernel indexes the syscall table to reach sys_read, validates the arguments, and — critically — uses copy_to_user to move data into the caller's buffer rather than dereferencing the user pointer directly. If data isn't ready the thread may sleep. Finally SYSRET returns to ring 3 with the byte count (or a negative errno) in rax. A syscall is a mode switch, not a context switch — same thread, higher privilege.

Q: Here's a char driver's read(). Critique it.
The things I check: does it use copy_to_user (not memcpy) and check its return for -EFAULT? Does it clamp the requested length to the buffer size (no overflow)? Does it return the number of bytes actually delivered (and advance *off for a seekable device)? Does it avoid sleeping while holding a spinlock, and avoid unbounded stack buffers (kernel stack is tiny)? The classic bug is memcpy(kbuf, ubuf, n) — trusting a raw user pointer — which is a security hole and a crash waiting to happen.

Q: Coherent vs streaming DMA — when do you use each?
Coherent (dma_alloc_coherent) for long-lived buffers both CPU and device poke frequently — descriptor rings, mailboxes — where you want the mapping kept consistent with no manual cache management. Streaming (dma_map_single/_sg) for one-shot transfers like a single packet or block: you map with a direction, hand ownership to the device, and unmap when it's done. Streaming is cheaper and cacheable but you must not touch the buffer while the device owns it, and the direction argument drives the cache flush/invalidate on non-coherent hardware.

Q: What does the IOMMU protect against, and why does virtualization need it?
Without an IOMMU, any DMA-capable device can read or write arbitrary physical memory — a driver bug or malicious peripheral can scribble over the kernel or another VM. The IOMMU (VT-d/AMD-Vi/SMMU) gives each device its own address space via per-device page tables and blocks unmapped accesses — an MMU for devices. Virtualization needs it for safe PCIe passthrough/SR-IOV: it remaps a device's DMA into the guest's memory so the guest drives real hardware at near-native speed while staying confined to its own RAM.

Q: Why split interrupt handling into top and bottom halves?
The top half runs in interrupt context with other interrupts (or preemption) disabled and can't sleep, so it must be minimal — ack the device, note what happened, and defer. The bottom half does the heavy work later: softirq/tasklet for fast non-blocking work (the network stack lives in softirq), or a workqueue when the work might sleep (it runs in a kernel thread). Doing a big copy or taking a mutex in the top half stalls the system and can deadlock. Threaded IRQs push most of the work into a kernel thread for cleaner, more predictable handling.

Q: How does NUMA affect a hot path, and how do you tune for it?
On a multi-socket box, memory hangs off a specific socket; a core reaching another socket's RAM pays extra latency and shares a limited inter-socket link. A hot thread touching remote memory can be dramatically slower. Fix it by co-locating: pin the thread to a node, allocate its data on that node (Linux's first-touch policy means the initializing thread decides placement — so initialize on the using thread), use numactl --membind or kmalloc_node, and steer the device's MSI-X interrupts to the same node. First-touch is the detail that shows real experience.

Q: What's the difference between MMIO and DMA?
MMIO is the CPU reaching the device: device registers are mapped into physical address space (via BARs), and the CPU reads/writes them one access at a time — great for control, too slow for bulk data. DMA is the device reaching memory: the device reads/writes RAM itself in bursts while the CPU does other work, then interrupts on completion. Control plane goes over MMIO; data plane goes over DMA. Both are set up by the driver in probe().

One-line summary

The kernel is a privileged runtime that owns the hardware: you reach it by trapping across the ring boundary with a syscall (§1–§2), extend it with modules and drivers that implement file_operations vtables (§3), and it discovers devices through the bus/device/driver model backed by ACPI or Device Tree (§4). Talking to a real device means MMIO through BARs for control (§5), DMA for bulk data with the IOMMU enforcing isolation (§6), and interrupts split top/bottom half for completion (§7) — all shaped by virtual memory, NUMA locality, and the page cache (§8), and debugged by reading the oops, call trace, and taint flags when it breaks (§9).
