The App Model — Activities, Fragments & Components

What an Android app actually is, and why it feels so different from a web server or a desktop program.

The analogy first. A web server owns its own main(): it starts, runs a loop, and stops when you tell it to. An Android app does not. Think of your app as a set of rooms in a building the operating system owns. The OS decides when to open a room (a screen), when to send someone away because a phone call arrived, and when to demolish the whole building to free up space. Your code is a collection of callbacks the OS invokes — you react; you don't drive.

INSIGHT

The single biggest mental shift for a backend/web engineer: you don't control your own process lifetime. The system can pause, stop, recreate, or outright kill your components at almost any time. Almost every Android "pitfall" — configuration changes, ANRs, leaks, lost state — is a consequence of this one fact.

The four app components

Every Android app is built from four kinds of entry points the system can launch independently. Each is declared in the AndroidManifest.xml.

ComponentWhat it isWeb/backend analogy
ActivityOne screen the user interacts with (e.g. an inbox screen). The primary UI entry point.A page / route handler
ServiceLong-running work with no UI (playing music, syncing). Modern apps prefer WorkManager for deferrable jobs.A background worker / cron job

Activities and Fragments

An Activity is a full screen. A Fragment is a reusable, embeddable slice of UI with its own lifecycle that lives inside an Activity — think a master list and detail pane that rearrange on a tablet vs. a phone. Historically apps had many Activities; the modern pattern is single-Activity architecture: one Activity hosts many Fragments (or, with Compose, many composable "screens") and the Navigation component swaps between them.

AWhy Fragments exist (and why they're notorious)CONTEXT▶
  • The good: reusable UI across screen sizes; a back stack managed by the FragmentManager; independent lifecycle so a piece of UI can be added/removed dynamically.
  • The pain: a Fragment has two lifecycles (the Fragment and its View), which is a classic leak source; nested-fragment and state-restoration bugs are common enough that "Fragment lifecycle" is a standard interview topic.
  • Where it's going: Jetpack Compose largely removes the need for Fragments as UI containers — a "screen" is just a composable function — but Fragments remain everywhere in existing codebases, so know them.
NOTE FOR WEB / BACKEND READERS

Map it to what you know: an Activity ≈ a route/page, the manifest ≈ your route table + deployment descriptor, an Intent ≈ a request/redirect (used both to navigate within your app and to hand work to other apps), and the process ≈ a container the platform can OOM-kill at will. The crucial difference: there is no long-lived server object you own. State that would live in a request-scoped session on the server must instead survive on the client across recreation — which is exactly what ViewModel and saved state solve.

INTERVIEW ANGLE

If asked "what happens when a user taps your app icon?", don't jump to UI. Say: the system resolves the launcher Activity from the manifest's intent-filter, starts (or reuses) your process, instantiates the Activity, and drives it through onCreate → onStart → onResume. Naming the manifest, the process, and the lifecycle in one breath signals you understand Android's ownership model, not just widgets.

The Activity Lifecycle

The state machine every Android engineer must know cold — plus configuration-change recreation and process death/restore, the two cases that separate juniors from seniors.

Analogy. A lifecycle callback is the OS knocking on your door to say what's about to happen: "you're now visible" (onStart), "you have the user's attention" (onResume), "someone else is taking the stage — wrap up fast" (onPause). You do the right cleanup/setup in each. Miss one and you leak resources, drain battery, or lose the user's data.

TRAP — the two cases juniors miss

(1) Configuration change: a rotation, dark-mode toggle, or language change destroys and recreates the Activity by default. Any state held in Activity fields is lost. (2) Process death: a backgrounded app can be killed with no callbacks at all — your ViewModel and every in-memory object vanish. On return, the system recreates your task from a fresh process. If you only kept state in memory, the user loses their work.

THE FIX

Two tools, two jobs. A ViewModel survives configuration changes (it's scoped to the screen, not the Activity instance) — put screen state there. A SavedStateHandle / onSaveInstanceState Bundle survives process death — the system holds it as a parcel (in the ActivityManager) and redelivers it when your process is recreated, so put the small essentials there (a scroll position, a draft text, the selected id). It does not survive a reboot or a user-initiated dismissal (swiping the app away). Big data is re-fetched from Room/network on restore.

INTERVIEW ANGLE

Expect "what happens when the user rotates the screen while a network call is in flight?" The strong answer: the Activity is destroyed and recreated, but the ViewModel and its viewModelScope coroutine survive, so the call is not restarted; when it completes it updates the ViewModel's StateFlow, and the recreated UI re-collects the latest state. Then volunteer the harder case — process death — and note that only SavedStateHandle survives it. That two-tier answer is the senior signal.

The Modern Stack — Kotlin, Compose, ViewModel, Flow

What a brand-new Android app is built from in the mid-2020s, and why each piece exists.

Analogy. If you know React with hooks, you already know most of modern Android. Jetpack Compose is React for native UI: you write functions that return UI as a function of state, and the framework re-renders (re-composes) when state changes. StateFlow is your observable store; ViewModel is where that store lives so it survives screen rotations; Coroutines are async/await.

Kotlin

Officially supported since 2017 and Google's preferred (Kotlin-first) language since 2019. Highlights an interviewer expects you to name: null safety in the type system (String vs String?), coroutines for structured concurrency, concise data classes, sealed classes for exhaustive state modeling, and extension functions. Java interop is seamless, so mixed codebases are normal.

Jetpack Compose — declarative UI

The old way (Android Views / XML) was imperative: you built a view tree in XML, found widgets by id, and mutated them (textView.setText(...)). Compose is declarative: the UI is a pure function of state, and you never mutate widgets by hand.

// Declarative UI: describes what to show for a given state.
// When `state` changes, Compose re-invokes this and updates only what differs.
@Composable
fun ProfileScreen(vm: ProfileViewModel = hiltViewModel()) {  // Hilt supplies repo + userId
    val ui by vm.state.collectAsStateWithLifecycle()
    when (val s = ui) {
        is ProfileUiState.Loading -> CircularProgressIndicator()
        is ProfileUiState.Success -> Text(s.user.name)
        is ProfileUiState.Error   -> ErrorView(s.message, onRetry = vm::reload)  // no-arg retry
    }
}
RECOMPOSITION

Compose's snapshot system tracks reads of snapshot state (State<T>). A StateFlow is not observed directly — it becomes observable only once you collect it into a State<T> via collectAsState()/collectAsStateWithLifecycle(). When a value a composable read changes, only that composable (and its subtree) re-runs — this is recomposition. Keep composables side-effect-free and cheap; do side effects in LaunchedEffect/DisposableEffect, not inline.

ViewModel — where state lives

A ViewModel holds and prepares UI state and survives configuration changes. It exposes state and receives events; it must never hold a reference to a View, Activity, or any UI Context (that would leak on rotation).

class ProfileViewModel(
    private val repo: UserRepository,
    private val userId: String,          // captured once; retry needs no argument
) : ViewModel() {

    private val _state = MutableStateFlow<ProfileUiState>(ProfileUiState.Loading)
    val state: StateFlow<ProfileUiState> = _state.asStateFlow()

    init { reload() }

    fun reload() {                                // () -> Unit, so vm::reload fits onRetry
        viewModelScope.launch {                     // auto-cancels when the VM clears
            _state.value = ProfileUiState.Loading
            _state.value = try {
                ProfileUiState.Success(repo.user(userId))
            } catch (e: IOException) {
                ProfileUiState.Error(e.message.orEmpty())
            }
        }
    }
}

Coroutines & Flow — async without callbacks

A coroutine is a suspendable computation: suspend functions look synchronous but yield the thread while waiting (no callback pyramids). A Flow is a cold, asynchronous stream — a sequence of values over time (like an Observable). StateFlow/SharedFlow are hot Flows for state and events.

// A cold Flow that emits, combines, and stays off the main thread.
fun searchResults(query: Flow<String>): Flow<List<Item>> =
    query
        .debounce(300)                 // wait for typing to settle
        .distinctUntilChanged()
        .flatMapLatest { q -> repo.search(q) } // cancels the stale search
        .flowOn(Dispatchers.IO)          // upstream runs on IO threads
INTERVIEW ANGLE

Be ready to justify StateFlow over LiveData ("always-valued, richer operators, and one concurrency model with the rest of my coroutine code") and to explain cold vs hot Flows (a cold Flow re-runs its producer per collector; a hot StateFlow shares one value among collectors). If you mention flatMapLatest for search-as-you-type and collectAsStateWithLifecycle to avoid collecting while the screen is stopped, you read as current.

App Architecture — MVVM, MVI & Unidirectional Data Flow

How to structure a screen so state is predictable and testable — the recurring senior-level design question.

Analogy. Unidirectional data flow (UDF) is a one-way conveyor belt: events go up (the user taps, the UI tells the ViewModel), state comes down (the ViewModel produces new state, the UI renders it). There is exactly one source of truth and one direction of change, so you can always answer "why does the screen look like this?" by reading the current state object.

The layers

  • UI layer (Compose): stateless composables that render a UiState and forward user events upward. No business logic.
  • ViewModel: converts events into new state, holds the StateFlow<UiState> that is the screen's single source of truth.
  • Data layer: a Repository hides the details of Room, Retrofit, and caching behind a clean interface — the ViewModel never talks to a database or the network directly.

MVVM vs MVI

MVVMMVI
State shapeOften several observable fieldsOne immutable UiState per screen
EventsViewModel exposes methodsA single onEvent(Intent) reducer
StrengthSimple, less boilerplateFully predictable; trivial to time-travel/replay/test
CostState can drift across fieldsMore ceremony for small screens
 
// MVI: one immutable state + one event entry point (a reducer).
data class UiState(val loading: Boolean = false, val items: List<Item> = emptyList())

sealed interface Event {
    data object Refresh : Event
    data class Select(val id: String) : Event
}

fun onEvent(e: Event) = when (e) {
    Event.Refresh   -> refresh()
    is Event.Select -> open(e.id)
}
MODEL STATE, DON'T FLAG IT

Prefer a sealed interface UiState { Loading; Success(data); Error(msg) } over three separate booleans (isLoading, hasError…). Sealed hierarchies make illegal states unrepresentable and force an exhaustive when in the UI — the compiler catches the case you forgot.

INTERVIEW ANGLE

"Design the architecture for a screen that loads a list, supports pull-to-refresh, and handles errors." Draw the three layers, put a single immutable UiState in the ViewModel, route user actions through one event function, and keep the Composable stateless. Then name the payoff: testability (the ViewModel is a plain class you unit-test with a fake repository) and survivability (state in the ViewModel outlives rotation). Mentioning dependency injection (Hilt) for supplying the repository is a bonus.

The Main Thread, ANRs & the 16 ms Frame Budget

Why one thread rules everything, why blocking it is fatal, and the math behind smooth scrolling.

Analogy. The main (UI) thread is a single cashier serving one line. It handles input events, runs your callbacks, and draws every frame. If you make the cashier do a slow task (a network call, a big file read), the entire line freezes — the screen stops responding. Do it long enough and Android shows the dreaded "Application Not Responding" (ANR) dialog.

The two rules of the main thread

Rule 1: Never block it

  • No network, disk, or heavy CPU work on the main thread.
  • Input events not handled within ~5 s → ANR.
  • A BroadcastReceiver that runs >10 s → ANR.

Rule 2: Only it can touch UI

  • All UI/state updates must happen on the main thread.
  • Background work must hand results back to it.
  • Coroutines make this a one-liner (withContext).
// WRONG — blocks the main thread → frozen UI → ANR
fun onClick() {
    val data = api.fetchBlocking()   // network call on the UI thread!
    render(data)
}

// RIGHT — suspend off the main thread, resume on it to update state
fun load() = viewModelScope.launch {          // starts on the main dispatcher
    _state.value = UiState.Loading
    val data = withContext(Dispatchers.IO) { api.fetch() }  // off-thread
    _state.value = UiState.Success(data)        // back on main — safe
}

The 16 ms frame budget & jank

A 60 Hz display refreshes every 1000 ms ÷ 60 ≈ 16.67 ms. To render smoothly, all your work for a frame — measure, layout, draw, recomposition — must finish inside that window. Miss it and the previous frame is shown again: a dropped frame, perceived as stutter or jank. On a 120 Hz display the budget shrinks to ~8.3 ms.

  • Common jank causes: heavy work in a composable/onBind, large-image decoding on the main thread, unbounded recomposition, synchronous disk reads, allocation storms triggering GC pauses.
  • Tools to name: Android Studio Profiler, Systrace/Perfetto, the Layout Inspector, Compose recomposition counts, and StrictMode to catch main-thread disk/network in debug builds.
INTERVIEW ANGLE

Connect the two ideas: ANR is the catastrophic end of the same spectrum whose mild end is jank — both come from doing too much on the main thread. If asked "the list scrolls choppily, how do you debug it?", answer with the budget (16.67 ms), profile to find the frame that overruns, then move the offending work off-thread (coroutine + Dispatchers.IO/Default), cache decoded images, and reduce recomposition scope. Quantify it — naming the 16.67 ms budget is a strong signal.

Memory & Leaks

Android's aggressive process killing plus long-lived references make leaks a top interview and production topic.

Analogy. A memory leak is a guest who won't leave. The Activity's "party" (its screen) is over and the OS wants to reclaim the room, but something is still holding the guest's coat — a reference — so the garbage collector can't clear it. Rotate the screen a few times and you've got a pile of dead Activities stuck in memory, eventually an OutOfMemoryError.

The classic leak: holding a Context/Activity

// LEAK 1 — a static/singleton holds an Activity Context forever
object ImageCache { var ctx: Context? = null }   // never store an Activity here

// LEAK 2 — a delayed callback outlives the screen and captures it
Handler(Looper.getMainLooper()).postDelayed({ useActivity() }, 60_000)

// SAFE — use applicationContext for long-lived needs, and
// lifecycle-scoped coroutines that auto-cancel on onDestroy
val appCtx = context.applicationContext            // lives as long as the app
lifecycleScope.launch { /* cancelled when the owner is destroyed */ }

Why an Activity Context is dangerous

  • An Activity Context is tied to one screen instance; retaining it past onDestroy pins the whole view hierarchy in memory.
  • The application Context lives for the app's lifetime — use it for singletons, DI graphs, and anything long-lived. But never use it to inflate UI or show a dialog (it has no theme/window).
  • Non-static inner classes, listeners, and Handler callbacks implicitly capture their outer Activity — a frequent silent leak.

Lifecycle-aware components — the modern defense

Jetpack ties work to a Lifecycle so it starts and stops itself automatically — no manual cleanup to forget.

ToolScoped toAuto-cleanup
viewModelScopeViewModelCoroutines cancel when the VM is cleared
lifecycleScopeActivity/FragmentCancels on onDestroy
repeatOnLifecycleA target state (e.g. STARTED)Collection stops when below that state
DisposableEffectA composable's presenceRuns onDispose cleanup on leave
TIP

Name LeakCanary — the standard library that auto-detects retained Activities/Fragments in debug builds and prints the reference chain holding them. "I'd add LeakCanary and read the leak trace" is a concrete, credible answer.

INTERVIEW ANGLE

Expect "your app's memory grows every time the user rotates — what's happening?" The answer walks the leak: rotation recreates the Activity, but something (a static field, a running thread, a registered listener, a ViewModel that wrongly holds a View) still references the old instance, so the GC can't collect it. Fix by using applicationContext for long-lived refs, lifecycle-scoped coroutines, unregistering listeners in onStop, and never letting a ViewModel touch a View. Cite LeakCanary as your detection tool.

Storage & Networking — Room & Retrofit

Local persistence and remote APIs, and the offline-first pattern that ties them together.

Room — a typed layer over SQLite

Analogy. SQLite is the embedded relational database every Android device ships with; Room is the ORM (like an ActiveRecord/JPA) that turns raw SQL and cursors into typed Kotlin — with compile-time verification of your queries. Room can return a Flow, so the UI updates automatically whenever the underlying rows change.

@Entity(tableName = "user")
data class UserEntity(@PrimaryKey val id: String, val name: String)

@Dao
interface UserDao {
    @Query("SELECT * FROM user WHERE id = :id")
    fun observe(id: String): Flow<UserEntity?>   // reactive: re-emits on change

    @Insert(onConflict = OnConflictStrategy.REPLACE)
    suspend fun upsert(user: UserEntity)          // suspend: runs off main thread
}

Other storage options to name: DataStore (the modern replacement for SharedPreferences, coroutine/Flow-based) for small key–value or typed settings; app-private files and the MediaStore for large binaries. Don't put big blobs in a database.

Retrofit + OkHttp — the networking stack

OkHttp is the HTTP client (connection pooling, timeouts, interceptors, caching). Retrofit sits on top and turns an annotated Kotlin interface into a type-safe API client; suspend functions integrate directly with coroutines. The call returns a DTO (Data Transfer Object) — the raw wire/JSON shape; toDomain() converts it to the clean model the app uses, and toEntity() converts it to the Room row that gets stored.

interface UserApi {
    @GET("users/{id}")
    suspend fun getUser(@Path("id") id: String): UserDto
}

val api: UserApi = Retrofit.Builder()
    .baseUrl("https://api.example.com/")
    .client(OkHttpClient.Builder().addInterceptor(logging).build())
    .addConverterFactory(MoshiConverterFactory.create())   // JSON ↔ DTO
    .build()
    .create(UserApi::class.java)

Offline-first: single source of truth

The senior pattern: the UI reads only from the database; the network's job is to keep the database fresh. Room emits a Flow the UI collects, so a successful sync silently updates the screen.

// Repository (holds an injected repoScope: CoroutineScope): DB is the source of truth; network refreshes it.
fun user(id: String): Flow<User> = dao.observe(id)
    .onStart { repoScope.launch { refresh(id) } }  // kick a NON-blocking refresh — don't await, or cached rows are delayed on a slow network
    .filterNotNull()
    .map { it.toDomain() }

private suspend fun refresh(id: String) {
    runCatching { dao.upsert(api.getUser(id).toEntity()) }  // write-through
}
INTERVIEW ANGLE

For "design the data layer for a feed that works offline", present offline-first with a single source of truth: Retrofit fetches, Room persists, the UI observes Room via Flow. Mention cache invalidation/refresh policy, WorkManager for reliable background sync (survives process death and reboots), and pagination (the Paging 3 library). The phrase "the database is the single source of truth, the network only refreshes it" is the one interviewers wait to hear.

The Manifest, Permissions & Gradle

The declaration file that defines your app to the OS, the runtime-permission model, and the build system that assembles it all.

AndroidManifest.xml

Analogy. The manifest is your app's passport plus floor plan: it declares who the app is (package, components), what rooms exist (Activities/Services), how it can be entered (intent-filters — including the launcher icon and deep links), and what capabilities it needs (permissions). The OS reads it before running a single line of your code.

<!-- AndroidManifest.xml -->
<manifest>
    <uses-permission android:name="android.permission.INTERNET" />
    <uses-permission android:name="android.permission.CAMERA" />

    <application android:name=".MyApp">
        <activity android:name=".MainActivity" android:exported="true">
            <intent-filter>
                <action   android:name="android.intent.action.MAIN" />
                <category android:name="android.intent.category.LAUNCHER" />
            </intent-filter>
        </activity>
    </application>
</manifest>

Permissions — install-time vs runtime

  • Normal permissions (e.g. INTERNET) are granted at install; just declare them.
  • Dangerous permissions (camera, location, contacts) must be requested at runtime (Android 6 / API 23+) and can be revoked by the user at any time — so check before every sensitive use.
  • Modern APIs prefer scoped, purpose-built contracts (e.g. the photo picker) that need no broad permission at all.
// Runtime request for a dangerous permission (Compose / Activity Result API)
val launcher = rememberLauncherForActivityResult(
    ActivityResultContracts.RequestPermission()
) { granted -> if (granted) openCamera() else showRationale() }

Button(onClick = { launcher.launch(Manifest.permission.CAMERA) }) {
    Text("Take photo")
}

Gradle — the build system

Analogy. Gradle is Android's npm+webpack+make combined: it resolves dependencies, compiles Kotlin, merges manifests and resources, runs annotation processors, and packages the signed APK/AAB. The key files: a top-level project build script, a per-module build.gradle.kts, and a libs.versions.toml version catalog.

// app/build.gradle.kts — module build configuration (Kotlin DSL)
plugins {
    id("com.android.application")
    id("org.jetbrains.kotlin.android")
}
android {
    namespace = "com.example.app"
    compileSdk = 35
    defaultConfig {
        applicationId = "com.example.app"
        minSdk = 24        // oldest OS you support
        targetSdk = 35     // OS behavior you target
    }
    buildTypes {
        release { isMinifyEnabled = true }   // R8 shrink/obfuscate
    }
    buildFeatures { compose = true }
}
dependencies {
    implementation(platform("androidx.compose:compose-bom:2024.09.00"))
    implementation("androidx.activity:activity-compose:1.9.2")
}

INTERVIEW ANGLE

Two common ones here. (1) "What's the difference between minSdk and targetSdk?" — install floor vs behavior target; a low minSdk widens your audience but forces compatibility handling. (2) "How do you handle a permission the user denied?" — check state, show a rationale, and degrade gracefully rather than nagging or crashing, because dangerous permissions can be revoked at any time. Knowing APK vs AAB and that R8 minifies release builds rounds out the "ships to production" signal.
