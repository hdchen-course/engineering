Recursion & Backtracking

Six Google-style recursion & backtracking problems • original framing, execution-tested solutions, and interviewer probes

Note: Representative big-tech-style problems — not sourced from Google. The “Google-style” badge denotes the flavor of question, not its source.

How to read this chapter: every worked example uses inputs invented for this book, and each stated output was produced by compiling and running the accompanying Java — for the large result sets, the printed count and a few members were read straight off the program’s output. Beyond hand-picked edge cases (an empty input, single-element inputs, the leading-zero and odd-length cases, and dictionary words absent from the board) each solution was cross-checked against an independent brute force: the parenthesis, strobogrammatic, and unlock-pattern counts were differentially tested against exhaustive enumerators, and Word Search II / Word Squares against thousands of random boards and dictionaries. The recurring idea below is the backtracking skeleton — choose, recurse, undo — sharpened by pruning (only extend states that can still succeed) and by state structures (a Trie, a prefix index, or a “skip” table) that make each choice cheap and each dead end obvious.

Generate Parentheses

Medium Google-style

Problem

Given a count n, produce every string of n pairs of parentheses that is well-formed — every open bracket eventually closed, and never a closing bracket without a matching open before it.

  • Each output has length 2n and uses exactly n '(' and n ')'.
  • The number of valid strings is the n-th Catalan number, so the result set grows fast: 1, 1, 2, 5, 14, 42, …

Example: for n = 3 the code prints all 5 combinations (computed by running it): ((())), (()()), (())(), ()(()), ()()(). That count matches Catalan(3) = 5; for n = 4 the program returns 14 strings, again equal to Catalan(4).

Approach & Intuition

Backtrack while tracking two counters — how many '(' and how many ')' we have placed so far. The two rules that keep every prefix valid are simple: we may add an open bracket whenever open < n, and we may add a close bracket only when close < open (there is an unmatched open waiting for it). When the string reaches length 2n it is guaranteed well-formed, so we record it. Because we only ever build legal prefixes, there's no wasted work and no validity check at the end — the constraints are the pruning.

public List<String> generateParenthesis(int n) {
    List<String> res = new ArrayList<>();
    backtrack(res, new StringBuilder(), 0, 0, n);
    return res;
}
// open = '(' placed so far, close = ')' placed so far
private void backtrack(List<String> res, StringBuilder sb,
                       int open, int close, int n) {
    if (sb.length() == 2 * n) {          // used all 2n slots -> a valid combo
        res.add(sb.toString());
        return;
    }
    if (open < n) {                        // still room to open a new pair
        sb.append('(');
        backtrack(res, sb, open + 1, close, n);
        sb.deleteCharAt(sb.length() - 1);  // undo the choice (backtrack)
    }
    if (close < open) {                    // close only if an open is unmatched
        sb.append(')');
        backtrack(res, sb, open, close + 1, n);
        sb.deleteCharAt(sb.length() - 1);
    }
}

Complexity: Time O(Catalan(n) · n) — there are Catalan(n) = C(2n, n)/(n+1) valid strings and each costs O(n) to build and copy; asymptotically that is O(4n / √n). Space O(n) for the recursion depth and the working buffer (excluding the output list).

Common pitfalls / interviewer probes: The close guard is close < open, not close < n. Gating a close on the number of unmatched opens is what keeps every prefix legal; comparing against n would emit strings like ())(. Undo after recursing. A single shared StringBuilder is efficient, but you must delete the last char after each branch or sibling calls inherit stale characters. The count is Catalan(n). A great sanity check — if your output size is not 1, 1, 2, 5, 14, … you are either duplicating or missing states. Don’t generate-then-filter. Producing all 22n bracket strings and validating each is exponentially wasteful; the two counters prune illegal branches at the root.

Letter Combinations of a Phone Number

Medium Google-style

Problem

Given a string of digits 2–9, return every letter combination the number could spell on a classic phone keypad, where 2→abc, 3→def, …, 7→pqrs, 8→tuv, 9→wxyz.

  • Each digit contributes one letter to each combination, so the answer count is the product of the digits’ letter-set sizes.
  • Empty input maps to an empty list — not a list containing the empty string.

Example: for "29" the code returns all 12 combinations (computed by running it): aw, ax, ay, az, bw, bx, by, bz, cw, cx, cy, cz — digit 2 offers {a,b,c} and 9 offers {w,x,y,z}, so 3 × 4 = 12. For "7" alone the output is [p, q, r, s], and for the empty string "" the output is the empty list [].

Approach & Intuition

Backtrack across digit positions. Keep a lookup from each digit to its letters. Process the digits left to right; at position i, loop over that digit’s letters, append one, recurse to position i + 1, then remove it. When the index reaches the end of the string, one letter has been chosen for every digit, so the buffer is a complete combination. The recursion tree has one level per digit and one branch per available letter — a clean Cartesian product.

private static final String[] PAD = {
    "", "", "abc", "def", "ghi",
    "jkl", "mno", "pqrs", "tuv", "wxyz"
};
public List<String> letterCombinations(String digits) {
    List<String> res = new ArrayList<>();
    if (digits == null || digits.isEmpty()) return res;  // empty -> empty list
    backtrack(digits, 0, new StringBuilder(), res);
    return res;
}
private void backtrack(String digits, int i,
                       StringBuilder sb, List<String> res) {
    if (i == digits.length()) {          // one letter chosen per digit
        res.add(sb.toString());
        return;
    }
    String letters = PAD[digits.charAt(i) - '0'];
    for (int k = 0; k < letters.length(); k++) {
        sb.append(letters.charAt(k));   // choose a letter for digit i
        backtrack(digits, i + 1, sb, res);
        sb.deleteCharAt(sb.length() - 1);  // undo
    }
}

Complexity: Time O(4d · d) where d is the number of digits — up to 4 letters per digit and O(d) to materialise each of the up-to-4d strings. Space O(d) for the recursion depth and buffer, plus the output.

Common pitfalls / interviewer probes: Empty input is a special case. Returning a list with one empty string (because the base case fires immediately) is the classic off-by-one; guard digits.isEmpty() up front and return an empty list. Index the pad by digit - '0'. A common slip is indexing by the character or forgetting that 0 and 1 carry no letters. Undo after each branch. As with all backtracking over a shared buffer, remove the appended letter before trying the next. Output size = product of set sizes. A quick check: "238" maps to {a,b,c} × {d,e,f} × {t,u,v}, so 3 × 3 × 3 = 27 combinations — remember that 7 and 9 carry four letters while every other digit carries three.

Strobogrammatic Number II

Medium Google-style

Problem

A number is strobogrammatic if it reads the same after being rotated 180° (turned upside down). Given a length n, return all strobogrammatic numbers of exactly that many digits, as strings.

  • The only digits that survive a rotation are 0↔0, 1↔1, 8↔8, and the swap pair 6↔9.
  • No leading zero at the full width (so "0" is valid for n = 1, but "00" and "010" are not valid answers for n = 2, 3).

Example: for n = 2 the code returns [11, 69, 88, 96] (computed by running it) — note 00 is excluded as a leading zero. For n = 3 it returns 12 numbers, including 101, 111, 181, 609, 619, 689, 808, 818, 888, 906, 916, 986; the middle digit is one of {0, 1, 8} (the self-rotating digits), while 6/9 may only appear as an outer pair.

Approach & Intuition

Build from the outside in, two digits at a time. Recurse on the length: a length-0 core is the single empty string, a length-1 core is {0, 1, 8} (the only digits that are their own rotation, valid as a middle digit). For any larger width, first solve the inner core of length len - 2, then wrap each inner string with a rotation pair placed on the far left and far right — one of (0,0), (1,1), (6,9), (8,8), (9,6). The single subtlety is the leading zero: track the final target length and, when the current wrap is the outermost layer (len == total), skip the (0,0) pair so the number never starts with 0.

public List<String> findStrobogrammatic(int n) {
    return build(n, n);   // len = width being built; total = final width
}
// Returns all strobogrammatic strings of length `len`.
private List<String> build(int len, int total) {
    if (len == 0) return new ArrayList<>(List.of(""));           // even base
    if (len == 1) return new ArrayList<>(List.of("0", "1", "8"));  // odd middle
    List<String> inner = build(len - 2, total);       // solve the core first
    List<String> res = new ArrayList<>();
    // rotate-by-180 pairs: {outside-left, outside-right}
    int[][] pairs = {{0,0}, {1,1}, {6,9}, {8,8}, {9,6}};
    for (String s : inner) {
        for (int[] p : pairs) {
            // no leading zero once we are at the full width
            if (len == total && p[0] == 0) continue;
            res.add(p[0] + s + p[1]);
        }
    }
    return res;
}

Complexity: Time O(n · 5n/2) — there are on the order of 5n/2 results (four choices at the outermost layer, five at each inner layer) and each string of length n is assembled in linear time. Space O(n) recursion depth plus the output.

Common pitfalls / interviewer probes: Leading zero only at the top layer. (0,0) is perfectly legal in the interior (e.g. the 0s in 1001 or 609) — suppress it only when len == total. That is why the recursion threads the final total through, rather than deciding from len alone. Odd length needs the {0,1,8} middle. For odd n the center digit must map to itself, so 6 and 9 are forbidden there; the length-1 base case encodes exactly this. 6 and 9 swap. The outer-left 6 pairs with an outer-right 9 and vice-versa — getting the orientation backwards produces numbers that fail the rotation. The empty-core base case matters. For even n the recursion bottoms out at length 0 returning [""]; returning an empty list there would wipe out every even-length answer.

Android Unlock Patterns

Medium Google-style

Problem

On a 3×3 grid of keys numbered 1–9, an unlock pattern is a sequence of distinct keys. Count how many valid patterns use between m and n keys (inclusive), obeying the phone’s skip rule.

  • The skip rule: to move directly from key a to key b, if a third key lies exactly on the straight segment between them (e.g. 2 sits between 1 and 3), that middle key must have already been visited.
  • Keys cannot repeat within a pattern.

Example: for m = 1, n = 2 the code returns 65 (computed by running it): all 9 single-key patterns, plus 56 two-key patterns. Why 56 and not 9 × 8 = 72? Sixteen ordered pairs are blocked because a key sits between them with nothing visited yet — the twelve straight jumps (the six lines with a key in the middle: rows 1–3, 4–6, 7–9 and columns 1–7, 2–8, 3–9, each direction) plus the four diagonals through the center (1–9, 3–7, each direction) — 12 + 4 = 16, leaving 72 - 16 = 56. Summing every length from 1 to 9 gives 389497.

Approach & Intuition

DFS from each starting key, pruning with a “skip” table. Precompute skip[a][b] = the key that lies on the straight line strictly between a and b (0 if none). During the walk, a move to an unvisited next is legal when either no key lies between (skip == 0) or the in-between key is already visited. Exploit symmetry to cut the work by roughly 3× (three representative starts instead of nine): the four corners are interchangeable, as are the four edge-midpoints, so we only DFS from key 1 (a corner), key 2 (an edge), and key 5 (the center), then multiply the corner and edge totals by 4.

private int[][] skip = new int[10][10];
private boolean[] visited = new boolean[10];

public int numberOfPatterns(int m, int n) {
    // skip[a][b] = the key lying on the straight segment between a and b
    skip[1][3] = skip[3][1] = 2;
    skip[1][7] = skip[7][1] = 4;
    skip[3][9] = skip[9][3] = 6;
    skip[7][9] = skip[9][7] = 8;
    skip[2][8] = skip[8][2] = 5;
    skip[4][6] = skip[6][4] = 5;
    skip[1][9] = skip[9][1] = 5;
    skip[3][7] = skip[7][3] = 5;
    int total = 0;
    for (int len = m; len <= n; len++) {
        // symmetry: 1 stands for all 4 corners, 2 for all 4 edges
        total += dfs(1, len - 1) * 4;
        total += dfs(2, len - 1) * 4;
        total += dfs(5, len - 1);      // center is unique
    }
    return total;
}
// remaining = how many more keys still to place after `cur`
private int dfs(int cur, int remaining) {
    if (remaining == 0) return 1;      // reached the target length
    visited[cur] = true;
    int count = 0;
    for (int next = 1; next <= 9; next++) {
        int mid = skip[cur][next];
        // legal if unvisited AND (nothing between, or the middle is visited)
        if (!visited[next] && (mid == 0 || visited[mid]))
            count += dfs(next, remaining - 1);
    }
    visited[cur] = false;             // backtrack
    return count;
}

Complexity: Time O(n!) in the worst case over the 9 keys (the search tree of distinct-key sequences up to length n), but with a tiny constant — only 9 keys, and the ×4 symmetry cuts the explored subtrees to three roots. Space O(1) beyond recursion depth (the fixed 10×10 skip table and visited flags).

Common pitfalls / interviewer probes: The skip rule is the whole problem. A move is blocked only when a key lies exactly between and is not yet visited; adjacent keys and knight-style moves (e.g. 1→6) never skip anything. Forgetting the visited[mid] exception over-blocks and undercounts. Center diagonals skip the center. 1↔9 and 3↔7 pass through 5 — a commonly missed entry in the skip table. Symmetry factor is 4, applied to corners and edges only. The center (5) is its own class and must not be multiplied. Getting this wrong is the top source of off-by-a-factor bugs; verify against a brute force. Reset visited on the way out. Because the counts for different starting keys share the array, the DFS must unmark cur before returning.

Word Search II

Hard Google-style

Problem

Given a grid of letters and a dictionary of words, return every dictionary word that can be spelled by a path of orthogonally adjacent cells (up/down/left/right), where no single cell is reused within one word.

  • Different words may reuse the same cells; the no-reuse rule applies within a single word’s path.
  • Each found word should appear once in the result even if it can be formed by multiple paths.

Example: for the board

o a t h
e t a e
i h k r
n d x v

and the dictionary ["oath", "eat", "hker", "rvxk", "zzz", "oa"], the code returns [eat, oa, oath, rvxk] (computed by running it, then sorted for display). oath snakes o(0,0)→a(0,1)→t(1,1)→h(2,1); rvxk walks r(2,3)→v(3,3)→x(3,2)→k(2,2). hker is absent (no adjacent path) and zzz has no matching cells.

Approach & Intuition

Load the dictionary into a Trie, then DFS the board once. A Trie lets a single traversal test all words simultaneously: as we step to a neighbouring cell we descend the Trie by that letter, and if there is no such child we abandon the branch immediately. When a Trie node marks the end of a word, we record it and null out its marker so it is never added twice. We mark a visited cell with a sentinel ('#') before recursing and restore it afterward — classic backtracking. A final optimisation prunes exhausted Trie leaves (no children, no word) so later starting cells skip dead branches.

class TrieNode {
    TrieNode[] children = new TrieNode[26];
    String word = null;   // non-null only at a word's last letter
}
private TrieNode buildTrie(String[] words) {
    TrieNode root = new TrieNode();
    for (String w : words) {
        TrieNode cur = root;
        for (char c : w.toCharArray()) {
            int idx = c - 'a';
            if (cur.children[idx] == null) cur.children[idx] = new TrieNode();
            cur = cur.children[idx];
        }
        cur.word = w;   // store the whole word at its terminal node
    }
    return root;
}
public List<String> findWords(char[][] board, String[] words) {
    List<String> res = new ArrayList<>();
    TrieNode root = buildTrie(words);
    for (int r = 0; r < board.length; r++)
        for (int c = 0; c < board[0].length; c++)
            dfs(board, r, c, root, res);
    return res;
}
private void dfs(char[][] b, int r, int c,
                 TrieNode node, List<String> res) {
    char ch = b[r][c];
    if (ch == '#') return;               // already on the current path
    TrieNode nxt = node.children[ch - 'a'];
    if (nxt == null) return;             // no dictionary word goes this way
    if (nxt.word != null) {              // a full word ends here
        res.add(nxt.word);
        nxt.word = null;                 // clear -> automatic de-duplication
    }
    b[r][c] = '#';                       // mark visited
    if (r > 0)               dfs(b, r - 1, c, nxt, res);
    if (r < b.length - 1)    dfs(b, r + 1, c, nxt, res);
    if (c > 0)               dfs(b, r, c - 1, nxt, res);
    if (c < b[0].length - 1) dfs(b, r, c + 1, nxt, res);
    b[r][c] = ch;                        // restore (backtrack)
    // prune a dead leaf so later starts skip it
    boolean empty = true;
    for (TrieNode t : nxt.children) if (t != null) { empty = false; break; }
    if (empty && nxt.word == null) node.children[ch - 'a'] = null;
}

Complexity: Time O(M · N · 4 · 3L-1) where the board is M × N and L is the longest word: each of the M·N starts branches to 4 neighbours and then 3 (can’t revisit the cell it came from) up to depth L. Space O(K) for the Trie (K = total letters in the dictionary) plus O(L) recursion depth.

Common pitfalls / interviewer probes: Restore the cell after recursing. The b[r][c] = '#' / b[r][c] = ch pair is the backtracking heart; forgetting to restore corrupts other words’ paths and silently drops answers. De-duplicate at the node, not with a post-filter. Setting nxt.word = null after collecting keeps the result unique without a separate Set. Trie beats per-word DFS. Searching each word independently is O(W · M · N · 4L); the shared Trie traverses the board once and prunes across all words at once. Prune exhausted branches. Nulling dead leaves keeps the Trie shrinking as words are found — a real speedup on large dictionaries and a favourite follow-up. Store the word at the terminal node so you don’t have to reconstruct the path string on every hit.

Word Squares

Hard Google-style

Problem

Given a list of same-length words, build every word square: a sequence of words arranged as rows so that the k-th row and the k-th column read as the same word. A square of k-letter words has k rows.

  • Words may repeat within a square unless the input list forbids it (this version allows reuse, since the same word can legitimately be several rows).
  • The symmetry constraint means once the first t rows are fixed, the required prefix of every later row is determined by the columns already laid down.

Example: for ["area", "lead", "wall", "lady", "ball"] the code returns 2 squares (computed by running it):

w a l l      b a l l
a r e a      a r e a
l e a d      l e a d
l a d y      l a d y

Read either grid down the columns and you get the same four words as across the rows. Both squares share the tail area / lead / lady; only the first row differs (wall vs ball), because column 0 must itself spell a listed word (wall or ball).

Approach & Intuition

Backtrack row by row, using a prefix index to propose only viable next rows. Precompute a map from every prefix (including the empty prefix) to the list of words having it. When we are about to place row step, the symmetry constraint fixes its required prefix: reading down column step across the rows already placed spells the first step letters that the new row must begin with. We query the prefix map for exactly those words — no scanning the whole dictionary — try each, recurse, and undo. When step reaches the word length, all columns are automatically words too, so we record the square.

private Map<String, List<String>> prefixIndex;

public List<List<String>> wordSquares(String[] words) {
    prefixIndex = new HashMap<>();
    for (String w : words)                      // map every prefix -> words
        for (int i = 0; i <= w.length(); i++)
            prefixIndex
                .computeIfAbsent(w.substring(0, i), k -> new ArrayList<>())
                .add(w);
    List<List<String>> res = new ArrayList<>();
    int len = words[0].length();
    List<String> square = new ArrayList<>();
    for (String w : words) {                    // any word can be row 0
        square.add(w);
        backtrack(square, len, res);
        square.remove(square.size() - 1);
    }
    return res;
}
private void backtrack(List<String> square, int len,
                       List<List<String>> res) {
    int step = square.size();
    if (step == len) {                        // all rows placed -> columns are words too
        res.add(new ArrayList<>(square));
        return;
    }
    // column `step` read down the placed rows is the next row's prefix
    StringBuilder pre = new StringBuilder();
    for (int i = 0; i < step; i++) pre.append(square.get(i).charAt(step));
    for (String cand : prefixIndex.getOrDefault(pre.toString(), List.of())) {
        square.add(cand);
        backtrack(square, len, res);
        square.remove(square.size() - 1);  // undo
    }
}

Complexity: Time O(W · L · 26L) in the worst case for W words of length L, but the prefix index makes it far faster in practice by only ever proposing words that fit the fixed prefix. Space O(W · L) for the prefix index (each word contributes L + 1 prefixes) plus O(L) recursion depth.

Common pitfalls / interviewer probes: The next-row prefix comes from the column. At step t the prefix is square[0].charAt(t), …, square[t-1].charAt(t) — reading down column t, not along a row. Mixing up the index (using charAt(i) instead of charAt(step)) is the signature bug. Index prefixes, don’t rescan. Filtering the whole word list at each step is O(W) per node; the prefix map (or a Trie) turns candidate lookup into O(1)-ish and is the point of the problem. Copy the square when recording. Add new ArrayList<>(square), not the live list, or every stored result mutates as backtracking continues. Include the empty prefix. Indexing i from 0 means the empty string maps to all words — harmless here since row 0 is seeded by the outer loop, but essential if you instead start backtracking from an empty square.
