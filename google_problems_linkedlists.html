Linked Lists

Four Google-style linked-list problems • original framing, execution-tested solutions, and interviewer probes

Note: Representative big-tech-style problems — not sourced from Google. The “Google-style” badge denotes the flavor of question, not its source.

How to read this chapter: every worked example uses inputs invented for this book, and each stated output was produced by compiling and running the accompanying Java. Beyond hand-picked edge cases (empty lists, a single node, removing the head, a final carry that grows the number, and null random pointers) each solution was cross-checked against an independent brute force across tens of thousands of random inputs: merge against a collect-and-sort, addition against native integer arithmetic, remove-Nth against array-index deletion, and the random-pointer deep copy against an index-map reconstruction that also asserts the original list is left untouched. The recurring idea below is the dummy head — a throwaway node in front of the real list so the “insert” and “delete the first node” cases need no special handling — together with two-pointer walks and careful pointer rewiring that never loses the rest of the list.

Merge Two Sorted Lists

Easy Google-style

Problem

Given the heads of two already-sorted singly linked lists (ascending), splice them into one sorted list and return its head. The result should reuse the existing nodes — no new values are allocated.

  • Either list may be empty; if both are empty the answer is an empty list (null head).
  • The lists need not be the same length — whichever runs out first leaves a sorted tail on the other that is attached all at once.

Example: merging [1, 3, 5, 7] and [2, 4, 6] the code returns [1, 2, 3, 4, 5, 6, 7] (computed by running it). When one input is empty — [] and [2, 4] — it returns the other list unchanged, [2, 4]; merging two empty lists returns [].

Approach & Intuition

Walk both lists with a single tail pointer behind a dummy head. The dummy is a stand-in node whose next will end up being the real answer — it means we never have to special-case “which list owns the first node.” At each step compare the two front values, splice the smaller node onto the growing tail, and advance that list. When one list is exhausted, the other is already sorted and its remaining nodes are correctly ordered relative to everything placed so far, so we attach the whole leftover tail in one move rather than copying node by node.

// singly linked list node used throughout this chapter
class ListNode {
    int val;
    ListNode next;
    ListNode(int v) { val = v; }
}

public ListNode mergeTwoLists(ListNode a, ListNode b) {
    ListNode dummy = new ListNode(0), tail = dummy;   // dummy head simplifies splicing
    while (a != null && b != null) {
        if (a.val <= b.val) {          // <= keeps the merge stable
            tail.next = a; a = a.next;
        } else {
            tail.next = b; b = b.next;
        }
        tail = tail.next;             // advance the growing tail
    }
    tail.next = (a != null) ? a : b;  // attach the leftover sorted tail
    return dummy.next;                // real head sits just past the dummy
}

Complexity: Time O(m + n) — every node from each list is visited exactly once. Space O(1): the merge is done by rewiring existing nodes, with only the dummy and a couple of pointers as overhead (no recursion, no copies).

Common pitfalls / interviewer probes: Attach the leftover tail. After the loop, exactly one list may still have nodes; forgetting tail.next = (a != null) ? a : b truncates the answer. Because the remainder is already sorted you attach it in O(1), not with another loop. Use a dummy head. Without it you must special-case picking the first node and guard against a null tail on the first splice — the dummy removes both. Prefer <= over <. Both produce a sorted list, but <= keeps equal elements from the first list ahead of the second (stability), which matters when the nodes carry satellite data. Don’t allocate new nodes. The interviewer usually wants an in-place splice; building a fresh list wastes O(m + n) space for no benefit.

Add Two Numbers

Medium Google-style

Problem

Two non-negative integers are stored as linked lists with their digits in reverse order — the head is the ones digit, the next node the tens digit, and so on. Add the two numbers and return the sum as a linked list in the same reverse-order form.

  • The lists may have different lengths; treat a missing digit as 0.
  • A carry out of the most significant digit produces a brand-new leading node (e.g. 99 + 1 = 100 gains a third digit).

Example: adding 7→1→6 (which reads as 617) and 5→9→2 (which reads as 295) the code returns 2→1→9, i.e. 912 = 617 + 295 (computed by running it). A pure-carry case, [5] + [5], returns [0, 1] (the number 10); and an unequal-length case with a final carry, 9→9 (99) + 1 (1), returns 0→0→1 (the number 100).

Approach & Intuition

The addition you learned in school: one node per column, carrying as you go. Because the digits are already least-significant-first, walking both lists in step visits matching place values together — no reversal needed. At each step sum the two current digits (using 0 when a list has ended) plus the incoming carry; the new digit is sum % 10 and the outgoing carry is sum / 10. A dummy head lets us append result nodes without special-casing the first one. The single loop condition l1 != null || l2 != null || carry != 0 keeps going until both lists are consumed and no carry remains, which is exactly what creates the final leading node when needed.

public ListNode addTwoNumbers(ListNode l1, ListNode l2) {
    ListNode dummy = new ListNode(0), cur = dummy;
    int carry = 0;
    // loop until both lists are done AND nothing is carried over
    while (l1 != null || l2 != null || carry != 0) {
        int sum = carry;                       // start with the incoming carry
        if (l1 != null) { sum += l1.val; l1 = l1.next; }  // missing digit == 0
        if (l2 != null) { sum += l2.val; l2 = l2.next; }
        carry = sum / 10;                     // 0 or 1
        cur.next = new ListNode(sum % 10);   // the column's digit
        cur = cur.next;
    }
    return dummy.next;
}

Complexity: Time O(max(m, n)) — one iteration per digit of the longer number, plus at most one extra for a trailing carry. Space O(max(m, n)) for the result list (the only extra memory besides a few scalars).

Common pitfalls / interviewer probes: Handle the final carry. The classic bug is stopping when both lists end and dropping a leftover carry — then 99 + 1 yields 00 instead of 100. Keeping carry != 0 in the loop condition emits that extra leading node automatically. Unequal lengths. Guard each read with a null check and treat an exhausted list as contributing 0; don’t assume the lists are the same length. Digit vs. carry split. The node value is sum % 10 and the carry is sum / 10 — swapping them is a common slip. Reverse order is a feature. Digits stored least-significant-first are precisely what let you add left-to-right without reversing; if the problem instead stored them most-significant-first you would reverse the inputs (or use stacks) before applying this same loop.

Remove Nth Node From End of List

Medium Google-style

Problem

Given the head of a singly linked list and a valid position n, remove the n-th node counting from the end of the list and return the head. You may assume 1 ≤ n ≤ length, so n = 1 removes the last node and n = length removes the first.

  • The target is identified by its distance from the tail, so a single forward pass must somehow “know” where the end is.
  • Removing the head is the tricky case — there is no previous node to rewire.

Example: from [1, 2, 3, 4, 5] removing the 2nd node from the end (the value 4) the code returns [1, 2, 3, 5] (computed by running it). Removing the 3rd-from-end of [1, 2, 3] — which is the head — returns [2, 3]; and removing the only node, [7] with n = 1, returns [].

Approach & Intuition

Two pointers separated by a gap of n, in one pass. Put a fast and a slow pointer on a dummy head, then advance fast by n steps so it leads slow by exactly n nodes. Now move both together until fast reaches the last node (fast.next == null). At that moment slow sits on the node just before the one to delete, so slow.next = slow.next.next unlinks the target. Anchoring both pointers on the dummy is what makes removing the head fall out for free: when n == length, slow never moves off the dummy and we correctly drop the original first node.

public ListNode removeNthFromEnd(ListNode head, int n) {
    ListNode dummy = new ListNode(0);
    dummy.next = head;                        // dummy so removing the head is uniform
    ListNode fast = dummy, slow = dummy;
    for (int i = 0; i < n; i++) fast = fast.next;  // open a gap of n
    while (fast.next != null) {          // walk until fast is on the last node
        fast = fast.next;
        slow = slow.next;
    }
    slow.next = slow.next.next;               // slow.next is the node to remove
    return dummy.next;
}

Complexity: Time O(L) for a list of length L — a single pass: fast traverses the whole list once. Space O(1): only the dummy and two pointers, no second pass and no length pre-count needed.

Common pitfalls / interviewer probes: The dummy head handles removing the first node. Without it, deleting the head (n == length) needs a separate branch because there is no predecessor; anchoring slow on the dummy makes slow.next = slow.next.next work uniformly. Stop when fast.next == null, not fast == null. You want slow to land on the node before the target; overshooting by one leaves slow on the target itself and deletes the wrong node. Gap size is exactly n. Advance fast by n (not n + 1) starting from the dummy — then the “fast on the last node” stopping rule puts slow in the right place. One pass beats two. You could compute the length then delete at position L - n, but the two-pointer gap does it in a single traversal, which interviewers often ask for.

Copy List with Random Pointer

Medium Google-style

Problem

Each node of a linked list has the usual next pointer and a random pointer that may point to any node in the list or to null. Return a deep copy: a brand-new list whose nodes mirror the values and whose next/random links point only among the copied nodes, never into the original.

  • A random pointer can target any node — including the node itself, an earlier node, a later node, or null.
  • The copy must be fully independent: mutating one list must not affect the other.

Example: take nodes 1→2→3→4 with random pointers 1.random→3, 2.random→1, 3.random→null, 4.random→2. Running the interleave method, the deep copy prints 1(r=3) -> 2(r=1) -> 3(r=null) -> 4(r=2) — identical structure to the input — while the original is verified to still print 1(r=3) -> 2(r=1) -> 3(r=null) -> 4(r=2) and every copied node is confirmed to be a distinct object from its original (computed by running it).

Approach & Intuition

Interleave a clone after every node, wire the randoms, then unzip — all in O(1) extra space. First, for each original node X, insert its copy X' directly after it, so the list becomes X→X'→Y→Y'→…. This adjacency is the trick: a copy always sits immediately after its original, so cur.next is the clone of cur. Second, set each clone’s random with cur.next.random = cur.random.next — the clone of whatever cur.random points at is simply that target’s next (and null stays null). Third, unzip the two lists apart, restoring the original’s next links as you extract the copies. (A simpler alternative uses a hash map from each old node to its new node: one pass to create clones, a second to copy next/random via the map — O(n) time but O(n) space.)

// node with an extra random pointer
class Node {
    int val;
    Node next;
    Node random;
    Node(int v) { val = v; }
}

public Node copyRandomList(Node head) {
    if (head == null) return null;
    // 1) interleave a clone after each node: A -> A' -> B -> B' -> ...
    for (Node cur = head; cur != null; cur = cur.next.next) {
        Node copy = new Node(cur.val);
        copy.next = cur.next;
        cur.next = copy;
    }
    // 2) wire each clone's random: clone of X.random is X.random.next
    for (Node cur = head; cur != null; cur = cur.next.next) {
        cur.next.random = (cur.random != null) ? cur.random.next : null;
    }
    // 3) unzip: extract copies AND restore the original list
    Node dummy = new Node(0), copyTail = dummy;
    for (Node cur = head; cur != null; cur = cur.next) {
        Node copy = cur.next;
        cur.next = copy.next;      // restore original's next
        copyTail.next = copy;      // splice copy onto the new list
        copyTail = copy;
    }
    return dummy.next;
}

Complexity: Time O(n) — three linear passes (interleave, wire randoms, unzip). Space O(1) extra beyond the output list: the interleaving stores the old→new mapping in the list itself, avoiding the O(n) hash map the alternative needs.

Common pitfalls / interviewer probes: Null random pointers. The wiring step must guard cur.random != null before dereferencing, otherwise a null random throws; when it is null the clone’s random stays null. Restore the original list when unzipping. The split loop must reset cur.next = copy.next so the input is left exactly as it was found — a copy routine that mangles its input is a real bug and a common probe. Wire randoms before unzipping. The identity “clone of a node is that node’s next” only holds while the list is still interleaved; compute all randoms first, then split. The hash-map version is fine too. If asked for the simplest correct solution, a map from original to copy is clean O(n)/O(n); the interleave method is the O(1)-space follow-up. Don’t deep-copy randoms into the original nodes. Every copied pointer must land on a copied node, never back into the source list.
