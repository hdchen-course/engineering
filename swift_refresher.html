Swift Refresher

Swift's distinctive model and the syntax around it — value types (struct vs class) with copy semantics, optionals instead of null, exhaustive enums and pattern matching, protocol-oriented design, generics with some/any, closures and capture lists, throws-based error handling, ARC memory management, and modern async/await + actors concurrency — a practical brush-up for an experienced programmer working in modern iOS or server-side Swift

The basics — let / var, type inference & value semantics

Swift is statically typed with aggressive type inference, so you rarely write types by hand. The single most important distinction to internalize up front — the one the rest of the language is built around — is value types vs reference types. Bindings are let (immutable) or var (mutable), and let is the default you should reach for. A struct (and every built-in like Int, String, Array) is a value type: assigning it or passing it makes a copy, so two names never secretly share mutable state.

let name = "Ada"           // inferred String, immutable
var count = 0              // inferred Int, mutable
count += 1
let pi: Double = 3.14159   // explicit type annotation
let ints = [1, 2, 3]       // inferred [Int]
print(name, count, pi, ints.count)

struct P { var x = 0 }
var a = P()
var b = a                  // COPY (value type)
b.x = 9
print(a.x, b.x)            // 0 9 — independent
// → output:
Ada 1 3.14159 3
0 9

String interpolation is \(expr) inside a literal, and print joins its arguments with a space. Prefer let everywhere and only widen to var when you truly mutate — the compiler warns about a var that is never mutated, which is a useful nudge toward immutable-by-default code.

Value semantics are the headline. Because b = a copies, function arguments can't be mutated by a callee unless you opt in, and threads can't overwrite each other's copies. This is the opposite of Java/Python object references and the key to reasoning about Swift code — the whole Struct vs Class section drills into it.

Optionals — the type-safe replacement for null

Swift has no implicit null. A value that may be absent has an optional type, Optional<T>, spelled T?. You cannot use an optional as if it were the wrapped value — you must first unwrap it. The safe tools are if let / guard let binding, the nil-coalescing operator ?? for a default, and optional chaining ?. which short-circuits to nil. Force-unwrap ! exists but crashes on nil — avoid it.

var maybe: Int? = nil
maybe = 7
if let v = maybe { print("has \(v)") }      // if let binding

func describe(_ s: String?) -> String {
    guard let s else { return "nil" }        // guard let shorthand
    return "len \(s.count)"
}
print(describe("hey"))
print(describe(nil))

let n = maybe ?? -1                          // nil-coalescing default
print(n)

let text: String? = "hello"
print(text?.uppercased() ?? "none")          // optional chaining
// → output:
has 7
len 3
nil
7
HELLO

guard let x else { … } (the shorthand form, where the new binding reuses the same name) is the idiomatic early-exit: it unwraps into the rest of the enclosing scope, and its else branch must leave the scope (return, throw, break). This keeps the happy path un-indented, unlike if let which only binds inside its own braces.

Force-unwrap ! is a runtime trap. maybe! when maybe is nil crashes with "Unexpectedly found nil while unwrapping an Optional". So does an implicitly-unwrapped optional (var x: Int!), which auto-unwraps on every use. Reserve ! for values you can prove are non-nil (e.g. an @IBOutlet after view load); everywhere else use if let/guard let/??.

Enums & pattern matching

Swift enums are far richer than C's integer constants. A case can carry associated values (a payload per case, making an enum a tagged union / sum type) and/or a raw value (a fixed underlying literal). You consume them with switch, which the compiler forces to be exhaustive — every case handled (or a default) — so adding a case surfaces every site that must change. Bind the payload in the pattern with let, and use if case / guard case to match a single case inline.

enum Shape {
    case circle(radius: Double)
    case rect(w: Double, h: Double)
}
func area(_ s: Shape) -> Double {
    switch s {
    case .circle(let r):      return .pi * r * r
    case .rect(let w, let h): return w * h
    }
}
print(area(.circle(radius: 2)))
print(area(.rect(w: 3, h: 4)))

enum Dir: Int { case n = 0, e, s, w }          // raw values
print(Dir.s.rawValue)                          // 2
print(Dir(rawValue: 3)!)                       // w (failable init)

let x = Shape.circle(radius: 1)
if case .circle(let r) = x { print("circle r=\(r)") }
// → output:
12.566370614359172
12.0
2
w
circle r=1.0

.pi, .circle(…), .rect(…) use leading-dot syntax: when the expected type is known, you can drop the type name and write just the member. Dir(rawValue: 3) is a failable initializer returning Dir? (an out-of-range raw value yields nil), which is why the example force-unwraps a value it knows is valid.

Exhaustive switch is a design tool: model state as an enum with associated values (e.g. enum Load { case idle, loading, done(Data), failed(Error) }) and the compiler will not let you forget a state. Prefer this over a struct full of optional/boolean flags that can represent impossible combinations.

Structs vs classes — the value/reference divide

Both struct and class bundle stored properties and methods, but their semantics differ sharply. A struct is a value type: it is copied on assignment and on being passed, it gets a free memberwise initializer, and mutating a property through a method requires marking that method mutating (because it conceptually replaces the value). A class is a reference type: assignment shares one instance, it supports inheritance and deinit, and you compare instances by identity with ===. Rule of thumb: reach for struct by default; use class when you need shared mutable state, identity, or inheritance.

struct Point { var x, y: Int }                 // value type, memberwise init
final class Box { var v: Int; init(_ v: Int) { self.v = v } }

var p1 = Point(x: 1, y: 2)
var p2 = p1                                     // copy
p2.x = 99
print(p1.x, p2.x)                               // 1 99 — independent

let b1 = Box(10)
let b2 = b1                                      // shared reference
b2.v = 42
print(b1.v, b2.v)                                // 42 42 — same object
print(b1 === b2)                                 // true — identity

struct Counter {
    private(set) var n = 0
    mutating func tick() { n += 1 }              // mutating on a struct
}
var c = Counter()
c.tick(); c.tick()
print(c.n)                                       // 2
// → output:
1 99
42 42
true
2

Note b1 and b2 are let yet b2.v = 42 compiles: for a class, let makes the reference constant, not the object's properties. For a struct, a let value is fully immutable — you couldn't call tick() on a let c, because a mutating method needs a var. That asymmetry is the value/reference divide in one example.

Copy-on-write (COW). Copying every Array/String/Dictionary eagerly would be slow, so the standard library's value-type collections share storage until a mutation happens, then copy lazily — you get value semantics at reference-copy cost. You can build the same optimization for your own types with isKnownUniquelyReferenced(&ref) guarding a private class buffer.

Protocols & protocol-oriented programming

A protocol is a set of requirements (methods, properties) a type can conform to — Swift's primary abstraction, used far more than class inheritance. The distinctively-Swift move is adding default implementations in a protocol extension, so conformers get behavior for free and only override what differs ("protocol-oriented programming"). The standard library synthesizes conformance to Equatable, Hashable, and Codable when every stored property already conforms — no boilerplate ==/hash.

protocol Greeter {
    var name: String { get }
    func greet() -> String
}
extension Greeter {
    func greet() -> String { "Hi, \(name)" }     // default implementation
}
struct Person: Greeter { let name: String }
print(Person(name: "Sam").greet())

struct Coord: Hashable { let x: Int; let y: Int }  // synthesized ==/hash
let s: Set = [Coord(x: 0, y: 0), Coord(x: 0, y: 0), Coord(x: 1, y: 1)]
print(s.count)                                   // 2 — deduped by synthesized conformance
// → output:
Hi, Sam
2

A protocol with an associated type (associatedtype Element, as in Sequence/Collection) is a generic constraint, not a concrete type — you can't declare a plain var xs: Sequence. Such protocols are used as generic bounds (<S: Sequence>) or, since Swift 5.7, behind any as a boxed existential — covered next in Generics.

Synthesized Codable turns JSON (de)serialization into one line: struct User: Codable { let id: Int; let name: String } then try JSONDecoder().decode(User.self, from: data). Customize key names with a nested CodingKeys enum. This is the everyday way Swift talks to web APIs.

Generics, opaque (some) & existential (any) types

Generics let one function or type work over many concrete types with full type-safety. Constrain a type parameter with a protocol (<T: Comparable>) and refine it with a where clause. Modern Swift adds two ways to talk about a protocol as a type: some P — an opaque type, a single concrete type the caller can't name but the compiler tracks (zero-cost, monomorphized); and any P — an existential, a box that can hold any conforming type (flexible, but with dynamic-dispatch and heap-boxing overhead).

func firstOrNil<T>(_ xs: [T]) -> T? { xs.first }
print(firstOrNil([10, 20]) ?? -1)                // 10

func total<S: Sequence>(_ s: S) -> Int where S.Element == Int {
    s.reduce(0, +)
}
print(total([1, 2, 3]))                          // 6

func makeRange() -> some Sequence { 0..<3 }      // opaque return type
print(Array(makeRange()))                        // [0, 1, 2]

let items: [any CustomStringConvertible] = [1, "two", 3.0]  // existentials
print(items.map { "\($0)" })                     // ["1", "two", "3.0"]
// → output:
10
6
[0, 1, 2]
["1", "two", "3.0"]

some vs any in one line: some P is "one specific hidden type" — the return of makeRange() is always the same concrete Range, so the compiler specializes and there's no boxing. any P is "any type, decided at run time" — the heterogeneous items array must box each element behind a protocol witness. Prefer some (and generic parameters) on hot paths; use any when you genuinely need to store mixed concrete types.

reduce(0, +) shows Swift operators are ordinary functions you can pass as values. The where S.Element == Int clause constrains the sequence's associated Element type — the mechanism that makes generic algorithms over Sequence/Collection precise without inheritance.

Closures — trailing syntax, capture lists & escaping

A closure is an anonymous function that captures its surrounding variables. Swift's ergonomics: a closure passed as the last argument can move outside the parentheses (trailing closure), and its parameters can be referenced positionally as $0, $1. A closure that outlives the call that received it must be marked @escaping (stored, or run later/asynchronously). Because a closure captures references strongly by default, one that captures self and is also stored by self creates a retain cycle — broken with a capture list [weak self] (or [unowned self]).

let nums = [1, 2, 3, 4]
let evens = nums.filter { $0 % 2 == 0 }    // trailing closure, $0 shorthand
print(evens)                               // [2, 4]

var stored: (() -> Void)?
func remember(_ f: @escaping () -> Void) { stored = f }  // escaping: kept for later

final class Model {
    var tag = "M"
    func wire() {
        remember { [weak self] in           // [weak self] lets Model deallocate — the globally-stored closure would otherwise keep it alive
            print("tag = \(self?.tag ?? "gone")")
        }
    }
}
var m: Model? = Model()
m?.wire()
m = nil             // release the only strong owner
stored?()           // weak self is now nil → prints "gone"
// → output:
[2, 4]
tag = gone

weak vs unowned in a capture list. [weak self] makes self an optional inside the closure (safe: it becomes nil if the object is gone). [unowned self] is non-optional and slightly faster, but is a dangling reference that crashes if the object was deallocated — use it only when the closure provably cannot outlive self. When in doubt, use weak and bind it (guard let self else { return }) at the top of the body.

Non-escaping closures (the default for synchronous higher-order functions like map/filter) cannot capture a retain cycle, because they can't outlive the call — so you only need capture lists for @escaping ones (completion handlers, stored callbacks, Task {}). That default is why most closures need no ceremony.

Error handling — throws / try, Result & defer

Swift errors are values: any type conforming to the empty Error protocol (usually an enum) can be thrown. A function that can fail is marked throws, and every call to it must be prefixed with try, making error-propagation points visible. Handle errors with do/catch; convert to an optional with try? (errors become nil); or assert success with try! (crashes on error). defer schedules cleanup that runs on any exit from the scope, and Result<Success, Failure> captures success-or-error as a first-class value.

enum ParseError: Error { case empty, notInt(String) }

func parse(_ s: String) throws -> Int {
    if s.isEmpty { throw ParseError.empty }
    guard let n = Int(s) else { throw ParseError.notInt(s) }
    return n
}

do {
    print("ok \(try parse("42"))")
} catch {
    print("error: \(error)")              // `error` is bound implicitly
}

let maybe = try? parse("nope")     // returns nil instead of throwing
print(maybe ?? -1)                 // -1

let r: Result<Int, ParseError> = .success(10)
print(r.map { $0 * 2 })            // success(20)

func withResource() {
    defer { print("cleanup runs last") }   // runs on scope exit
    print("work")
}
withResource()
// → output:
ok 42
-1
success(20)
work
cleanup runs last

Unlike exceptions in many languages, a Swift throws call is checked at compile time: you cannot ignore that a function throws — you must try it and either propagate (mark the caller throws) or handle it. This makes the failure surface explicit in the type signature, much like Rust's Result — indeed a throws function and a -> Result function express the same thing, and Result has a get() that bridges back to try.

defer blocks run in reverse order of declaration, at scope exit, whether you leave by return, throw, or falling off the end. Use it to pair acquire/release right next to each other (open/close a file, lock/unlock) so cleanup can't be forgotten on an error path.

Memory — ARC, weak / unowned & retain cycles

Reference types (classes, closures, actors) are managed by ARC (Automatic Reference Counting): the compiler inserts retain/release so an object is freed when its strong reference count hits zero — deterministic, no tracing GC pause. Value types (structs, enums) aren't reference-counted at all; they're copied. The one thing you must manage is the retain cycle: two objects holding each other strong never reach zero. Break it by making one side weak (optional, auto-nils on dealloc) or unowned (non-optional, for a reference that logically can't be nil first).

final class Node {
    let name: String
    var next: Node?             // strong
    weak var prev: Node?        // weak → breaks the cycle
    init(_ name: String) { self.name = name }
    deinit { print("deinit \(name)") }
}
do {
    let a = Node("A")
    let b = Node("B")
    a.next = b                  // a strongly holds b
    b.prev = a                  // weak back-reference
    print("linked")
}   // scope ends: both deinit, no leak
print("scope done")
// → output:
linked
deinit A
deinit B
scope done

Make both next and prev strong and neither deinit fires — the two nodes keep each other alive forever, a classic leak. The same shape appears with a stored closure capturing self (see Closures) and with a delegate property, which is why delegates and "back-pointers" are conventionally weak.

Because structs/enums are value types, most Swift data can't form a reference cycle at all — a big reason idiomatic Swift leans on value types. Reserve classes (and the cycle bookkeeping) for the cases that genuinely need shared identity or reference semantics. Use Xcode's Memory Graph Debugger or Instruments' Leaks to find cycles that slipped through.

Concurrency — async/await, Task & actors

Modern Swift concurrency replaces nested completion handlers with straight-line code. A function that suspends is marked async, and every call to it is prefixed with await, marking the potential suspension point. You launch concurrent work with Task { … }, and run independent async calls in parallel with async let. The headline safety feature is the actor: a reference type that serializes access to its mutable state, so you can't race on it — access from outside is awaited. @MainActor pins work to the main thread (UI), and the Sendable protocol marks types safe to cross concurrency boundaries — the compiler checks these under strict concurrency.

actor BankAccount {
    private(set) var balance = 0
    func deposit(_ n: Int) { balance += n }   // actor serializes mutations
}

func work() async -> Int {
    let acc = BankAccount()
    async let a: Void = acc.deposit(100)      // run concurrently
    async let b: Void = acc.deposit(50)
    _ = await (a, b)                          // await both to finish
    return await acc.balance                  // hop onto the actor to read
}

@main
struct App {
    static func main() async {                // @main entry runs on the main actor
        let total = await work()              // suspend until work() returns
        print("balance = \(total)")           // 150 — no data race
    }
}
// → output (built with: swiftc -parse-as-library file.swift):
balance = 150

An actor guarantees that at most one task touches its mutable state at a time, turning "did I lock everything correctly?" into a compile-time property. The cost is that every cross-actor call is async (you await the hop), and values you pass across must be Sendable — value types usually are automatically; classes are only Sendable if immutable or internally synchronized. In Swift 6's strict-concurrency mode, violating this is a compile error, not a runtime data race.

@MainActor is how UI code stays correct: annotate a type or method and its work is guaranteed to run on the main thread. Calling a @MainActor method from a background context is an await (a hop back to main). Never block the main actor with synchronous long work — await an actor or a background Task instead, or the UI stalls.

Common pitfalls (and their fixes)

1 · Force-unwrap and force-try crashes

The exclamation mark is the most common cause of production crashes: optional! on a nil, try! call() when it throws, array[i] out of bounds, and implicitly-unwrapped optionals (T!) that are used before being set all trap (abort). Prefer if let/guard let, try?/do-catch, and indices.contains(i) or first/.first(where:) over indexing. Reserve ! for genuinely-guaranteed values.

2 · Struct-vs-class mutation surprises

Because a struct is copied, mutating one copy never affects another — great for safety, surprising if you expected shared state. The reverse case surprises people too: storing a value type inside a class and mutating the class's copy won't change the original you assigned from. When you truly need shared mutable state (a cache, a coordinator), use a class deliberately. And remember a struct's mutating method can't be called on a let.

3 · Integer overflow traps by default

Unlike C, ordinary arithmetic on Swift's fixed-width integers traps on overflow rather than silently wrapping — a safety feature, but a crash if you didn't expect it. Use the overflow operators &+, &-, &* when you actually want two's-complement wraparound (e.g. hashing).

let big = Int8.max            // 127
let wrapped = big &+ 1        // &+ wraps to -128; plain `big + 1` would TRAP
print(big, wrapped)
// → output:
127 -128

4 · [weak self] forgotten in escaping closures

A stored/escaping closure that captures self strongly, when self also holds that closure, leaks both. Add [weak self] (then guard let self else { return }). Conversely, don't reflexively add [weak self] to a non-escaping closure — it can't cause a cycle and the extra optionality is just noise.

5 · Existential (any) vs generic performance

Reaching for any P (or an untyped protocol) everywhere boxes values and dispatches dynamically. On hot paths prefer generics or some P, which the compiler specializes to concrete types. Use any only where heterogeneity is real (mixed concrete types in one collection).

6 · Array value semantics & copy-on-write

Assigning an array copies it (logically); the copy is shared under COW until you mutate. This means passing a big array around is cheap until a write, and a write inside a tight loop over a shared array can trigger a hidden full copy. It also means you never accidentally alias — mutating ys below leaves xs untouched.

var xs = [1, 2, 3]
var ys = xs                   // value semantics (copy-on-write under the hood)
ys.append(4)                  // mutating ys triggers the copy
print(xs, ys)                 // xs unchanged
// → output:
[1, 2, 3] [1, 2, 3, 4]

A meta-pitfall for newcomers from Java/Python: treating everything as a shared reference. In Swift the default is the opposite — value semantics. Ask "is this a value or an identity?" for every type you design: values are structs/enums (copied, thread-friendly, no cycles); identities are classes/actors (shared, ARC-managed, watch for cycles). Choosing correctly removes whole categories of bugs.

Tooling & interop

Swift is compiled by swiftc (an LLVM front end), organized into packages by the Swift Package Manager (SwiftPM), and edited in Xcode on Apple platforms (Swift also runs on Linux and Windows for server/CLI work). A single file runs two ways from the command line:

# run a script directly (top-level code allowed)
swift prog.swift

# or compile to a binary, then run it
swiftc prog.swift -o prog
./prog

# a file using @main needs library parsing (no top-level code)
swiftc -parse-as-library prog.swift -o prog
Tool / commandWhat it does
swift file.swiftCompile-and-run a script in one step; top-level statements execute in order.
swiftcThe compiler; produces an executable or library. Add -O for optimized release builds.
swift build / swift run / swift testSwiftPM: build, run, and test a package defined by a Package.swift manifest.
Xcode / xcodebuildThe IDE and its build tool; ships the debugger, Instruments, and the concurrency/memory checkers.

SwiftUI & Objective-C interop

SwiftUI is Apple's declarative UI framework: you describe the view hierarchy as value-type View structs and the framework diffs and re-renders on state change (@State, @Observable) — a natural fit for Swift's value semantics. Swift also interoperates with Objective-C in both directions within a target: Swift sees Objective-C through a bridging header, and Objective-C sees Swift symbols marked @objc via a generated -Swift.h. Objective-C NSError ** methods bridge to Swift throws, and nullability annotations map to optionals — which is exactly the boundary the Objective-C chapter describes from the other side.

Interview angle. A crisp "what makes Swift distinctive?" answer: it is a value-semantics-first, protocol-oriented language with a strong static type system that eliminates null (optionals) and unhandled errors (throws) at compile time, manages reference types with ARC (so the real skill is spotting retain cycles), and builds data-race safety into the type system via async/await and actors. Prefer struct + protocol + generics; reach for class/actor only when you need identity or shared state.

All but the concurrency example build as plain scripts; the @main concurrency snippet was built with swiftc -parse-as-library, as noted on its output block.
