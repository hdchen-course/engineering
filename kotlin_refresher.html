Kotlin Refresher

Kotlin's distinctive model and the syntax around it — null safety, val/var and expressions, data and sealed classes, extension functions, the functional collection ops, scope functions, coroutines, and seamless Java interop — a tight brush-up for a JVM developer coming from Java

Basics — val/var, type inference & expressions

Kotlin flips Java's default: val declares a read-only binding (like a final local), and you reach for var only when you genuinely need to reassign. Types are inferred from the initializer, so you write them only when you want to. The bigger shift for a Java developer is that control flow is made of expressions: if, when, and even try return values, so there is no ternary operator and far fewer throwaway mutable variables. String templates ($var, ${expr}) replace concatenation.

val name = "Kotlin"          // read-only (like final); type inferred as String
var count = 0                // mutable
count += 1

val pi: Double = 3.14159     // explicit type when you want it

// if is an EXPRESSION — it yields a value (no ternary needed)
val max = if (count > 0) count else 0

// when is an expression too
val label = when {
    count < 0  -> "negative"
    count == 0 -> "zero"
    else       -> "positive"
}

println("name=$name, max=$max, label=$label, len=${name.length}")
// → output:
name=Kotlin, max=1, label=positive, len=6

Because if/when are expressions, the last expression of the chosen branch is its value — note there is no return inside them. This is why idiomatic Kotlin has so few reassignable vars: you compute a value into a val instead of declaring it uninitialized and mutating it. Prefer val by default and let the compiler flag the ones that must change.

Null safety — the headline feature

Kotlin's type system tracks nullability. String can never hold null; only the distinct type String? can. That single distinction moves the entire class of NullPointerExceptions from run time to compile time. To touch a nullable value you must acknowledge the null case — with the safe call ?. (returns null instead of throwing), the Elvis operator ?: (supply a fallback), or a null check that the compiler turns into a smart cast.

var s: String = "hi"
// s = null                       // compile error: String is not nullable

var maybe: String? = "text"       // nullable type
maybe = null                        // ok

val len:  Int? = maybe?.length      // safe call → null when maybe is null
val len2: Int  = maybe?.length ?: -1 // Elvis → fallback of -1

fun describe(x: String?): String {
    if (x == null) return "none"
    return "len=${x.length}"          // x is smart-cast to non-null String here
}

println("$len $len2 ${describe(null)} ${describe("abc")}")
// → output:
null -1 none len=3

The smart cast works because Kotlin flow-analyzes: after if (x == null) return, the only way to reach the next line is with x non-null, so x has type String (not String?) from there on — no cast, no re-check. The same applies after x != null guards and inside is checks.

lateinit: a non-null property initialized later

Some non-null properties can't be set at construction (dependency injection, lifecycle callbacks). lateinit var promises to assign before first read; touching it early throws UninitializedPropertyAccessException. Guard with ::prop.isInitialized when unsure.

class Session {
    lateinit var token: String       // non-null, set later (not at construction)
    fun login() { token = "abc123" }
    fun status() =
        if (::token.isInitialized) token else "<none>"
}

fun main() {
    val sess = Session()
    println(sess.status())   // not initialized yet
    sess.login()
    println(sess.status())   // now set
}
// → output:
<none>
abc123

The not-null assertion x!! converts T? to T and throws NullPointerException if x is null — it re-introduces exactly the failure Kotlin was designed to prevent. Treat every !! as a code smell: prefer ?., ?:, a smart-casting if/?.let, or requireNotNull(x) (which throws a meaningful message) when you truly must fail on null.

Functions — defaults, extensions & lambdas

Functions are declared with fun and can live at the top level (no enclosing class needed). Two features remove a lot of Java boilerplate: default and named arguments (one function instead of a pile of overloads) and extension functions (add methods to a type you don't own). Lambdas are first-class, and when a lambda is the last argument it can move outside the parentheses — the trailing-lambda syntax that makes Kotlin DSLs read so cleanly.

// single-expression function; return type inferred from the body
fun square(n: Int) = n * n

// default + named arguments — no overload explosion
fun greet(name: String, greeting: String = "Hello", loud: Boolean = false): String {
    val msg = "$greeting, $name"
    return if (loud) msg.uppercase() else msg
}

// extension function: add a method to an existing type
fun String.shout() = this.uppercase() + "!"

// higher-order function taking a lambda (Int) -> Unit
fun repeatDo(n: Int, action: (Int) -> Unit) {
    for (i in 0 until n) action(i)
}

fun main() {
    println(square(5))
    println(greet("Ada"))
    println(greet("Ada", loud = true))   // named arg skips 'greeting'
    println("kotlin".shout())
    repeatDo(3) { i -> print("$i ") }    // trailing lambda, outside the parens
    println()
}
// → output:
25
Hello, Ada
HELLO, ADA
KOTLIN!
0 1 2

An extension function is resolved statically — it is compiled to a plain static method taking the receiver as its first parameter, and does not actually modify String or dispatch virtually. Named arguments also make defaults safe to reorder: greet("Ada", loud = true) keeps greeting at its default without a positional placeholder. Inside a lambda with one parameter you can drop the declaration and use the implicit name it.

Classes — primary constructors, data & sealed

Kotlin classes are concise: the primary constructor and its properties are declared in the class header, and a property with val/var gets a backing field and accessors automatically (override them with a custom get()/set()). A data class auto-generates equals/hashCode/toString/copy and the componentN destructuring operators. A sealed class defines a closed hierarchy, which makes a when over it exhaustive — no else branch required, and adding a subtype turns every such when into a compile error until you handle it.

// primary constructor + properties inline; val = read-only property
data class User(val id: Int, var name: String)

// custom getter over a backing property (computed, no backing field)
class Temperature(var celsius: Double) {
    val fahrenheit: Double
        get() = celsius * 9 / 5 + 32
}

// sealed hierarchy: when over it is exhaustive (no else needed)
sealed class Outcome
data class Ok(val value: Int)   : Outcome()
data class Err(val message: String) : Outcome()

fun render(r: Outcome): String = when (r) {
    is Ok  -> "ok: ${r.value}"
    is Err -> "err: ${r.message}"
}

// companion object: the closest thing to Java 'static' members
class Counter private constructor(val start: Int) {
    companion object {
        fun create() = Counter(0)
    }
}

fun main() {
    val u1 = User(1, "Ann")
    val u2 = u1.copy(name = "Bob")   // copy() from data class
    println(u1)                        // toString() from data class
    println(u2)
    println(u1 == User(1, "Ann"))   // structural equals from data class
    println(Temperature(100.0).fahrenheit)
    println(render(Ok(42)))
    println(render(Err("nope")))
    println(Counter.create().start)
}
// → output:
User(id=1, name=Ann)
User(id=1, name=Bob)
true
212.0
ok: 42
err: nope
0

copy gives you cheap immutable updates: keep properties as val and produce a modified clone rather than mutating in place. The exhaustive when over a sealed type is the Kotlin analogue of Rust's match over an enum — the compiler is your safety net when the hierarchy grows. A companion object is a real singleton object (not a static namespace); you can name it, have it implement interfaces, and add extensions to it.

Collections — read-only views & functional ops

Kotlin splits collections into read-only interfaces (List, Set, Map) and mutable ones (MutableList, …). listOf gives you a read-only List; mutableListOf gives you one you can add to. The read-only type is a view/interface, not a deep-frozen guarantee — it simply doesn't expose mutators. On top sits a rich set of functional operators (map, filter, groupBy, associate, fold) that return new collections and read like a pipeline.

fun main() {
    val nums = listOf(1, 2, 3, 4, 5, 6)   // read-only List<Int>
    val doubled = nums.map { it * 2 }
    val evens   = nums.filter { it % 2 == 0 }
    val sum     = nums.fold(0) { acc, n -> acc + n }

    val words = listOf("apple", "banana", "avocado", "cherry")
    val byInitial = words.groupBy { it.first() }   // Char -> List<String>

    val mutable = mutableListOf(1, 2, 3)
    mutable.add(4)

    println(doubled)
    println(evens)
    println("sum=$sum")
    println(byInitial)
    println(mutable)
}
// → output:
[2, 4, 6, 8, 10, 12]
[2, 4, 6]
sum=21
{a=[apple, avocado], b=[banana], c=[cherry]}
[1, 2, 3, 4]

groupBy returns a LinkedHashMap, so the keys appear in first-encounter order (a, then b, then c). The eager operators above allocate an intermediate collection at each step — fine for small data, wasteful for large chains.

Sequences: lazy evaluation for long chains

Wrapping a source in asSequence() makes the operators lazy: elements flow through the whole pipeline one at a time, and terminal operators like first() stop as soon as they're satisfied — no intermediate lists.

val firstBig = (1..1_000_000).asSequence()
    .map { it * 2 }
    .filter { it > 10 }
    .first()          // evaluates only until the first match
println(firstBig)
// → output (only 6 elements are ever produced, not a million):
12

Rule of thumb: use plain (eager) operators for small collections and short chains — they're simpler and often faster. Switch to asSequence() when the source is large and you chain several operators, or when a terminal like first/find/take can short-circuit.

Scope functions — let / run / with / apply / also

Five standard-library functions run a block "on" an object; they differ in only two dimensions — how the object is referenced inside the block (it vs the receiver this) and what the whole call returns (the block's result vs the object itself). Memorizing that 2×2 dissolves the classic confusion.

FunctionObject referenced asReturnsTypical use
letitlambda resultrun a block on a non-null value (x?.let { … })
runthislambda resultcompute a result from the object's members
withthis (as argument)lambda resultgroup several calls on one object
applythisthe objectconfigure then return the object (builders)
alsoitthe objectside effects (logging) in a chain
data class Config(var host: String = "", var port: Int = 0)

fun main() {
    // apply: configure the object, RETURN the same object
    val cfg = Config().apply {
        host = "localhost"   // 'this' is the Config
        port = 8080
    }
    println(cfg)

    // let: run a block on a non-null value, RETURN the block's result
    val nm: String? = "kotlin"
    val len = nm?.let { it.length }   // it = "kotlin"
    println(len)

    // also: side-effect (e.g. logging), RETURN the same object
    val doubled = listOf(1, 2, 3)
        .map { it * 2 }
        .also { println("after map: $it") }
    println(doubled)

    // run: compute a result using 'this'
    val summary = cfg.run { "$host:$port" }
    println(summary)
}
// → output:
Config(host=localhost, port=8080)
6
after map: [2, 4, 6]
[2, 4, 6]
localhost:8080

Overusing scope functions — especially nesting them — quickly becomes unreadable, and mixing it- and this-based ones inside each other makes it hard to tell which object this refers to. Reach for them when they remove a temporary variable or make a builder-style block clearer, not reflexively. When in doubt, a named val and a plain call are easier to read.

Coroutines — structured concurrency

A coroutine is a suspendable computation: a suspend function can pause at a suspension point (like delay or a network call) and release its thread instead of blocking it, resuming later. That is why a server can run hundreds of thousands of coroutines on a small thread pool — they are far cheaper than OS threads. You start them with builders (launch for fire-and-forget, async for a result via await) inside a CoroutineScope, and structured concurrency guarantees the scope waits for all its children — no leaked background work.

import kotlinx.coroutines.*

suspend fun fetch(id: Int): Int {
    delay(100)          // suspends the coroutine; does NOT block the thread
    return id * 10
}

fun main() = runBlocking {          // bridges the blocking & suspending worlds
    val a = async { fetch(1) }        // starts concurrently
    val b = async { fetch(2) }
    println(a.await() + b.await())   // 30 — after ~100ms total, not ~200ms
    launch { println("done") }         // child coroutine; runBlocking waits for it
}
// → output:
30
done

The two async calls run concurrently, so the two delay(100)s overlap: the sum prints after roughly one 100 ms wait, not two. runBlocking then keeps the JVM alive until the launched child finishes — that is structured concurrency: a parent scope never completes while its children are still running. In real apps you rarely use runBlocking outside main/tests; you launch into a lifecycle-bound scope instead.

Dispatchers decide which thread(s) a coroutine uses: Dispatchers.Default for CPU-bound work, Dispatchers.IO for blocking I/O, Dispatchers.Main for UI. Switch with withContext(Dispatchers.IO) { … } around a blocking call so it doesn't starve the others. Coroutines need the kotlinx-coroutines-core dependency; they are a library, not a language keyword (only suspend is).

Java interop — and its friction points

Kotlin compiles to the same JVM bytecode as Java and calls Java code directly: Java classes, the entire JDK, and existing libraries are used with normal Kotlin syntax, and a Java getter/setter pair shows up as a Kotlin property. The one real friction is nullability. The Java type system doesn't distinguish String from String?, so a value coming from Java has a platform type, written String! in diagnostics — Kotlin trusts you not to null-check it, which means a Java null can slip through and blow up at the first dereference.

import java.util.ArrayList

fun main() {
    val list = ArrayList<String>()   // a Java class, used with Kotlin syntax
    list.add("a")
    list.add("b")
    println(list.size)               // Java's size() surfaces as a property
    println(list)
}
// → output:
2
[a, b]

Platform types are the trap. If a Java method is not annotated, its return has type T! and Kotlin lets you assign it to either T or T? with no warning — so a surprise null becomes an NPE at the point of use, not at the boundary. Annotate the Java side with @Nullable/@NonNull (JetBrains, JSR-305, or AndroidX) so Kotlin imports the right nullability, and treat unannotated returns as nullable when you're unsure.

Making Kotlin pleasant to call from Java

Going the other way, a few annotations smooth the Kotlin→Java boundary. @JvmStatic emits a real static method (instead of forcing Companion.method()), and @JvmOverloads generates the overloads Java needs because Java has no default arguments.

class Api {
    companion object {
        @JvmStatic fun version() = "1.0"   // Java calls Api.version()
    }

    @JvmOverloads
    fun connect(host: String, port: Int = 80) {
        // Java sees connect(host) AND connect(host, port)
    }
}

Other everyday interop helpers: @JvmName("…") renames the generated method (useful to dodge JVM signature clashes), @JvmField exposes a property as a plain public field, and @Throws(IOException::class) declares checked exceptions so Java callers must catch them (Kotlin itself has no checked exceptions).

Common pitfalls (and their fixes)

1 · !! everywhere

Reaching for the not-null assertion x!! to silence a nullability error just re-creates the NPE Kotlin removed — now with less context. Prefer a safe call x?.…, an Elvis fallback x ?: default, a smart-casting if (x != null) { … }, or requireNotNull(x) { "why" } when a null genuinely is a bug you want to fail on with a message.

2 · Leaking a mutable collection through a read-only type

Exposing a MutableList as a List looks safe, but if you hand back the same backing instance, a caller can cast it back and mutate your internals. Keep the mutable one private and expose a read-only property (or a defensive copy with .toList()).

class Cart {
    private val _items = mutableListOf<String>()
    val items: List<String> get() = _items   // read-only VIEW of the same list
    fun add(x: String) { _items.add(x) }
}

The items type hides the mutators, but it is still the live list — mutations via add show through it. When callers must not observe later changes at all, return _items.toList() (a snapshot copy).

3 · companion object is not Java static

Members of a companion object are instance members of a real singleton, not true statics. From Java they are reached as MyClass.Companion.foo() unless annotated @JvmStatic. Don't assume a companion function is a zero-overhead static call, and annotate the ones Java needs to see as static.

4 · equals on a non-data class

Only data classes get structural equals/hashCode. A regular class uses identity, so two "equal-looking" instances compare unequal — and break as HashMap/HashSet keys.

class Point(val x: Int, val y: Int)      // NOT a data class

fun main() {
    val a = Point(1, 2)
    val b = Point(1, 2)
    println(a == b)   // identity equality — no generated equals
}
// → output:
false

Fix by making it a data class (value equality) or overriding equals/hashCode by hand. Note == in Kotlin calls equals; reference equality is the separate ===.

5 · lazy vs lateinit

Both defer initialization, but they solve different problems. by lazy { … } is for a val computed once on first access (thread-safe by default). lateinit var is for a non-null var assigned externally later (DI, setup) — no default, and reading it early throws. Use lazy when you own the computation; lateinit when something else sets the value.

val config: String by lazy {   // computed once, on first access
    println("computing")
    "loaded"
}

fun main() {
    println(config)   // triggers the block, then prints the value
    println(config)   // cached — block does NOT run again
}
// → output:
computing
loaded
loaded

A meta-pitfall for Java developers: writing Kotlin as "Java with a different syntax" — var everywhere, manual null checks instead of ?./?:, getter/setter boilerplate, and utility classes full of static methods instead of top-level or extension functions. The idiomatic style (immutability by default, expressions over statements, the standard-library operators) is what makes Kotlin worth the switch.

Tooling & ecosystem

Kotlin is built and tested with the same toolchain as the JVM ecosystem. Most projects use Gradle with the Kotlin DSL (build.gradle.kts) — the build script is itself Kotlin, so you get completion and type checking on your build. The kotlinc compiler produces JVM bytecode (and, via other backends, JavaScript and native binaries).

ToolWhat it does
kotlinc / kotlinCompile to JVM bytecode; run a compiled program or a .kts script.
gradle buildBuild via Gradle, configured in a Kotlin-DSL build.gradle.kts.
ktlintFormatter + linter enforcing the official Kotlin style — no style debates.
detektStatic analysis: code smells, complexity, and configurable rule sets.
// build.gradle.kts — the Gradle Kotlin DSL
plugins {
    kotlin("jvm") version "2.0.0"
    application
}

dependencies {
    implementation("org.jetbrains.kotlinx:kotlinx-coroutines-core:1.8.1")
    testImplementation(kotlin("test"))
}

application {
    mainClass.set("MainKt")
}

Interview angle. A strong "why Kotlin?" answer connects the pieces: null safety in the type system removes the JVM's most common runtime crash; immutability-by-default (val) plus expressions and data classes cut boilerplate and bugs; coroutines give cheap structured concurrency; and 100% Java interop means you adopt it incrementally in an existing JVM codebase with no rewrite. Google made Kotlin an official language for Android development in 2017 (and later "Kotlin-first"), which is a large part of its adoption story.

Kotlin is also multiplatform (KMP): the same Kotlin business logic can compile to JVM, Android, native (via Kotlin/Native), and JavaScript, letting teams share a core module across platforms while keeping platform-specific UI native. Wire ktlint/detekt into CI and use IntelliJ IDEA (or Android Studio) for first-class inline types, quick fixes, and the Java-to-Kotlin converter.
