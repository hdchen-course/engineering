String Simulation & Scanning — Google-style Problems

Note: Representative big-tech-style problems — not sourced from Google. The “Google-style” badge denotes the flavor of question, not its source.

Expressive Words

Medium Google-style

Problem

When people type with feeling they "stretch" letters, repeating a character many times — "go" might be typed "gooo". A group of one or more identical adjacent letters is extendable if, after stretching, its length becomes 3 or more. Given a target string s and a list of words, count how many words can be made equal to s by extending zero or more of their letter groups.

  • You may only lengthen a group, never shorten it, and a group can be extended only if the resulting run has length ≥ 3.
  • A group already of length ≥ 3 in s may match a shorter word group; a length-1 or length-2 target group can only be matched by an equal-length word group (there is nothing to stretch into).

Example: for s = "ggghhh" and words = ["gh", "ggh", "gggh", "ghhh", "ghg"] the answer is 4. The target groups are g×3 and h×3, both stretchable, so the first four words all extend to "ggghhh"; "ghg" fails because its three groups (g, h, g) can never line up with the target's two.

Approach & Intuition

Walk both strings group by group, in step. For each aligned pair of runs, let l be the target run length and r the word run length. The pair is compatible only when the letters match and one of two things holds: the lengths are already equal (no stretch needed), or the target run is strictly longer and at least 3 (so it could have been stretched from the shorter word run). Any of the failing conditions — letters differ, the word run is longer than the target (l < r), or the target is longer but under 3 (l > r && l < 3) — rejects the word. The word matches only if both strings are fully consumed at the same time.

public int expressiveWords(String s, String[] words) {
    char[] cs = s.toCharArray();
    int res = 0;
    for (String word : words)
        if (stretchesTo(cs, word.toCharArray())) res++;   // count each matching word
    return res;
}

// Can the run structure of 'ct' (a word) be stretched into 'cs' (the target)?
private boolean stretchesTo(char[] cs, char[] ct) {
    int m = cs.length, n = ct.length, i = 0, j = 0;
    while (i < m && j < n) {
        int i0 = endOfRun(cs, i), j0 = endOfRun(ct, j);
        int l = i0 - i, r = j0 - j;             // lengths of the two aligned runs
        // Reject if: word run longer than target (can't shrink);
        //            target longer but under 3 (nothing could stretch into it);
        //            or the two run characters differ.
        if (l < r || (l > r && l < 3) || cs[i] != ct[j]) return false;
        i = i0; j = j0;                        // jump both cursors past the runs
    }
    return i == m && j == n;                     // both strings exhausted together
}

// Return the index one past the run of equal chars starting at i.
private int endOfRun(char[] cs, int i) {
    int j = i, n = cs.length;
    while (j < n && cs[i] == cs[j]) j++;
    return j;
}

Complexity: Time O(W·|s| + ∑|word|) (W = number of words) — the target run s is re-scanned once per word, and each word's characters are visited once. Space O(1) beyond the input (a few cursors).

Common pitfalls / interviewer probes: (1) The asymmetry is the whole problem: l > r is allowed only when l >= 3, but l < r is never allowed — you can stretch a group longer, never squeeze it shorter. (2) A target run of length 1 or 2 must be matched exactly; forgetting the l < 3 guard wrongly accepts words like "xy" against "xxyy". (3) The final i == m && j == n check rejects words whose group pattern differs (extra or reordered groups such as "ghg"), even when a prefix matched. (4) Both cursors must advance by whole runs; comparing character-by-character loses the group-length information the decision depends on.

Find And Replace in String

Medium Google-style

Problem

You are given a string s and three parallel arrays: indices, sources, and targets. Each entry k describes a potential edit: if the substring of the original s starting at indices[k] exactly equals sources[k], replace that occurrence with targets[k]; otherwise leave that spot untouched. All checks are made against the original string, all replacements are applied simultaneously, and the edits are guaranteed not to overlap. Return the resulting string.

  • The indices may arrive in any order and are not sorted.
  • A source that runs past the end of s, or that does not match character-for-character, is skipped.

Example: for s = "codebase", indices = [4, 0], sources = ["base", "code"], targets = ["X", "Y"], both checks succeed — "code" at index 0 and "base" at index 4 — giving "YX". With s = "abcabc", indices = [0, 3], sources = ["ab", "xy"], targets = ["Z", "W"], only the first matches ("ab" at 0), while "xy" does not match "ab" at index 3, so the result is "Zcabc".

Approach & Intuition

Because indices can be out of order, first sort a permutation of edit-indices by their position in s. Then sweep s left to right with a write cursor i and an edit cursor j. When i reaches the next edit's start position, verify the source still matches the original text there; if so, emit the target and jump i past the whole source (the loop's ++i supplies the final step), otherwise emit the single original character. Every other position is copied verbatim. Matching against the original array (never a partially rebuilt string) is what makes the "simultaneous" semantics fall out naturally.

public String findReplaceString(String s, int[] indices,
                                String[] sources, String[] targets) {
    char[] cs = s.toCharArray();
    int m = indices.length, n = cs.length;
    Integer[] idx = new Integer[m];              // a permutation of edit ids
    for (int i = 0; i < m; ++i) idx[i] = i;
    Arrays.sort(idx, (a, b) -> indices[a] - indices[b]); // order edits by position

    StringBuilder sb = new StringBuilder();
    for (int i = 0, j = 0; i < n; ++i) {
        if (j < m && i == indices[idx[j]]) {         // an edit begins at this index
            if (matchesAt(cs, i, sources[idx[j]])) {
                sb.append(targets[idx[j]]);        // source matched: write the target
                i += sources[idx[j]].length() - 1;  // skip the rest of the source
            } else sb.append(cs[i]);                  // no match: keep original char
            j++;                                   // this edit is now resolved
        } else sb.append(cs[i]);                      // ordinary character, copy as-is
    }
    return sb.toString();
}

// Does the original text at cs[i..] start with the source string t?
private boolean matchesAt(char[] cs, int i, String t) {
    char[] ct = t.toCharArray();
    int m = cs.length, j = 0;
    while (i < m && j < ct.length && cs[i] == ct[j]) { i++; j++; }
    return j == ct.length;                          // true only if all of t was consumed
}

Complexity: Time O(m log m + n + ∑|source|) — the sort dominates the edit count, plus one sweep of s and the match checks. Space O(m + n) for the index permutation and the output buffer.

Common pitfalls / interviewer probes: (1) Never mutate s in place and re-check against the changed text — all matches are defined against the original, which the char-array approach preserves for free. (2) Sorting is essential because indices is unsorted; a naive left-to-right assumption breaks on inputs like indices = [4, 0]. (3) The i += len - 1 step relies on the loop's own ++i; using i += len skips one character too many. (4) The match must stop at the end of s (the i < m guard) so a source longer than the remaining text fails cleanly instead of throwing. A common follow-up is to guarantee overlaps or to apply edits as a single left-to-right pass with a merged, pre-sorted event list.

Missing Ranges

Easy Google-style

Problem

Given a sorted array nums whose values all lie within the inclusive bounds [lower, upper], report every maximal range of integers in [lower, upper] that is absent from nums. Each missing range is formatted as "a->b", or just "a" when it is a single number.

  • The array may be empty; it may also cover the whole interval, in which case nothing is missing.
  • Values are assumed to fall inside [lower, upper]; duplicates are harmless.

Example: for nums = [2, 5, 6, 9], lower = 1, upper = 10 the missing numbers are 1, 3, 4, 7, 8, 10, which collapse to ["1", "3->4", "7->8", "10"]. For an empty nums with lower = 3, upper = 7 the whole span is missing: ["3->7"].

Approach & Intuition

Keep a moving frontier lower that marks the smallest integer not yet accounted for. Sweep the sorted array: if the current value equals lower, the frontier simply advances by one (nothing missing there). If the current value is strictly greater than lower, everything from lower up to value - 1 is a gap — emit it as a single number or a range — then jump the frontier just past this value. After the sweep, any remaining span from lower to upper is the final missing range (or single number when they coincide).

public List<String> findMissingRanges(int[] nums, int lower, int upper) {
    List<String> res = new LinkedList<>();
    for (int i : nums) {
        if (i == lower) lower++;               // value fills the frontier: no gap
        else if (lower < i) {                   // a gap [lower, i-1] opened up
            if (lower == i - 1) res.add("" + lower);          // gap is one number
            else res.add(lower + "->" + (i - 1));            // gap is a range
            lower = i + 1;                    // advance past this value
        }
        // (values below the frontier, e.g. duplicates, are ignored)
    }
    // trailing gap between the frontier and the upper bound
    if (lower < upper) res.add(String.format("%d->%d", lower, upper));
    else if (lower == upper) res.add("" + lower);
    return res;
}

Complexity: Time O(n) — a single pass over the sorted array. Space O(1) beyond the output list.

Common pitfalls / interviewer probes: (1) The single-number vs range distinction (lower == i - 1) is easy to miss — a lone missing value should print as "4", not "4->4". (2) The trailing check after the loop is mandatory: gaps at the top of the interval (and the all-empty case) are only emitted there. (3) Integer-overflow trap — when the bounds reach the 32-bit extremes, i - 1 or i + 1 can wrap; a common test input is upper = Integer.MAX_VALUE, so widen to long or reorder the arithmetic if that is in scope. (4) Advancing with lower = i + 1 (not lower = i) is what skips the value just consumed; forgetting it re-reports that number. The natural follow-up asks to merge this with a live stream or to output the count of missing integers instead of the ranges.

Maximize Distance to Closest Person

Medium Google-style

Problem

A row of seats is given as an array where 1 marks an occupied seat and 0 an empty one. Alex wants to sit in some empty seat so that the distance to the nearest already-seated person is as large as possible. Return that maximum possible distance, measured in seats.

  • There is at least one person and at least one empty seat.
  • Distance is the absolute difference of indices; only the single closest neighbour matters.

Example: for [0, 0, 1, 0, 0, 0, 0, 1, 0] the answer is 2 — sitting at index 4 or 5 sits three seats from the farther occupant but the nearer one is 2 away (the interior gap between indices 2 and 7 gives floor((7-2)/2) = 2, matching the leading run's distance of 2 and beating the trailing run of 1). For [1, 0, 0, 0, 0] the answer is 4: sit at the far right end.

Approach & Intuition

Every empty seat's best value comes from exactly one of three situations: a leading empty run before the first person (sit at the far left, distance = its index), an interior run between two people (sit in the middle, so floor((gap)/2)), or a trailing run after the last person (sit at the far right, distance = end minus last person). Sweep once, remembering j = the index of the previous occupied seat. Each time you meet a person, score the run that just closed; at the final index, score any trailing run.

// j = index of the previous occupied seat (-1 until we meet the first person).
// Each occupied seat closes an empty run whose best seat we score here.
public int maxDistToClosest(int[] seats) {
    int n = seats.length, res = 0;
    for (int i = 0, j = -1; i < n; ++i) {
        if (1 == seats[i]) {                          // an occupied seat
            // leading run: sit far left, distance i
            if (-1 == j) res = Math.max(res, i);
            // interior run: sit in the middle, floor(gap/2)
            else res = Math.max(res, (i - j) >> 1);
            j = i;                                   // remember this occupant
        } else if (i + 1 == n && -1 != j) {  // trailing run ends at last seat
            res = Math.max(res, i - j);              // sit far right, distance i - j
        }
    }
    return res;
}

Complexity: Time O(n) — a single left-to-right pass. Space O(1).

Common pitfalls / interviewer probes: Three distinct cases, not one formula — the leading and trailing runs are scored with the full length (you sit at the end), while an interior run is halved because a neighbour bounds you on both sides. Collapsing them into one rule is the classic bug. The >> 1 is floor-division by two — for an odd interior gap the middle seat is one closer on the tighter side, which is exactly what the floor captures. Reconcile with the input contract — the code assumes at least one person exists; with an all-empty row j would stay -1, neither branch that lifts res fires, and it returns 0 rather than n. That is fine under the stated guarantee, but if the guarantee is dropped you must special-case it. A frequent follow-up asks for the actual seat index, or for a circular row.

Next Closest Time

Medium Google-style

Problem

Given a 24-hour time as a string "HH:MM", form the closest later time that reuses only the four digits already present (any digit may be reused any number of times). If no later time can be built today, wrap around to the earliest time of the next day. Return it as "HH:MM".

  • The input is a valid time, so hours are 00..23 and minutes 00..59.
  • "Closest later" is measured forward in minutes, wrapping past midnight if necessary.

Example: "13:55" → "15:11" — no minute above 55 can be built from {1,3,5}, so the hour advances to the next reachable value 15 and the minutes reset to the smallest pair 11. And "22:29" → "22:22": nothing larger fits today (digits are {2,2,2,9}), so it wraps to the smallest time of tomorrow.

Approach & Intuition

Because only four digits are in play, the search space is tiny. Try to bump the minutes first while keeping the hour: find the smallest two-digit value, built from the available digits, that is strictly greater than the current minute and still below 60. If that fails, bump the hour the same way (below 24) and reset the minutes to the smallest possible pair. If even the hour can't advance, the whole clock has peaked, so wrap to the smallest digit repeated in all four slots.

// Advance MINUTES first (same hour); else advance HOURS and reset minutes to
// the smallest; else wrap to the earliest time of the next day. Every field
// is rebuilt only from the four input digits.
public String nextClosestTime(String time) {
    String[] ss = time.split(":");
    int hour = Integer.parseInt(ss[0]), minute = Integer.parseInt(ss[1]);
    int[] digit = new int[]{hour / 10, hour % 10, minute / 10, minute % 10};
    Arrays.sort(digit);                                // ascending: digit[0] is the smallest

    String nextMin = next(digit, minute, 60);         // a larger valid minute, same hour?
    if (null != nextMin) return ss[0] + ":" + nextMin;

    String nextHour = next(digit, hour, 24);         // else a larger valid hour...
    if (null != nextHour)                  // ...minutes reset to smallest pair
        return nextHour + ":" + String.format("%d%d", digit[0], digit[0]);

    // Nothing bigger today: wrap to the smallest representable time.
    return String.format("%d%d:%d%d", digit[0], digit[0], digit[0], digit[0]);
}

// Smallest two-digit number (from the sorted digits, repeats allowed) that is
// strictly greater than `target` and strictly less than `limit`; null if none.
private String next(int[] digit, int target, int limit) {
    for (int i = 0; i < digit.length; ++i) {
        if (0 < i && digit[i] == digit[i - 1]) continue;   // skip duplicate tens digit
        for (int j = 0; j < digit.length; ++j) {
            if (0 < j && digit[j] == digit[j - 1]) continue;   // skip duplicate units digit
            int res = digit[i] * 10 + digit[j];
            if (res >= limit) continue;               // out of range (>= 60 or >= 24)
            if (res > target) return String.format("%02d", res);
        }
    }
    return null;
}

Complexity: Time O(1) — each next call examines at most 4 × 4 digit pairs and there are two calls, all independent of input size. Space O(1).

Common pitfalls / interviewer probes: Why the first hit is the minimum — the digits are sorted ascending and the tens digit dominates the value, so scanning tens-then-units in order returns the smallest value that clears target; returning any later match would be wrong. Two different limits — minutes are capped at 60 and hours at 24; reusing one cap for both yields impossible clocks like "25:00" or "xx:70". Reset, don't retain — when the hour rolls forward the minutes must drop to the smallest pair, not keep the old value. The wrap is always valid — the smallest digit of any legal HH:MM is at most 2 (the hour's tens digit is 0, 1, or 2), so digit[0]digit[0] ≤ 22 < 60; no special-casing needed. The duplicate-digit continues are a minor speedup, not required for correctness. A common follow-up is to compute the elapsed-minute distance explicitly, or to allow a chosen subset of digits.

Read N Characters Given Read4 II — Call Multiple Times

Hard Google-style

Problem

You are given a lower-level API read4(char[] buf4) that copies up to four characters from a file into buf4 and returns how many it actually read (0 at end of file). Using only read4, implement read(char[] buf, int n) that fills buf with up to n characters and returns the count read. Crucially, read may be called many times on the same file, so leftover characters fetched by an earlier read4 must survive between calls.

  • buf is guaranteed large enough to hold the characters returned by that call.
  • Once the file is exhausted, every subsequent call must return 0.

Example: for the file "greenhouse" and the call sequence read(2), read(2), read(3), read(4) the returns are 2, 2, 3, 3 filling "gr", "ee", "nho", "use". Note the second read(2) is served entirely from the "ee" chunk the first call left buffered (the opening read4 fetched "gree" and only "gr" was handed out) — no new read4 happens — and the final read(4) returns only 3 because the file ran out, after which every further call returns 0.

Approach & Intuition

The single-call version can just loop read4 into buf. The "call multiple times" twist is that one read4 may over-fetch: if the caller asked for 2 but read4 grabbed 4, the extra 2 characters must be remembered for the next read. So promote the 4-char scratch buffer, a read cursor pos, and a remaining-count cnt to instance fields. Each call first drains any leftover buffered characters, and only refills via read4 when the request is still unmet.

/**
 * read4(char[] buf4) is provided by the parent class Reader4: it copies up to
 * 4 characters into buf4 and returns how many it read (0 at end of file).
 * Because read() is called repeatedly, leftover characters from a previous
 * read4 must persist between calls -- hence the instance fields below.
 */
public class Solution extends Reader4 {
    private char[] buffer = new char[4];   // last chunk fetched by read4
    private int pos;                       // next unread index within buffer (0..3)
    private int cnt;                       // unread characters still left in buffer

    public int read(char[] buf, int n) {
        int i = 0, res = 0;             // i = write index into buf, res = total copied
        while (0 < n) {
            int k = Math.min(cnt, n);     // take as many buffered chars as we still need
            for (int j = 0; j < k; ++j, pos = (pos + 1) & 3) {
                buf[i++] = buffer[pos];    // (pos + 1) & 3 wraps 3 -> 0 (buffer is 4 wide)
            }
            cnt -= k;                      // consumed k buffered chars...
            n   -= k;                      // ...satisfying k of the request
            res += k;
            if (0 < n) {                     // still hungry: refill from the file
                pos = 0;
                if (0 == (cnt = read4(buffer))) break;   // end of file: stop
            }
        }
        return res;
    }
}

Complexity: Time O(n) per call — every returned character is copied exactly once and read4 is invoked proportionally to the characters consumed. Space O(1) — a fixed 4-character buffer plus two integers, retained across calls.

Common pitfalls / interviewer probes: State must persist — the entire difficulty over the single-call variant is that buffer, pos, and cnt are instance fields; making them locals silently drops the over-fetched tail and corrupts the next call. Reset the cursor only before a fresh fetch — pos = 0 belongs immediately before read4, never after merely draining leftovers, or you would re-read stale characters. Stop at EOF — once read4 returns 0 you must break; looping again while n > 0 would spin forever. Honour partial reads — requesting more than the file holds returns the true smaller count, and every later call returns 0. The & 3 is just a fast % 4. A natural follow-up asks to make the class thread-safe, which requires synchronising the shared cursor state.
