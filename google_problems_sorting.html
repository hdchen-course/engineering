Sorting & Searching

Seven Google-style sorting & searching problems • original framing, execution-tested solutions, and interviewer probes

Note: Representative big-tech-style problems — not sourced from Google. The “Google-style” badge denotes the flavor of question, not its source.

How to read this chapter: every worked example uses inputs invented for this book, and each stated output was produced by compiling and running the accompanying Java. Beyond hand-picked edge cases (an absent search target, an empty input array, a single element, all-equal duplicates, touching and fully-nested intervals, and both the odd- and even-total median cases) each solution was cross-checked against an independent brute force over hundreds of thousands of random inputs. The recurring idea below is to impose or exploit order — either counting/sorting to normalise, or binary-searching a monotone predicate (on an index, a value, or a partition), and, when order must be built while counting inversions, a stable merge sort that carries original indices.

Valid Anagram

Easy Google-style

Problem

Given two strings, decide whether one is an anagram of the other — that is, whether they contain exactly the same characters with the same multiplicities, just possibly reordered.

  • Strings of different lengths can never be anagrams, so a length mismatch is an instant false.
  • Assumptions: the solution shown treats input as lowercase ASCII letters a–z and is case-sensitive (so "Rat" and "tar" would not match). For mixed case, normalise first; for full Unicode, count code points in a hash map instead of a fixed 26-slot array.

Example: for "garden" and "danger" the answer is true (computed by running the code): both hold one each of a, d, e, g, n, r. For "listen" and "stolen" — same length, but listen has an i where stolen has an o — the code returns false.

Approach & Intuition

Two strings are anagrams exactly when their character frequency tables are identical. Rather than sort both (an O(n log n) route), tally counts in a single linear pass: increment for every character of the first string and decrement for every character of the second, into the same array. If the strings truly match, every count returns to zero; any non-zero slot at the end signals a surplus or deficit. Checking lengths first lets the paired increment/decrement loop run over one shared index.

public boolean isAnagram(String s, String t) {
    if (s.length() != t.length()) return false;  // different lengths can't match
    int[] count = new int[26];                    // assume lowercase a-z
    for (int i = 0; i < s.length(); i++) {
        count[s.charAt(i) - 'a']++;              // tally s
        count[t.charAt(i) - 'a']--;              // untally t in the same pass
    }
    for (int c : count) if (c != 0) return false;  // any imbalance -> not an anagram
    return true;
}

Complexity: Time O(n) — one pass to tally plus a fixed 26-slot sweep. Space O(1) — the count array has constant size (or O(k) for an alphabet of k distinct symbols).

Common pitfalls / interviewer probes: State the character-set assumption out loud. The 26-slot array assumes lowercase a–z; interviewers routinely follow up with “what about uppercase, spaces, or Unicode?” — the clean answer is a HashMap keyed by code point (and codePointAt/surrogate handling for characters beyond the Basic Multilingual Plane). Case sensitivity. As written, 'A' and 'a' differ; if the definition should ignore case, lowercase both inputs first. Length check first. Comparing lengths up front is both a fast reject and what lets the single loop index both strings safely. Counting beats sorting. The two-string tally is O(n); sorting both and comparing is O(n log n) — correct, but slower, and worth mentioning as the trade-off.

Peak Index in a Mountain Array

Medium Google-style

Problem

An array is a mountain: it strictly increases to a single peak and then strictly decreases. Return the index of that peak.

  • The peak is the unique maximum, and it is neither the first nor the last element (there is at least one step up and one step down).
  • A linear scan finds it in O(n), but the strict monotonicity on each side lets us do better with binary search.

Example: for [1, 4, 7, 9, 6, 3, 2] the answer is 3 (computed by running the code) — the peak value 9 sits at index 3. Left of it the values climb (1<4<7<9); right of it they fall (9>6>3>2), so index 3 is the turning point.

Approach & Intuition

Binary-search the slope. At any middle index, compare it with its right neighbour. If arr[mid] < arr[mid + 1] we are still on the ascending flank, so the peak must lie strictly to the right — move lo up. Otherwise we are on the descending flank (or exactly at the peak), so the peak is at mid or to its left — keep mid by setting hi = mid. The window shrinks every step and converges on the single index where the slope flips. Reading arr[mid + 1] is always safe because the loop condition lo < hi guarantees mid < hi ≤ arr.length - 1.

public int peakIndexInMountainArray(int[] arr) {
    int lo = 0, hi = arr.length - 1;
    while (lo < hi) {
        int mid = lo + (hi - lo) / 2;
        if (arr[mid] < arr[mid + 1]) lo = mid + 1;  // still ascending -> peak is to the right
        else hi = mid;                               // descending (or at peak) -> keep mid
    }
    return lo;                                       // lo == hi == peak index
}

Complexity: Time O(log n) — the search window halves each step. Space O(1).

Common pitfalls / interviewer probes: Compare against the neighbour, not against both sides. The whole trick is the single comparison arr[mid] vs arr[mid + 1]; it tells you which flank you are on without needing arr[mid - 1]. The mid + 1 read is in-bounds. Because the loop runs only while lo < hi, mid is at most hi - 1, so mid + 1 never exceeds the last index — no guard needed. Use hi = mid, not hi = mid - 1, on the descending side. mid itself may be the peak, so discarding it would skip the answer. Converge to a single index. The lo < hi / return-lo shape leaves exactly one candidate; a lo <= hi loop needs a separate stored answer. Follow-up: a general “find any peak” array (not guaranteed unimodal) uses the same neighbour-comparison binary search and still runs in O(log n).

Find First and Last Position of Element in Sorted Array

Medium Google-style

Problem

Given a non-decreasing sorted array and a target value, return the first and last indices at which the target appears, as [first, last]. If the target is absent, return [-1, -1]. The whole thing must run in O(log n).

  • Duplicates form a contiguous block, so the answer is the inclusive index range of that block.
  • A single occurrence yields first == last; a missing target yields [-1, -1].

Example: for [2, 4, 4, 4, 4, 7, 9] and target 4 the answer is [1, 4] (computed by running the code): the run of 4s starts at index 1 and ends at index 4. Searching the same array for 5 returns [-1, -1] — 5 never appears.

Approach & Intuition

Two lower-bound searches. Define lowerBound(key) as the smallest index whose value is ≥ key (or length if none) — the classic half-open binary search. The first occurrence of the target is simply lowerBound(target); if that index is off the end or the value there is not the target, the target is absent. The last occurrence is lowerBound(target + 1) - 1: the position just before the first element strictly greater than the target. One reusable primitive answers both ends without a separate “upper bound” variant.

public int[] searchRange(int[] nums, int target) {
    int first = lowerBound(nums, target);
    if (first == nums.length || nums[first] != target)
        return new int[]{-1, -1};             // target absent
    int last = lowerBound(nums, target + 1) - 1;  // one before first value > target
    return new int[]{first, last};
}
// Smallest index i with nums[i] >= key, or nums.length if none exists.
private int lowerBound(int[] nums, int key) {
    int lo = 0, hi = nums.length;             // half-open [lo, hi)
    while (lo < hi) {
        int mid = lo + (hi - lo) / 2;
        if (nums[mid] < key) lo = mid + 1;    // key is further right
        else hi = mid;                          // mid could be the boundary
    }
    return lo;
}

Complexity: Time O(log n) — two binary searches, each halving the window. Space O(1).

Common pitfalls / interviewer probes: Handle the absent target explicitly. After the first search you must check both first == nums.length (ran off the end) and nums[first] != target (landed on a larger value) before indexing — skipping the first guard throws on an out-of-range access. Derive the last index without a second search variant. lowerBound(target + 1) - 1 reuses the same primitive; writing a separate upper-bound search is a common source of off-by-one bugs. Use a half-open [lo, hi) with hi = nums.length. This lets lowerBound legitimately return length (target bigger than everything) instead of clamping. Don’t linear-scan to the ends. Finding one occurrence then walking outward is O(n) on a long run of duplicates — the interviewer’s O(log n) requirement forbids it. target + 1 overflow. If the target can equal Integer.MAX_VALUE, compute the upper bound with a long key or a strict-greater search instead.

Merge Intervals

Medium Google-style

Problem

Given a list of intervals [start, end] in arbitrary order, merge every set of overlapping intervals and return the resulting non-overlapping intervals.

  • Intervals that merely touch at an endpoint (like [1, 4] and [4, 5]) count as overlapping here and combine into [1, 5].
  • An interval can be fully nested inside another ([2, 3] inside [1, 10]), so the merged end must be the running maximum, not just the latest end.

Example: for [[1, 4], [2, 5], [7, 9], [8, 8], [11, 13]] the answer is [[1, 5], [7, 9], [11, 13]] (computed by running the code). After sorting by start, [1, 4] and [2, 5] overlap into [1, 5]; [8, 8] is nested inside [7, 9] so it leaves [7, 9] unchanged; [11, 13] stands alone.

Approach & Intuition

Sort by start, then sweep once. Once intervals are ordered by their start, any interval that overlaps the one we are currently building must begin at or before that interval’s current end — overlaps can only come from the immediate neighbour in sorted order. Carry a running cur; for each next interval, if its start is ≤ cur[1] it overlaps, so extend cur’s end to max(cur[1], next[1]) (crucial for nested intervals); otherwise there is a gap, so commit cur to the output and start a fresh one. Commit the final cur after the loop.

public int[][] merge(int[][] intervals) {
    if (intervals.length == 0) return new int[0][];
    Arrays.sort(intervals, (a, b) -> Integer.compare(a[0], b[0]));  // by start
    List<int[]> out = new ArrayList<>();
    int[] cur = intervals[0].clone();                     // running merged interval
    for (int i = 1; i < intervals.length; i++) {
        if (intervals[i][0] <= cur[1])                    // overlaps (or touches) cur
            cur[1] = Math.max(cur[1], intervals[i][1]);   // extend end (handles nesting)
        else { out.add(cur); cur = intervals[i].clone(); }   // gap -> commit, start new
    }
    out.add(cur);                                        // commit the last one
    return out.toArray(new int[0][]);
}

Complexity: Time O(n log n) — dominated by the sort; the sweep is O(n). Space O(n) for the output (plus O(log n) to O(n) sort overhead).

Common pitfalls / interviewer probes: Sort first. Without ordering by start, overlaps are not confined to adjacent intervals and the single-pass sweep is invalid. Extend the end with max, not assignment. A nested interval such as [8, 8] inside [7, 9] would shrink the end if you blindly wrote cur[1] = next[1]; taking the max keeps the widest reach. Decide whether touching merges. This solution treats [1, 4] and [4, 5] as overlapping (<=); if the problem says touching intervals stay separate, use strict < — clarify with the interviewer. Don’t forget the final commit. The last cur is still open when the loop ends and must be appended. Clone before mutating. Writing into intervals[i] directly can corrupt the caller’s data; copy the endpoints into cur.

Insert Interval

Medium Google-style

Problem

You are given a list of non-overlapping intervals already sorted by start, plus one new interval. Insert the new interval so the list stays sorted and non-overlapping, merging where necessary. Do it in a single O(n) pass — no re-sort.

  • Because the existing intervals are already sorted and disjoint, you can walk them once in three phases: those strictly before the new interval, those that overlap it, and those strictly after.
  • The new interval may overlap zero, some, or all existing intervals — or slot cleanly into a gap.

Example: inserting [4, 8] into [[1, 3], [6, 9], [11, 14]] gives [[1, 3], [4, 9], [11, 14]] (computed by running the code). [1, 3] ends before 4, so it is emitted untouched; [4, 8] overlaps [6, 9] and merges into [4, 9]; [11, 14] starts after 9, so it follows unchanged.

Approach & Intuition

Three sequential phases over the sorted list. First, copy every interval that ends strictly before the new interval starts (intervals[i][1] < newStart) — these cannot overlap. Second, absorb every interval that does overlap (its start ≤ the running merged end): widen the merged interval’s start to the smaller start and its end to the larger end. Third, append the finished merged block, then copy the remaining tail unchanged. Because the input is pre-sorted and disjoint, each interval is visited once — no sorting needed, so it beats the O(n log n) of a merge-from-scratch.

public int[][] insert(int[][] intervals, int[] newInterval) {
    List<int[]> out = new ArrayList<>();
    int i = 0, n = intervals.length;
    while (i < n && intervals[i][1] < newInterval[0])   // ends before new starts: no overlap
        out.add(intervals[i++]);
    int s = newInterval[0], e = newInterval[1];
    while (i < n && intervals[i][0] <= e) {          // overlaps the new interval
        s = Math.min(s, intervals[i][0]);
        e = Math.max(e, intervals[i][1]);
        i++;
    }
    out.add(new int[]{s, e});                        // the merged block
    while (i < n) out.add(intervals[i++]);            // everything strictly after
    return out.toArray(new int[0][]);
}

Complexity: Time O(n) — a single pass, since the list is already sorted. Space O(n) for the output.

Common pitfalls / interviewer probes: Get the phase boundaries right. The “before” test is intervals[i][1] < newStart (ends strictly before) and the “overlap” test is intervals[i][0] <= e (starts at or before the growing end) — mixing up which endpoint each compares is the classic bug. Grow both ends of the merged block. The new interval can extend left of the first overlap (so take min of starts) and right of the last (so take max of ends). Compare against the updated e. As the merged interval grows it can reach intervals that did not overlap the original new interval; the loop must test against the current e, which is why it grows inside the loop. Handle the extremes. A new interval before everything, after everything, or spanning the whole list all fall out of the same three phases — no special cases. Don’t re-sort. Concatenating and calling Merge Intervals works but is O(n log n); the interviewer wants the linear insert that exploits the existing order.

Median of Two Sorted Arrays

Hard Google-style

Problem

Given two sorted arrays, return the median of the combined set of all their elements, in O(log(min(m, n))) time. Do not actually merge them.

  • If the total count is odd, the median is the single middle element; if even, it is the average of the two middle elements.
  • Either array may be empty, so the answer can come entirely from one side.

Example: for [1, 3, 8] and [2, 4, 5, 6] the answer is 4.0 (computed by running the code): the merged order is 1, 2, 3, 4, 5, 6, 8 — seven elements, odd, so the middle one is 4. For [1, 2] and [3, 4, 5, 6] the merged order is 1, 2, 3, 4, 5, 6 (even total), so the median is (3 + 4) / 2 = 3.5. And for [] and [5] the answer is 5.0 — the lone element.

Approach & Intuition

Binary-search a partition of the shorter array. Imagine cutting each array into a left part and a right part so that all (m + n + 1) / 2 elements of the combined left half are ≤ every element of the combined right half. Choosing how many come from the shorter array a (call it i) forces how many come from b (j = half - i), so there is only one degree of freedom to search. The partition is correct when the last left element of each array does not exceed the first right element of the other (aL ≤ bR and bL ≤ aR). Use ±∞ sentinels when a cut lands at an array’s edge so the boundary comparisons just work. Always binary-search the smaller array so j can never go negative and the range stays O(log(min(m, n))).

public double findMedianSortedArrays(int[] a, int[] b) {
    if (a.length > b.length) return findMedianSortedArrays(b, a);  // search the shorter one
    int m = a.length, n = b.length;
    int lo = 0, hi = m, half = (m + n + 1) / 2;   // left side holds ceil(total/2)
    while (lo <= hi) {
        int i = lo + (hi - lo) / 2;              // take i from a ...
        int j = half - i;                        // ... and the rest from b
        int aL = (i == 0) ? Integer.MIN_VALUE : a[i - 1];
        int aR = (i == m) ? Integer.MAX_VALUE : a[i];
        int bL = (j == 0) ? Integer.MIN_VALUE : b[j - 1];
        int bR = (j == n) ? Integer.MAX_VALUE : b[j];
        if (aL <= bR && bL <= aR) {              // correct partition
            if (((m + n) & 1) == 1) return Math.max(aL, bL);  // odd total
            return (Math.max(aL, bL) + (double) Math.min(aR, bR)) / 2.0;
        } else if (aL > bR) hi = i - 1;      // took too many from a
        else lo = i + 1;                       // took too few from a
    }
    throw new IllegalArgumentException("inputs not sorted");
}

Complexity: Time O(log(min(m, n))) — the search runs over the shorter array only. Space O(1) (the tail recursion just swaps arguments once).

Common pitfalls / interviewer probes: Binary-search the smaller array. If you search the longer one, j = half - i can go negative and the index math breaks; the leading swap guarantees 0 ≤ j ≤ n. Use ±∞ at the edges. When a cut is at position 0 or the array’s length there is no left/right neighbour; substituting Integer.MIN_VALUE/MAX_VALUE makes the boundary comparisons pass without special-casing empty sides. Odd vs. even with the right half. Using half = (m + n + 1) / 2 puts the extra element on the left for odd totals, so the odd-case median is max(aL, bL) and the even-case median averages max(aL, bL) with min(aR, bR). Cast to double before averaging. (max(aL, bL) + min(aR, bR)) can overflow or truncate; average as double. Empty array. With a empty, m = 0, i = 0, and every value comes from b — the sentinels make this fall out correctly.

Count of Smaller Numbers After Self

Hard Google-style

Problem

Given an integer array, return a new array counts where counts[i] is the number of elements to the right of index i that are strictly smaller than nums[i].

  • The last element always has 0, since nothing is to its right.
  • The brute-force double loop is O(n²); the challenge is to reach O(n log n).

Example: for [6, 3, 8, 3, 1] the answer is [3, 1, 2, 1, 0] (computed by running the code). To the right of the leading 6 sit 3, 3, 1 — all smaller, so 3; the first 3 has only 1 to its right; 8 has 3, 1 — two smaller; the second 3 has just 1; the final 1 has nothing after it.

Approach & Intuition

This is a disguised inversion-counting problem, and a stable merge sort that carries original indices solves it in O(n log n). Sort an array of indices (never the values themselves) by their values. During each merge, the left half holds elements that were originally to the left of the right half. When you pull an element from the right half because it is strictly smaller than the current left element, it has “jumped ahead of” every left element still waiting — so keep a running moved counter of right elements already placed, and whenever you finally place a left element, credit it with the current moved. Stability matters: on ties, take from the left first so equal values are not miscounted as smaller.

public List<Integer> countSmaller(int[] nums) {
    int n = nums.length;
    int[] count = new int[n];
    int[] idx = new int[n];                     // sort indices, not values
    for (int i = 0; i < n; i++) idx[i] = i;
    sort(nums, idx, new int[n], 0, n - 1, count);
    List<Integer> out = new ArrayList<>(n);
    for (int c : count) out.add(c);
    return out;
}
// Stable merge sort on idx keyed by nums[idx]; tally right-half elements that pass each left element.
private void sort(int[] nums, int[] idx, int[] tmp, int lo, int hi, int[] count) {
    if (lo >= hi) return;
    int mid = lo + (hi - lo) / 2;
    sort(nums, idx, tmp, lo, mid, count);
    sort(nums, idx, tmp, mid + 1, hi, count);
    int i = lo, j = mid + 1, k = lo, moved = 0;   // moved = right elems already placed
    while (i <= mid && j <= hi) {
        if (nums[idx[j]] < nums[idx[i]]) {         // right value smaller -> it passed left[i..mid]
            moved++;
            tmp[k++] = idx[j++];
        } else {                                   // left <= right (stable): credit moved
            count[idx[i]] += moved;
            tmp[k++] = idx[i++];
        }
    }
    while (i <= mid) { count[idx[i]] += moved; tmp[k++] = idx[i++]; }  // remaining left keep the tally
    while (j <= hi)  { tmp[k++] = idx[j++]; }
    System.arraycopy(tmp, lo, idx, lo, hi - lo + 1);      // write the merged order back
}

Complexity: Time O(n log n) — standard merge-sort recursion. Space O(n) for the index, temp, and count arrays.

Common pitfalls / interviewer probes: Sort indices, carry the original position. The counts are indexed by each element’s original location, so you must move indices through the merge and write into count[idx[i]], not into a positional slot. Stability — take left on ties. The comparison must be strict (nums[idx[j]] < nums[idx[i]]); using <= would count equal values as “smaller” and over-report. Equivalently, on a tie the left element is emitted first. Credit the remaining left elements when the right half drains. After the right half is exhausted, every left element still queued must still receive the full moved count — the while (i <= mid) drain loop does this; dropping it under-counts. Copy the merged order back. Forgetting the arraycopy leaves idx unsorted for the parent merge and corrupts later counts. Alternative: a Fenwick/BIT over compressed values. Coordinate-compress the values, then scan right to left querying the prefix count of strictly-smaller values — also O(n log n) and a common follow-up.
