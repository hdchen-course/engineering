Why Three Old Papers Still Rule the Interview

A warehouse analogy, the stack the three papers form together, and the one design idea they all share.

The one-sentence idea (start here)

Imagine you must store and search every book ever written, but the only shelves you can afford are cheap wooden ones that collapse a few times a day. You would not buy one gold-plated unbreakable shelf — you would buy thousands of cheap shelves, keep three copies of every book, and hire software robots to notice a collapse and re-shelve the copies automatically. That is the whole philosophy behind all three Google papers.

The core philosophy (memorize this)

All three papers share one radical bet: hardware failure is normal, not exceptional — so tolerate it in software. Instead of expensive reliable machines, use thousands of cheap ones and let the software detect failures, re-replicate data, and re-run work. In 2003 this was a genuinely new way to build systems. Today it is simply how the cloud works.

The stack: each paper is a layer

They were not three unrelated projects. GFS sits at the bottom; MapReduce and Bigtable both sit on top of GFS as siblings (Bigtable also uses Chubby for locks) — the diagram orders them by abstraction level, not by a dependency of one on the other:

The dependency chain

BigtableGFS (stores files) + Chubby (locks)Applications that need low-latency lookupsSorted, versioned key-value at petabyte scale

Why interviewers still care in 2026

You will almost never be asked to "explain GFS." Instead, these papers are the source code of the vocabulary a system-design interview runs on. When you propose sharding, replication, a write-ahead log, an LSM tree, or speculative execution, you are quoting these papers — and naming the lineage signals depth.

  • Partitioning / sharding — GFS chunks, Bigtable tablets.
  • Replication & leader-based writes — GFS chunk replicas + leases.
  • Write-ahead log + checkpoint — GFS operation log, Bigtable commit log.
  • LSM trees & compaction — Bigtable memtable → SSTable (see also Cassandra).
  • Data locality & speculative execution — MapReduce scheduling.
INTERVIEW ANGLE

If asked "where do these ideas come from?", answer in one breath: "Google published three papers — GFS for storage, MapReduce for batch compute, Bigtable for structured serving. Together they proved you can run at web scale on cheap hardware by tolerating failure in software. HDFS, Hadoop/Spark, and HBase/Cassandra are the open-source descendants." That single sentence frames the whole chapter.

GFS The Google File System (2003)

A shared drive so large it lives on thousands of machines — and keeps working while some of them die.

The problem, in one picture

Google needed to store the crawled web: files that are tens of gigabytes, mostly written by appending to the end, read by big sequential scans, on a cluster where at any moment some machine is broken. Ordinary filesystems assume one reliable disk and lots of small files — the exact opposite. GFS was designed backwards from Google's real workload.

Tiny mental model

Think of a giant book that is too big for one shelf. GFS tears it into fixed 64 MB pages ("chunks"), photocopies each page 3 times, and scatters the copies across many shelves. A single librarian (the master) keeps only the index card — "page 5 of book X is on shelves 2, 7, and 11" — and never touches the pages themselves. Readers get the shelf numbers from the librarian, then walk straight to a shelf.

Design assumptions drove every choice

AssumptionDesign consequence
Failures are the norm, not the exceptionSelf-healing: detect dead machines, re-replicate automatically
Files are huge (multi-GB)Optimize for big sequential I/O; large 64 MB chunks
Most writes append; few overwriteA special atomic record append; relaxed consistency elsewhere
Sustained bandwidth beats low latencyBatch and pipeline data; don't optimize per-op latency
Apps and FS are co-designedGFS can expose a weaker, cheaper consistency model

Architecture: single master + chunkservers

Why a single master is a feature, not a bug

One master sounds fragile, but it makes the whole design tractable: one authoritative place for all metadata, no distributed consensus for namespace operations. Google made it safe with four moves:

  • It never touches data — only metadata, so it is not a bandwidth bottleneck.
  • Metadata fits in RAM — roughly 64 bytes per chunk, so millions of chunks are cheap to track.
  • Operation log + checkpoints — every metadata change is logged (and replicated) before responding, so the master can rebuild its state after a crash.
  • Shadow masters serve read-only metadata during a failover.
LIMITATION TO NAME

The single master caps namespace operations per second and is a scaling ceiling. Google's successor, Colossus, distributed the master. In an interview: "Single master keeps metadata consistent and simple; for higher scale I'd shard the metadata itself (like Colossus) or use a metadata DHT (a hash-based lookup spread across nodes)."

Why 64 MB chunks?

Benefit of large chunksWhy it matters
Tiny metadataA 1 TB file is only ~16K chunk entries — not millions of 4 KB blocks
Fewer master round-tripsAsk once, then stream 64 MB without re-consulting the master
Efficient network useOne long-lived TCP connection moves a lot of sequential data

The cost: a small file wastes a chunk handle, and a popular small file becomes a hotspot on the few servers that hold it (mitigated by raising its replication factor).

Read path (control vs. data)

Write path: leases & a single mutation order

The hard part: several clients may write the same chunk at once, and all 3 replicas must apply those writes in the same order. GFS solves it by separating control flow (who decides the order) from data flow (how bytes travel).

Data flow (③)

The client pushes bytes to the nearest replica, which forwards to the next nearest, chaining down the line. Each machine uses its full outbound bandwidth — bytes are not multiplied at any single sender.

Control flow (⑤–⑦)

The write command goes only to the primary. It stamps every mutation with a serial number and tells the secondaries the exact order — so all replicas end up byte-identical.

THE LEASE PATTERN

The master grants a 60-second lease making one replica the primary. During the lease the primary orders writes without asking the master again (cheap!). Leases renew via heartbeat; if the primary dies, the lease simply expires and the master safely appoints another. A lease is time-bounded delegated authority — the same idea powers distributed locks, leader election, and cache TTLs.

Relaxed consistency & atomic record append

GFS deliberately offers weaker guarantees than a normal filesystem, because the workload allows it and it makes writes far cheaper.

OperationGuaranteeMeaning
Write at a given offset (succeeds)DefinedAll replicas hold identical bytes there
Concurrent writes to one regionConsistent but undefinedReplicas agree, but content is an interleaving no single writer intended
record appendAt-least-once, at a GFS-chosen offsetThe record appears at least once (maybe with duplicates/padding); GFS, not the client, picks where

Why accept "at least once"? If an append fails on one replica, the client retries — and the replicas that already succeeded now hold the record twice. GFS chose this because appends are the dominant write, the alternative (distributed transactions) is far too expensive, and applications can dedupe using record IDs/checksums. Append is atomic up to a size limit: a record appears whole or not at all — never half-written.

"For a high-throughput log or event store, I'd use append-only writes with at-least-once semantics and client-side dedup by event ID — the exact trade-off GFS made. It collapses the write path at the cost of requiring idempotent consumers."

Fault tolerance in software

FailureDetected byRecovery
Chunkserver crashMissed heartbeatsMaster re-replicates under-replicated chunks elsewhere
Silent disk corruptionPer-64 KB-block checksums, verified on readServe from a healthy replica; re-replicate the bad one
Master crashExternal monitoringRebuild from operation log + latest checkpoint; shadows serve reads

INTERVIEW ANGLE

Expect "design a distributed file system / blob store." Cover these points: fixed-size chunks (64–128 MB), 3× replication across racks, a metadata master with operation log + checkpoints, data flows client↔chunkserver directly (master out of the data path), and lease-based primaries for write ordering. Then volunteer the ceiling: "single master limits namespace ops; at higher scale I'd shard metadata." GFS's open-source twin is HDFS (NameNode = master, DataNodes = chunkservers); cloud object stores like S3/GCS dropped POSIX-ish file semantics (the standard open/read/write file interface) for a simpler key→blob API.

MapReduce Simplified Data Processing on Large Clusters (2004)

Write code for one record; the framework runs it on a thousand machines and cleans up after every failure.

The problem, in one picture

Suppose you must count how many times each word appears across a billion web pages. The counting is trivial; the hard part is splitting the data across machines, scheduling work, handling the machine that dies mid-job, and moving intermediate results around. Before MapReduce, every team re-wrote that plumbing by hand. MapReduce lets you write just two small functions and hides all the distribution.

// You write only these two functions:
map(key, value)    // e.g. (docName, docText)
    for word in value:
        emit(word, 1)                 // intermediate (key, value)

reduce(key, values)  // e.g. ("the", [1,1,1,...])
    emit(key, sum(values))          // final (key, value)
The genius is NOT the math

"map" and "reduce" are decades-old functional-programming ideas. The contribution is the execution framework: automatic parallelization, fault tolerance, data-locality scheduling, and load balancing. You write sequential per-record code; the framework turns it into a distributed job.

Execution flow, in words

  1. Split: input on GFS is cut into M pieces (16–64 MB) — M map tasks.
  2. Assign: the master hands tasks to idle workers — assigning each map task to a worker that already holds its input split (data locality). Reduce tasks get no locality preference since their input arrives over the network via shuffle.
  3. Map: each worker runs map() on its split and buffers emitted pairs in memory.
  4. Partition & spill: buffered pairs are partitioned into R regions by hash(key) mod R and written to local disk. Locations are reported to the master.
  5. Shuffle: each reduce worker pulls its partition from every map worker's local disk over RPC.
  6. Sort/group: the reducer sorts by key so all values for a key sit together.
  7. Reduce: for each key, run reduce(key, values); write output to GFS (one file per reducer).
Why intermediate data lives on LOCAL disk (not GFS)

Writing map output to GFS would triple the I/O (3× replication) for data that is thrown away at the end of the job. Keeping it local is cheaper — the price is that if a worker dies, its map output is gone and those maps must be re-run. A deliberate trade-off: cheap common case, more work on failure.

Fault tolerance = just re-execute

FailureRecovery
Map worker diesRe-run all its map tasks — even completed ones, since their output was on the dead worker's local disk
Reduce worker diesRe-run only in-progress reduces (completed ones already wrote to GFS)
Master diesAbort and restart the job (rare enough that the paper accepts it)

Because map and reduce are deterministic and output files are published by atomic rename, a re-executed job produces the same result as a failure-free run — "exactly-once" output even with "at-least-once" execution.

Two optimizations worth naming

Combiner — a local mini-reduce

For associative/commutative reduces (like sum), run a "combiner" on the map worker before shuffling. Instead of shipping ("the",1) a thousand times, ship ("the",1000) once — slashing network traffic.

// without combiner: map emits ("the",1) x1000  -> all cross the network
// with combiner:    ("the",1) x1000 -> combiner -> ("the",1000) sent once

Backup tasks — beating the straggler

One slow machine (a "straggler") can hold up a whole 1000-machine job — the classic long tail. Near the end, the master launches backup copies of the remaining in-flight tasks; whichever finishes first wins. This can cut total job time by tens of percent for a small amount of extra compute.

"For tail latency I'd use speculative execution — duplicate the last few slow tasks and take the first to finish. Same idea as hedged requests in latency-sensitive services: spend a little extra compute to kill the long tail."

What MapReduce is bad at — and what replaced it

"MAPREDUCE IS DEAD, LONG LIVE MAPREDUCE"

Google largely retired MapReduce internally by the mid-2010s (Flume, Dataflow, Dremel/BigQuery). But the concepts — shuffle, partitioning, combiner, speculative execution, data locality — are the DNA of Spark, Flink, and every modern data pipeline. Learn MapReduce and you understand all of them.

INTERVIEW ANGLE

For "design a data-processing pipeline": partition input, map (local per-record work emitting keys), shuffle (hash-partition to reducers), reduce (aggregate per key), output. Then earn seniority points: name the combiner, data locality, and speculative execution, and add: "MapReduce writes to disk between stages, so for iterative or low-latency work I'd reach for Spark's in-memory model instead." Open-source lineage: Hadoop MapReduce → Spark; cloud: Dataproc/EMR/Dataflow.

Bigtable A Distributed Storage System for Structured Data (2006)

Not a relational database — a giant, sparse, sorted map that scales to petabytes and serves live traffic.

The problem, in one picture

GFS stores big files; MapReduce processes them in batch. But products like Search, Maps, and Analytics need to read and write individual records with low latency, all day — and there are billions of them, changing constantly. A single SQL database can't hold it, and full relational features (joins, multi-row transactions) are more than these apps need. Bigtable is the middle path: a huge sorted key-value store with just enough structure.

Tiny mental model

Picture one enormous spreadsheet, sorted by row name, where most cells are empty and empty cells cost nothing. Every cell can keep several dated versions ("what did this page look like last Tuesday?"). It's so tall it's sliced into horizontal strips ("tablets") handed to different servers. That's Bigtable.

The data model: (row, column, timestamp) → value

The entire model in one line: a Bigtable is a sorted map from (row_key, column_key, timestamp) to an uninterpreted byte string.

ConceptWhat it isWhy it's designed that way
Row keyArbitrary bytes; rows kept in sorted orderSorting makes range scans efficient; the only index you get
Column familyA declared group of columns (few, static)Unit of access control; storage tuning (compression, in-memory caching) is set per locality group — a set of families — not per family
Column qualifierA name within a family, created dynamicallySparse data with no cost for empty columns
Timestamp64-bit version per cellTime-travel reads + automatic version garbage collection
TabletA contiguous range of rows (~100–200 MB)Unit of distribution & load balancing; splits automatically
ROW-KEY DESIGN IS EVERYTHING

Since the sorted row key is the only index, it must encode your access pattern. Reverse a domain (com.google.maps/p1) to keep a site's pages adjacent. For time-series use sensorId#timestamp so one sensor scans cheaply. Anti-pattern: a bare timestamp prefix — every new write lands on the same last tablet, creating a hotspot.

Architecture: master, tablet servers, Chubby, GFS

ComponentJobIf it fails
MasterAssign tablets, balance load, GC filesExisting serving continues (it's off the data path); no new assignments
Tablet serverServe reads/writes for its tabletsIts tablets are unavailable until the master reassigns them
ChubbyElect master, track live servers, store schema/root locationBigtable becomes unavailable (hard dependency)
GFSDurable storage for all filesData at risk only if all replicas fail (very unlikely)
CHUBBY DEPENDENCY

If a tablet server loses its Chubby session it kills itself, to avoid split-brain (two servers thinking they own the same tablet). Strong consistency needs coordination, and Chubby (a Paxos-backed lock service) supplies it. In interviews: "I'd use a coordination service — ZooKeeper or etcd — for leader election and liveness, the role Chubby plays for Bigtable."

The storage engine: LSM (memtable + SSTables)

This is the most reused idea in the paper. Writes go to memory first and to immutable sorted files later; reads merge memory and files. It's a Log-Structured Merge tree.

Why write to the log first?

If the server crashes after updating the RAM memtable but before flushing an SSTable, the memtable is gone. The commit log (durable on GFS) lets the new server replay entries and rebuild the memtable — zero data loss. One commit log per tablet server (not per tablet) keeps it a single sequential write stream; the price is a more complex, sort-by-tablet recovery.

SSTables are immutable — so deletes are "tombstones"

You never edit an SSTable. A delete writes a tombstone marker that shadows older values; the data is physically removed only during a major compaction. Consequence: a delete-heavy workload can temporarily grow on disk.

Compaction & tablet splitting

CompactionDoesEffect
MinorFlush memtable → new SSTableFrees RAM; adds one SSTable
MergingMerge several SSTables into oneFewer files → less read amplification (fewer files to check per read)
MajorMerge all into one SSTablePermanently drops tombstoned data; reclaims space

When a tablet grows past ~100–200 MB the server splits it: pick a middle row key, write two entries into the METADATA table, tell the master. It's metadata-only — no data is copied; both halves reference the same SSTables with narrowed ranges. To find any tablet, clients follow a 3-level hierarchy (Chubby → root tablet → METADATA tablets → user tablet) — at most a few RPCs, and clients cache aggressively so warm lookups are free.

This IS every modern NoSQL engine

Memtable + WAL + immutable SSTables + compaction + bloom filters is the storage engine of LevelDB, RocksDB, HBase, and Cassandra. Understand Bigtable's engine and you understand all of them. The big fork: Bigtable/HBase are CP (single owner per tablet, strong single-row consistency), while Cassandra took Bigtable's data model but Dynamo's AP replication (eventual consistency, no single owner).

INTERVIEW ANGLE

For "design a scalable key-value / time-series / wide-column store": write path = WAL → memtable, flush to immutable SSTables; read path = memtable then SSTables newest-first with bloom filters; compaction to bound read amplification; range-partition by row key into tablets/shards that split and rebalance; and stress that row-key design encodes the access pattern. Trade-off to state: "LSM favors write throughput at the cost of read amplification; for read-heavy loads I'd compact more aggressively or use a B-tree engine."
