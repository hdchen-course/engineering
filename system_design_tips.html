Framework — How to Approach Any System Design Question

A structured 5-step approach that works for any system design interview. Master the framework, then customize per question.

Decision Framework — 5 Dimensions

1. Access Pattern

Read-heavy or Write-heavy? → Read Replicas or NoSQL

Key: Read-to-Write Ratio, Latency Requirements
2. Consistency

Strong Consistency (payment) vs Eventual Consistency (social posts)

Key: CAP Theorem, Data Accuracy
3. Scale

Current QPS and data growth rate? Sharding vs Vertical Scale-up

Key: Traffic Peaks, Data Scale
4. Failure Handling

Circuit Breaker and Failover strategies

Key: Fault Tolerance, Backup Plans
5. Operational Complexity

Managed Services (RDS/S3) early on to reduce toil

Key: Team Cost, Maintenance Difficulty
"Before jumping into the solution, I'd like to understand access patterns, consistency requirements, and scale — these will guide most of the design decisions."
STEP 1 Clarify Requirements (3-5 min) ▶
Functional Requirements
  • What does the system do? List core features.
  • What are the main use cases? Walk through user stories.
Non-Functional Requirements
  • Scale: How many users? DAU/MAU?
  • Latency: Real-time? Sub-100 ms? Batch is OK?
  • Availability: 99.9%? 99.99%?
  • Consistency: Strong or eventual?
  • Durability: Can we lose data? How long to retain?
Questions to Ask
  • Users: How many? Read-heavy or write-heavy? Geographic distribution?
  • Data: How much? Growth rate? Access patterns?
  • Constraints: Budget, team size, existing tech stack?
TIP

Spending 3-5 minutes here saves you from designing the wrong system. Interviewers want to see you ask smart questions.

STEP 2 Back-of-the-Envelope Estimation (2-3 min) ▶
  • DAU / MAU — daily and monthly active users
  • QPS — queries per second: average and peak
  • Storage — per-record size × records × retention period
  • Bandwidth — QPS × response size
  • Memory (if caching) — working set size
"Let me do a quick estimation to sanity check the scale. Assume 1M daily active users, each making ~10 requests per day — that's about 100 QPS on average. Peak traffic is usually ~10x, so around 1,000 QPS. This helps us decide whether a single DB is sufficient or we need sharding early."
QUICK FORMULA

QPS = DAU × actions_per_user / 86,400
Peak QPS = Average QPS × 10
Storage = records × size × retention_days

STEP 3 High-Level Design (5-10 min) ▶
  • Start with a simple architecture that satisfies current requirements
  • Draw the main components: clients, load balancer, API servers, database, cache, queue
  • Show the data flow for the core use case
  • Keep it simple — don't over-engineer at this stage
Walk Through a Basic Use Case (E-Commerce Order)
  1. Client sends POST /orders to load balancer
  2. Load balancer routes to an API server
  3. API server validates, checks inventory in cache (Redis)
  4. Cache miss → query inventory DB
  5. If in stock → start transaction: decrement inventory + create order record
  6. Push order event to message queue for async processing (payment, notification, shipping)
  7. Return 201 Created to client
EVOLUTION System Evolution — Design in Phases ▶
"I intentionally avoid starting with a complex architecture. I'd begin with a simple monolith and single DB. As we scale: the first bottleneck is usually reads — add cache and replicas. Then write scaling — consider sharding. Only introduce microservices when team or domain boundaries require it."
STEP 4 Deep Dive (10-15 min) ▶
  • The interviewer usually picks 1-2 areas to go deeper
  • Be ready to discuss: database schema, API design, caching strategy, data partitioning
  • Show trade-offs, not just one solution
"I'd choose X here because [reason]. The trade-off is [downside], but it's acceptable because [context]."
WARNING

Don't just describe a solution — always explain WHY you chose it and what you're giving up. This is the #1 differentiator between senior and junior candidates.

STEP 5 Wrap Up (3-5 min) ▶
  • Summarize key decisions and trade-offs
  • Mention what you'd improve with more time
  • Discuss monitoring, alerting, operational concerns
PRO TIP

Ending with "Here's what I'd do next with more time..." shows maturity and self-awareness.

OBSERVABILITY Monitoring / Observability — Always Mention This ▶
Three Pillars
  • Metrics: request rate, error rate, latency (p50/p95/p99), CPU/memory, queue depth, cache hit rate
  • Logging: structured logs with request IDs for traceability
  • Tracing: distributed tracing (X-Ray, Jaeger) to follow a request across multiple services
What to Monitor — By Layer
LayerMetrics
ApplicationRequest rate (QPS), error rate (4xx, 5xx), latency (p50/p95/p99)
InfrastructureCPU/memory utilization, disk I/O, network throughput, instance count
DatabaseQuery latency (slow query log), connection pool usage, replication lag, lock wait time
CacheHit rate, memory usage, eviction rate, connection count
QueueQueue depth, message age, dead letter queue size
Business Metrics Framework
  1. Primary Action — "What is the primary action users take?" → core metric
  2. Success Signal — "What does success look like?" → conversion rate, completion rate
  3. Failure Signal — "What would indicate something is wrong?" → drop in orders, spike in cancellations
SLO SLO / SLA / Error Budget ▶
"We define SLOs — for example, 99.9% availability and p99 latency under 200 ms."
"We track error budget: if we've consumed 80% of our monthly error budget, we pause feature releases and focus on reliability."
"SLOs also guide design decisions — if we need 99.99% availability, we may need multi-region setup."
NOTE

SLI = what you measure (latency). SLO = what you target (p99 < 200 ms). SLA = what you promise to customers (with penalties). Error Budget = 100% - SLO (room for experimentation).

SECURITY Security & Data Privacy — 30 Second Mention ▶
  • Authentication & Authorization: OAuth 2.0 / JWT. API gateway validates tokens. RBAC for access control.
  • Encryption: AES-256 at rest, TLS in transit. PII encrypted at application level.
  • Data Privacy: PII stored separately. Data retention policies. GDPR/CCPA compliance.
  • Input Validation: All user input validated and sanitized at API gateway level.
TIP

You don't need to go deep here, but mentioning security shows you think about production systems holistically. 30 seconds is enough.

Key Concepts to Know

Core building blocks of any distributed system. Know these cold — they come up again and again.
Scaling ▶
  • Vertical scaling: bigger machine (simple but has limits — can't scale CPU forever)
  • Horizontal scaling: more machines (needs stateless design, load balancer)
  • Database scaling: read replicas (read-heavy), sharding (write-heavy), partitioning (data size)
KEY INSIGHT

Scale vertically first (it's simpler), then horizontally when you hit a ceiling. Most startups never need horizontal scaling on day 1.

Load Balancing ▶
  • Round robin: rotate through servers sequentially
  • Least connections: send to server with fewest active connections
  • IP hash: hash client IP to always route to same server
  • Weighted: assign weights per server capacity
L4 vs L7
  • L4 (TCP): Routes based on IP/port. Fast, low overhead. Example: AWS NLB.
  • L7 (HTTP): Can inspect headers, URL path, cookies. Content-based routing, SSL termination. Example: AWS ALB, Nginx.
  • Health checks: LB pings backends, removes unhealthy ones automatically
  • Failover: unhealthy server removed from pool, traffic redistributed
Caching ▶
  • Cache-aside (lazy loading): app checks cache first, fills on miss
  • Write-through: write to cache and DB simultaneously
  • Write-behind: write to cache, async write to DB
  • Cache invalidation: TTL, event-driven, versioning
  • Tools: Redis, Memcached, CDN for static content
REMEMBER

"There are only two hard things in computer science: cache invalidation and naming things." — Phil Karlton

Database ▶
SQL
  • Strong consistency, ACID transactions, JOINs, schema enforcement
  • Examples: PostgreSQL, MySQL
NoSQL
  • Flexible schema, horizontal scaling, eventual consistency
  • Examples: DynamoDB, Cassandra, MongoDB
When to Use What
  • SQL for complex queries, transactions, relational data
  • NoSQL for high write throughput, flexible schema, simple access patterns
Indexing
  • B-tree: range queries, ordered data
  • Hash: exact match lookups
  • Composite: multi-column, order matters (leftmost prefix rule)
Message Queues ▶
  • Decouple producers and consumers
  • Buffer traffic spikes
  • Enable async processing
  • Tools: SQS, Kafka, RabbitMQ
  • Delivery: At-least-once vs exactly-once
TIP

Most systems use at-least-once delivery + idempotent consumers. Exactly-once is extremely expensive.

Consistency Models ▶
  • Strong consistency: read always returns latest write (slower, less available)
  • Eventual consistency: reads may be stale temporarily (faster, more available)
  • CAP theorem: in a network partition, choose Consistency or Availability
REAL WORLD

Most real systems choose availability + eventual consistency. Strong consistency is reserved for financial transactions, inventory counts, and similar critical paths.

Rate Limiting ▶
  • Token bucket: tokens refill at fixed rate, request consumes a token. Allows bursts.
  • Sliding window: count requests in rolling time window
  • Fixed window: count in fixed time buckets (simpler but boundary problem)
  • Scope: Per-user, per-IP, per-API-key
  • Response: Return 429 Too Many Requests

Common Patterns

Classic system design problems distilled to their core patterns and key decisions.
URL Shortener CLASSIC ▶
  • ID Generation: Hash function (MD5/SHA, take first 7 chars) or counter-based auto-increment ID
  • Encoding: Base62 encoding (a-z, A-Z, 0-9) — 7 chars = 62^7 = 3.5 trillion URLs
  • Storage: Key-value store (short_url → long_url)
  • Caching: Cache hot URLs in Redis (Pareto: 20% URLs get 80% traffic)
  • Redirect: 301 (permanent, cached by browser) vs 302 (temporary, server sees every hit for analytics)
KEY DECISION

301 vs 302: Use 302 if you need analytics (click tracking). Use 301 if you want to reduce server load.

Chat System MEDIUM ▶
  • Protocol: WebSocket for bidirectional real-time communication
  • Message delivery: Message queue for reliable delivery
  • Fan-out: Fan-out on write (fast read for small groups) vs fan-out on read (for large groups/celebrities)
  • Presence service: heartbeat-based online/offline status
  • Storage: Append-only log (Cassandra) for message history
  • Scaling: Redis Pub/Sub for cross-server message routing
News Feed / Timeline MEDIUM ▶
  • Fan-out on write: When user posts, push to all followers' timelines. Fast read, slow write. Good for users with few followers.
  • Fan-out on read: When user opens feed, pull from all followed users. Slow read, fast write. Good for celebrities.
  • Hybrid approach: Fan-out on write for normal users, fan-out on read for celebrities (>10K followers)
  • Ranking: ML-based ranking (engagement prediction, recency, relevance)
REAL WORLD

Twitter uses a hybrid: regular users' tweets are fanned out on write. Celebrity tweets are pulled on read and merged into the timeline.

Rate Limiter CLASSIC ▶
  • Token Bucket: Most common. Allows bursts. Smooth average rate. Tokens refill steadily.
  • Fixed Window: Simplest. Count requests in fixed time windows. Boundary problem (2x burst at window edges).
  • Sliding Window Log: Precise. Store timestamp of each request. High memory usage.
  • Sliding Window Counter: Good balance. Weighted count from current + previous window.
  • Distributed: Redis INCR + EXPIRE for atomic counter across all servers.
Notification System MEDIUM ▶
  • Channels: Push (APNs, FCM), SMS, Email — different reliability and cost
  • Priority queue: urgent notifications processed first
  • User preferences: opt-in/opt-out per channel, quiet hours
  • Retry: exponential backoff for failed deliveries
  • Deduplication: idempotency key prevents sending same notification twice
  • Rate limiting: don't spam users (max N notifications per hour)

Database Deep Dive

Partitioning, replication, and indexing strategies — the foundation of scalable storage.
Partitioning / Sharding ▶
  • Horizontal partitioning: split rows across shards by key
  • Hash-based: consistent hashing to distribute evenly. Good uniform distribution.
  • Range-based: by date, region, alphabet. Risk of hot spots (e.g., all new data goes to latest partition).
TRAP

Resharding is extremely painful — plan your sharding key carefully upfront. Bad shard key = hot partitions = one shard overloaded while others idle.

TIP

Good shard keys: user_id (even distribution), order_id. Bad shard keys: country (skewed), date (hot partition).

Replication ▶
  • Single-leader: one write node, multiple read replicas. Simple, good for read-heavy. Replication lag is the trade-off.
  • Multi-leader: multiple write nodes. Needed for multi-region writes. Conflict resolution required (last-write-wins, vector clocks, CRDTs).
  • Leaderless: quorum reads/writes (Dynamo-style). W + R > N makes the read and write sets overlap, so a read sees at least one replica with the latest acknowledged write — but this is not full linearizability (concurrent or partial writes and read-repair races can still surface stale values). Highly available.
QUORUM FORMULA

W + R > N where W = write quorum, R = read quorum, N = total replicas. Example: N=3, W=2, R=2 ensures at least one node has the latest write.

Indexing ▶
  • Primary index (clustered): determines physical row order. Only one per table.
  • Secondary index (non-clustered): separate structure, pointer to row. Can have many.
  • Composite index: multi-column. Order matters — leftmost prefix rule. INDEX(a,b,c) supports queries on (a), (a,b), (a,b,c) but NOT (b) or (c) alone.
TRADE-OFF

Too many indexes slow down writes. Every INSERT/UPDATE/DELETE must update all indexes. Balance read performance against write overhead.

Quick reference for RESTful API conventions and best practices.

Pagination ▶
  • Cursor-based (scalable): GET /messages?cursor=abc123&limit=10. Uses WHERE id > cursor LIMIT 10. Consistent performance regardless of page depth.
  • Offset-based (simple): GET /messages?offset=20&limit=10. DB must skip N rows — slow at high offsets.
TIP

Use cursor-based for infinite scroll or large datasets. Offset-based is OK for admin panels with few pages.

Versioning & Idempotency ▶
Versioning
  • URL path: /v1/resource (most common)
  • Accept header: Accept: application/vnd.api+json; version=1
Idempotency
  • POST with idempotency key for safe retries
  • Client generates UUID, sends as header Idempotency-Key: uuid
  • Server checks if key was seen before → return cached result. New? → execute and store.
Rate Limiting Headers
  • X-RateLimit-Limit — max requests allowed in window
  • X-RateLimit-Remaining — requests left in current window
  • X-RateLimit-Reset — when the window resets (epoch time)

MEMORIZE THIS

1 day = 86,400 seconds ≈ 10^5 seconds. So 1M requests/day ≈ 10 QPS. Just divide daily volume by 10^5 for average QPS.

INSIGHT

Resolving the "~10 vs ~12 QPS" discrepancy: both numbers describe 1M requests/day — one is exact, one is a mental-math shortcut. Exact: 1,000,000 / 86,400 s = 11.6 QPS (round to ~12). The "~10 QPS" figure is the interview back-of-the-envelope trick — divide by 100,000 instead of 86,400 (since 86,400 is close-ish to 105), which is fast to do in your head and deliberately conservative. Use ~10 to reason out loud; use ~12 if you write the precise arithmetic.

  • Clean rule (exact avg): 1M/day ≈ 12 QPS, 10M/day ≈ 116 QPS, 100M/day ≈ 1,160 QPS (each 10x scales linearly).
  • Mental-math rule (÷100k): 1M/day ≈ 10 QPS, 10M/day ≈ 100 QPS, 100M/day ≈ 1,000 QPS — always slightly under the true value, which is safe for "at least this much" capacity talk.
  • Peak vs average: the numbers above are averages. Apply a peak factor of 2-10x (daily traffic cycles, bursts, thundering-herd) before sizing servers, connection pools, or rate limits. State your assumed factor explicitly.
"Is 1M requests/day 10 or 12 QPS?" — Answer: exactly 11.6 (≈12); 10 is the divide-by-100k approximation. Then immediately add: "but I'd design for peak, so ~24-120 QPS depending on burstiness."
TIP

Latency numbers: quote the canonical table, but know it's dated. The "Latency Numbers Every Programmer Should Know" list traces to Jeff Dean's ~2009 talks (building on Peter Norvig's ~2001 list); Jonas Bonér's gist popularized the static list in 2012, and Colin Scott's year-by-year interactive version (~2016-2017) is where most people first meet it. It's still the shared vocabulary interviewers expect — anchor on it, then note that real hardware moved on. Two figures are most out of date:

NOTE

The relative ordering (L1 < RAM < SSD < network < disk seek < cross-continent RTT) is what actually matters for design and hasn't changed. Cite both: "The classic table says SSD random read is ~150 µs; modern NAND NVMe is closer to ~40-100 µs — either way it's ~100-1000x slower than RAM, so I'll cache hot reads." The sub-20 µs numbers you may have seen were Intel Optane / 3D XPoint, not commodity NAND (Optane was discontinued in 2022, and QLC is slower than TLC, not faster). Rotational-disk seek (~10 ms) and CA↔Europe RTT (~150 ms) are still accurate — physics and geography don't get firmware updates.

Common Mistakes

Avoid these pitfalls — they are the most common reasons candidates fail system design interviews.
MISTAKE #1

Jumping into solution without clarifying requirements. You'll design the wrong system. Always spend 3-5 minutes asking questions first.

MISTAKE #2

Not doing back-of-the-envelope math. Without numbers, you can't justify whether a single DB suffices or you need sharding. A quick calculation shows you thought about scale.

MISTAKE #3

Single point of failure. Always ask "what if this component goes down?" Every critical component needs redundancy or a failover plan.

MISTAKE #4

Ignoring data consistency requirements. Not all data needs strong consistency. But payment data does. Know the difference and state your choice explicitly.

MISTAKE #5

Over-engineering. Don't add Kafka, microservices, and Kubernetes for 100 users. Start simple. Evolve as needed. Show you know WHEN complexity is justified.

MISTAKE #6

Not discussing trade-offs. Every decision has pros and cons. Saying "I'd use Redis" without explaining why (and what you give up) shows shallow understanding.

MISTAKE #7

Forgetting operational concerns. Monitoring, logging, alerting, deployment, rollback — these separate production systems from hobby projects.

Phrases That Show Depth

Use these phrases to demonstrate senior-level thinking during your interview.
"The trade-off here is..."
"At this scale, we'd need to consider..."
"One concern with this approach is..."
"We could start simple with X and evolve to Y as traffic grows"
"This depends on whether we prioritize consistency or availability"
"Let me do a quick calculation to see if this fits in memory"
WHY THESE WORK

These phrases signal that you think in trade-offs (not absolutes), consider scale implications, and approach design incrementally. This is exactly how senior engineers reason about systems.

ANTI-PATTERNS TO AVOID

"We should use [technology]" without explaining why.
"This is the best approach" — nothing is universally best.
"We need microservices" — without justifying the complexity.

Interview Anti-Patterns AVOID ▶
DON'T SAY

"I choose MongoDB because it's faster" — faster at what? This shows shallow understanding.

DON'T SAY

"SQL can't scale horizontally" — it can (Vitess, ProxySQL, CockroachDB), just more operational cost.

DON'T SAY

"NoSQL has no transactions" — MongoDB 4.0+ supports multi-document transactions.

DO SAY

"Both can do X, but [this one] was designed for it, so the operational cost and performance characteristics are better for our use case because [specific reason]."

Message Queue — When, Why, and Trade-offs

Queues are powerful but add complexity. Know when they help and when they hurt.
When to Add a Queue USE ▶
  • Decoupling: Service A doesn't wait for Service B. They evolve independently.
  • Traffic spike buffering: Queue absorbs spike, consumers process steadily at their own pace.
  • Fan-out: One event, multiple consumers (e.g., order placed → email, analytics, inventory update).
  • Retry/reliability: Failed messages stay for retry. Dead Letter Queue (DLQ) for repeated failures.
When NOT to Add a Queue AVOID ▶
  • User needs immediate response: "Is my payment successful?" can't wait for async processing.
  • System is simple: 2-3 services, direct HTTP calls are fine.
  • Low traffic: 3 requests/day doesn't need buffering — it adds needless complexity.
OVER-ENGINEERING

Adding a queue to a simple system is a common over-engineering mistake. Only add when you have a clear need (decoupling, buffering, fan-out, or reliability).

Trade-offs of Queues ▶
  • Eventual consistency: user sees "order placed" but email arrives seconds later. User might refresh and not see update yet.
  • Increased complexity: message ordering, deduplication, DLQ monitoring, consumer idempotency — all new concerns.
  • Harder debugging: request spans multiple services asynchronously. Distributed tracing becomes essential.
Queue vs Pub/Sub ▶
  • Queue model (SQS): one message → one consumer. Competing consumers split work.
  • Pub/Sub model (SNS, Kafka topics): one message → all subscribers get a copy.
  • Fan-out pattern (SNS + SQS): SNS broadcasts to multiple SQS queues, each feeds one service.
  • Google Pub/Sub: does both models in one service.
Delivery Semantics ▶
SemanticMeaningTrade-off
At-most-onceSend once, if lost it's lostFastest, may lose messages
At-least-onceGuaranteed delivery, may duplicateConsumer must be idempotent
Exactly-onceNo loss, no duplicatesKafka supports but with performance cost
BEST PRACTICE

Most systems use at-least-once + idempotent consumers. This gives you reliability without the performance penalty of exactly-once.

Consumer Idempotency — Key Interview Point

Use order ID (or message ID) as idempotency key. Before processing, check if already processed. If yes, skip. This makes at-least-once delivery safe.

Caching — When to Use, When Not to, and Trade-offs

Caching is a multiplier for read performance — but misuse creates consistency nightmares.
When Cache Makes Sense USE ▶
  • Read-heavy workload (10:1+ read-to-write ratio)
  • Expensive computation (aggregation, ML inference results)
  • Hot data (power law / Pareto — 20% of data serves 80% of requests)
  • Latency-sensitive (sub-10 ms response needed)
When Cache Does NOT Make Sense AVOID ▶
  • Write-heavy workload: cache invalidated constantly, defeating the purpose
  • Low traffic: 3 requests/day, cache overhead not worth it
  • Data must be real-time: stock prices, live inventory counts (stale data = wrong decisions)
  • Large working set with no hot data: everything accessed equally = cache keeps evicting
Caching Strategies CRITICAL ▶
StrategyFlowProsConsBest For
Cache-Aside (Lazy Loading)Read: Miss → DB → Update Cache. Write: DB → Delete CacheSimple, only caches what's neededCold start (first read slow)Most common, general-purpose
Write-ThroughWrite: Cache AND DB at once. Read: Always from cacheConsistent, always freshDouble write latencyData integrity critical
Write-Behind (Write-Back)Write: Cache only → Async to DB. Read: Always from cacheBlazing fast writesRisk of data loss if cache crashesWrite-heavy, gaming, metrics
Cache Invalidation ▶
  • TTL (Time-To-Live): simplest. Short TTL (30s) = fresher but more misses. Long TTL (1h) = better hit rate but stale risk.
  • Event-driven invalidation: explicitly delete cache on data change. Fresher but requires pub/sub infrastructure.
  • Versioning: append version to cache key (e.g., user:123:v5). Old entries naturally become unused.
Common Cache Problems TRAPS ▶
CACHE STAMPEDE (THUNDERING HERD)

Popular key expires → hundreds of requests hit DB simultaneously. Fix: lock (only one request rebuilds), staggered TTL with jitter, pre-warm before expiry.

CACHE PENETRATION

Requests for non-existent data always miss cache, always hit DB. Fix: cache "not found" result with short TTL, bloom filter to check existence before query.

HOT KEY

One key gets disproportionate traffic, overloading a single cache node. Fix: replicate across nodes, add local in-memory cache (L1) in front of Redis.

Redis as Cache — Why It Dominates ▶
  • In-memory, sub-millisecond reads
  • Rich data structures (strings, hashes, lists, sorted sets)
  • Built-in TTL per key
  • Atomic operations (INCR, LPUSH, ZADD) for counters, rate limiters, leaderboards
  • Optional persistence (RDB snapshots, AOF)
  • Cluster mode for horizontal scaling
Multi-Layer Caching ▶

Layer caches to reduce load at each level:

LAYERS

Client (browser/CDN) → API Gateway cache → Application cache (Redis) → Database

Each layer catches requests before they reach the more expensive layer below. CDN handles static assets, API Gateway caches common responses, Redis handles dynamic hot data.

APIgRPC vs REST vs GraphQLAPI STYLE▶
"We're standing up a new service. Do we expose REST, gRPC, or GraphQL — and why?"

All three are ways to move structured data between a client and a server; they differ in transport, encoding, and who decides the shape of the response. There is no universally "best" one — the right pick falls out of who the caller is (public third party, internal service, or a UI aggregating many backends).

REST

  • Model: resources addressed by URLs, manipulated with HTTP verbs (GET/POST/PUT/PATCH/DELETE) and status codes. Usually JSON over HTTP/1.1 or HTTP/2.
  • Strengths: ubiquitous, human-readable, trivially debuggable (curl/browser), and it rides the mature HTTP toolchain — CDNs, proxies, and GET response caching via Cache-Control/ETag for free.
  • Weakness: fixed response shapes lead to over-fetching (endpoint returns more than the client needs) and under-fetching (client must call N endpoints to build one screen).

gRPC

  • Model: contract-first RPC. You define services/messages in a .proto file and generate typed client + server stubs. Runs over HTTP/2, serializes with Protocol Buffers (compact binary).
  • Strengths: low latency and small payloads, strong typing, and four call styles — unary, server-streaming, client-streaming, and bidirectional streaming — all multiplexed over one HTTP/2 connection. Excellent for high-volume internal service-to-service traffic.
  • Weakness: not natively callable from browsers — JS can't control the raw HTTP/2 frames gRPC needs — so browser clients require grpc-web plus a proxy (e.g. Envoy) or a gateway. Binary payloads are also harder to read at a glance than JSON.

GraphQL

  • Model: a single endpoint (typically POST /graphql) exposing one typed schema; the client specifies exactly which fields it wants in each query.
  • Strengths: directly kills over- and under-fetching — one round trip returns precisely the shape the UI needs, aggregated across multiple backends. Strongly typed schema with introspection.
  • Weakness: resolvers can trigger the N+1 query problem (mitigated with batching/DataLoader), and because most operations are a single POST, you lose HTTP-level caching and must cache at the application/field layer instead. Server complexity is higher.

When to pick which

Public / third-party API

Broadest client compatibility, easy to document (OpenAPI), cacheable, debuggable without special tooling.

Key: REST
Internal microservice-to-service

You control both ends, want a strict contract, low latency, small payloads, and streaming.

Key: gRPC

Key: GraphQL
TIP

Tip: These aren't mutually exclusive — a very common production topology is GraphQL (or REST) at the edge for browsers, gRPC behind it for service-to-service calls. Pick per hop, not per company: the browser boundary favors REST/GraphQL, the internal mesh favors gRPC.

NOTE

Interview framing: lead with the caller and the boundary ("who calls this, and can they speak HTTP/2?") rather than declaring a favorite. Naming a concrete trade-off — grpc-web proxy for browsers, N+1/caching cost for GraphQL, over-fetching for REST — signals you've actually operated these.

API Design — Talking Points

Idempotency, pagination, and HTTP status codes — the details that matter.
Idempotency — Deep Dive ▶
Definition — say this first

Idempotent = doing it once and doing it N times leave the system in the same state. It's about the side effect, not the response body. (Note: "idempotent" ≠ "safe" — GET is both; DELETE is idempotent but not safe because it changes state.)

MethodIdempotent?Why
GETYes (& safe)No state change at all
PUTYes"Set to X" — repeating sets it to X again (same state)
DELETEYesDeleting twice = still gone (same end state)
POSTNo"Create new" — repeating makes duplicates. This is the one you must protect with an idempotency key.
The core problem

Networks retry — timeouts, load balancers, client retries, at-least-once queues. The request may have already succeeded but the response got lost. Retrying a POST /charge would charge the user twice. Idempotency makes "do it again" safe.

Idempotency-key pattern — the full lifecycle
  1. Client generates a unique key (UUID) per logical operation and sends it: Idempotency-Key: <uuid>. Crucially the key is generated once and reused across retries of the same operation (not regenerated each retry).
  2. Server looks up the key in an idempotency store:
    • Not seen → record key as in-progress, execute the operation, store the result + response, mark done, return it.
    • Seen & done → skip execution, return the stored response (same status + body).
    • Seen & in-progress → a concurrent duplicate is mid-flight → return 409 Conflict (optionally with Retry-After), or block until it finishes.
The concurrency trap (senior-level point)

Two retries can arrive simultaneously — both do the "not seen?" check before either writes. Naive check-then-act races and you charge twice anyway. Fix: make the key insert atomic — a unique constraint / conditional write (INSERT ... ON CONFLICT DO NOTHING, or DynamoDB attribute_not_exists). Whoever wins the insert executes; the loser reads the result. The DB's uniqueness guarantee is what actually enforces idempotency.

Design decisions to raise
DecisionAnswer
Where to store keys?Fast KV with TTL (Redis) for the common path, or the same transactional DB as the write so the key + the effect commit atomically (best correctness). Redis-only risks key-stored-but-write-failed splits.
How long to keep keys?A TTL (e.g. 24h) — long enough to cover all realistic retries, not forever. Bounds storage.
Scope of a key?Per user + per endpoint, so one client's key can't collide with another's. Often store a hash of the request body too, to reject "same key, different payload" (a client bug).
What do you return on replay?The exact original response (status + body), so the client can't tell it was a replay. Store it with the key.
Idempotency vs exactly-once

"Exactly-once delivery" is famously near-impossible/expensive. The practical pattern is at-least-once delivery + idempotent processing = effectively-once. So idempotency is how you get exactly-once semantics without exactly-once delivery. (Ties to the Message Queue section.)

Where idempotency shows up (mention breadth)
  • Payments / orders — the classic: don't double-charge on retry.
  • Queue consumers — at-least-once delivery means dedupe by message ID before processing.
  • Webhooks — providers retry; consumers must dedupe by event ID.
  • Infra / deploys (CDK, Terraform) — "apply" is idempotent: converge to desired state whether run once or thrice.
Common interview follow-ups

"Two identical requests arrive at the same instant?" → atomic key insert (unique constraint); loser returns the winner's result.
"Where do you store the key and for how long?" → transactional DB (or Redis) keyed by user+endpoint, with a TTL covering retry windows.
"Same key but different request body?" → reject (409) — store a body hash to detect it; it's a client bug.
"Isn't PUT already idempotent, why need a key?" → PUT is idempotent for "set to X", but POST create-new isn't — that's the case needing a key. Also, even PUT needs care if the handler has extra side effects (emails, events).

Rate Limiting & Resilience Patterns

Protecting your system from abuse (inbound) and from cascading failures (outbound).
Inbound Rate Limiting ▶
Where to Apply
  • API Gateway (coarse): IP-based, global limits. First line of defense.
  • Application (fine): per-user, per-endpoint limits. Business logic aware.
Algorithms
AlgorithmDescriptionPros/Cons
Token BucketTokens refill at fixed rate. Request consumes token.Most common. Allows bursts. Smooth average.
Fixed WindowCount requests in fixed time windowsSimplest. Boundary problem (2x burst at window edges)
Sliding Window LogStore timestamp of every request in windowPrecise. High memory usage.
Sliding Window CounterWeighted count from current + previous windowGood balance of precision and efficiency
Distributed Rate Limiting

Redis INCR + EXPIRE for atomic counter across all servers. All API instances share one counter in Redis.

Outbound Resilience Patterns ▶
  • Respect External Rate Limits: read X-RateLimit-Remaining, Retry-After headers. Back off proactively.
  • Retry with Exponential Backoff + Jitter: 1s, 2s, 4s, 8s... + random jitter to avoid thundering herd. Max 3 attempts.
  • Timeout: Always set timeouts. Separate connect timeout (2s) and read timeout (10s). Never wait forever.
  • Bulkhead: Separate connection pools per external service. If payment service hangs, it doesn't exhaust connections for other services.
Circuit Breaker Pattern ▶
KEY INSIGHT

Circuit breaker prevents cascading failures. When a downstream service is down, hammering it with retries makes things worse. Fail fast, give it time to recover, then test with a single request.

CDN — Quick Reference

Content Delivery Network basics for system design interviews.
What CDN Does ▶
  • Caches static content (JS, CSS, images, videos) at edge locations close to users
  • Reduces latency (content served from nearest edge, not origin)
  • Reduces origin server load (most static requests never reach your servers)

ModeHow It WorksBest For

BEST PRACTICE

Use content hashing in filenames: app.a3b2c1.js. When content changes, filename changes, CDN fetches new version. Build tools (webpack, vite) do this automatically. Never manually purge CDN.

What NOT to Put on CDN AVOID ▶

Never cache authenticated API responses in CDN without careful configuration. A misconfigured CDN can serve one user's private data to another.

Appendix A: MySQL Index Internals

Deep understanding of InnoDB indexing — a differentiator in database-focused interviews.
Clustered Index (Primary Key) ▶
  • InnoDB stores rows physically ordered by primary key
  • Only one per table (it IS the table)
  • Range queries on PK are very fast (sequential disk reads)
  • Auto-increment = sequential writes (fast, appends to end)
  • UUID = random inserts (slow, page splits, fragmentation)
PERFORMANCE IMPACT

UUID as primary key causes random page splits and poor cache utilization. For high-write workloads, auto-increment or time-sorted IDs (ULID, Snowflake) are much better.

Secondary Index ▶
  • Separate B-tree structure
  • Leaf nodes contain: indexed column values + primary key value
  • Lookup = 2 steps: secondary index → get PK → clustered index (table) to get full row
  • Covering index skips step 2 — if all needed columns are in the index, no need to go to clustered index
OPTIMIZATION

A covering index (includes all columns the query needs) eliminates the "bookmark lookup" to the clustered index. This can be 2-3x faster for read-heavy queries.

Composite Index ▶
  • Follows leftmost prefix rule
  • INDEX(a, b, c) works for queries on:
Query ConditionUses Index?
WHERE a = ?Yes
WHERE a = ? AND b = ?Yes
WHERE a = ? AND b = ? AND c = ?Yes (full)
WHERE b = ?No (skips leftmost)
WHERE c = ?No (skips leftmost)
WHERE a = ? AND c = ?Partial (uses a only)
Impact on Writes ▶
  • Every index must be updated on INSERT/UPDATE/DELETE
  • More indexes = slower writes
  • Rule of thumb: 5-7 indexes max per table for OLTP (Online Transaction Processing) workloads
  • Monitor: SHOW INDEX FROM table, check for unused indexes via slow query log
BALANCE

Indexes are a read-write trade-off. Add indexes for frequent queries. Remove indexes that are never used. Monitor and adjust.

Appendix B: PostgreSQL vs MySQL Index Differences

Understanding the storage engine differences explains why companies choose one over the other.

Why Uber Switched from PostgreSQL to MySQL ▶
  • At high write throughput, PostgreSQL's heap bloated with dead tuples
  • VACUUM couldn't keep up with the rate of dead tuple generation
  • Replication amplified the problem (WAL replayed dead tuples on replicas)
  • MySQL's undo log approach kept the table compact
  • InnoDB clustered index = sequential writes for append-heavy patterns (trip data)
CONTEXT MATTERS

This doesn't mean "MySQL is always better." Uber's workload was very specific: append-heavy, high write throughput, many replicas. For most read-heavy workloads with complex queries, PostgreSQL is excellent.

"The choice between PostgreSQL and MySQL depends on workload characteristics. For append-heavy, high-write workloads with many replicas, MySQL's InnoDB storage engine handles dead tuples more gracefully. For complex analytical queries and rich SQL features, PostgreSQL often wins."

  • Role: Find points of interest, businesses, landmarks via text queries

  • Features: Fuzzy matching, category filters, distance-weighted relevance scoring
6 Routing Service (Pathfinding with Dijkstra/A*, ETA) ▶
  • Role: Compute optimal routes between points, estimate arrival times
  • Algorithms: Dijkstra (shortest path), A* (heuristic-guided), Contraction Hierarchies (pre-computed long-distance)
  • ETA: Historical traffic data + real-time conditions + ML predictions
  • Graph: Road network as weighted directed graph — edges = road segments, weights = travel time
7 Geo-Database (PostGIS / Cosmos DB, Spatial Indexing) ▶
  • Role: Store and query geospatial data with spatial indexes
  • Tech: PostGIS (PostgreSQL extension), MongoDB with 2dsphere, Azure Cosmos DB with spatial
  • Index types: GiST (R-tree based), SP-GiST (space-partitioned), BRIN (block range for sorted data)
  • Queries: ST_DWithin (within distance), ST_Intersects (overlap), ST_Contains (inside polygon)
8 Cache (Redis with Geo Commands, Hot Locations) ▶
  • Role: Cache hot locations, store real-time coordinates for moving entities
  • Commands: GEOADD (store coords), GEORADIUS (find nearby), GEODIST (distance between)
  • Use case: Driver/courier real-time position tracking — update every 3-5 seconds
  • TTL: Short expiry for real-time data, longer for POI cache

Key Concepts

Tile System CORE ▶
  • Map divided into tiles at different zoom levels
  • Quadtree addressing: each tile subdivides into 4 children
  • Zoom level N has 4N tiles
  • Standard tile size: 256x256 or 512x512 pixels
  • URL pattern: /{z}/{x}/{y}.png — easily cacheable by CDN
TIP

Tiles are immutable per version — perfect for CDN caching. When map data updates, increment the version in the URL path to bust cache.

Geohashing CORE ▶
  • Concept: Convert 2D coordinates (lat, lng) to a 1D string
  • Property: Nearby points share a common prefix
  • Use case: Proximity queries — find all entities with the same geohash prefix
  • Trade-off: Precision vs cell size — longer hash = smaller cell = more precise
  • Example: Geohash length 6 = ~1.2 km x 0.6 km cell
EDGE CASE

Two points can be very close but have different geohash prefixes if they straddle a cell boundary. Solution: query the target cell AND its 8 neighbors.

Spatial Indexing CORE ▶

R-treeBounding rectangles, hierarchicalRange queries, polygon containment
QuadtreeRecursive subdivision into 4 quadrantsPoint queries, variable density data
GeohashString prefix matchingProximity queries, distributed caching

Choice depends on query pattern: R-tree for complex geometry, Quadtree for adaptive resolution, Geohash for simple key-value stores.

Real-time Location Updates IMPORTANT ▶
  • Protocol: Use WebSocket for driver/courier tracking (bidirectional, low overhead)
  • Storage: Store in Redis with GEOADD key lng lat member
  • Query: Find nearby with GEORADIUS key lng lat radius unit
  • Update frequency: Every 3-5 seconds per active entity
  • Fan-out: Push updates to riders/customers watching a specific driver via pub/sub

Additional Design Patterns

Quick-reference cards for common, classic system design problems. Each covers key components, data flow, tricky parts, and an interview phrasing.
Design a Web Crawler HARD ▶
Key Components
  • URL Frontier: Priority queue — manages which URLs to crawl next (BFS order, priority by domain importance)
  • Fetcher: HTTP client + headless browser for JS-rendered pages
  • Parser: Extract links, text content, metadata from fetched pages
  • Content Store: Detect duplicates via content hash (SimHash / MinHash for near-duplicates)
  • URL Filter: Respect robots.txt, deduplicate URLs, apply domain rules
Data Flow
  • Seed URLs → URL Frontier → Fetcher → Parser → extract links → filter & dedup → back to Frontier
  • Parsed content → Content Store (check hash for duplicates) → Index / Storage
Key Decisions
  • BFS vs DFS: BFS preferred — ensures breadth coverage, avoids getting trapped deep in one site
  • Politeness: Rate limit per domain (1 req/s default), separate queue per host
  • Distributed coordination: Consistent hashing to assign URL domains to worker nodes
Tricky Parts
  • Infinite loops: URL normalization + Bloom filter for seen-URL dedup
  • Spider traps: Detect via max depth limit, URL pattern detection
  • Dynamic content: Headless browser rendering increases cost 10x — use selectively
"I'd use a distributed URL frontier partitioned by domain to enforce politeness. Each worker fetches, parses links, and adds new URLs back to the frontier after checking against a bloom filter for deduplication."
Design a Unique ID Generator MEDIUM ▶
Key Components & Approaches
ApproachProsCons
UUID (128-bit)No coordination needed, simpleLong (36 chars), not sortable by time

  • 41 bits: Timestamp in milliseconds (supports ~69 years from epoch)

"I'd use a Snowflake-like approach: 64-bit IDs with timestamp prefix for rough time-ordering, machine ID for distributed generation without coordination, and a sequence counter for same-millisecond uniqueness."
Design a Search Autocomplete System MEDIUM ▶
Key Components
  • Trie: Prefix tree for fast prefix matching — each node represents a character
  • Frequency counter: Track query popularity for ranking suggestions
  • Cache: Redis cache for hot prefixes (top 10-20% of queries)
Data Flow
  • User types → check cache → query trie → rank by frequency → return top-5
  • Each keystroke triggers a lookup (debounced 100-200 ms on client side)
Optimization
  • Precompute top-K: Store top-K completions at each trie node — avoids traversal at query time
  • Async updates: Frequency counters updated via batch pipeline (e.g., every 15 min), not on the read path
  • Shard by prefix: Partition trie across nodes by first 1-2 characters
Tricky Parts
  • Handling typos: Edit distance (Levenshtein) for fuzzy matching — expensive, use only for cache misses
  • Personalization: Per-user recent queries layered on top of global suggestions
  • Freshness vs popularity: Blend time-decay with frequency — trending topics surface faster
"I'd build a trie where each node stores the top-K completions precomputed. Hot prefixes are cached in Redis. Frequency updates happen async via a batch pipeline, not on the read path."
Design YouTube / Video Streaming HARD ▶
Key Components
  • Upload service: Chunked upload (resume on failure), virus scan, format validation
  • Transcoding pipeline: Convert to multiple resolutions (360p, 720p, 1080p, 4K) + formats (H.264, VP9, AV1)
  • CDN: Edge delivery of video segments for low-latency playback globally
  • Metadata DB: Title, description, tags, thumbnails, view counts, user interactions
  • View counter: Eventual consistency — aggregate in batches, not real-time per view
Key Decisions
  • ABR (Adaptive Bitrate): Client dynamically switches quality based on bandwidth — uses manifest file (HLS/DASH)
  • DAG-based pipeline: Transcoding as a directed acyclic graph — split, encode, merge, thumbnail, watermark in parallel
  • Eventual consistency: View counts, likes — write to message queue, aggregate async
Tricky Parts
  • Copyright detection: Content fingerprinting (audio + video hash) checked during upload
  • Live streaming vs VOD: Live requires real-time encoding + low-latency CDN (WebRTC or LL-HLS)
  • Cold start: New videos not yet on CDN — use origin shield to reduce thundering herd on origin
"Upload triggers an async transcoding pipeline that produces multiple resolutions. Videos are served via CDN with ABR streaming — the client dynamically switches quality based on bandwidth."
Design Google Drive / Dropbox HARD ▶
Key Components
  • Block server: Chunked storage — files split into 4 MB blocks, stored in object storage (S3)
  • Metadata DB: File tree structure, versions, permissions, sharing links
  • Sync service: Detect local changes, resolve conflicts, orchestrate upload/download
  • Notification service: Alert other clients when files change (long polling / WebSocket)
Key Decisions
  • Block-level dedup: Only upload changed blocks on edit — content-addressable hashing (SHA-256)
  • Conflict resolution: Last-write-wins for simple cases, branching (create conflict copy) for simultaneous edits
  • Long polling: Client holds connection open — server responds when file changes occur (lower overhead than WebSocket for infrequent updates)
Tricky Parts
  • Large files: Chunking + parallel upload + resumable uploads for reliability
  • Offline edits: Queue changes locally, sync when connection restores, merge conflicts
  • Concurrent edits: Operational Transform (Google Docs approach) or CRDT for real-time collaboration
"Files are split into blocks and stored with content-addressable hashing for dedup. Only modified blocks are uploaded on edit. A sync service detects conflicts and the notification service alerts other clients via long polling."
DT1Saga & the Dual-Write Problem (Outbox + CDC)DISTRIBUTED TX▶
"An order-service updates its DB and then calls payment-service. The DB commit succeeds, the process crashes before the event is published. How does payment ever find out?"

SAGA: distributed transactions without 2PC

A Saga replaces one ACID transaction that spans services with a sequence of local transactions, one per service, where each step commits locally and then hands off to the next — either by emitting an event (choreography) or by an orchestrator issuing the next command (orchestration). There is no global lock and no two-phase commit (2PC) — 2PC needs a synchronous coordinator holding locks across services, which kills availability and does not scale for microservices. Instead of rollback, a Saga uses compensating transactions: semantic undo actions (refund payment, release inventory) that reverse an already-committed step.

Choreography

No central coordinator. Each service listens for events and reacts by emitting its own. Fully decoupled, event-driven.

Key: great for a few steps; cyclic event dependencies get hard to trace / reason about
Orchestration

A central orchestrator (state machine) issues commands to each service and awaits replies, driving the compensation path on failure.

Key: explicit control flow and easy to observe; the orchestrator is a new component to build and own
Compensation

Backward recovery. Steps that already committed are undone in reverse order via semantic inverses. Compensations must be idempotent and (ideally) commutative-safe.

Key: some actions can't be undone (email sent) — order such steps last or make them pivot
Isolation gap

Sagas give ACD not full ACID — no isolation. Other txns can read intermediate state (dirty reads).

Key: use semantic locks / status flags (PENDING → CONFIRMED) to guard partial state

The Dual-Write Problem

Every Saga step must do two things atomically: commit the business state and publish an event. But the database and the message broker (Kafka, SQS, RabbitMQ) are two separate systems with no shared transaction. Writing to both is a dual write, and there is no ordering of the two that is safe:

  • DB first, then publish: crash after commit but before publish → state changed, no event, downstream never learns. Lost event.
  • Publish first, then DB: crash after publish but before commit → event fired for state that was rolled back. Phantom event.
  • Wrap both in one txn: impossible without a distributed transaction across DB + broker (XA/2PC) — the very thing we're avoiding, and most brokers (Kafka) don't support XA well.
TRAP

Trap — "just publish inside the @Transactional method": the broker call is not part of the DB transaction. A rollback of the DB does not un-send the message, and a broker timeout after a successful commit does not undo the commit. The two stores drift out of sync under partial failure, and this is invisible in the happy-path tests you run locally.

Transactional Outbox

Make the write single-store. In the same local ACID transaction as the business row, insert a row into an outbox table describing the event. Because both writes hit the same database, they commit or roll back together — atomicity restored, no 2PC. A separate message relay then reads the outbox and publishes to the broker, marking (or deleting) rows once delivered.

ConcernHow the outbox handles it
AtomicityBusiness row + outbox row in one local transaction — no dual write
Relay deliveryAt-least-once: relay may crash after publish, before marking sent → re-publishes on restart
DuplicatesGuaranteed possible → consumers must be idempotent (dedupe on event ID / business key)
OrderingInclude a monotonic sequence / aggregate ID; partition by aggregate to preserve per-entity order
CleanupDelete or archive sent rows (or use CDC + tombstones) to keep the table small
Two ways to build the relay
Polling publisher

A background job runs SELECT ... WHERE published = false ORDER BY id, publishes each, marks sent. Simple, works on any DB.

Key: polling interval trades latency vs load; needs SKIP LOCKED / status column to avoid double-processing across instances
CDC (log tailing)

Tail the DB's replication log (MySQL binlog, Postgres WAL). Inserts into the outbox appear as change events with no polling and near-zero added query load.

Key: lower latency, no read pressure on the primary; needs log-level access + a connector to operate

CDC via Debezium as the relay

Change Data Capture turns committed row changes into an event stream by reading the database's own transaction log — the source of truth for what actually committed — rather than querying tables. Debezium is the de-facto open-source CDC platform (Apache License 2.0, sponsored by Red Hat). It typically runs as a set of source connectors on Kafka Connect; for non-Kafka sinks you have two distinct options — Debezium Server, a standalone runtime that routes to Kinesis / Pub-Sub / Pulsar / etc., and the Debezium Engine (Embedded), an embeddable Java library (Debezium Server uses this engine internally).

  • MySQL / MariaDB: reads the binlog (requires binlog_format=ROW).
  • PostgreSQL: reads the WAL via logical decoding. Debezium's default plugin.name is decoderbufs (needs the protobuf-c output plugin installed server-side); pgoutput (built into Postgres since PG 10, no extra install) is the commonly-chosen alternative you switch to — not the shipped default.
  • MongoDB: consumes change streams / the oplog. SQL Server, Oracle, Db2, Cassandra connectors also exist.

Debezium also provides an Outbox Event Router SMT (single message transform) that reads outbox-table change events and routes each to a topic derived from the aggregate type — the outbox pattern and CDC combined into a first-class feature. CDC guarantees at-least-once delivery (it can re-emit after a restart from the last committed log offset), which again puts the burden on idempotent consumers: dedupe on the event's unique ID, use upserts, or track processed offsets.

NOTE

Ties together: Outbox solves atomicity (one local txn), CDC solves the relay efficiently (log tailing, no polling), and idempotent consumers absorb the at-least-once duplicates that both introduce. The trio is how a Saga step reliably emits its event without 2PC.

DT2Event Sourcing & CQRSDATA MODELING▶
"Instead of storing that the account balance is $100, store every deposit and withdrawal that ever happened — the balance is a question you answer by replaying them."

Event Sourcing: events as the source of truth

Rather than persisting the current state and overwriting it on each update, Event Sourcing stores an append-only, immutable log of domain events (OrderPlaced, ItemShipped). Current state is derived by replaying the events for an aggregate from the beginning. The event store is the system of record; nothing is ever updated or deleted in place.

  • Full audit / temporal queries: you have the entire history for free — "what was this state on this date?" is just a replay up to a point in time.
  • Rebuild & retro-fix: new read models or bug-fixed projections can be built by replaying from the log; you can reconstruct state you never thought to store.
  • Snapshots: replaying millions of events is slow, so periodically persist a snapshot of aggregate state and replay only events after it.
  • Immutability constraint: events are facts that happened — never mutate them. Correct mistakes with new compensating events, and version event schemas (upcasting) as they evolve.

CQRS: split the write model from the read model

Command Query Responsibility Segregation uses separate models for writing (commands that change state) and reading (queries). The write side is optimized for validation and consistency; the read side is optimized for query shape. They are frequently different data stores kept in sync asynchronously.

AspectWrite model (command)Read model (query)
PurposeValidate + apply state changesServe queries fast
ShapeNormalized aggregates / event logDenormalized, query-tailored views
StoreEvent store / RDBMSElasticsearch, Redis, materialized SQL views
ConsistencyStrongly consistent per aggregateEventually consistent (updated via projections)
ScalingScale for write throughput / contentionScale reads independently (replicas, caches)

Projections are the glue: a processor subscribes to the event stream and updates one or more denormalized read models (also called materialized views or view models). Each projection is independent, can be rebuilt by replay, and can be tuned to exactly one query pattern. CQRS is independent of Event Sourcing — you can do CQRS over a plain RDBMS — but the two compose naturally: events feed the projections.

TRAP

Trap — read-model lag: because projections update asynchronously, a client that issues a command and immediately queries may not see its own write (read-after-write violation). Symptom: user submits a form, the list still shows the old value for a few hundred ms. Mitigations: return the new state directly from the command response, subscribe/poll for the projection to catch up, pin that session to read from the write model, or surface a "pending" UI state. Do not assume the read side is immediately consistent.

When to use — and when it's overkill

Use it when

Audit/compliance demands full history; complex domains with rich behavior (DDD); read and write loads differ by orders of magnitude; you need temporal queries or to derive new views retroactively.

Key: the log-of-facts is a genuine asset, not just overhead
Avoid it when

Simple CRUD with balanced read/write, small team, no audit need. The extra stores, projections, eventual-consistency handling, and event-versioning cost outweigh the benefit.

Key: a normalized RDBMS with an audit column is often enough
Adopt incrementally

You don't need all-or-nothing. Apply CQRS to one hot read path, or event-source one aggregate, rather than the whole system.

Key: scope to the bounded context that actually hurts
Hidden costs

Event schema evolution / upcasting, snapshotting, projection rebuild time, eventual-consistency UX, debugging across the log + views.

Key: operational complexity is the real price, not the code
WATCH

Consistency model: the write side is consistent per aggregate; the read side is eventually consistent. Design the UX and the API contract around that lag rather than fighting it — treating a CQRS read model as strongly consistent is the most common way these systems go wrong.
