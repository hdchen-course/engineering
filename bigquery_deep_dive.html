Google BigQuery Deep Dive

Serverless columnar data warehouse internals: Dremel, storage/compute separation and slots, partitioning & clustering, the bytes-scanned vs slot-reservation cost model, streaming vs batch ingestion, nested data, materialized views, and OLAP-vs-OLTP boundaries — with a worked cost example and interview Q&A.

What BigQuery Is

BigQuery is Google Cloud's serverless, columnar, massively-parallel analytics data warehouse. There are no instances to size, no nodes to patch, and no indexes to build: you create datasets and tables, load data, and run SQL. The service transparently allocates compute for the duration of each query and releases it afterward. Its defining architectural choice is the full separation of storage and compute, connected by Google's petabit-scale network.

Lineage: BigQuery is the externalized product form of Dremel, the interactive query system Google described in its 2010 Dremel paper. Under the hood it stitches together four internal Google systems: Dremel (execution engine), Colossus (distributed storage), Jupiter (data-center network), and Borg (cluster orchestration).

Separation of Storage & Compute

Fig 1: Compute (Dremel slots) and storage (Colossus) scale independently, joined by the Jupiter network
Why this design wins: because compute is stateless and storage is remote, Google can assign thousands of slots to a single query and then reclaim them instantly. You never pay for idle nodes, storage grows without touching compute, and many tenants share the same physical fleet. The trade-off is that every query pays a network + scheduling tax (typically hundreds of ms to seconds of latency), which is why BigQuery is an OLAP engine, not an OLTP database.

Columnar Storage: Capacitor

Why columnar matters for analytics▶
  • BigQuery stores tables in Capacitor, a columnar format (successor to the original ColumnIO). Each column is encoded and compressed independently on Colossus.
  • Analytical queries touch few columns but many rows (e.g. SUM(revenue) GROUP BY country over a 200-column table). Columnar layout means the engine reads only revenue and country — not the other 198 columns.
  • Values within a column are similar, so run-length and dictionary encodings compress far better than row storage. Fewer bytes on disk = fewer bytes scanned = lower cost and higher speed.
  • Capacitor also stores per-column, per-block statistics (min/max, etc.) so the engine can skip blocks that cannot match a filter.
  • There are no user-managed indexes. You influence physical layout only through partitioning and clustering (next tab). A "search index" feature exists for point lookups on text, but the day-to-day performance levers are partition + cluster.
Direct consequence for cost: because storage is columnar and billing (on-demand) is by bytes scanned, SELECT * is the single most expensive habit in BigQuery — it forces the engine to read every column. Always project only the columns you need.

Slots: the Unit of Compute

What is a slot?▶
  • A slot is BigQuery's abstract unit of compute capacity — a bundle of CPU, memory, and networking used to execute one unit of a query's work. You do not map slots to machines; the scheduler does.
  • A query is compiled into a DAG of stages; each stage is split into parallel tasks; tasks are executed by available slots. More slots → more parallelism → faster (up to the query's inherent parallelism).
  • Slots are fair-shared and elastic: a query that needs more capacity borrows idle slots and gives them back when stages complete. This dynamic scheduling is why the same query can run in 3 s or 30 s depending on concurrent load.
  • On the default on-demand model you don't manage slots at all (there's a shared pool, historically up to ~2,000 slots per project); you pay by bytes scanned. With capacity / editions you provision or autoscale a slot pool and pay for slot-time instead (see Cost tab).
Data shuffle: between stages, intermediate results are repartitioned through an in-memory shuffle tier backed by Colossus for spill. This is how BigQuery does distributed JOIN, GROUP BY, and ORDER BY without the query author choosing a distribution key — a contrast with older MPP warehouses that require you to pick a DISTKEY.

Partitioning

A partitioned table is physically divided into segments so the engine can prune (skip) whole partitions that a query's filter can't match. Pruned partitions are never read, so they cost nothing on the on-demand model and add no scan time.

Partition typeColumn / mechanismGranularityTypical use
Time-unit columnA DATE columnDay, Month, or Year (no Hour — a DATE has no time component)Event/log tables partitioned by event date
Time-unit columnA TIMESTAMP or DATETIME columnHour, Day, Month, or YearEvent/log tables needing hourly resolution
Ingestion timePseudo-columns _PARTITIONTIME / _PARTITIONDATEHour, Day, Month, or YearStreaming appends where load time ≈ event time
Integer rangeAn INT64 column with start/end/intervalFixed numeric bucketsPartition by customer_id ranges, etc.
Key limits & pitfalls (defensible facts):
  • A table can have at most 10,000 partitions. Daily partitioning therefore covers ~27 years — fine; hourly partitioning exhausts the limit in ~416 days, so pick granularity deliberately.
  • Pruning only happens when the filter compares the partition column to a constant / literal (or a small set). Wrapping the partition column in a function, or joining it against another table, can defeat pruning.
  • Set require_partition_filter = TRUE to force every query to include a partition filter — a cheap guardrail against accidental full-table scans.
  • You can only partition on one column. Need a second dimension? Combine partitioning with clustering.
-- Daily-partitioned, clustered events table
CREATE TABLE analytics.events (
  event_ts   TIMESTAMP,
  user_id    INT64,
  country     STRING,
  event_type STRING,
  payload    JSON
)
PARTITION BY DATE(event_ts)
CLUSTER BY country, event_type
OPTIONS (
  require_partition_filter = TRUE,       -- block un-pruned scans
  partition_expiration_days = 400        -- auto-delete old partitions
);

Clustering

Sorting within storage blocks for extra pruning▶
  • Clustering physically sorts data by up to 4 columns (within each partition, if the table is also partitioned). Rows with similar clustering values land in the same storage blocks.
  • Because Capacitor keeps per-block min/max metadata, a filter on a clustering column lets the engine skip blocks that can't match — block-level pruning on top of partition-level pruning.
  • Column order matters: clustering is a sort prefix, exactly like a composite key. A filter on the first clustering column prunes best; filtering only the second column prunes weakly.
  • Automatic reclustering keeps data sorted as you append, and Google does not charge for the reclustering compute.
  • Clustering shines on high-cardinality columns (user_id, country, sku) where partitioning would exceed the 10,000-partition limit.
Partition vs cluster, in short: partitioning gives you coarse, guaranteed, metadata-priced pruning and cheap lifecycle management (drop/expire a whole partition). Clustering gives you fine-grained, best-effort pruning within partitions and supports up to 4 dimensions. Use both: partition by date, cluster by your common filter columns.

Worked Example: Partitioning & Bytes Scanned

📊 A 10 TiB events table, 365 daily partitions

Assume analytics.events holds 10 TiB spread evenly across one year of daily partitions — about 28 GiB per partition — and on-demand pricing of $6.25 per TiB scanned (US multi-region, 2026).

QueryBytes scannedOn-demand cost
SELECT * FROM events (no filter) ~10 TiB (all columns, all partitions) $62.50
WHERE DATE(event_ts) = '2026-08-01' ~28 GiB (one partition, all columns) ≈ $0.17
Same day, but SELECT country, event_type only ~1–2 GiB (2 columns of 1 partition) ≈ $0.01
+ WHERE country = 'US' (clustered col) Fraction of that — block pruning skips non-US blocks < $0.01

The single-day + two-column + clustered query scans roughly 3–4 orders of magnitude less than the naive SELECT *. Partitioning removed 364/365 of the rows; columnar projection removed most of the columns; clustering skipped most of the remaining blocks.

Why DATE(event_ts) still prunes here: the table is PARTITION BY DATE(event_ts), so filtering on that exact partitioning expression prunes normally. The earlier warning is about wrapping the column in an additional/different function (e.g. EXTRACT(...), CAST) or filtering a non-partition column — that is what defeats pruning.

Costing traps to state in an interview:
  • LIMIT does not reduce bytes scanned — the engine still scans the referenced columns/partitions before limiting. It bounds output rows, not cost.
  • On-demand billing is bytes processed, rounded up, with a 10 MB minimum per table referenced and per-query minimums; tiny queries aren't free.
  • Querying _PARTITIONTIME or table metadata (row count via __TABLES__, table preview, cached results, dry runs) can be free — but a real scan is not.
  • Clustering pruning is estimated, not guaranteed: a dry run shows the upper-bound bytes; the actual bytes billed after a clustered scan can be lower.

Two Compute Pricing Models

BigQuery splits billing into storage (always billed by bytes stored) and compute (billed one of two ways). Choosing the compute model correctly is the core cost-engineering decision.

On-demand (per bytes scanned)
  • Pay $6.25 per TiB of data processed by queries (US, 2026). First 1 TiB/month free.
  • Zero capacity management; uses a shared slot pool (historically ~2,000 slots/project).
  • Cost is a pure function of bytes scanned → partitioning/clustering/column projection directly cut the bill.
  • Best for: spiky, unpredictable, or low-volume workloads; getting started.
  • Risk: one careless SELECT * over a huge table is an instant large bill.
Capacity / Editions (per slot-time)
  • Provision or autoscale a pool of slots; pay per slot-hour regardless of bytes scanned.
  • Editions: Standard (~$0.04), Enterprise (~$0.06), Enterprise Plus (~$0.10) per slot-hour, US pay-as-you-go.
  • Commitments (1-year / 3-year) discount the slot rate for predictable baseline load.
  • Best for: steady, high-volume workloads where bytes-scanned would exceed a fixed slot budget; predictable monthly cost.
  • Bytes scanned are no longer billed — but a runaway query just makes everything else slower (queues for slots).
The break-even mental model: compute the effective cost of your monthly bytes-scanned under on-demand, and compare to the cost of a reservation that would satisfy the same workload's slot demand. High, steady scan volume → reservations win. Bursty or small → on-demand wins. Many teams use both: a baseline reservation for scheduled pipelines + on-demand (or autoscaling) for ad-hoc analysts.

Logical vs physical storage billing: logical bills uncompressed bytes; physical bills the compressed bytes on disk (usually much smaller) but at ~2× the rate. If your data compresses well (typical for columnar), physical billing is often cheaper. Long-term discount applies automatically per partition that hasn't been edited in 90 days — and does not slow reads. First 10 GiB storage/month is free.

Cost-Control Tactics

💰 Practical guardrails
  1. Project only needed columns — never SELECT * on wide tables (columnar billing).
  2. Partition + cluster every large table on its common filter columns; set require_partition_filter.
  3. Cap per-query bytes with maximum_bytes_billed (job-level or default). The query fails instead of scanning more than the cap.
  4. Dry-run before running (--dry_run / dryRun) to see the byte estimate; wire it into CI for expensive scheduled queries.
  5. Custom quotas — set per-project / per-user daily query byte limits to contain blast radius.
  6. Materialized views & BI Engine for repeated aggregations (see the MV, BI Engine & ELT tab) so you don't rescan raw data every dashboard refresh.
  7. Exploit free operations — cached results, table preview, and metadata queries don't scan.
  8. Reservations for predictable pipelines to convert a variable bytes bill into a fixed slot bill.
-- Fail the job rather than scan more than 50 GiB
SELECT country, COUNT(*) AS n
FROM analytics.events
WHERE DATE(event_ts) BETWEEN '2026-08-01' AND '2026-08-07'
GROUP BY country;
-- run with:  bq query --maximum_bytes_billed=53687091200 --use_legacy_sql=false '...'

-- Estimate cost without running (bytes only, $0 charged):
-- bq query --dry_run --use_legacy_sql=false 'SELECT ...'

Default to batch. Batch loading is free and atomic — for scheduled ELT there's no reason to stream. Reach for the Storage Write API only when you genuinely need seconds-fresh data. The modern Storage Write API supersedes the old insertAll streaming endpoint, offering higher throughput, exactly-once delivery, and lower cost, with both pending (commit-later, batch-like) and committed (immediately visible) stream modes.
Free query-to-query loads: CREATE TABLE AS SELECT (CTAS), INSERT ... SELECT, and LOAD DATA from GCS are the backbone of ELT and don't incur separate ingestion charges — you pay only for the query compute (bytes scanned or slots). This is why the idiomatic BigQuery pattern is land raw → transform with SQL.

Nested & Repeated Fields

STRUCT (RECORD) and ARRAY (REPEATED)▶
  • BigQuery natively supports nested data via STRUCT (a record with sub-fields) and repeated data via ARRAY (a column holding many values per row). Combine them: an ARRAY<STRUCT> models a one-to-many relationship inside a single row.
  • This is Dremel's original contribution: it stores nested structures columnar using repetition and definition levels, so nested fields still get columnar compression and per-column scanning.
  • Denormalizing child records into a repeated field often beats a JOIN: the related data is co-located, and you avoid a shuffle. Classic pattern — an order row with a repeated line_items array rather than a separate items table.
  • Flatten a repeated field with UNNEST, which cross-joins each array element back to its parent row.
-- Schema: orders with a repeated array of line-item STRUCTs
CREATE TABLE shop.orders (
  order_id   INT64,
  customer   STRUCT<id INT64, country STRING>,
  line_items ARRAY<STRUCT<sku STRING, qty INT64, price NUMERIC>>
);

-- Query: revenue per SKU — UNNEST flattens the array
SELECT
  li.sku,
  SUM(li.qty * li.price) AS revenue
FROM shop.orders AS o,
  UNNEST(o.line_items) AS li          -- one row per line item
WHERE o.customer.country = 'US'        -- dotted access into the STRUCT
GROUP BY li.sku
ORDER BY revenue DESC;
Why denormalize here but normalize in OLTP? An OLTP store normalizes to make row-level updates cheap and consistent. BigQuery is append/scan-oriented: co-locating children as repeated fields removes JOIN shuffles and matches the columnar scan model. It's the OLAP inversion of the classic normalization advice.

Materialized Views

Precomputed, incrementally-refreshed aggregates with automatic rewrite▶
  • A materialized view (MV) stores the precomputed result of a query and keeps it up to date. Unlike a plain view (which is just saved SQL re-run every time), an MV persists data and is refreshed incrementally as the base table changes.
  • Automatic query rewrite ("smart tuning"): the optimizer can transparently rewrite a query against the base table to read from a matching MV instead — even if the query never names the MV — cutting bytes scanned and latency.
  • MVs are ideal for repeated aggregations: dashboards, daily rollups, GROUP BY over huge fact tables. You pay compute to maintain the MV incrementally, not a full rescan per query.
  • Refresh can be automatic (background, within minutes) or manual; queries against a stale MV can still read fresh base rows and combine them, so results stay correct.
  • Constraints: MVs support a subset of SQL (aggregations, a single base table or limited joins depending on features enabled). Complex logic may need a scheduled table rollup instead.
CREATE MATERIALIZED VIEW analytics.daily_country_counts AS
SELECT
  DATE(event_ts) AS day,
  country,
  COUNT(*)      AS events,
  APPROX_COUNT_DISTINCT(user_id) AS users   -- exact COUNT(DISTINCT) is not MV-supported
FROM analytics.events
GROUP BY day, country;
-- A later ad-hoc GROUP BY day,country against events
-- can be auto-rewritten to read this MV.

BI Engine

In-memory acceleration for interactive dashboards▶
  • BI Engine is an in-memory analysis layer inside BigQuery. You reserve capacity in GiB; hot columnar data is cached in RAM and queries served from it return in sub-second time.
  • It accelerates the same SQL transparently — no query changes. It's aimed at BI tools with many concurrent, repetitive queries (Looker / Looker Studio, and other connectors).
  • Best paired with partitioning/clustering (so the working set fits in the reservation) and materialized views (so aggregates are cheap to cache).
Layering the accelerators: raw fact table → partition + cluster to prune → materialized view to precompute rollups → BI Engine to serve them from memory. Each layer removes work the next one would otherwise repeat.

ETL vs ELT

ETL — transform, then load
  • Data is cleaned/reshaped in an external engine before landing in the warehouse.
  • Google tooling: Dataflow (Apache Beam) for streaming/batch, Dataproc (Spark) for heavy custom transforms.
  • Fits: complex non-SQL logic, PII scrubbing before storage, joining many external sources.
ELT — load raw, transform in-warehouse
  • Land raw data first, then transform with SQL inside BigQuery (its native strength).
  • Tooling: Dataform (SQL-based transformation/orchestration built into BigQuery) or dbt; scheduled queries; CTAS/INSERT.
  • Fits: most analytics pipelines — cheaper (batch loads are free), versionable, and leverages BigQuery's parallel SQL.
Why ELT is the default on BigQuery: a serverless engine that scans TiB in seconds makes "load everything raw, transform later with SQL" cheap and flexible. You keep raw data for reprocessing, express transforms as version-controlled SQL, and let the warehouse parallelize. Reserve ETL (Dataflow/Dataproc) for logic SQL can't express or for transforms that must happen before data is stored.

Common Interview Questions

Q: How does BigQuery run a query so fast without indexes?▶

Three things: (1) columnar storage (Capacitor) means it reads only the referenced columns, heavily compressed; (2) massive parallelism — the Dremel engine fans the scan across thousands of slots in a multi-level serving tree, with an in-memory shuffle between stages; (3) pruning via partitioning (skip partitions) and clustering (skip blocks) plus per-block min/max metadata. There are no B-tree indexes; you shape performance with partition + cluster + column projection.

Q: A query cost $60. How do you bring it down?▶
  1. Stop scanning columns you don't need — replace SELECT * with an explicit column list.
  2. Add a partition filter so the engine prunes to the relevant date range; enforce with require_partition_filter.
  3. Cluster the table on the columns in the WHERE clause for block pruning.
  4. If it's a repeated aggregation, build a materialized view so it isn't recomputed from raw each time.
  5. Set maximum_bytes_billed and a default so a future mistake fails fast instead of billing.
  6. If this workload is steady and heavy, move it to a slot reservation so cost is fixed regardless of bytes.
Q: On-demand vs slot reservations — how do you choose?▶

Model both. On-demand ($6.25/TiB scanned) is best for spiky, unpredictable, or low-volume usage — you pay nothing when idle, but a bad scan is a real bill. Reservations (per slot-hour, with 1/3-year commitment discounts) suit steady, high-volume workloads: predictable monthly cost and no per-byte surprises, at the price of managing capacity. In practice, many teams reserve a baseline for scheduled pipelines and let ad-hoc analysts use on-demand or an autoscaling reservation.

Q: When should you NOT use BigQuery?▶
  • OLTP / transactional apps — high-frequency single-row reads/writes with ms latency → Cloud SQL, Spanner, or Bigtable.
  • Point lookups by key at scale → Bigtable / a key-value store; BigQuery pays a per-query scheduling tax.
  • Frequent per-row mutations — BigQuery does bulk DML well but is not designed for constant tiny UPDATEs.
  • Sub-ms serving for user-facing requests → cache (Memorystore/Redis) or a serving DB.
Q: Partitioning vs clustering — what's the difference?▶

Partitioning splits a table into segments on one column (time-unit, ingestion-time, or integer-range), giving coarse, guaranteed pruning, cheap lifecycle management (expire/drop a partition), and a hard limit of 10,000 partitions. Clustering sorts data by up to 4 columns within each partition for fine-grained, best-effort block pruning, and handles high-cardinality columns that would overflow the partition limit. They're complementary — partition by date, cluster by your frequent filter columns.

Q: Why denormalize with nested/repeated fields?▶

In OLAP the goal is fast scans, not cheap row updates. Storing children (e.g. order line items) as an ARRAY<STRUCT> inside the parent row co-locates related data, so you avoid a distributed JOIN and its shuffle, while Dremel still stores each nested field columnar (repetition/definition levels) for compression and selective scanning. You flatten with UNNEST when you need per-element rows. This is the deliberate inverse of OLTP normalization.

30-Second Summary

✅ Say this and you've covered BigQuery
  • Architecture: serverless, columnar (Capacitor on Colossus), Dremel execution in slots, storage/compute separated over the Jupiter network.
  • Performance levers: partition (coarse pruning, 1 column, ≤10k), cluster (4 cols, block pruning), project only needed columns — no indexes.
  • Cost: on-demand $6.25/TiB scanned (1 TiB/mo free) vs capacity slot-reservations; storage active vs long-term, logical vs physical.
  • Ingestion: batch loads are free/atomic (default); Storage Write API for seconds-fresh streaming; ELT with SQL is idiomatic.
  • Acceleration: materialized views (incremental + auto-rewrite) and BI Engine (in-memory, sub-second).
  • Boundary: OLAP, not OLTP — big scans and aggregation, not single-row transactional serving.
