Why Build a Whole Chip Just to Multiply Matrices?

Start with the one operation a neural network can't stop doing, then watch how a chip built only for that op wins.

The high-schooler version. A neural network is mostly one move repeated billions of times: take a list of numbers, multiply it by a big grid of numbers, add up the results, apply a simple squashing function, repeat. That "multiply-a-list-by-a-grid-and-sum" is a matrix multiply. If 90% of your work is one operation, it is wasteful to run it on a chip designed to do everything a little bit well. Instead, build a chip that does that one thing ridiculously well and skips the rest. That chip is a TPU (Tensor Processing Unit) — an ASIC (application-specific integrated circuit) for matrix math.

The core bet

A CPU spends most of its silicon guessing what to do next — branch predictors, out-of-order engines, deep caches. Deep learning doesn't need guessing; it needs the same dense multiply, over and over, in a totally predictable pattern. A TPU spends that silicon on arithmetic units and memory bandwidth instead. Same transistor budget, radically different allocation.

A tiny worked example: one matrix multiply

Multiply a 2×2 activation matrix A by a 2×2 weight matrix B:

A = [ 1  2 ]      B = [ 5  6 ]      C = A × B = [ 1·5+2·7   1·6+2·8 ] = [ 19  22 ]
    [ 3  4 ]          [ 7  8 ]                  [ 3·5+4·7   3·6+4·8 ]   [ 43  50 ]

Four output numbers, each a sum of two multiply-accumulate (MAC) steps. A real transformer layer does the same thing with matrices that are thousands wide — billions of MACs per layer. The question every accelerator answers is: how do you feed a grid of multipliers so none of them ever sits idle waiting for data? Google's answer is the systolic array.

The systolic array: a heartbeat of arithmetic

"Systolic" comes from systole, the heart's pumping beat. Data marches through a grid of tiny multiply-accumulate cells (PEs, "processing elements") in lockstep, one hop per clock cycle — like a bucket brigade passing water. Each PE does one job: multiply the number flowing through it by a partner number, add it to a running total, and pass both along to its neighbors. No PE ever reads or writes main memory mid-computation; operands are reused in place as they stream by. That reuse is the whole trick — it's why a TPU can keep 16,384 multipliers busy without a memory system 16,384 times as fast.

Read the animation like this

Each cell is "output-stationary": it owns one answer, C[i][j], and grows it by one MAC per cycle. The values arrive skewed (a diagonal wavefront) so that the right A element and the right B element land in the same cell at the same instant. A 128×128 MXU works on this same operand-reuse principle — 16,384 cells, ~16,384 MACs every cycle — and the data skew keeps every cell fed without a single mid-flight memory read. (The production MXU is weight-stationary: it preloads weights and streams only activations; we animate the output-stationary variant because the accumulators are easier to watch grow. Both share the same in-place operand-reuse idea.)

Why this beats "just add more ALUs"

  • Operand reuse in the wires, not in memory. A naive multiplier array reads two operands from memory per MAC. The systolic array reads each input once at the edge and reuses it across an entire row/column. That cuts memory traffic by ~O(N), which matters because bandwidth, not multipliers, is the scarce resource.
  • Deterministic timing. Everything is a fixed pipeline; there are no cache misses or mispredicted branches to stall on, so the compiler can schedule to the cycle.
  • Density. A MAC cell is tiny. Filling the die with them (instead of control logic) buys enormous peak throughput per mm² and per watt.
INTERVIEW ANGLE

If asked "why does a TPU exist when GPUs already do matrix math?", don't lead with FLOPS. Lead with the systolic array's operand reuse: "It amortizes each memory read across a whole row and column of the array, so it hits high utilization at far lower memory bandwidth than a general SIMD (Single-Instruction, Multiple-Data) engine. The specialization is the point — it trades flexibility for MAC density and predictable scheduling." Then mention that peak FLOPS is meaningless without saying what utilization you actually sustain.

TPU vs GPU: Two Ways to Spend a Transistor Budget

Both accelerate matrix math. They disagree about how much generality is worth paying for.

The analogy. A GPU is a fleet of thousands of small, flexible workers (cores) who can each be told to do slightly different things — great for graphics, physics, and yes, ML. A TPU is a giant purpose-built assembly line (the MXU) that only makes one product but makes it faster per dollar and per watt. GPUs keep some general-purpose machinery (caches, schedulers, warps) so they can pivot to new workloads; TPUs throw most of that out.

The chip anatomy that matters

What a TPU keeps

  • MXU — a large systolic matrix unit (e.g. 128×128 MACs) that is the beating heart.
  • HBM — high-bandwidth memory stacked next to the chip (tens of GB, ~TB/s) holding weights & activations.
  • On-chip scratchpad (VMEM/CMEM) — explicit, compiler-managed SRAM (Static RAM — fast memory built into the chip itself). No hardware cache guessing.
  • Vector unit + scalar unit — for the non-matmul bits (activations, norms, softmax).
  • ICI links — dedicated chip-to-chip ports for building pods (covered in the Pods tab).

What a TPU throws away

  • Branch predictors / speculation — the loop is known ahead of time; nothing to predict.
  • Out-of-order execution — the compiler (XLA) orders everything statically.
  • Deep multi-level caches — replaced by a scratchpad the compiler fills explicitly.
  • Wide instruction decode / lots of control logic — a few big instructions do enormous work.
Cache vs scratchpad — the deepest difference

A CPU/GPU cache is reactive: hardware guesses what you'll reuse and hides misses behind it. A TPU has a software-managed scratchpad: XLA knows the exact access pattern of a matmul, so it schedules the loads — DMA (Direct Memory Access — the chip copying a block of data itself, no CPU in the loop) this tile of weights in, compute on it, prefetch the next tile — with no guessing and no miss penalty. Predictable workload → you can replace speculation with a compiler.

DON'T OVERSTATE IT

"TPU beats GPU" is a bad interview answer. The honest framing: TPUs win on perf-per-dollar and perf-per-watt for large, regular matmul-heavy training/inference at scale, and integrate tightly with Google's stack. GPUs win on flexibility, kernel ecosystem (CUDA), and irregular or research workloads. The right chip depends on the workload's regularity, the software you already have, and how much of the datacenter you can co-design.

INTERVIEW ANGLE

Probes here usually target the cache question: "Why no big caches on a TPU?" Crisp answer: "Because the access pattern of a matmul is statically known, a compiler can schedule DMAs into an explicit scratchpad better than a reactive cache can guess. Caches spend area and energy hiding unpredictability the TPU doesn't have." The Memory & Precision Story: bf16, int8, and the Roofline

Peak multipliers are useless if you can't feed them. Precision and bandwidth decide whether the MXU is fed or starved.

The analogy. Imagine a chef (the MXU) who can chop 1000 onions a minute, but the onions arrive on a single conveyor belt (memory bandwidth). If the belt only delivers 200 onions a minute, the chef idles 80% of the time. Two fixes: (1) a faster belt (HBM with huge bandwidth), and (2) smaller onions — use fewer bits per number so more values fit per byte moved. That second fix is reduced precision.

Number formats: why bf16 and int8 exist

Why bf16, not fp16, on TPUs

The killer feature of bfloat16 is that it keeps the same 8-bit exponent as FP32. Gradients in deep nets span a huge dynamic range; bf16 can represent tiny and huge magnitudes just like FP32 (it just rounds the fine detail), so training is stable without the extra "loss scaling" work FP16 needs. You halve memory and bandwidth and roughly double matmul throughput, almost for free on accuracy. That's why it's the TPU default.

The trick: matmul in bf16, accumulate in fp32

Multiplying two bf16 numbers loses detail, but summing thousands of products in bf16 would lose far more (rounding error piles up). TPUs multiply in bf16 but accumulate the running sum in fp32 inside the MXU. You get the memory/throughput win of 16-bit inputs and the numerical stability of a 32-bit accumulator. Remember this — it is a classic interview detail.

Worked example: is your layer compute-bound or memory-bound?

This is the roofline question, and it decides whether more FLOPS even help. Define arithmetic intensity = FLOPs performed ÷ bytes moved from HBM.

# A matmul: (M x K) x (K x N).  Take M=N=K=8192, weights in bf16 (2 bytes).
FLOPs   = 2 × M × N × K        = 2 × 8192³   ≈ 1.1e12 FLOP   # ×2 = one multiply + one add per MAC
bytes   = 2 × (M·K + K·N + M·N)   ≈ 2 × 3 × 8192² ≈ 4.0e8 bytes
intensity = 1.1e12 / 4.0e8         ≈ 2750 FLOP/byte   # very high → compute-bound (good!)
# Now a memory-bound op: read a big activation, do 1 add per element.
# intensity ≈ a fraction of a FLOP/byte (well below 1) → you are limited by HBM bandwidth, not the MXU.
# Rule: compare intensity to the chip's (peak FLOPS / peak bandwidth) ratio.
# Below that ratio = memory-bound (feed the chef faster); above = compute-bound.
Why this matters operationally

Large dense matmuls are comfortably compute-bound — the whole reason the MXU pays off. But attention, layer-norm, and element-wise ops are often memory-bound. That's why XLA works so hard to fuse those ops (do several in one pass while data is on-chip) — fusion raises arithmetic intensity and stops the MXU from starving. Precision (bf16/int8) also raises effective intensity by shrinking the bytes moved.

The memory that isn't HBM

  • HBM (tens of GB/chip): holds the model's weights, activations, and optimizer state for the shard on this chip. If the model doesn't fit, you must split it across chips (next tabs).
  • On-chip SRAM scratchpad (MB-scale): the working set the MXU actually touches; filled by DMA under compiler control. Orders of magnitude faster than HBM but tiny.
  • The budget equation: weights + activations + optimizer_state must fit in aggregate HBM across your chips. Adam roughly triples weight memory (params + 2 moments). This single inequality is why big models need many chips at all.
INTERVIEW ANGLE

Expect "your matmul isn't hitting peak FLOPS — why?" The senior answer walks the roofline: compute arithmetic intensity, compare to the chip's FLOPS/bandwidth ratio, and conclude memory-bound vs compute-bound. Then name fixes by category: bigger tiles / higher batch (raise intensity), operator fusion (fewer HBM round-trips), and lower precision (fewer bytes). Naming bf16-multiply / fp32-accumulate unprompted signals real depth.

Scaling Out: Pods, the 3D Torus, and Optical Switches

One chip is a tool. Thousands of chips wired the right way are a single supercomputer. The wiring is the design.

The analogy. Give 4096 people a math problem too big for one person. How you seat them and who can hand notes to whom decides everything. Seat them in isolated cubicles and they waste all day walking notes around. Seat them in a grid where every person can pass notes to four neighbors, and wrap the edges so it's a donut with no far corners — now a note reaches anyone in a few hops. That seating chart is the torus interconnect, and the note-passing is the ICI (Inter-Chip Interconnect).

Why a torus, and why 3D

A TPU chip has a handful of dedicated ICI ports (v4: 6 links per chip). Wire each chip to its neighbors in a 3D grid and wrap every edge around (so dimension x is a ring, and so are y and z) and you get a 3D torus. Properties that make it ideal for training:

  • No far corners. Wraparound halves the worst-case distance; any chip reaches any other in at most (dimension/2) hops per axis.
  • Every link is used by collectives. The dominant communication in training — AllReduce of gradients — maps beautifully onto rings, and a torus is rings in three directions. Bandwidth-optimal ring algorithms saturate all links at once.
  • Bisection bandwidth grows with the cross-section. (Bisection bandwidth = the total link capacity you'd cut if you sliced the machine in half — a measure of how fast the two halves can talk.) More chips per axis = more parallel links across any cut = more aggregate throughput for all-to-all traffic.

Optical Circuit Switches (OCS): the reconfigurable part

Inside a cube, chips are wired with fixed copper ICI — always connected, cheap, fast. But between cubes, TPU v4 routes links through Optical Circuit Switches. An OCS is not a packet switch; it physically steers beams of light — think of a robot that unplugs and re-plugs fiber in about 10 milliseconds. Once set, it adds essentially zero latency (it's just a mirror), but you must decide the topology before the job runs.

THE CATCH

OCS reconfiguration takes milliseconds, so you cannot reshape the network inside a single training step. It's a scheduling-time decision, not a per-iteration one. And a torus's low-diameter, all-links-busy behavior only holds if the compiler maps collectives onto it well — a badly placed job can still create hot spots.

INTERVIEW ANGLE

"How do you handle a failed chip in a 4096-chip pod?" Strong answer: detect via ECC (Error-Correcting Code memory, which flags bit errors)/timeout/health-check, then the OCS reconfigures healthy cubes around the fault so the job reshapes onto good hardware, and training resumes from the last checkpoint. Contrast with a fixed-wired mesh where one dead node can strand a whole region. The meta-point interviewers want: at this scale, failure is routine, so the interconnect must be designed for graceful reconfiguration, not treated as an exception.

Splitting a Big Model Across Chips

When the model won't fit (or won't train fast enough) on one chip, you cut it up. There are three cuts, and real systems use all three.

The analogy. A giant restaurant order. Data parallelism: clone the kitchen — many identical kitchens each cook different tables, then compare notes so recipes stay in sync. Model (tensor) parallelism: one dish is so big that several chefs each cook part of the same dish and combine it. Pipeline parallelism: an assembly line — station 1 does appetizers, station 2 mains, and plates flow down the line. Each cut trades a different resource.

The three cuts

Data parallel

  • Full model copy per chip; each sees a different batch shard.
  • Sync via AllReduce of gradients every step.
  • Cost: communicate ~model-size of gradients per step.
  • Limit: model must fit on one chip.

Model / tensor parallel

  • Split each big weight matrix across chips.
  • Chips exchange partial results within a layer (AllGather / ReduceScatter).
  • Cost: heavy comms every layer → keep it inside a fast-linked group.
  • Wins: fits layers too big for one chip.

Pipeline parallel

  • Assign consecutive layers to different chip groups (stages).
  • Micro-batch so stages stay busy; mind the "bubble" at fill/drain.
  • Cost: only activations cross stage boundaries (cheap).
  • Wins: spreads depth & memory across many chips.

How they combine: a concrete layout

Real large-model runs stack the cuts to match the hardware. A representative flagship-scale layout on a v4 pod:

# Example split of a very large model across ~3,000 chips
tensor_parallel  = 12    # split each layer across 12 fast-linked chips (inside a cube)
data_parallel    = 256   # 256 replicas of the whole model, fed different batches
pipeline_stages  = 1     # kept simple here; pipelining adds a scheduling "bubble"
chips            = tensor_parallel × data_parallel   # = 3072 chips (12 × 256)

# Placement rule of thumb, ranked by comms cost:
#   tensor-parallel group  → put on the SAME cube (highest bandwidth, every layer talks)
#   pipeline stages        → adjacent cubes (only activations cross, less traffic)
#   data-parallel replicas → spread across the pod (AllReduce once per step)
The mapping principle

Match communication frequency to link bandwidth. Tensor parallelism talks every layer, so it belongs on the tightest links (within a cube). Data parallelism talks once per step, so it tolerates the pod-wide torus. Pipeline parallelism only ships activations between stages, so it fits neighboring cubes. Getting this placement right is a huge chunk of real-world training performance — and it's what OCS topology reconfiguration exists to enable.

The main collective: ring AllReduce

Data-parallel training lives or dies on AllReduce: every chip ends up with the element-wise sum of everyone's gradients. The bandwidth-optimal way on a ring is two phases — reduce-scatter (each chip becomes the owner of one fully-summed chunk) then all-gather (everyone circulates their finished chunk). The cost approaches 2·(N-1)/N × (data / link_bandwidth) — note it barely grows with N, which is exactly why a torus scales.

# Ring AllReduce on N chips, gradient of size D bytes/chip
reduce_scatter: N-1 steps, each chip sends D/N bytes per step
all_gather:     N-1 steps, each chip sends D/N bytes per step
total sent/chip ≈ 2 × (N-1)/N × D      # → ~2D as N grows: near-constant per chip!
PIPELINE BUBBLE

Pipeline parallelism's tax is the bubble: while the pipeline fills and drains, some stages sit idle. With S stages and m micro-batches, idle fraction ≈ (S-1)/(m + S-1). Fix: use many micro-batches (large m) so the bubble amortizes. Be ready to state this formula.

INTERVIEW ANGLE

"You have a model 10× too big for one chip's HBM — how do you train it?" Structure the answer: (1) tensor-parallel to fit each layer, placed within a cube; (2) data-parallel replicas across the pod, synced by ring AllReduce; (3) pipeline only if depth/memory still doesn't fit, sizing micro-batches to shrink the bubble. Close with the placement principle — comms frequency vs link bandwidth — and note that AllReduce cost per chip is roughly constant in N, which is why it scales.

The Software Stack: JAX → XLA → TPU, orchestrated by Pathways

You write array math in Python; a compiler turns it into TPU machine code; a runtime spreads it over the pod. Here's the whole pipe — and exactly where the engineer's control ends and the chip's begins.

The analogy. You write a recipe in plain language (JAX). A translator (XLA) rewrites it into precise machine steps for one specific kitchen — deciding which prep to batch together, what to keep on the counter vs the fridge, and when to fetch the next ingredient. A head chef (Pathways) coordinates hundreds of kitchens so the whole banquet comes out together.

Layer by layer

# 1) You write array math (looks like NumPy). JAX traces it into a graph (HLO).
import jax, jax.numpy as jnp
from jax.sharding import Mesh, NamedSharding, PartitionSpec as P
from jax.experimental import mesh_utils

def layer(x, w):
    return jax.nn.relu(x @ w)        # @ = matmul → lands on the MXU

# 2) You DECLARE how tensors are split across chips (sharding). You don't write comms.
mesh = Mesh(mesh_utils.create_device_mesh((4, 2)), axis_names=("data", "model"))
w = jax.device_put(w, NamedSharding(mesh, P(None, "model")))   # shard weight's columns across the "model" axis
f = jax.jit(layer)                       # 3) jit → XLA compiles for the TPU
# 4) XLA + GSPMD infer the collectives (AllReduce/AllGather), fuse ops, plan memory,
#    and emit TPU machine code. 5) Pathways dispatches it across pods.

What XLA actually buys you

Two things dominate. Fusion: instead of running matmul → write HBM → read HBM → add bias → write → read → relu, XLA does the add and relu while the data is still on-chip, collapsing memory round-trips (remember the roofline — this raises arithmetic intensity). Static scheduling: because the graph is known, XLA plans every DMA and every MXU issue ahead of time — the reason a TPU can skip caches and speculation.

Pathways: from "one pod, one job" to a shared fabric

The older model was SPMD, one program per pod: a job locked an entire pod, and while chips did communication they sat idle on compute. Pathways reframes ML as an asynchronous dataflow graph executed by a single logical controller:

  • Single-controller orchestration: one client describes the whole computation; Pathways dispatches pieces to islands of TPUs — instead of every chip independently running the identical program.
  • Asynchronous dispatch: it schedules the next op before the previous finishes (like CPU instruction pipelining, but for a cluster), keeping hardware full while other work communicates.
  • Multi-pod & multi-tenant: a job can span pods; multiple jobs can share a pod. Higher utilization = more research per dollar.
  • Talks to Borg & the infra layer: Pathways is the customer of the TPU hardware team — it asks the cluster manager for chips, runs on the per-host dispatchers your infra maintains, and reacts when your monitoring flags a failure.

MENTAL MODEL

You never write "send these bytes to chip 37." You declare how data is laid out and let the compiler synthesize the movement. The engineer's leverage is sharding strategy, precision, batching, and placement hints — get those right and the compiler does the rest; get them wrong and no amount of hardware saves you.

INTERVIEW ANGLE

"Walk me from your Python to the TPU." Hit the five stops — JAX trace → HLO → XLA (fusion + scheduling) → GSPMD (sharding → collectives) → Pathways (dispatch across pods) — and then draw the control boundary out loud: "I control the math, sharding intent, precision and placement; the compiler owns fusion, layout, and the actual collectives; the chip owns the MACs and DMAs." That boundary statement is the senior signal.

How This Competes: NVIDIA and Inference ASICs

The accelerator market is not one race. It's "flexible general GPUs" vs "co-designed TPUs" vs "narrow ultra-efficient inference chips" — each optimal in a different region.

The analogy. GPUs are Swiss Army knives — do almost anything, huge ecosystem, sold to everyone. TPUs are a factory line Google built for its own banquet — unbeatable perf-per-watt when the menu is known. Narrow inference ASICs are single-purpose kitchen robots — blazingly fast at one dish (serving a fixed model) and useless at anything else.

The moat that isn't silicon

The hardest thing to copy isn't the chip — it's the software + fleet co-design. NVIDIA's real moat is CUDA and a decade of kernels. Google's is XLA/JAX/Pathways plus owning the datacenter, so it can co-design chip, interconnect, compiler, and scheduler as one system. A startup with a faster multiplier still has to answer: what compiles to it, and who operates 4096 of them?

Training vs inference splits the market

  • Training wants flexibility (models change weekly), huge memory, and fast collectives — favors general accelerators (GPU/TPU) with strong interconnect.
  • Inference wants low latency and cost-per-query on a fixed model — opens the door to quantized (int8/fp8) serving and narrow ASICs. This is why "inference chips" are a distinct category, not just small training chips.
  • Perf-per-watt is the real currency. At datacenter scale, power and cooling dominate cost. "Faster" loses to "same speed at half the watts." That framing — not peak FLOPS — is how these products actually compete.
INTERVIEW ANGLE

"Why would anyone use a TPU over an NVIDIA GPU?" Don't take sides. Say: "For large, regular, long-running workloads inside Google's stack, TPUs win on perf-per-watt and total cost because the whole stack is co-designed; for portable, fast-changing, kernel-heavy research, GPUs win on ecosystem and flexibility. And for high-volume serving of a fixed model, a narrow inference ASIC can beat both on cost-per-query. The right answer is workload-dependent, and the deciding metric is usually perf-per-watt, not peak FLOPS."

Traps that read as junior

AVOID

Leading with peak FLOPS. Peak FLOPS without sustained utilization or perf-per-watt is a marketing number. Always tie compute to the roofline and to power.

AVOID

"TPU beats GPU." The honest answer is workload-dependent. Name the axes: regularity, ecosystem, scale, power, and who owns the stack.

AVOID

Hand-waving "and then it does AllReduce." Know that it's reduce-scatter + all-gather on a ring, and that per-chip bytes are ~2D regardless of N — that's the reason it scales.

AVOID

Blurring the control boundary. You declare sharding; the compiler synthesizes collectives. Saying "I'd write the send between chips" signals you don't know the model.

A 60-second whole-stack narrative

"A neural net is mostly matmul, so Google built an ASIC whose die is mostly a systolic MXU — 128×128 MACs reusing operands in-place, fed by HBM, no caches or branch prediction because a compiler schedules the known access pattern. One chip isn't enough for big models, so chips are wired into a 3D torus with optical switches that reshape the topology per job and route around failures. Models are split with tensor, pipeline, and data parallelism, placed to match comms frequency to link bandwidth, and synced with ring AllReduce. You write it in JAX, XLA fuses and schedules it, GSPMD turns your sharding hints into collectives, and Pathways dispatches it across pods. It competes with NVIDIA on perf-per-watt and full-stack co-design rather than flexibility — and with narrow inference ASICs on cost-per-query for fixed models."

Terminology & Acronyms

Quick reference for the key terms in this chapter.

TermMeaning
TPUTensor Processing Unit — Google's ASIC built to run neural-network matrix math.
ASICApplication-Specific Integrated Circuit — a chip designed for one narrow job, not general use.
MACMultiply-Accumulate — one multiply plus one add; the core step of a matrix multiply.
Systolic arrayA grid of MAC cells that stream operands to neighbors in lockstep, reusing each input in place.
PEProcessing Element — a single multiply-accumulate cell within the systolic array.
MXUMatrix Multiply Unit — the TPU's large systolic array (e.g. 128×128 MACs).
SIMDSingle-Instruction, Multiple-Data — one instruction applied in parallel to many data lanes.
HBMHigh-Bandwidth Memory — DRAM stacked next to the chip holding weights and activations.
SRAMStatic Random-Access Memory — fast on-chip scratchpad (VMEM/CMEM) filled under compiler control.
DMADirect Memory Access — the chip copying a block of data itself, with no CPU in the loop.
ICIInter-Chip Interconnect — dedicated chip-to-chip links used to build pods (6 per v4 chip).
XLAAccelerated Linear Algebra — the optimizing compiler that fuses ops and schedules TPU code.
bfloat16 (bf16)A 16-bit float keeping FP32's 8-bit exponent range; the default TPU training precision.
INT88-bit integer format for quantized inference; 4× smaller than FP32.
Arithmetic intensityFLOPs performed divided by bytes moved from HBM; decides compute-bound vs memory-bound.
RooflineA model comparing arithmetic intensity to the chip's FLOPS/bandwidth ratio to find the limiter.
3D torusA 3D grid of chips with every edge wrapped into a ring, giving short paths and busy links.
Bisection bandwidthTotal link capacity cut when the machine is sliced in half; how fast the two halves talk.
OCSOptical Circuit Switch — physically steers light to rewire inter-cube links in ~10 ms.
ECCError-Correcting Code memory — detects and flags bit errors, aiding fault detection.
AllReduceCollective where every chip ends with the element-wise sum of all chips' gradients.
Data parallelismFull model copy per chip, each fed a different batch shard; gradients synced by AllReduce.
Tensor (model) parallelismA single weight matrix split across chips that exchange partial results within a layer.
Pipeline parallelismConsecutive layers assigned to different chip groups (stages); only activations cross stage boundaries.
JAXA NumPy-like Python library with autodiff and jit/vmap/sharding for accelerators.
HLOHigh-Level Optimizer graph — XLA's hardware-agnostic op graph traced from your code.
GSPMDAuto-partitioning inside XLA that turns sharding hints into collective ops on the torus.
PathwaysGoogle's distributed runtime that dispatches programs across pods with a single controller.
