1. What "Low Latency" Means Here

Most software is tuned for throughput — total work per second. Low-latency systems are tuned for the opposite: the time for a single operation to complete, and specifically for the worst such times. A trading system that averages 2 µs but occasionally stalls for 2 ms has already lost the trade on that stall. The metric that matters is the tail of the latency distribution — p99, p99.9, p99.99 — not the mean.

Tail latency & jitter

p99 latency is the value below which 99% of operations complete: 1 in 100 is slower. p99.9 is 1 in 1000. In a system that handles millions of events, the tail is not rare — it is happening constantly, and it is what a user (or a market) actually feels. Jitter — the variance in latency — is the enemy: a predictable 5 µs is far easier to build around than a mean of 2 µs that spikes unpredictably. Sources of jitter are exactly this chapter's subject matter: cache misses, branch mispredictions, heap allocation, lock contention, page faults, context switches, and interrupts.

A typical latency distribution: a tight peak near the median with a long right tail. The mean hides the tail; p99 and p99.9 are what low-latency work targets.

Mechanical sympathy

The mindset that runs through the whole chapter is mechanical sympathy — writing code that works with the hardware rather than against it. The compiler and CPU do enormous work on your behalf (out-of-order execution, prefetching, branch prediction, multiple cache levels), but they can only help code whose access patterns and control flow are friendly. You do not need to write assembly; you need to know what the machine rewards: predictable, contiguous, cache-resident, branch-friendly, allocation-free hot paths. Everything below is a corollary of that one idea.

Interview signal

When asked to "make this faster," a strong candidate first asks "faster on average, or at the tail?" and "what's the hot path's working-set size relative to cache?" Naming p99 and jitter — and treating the CPU's cache/branch-predictor as things you design for — signals the low-latency mindset before you touch a line of code.

2. The Memory Hierarchy & Cache

The single most important fact in performance engineering: not all memory is equally far away. A modern CPU core reads from a small, fast L1 cache in a few cycles, but a miss all the way to DRAM costs roughly two orders of magnitude more. The absolute numbers vary by machine, but the ratios are stable and huge — and they mean that how your data is laid out matters more than how many instructions you execute.

The memory hierarchy. Each level down is larger but dramatically slower. The cycle/ns figures are rough, machine-dependent orders of magnitude — the point is the ratios, not the digits.

Cache lines: the unit of transfer

The CPU never loads a single byte from memory. It loads a whole cache line — 64 bytes on x86-64 and many ARM cores (128 bytes on some, including Apple silicon). Touch one byte and its 63 neighbours come along for free. This is why spatial locality (accessing nearby addresses) and temporal locality (reusing recent addresses) are the two levers of cache-friendly code: contiguous access streams whole lines and lets the hardware prefetcher run ahead of you; scattered access wastes most of every line it fetches and pays the full miss latency each time.

Benchmark: contiguous scan vs pointer-chasing

The classic demonstration: sum the same N values two ways. First a contiguous std::vector (perfect locality, prefetcher-friendly, and vectorizable). Then a linked list whose nodes are shuffled in memory so each next is an unpredictable jump — every hop is a dependent load that likely misses to DRAM.

// contiguous: perfect spatial locality, prefetcher streams ahead
int64_t s1 = 0;
for (size_t i = 0; i < N; ++i) s1 += arr[i];

// pointer-chase: each 'next' is a dependent, cache-missing jump
int64_t s2 = 0;
Node* p = head;
while (p) { s2 += p->val; p = p->next; }   // nodes shuffled in memory
Measured — one run, 8M int64 elements, -O2

contiguous sum : 1.04 ms · pointer-chase : 843.62 ms → the pointer-chase was ~800× slower on this run (checksums equal, so it is the same work). Two effects compound: the contiguous scan streams from cache and vectorizes, while the chase is latency-bound — each hop waits ~100 ns for DRAM because the next address isn't known until the current load returns, so the prefetcher can't help. This is an extreme case; the ratio on your machine will differ, but the ordering will not.

Takeaway

An O(n) array scan can crush an O(n) linked-list traversal by orders of magnitude for the same asymptotic work. Big-O counts operations; the hardware charges by memory-access pattern. On the hot path, prefer contiguous containers (std::vector, arrays) over node-based ones (std::list, std::map, pointer trees).

3. Data-Oriented Design

If cache lines are the currency, then data-oriented design (DOD) is the budget: lay out data so that the bytes the hot path touches are packed together and the bytes it ignores are elsewhere. The headline pattern is Struct-of-Arrays (SoA) versus Array-of-Structs (AoS).

AoS vs SoA

In AoS you store vector<Particle> where each Particle holds position, velocity, name, flags. A loop that needs only position still drags every cold field through cache — each 64-byte line is mostly wasted. In SoA you store one array per field (vector<double> px; vector<double> py; …); a position-only pass now reads a dense array where every byte of every line is useful, and it vectorizes cleanly.

AoS interleaves a hot field (px) with cold fields, so a px-only scan wastes most of each cache line. SoA stores px contiguously, making every fetched line fully useful.

Hot/cold splitting & the caveat

The general principle beneath SoA is hot/cold splitting: keep the fields the hot path touches every iteration in one compact structure, and push rarely-used fields (error strings, debug metadata, audit fields) into a separate "cold" structure reached by index or pointer. The goal is to shrink the hot working set until it fits in cache.

// AoS: hot 'px' interleaved with cold fields
struct Particle { double px; double vx,vy,vz; char name[24]; };
std::vector<Particle> aos;          // sizeof(Particle) == 56 here

// SoA: each field its own dense array — scan reads only what it needs
std::vector<double> px, vx, vy, vz;
Measured — and an honest caveat

On this Apple-silicon dev machine a sequential px-only scan of 4M elements was only ~1.1× faster in SoA than AoS, because the chip's enormous memory bandwidth and aggressive prefetcher hide the wasted-line cost of a regular stride. The DOD win is real but bandwidth- and architecture-dependent: on bandwidth-bound x86 servers, or with random/gather access that defeats prefetch, the same layout change can be several-fold. Always measure on the target hardware — this is exactly the kind of effect a microbenchmark can under- or over-state (§10).

4. Branch Prediction

Modern CPUs are deeply pipelined and speculative: to keep the pipeline full they guess which way each branch will go and execute ahead. A correct guess is nearly free. A misprediction means the speculatively-executed work is thrown away and the pipeline refills — a penalty of roughly 10–20 cycles. A branch the predictor can learn (a loop bound, a rarely-taken error check) costs almost nothing; a branch driven by unpredictable data costs a misprediction about half the time.

Branch prediction: a correct guess keeps the pipeline full; a misprediction flushes speculative work and refills, costing roughly 10–20 cycles.

Benchmark: sorted vs shuffled data

Sum only the values >= 128 in an array of random bytes. The data is identical; only the order changes. On sorted data the branch flips exactly once (all "no", then all "yes") — trivially predictable. On shuffled data it is a coin flip every iteration — maximally unpredictable.

for (size_t i = 0; i < N; ++i)
    if (data[i] >= 128)          // ~50% taken; order sets predictability
        sum += heavy(data[i]);   // noinline body ⇒ a real branch, not a cmov
Measured — one run, 20M elements, -O2

shuffled : 64.55 ms · sorted : 10.95 ms → sorting the data first made the identical loop ~5.9× faster, purely from branch predictability.

The cmov twist and branchless code

Here is a subtlety worth its own paragraph: with a simple body (sum += data[i];), the same benchmark showed almost no difference (~1.2×) — because at -O2 the compiler turned the if into a branchless conditional move (cmov), which has no branch to mispredict. Only when the taken path calls a non-inlinable function does a genuine branch survive and the misprediction cost appear. That is the lesson behind branchless programming: replace a data-dependent branch with arithmetic or a conditional move so there is nothing to mispredict.

// branchy: mispredicts on unpredictable data
if (x >= 128) sum += x;

// branchless: a mask, no control-flow to mispredict
int take = -(x >= 128);   // 0 or -1 (all-ones)
sum += x & take;              // adds x or 0, no branch

You can also hint the predictor for genuinely lopsided branches with [[likely]] / [[unlikely]] (C++20) or __builtin_expect(cond, 0). Use these only where you truly know the bias (e.g. an error path taken 1 in a million times); on a 50/50 branch a hint helps nothing — you need branchless code or better data ordering instead.

Don't blindly copy branchless code

Branchless code trades a possible flush for guaranteed extra instructions. For a well-predicted branch (the common case), the branchy version is faster because the predictor makes it nearly free. Branchless wins only for unpredictable branches on the hot path — and even then, verify with a measurement, because the compiler may already be emitting cmov.

5. Allocation on the Hot Path

Calling new/malloc (or anything that does, like growing a std::vector or building a std::string) on the critical path is a classic latency killer. A general-purpose allocator may take a lock, search free lists, touch cold metadata, and — worst of all — occasionally ask the kernel for more memory (a syscall and possibly a page fault), producing a rare but brutal tail spike. The rule on the hot path is simple: allocate nothing.

Pre-allocation & object pools

The fix is to move all allocation to startup. Pre-allocate buffers and containers to their worst-case size (vector::reserve), then reuse them. For dynamic lifetimes, use an object pool: a fixed block of pre-constructed objects with a free-list; acquiring and releasing are O(1) index operations that never touch the OS allocator.

template <class T, size_t N>
class Pool {
public:
  Pool() { for (size_t i=0;i<N;++i) free_[i]=&slots_[i]; top_=N; }
  T* acquire() {                       // nullptr when exhausted — no alloc
    if (top_==0) return nullptr;
    return free_[--top_];
  }
  void release(T* p) { free_[top_++] = p; }   // O(1), no free()
private:
  std::array<T, N>  slots_{};
  std::array<T*, N> free_{};
  size_t           top_ = 0;
};
Compiled & run — assertions pass

A test that acquires two objects, releases one, and re-acquires confirms the slot is reused (same pointer, no allocation), and that exhausting the pool returns nullptr gracefully instead of allocating: pool ok: reused slot=yes, exhaustion handled.

Arena / bump allocators

When many objects share one lifetime (e.g. everything allocated while processing a single message), an arena (a.k.a. bump or linear allocator) is unbeatable: hold a big pre-allocated buffer and a cursor; each allocation just returns the cursor and advances it (a pointer add). There is no per-object free — you "reset" the whole arena to the start when the batch is done. Allocation becomes a few instructions with zero fragmentation and no locking.

class Arena {
  char* buf_; size_t cap_, off_ = 0;
public:
  Arena(char* b, size_t c) : buf_(b), cap_(c) {}
  void* alloc(size_t n, size_t align) {
    size_t p = (off_ + align - 1) & ~(align - 1);   // round up
    if (p + n > cap_) return nullptr;             // out of arena
    off_ = p + n; return buf_ + p;                 // bump the cursor
  }
  void reset() { off_ = 0; }                        // free everything at once
};
Interview signal

"How do you avoid heap allocation on the hot path?" → pre-size everything at startup (reserve), reuse buffers, and use object pools or arenas for dynamic needs. Mention that the danger isn't just malloc's average cost but its tail: the occasional sbrk/mmap syscall and page fault are what wreck p99.

6. False Sharing & Alignment

Caches are kept coherent between cores at the granularity of a cache line, not a variable. If two threads write to two different variables that happen to sit on the same 64-byte line, the line ping-pongs between the cores' caches: each write invalidates the other core's copy, forcing a reload. The variables are logically independent, but the hardware treats them as one unit — this is false sharing, and it can silently destroy multithreaded performance.

False sharing: two hot variables on one cache line force the line to bounce between cores. Padding each to its own line removes the contention.

The fix: pad to a cache line

Give each independently-written variable its own line with alignas. C++17 provides std::hardware_destructive_interference_size as the portable "avoid false sharing" pad size (use a constant like 64 if your standard library doesn't expose it).

// BAD: a and b share a line — false sharing
struct Counters { std::atomic<int64_t> a, b; };

// GOOD: each counter on its own cache line
struct Counters {
  alignas(64) std::atomic<int64_t> a{0};
  alignas(64) std::atomic<int64_t> b{0};
};
Measured — one run, two threads × 50M relaxed increments, -O2

unpadded : 379.28 ms · padded : 100.12 ms → padding the two counters onto separate lines made the same workload ~3.8× faster (both counters reach 50,000,000, so correctness is unchanged — only the cache-coherence traffic differs).

The insidious part

False sharing produces no wrong answers and no visible lock — just mysterious slowdown that worsens with more cores. It's a top suspect whenever adding threads makes a per-thread-counter or per-thread-queue workload slower. Look for hot, independently-written fields packed close together (adjacent array slots, struct members, per-thread stats).

7. Atomics & Memory Ordering

std::atomic<T> gives you operations that are indivisible across threads (no torn reads/writes) and lets you specify a memory order — how strongly the atomic's effects are ordered relative to surrounding non-atomic memory operations. Choosing the weakest correct order is where a lot of low-latency concurrency performance lives, but choosing wrong is a data race.

The orderings you actually use

OrderGuaranteeUse when
relaxedAtomicity only — no ordering with other memory ops.Independent counters/stats where only the final value matters, not its ordering vs other data.
acquire (loads)No later read/write in this thread can be reordered before it; sees writes released by another thread.The consumer side: load a flag/index, then read the data it protects.
release (stores)No earlier read/write can be reordered after it; publishes prior writes to an acquiring reader.The producer side: write the data, then store the flag/index that publishes it.
seq_cstAll of the above plus a single total order across all seq_cst ops (the default).When you need a global order (e.g. Dekker-style store-then-load handshakes) or when in doubt.

The acquire/release pattern

The main tool of lock-free code is a release store paired with an acquire load on the same atomic. The producer writes some data and then does a release store to a flag; when the consumer sees that flag via an acquire load, it is guaranteed to also see everything the producer wrote before the release. This is how you publish data safely without a lock.

int payload = 0;
std::atomic<bool> ready{false};

// producer
payload = 42;
ready.store(true, std::memory_order_release);   // publish

// consumer
while (!ready.load(std::memory_order_acquire)) {}   // wait
// here, payload == 42 is guaranteed (release/acquire synchronizes-with)

The cost of seq_cst

seq_cst is the safe default and the right choice when you're unsure, but its total-order guarantee can require a real hardware fence — most visibly for the store-then-load (StoreLoad) pattern, which on x86 forces an mfence and on ARM a dmb ish. On weakly-ordered CPUs, relaxed/acquire/release avoid that fence where they're sufficient.

Measured — and a caveat about what this shows

A single-threaded, uncontended fetch_add loop showed essentially no difference (~1.0×) between relaxed and seq_cst on this Apple-silicon machine — an uncontended atomic read-modify-write is already ordered cheaply here. A store-then-load loop (which needs the StoreLoad barrier) showed only ~1.04×. The real cost of seq_cst shows up under contention and on hot StoreLoad handshakes, not in a single uncontended RMW — so measure the actual pattern, and reach for weaker orderings only where profiling and correctness both justify it.

Relaxed is not "no rules"

relaxed guarantees atomicity but zero ordering: other threads may observe its effect out of order relative to your other writes. It is correct only when the atomic's value is genuinely independent of the surrounding data — a free-running statistic counter, say. Use it to publish data that another thread will read, and you have a race. When unsure, use seq_cst; downgrade only with a specific reason.

8. Lock-Free Basics: the SPSC Ring Buffer

Locks are fine for most code, but on the hot path a contended mutex means a syscall, a context switch, and unbounded tail latency. Lock-free data structures use atomics instead, guaranteeing that some thread always makes progress. The canonical low-latency structure — the one HFT and audio and networking code reaches for constantly — is the single-producer / single-consumer (SPSC) ring buffer: exactly one thread pushes, one thread pops, and they hand off with no lock at all.

SPSC ring buffer: a fixed power-of-two array with a producer-owned head and consumer-owned tail. Each side publishes its index with a release store the other reads with acquire.

A correct SPSC queue

The trick to correctness: the producer only writes head, the consumer only writes tail, and each publishes its index with a release store the other reads with an acquire load. That acquire/release pairing guarantees the consumer sees the slot's data before it sees the advanced head. Capacity is a power of two so wrap-around is a bitmask, not a modulo.

template <class T, size_t Cap>    // Cap must be a power of two
class SpscRing {
public:
  bool push(const T& v) {
    const size_t h = head_.load(std::memory_order_relaxed);
    const size_t n = (h + 1) & (Cap - 1);
    if (n == tail_.load(std::memory_order_acquire)) return false;  // full
    buf_[h] = v;
    head_.store(n, std::memory_order_release);   // publish the write
    return true;
  }
  bool pop(T& out) {
    const size_t t = tail_.load(std::memory_order_relaxed);
    if (t == head_.load(std::memory_order_acquire)) return false;  // empty
    out = buf_[t];
    tail_.store((t + 1) & (Cap - 1), std::memory_order_release);
    return true;
  }
private:
  std::array<T, Cap> buf_{};
  alignas(64) std::atomic<size_t> head_{0};   // producer writes
  alignas(64) std::atomic<size_t> tail_{0};   // consumer writes — own line
};
Compiled & run — correctness verified

A producer thread pushed 5,000,000 integers 0..N-1 while a consumer popped them on another thread. The result: transferred 5000000 items, sum OK, and the consumer checked that every value arrived exactly once and in order (no gaps, no duplicates). Note head_ and tail_ are on separate cache lines (§6) so producer and consumer don't false-share.

Lock-free ≠ wait-free, and the ABA problem

  • Lock-free vs wait-free. Lock-free guarantees that some thread makes progress in a bounded number of steps (the system never stalls), but an individual thread may retry indefinitely. Wait-free is stronger: every thread finishes in a bounded number of steps. This SPSC queue is actually wait-free for push/pop; general multi-producer structures usually settle for lock-free.
  • The ABA problem. In compare-and-swap (CAS) loops on shared pointers/indices, a value can change from A to B and back to A between your read and your CAS; the CAS succeeds even though the world moved underneath you. Classic fixes are tagged pointers (pack a version counter alongside the pointer) or hazard pointers / epoch-based reclamation. SPSC sidesteps ABA entirely because each index has exactly one writer — another reason it's the first lock-free structure to reach for.

9. Kernel-Bypass & the OS

Even perfect user code can be derailed by the operating system. A context switch (the kernel parking your thread to run another) costs microseconds directly and far more indirectly, because the new thread pollutes your caches and TLB — when you resume, your hot data is cold. A system call crosses into the kernel and back. A page fault can stall for milliseconds. Low-latency engineering is largely about denying the OS the chance to do any of these on the hot path.

Spin, don't sleep

On the hot path, waiting by sleeping (a blocking mutex, a condition variable, epoll) invites a context switch and its cache-cold aftermath. Instead you busy-poll (spin), burning a core to stay hot and react in nanoseconds. It wastes CPU — the deliberate trade a latency-critical system makes.

// busy-poll a lock-free queue instead of blocking
Msg m;
while (!queue.pop(m)) {
  __builtin_ia32_pause();   // x86 PAUSE; ARM: __yield() / "yield" — hint, not a sleep
}
handle(m);   // stayed on-core, caches warm, no syscall

The PAUSE/yield hint reduces power and helps sibling hyperthreads without giving up the core to the scheduler.

Pinning, isolation, huge pages, NUMA

  • CPU pinning & isolation. Pin the hot thread to a dedicated core (pthread_setaffinity_np / taskset on Linux) and isolate that core from the scheduler and interrupts (kernel isolcpus/nohz_full, IRQ affinity). The thread then runs undisturbed — no migration, no other work stealing its caches.
  • Huge pages. The TLB caches virtual→physical translations. With 4 KiB pages a large working set thrashes the TLB; 2 MiB/1 GiB huge pages cover far more memory per TLB entry, cutting TLB misses and page-table walks.
  • NUMA. On multi-socket machines, memory attached to another socket is slower to reach. Keep a thread's data on its local NUMA node (allocate on the node the thread is pinned to) to avoid cross-socket hops.

Kernel-bypass networking (conceptual)

The kernel network stack copies packets, switches context on interrupts, and adds latency and jitter. Kernel-bypass networking — DPDK, Solarflare/Onload, RDMA, or AF_XDP — maps the NIC's queues directly into user space so the application polls packets itself, with zero syscalls and often zero copies on the data path. In HFT this is standard: the trading process busy-polls the NIC, parses market data, and writes an order straight back to the wire without the kernel ever touching the hot path. The concept to carry into an interview: the fastest syscall is the one you never make.

Interview signal

"Why busy-poll instead of blocking?" → blocking parks the thread, and waking it costs a context switch plus cache/TLB refill — microseconds of jitter. Spinning trades a whole core for staying hot and reacting in nanoseconds. Pair that with CPU pinning + core isolation so nothing else perturbs the polling thread, and mention kernel-bypass as the same idea applied to the NIC.

10. Measurement & Pitfalls

Every number in this chapter came from a benchmark, and benchmarks lie constantly if you let them. The discipline of measuring correctly is itself a core low-latency skill — more valuable than any single trick, because it's how you tell a real win from a fantasy.

How to benchmark

  • Warm up. The first iterations pay cold caches, lazy page faults, and CPU frequency ramp-up. Discard them; measure the steady state.
  • Measure the distribution, not the mean. Collect many samples and report p50 / p99 / p99.9 (§1). A mean hides exactly the tail you care about.
  • Use a steady clock. std::chrono::steady_clock is monotonic (never jumps backward like a wall clock can). For the finest-grained, cycle-level timing, rdtsc reads the CPU timestamp counter directly — but beware frequency scaling and multi-core sync issues.
  • Pick the right optimization level. Measure at the -O2/-O3 you actually ship. Debug builds tell you nothing about production latency.

Stop the optimizer from deleting your benchmark

The single most common microbenchmark bug: the compiler proves your result is unused and deletes the entire loop, so you "measure" nothing and report an impossibly fast time. The fix is a sink that forces the result to be considered used — the idea behind Google Benchmark's benchmark::DoNotOptimize. A simple portable version uses an inline-asm barrier (or a volatile sink):

template <class T>
inline void do_not_optimize(T const& v) {
  asm volatile("" : : "r,m"(v) : "memory");   // pretend v is read + clobber memory
}

// usage: compute, then make the result "observable"
double acc = seed;
for (int i = 0; i < 1000; ++i) acc = std::sqrt(acc + 1.0);
do_not_optimize(acc);   // without this, the whole loop can vanish
Compiled & run — a p50/p99/p99.9 harness

A 200-trial harness timing that sqrt loop with do_not_optimize and reporting sorted percentiles produced, on one run: p50 ≈ 4292 ns · p99 ≈ 4458 ns · p99.9 ≈ 4917 ns. The absolute values are illustrative and machine-specific; what matters is the shape — a tight p50 with a p99.9 tail well above it, which is exactly the thing to drive down.

Why microbenchmarks lie

Common ways a microbenchmark deceives you

(1) Dead-code elimination deletes unmeasured work (above). (2) Unrealistic cache state — a benchmark loop keeps everything hot, so a "fast" function that always hits L1 in the test misses to DRAM in production. (3) Constant folding — the compiler precomputes results from compile-time-known inputs; feed runtime data. (4) Perfect branch prediction — a repeated pattern trains the predictor in ways real traffic won't (see §4's cmov surprise). (5) Frequency scaling / thermal effects shift results between runs. (6) Measuring the mean hides the tail. Always sanity-check that the ordering of results matches a mechanism you can explain.

Interview framing — probe Q&As

Q: Why optimize for tail latency (p99/p99.9) instead of the mean?
Because users and markets feel the worst case, not the average, and at scale the tail happens constantly — a service handling millions of ops/sec sees its p99.9 case thousands of times a second. The mean hides jitter from cache misses, GC-like allocation spikes, context switches, and lock contention. You target p99/p99.9 and attack the sources of variance directly.

Q: What is a cache line, and how does it cause false sharing?
A cache line (typically 64 bytes) is the unit of memory transfer and of cache coherence. False sharing happens when two threads write two independent variables that share one line: each write invalidates the other core's copy, so the line ping-pongs and both threads slow down despite no logical contention. Fix by padding each hot, independently-written variable to its own line with alignas(64) (or hardware_destructive_interference_size). Measured here: ~3.8× faster once padded.

Q: When is a relaxed atomic safe?
Only when you need atomicity but no ordering relative to other memory — a free-running statistics counter whose exact interleaving with surrounding writes doesn't matter, and whose value no other thread uses to gate reads of other data. The moment you use the atomic to publish data another thread will read, you need release/acquire (or seq_cst). Relaxed guarantees the value won't tear, nothing about ordering.

Q: Why avoid heap allocation on the hot path?
Because malloc/new can lock, walk free lists, and occasionally hit the kernel (mmap/sbrk) and take a page fault — a rare but multi-microsecond spike that wrecks p99. Pre-allocate at startup (reserve), reuse buffers, and use object pools or arenas so the critical path does only pointer arithmetic, never touches the OS allocator, and has no unbounded tail.

Q: How would you measure a function's latency without fooling yourself?
Warm up first; run many trials with a monotonic clock (steady_clock or rdtsc); prevent dead-code elimination with a DoNotOptimize/volatile sink; feed runtime (not constant) inputs so nothing is folded away; build at production -O2/-O3; and report p50/p99/p99.9, not the mean. Then confirm the result's ordering matches a mechanism you can explain — otherwise the benchmark is probably lying.

One-line summary

Low-latency C++ is applied mechanical sympathy: target the tail, keep the hot path's working set contiguous and cache-resident (§2–§3), make branches predictable or branchless (§4), allocate nothing on the critical path (§5), pad hot shared data to avoid false sharing (§6), pick the weakest correct memory order and hand data off through a lock-free SPSC ring (§7–§8), keep the OS off the hot path via spinning, pinning, huge pages and kernel-bypass (§9), and measure the distribution honestly so you optimize the real bottleneck, not a benchmark artifact (§10).

Mechanical sympathyWriting code that works with the hardware — cache, prefetcher, branch predictor — rather than against it.
Cache lineThe fixed unit of memory transfer and cache coherence, typically 64 bytes (128 on some ARM/Apple silicon).
PrefetcherHardware that predicts upcoming addresses and loads them early; effective only on regular, contiguous access.
DOD (data-oriented design)Laying out data so the bytes the hot path touches are packed together and cold fields sit elsewhere.
AoS / SoAArray-of-Structs (one record per element) vs Struct-of-Arrays (one dense array per field); SoA packs a scanned field.
cmovConditional-move instruction: selects a value without a branch, so there is nothing to mispredict.
Branch (mis)predictionThe CPU speculatively guesses each branch's direction to keep its pipeline full; a wrong guess (misprediction) flushes speculative work and refills the pipeline, costing ~10–20 cycles — costly only for data-unpredictable branches.
Object poolFixed set of pre-constructed objects with a free-list; acquire/release are O(1) and never call the allocator.
Arena allocatorBump/linear allocator over a pre-sized buffer; each allocation advances a cursor, and the whole block is reset at once.
False sharingTwo independent variables on one cache line, so cross-core writes ping-pong the line and slow both threads.
Memory orderHow an atomic's effects are ordered against surrounding memory: relaxed, acquire, release, or seq_cst (sequentially consistent).
Lock-free vs wait-freeLock-free: some thread always makes progress. Wait-free (stronger): every thread finishes in bounded steps.
SPSCSingle-producer / single-consumer: exactly one thread pushes and one pops, enabling a lockless handoff.
CAS (compare-and-swap)Atomic "set to new only if still equal to expected"; the primitive most lock-free updates loop on.
ABA problemA value changes A→B→A between a read and a CAS, so the CAS wrongly succeeds despite intervening change.
TLB (translation lookaside buffer)Cache of virtual→physical address translations; huge pages cover more memory per entry, cutting misses.
NUMA (non-uniform memory access)On multi-socket machines, memory on a remote node is slower; keep a thread's data on its local node.
Kernel-bypassMapping NIC queues into user space to poll packets with no syscalls/copies — e.g. DPDK, RDMA, AF_XDP.
rdtscx86 instruction reading the CPU time-stamp counter for sub-nanosecond timing; watch frequency scaling and multi-core sync.
