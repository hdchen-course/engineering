Assorted Problems I — Strings & Math

Eight Google-style string- and number-manipulation problems • original framing, execution-tested code, and interviewer probes

Note: Representative big-tech-style problems — not sourced from Google. The “Google-style” badge denotes the flavor of question, not its source.

How to read this chapter: an assortment of the “warm-up” string and math problems that open many interviews — short to state, but each hides one subtlety (overflow, a bijection, a boundary, a double-count) that separates a correct answer from a plausible-looking wrong one. Every worked example was invented for this book, and each stated output was produced by compiling and running the accompanying Java. Beyond the hand-picked cases, every solution here was cross-checked against an independent reference over hundreds of thousands of random inputs — reverse against a 64-bit reversal with range clamp, isIsomorphic against a canonical pattern encoding, license formatting against a naive left-to-right rebuild, Bulls-and-Cows against a list-removal counter, the strobogrammatic check against a literal 180° rotate-and-compare, and the LR-string reachability against a breadth-first search over all reachable states — asserting identical results at every step. The recurring lesson: name the one edge case before you code, because these problems are all edge cases.

Reverse Integer

Medium Google-style

Problem

Given a signed 32-bit integer, return it with its decimal digits reversed, preserving the sign. If the reversed value falls outside the 32-bit range [-231, 231-1], return 0. You may not use a wider 64-bit type to dodge the overflow — detect it during the build.

  • Trailing zeros vanish on reversal: -6820 becomes -286.
  • The valid range is asymmetric: the most negative value -2147483648 has no positive counterpart, so overflow must be checked on both ends.

Example: reverse(12345)→54321; reverse(-6820)→-286 (reversing 6820 drops the trailing zero to give 286, sign kept); reverse(1534236469)→0 (its reversal 9646324351 exceeds 2147483647, so we return 0) — all computed by running it.

Approach & Intuition

Peel digits off the end with % 10 and rebuild, but test for overflow before each multiply-and-add. Working in int throughout, the signed remainder x % 10 carries the sign for free (in Java the remainder takes the dividend's sign: -6820 % 10 is 0 and -682 % 10 is -2), so no separate sign bookkeeping is needed. The only danger is that res * 10 + digit can overflow. We guard it by comparing res against Integer.MAX_VALUE/10 (and MIN_VALUE/10): if res is already past that threshold, or exactly at it with a digit that would tip it over (> 7 on the positive end, < -8 on the negative), we return 0.

public int reverse(int x) {
    int res = 0;
    while (x != 0) {
        int digit = x % 10;          // signed: keeps x's sign, no abs() needed
        x /= 10;
        // check overflow BEFORE res = res*10 + digit
        if (res > Integer.MAX_VALUE / 10 ||
            (res == Integer.MAX_VALUE / 10 && digit > 7)) return 0;
        if (res < Integer.MIN_VALUE / 10 ||
            (res == Integer.MIN_VALUE / 10 && digit < -8)) return 0;
        res = res * 10 + digit;
    }
    return res;
}

Complexity: Time O(d) where d is the number of digits (at most 10 for a 32-bit int) — effectively O(1). Space O(1): a single accumulator.

Common pitfalls / interviewer probes: Overflow is the whole problem. Reversing into a wider long and then range-checking works but is explicitly what a strong interviewer disallows — the point is to catch overflow while staying in 32 bits, hence the “compare against MAX/10 before multiplying” trick. The magic 7 and -8 are the last digits of 2147483647 and -2147483648. Signed remainder. In Java % follows the dividend’s sign, so a single loop handles negatives without a separate abs pass (which would itself overflow on MIN_VALUE). Trailing zeros. They disappear naturally — reverse(120) is 21, not 021 — because leading zeros carry no value.

Isomorphic Strings

Easy Google-style

Problem

Two strings are isomorphic if the characters of the first can be replaced to obtain the second, with a consistent one-to-one mapping: every occurrence of a character maps to the same character, and no two distinct characters map to the same one. The mapping must be a bijection — order is preserved and character identity may change.

  • Equal lengths are required; a mismatch is an immediate false.
  • The mapping is checked in both directions: a→x forbids any other source char also mapping to x.

Example: ("abca","zxyz")→true (a→z, b→x, c→y, and the final a→z is consistent); ("mango","hello")→false (both n and g would have to map to l — two sources collide on one target); ("aa","cd")→false (a maps to c then d — one source, two targets, caught by the forward map at index 1) — computed by running it.

Approach & Intuition

Keep two maps and verify both directions as you scan. A single forward map s→t catches “one character maps to two different ones,” but misses the mirror failure where two source characters land on the same target — that violates the one-to-one requirement too. So we maintain a reverse map t→s as well. At each index, if either map already binds the character to something different from the current partner, the strings are not isomorphic; otherwise we record both bindings and continue.

public boolean isIsomorphic(String s, String t) {
    if (s.length() != t.length()) return false;
    Map<Character,Character> st = new HashMap<>();   // s -> t
    Map<Character,Character> ts = new HashMap<>();   // t -> s (mirror check)
    for (int i = 0; i < s.length(); i++) {
        char a = s.charAt(i), b = t.charAt(i);
        // a already bound to a DIFFERENT char? not consistent
        if (st.containsKey(a) && st.get(a) != b) return false;
        // b already claimed by a DIFFERENT source? collision
        if (ts.containsKey(b) && ts.get(b) != a) return false;
        st.put(a, b);
        ts.put(b, a);
    }
    return true;
}

Complexity: Time O(n) — one pass with constant-time map operations. Space O(k) where k is the number of distinct characters (bounded by the alphabet, so O(1) for a fixed charset).

Common pitfalls / interviewer probes: Check both directions. The single most common bug is using only the forward map, which wrongly accepts ("mango","hello") because it never notices that n and g both map to l. A bijection needs the reverse map too. Length guard first. Unequal lengths can never be isomorphic; check it up front to avoid an index error. Whole-alphabet variant. An int[256] pair of arrays initialized to a sentinel is a faster, allocation-free alternative to the two hash maps when the charset is small and fixed.

Jewels and Stones

Easy Google-style

Problem

You are given a string jewels, each character a distinct type of jewel, and a string stones, each character a stone you hold. Return how many of your stones are also jewels. Characters are case-sensitive, so "a" and "A" are different types.

  • Each character in jewels is distinct; stones may repeat freely.
  • Count every matching stone, including duplicates.

Example: jewels="xZ", stones="xxyZZ" → 4 — the stones x, x, Z, Z are jewels (the lone y is not), computed by running it.

Approach & Intuition

Put the jewel types in a hash set, then scan the stones once and tally membership. Because jewels tells us exactly which characters count, a set gives O(1) “is this a jewel?” lookups; a linear pass over stones then adds one for every stone found in the set. This is the canonical “precompute a lookup, then stream the input” shape.

public int numJewelsInStones(String jewels, String stones) {
    Set<Character> set = new HashSet<>();
    for (char c : jewels.toCharArray()) set.add(c);   // jewel types
    int count = 0;
    for (char c : stones.toCharArray())
        if (set.contains(c)) count++;                  // O(1) membership per stone
    return count;
}

Complexity: Time O(j + s) for jewel and stone lengths — build the set, then one pass. Space O(j) for the set.

Common pitfalls / interviewer probes: Case sensitivity. 'a' and 'A' are separate jewel types; don’t lowercase. Don’t nest loops. A brute-force “for each stone, scan all jewels” is O(j×s); the set collapses the inner scan to O(1). Fixed-charset shortcut. If inputs are ASCII, a boolean[128] flag array is even leaner than a HashSet and avoids boxing.

Unique Email Address

Easy Google-style

Problem

An email splits at '@' into a local part and a domain. When normalizing the local part: dots are ignored and everything from the first '+' onward is dropped. The domain is left untouched. Given a list of addresses, return how many distinct mailboxes they actually reach.

  • Dots and '+' rules apply only to the local part — a dot in the domain is significant.
  • Two addresses that normalize to the same local@domain reach the same inbox and count once.

Example: given john.doe+work@mail.com, johndoe@mail.com, j.o.h.n.doe@other.com, alice+promo@mail.com → 3. The first two both normalize to johndoe@mail.com (dots stripped, +work dropped); the third is johndoe@other.com (different domain); the fourth is alice@mail.com — three distinct inboxes, computed by running it.

Approach & Intuition

Normalize each address to a canonical string and count the distinct results in a set. Split once at '@'. In the local part, first truncate at the earliest '+' (a later '+' would already be gone), then delete all dots. Re-join with the untouched domain and add to a HashSet; the set’s final size is the answer. The ordering — cut at '+' before or after removing dots — doesn’t matter here since neither operation reintroduces the other’s trigger, but cutting first is marginally less work.

public int numUniqueEmails(String[] emails) {
    Set<String> seen = new HashSet<>();
    for (String e : emails) {
        int at = e.indexOf('@');
        String local = e.substring(0, at);
        String domain = e.substring(at);        // includes '@', left untouched
        int plus = local.indexOf('+');
        if (plus >= 0) local = local.substring(0, plus);  // drop from first '+'
        local = local.replace(".", "");            // ignore all dots (local only)
        seen.add(local + domain);
    }
    return seen.size();
}

Complexity: Time O(total characters) across all addresses. Space O(total characters) for the set of normalized keys.

Common pitfalls / interviewer probes: Rules apply to the local part only. Stripping dots from the domain too is the classic bug — mail.com and mailcom are different hosts. Split at '@' first and never touch the domain. Drop from the first '+'. Everything after it (including any later '+' or dots) is gone, so truncating at the earliest '+' is correct. Keep the '@' attached. Building the key as local + domain where domain still carries its '@' avoids accidentally merging a local and a domain that happen to concatenate to the same string.

License Key Formatting

Easy Google-style

Problem

Given a license string of alphanumerics and dashes and an integer k, reformat it so that each group contains exactly k characters, groups are joined by dashes, and all letters are uppercase. The first (leftmost) group may be shorter than k but must be non-empty; every group after it has exactly k characters.

  • Remove all existing dashes first; they carry no positional meaning.
  • Grouping is counted from the right, so any remainder lands in the first group.

Example: ("2b-Xk9--p", k=3)→"2BX-K9P" (six real chars 2BXK9P split cleanly into two groups of 3); ("abcde-fg", k=2)→"A-BC-DE-FG" (seven chars ABCDEFG: groups of 2 from the right leave a lone A as the shorter first group) — computed by running it.

Approach & Intuition

Scan the original from the right, appending kept characters and inserting a dash every k characters. Walking right-to-left lets the “short group” fall out for free: we count only the characters we keep, and whenever the count so far is a positive multiple of k we place a dash before adding the next character. Skipping dashes as we go means the input’s original grouping is irrelevant. At the end we reverse the buffer once to restore left-to-right order. Using sb.length() % (k+1) == k tracks position within the current group including the dashes already written.

public String licenseKeyFormatting(String s, int k) {
    StringBuilder sb = new StringBuilder();
    for (int i = s.length() - 1; i >= 0; i--) {   // right to left
        char c = s.charAt(i);
        if (c == '-') continue;                     // drop old dashes
        // every k kept chars, insert a group separator first
        if (sb.length() % (k + 1) == k) sb.append('-');
        sb.append(Character.toUpperCase(c));
    }
    return sb.reverse().toString();                 // flip back to left-to-right
}

Complexity: Time O(n) for a string of length n — one scan plus one reverse. Space O(n) for the output buffer.

Common pitfalls / interviewer probes: The first group is shorter, not the last. Grouping from the right is what forces the remainder into the leftmost group; grouping from the left instead would wrongly shorten the final group. Uppercase every letter. Digits pass through unchanged, but letters must be uppercased. All-dashes / empty result. If the input is only dashes, the result is the empty string — make sure no leading dash survives (scanning right-to-left and reversing handles this, since the dash is only inserted between kept characters). The % (k+1) counter. Because dashes live in the buffer too, the group boundary is at length k, then 2k+1, then 3k+2… which is exactly “length mod k+1 equals k.”

Bulls and Cows

Medium Google-style

Problem

In the guessing game, given a secret number and a guess of equal length (both strings of digits), return a hint "xAyB" where x is the number of bulls (digits correct in both value and position) and y is the number of cows (digits present in the secret but in the wrong position). Each secret digit and each guess digit can be paired at most once.

  • A digit already counted as a bull is not available to also be a cow.
  • Cows are bounded by how many copies of a digit the secret and guess share among their non-bull positions.

Example: secret="1123", guess="0111" → "1A1B". Position 1 matches (1=1) → 1 bull. Among the rest, the secret’s non-bull digits are {1,2,3} and the guess’s are {0,1,1}; they share a single 1, so 1 cow — the guess’s second extra 1 has no partner. Computed by running it.

Approach & Intuition

Count bulls in one pass; for everything that is not a bull, tally digit frequencies on each side and sum the per-digit minimums. Bulls are exact position matches, easy to count directly. For cows, the subtlety is not double-counting: a digit can only be a cow as many times as it appears un-matched on both sides. So we histogram the non-bull digits of the secret and of the guess separately, then for each digit 0–9 add min(secretCount, guessCount). Positions consumed as bulls are excluded from both histograms, so they can never leak into the cow count.

public String getHint(String secret, String guess) {
    int bulls = 0, cows = 0;
    int[] s = new int[10], g = new int[10];   // non-bull digit histograms
    for (int i = 0; i < secret.length(); i++) {
        char sc = secret.charAt(i), gc = guess.charAt(i);
        if (sc == gc) bulls++;                     // exact position match
        else { s[sc - '0']++; g[gc - '0']++; }    // defer to cow tally
    }
    for (int d = 0; d < 10; d++)
        cows += Math.min(s[d], g[d]);            // shared copies only
    return bulls + "A" + cows + "B";
}

Complexity: Time O(n) — one pass to classify, then a constant 10-bucket sum. Space O(1): two fixed size-10 arrays.

Common pitfalls / interviewer probes: Don’t double-count. The defining trap: a digit that is a bull must be removed from cow consideration, and a cow can be claimed only up to the shared count. Summing min(s[d], g[d]) over non-bull positions handles both automatically. Bulls first, then cows. Counting cows over all positions (including the matched ones) inflates the answer. Single pass is enough. You can classify bulls and build both histograms in the same loop; a second pass only sums the 10 buckets. Repeated digits. The whole difficulty comes from repeats — with all-distinct digits any frequency scheme works, so interviewers test "1123"-style inputs on purpose.

Strobogrammatic Number

Easy Google-style

Problem

A strobogrammatic number reads the same after being rotated 180° (turned upside down). Given a number as a string, decide whether it is strobogrammatic. Under rotation the digits pair up as 0↔0, 1↔1, 8↔8, and 6↔9 (each becomes the other); every other digit (2,3,4,5,7) is invalid.

  • Rotation reverses the order and flips each digit, so the check pairs position i with position n-1-i.
  • A single middle digit must map to itself — only 0, 1, 8 qualify (so lone 6 or 9 fails).

Example: "1961"→true (rotated: the outer 1…1 pair to 1…1, the inner 9,6 become 6,9 read back to 9,6); "962"→false (2 is not a rotatable digit, and 9’s partner would need to be 6, not 2); "6"→false (a lone 6 rotates to 9, not itself); "8"→true — computed by running it.

Approach & Intuition

Walk two pointers inward and confirm each outer pair is a valid rotation of the other. Because a 180° turn both reverses the string and swaps 6/9, the character at the left pointer must be the rotation-partner of the character at the right pointer. A small map encodes the five legal digits and their partners; anything else fails immediately. When the pointers meet on a middle character (odd length), the same test applies with l == r, which correctly demands a self-symmetric digit (0, 1, or 8).

public boolean isStrobogrammatic(String num) {
    Map<Character,Character> pair = new HashMap<>();
    pair.put('0','0'); pair.put('1','1'); pair.put('8','8');
    pair.put('6','9'); pair.put('9','6');      // 2,3,4,5,7 absent -> invalid
    int l = 0, r = num.length() - 1;
    while (l <= r) {                            // l==r handles the odd middle digit
        char a = num.charAt(l), b = num.charAt(r);
        // left char must be the rotation-partner of the right char
        if (!pair.containsKey(a) || pair.get(a) != b) return false;
        l++; r--;
    }
    return true;
}

Complexity: Time O(n) — each pointer moves through half the string. Space O(1): a fixed five-entry map.

Common pitfalls / interviewer probes: 6 and 9 are partners, not self-symmetric. A lone 6 or 9 in the middle is invalid because it rotates into the other digit; only 0/1/8 map to themselves. Checking pair.get(a) != b at l == r enforces this automatically. Reject 2,3,4,5,7 outright. They have no upside-down form; leaving them out of the map makes containsKey fail fast. It’s a paired check, not “each digit rotatable.” "69" is valid but "66" is not — the partner relationship across the two ends is what matters, not whether each digit individually rotates. Leading-zero nuance. As a standalone predicate "00" reads the same rotated and is accepted; if the caller treats these as numbers, it may separately forbid leading zeros — clarify the contract.

Swap Adjacent in LR String

Medium Google-style

Problem

Two strings start and end consist of the characters 'L', 'R', and 'X'. In one move you may replace "XL" with "LX" (an L slides one step left) or "RX" with "XR" (an R slides one step right). Decide whether start can be transformed into end by any sequence of such moves.

  • L and R never pass through each other — the relative order of the non-X characters is invariant.
  • Each L can only end up at the same index or to the left of where it started; each R only at the same index or to the right.

Example: ("XL","LX")→true (the L slides left); ("LXXRX","LXXXR")→true (the R slides one step right, the L is already in place); ("XRLX","XLRX")→false (that would require L and R to swap order, which no move allows); ("XRX","RXX")→false (the R would have to move left) — all computed by running it.

Approach & Intuition

Ignore the Xs and compare the two token streams position by position, enforcing the direction each token may drift. Since a move only swaps a letter with an adjacent X, the subsequence of non-X characters never changes order — so first, dropping all Xs, start and end must yield the identical L/R sequence. Second, an L can only travel left, so its index in start must be >= its index in end; an R can only travel right, so its start index must be <= its end index. We check both with two pointers that skip Xs on each side and compare the aligned tokens.

public boolean canTransform(String start, String end) {
    if (start.length() != end.length()) return false;
    int n = start.length(), i = 0, j = 0;
    while (i < n || j < n) {
        while (i < n && start.charAt(i) == 'X') i++;   // next real token in start
        while (j < n && end.charAt(j) == 'X') j++;     // next real token in end
        if (i == n || j == n) return i == n && j == n;  // both must run out together
        if (start.charAt(i) != end.charAt(j)) return false; // order of L/R differs
        char c = start.charAt(i);
        if (c == 'L' && i < j) return false;         // L can't move right
        if (c == 'R' && i > j) return false;         // R can't move left
        i++; j++;
    }
    return true;
}

Complexity: Time O(n) — each pointer advances through the string once. Space O(1): just the two indices.

Common pitfalls / interviewer probes: Two invariants, both required. Matching the X-stripped token sequences catches order violations (("XRLX","XLRX")), and the per-token index comparison catches illegal drift direction (("XRX","RXX")) — you need both checks, not just one. Direction is fixed per token. L only decreases its index, R only increases it; mixing these up is the core bug. Tokens must exhaust together. If one side runs out of L/R tokens before the other, they had different token counts — return false unless both pointers reached the end. Length guard. Different lengths can never match; check it first. Why not brute-force BFS? Exploring all reachable states is exponential; the two-invariant characterization is the O(n) insight the interviewer is after (and it’s exactly what a BFS over small inputs confirms).
