Design a Unique ID Generator (at scale)

A deceptively deep warm-up: hand out billions of globally-unique IDs per day, with no central bottleneck, ideally roughly time-sortable, and compact enough to fit an 8-byte integer. The key part is a bit-packed 64-bit "Snowflake"-style ID — every field width, range, and shift below is arithmetically derived and re-checked so you can quote it in an interview.
Read this like a story

Start at the top even if you know the answer. The chapter builds from "why is this hard at all" through why the naive options fail, the estimation that fixes the bit budget, UUIDs, then the 64-bit Snowflake layout (the part interviewers grade), the clock-skew problems that trip people up, the ticket-server / segment / K-sortable alternatives, a trade-offs table, and a probe-by-probe interview script. The bit math is boxed so you can find it fast on a re-read.

1. Problem & Requirements

A unique ID generator hands every new entity — a row, a message, an order, an event — an identifier that is guaranteed distinct across the whole system, forever. It sounds trivial (a database AUTO_INCREMENT column does it), but at scale the naive answer collapses: a single counter becomes a bottleneck and a single point of failure, and once you shard across data centers there is no one place to increment.

Functional requirements

  • Globally unique. No two IDs ever collide, across all nodes and all data centers, for the lifetime of the system.
  • High throughput. The generator must generate IDs at least as fast as the fleet creates entities — think tens of thousands to millions per second at peak.
  • Roughly time-ordered / sortable (ideally). Newer IDs should sort after older ones. This is not strictly required for uniqueness, but it makes IDs usable as a rough timeline and — crucially — kind to database indexes (§7, §9).
  • Compact. Prefer an ID that fits a 64-bit integer (8 bytes) so it stores as a BIGINT, fits a CPU register, and keeps indexes small — rather than a 128-bit / 36-character UUID.

Non-functional requirements

  • No central bottleneck. ID generation is on the write path of everything; a single shared allocator caps the whole system's write throughput and is a SPOF.
  • Low latency. Generating an ID should be a local, in-process operation — ideally zero network hops on the hot path.
  • High availability. If one generator dies, the rest keep generating; there is no single node whose loss stops all writes.
Clarify before you draw

Ask up front: must IDs be strictly monotonic or just roughly time-ordered? do they need to be unguessable (security) or is sortability more valuable? single region or multi-datacenter? what peak IDs/sec? must they fit 64 bits? "Sortable" and "unguessable" pull in opposite directions — you usually cannot have both — so pin down which one matters before you commit to a design.

2. Why Not the Naive Options

Two answers spring to mind first. Both are worth stating precisely, because naming exactly why they fail is what motivates everything after.

Auto-increment on a single database

A single relational table with an AUTO_INCREMENT primary key gives perfectly unique, perfectly sortable IDs with zero effort. It is the right answer for a small app — and the wrong answer at scale:

Single point of failure + bottleneck

Every insert in the entire system must go through the one node that owns the counter. That node caps total write throughput at what a single database can sustain, and if it goes down, no one can generate an ID — writes stop everywhere. You also cannot generate an ID before the row is written (you need a round-trip to the DB), so it is not usable as a client-side or pre-insert identifier.

Plain UUIDv4 (random 128-bit)

A random UUID (version 4) is generated locally with no coordination — great for availability. But it costs on the other axes:

Not sortable
  • 122 random bits carry no time component, so UUIDv4s sort in essentially random order — useless as a timeline.
Index-unfriendly
  • Random keys scatter inserts across a B-tree, causing page splits and poor cache locality (§9). 128 bits / 16 bytes also bloats every index.

So neither extreme is satisfying: the single counter is coordination-heavy and a SPOF; UUIDv4 is coordination-free but large, random, and index-hostile. The rest of the chapter finds the middle: coordination-free like a UUID, but compact and time-ordered like a counter.

3. Estimation — Sizing the Bit Budget

The estimation here is not about servers or storage; it is about how many bits the ID needs, which is what tells you a 64-bit integer suffices.

How many IDs, and therefore how many bits?

Suppose peak demand is 1,000,000 IDs/sec across the whole fleet, and we want the ID space to last 10 years without exhaustion.

seconds/day = 86,400
IDs over 10 yr = 106/s × 86,400 × 365 × 10 = 3.1536 × 1014 (≈ 315 trillion)
bits needed = log2(3.1536 × 1014) ≈ 48.2 bits # so < 49 bits carries 10 years of IDs

Fewer than 49 bits would carry the raw count. But we also want each ID to encode when it was made and which node made it (so nodes need not coordinate), which costs more bits. That is exactly what a 64-bit budget buys us with room to spare:

263 − 1 = 9,223,372,036,854,775,807 ≈ 9.2 × 1018 # max value of a signed 64-bit long (Long.MAX_VALUE)
264 = 18,446,744,073,709,551,616 ≈ 1.8 × 1019 # full unsigned range

Why 64 bits "fits a long"

  • A signed 64-bit integer — Java's long, a SQL BIGINT, a Go int64 — is 8 bytes, fits a CPU register, and compares/sorts with a single instruction.
  • It is half the storage of a 128-bit UUID (8 B vs. 16 B) in every row and every index entry — a large saving across billions of rows.
  • Keeping the top (sign) bit 0 means the value is always non-negative, so it round-trips cleanly through languages that only have signed integers (a classic source of bugs otherwise).
Takeaway

The count needs ~48 bits over a decade; a 64-bit integer gives us those plus enough headroom to also pack a timestamp and a machine id, all while fitting a BIGINT. That headroom is precisely what the Snowflake layout in §5 spends.

4. UUID / GUID

Before the bit-packed design, know the UUID well — it is the coordination-free baseline, and interviewers expect you to say when it is genuinely the right call.

What a UUID is

A UUID (Universally Unique IDentifier; Microsoft calls it a GUID) is a 128-bit value, conventionally written as 32 hexadecimal digits in five hyphen-separated groups — xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx, 36 characters including the four hyphens. A few bits are reserved to mark the version (how it was generated) and the variant.

v4 (random) vs. v1 (time + node)

AspectUUIDv4 (random)UUIDv1 (time-based)
Content122 random bits (6 bits fixed for version+variant)60-bit timestamp + 14-bit clock sequence + 48-bit node (often the MAC address)
Uniqueness basisAstronomically low collision probability from randomnessUniqueness from time + node identity
Sortable?No — random orderRoughly, but the timestamp bytes are shuffled, so it is not lexicographically sortable without rearranging
Leaks?NothingCan leak the MAC address and creation time

The random space is enormous, which is why collisions are ignored in practice:

UUIDv4 random space = 2122 ≈ 5.3 × 1036 # 128 bits minus 6 for version+variant
Pros
  • Generated locally, offline, zero coordination — perfect availability
  • No central service, no SPOF, no network hop
  • Trivial to implement in every language/library
Cons
  • 128 bits / 36 chars — 2× the storage of a 64-bit ID
  • v4 is not sortable and is index-hostile (random inserts)
  • v1 can leak MAC + time
When a UUID is genuinely fine

When you need IDs generated offline / client-side with no coordination at all, do not care about sort order, and can pay the 16 bytes — e.g. idempotency keys, request-trace IDs, or client-generated object keys. If you need compactness and time-ordering, reach for the 64-bit design next. (Newer time-ordered UUID formats such as v7 close much of the sortability gap while staying 128-bit — see §7's K-sortable note.)

5. Snowflake-Style 64-Bit IDs — the Key Part

The go-to answer, popularized by a well-known social platform's open-source "Snowflake" generator, is to pack meaning into a 64-bit integer: a timestamp so IDs are time-sortable, a machine id so nodes never coordinate, and a per-millisecond sequence so one node can generate many IDs in the same millisecond. Uniqueness is structural — two IDs differ because their (time, machine, sequence) triple differs.

The bit layout: 1 + 41 + 10 + 12 = 64

The four fields of a Snowflake-style 64-bit ID. The high bit is a fixed 0 so the value is always a non-negative signed long.

Verifying each field's range

# 41-bit timestamp in milliseconds — how many years?
241 ms = 2,199,023,255,552 ms
ms per year = 86,400,000 × 365 = 31,536,000,000 ms
range = 2,199,023,255,552 / 31,536,000,000 ≈ 69.7 years # from a CUSTOM epoch, not 1970

# 10-bit machine id
210 = 1,024 machines # e.g. 32 datacenters × 32 nodes

# 12-bit per-millisecond sequence
212 = 4,096 IDs per ms per machine

Throughput this implies

per node = 4,096 IDs/ms × 1,000 ms/s = 4,096,000 ≈ 4.096 M IDs/sec/node
whole fleet = 4.096 M × 1,024 nodes = 4,194,304,000 ≈ 4.19 billion IDs/sec # = 2²² × 1000

Against the 1 M IDs/sec peak from §3, one node alone (4.096 M/s) already covers the whole fleet's demand four times over — so the machine-id and sequence fields are generously sized.

Why a custom epoch?

The 41-bit timestamp counts milliseconds since a custom epoch (the day you launched the service), not the Unix 1970 epoch. Starting the clock at launch spends none of the 69.7-year budget on decades that already elapsed — you get the full ~69.7 years from launch. Because the timestamp occupies the high bits, IDs are naturally ordered by creation time.

Packing and unpacking — the bit math

To build the ID, shift each field into its position and OR them together. The timestamp goes above the machine and sequence fields, so it shifts left by 10 + 12 = 22; the machine id shifts left by 12; the sequence occupies the low 12 bits.

# build a 64-bit ID (elapsed = now_ms − CUSTOM_EPOCH_ms)
id = (elapsed << 22) | (machine_id << 12) | sequence
#         ^bits 62..22        ^bits 21..12      ^bits 11..0

# unpack it back out with shifts + masks
sequence   = id & 0xFFF            # low 12 bits  (0xFFF   = 4095 = 2^12 − 1)
machine_id = (id >> 12) & 0x3FF   # next 10 bits (0x3FF   = 1023 = 2^10 − 1)
elapsed    = id >> 22               # top 41 bits
timestamp  = elapsed + CUSTOM_EPOCH_ms

A worked example, computed by hand

Take elapsed = 10,000,000 ms (about 2.8 hours after the epoch), machine_id = 42, sequence = 7:

elapsed << 22 = 10,000,000 × 222 = 10,000,000 × 4,194,304 = 41,943,040,000,000
machine << 12 = 42 × 212 = 42 × 4,096 = 172,032
sequence = = 7
# fields occupy disjoint bit ranges, so OR is just addition here
id = 41,943,040,000,000 + 172,032 + 7 = 41,943,040,172,039

# unpack check:
41,943,040,172,039 & 0xFFF = 7 ✓ # 172,039 − 42×4096 = 7
(41,943,040,172,039 >> 12) & 0x3FF = 42 ✓
41,943,040,172,039 >> 22 = 10,000,000 ✓

41,943,040,172,039 < 263−1 (9.2×1018) ⇒ fits a signed long ✓
Pros
  • Coordination-free on the hot path — pure local bit math, no network
  • Time-sortable (timestamp is the high bits)
  • Compact: fits a 64-bit BIGINT / long
Cons
  • Depends on the wall clock → clock-skew hazards (§6)
  • Needs unique machine-id assignment (§6)
  • Leaks approximate creation time and node — not unguessable

6. Clock Skew & the Hard Problems

Because the timestamp drives both ordering and uniqueness, time is where a Snowflake design gets subtle. Three problems come up, and all three are common probes.

The clock moving backwards

If a node's wall clock jumps backwards — an NTP correction, an unsmeared leap second, a VM migration — then elapsed can be smaller than a timestamp already used, and the generator could re-issue an ID it has handed out. That breaks uniqueness. The generator must track the last timestamp it emitted and react when now < last_timestamp:

# guard against a backward clock
if now < last_ts:
    drift = last_ts - now
    if drift <= MAX_TOLERABLE:
        wait_until(last_ts)      # small skew: block until the clock catches up
    else:
        raise ClockMovedBackwards   # large skew: refuse rather than risk a dup
Refuse, wait, or borrow

Three standard responses to a backward clock: (1) wait — block until the clock reaches last_ts again (fine for a few ms of skew); (2) refuse — throw an error and let the caller retry or route to another node (safe for large jumps); (3) borrow bits — some designs reserve extra sequence/"generation" bits so a small backward step can advance a counter instead of the clock. Keep clocks tight with NTP, and use a monotonic clock for elapsed-time math so it never runs backwards in the first place.

Sequence overflow within a millisecond

If one node is asked for more than 4,096 IDs in the same millisecond, the 12-bit sequence overflows. The fix is to spin to the next millisecond: block until the clock ticks over, then reset the sequence to 0.

# same millisecond: bump sequence; on overflow, wait for the next ms
if now == last_ts:
    sequence = (sequence + 1) & 0xFFF   # wrap within 0..4095
    if sequence == 0:                # overflowed 4096 → this ms is full
        now = wait_next_ms(last_ts)     # busy-wait until now > last_ts
else:
    sequence = 0                     # new millisecond → fresh sequence
last_ts = now

Since 4,096 IDs/ms is 4.096 M/s, overflow only happens under extreme single-node load — and even then it costs at most a sub-millisecond wait, not a collision.

Assigning unique machine ids

Every generator needs a distinct 10-bit machine id (0–1023); two nodes sharing one could produce identical IDs in the same millisecond. Options:

  • Static config: bake the id into each node's deployment config. Simple, but error-prone to keep unique as the fleet changes.
  • Coordination service: a strongly-consistent store such as ZooKeeper or etcd leases a unique id to each node on startup (e.g. an ephemeral sequential znode), reclaiming it when the node leaves. This is the common robust choice.
  • Derived: map from something already unique (host ordinal in an orchestrator, or a slice of the IP) — cheap, as long as it stays within 1024 and never repeats.
The coordinator hands each node a distinct machine id once, at startup (purple, fanning to all three). After that, every node generates IDs from its own clock + machine id + sequence with zero coordination (green) — so there is no central bottleneck or SPOF on the write path.

7. Alternatives

Snowflake is the default, but three families of alternatives come up — know when each wins.

Ticket server (DB-backed, HA by odd/even)

A ticket server is a tiny dedicated database whose only job is to hand out increasing integers via an atomic operation (e.g. REPLACE INTO ... ; SELECT LAST_INSERT_ID()). It gives clean, compact, sortable IDs — but a single ticket DB is a SPOF. The classic HA trick (from a well-known photo-sharing site's design) runs two ticket servers with staggered auto-increment so they never collide:

# two servers, stepped so their outputs never overlap
server A: auto_increment_offset = 1, auto_increment_increment = 2 → 1, 3, 5, 7, … # odd
server B: auto_increment_offset = 2, auto_increment_increment = 2 → 2, 4, 6, 8, … # even

Either server can die and the other keeps issuing IDs; the odd/even split guarantees no duplicate. It scales to two (or, with a larger step, N) servers, not to hundreds — so it fits moderate scale where a compact monotonic id is wanted without full Snowflake machinery.

Database segment / range allocation

Instead of one round-trip to the DB per ID (a ticket per ID), hand out a whole block at a time. Each app server asks the DB for a segment — say IDs [1..1000] — increments locally with no coordination, and only returns to the DB when its block is nearly exhausted to grab the next one.

DB coordination rate = 1 round-trip per block, not per ID
with block = 1,000 ⇒ 1000× fewer DB writes than a per-ID ticket

This keeps the compactness of a counter while slashing coordination — the trade-off is that IDs are only roughly ordered across servers (each burns through its own block), and a crashing server loses the rest of its unused block (a harmless gap).

K-sortable IDs — ULID / KSUID (and UUIDv7)

If you want UUID-style local generation and sortability, use a K-sortable ID: put a time prefix in the high bits so the value sorts (roughly) by creation time, then fill the rest with randomness for uniqueness. ULID is the common example:

ULID = 128 bits = 48-bit timestamp (ms) + 80-bit randomness
48-bit ms range = 248 / 31,536,000,000 ≈ 8,900 years # timestamp won't overflow for millennia
# encoded as 26 Crockford-base32 chars; KSUID and UUIDv7 use the same time-prefix idea

Why a time prefix helps a B-tree index

This is the practical payoff and a key interview point. A B-tree index keeps keys sorted, so monotonically increasing keys always insert at the right edge of the tree — the current rightmost leaf stays hot in cache, pages fill sequentially, and there are few page splits. A random key (UUIDv4) inserts all over the tree: every insert may touch a cold page, causing random I/O, page splits, and fragmentation. So a time-prefixed ID gives you the write-locality of an auto-increment key without a central counter.

The core idea

Sortable = time in the high bits. That single property gives you both a usable rough timeline and friendly, append-mostly index inserts. It is exactly why Snowflake, ULID, KSUID, and UUIDv7 all lead with a timestamp.

The tensions to name out loud

  • Sortable vs. unguessable. A time-prefixed ID reveals roughly when it was made and lets an attacker estimate volume or enumerate neighbors; a random ID hides that but cannot sort. You usually pick one. If you need both, keep an internal sortable ID and expose a separate opaque/encrypted one.
  • 64-bit Snowflake vs. 128-bit UUID. Snowflake is half the size and sortable but depends on a clock and a machine id; UUIDv4 is bigger and unsortable but utterly coordination-free. Choose by whether compactness+ordering or pure offline simplicity matters more.
  • Coordination-free vs. central. Central allocators (auto-increment, ticket server) give strict ordering but bottleneck and can SPOF; coordination-free schemes (Snowflake, UUID) scale out but give only rough ordering.
  • Leaking machine / time info. Snowflake and v1 UUIDs embed node and time — convenient for debugging, a mild information leak for security.

9. Interview Framing

How to drive the conversation

  1. Clarify (1–2 min): strictly monotonic or roughly ordered? sortable or unguessable? single region or multi-DC? peak IDs/sec? must fit 64 bits? (§1)
  2. Reject the naïve options and say why: single counter = SPOF+bottleneck; UUIDv4 = big, random, index-hostile (§2).
  3. Size the bit budget — count of IDs over the lifetime → ~48 bits, so 64 bits fits with room for time+machine fields (§3).
  4. Present the Snowflake layout (1+41+10+12), verify each field's range, show the pack/unpack shifts (§5).
  5. Cover the hard parts: backward clock, sequence overflow, machine-id assignment (§6); then trade-offs and alternatives (§7–§8).

What interviewers probe (with one-liners)

Q: Why a 64-bit ID rather than a 128-bit UUID?
64 bits fits a BIGINT/long — 8 bytes, register-native, half the storage and index size of a 128-bit UUID — and a Snowflake layout still packs a timestamp (sortable) plus a machine id (coordination-free). The bit budget is ample: ~48 bits carries a decade of IDs, leaving room for the time and machine fields. Use 128-bit only when you truly need offline generation with no coordination and don't care about size.

Q: How do you handle the clock moving backwards?
Track the last emitted timestamp. If now < last_ts by a small amount, block until the clock catches up; if the jump is large, refuse and let the caller retry elsewhere. Keep clocks tight with NTP and use a monotonic clock for elapsed math so it can't run backwards. Never emit an ID for a time you've already used — that's the only way to break uniqueness.

Q: How are machine ids assigned?
Each node needs a distinct 10-bit id (0–1023). Lease them from a strongly-consistent coordinator like ZooKeeper or etcd on startup (ephemeral sequential nodes), or derive from a stable host ordinal / IP, or in the simplest case bake it into config. The cap is 1024 nodes — plenty, and expandable by rebalancing bits if needed.

Q: Why does a time-ordered ID help a B-tree index?
Monotonic keys always insert at the rightmost leaf, so pages fill sequentially, the hot page stays cached, and page splits are rare. A random key (UUIDv4) scatters inserts across the whole tree — cold-page I/O, splits, fragmentation. Time-in-the-high-bits gives auto-increment-like write locality without a central counter.

Q: UUIDv4 or Snowflake — how do you choose?
UUIDv4 if IDs must be generated offline/client-side with zero coordination and ordering doesn't matter (e.g. idempotency keys). Snowflake if you want compact, sortable, high-throughput IDs across a fleet and can run a clock + machine-id assignment. If you need offline generation and sortability, a K-sortable 128–160-bit ID (ULID/KSUID/UUIDv7) splits the difference.

Q: Where's the single point of failure?
On the hot path, nowhere — each node generates locally from its own clock, machine id, and sequence, so losing a node loses only that node's throughput, and there's no central allocator capping writes. The only shared dependency is the machine-id coordinator, and it's touched once at startup (not per ID), so it can be briefly unavailable without stopping generation.

One-line summary

A scalable unique ID generator packs a custom-epoch millisecond timestamp, a machine id, and a per-ms sequence into a 64-bit integer (1+41+10+12): unique by construction, roughly time-sortable, compact as a BIGINT, and coordination-free on the hot path — with clock-skew guards, sequence-overflow spin, and coordinator-assigned machine ids as the details that separate a senior answer from a naïve one.
