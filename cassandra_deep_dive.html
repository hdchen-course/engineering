Apache Cassandra Deep Dive

A wide-column, masterless, AP database. This guide covers the ring and consistent hashing, query-driven data modeling, the LSM write/read path, tunable consistency, multi-DC replication, and the anti-patterns interviewers probe. Facts reflect Cassandra 4.x / 5.0 (2024–2026).

What Cassandra Is (and Isn't)

Apache Cassandra is a wide-column, masterless (peer-to-peer), horizontally scalable distributed database. It descends from two lineages: the data model of Google Bigtable (a sparse, wide-column map) and the distribution model of Amazon Dynamo (consistent hashing, replication, tunable eventual consistency). Every node is identical — there is no primary, no config server, no single point of failure. It is designed to run across many commodity nodes and multiple data centers.

DimensionCassandra's choiceConsequence
CAP positionAP — Available + Partition-tolerant, tunable toward CStays writable during network partitions; consistency is a per-query knob, not a fixed guarantee
TopologyMasterless ring, every node a peerNo failover election for writes; any node can coordinate any request
Storage engineLog-structured merge tree (LSM)Writes are append-only and extremely fast; reads may touch multiple SSTables
ScalingLinear horizontal scale-outAdd nodes to add throughput and capacity; no sharding logic in the app
Conflict resolutionLast-write-wins by cell timestampSimple and lock-free, but clock skew and blind updates can silently lose data
One-line pitch: Cassandra trades joins, ad-hoc queries, and strong-by-default consistency for predictable low-latency writes at massive scale, no single point of failure, and painless multi-region operation. If you need those trades reversed, you want a different database.

The Ring & Consistent Hashing

Cassandra maps every node onto a token ring. A partitioner hashes the partition key of each row to a token; the row lives on the node that owns that token range. The default partitioner is Murmur3Partitioner, which produces 64-bit tokens over the range -2^63 … 2^63-1.

Fig 1: A key hashes to a token; the owning node plus the next N-1 nodes clockwise form the replica set.
  • Ownership: the first node clockwise from a token owns it. With replication factor (RF) = N, the row is also stored on the next N-1 nodes walking clockwise, subject to the replica-placement strategy (e.g. skip nodes in the same rack).
  • Consistent hashing means adding or removing a node only reshuffles the token ranges adjacent to it — not the whole dataset. This is what makes elastic scaling cheap.
  • Any node can be the coordinator for a request. A client connects to some node; that node hashes the key, forwards to the replicas, gathers responses, and enforces the consistency level. Drivers are token-aware and usually pick a replica as coordinator to save a hop.

Virtual Nodes (vnodes)

Why vnodes fixed the "one token per node" problem▶

Originally each node owned exactly one contiguous token range. That made ring balance fragile: adding a node only split one neighbor's range, and rebuilding a failed node streamed from just one or two peers. Virtual nodes give each physical node many small, non-contiguous token ranges instead.

  • Configured by num_tokens in cassandra.yaml. Cassandra 1.2–3.x defaulted to 256; Cassandra 4.0 changed the default to 16, paired with allocate_tokens_for_local_replication_factor for even, RF-aware placement.
  • Fewer tokens (e.g. 8–16) is now preferred: 256 vnodes hurt availability (any two nodes down likely share a range) and made repair and token allocation heavier. 16 balances distribution against those costs.
  • Rebuild parallelism: a replacement node streams its many ranges from many peers at once, so recovery is far faster than the single-token era.
  • Heterogeneous hardware: a bigger node can be given more tokens to own a larger slice of the ring.
Interview note: "256 vnodes" is stale advice. Modern guidance (4.0+) is a small num_tokens (8–16) with the token allocation algorithm enabled. Be ready to explain the availability trade-off: more vnodes = more even data, but higher probability that any pair of node failures loses a quorum for some range.

Gossip, Snitches & Failure Detection

How peers agree on cluster state without a coordinator▶
  • Gossip: once per second each node exchanges state (up/down, load, schema version, tokens) with a few random peers. State converges epidemically across the cluster in O(log N) rounds — no central membership service.
  • Phi-accrual failure detector: rather than a binary up/down, each node computes a suspicion level (phi) from the recent gossip inter-arrival history, so flaky networks don't cause instant false failures.
  • Snitch: tells Cassandra the topology — which rack and data center each node is in — so replicas are spread across failure domains and reads prefer local nodes. GossipingPropertyFileSnitch is the standard production choice (each node declares its own DC/rack, propagated via gossip). Cloud snitches (e.g. Ec2Snitch) infer DC/rack from instance metadata.
  • Seeds are well-known bootstrap nodes a new node contacts first to join the gossip mesh; they are not masters and hold no special data.

Query-Driven Modeling — The Core Mindset

Unlearn the relational reflex. In an RDBMS you model the entities (normalize), then write whatever queries you need. In Cassandra you do the opposite: start from the queries your application must serve, then design one table per query pattern so every read is a single-partition lookup. Cassandra has no joins, no ad-hoc WHERE, and no cross-partition aggregation at scale. The schema is a materialized answer to a known question.
  1. Identify the access patterns — the exact reads the app issues ("show a user's messages in a room, newest first").
  2. Design one table per query — duplicate data across tables as needed. Denormalization is expected, not a smell.
  3. Choose the partition key so each query hits exactly one partition, and partitions stay bounded (not unbounded-growth).
  4. Choose clustering columns to give the on-disk sort order the query wants.
Mantra: "Writes are cheap, disk is cheap, joins don't exist." Optimize for reads by writing the same fact into multiple denormalized tables at write time.

Partition Key vs Clustering Columns

A CQL PRIMARY KEY has two parts. Understanding the split is the single most important modeling skill.

PartRoleDetermines
Partition key (first component; parenthesized if compound)Hashed to a token → picks the node(s)Where the data lives. All rows with the same partition key are stored together on the same replicas.
Clustering columns (the rest)Sort rows within a partition on diskOrder of rows in the partition, and which range slices are efficient.
 
PRIMARY KEY ((room_id), bucket, sent_at, message_id)
--            ^^^^^^^^^  ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
--          partition key       clustering columns
--          (picks node)     (sort order within partition)

-- Compound partition key (both hashed together as the token):
PRIMARY KEY ((room_id, bucket), sent_at, message_id)
  • Rows in a partition are physically sorted by clustering columns, so ORDER BY and range slices (sent_at > ?) are free — no sort step.
  • You can only filter on clustering columns following the leftmost-prefix rule (like a composite index): you must restrict earlier clustering columns before ranging on a later one.
  • The partition key must be fully specified with equality (= or IN) for an efficient query. You cannot range-scan across partitions without ALLOW FILTERING (a red flag — see Pitfalls).

Worked Example: Chat Messages

One data model, three query patterns, three tables▶

Access patterns: (1) fetch the latest messages in a room, newest first; (2) look up a single message by id; (3) list the rooms a user belongs to. We build a table for each.

-- Keyspace: NetworkTopologyStrategy pins replicas per data center.
CREATE KEYSPACE chat
  WITH replication = {
    'class': 'NetworkTopologyStrategy',
    'us_east': 3,
    'eu_west': 3
  };

-- Query 1: messages in a room, newest first, time-bucketed to bound partition size.
CREATE TABLE chat.messages_by_room (
  room_id     uuid,
  bucket      date,          -- e.g. one partition per room per day
  sent_at     timestamp,
  message_id  timeuuid,
  sender_id   uuid,
  body        text,
  PRIMARY KEY ((room_id, bucket), sent_at, message_id)
) WITH CLUSTERING ORDER BY (sent_at DESC, message_id DESC);

-- Read it (single partition, already sorted newest-first):
SELECT sender_id, body, sent_at
FROM chat.messages_by_room
WHERE room_id = ? AND bucket = ?
LIMIT 50;

-- Query 2: fetch one message by id (separate lookup table).
CREATE TABLE chat.message_by_id (
  message_id  timeuuid PRIMARY KEY,
  room_id     uuid,
  sender_id   uuid,
  body        text,
  sent_at     timestamp
);

-- Query 3: rooms a user is in.
CREATE TABLE chat.rooms_by_user (
  user_id  uuid,
  room_id  uuid,
  joined_at timestamp,
  PRIMARY KEY ((user_id), room_id)
);
Why the bucket? A busy room could accumulate millions of messages. A partition that grows without bound becomes a "large partition" — slow reads, GC pressure, and eventually a hard failure. Adding a time bucket (day/week) to the partition key caps each partition's size. The application reads recent buckets and pages backward. This "time bucketing" is one of the most common Cassandra modeling techniques.

Writing all three at once: the app issues three INSERTs (optionally in a LOGGED BATCH for atomicity across tables). There is no join to reassemble later — each table already answers its query directly.

No Joins, No Referential Integrity

⚠ What Cassandra deliberately does not do
  • No joins. You denormalize and duplicate. If a user renames themselves, you update every table that embedded the old name (or store only ids and accept a second lookup).
  • No foreign keys / referential integrity. Consistency across tables is the application's job.
  • No ad-hoc aggregation at scale. GROUP BY/aggregates only work efficiently within a single partition. Cluster-wide analytics belong in Spark, a warehouse, or a purpose-built OLAP store.
  • No multi-partition transactions. A LOGGED BATCH gives atomicity (all-or-nothing) but not isolation, and it is not a distributed transaction — use it for keeping denormalized copies in sync, not for cross-entity invariants.
  • Limited uniqueness. The only free uniqueness is the primary key. Enforcing "unique email" needs a lightweight transaction (IF NOT EXISTS, Paxos) — slow and to be used sparingly.

Wide-Column Storage Shape

How a CQL row maps to the underlying partition▶

Under the hood a partition is a sorted map: partition key → (clustering key → (column → cell)). Each cell carries a value plus a write timestamp and optional TTL. Columns absent in a row simply store nothing — the model is sparse, so wide, mostly-empty rows cost nothing for the missing cells. This is the "wide-column" shape: a single partition can hold from one row up to (bounded) millions of clustered rows, each a different set of cells.

  • Collections (set, list, map) and UDTs let you nest structure inside a row, but each collection is read/written whole and should stay small (thousands of elements, not millions).
  • Counters are a special column type with their own replication rules; a table is either all-counter or no-counter.
  • Static columns are shared across all rows of a partition — handy for per-partition metadata.

The Write Path (LSM Tree)

Cassandra is a log-structured merge-tree store. Writes never do a read-modify-write on disk and never seek — they are pure appends, which is why write throughput is so high and so predictable.

Fig 2: Every write appends to the commit log and updates the in-memory memtable; memtables later flush to immutable SSTables.
  1. Commit log append. The mutation is appended to the on-disk commit log for durability (crash replay). By default the commit log is periodic (fsync every commitlog_sync_period, default ~10s); batch/group modes fsync before ack for stronger durability at higher latency.
  2. Memtable update. The mutation is applied to an in-memory memtable, sorted by clustering key. Reads see it immediately.
  3. Ack. Once enough replicas have done the above to satisfy the consistency level, the coordinator acks the client. There is no read before write for normal inserts/updates — an update is just a new timestamped cell.
  4. Flush. When a memtable fills (heap thresholds) or on demand, it is flushed to a new immutable SSTable on disk, and the corresponding commit log segments become eligible for recycling.
Why writes are fast: no disk seek, no read-modify-write, no in-place mutation, no uniqueness check (for plain writes). An UPDATE and an INSERT are the same operation — an "upsert" of timestamped cells. This also means a blind UPDATE to a non-existent row silently creates it.

SSTable Anatomy & the Read Path

Reads must merge many immutable files — the helpers that keep it fast▶

Because SSTables are immutable, a single partition's data (and its updates and deletes) can be spread across the memtable and multiple SSTables. A read must find and merge all of them, keeping the newest cell per column by timestamp. Several structures make this cheap:

  • Bloom filter (per SSTable, in RAM): a probabilistic test for "might this SSTable contain this partition key?" A negative answer lets the reader skip the SSTable entirely with zero disk I/O. False positives are possible, false negatives are not.
  • Partition index + summary: map a partition key to its byte offset in Data.db; the summary is a sampled, in-memory shortcut into the index.
  • Key cache / row cache / chunk cache: cache hot key locations, whole rows, and decompressed file chunks respectively.
  • Compression offsets: data is compressed in blocks; an offset map allows reading just the needed block.

Read steps: (1) check memtables; (2) for each SSTable, consult its bloom filter, skip on a miss; (3) for candidates, use the index to seek the partition and read the needed rows; (4) merge all fragments by timestamp, applying tombstones; (5) return the reconciled result. The more SSTables a partition is spread across, the more work a read does — which is exactly what compaction fights.

Cassandra 5.0 storage upgrades: a new trie-indexed SSTable format (BTI, selectable via sstable_format) uses memory-efficient tries for partition/row indexing, and trie-based memtables reduce heap overhead. These are additive improvements to the same LSM model, not a redesign.

Compaction Strategies

Compaction merges SSTables in the background: it collapses multiple versions of a cell to the newest, drops data shadowed by tombstones (after gc_grace_seconds), and reduces the number of files a read must touch. Choosing the strategy to match the workload is a classic tuning question.

DTCS is deprecated. The old DateTieredCompactionStrategy was deprecated and superseded by TWCS; don't propose DTCS in 2026. For time-series, the answer is TWCS (or UCS configured for it). Note STCS remains the out-of-the-box default table strategy; UCS is available in 5.0 and is the strategic direction.

Read vs Write Amplification — the LSM Trade

⚖ The lever every compaction choice pulls
  • Write amplification: a byte written once is rewritten several times as compaction merges files. LCS has the most; STCS/TWCS the least.
  • Read amplification: a read may touch many SSTables. LCS minimizes it (few files per partition); STCS can be worse over time.
  • Space amplification: obsolete/overwritten data and tombstones occupy disk until compacted away.

The interview-ready summary: LSM databases turn random write I/O into sequential appends (great for writes) at the cost of reads having to merge across files and background compaction rewriting data. The compaction strategy is how you choose where on that read/write/space triangle to sit.

Tunable Consistency

Cassandra does not pick consistency for you globally. Every read and write specifies a consistency level (CL) — how many replicas must respond before the operation is considered successful. This is the tunable dial between latency/availability and consistency.

Consistency levelReplicas requiredTypical use
ONE / TWO / THREE1 / 2 / 3 replicas respondLowest latency; weakest guarantee. ONE read may return stale data.
LOCAL_ONE1 replica in the local DCFast reads that must not cross DCs.
QUORUMmajority of all replicas across all DCsStrong consistency single-DC; cross-DC latency in multi-DC.
LOCAL_QUORUM multi-DC go-tomajority of replicas in the local DCStrong-enough consistency without paying cross-DC round trips. The default choice for multi-region apps.
EACH_QUORUMa quorum in every DCWrites that must be durable in all regions (rare; high latency).

ANY (writes only)at least a hint is storedMaximum availability; a write can succeed with only a hinted handoff and no live replica.

Quorum for N replicas is floor(N/2) + 1. For RF=3, QUORUM = 2. For RF=5, QUORUM = 3.

The R + W > N Rule

When do reads see the latest write? Strong consistency without a leader▶

Let N = replication factor, W = write consistency level, R = read consistency level. If R + W > N, the read replica set and the write replica set are guaranteed to overlap in at least one replica — so at least one node in the read holds the latest write, and the coordinator reconciles the responses by cell timestamp and returns that fresh value. (Read repair additionally writes the fresh value back to any stale replicas, but is not required for this read to be fresh.)

NWRR+W>N?Guarantee
3QUORUM (2)QUORUM (2)2+2=4 > 3Strong — reads see the latest committed write.
3ALL (3)ONE (1)3+1=4 > 3Strong reads, but writes fail if any replica is down.
3ONE (1)ONE (1)1+1=2 ≤ 3Eventual only — a read may miss a recent write.
3LOCAL_QUORUM (2)LOCAL_QUORUM (2)within a DC: 2+2 > 3Strong within the local DC; other DCs converge asynchronously.
Interview move: The most common production setting for a globally-distributed app is RF=3 per DC with LOCAL_QUORUM reads and writes. That satisfies R+W>N inside each DC (2+2>3) for low-latency strong-enough consistency, while cross-DC replication stays asynchronous. Reach for EACH_QUORUM/QUORUM only when you truly need cross-region read-after-write.
Caveat — no isolation. R+W>N gives you freshness, not transactional isolation. Concurrent writers still resolve by last-write-wins timestamp, so lost updates are possible. For compare-and-set semantics you need lightweight transactions (Paxos), covered below.

Hinted Handoff

Keeping writes flowing when a replica is briefly down▶
  • If a replica is down when a write arrives, the coordinator stores a hint — a saved copy of the mutation destined for the dead replica.
  • When the replica comes back within the hint window (max_hint_window_in_ms, default 3 hours), the coordinator replays the hint to it, restoring the missed write.
  • Hints improve availability and reduce the repair burden after short outages. They do not count toward the write's consistency level (except that CL ANY can be satisfied by a hint alone).
  • If a node is down longer than the hint window, hints stop being stored for it and you must rely on anti-entropy repair to restore consistency — this is why replacing a long-dead node without repair risks resurrecting deleted data.

Read Repair & Anti-Entropy Repair

Two mechanisms that converge divergent replicas▶

Read repair (during reads)

  • On a read at CL ≥ QUORUM, the coordinator asks one replica for full data and the others for a lightweight digest. If digests disagree, it detects divergence, fetches the conflicting data, reconciles by timestamp, returns the correct answer to the client, and writes the fresh version back to the stale replicas — blocking read repair.
  • Configured per table via the read_repair option (BLOCKING default, or NONE). Note: the old probabilistic read_repair_chance / dclocal_read_repair_chance table options were removed in Cassandra 4.0 — don't cite them.

Anti-entropy repair (background / scheduled)

  • nodetool repair compares data between replicas using Merkle trees (hash trees over token ranges) to find differing ranges cheaply, then streams only the differences.
  • This is the authoritative way to make replicas fully consistent, and it is operationally mandatory: run repair on every node at least once per gc_grace_seconds (default 10 days) to avoid zombie data — deleted rows reappearing because a tombstone was purged before all replicas saw it.
  • Tools like Cassandra Reaper schedule and throttle repairs so they don't overwhelm the cluster. Cassandra 4.0+ also supports incremental repair that tracks already-repaired data.
Convergence trio: hinted handoff (short outages), read repair (on the read path, for hot data), and anti-entropy repair (the backstop for cold data and long outages) together make an eventually-consistent system converge. A common probe is how deleted data could "come back" — the answer is a missed tombstone plus skipped repair.

Lightweight Transactions (LWT)

Compare-and-set via Paxos — powerful but expensive▶

When you truly need linearizable compare-and-set (e.g. "register this username only if free"), Cassandra offers LWT using a Paxos consensus round scoped to a single partition:

INSERT INTO users (email, user_id)
VALUES ('a@example.com', ?)
IF NOT EXISTS;                       -- succeeds only if the row doesn't exist

UPDATE accounts SET balance = ?
WHERE id = ?
IF balance = ?;                      -- conditional update (CAS)
  • Uses SERIAL / LOCAL_SERIAL consistency for the Paxos ballot; LOCAL_SERIAL keeps it within one DC.
  • Costs roughly 4 round trips instead of 1 — often an order of magnitude slower than a normal write.
  • Only atomic within a single partition; not a general multi-row transaction. Use sparingly for genuine uniqueness/CAS needs, never on the hot write path in bulk.

Multi-DC Replication

Why Cassandra is a natural fit for global, multi-region deployments▶
  • NetworkTopologyStrategy lets you set an independent replication factor per data center, e.g. {'us_east': 3, 'eu_west': 3}. Every DC holds a full, independent set of replicas.
  • Cross-DC replication is asynchronous by default — a write acked at LOCAL_QUORUM in one DC propagates to other DCs in the background, so a regional link problem doesn't stall local writes.
  • Reads and writes use LOCAL_* consistency to stay within the caller's region, keeping latency low; the snitch ensures each request prefers local replicas.
  • Common patterns: active-active (every region serves reads and writes to local users), geo-locality / data residency (keep certain data in-region), and adding an analytics DC that never serves user traffic.
Contrast with leader-based systems: because there is no primary, there is no cross-region leader election or failover on the write path. A whole DC can go offline and the others keep serving — this operational simplicity for multi-region is one of Cassandra's strongest selling points.

Tombstones — Deletes Are Writes

How deletion works in an append-only store, and why it bites▶

Because SSTables are immutable, a delete cannot erase data in place. Instead it writes a tombstone — a special marker with a timestamp that says "this cell/row/range is deleted." On read, the tombstone shadows any older data. The data is only physically removed later, during compaction, after gc_grace_seconds.

  • gc_grace_seconds (default 864000 = 10 days): tombstones must survive at least this long so that every replica learns of the delete via repair before the tombstone is purged. Purging too early causes zombie data (deleted rows resurrecting from a replica that never saw the delete).
  • Read amplification from tombstones: a query that scans a partition full of tombstones has to read and merge them all. Cassandra warns at tombstone_warn_threshold (default 1000 per read) and aborts the query at tombstone_failure_threshold (default 100000).
  • TTL is a tombstone. Data written with a TTL becomes a tombstone when it expires — mass expirations create tombstone storms.
Classic anti-pattern: a queue/ring-buffer table where rows are inserted and deleted constantly. Reads at the "head" scan across thousands of tombstones from already-deleted rows and get slow or fail. Fixes: model with TWCS and TTL so whole SSTables expire, bucket by time, or avoid the queue-on-Cassandra pattern entirely.

Secondary Index Pitfalls

Why "just add an index" is usually the wrong instinct▶

Cassandra indexes are local to each node (each node indexes only its own data). Querying a secondary index without also restricting the partition key forces the coordinator to scatter-gather across every node in the ring — an anti-pattern that does not scale.

Preferred solution: instead of indexing, model another table keyed by the column you need to query (a "query table" / manual materialized view). If you must index, use SAI (5.0) and still constrain by partition key where possible. Native materialized views exist but have long carried correctness caveats and are treated as experimental — prefer application-maintained query tables.

Large Partitions & Hotspots

⚠ The two failure modes of a bad partition key
  • Unbounded partitions: a partition key like country or a single hot room_id can grow to gigabytes. Large partitions cause slow reads, long compactions, GC pauses, and eventually node instability. Fix: add a bucketing component (time bucket, hash bucket) to the partition key to cap size.
  • Hotspots / hot partitions: if traffic concentrates on one partition key (a celebrity user, a "global" counter), one replica set gets overloaded while the ring sits idle — you've re-created a single point of load on a distributed system. Fix: spread the key (sharding a hot partition into key + shard_no), or cache in front.
  • Low-cardinality partition keys waste the ring: with only a handful of distinct keys, data can't spread across nodes.

When to Use Cassandra — and When to Avoid It

Reach for Cassandra when…
  • Very high, sustained write throughput (telemetry, event logs, IoT, time-series, feeds, messaging).
  • Availability > strict consistency — the app can tolerate tunable/eventual consistency and must stay up during failures (AP).
  • Multi-region / active-active with local low-latency reads and writes and no cross-region write leader.
  • Predictable scale-out — capacity and throughput grow near-linearly by adding nodes.
  • Known, bounded query patterns that can be satisfied by single-partition lookups.
Avoid Cassandra when…
  • You need ad-hoc queries, joins, or cluster-wide aggregation — use an RDBMS or a warehouse.
  • You need strong ACID multi-row transactions or complex referential integrity.
  • The workload is read-heavy with unpredictable access paths that can't be modeled as query tables.
  • Data volume is small — the operational overhead isn't justified; a single Postgres/MySQL is simpler.
  • You need heavy full-text search or true OLAP — use OpenSearch/Elasticsearch or ClickHouse/BigQuery.

Common Interview Q&A

Q: Walk me through what happens on a write at LOCAL_QUORUM, RF=3.▶

A: The client's driver (token-aware) sends the write to a coordinator, ideally a replica for that key. The coordinator hashes the partition key to a token, finds the 3 replicas in the local DC, and forwards the mutation to all of them in parallel. Each replica appends to its commit log and updates its memtable, then acks. Once 2 of 3 (local quorum) ack, the coordinator returns success to the client. If a replica is down, the coordinator stores a hint for it. Cross-DC replicas receive the write asynchronously. No read occurs; the write is an upsert of timestamped cells.

Q: A user deleted a row two weeks ago but it reappeared. Why?▶

A: Zombie data. The delete wrote a tombstone that lived for gc_grace_seconds (10 days) and was then purged by compaction. But one replica was down/partitioned during the delete and never received the tombstone, and no anti-entropy repair ran within the grace window. After purge, that replica still holds the old (undeleted) data with an older-but-now-unshadowed timestamp, and read repair/streaming propagates it back. Fix: run nodetool repair on every node at least once per gc_grace_seconds (use Reaper), and never resurrect a long-dead node without repairing.

Q: How do you make reads see the latest write?▶

A: Choose consistency levels so R + W > N. With RF=3, using QUORUM (or LOCAL_QUORUM within a DC) for both reads and writes gives 2+2 > 3, so the read and write replica sets overlap and the coordinator reconciles the responses by timestamp, returning the freshest value (blocking read repair then writes it back to stale replicas). This gives read-your-writes freshness — but not isolation; concurrent writers still resolve by last-write-wins, so use LWT for compare-and-set.

Q: Design a table for "the 50 most recent orders for a customer."▶
CREATE TABLE orders_by_customer (
  customer_id  uuid,
  order_ts     timestamp,
  order_id     timeuuid,
  amount       decimal,
  status       text,
  PRIMARY KEY ((customer_id), order_ts, order_id)
) WITH CLUSTERING ORDER BY (order_ts DESC, order_id DESC);

SELECT * FROM orders_by_customer WHERE customer_id = ? LIMIT 50;

A: Partition by customer_id so one customer's orders live together; cluster by order_ts DESC so the newest sort first and the read is a single-partition slice, no filtering. If a customer could have millions of orders, add a time bucket to the partition key (e.g. (customer_id, year_month)) to bound partition size, and page across buckets.

Q: STCS vs LCS vs TWCS — which and why?▶

A: STCS (default) for write-heavy/general workloads — low write amplification, but reads can touch many SSTables. LCS for read-heavy or update-heavy tables where you want few SSTables per partition and predictable read latency — at the cost of high write amplification. TWCS for time-series/append-only-with-TTL, where whole time-windowed SSTables expire and drop cheaply, avoiding tombstone build-up. In 5.0, UCS unifies these behaviors under one tunable strategy. (Never propose DTCS — it was replaced by TWCS.)

Q: Why not just add a secondary index to query by email?▶

A: Secondary indexes are local per node, so a query on a high-cardinality column like email without a partition-key restriction scatter-gathers across the whole ring — it doesn't scale and latency is unpredictable. The idiomatic fix is a second query table keyed by email (PRIMARY KEY (email)) that the app writes alongside the main table. If you genuinely need indexing, Cassandra 5.0's SAI is the modern, lower-overhead option, but a well-modeled query table is still preferred, and uniqueness ("email not already taken") requires an LWT.

Q: How does Cassandra achieve no single point of failure?▶

A: Every node is a peer (masterless). Membership and state spread via gossip; any node can coordinate any request; data is replicated to RF nodes chosen by consistent hashing and the snitch's topology. There's no leader to elect and no config master to lose. A node — or an entire data center — can fail while the rest keep serving reads and writes (at the chosen consistency level), and hinted handoff plus repair heal the gap when it returns.

Rapid-Fire Facts (2024–2026)

  • Default partitioner Murmur3Partitioner, 64-bit token range -2^63 … 2^63-1.
  • num_tokens default is 16 since Cassandra 4.0 (was 256), with RF-aware token allocation.
  • gc_grace_seconds default 864000 (10 days); tombstone warn/fail thresholds 1000 / 100000 per read.
  • Hint window max_hint_window_in_ms default 3 hours.
  • Quorum = floor(RF/2)+1; strong consistency needs R+W>RF.
  • Read repair options: read_repair = BLOCKING (default) or NONE; probabilistic read_repair_chance removed in 4.0.
  • Compaction: STCS (default), LCS, TWCS, and UCS (new in 5.0); DTCS deprecated (superseded by TWCS).
  • Cassandra 5.0 (GA 2024) added Storage-Attached Indexes (SAI), trie memtables/BTI SSTables, Unified Compaction, and vector search (VECTOR type + ANN).
