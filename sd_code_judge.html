Design a Code Judge (Online Judge)

The system behind a competitive-programming platform: accept a code submission, run it against hidden test cases inside a locked-down sandbox, and return a verdict in seconds — safely, fairly, and under contest-scale spikes. The crux is running untrusted code without letting it escape, cheat the clock, or take down a neighbor.
Read this like a story

Start at the top. The chapter builds from "what is a verdict" that a high-schooler can follow, up to the senior crux — isolating hostile code with seccomp, cgroups, and microVMs while enforcing CPU/memory limits deterministically. Every number and mechanism below is stated precisely so you can quote it in an interview.

1. The Problem & Requirements

A code judge (or online judge) is the engine behind an online-judge / competitive-programming platform. A user submits source code for a problem; the judge compiles it, runs it against a set of hidden test cases, checks each output, enforces strict time and memory limits, and returns a verdict — Accepted, Wrong Answer, and so on. Think of it as an automated exam grader that must also assume every exam paper might be trying to attack the grader.

Functional requirements

  • Accept a submission: {problem ID, language, source code, user, contest?}. Return a submission ID immediately.
  • Compile & run the code against the problem's hidden test cases (inputs the author wrote, never shown to the user).
  • Return a verdict fast — ideally within a few seconds — plus per-test detail (which test failed, time/memory used).
  • Support many languages (C, C++, Java, Python, Go, …), each with its own compile step, runtime, and limits.
  • Scoring modes: all-or-nothing (ICPC-style) or partial credit via subtasks (IOI-style).
  • Live status: the user sees Pending → Running → <verdict> update in near real time.

Non-functional requirements

Must have

  • SECURE execution of untrusted code. This is the crux — the code is written by strangers and may be actively hostile. It must not escape the sandbox, read other users' data, touch the network, or harm the host.
  • Fairness / consistent limits. The same submission must get the same verdict every time, and two users' limits must not interfere. A "1-second limit" must mean the same thing on every worker.
  • Correctness of judging. Output comparison and limit enforcement must be exact — a false Accepted or false Wrong Answer destroys trust.

Should have

  • Throughput under contest spikes. Traffic is extremely bursty: near-idle most of the time, then tens of thousands of submissions in the last minutes of a contest.
  • Low latency from submit to verdict (queue wait + judging time), so contestants can iterate.
  • Elasticity & cost: scale workers up for a contest, back down afterward.
The one line that frames the whole design

"This is a system for running untrusted, potentially malicious code at scale, and returning a deterministic verdict." Say that early. It tells the interviewer you know security and determinism — not throughput — are the hard parts, and it shapes every later decision (sandbox choice, CPU-time vs. wall-time limits, retry policy).

2. Back-of-the-Envelope Estimation

Sizing here is unusual: the average load is tiny, but the contest peak is enormous and short. The whole scaling story flows from that gap, so quantify it.

Submission volume & QPS

Suppose 1,000,000 submissions/day across practice and contests.

seconds/day = 86,400 ≈ 105
average QPS = 1,000,000 / 86,400 ≈ 12 submissions/sec

# Contest peak — the number that actually drives the design:
# 30,000 contestants hammering a problem in the last ~5 min, ~2 tries each
peak load = (30,000 × 2) / 300 s = 60,000 / 300 = ~200 submissions/sec # ≈ 17× average

Worker count — apply Little's Law

A submission occupies a worker for the whole judging job: compile once, then run ~20–40 test cases. Say the average job holds a sandbox for ~10 seconds of wall time (compile + all tests). The number of concurrent jobs in flight is arrival rate × service time:

# Little's Law: L (in flight) = λ (arrival rate) × W (time in system)
steady concurrency = 12/s × 10 s = 120 concurrent jobs
peak concurrency = 200/s × 10 s = 2,000 concurrent jobs

# One sandbox runs one submission at a time (isolation). Pack ~16 sandboxes/host:
peak hosts ≈ 2,000 / 16 = ~125 worker hosts
steady hosts ≈ 120 / 16 = ~8 worker hosts
Takeaway

Peak concurrency is ~17× steady state. You cannot provision for peak 24/7 (wasteful) nor for average (contests would overwhelm it). That gap is exactly why the architecture is a queue + autoscaling worker pool — the queue absorbs the spike while workers scale out. Little's Law (L = λ × W) is the clean way to defend the worker count.

3. High-Level Architecture

The backbone is deliberately simple: a stateless API accepts submissions and drops them on a durable queue; a pool of sandboxed judge workers pulls jobs, runs them in isolation, writes the verdict to a result store, and a notifier pushes the update to the user. The queue is the shock absorber that decouples the spiky front end from the finite worker pool.

API enqueues; the autoscaled pool of sandboxed workers pulls jobs, runs each in isolation, writes the verdict to the store; the notifier pushes it back to the client. The queue decouples spiky submits from finite workers.

What each component does

  • API service (stateless): authenticates, validates (size limit, allowed language), writes submission metadata as Pending, and enqueues a job. It returns instantly — judging is asynchronous.
  • Submission queue (durable): the buffer between bursty submits and the finite worker pool. Durable so a submission is never lost if a worker dies. Supports priority (contest vs. practice) and backpressure.
  • Judge workers (sandboxed): the heart of the system. Each pulls one job, spins up an ephemeral one-shot sandbox, compiles, runs every test case under strict limits, computes the verdict, and reports it. Stateless and horizontally scalable.
  • Result store: persists verdicts and per-test detail (DB + object store for large logs/diffs).
  • Notifier: pushes status changes to the client (WebSocket/SSE) or answers polls, so the UI shows Pending → Running → verdict live.
  • Test-case store: hidden inputs/expected outputs in object storage, fetched (and cached) by workers.

4. Submission Lifecycle & Verdicts

Every submission walks a small state machine: Pending (queued) → Running (a worker has it) → a terminal verdict. The verdict taxonomy below is the shared vocabulary of every competitive-programming platform.

Compile can short-circuit to CE. Otherwise each test runs in a sandbox: a limit/crash yields TLE/MLE/RE/OLE; a clean run goes to the checker, which yields WA/PE or, if every test passes, AC.

The verdicts and how each is detected

VerdictMeaningHow the judge detects it
AC — AcceptedAll tests pass within all limitsEvery test's output matches the checker and stays under time/memory
WA — Wrong AnswerOutput is incorrect on some testChecker reports a mismatch (after normalizing per the comparison mode)
TLE — Time Limit ExceededRan too longCPU time > limit (busy loop) or wall-clock watchdog fires (sleep/deadlock)
MLE — Memory Limit ExceededUsed too much memorycgroup memory cap hit → the kernel OOM-kills the process (or an allocation fails)
RE — Runtime ErrorCrashed while runningNon-zero exit or fatal signal — SIGSEGV, SIGFPE (÷0), SIGABRT, uncaught exception
CE — Compile ErrorDid not buildCompiler process exits with a non-zero status; stderr returned to the user
PE — Presentation ErrorRight values, wrong formattingOptional verdict: values match but whitespace/layout differs from expected
OLE — Output Limit ExceededPrinted far too muchBytes written to stdout exceed a cap → killed (guards against disk/pipe flooding)
Why TLE needs two clocks

CPU time alone misses a program that sleep()s or blocks on I/O — it burns wall-clock time while using almost no CPU. Wall-clock time alone is unfair — it counts scheduler delays and noisy neighbors against the submission. So judges enforce both: a CPU-time limit (the fair primary limit, e.g. 1 s) and a larger wall-clock watchdog (e.g. 3–10 s) that kills hangs. TLE is declared when either is breached.

5. Sandboxed Execution — the Crux

You are about to exec() a binary a stranger uploaded. It may try to read /etc/passwd, open a socket to steal (leak out) the hidden test data, fork()-bomb the host, spin forever, allocate all of RAM, or write another user's files. The sandbox's job is to make every one of those impossible, not merely discouraged. Isolation is built in layers (defense in depth): if one layer is bypassed, the next still contains the code.

Defense in depth: each layer wraps the one inside it. The untrusted process at the center can only touch what every layer permits; breaching one layer still leaves the rest.

The isolation layers, one by one

  • Container or microVM boundary. A container uses Linux namespaces to give the process its own view of PIDs, mounts, network, users, and IPC — it can't even see other processes. A microVM (a lightweight VM booted by a KVM-based monitor) goes further: a real guest kernel behind hardware virtualization, so a kernel exploit hits the guest, not the host.
  • seccomp-bpf syscall filtering. Install a BPF filter that allowlists only the syscalls a solution legitimately needs (read, write, mmap, exit…) and kills the process on anything else — socket, ptrace, mount, clone with dangerous flags. This shrinks the kernel attack surface enormously.
  • cgroups for resource caps. Linux control groups (cgroups v2) enforce hard limits: memory.max caps RAM (over-allocate → the kernel OOM-kills → MLE), a CPU quota bounds CPU, and pids.max caps process count so a fork bomb can't exhaust the host.
  • CPU + wall-clock time limits. A CPU-time cap (via setrlimit(RLIMIT_CPU) or cgroup accounting) is the fair primary limit; a wall-clock watchdog kills hangs and sleeps (see §4). Breach either → TLE.
  • No network. Put the process in an empty network namespace with no interfaces (or drop all packets). Solutions never need the network; blocking it stops the code from stealing data or contacting an outside server.
  • Read-only file system. Mount the root FS read-only; give the process only a tiny writable tmpfs scratch dir, size-capped. It can't read other submissions, the test data of other problems, or host secrets.
  • Dropped privileges. Run as an unprivileged, per-run user (never root), drop all Linux capabilities, and set no_new_privs so it can't gain privileges via setuid binaries.
  • Ephemeral, one-shot sandbox. Build a fresh sandbox per run and destroy it afterward. No state survives to the next submission, so one user's code can never observe or corrupt another's — and it guarantees a clean, identical starting environment every time (which feeds determinism, §8).

Compile step vs. run step

The two phases have different risk and limit profiles, so treat them separately:

Compile step

  • Runs the compiler on untrusted source — itself sandboxed (a hostile program can abuse the compiler, e.g. #include tricks or infinite template expansion).
  • Gets its own generous-but-bounded time/memory limit and no network (so it can't fetch packages).
  • Failure → CE, with compiler stderr returned. Interpreted languages skip or do a syntax check.

Run step

  • Executes the compiled artifact once per test case under the strict problem limits (e.g. 1 s CPU, 256 MB).
  • Feeds the test input on stdin, captures stdout, enforces all sandbox layers above.
  • Failure modes map to TLE / MLE / RE / OLE; clean output goes to the checker.
Do not skip the sandbox on "trusted" languages

There is no trusted language. Python can os.system, Java can spawn threads and open sockets, C can do anything. Every language runs behind the same isolation layers; only the limits and the compile/interpret step differ. A judge that sandboxes C but runs Python "in-process" is one import socket away from a breach.

6. Judging & Test Cases

Once a program produces output for a test, the checker decides pass/fail. The subtlety is that "correct output" is not always a single string — many problems accept multiple valid answers.

Output comparison modes

  • Exact match: output must equal expected byte-for-byte. Strictest; brittle against trailing whitespace, so rarely the default.
  • Token / whitespace-normalized: split both into tokens and compare token-by-token, ignoring trailing spaces and newline style. This is the common default — it accepts "1 2 3\n" vs. "1 2 3".
  • Special checker (custom judge): a problem-specific program that reads the input, the contestant's output, and the reference, then decides. Required when multiple answers are valid — e.g. "print any shortest path," or floating-point answers accepted within a tolerance (|a − b| ≤ 1e-6). The checker itself is trusted code written by the problem author and runs sandboxed too.
  • Interactive problems: an interactor program exchanges messages with the solution over stdin/stdout in real time (e.g. a guessing game) and emits the verdict.
# token comparison (the usual default)
got = tokenize(stdout); exp = tokenize(expected)
if got == exp: PASS else: WA # trailing whitespace/newlines ignored

# special checker (multiple valid answers)
verdict = checker(test_input, got, reference) # author-written, sandboxed
PASS if checker says "ok", else WA

Per-test limits & scoring

  • Per-test time/memory: limits are enforced per test case, not per submission — a solution that is fast on small inputs but TLEs on a big one must fail that test.
  • All-or-nothing (ICPC-style): the first failing test decides the whole verdict; the judge can stop early on the first failure to save resources.
  • Partial scoring / subtasks (IOI-style): tests are grouped into subtasks, each worth points; a subtask scores its points only if all its tests pass. Total score is the sum, so a partial solution still earns partial credit.
Early-exit vs. full run

For all-or-nothing scoring, stop at the first non-AC test — it can't change the verdict and it frees a worker sooner. For subtasks/partial scoring you generally run everything (or at least every subtask) to compute the score. State which mode you assume; it changes the average job time from §2.

7. Scaling for Contest Spikes

Recall §2: peak is ~17× steady. The design must expand for a contest and contract afterward without dropping submissions or starving practice users.

Worker pool + autoscaling

  • Scale on queue depth, not CPU. The signal that you're behind is a growing queue / rising oldest-message age. Autoscale the worker pool on queue backlog so capacity tracks demand; scale in when the backlog drains.
  • Pre-warm for scheduled contests. Contests have known start times — provision the peak worker fleet before the start so the first spike doesn't wait on cold-boot. This is the single biggest latency win.
  • Pre-baked language-runtime images. Bake compilers/runtimes into the worker/sandbox image so no per-job install is needed; keep sandbox base images warm to shave startup time.

Backpressure & priority

  • Priority queues: run contest submissions ahead of practice ones. During a spike, practice jobs wait (or route to a separate, smaller pool) so live contestants get fast feedback.
  • Backpressure: the queue is bounded and durable. If the backlog exceeds a threshold you slow low-priority intake — return a "queued, results delayed" state or apply per-user submission rate limits — rather than overloading the fleet. The queue turns a spike into a (briefly) longer wait instead of an outage.
  • Result caching / dedup: the exact same source for the same problem yields the same verdict, so an identical resubmission can be deduped; compile artifacts can be cached and reused across a submission's test runs. Cache carefully — cache by a hash of {problem version, language, source, limits}, and invalidate when test data changes.
Why async judging wins here

Synchronous judging (hold the HTTP connection until the verdict) is simpler but couples front-end capacity to worker capacity and collapses under a spike — every slow judge ties up a connection. Asynchronous judging (enqueue, return a submission ID, push the verdict later) lets the queue absorb the burst and the workers drain it at their own pace. For a bursty, seconds-long workload, async is the right default.

8. Reliability & Fairness

Because a verdict affects rankings and pass/fail, the judge must be both deterministic (same input → same verdict) and robust to infrastructure hiccups — while never letting infra failures corrupt a legitimate verdict.

Deterministic, fair limits

  • Measure CPU time, not wall time, for the primary limit. Wall time varies with load; CPU time is (mostly) reproducible. Pair it with the wall watchdog only to catch hangs (§4).
  • Pin resources & a consistent hardware class. Run each sandbox on dedicated CPU cores, judge on one machine type, and consider disabling CPU frequency scaling / turbo so a "1-second" limit means the same thing on every worker and across re-judges.
  • Isolate the noisy neighbor. cgroup CPU/memory caps plus core-pinning stop one submission from stealing cycles from another sharing the host — otherwise a heavy job could cause a light job to spuriously TLE.

Retries — the critical distinction

Retry infra failures, NEVER retry a real verdict

If a worker crashes, the host OOMs, or a job times out in the queue (infrastructure), the submission is still Pending/Running — safely re-enqueue and judge it again. But WA, TLE, MLE, RE, CE are correct verdicts about the code — retrying them would let a flaky submission "win" on a lucky retry and destroy fairness. The judge must clearly separate "the judge failed" (retry) from "the code failed" (final).

  • Idempotent judging & re-judge: judging a submission ID must be safe to run more than once and must produce the same result; a re-judge (e.g. after fixing test data) deterministically replaces the prior verdict rather than appending. Idempotency keys on the queue message prevent a redelivered job from being judged twice concurrently.
  • At-least-once queue + dedup: durable queues deliver at least once, so guard against double-judging with a per-submission lock/idempotency key.
  • Timeouts as a safety net: a job that exceeds a hard ceiling (stuck sandbox) is killed and either re-queued (infra) or marked with a system error for a human to inspect — never silently dropped.

9. Plagiarism & Anti-Cheat

Judges are graded competitions, so people try to cheat — by copying solutions or by gaming the judge. The defenses are worth a mention; keep them generic (the exact thresholds are policy, not architecture).

Structural similarity detection

Naïve text diffing is easily defeated by renaming variables or reformatting. The standard approach is structural fingerprinting (the idea behind MOSS-style detectors):

  1. Tokenize / normalize: lex the source into tokens, discarding whitespace, comments, and identifier names so that renaming or reformatting doesn't change the representation. Optionally compare AST structure for language-aware matching.
  2. Fingerprint: hash overlapping k-grams of tokens and select a stable subset of those hashes (a "winnowing"-style document fingerprint) so two files can be compared by how many fingerprints they share.
  3. Score & review: pairs with high fingerprint overlap are flagged for human review — the tool surfaces suspicion, it doesn't convict.

Gaming the judge, and the guards

  • Hidden test cases stop hardcoding: a solution can't just print the expected answers if it never sees them. Rotating/randomized tests further reduce guessing.
  • Submission rate limiting per user/problem blunts brute-forcing outputs by spamming submissions (this reuses the rate-limiter from Chapter 1).
  • The sandbox itself is anti-cheat: no network and a read-only FS mean a submission can't fetch answers or read another user's data.
Keep it generic in an interview

Describe the shape — tokenize, fingerprint, compare, human-review — not any proprietary detector's internals or tuned thresholds. Similarity is a signal for review, never an automatic penalty; false positives (common library code, standard templates) are real, so a human makes the final call.

10. Trade-offs & Interview Framing

Isolation mechanism trade-offs

MechanismIsolation strengthStartup / overheadNotes
Process isolation (seccomp + rlimits + ptrace)Weakest — shares the host kernel with only syscall filteringLowest — just fork/execFast and simple, but a kernel bug = a host escape. OK only with tight seccomp and low trust budget.
Container (namespaces + cgroups + seccomp)Strong — isolated view + resource caps, still one shared kernelLow–medium — ms to startThe common best balance: good isolation, cheap, elastic. Kernel remains the shared attack surface.
microVM (KVM-based, e.g. lightweight VMMs)Strongest — separate guest kernel behind hardware virtualizationMedium — ~100+ ms boot, more memoryBest for hostile multi-tenant code; a guest kernel exploit doesn't reach the host. Slightly heavier.

Other key trade-offs

Async judging (queue + workers)
  • Absorbs contest spikes; workers drain at their own pace
  • Front-end decoupled from worker capacity
  • Slightly more moving parts (queue, notifier)
Sync judging (hold the request)
  • Simplest to build and reason about
  • Couples front-end to worker capacity; collapses under a spike
  • Only viable at tiny scale / no contests
The 30-second decision

Hostile multi-tenant code, security first? → microVM. Elastic, cost-sensitive, strong-enough isolation? → container (namespaces + cgroups + seccomp) — the usual answer. Bursty contest load? → async, queue + autoscaling pool, priority for contest over practice. Fair limits? → CPU time primary, wall-clock watchdog, pinned cores.

How to drive the conversation

  1. Clarify (1–2 min): Which languages? Contest or practice or both? All-or-nothing or partial scoring? Latency target? Trust model (public internet = fully hostile)?
  2. State the crux: "This is about running untrusted code safely and returning a deterministic verdict." Lead with security + determinism.
  3. Estimate: steady vs. contest-peak QPS and worker concurrency via Little's Law (§2) → motivates queue + autoscale.
  4. Architecture: API → queue → sandboxed worker pool → result store → notify; the queue as the spike absorber.
  5. Go deep on the sandbox: the layered isolation (§5) and how each verdict is detected (§4).
  6. Cover fairness & failure: CPU-time limits, retry infra-not-verdicts, idempotent re-judge (§8); then anti-cheat (§9).

What interviewers probe (with one-liners)

Q: How do you run untrusted code safely?
Layered isolation: run the code in a container or microVM with an empty network namespace, a read-only FS, dropped privileges/capabilities and no_new_privs, a seccomp-bpf syscall allowlist, and cgroup CPU/memory/pids caps. Each run is an ephemeral, one-shot sandbox destroyed afterward. A microVM adds a separate guest kernel so even a kernel exploit doesn't reach the host.

Q: How do you detect TLE vs. MLE?
TLE: enforce a CPU-time limit (the fair primary) and a larger wall-clock watchdog — CPU time catches busy loops, wall time catches sleeps/deadlocks; breach either → TLE. MLE: set a cgroup memory.max; exceeding it makes the kernel OOM-kill the process (or an allocation fails) → MLE.

Q: How do you handle a contest spike?
Async, queue-backed judging: the API enqueues and returns instantly; an autoscaling worker pool scales on queue depth. Pre-warm workers before a scheduled contest, give contest submissions queue priority over practice, and apply backpressure (bounded queue + per-user rate limits) so a spike becomes a longer wait, not an outage.

Q: What if a problem has multiple correct outputs?
Use a special checker — an author-written, sandboxed program that reads the input, the contestant's output, and a reference, and decides ok/WA. It handles "print any valid answer," floating-point tolerance, or interactive problems, which exact/token comparison can't.

Q: When do you retry a submission?
Only on infrastructure failure — worker crash, host OOM, stuck sandbox — where no valid verdict was produced; re-enqueue and judge again. Never retry a real verdict (WA/TLE/MLE/RE/CE); a lucky retry would break fairness. Judging must be idempotent so a redelivered job isn't double-counted.

Q: How do you make verdicts fair and reproducible?
Measure CPU time (not wall time) for the primary limit, pin sandboxes to dedicated cores on a consistent hardware class, cap resources with cgroups to kill noisy-neighbor interference, and start every run from an identical fresh sandbox. Same code + same tests → same verdict, every time.

Q: How do you detect plagiarism?
Structural fingerprinting: tokenize/normalize the source (drop names, whitespace, comments), hash overlapping k-grams and select a stable fingerprint subset, then flag high-overlap pairs for human review. Combine with hidden tests, submission rate limits, and the no-network sandbox. It's a review signal, not an automatic penalty.

One-line summary

A code judge = accept a submission → enqueue → a pool of ephemeral, layered sandboxes (namespaces/microVM + seccomp + cgroups + no net + read-only FS + dropped privs) compiles and runs it against hidden tests under CPU-time and memory caps → a checker turns output into a verdict. Security and determinism are the hard parts; a durable priority queue with an autoscaling worker pool absorbs contest spikes; retry infra failures but never real verdicts.
