Java Refresher

The JVM, the language, and modern Java (8 → 21) — from bytecode and GC to generics, collections, concurrency, streams, and records

The JVM: write once, run the same everywhere

Analogy: imagine a universal music player. Composers don't ship sheet music tuned to one specific piano — they ship a standard file (say, a MIDI file), and every device plays it the same way. Java works like that. You write .java source, the compiler turns it into a portable bytecode file (.class), and the Java Virtual Machine (JVM) on any OS plays that bytecode. The bytecode is the MIDI file; the JVM is the player.

The tiny runnable example
// Hello.java
public class Hello {
  public static void main(String[] args) {
    System.out.println("Hello, JVM!");
  }
}
# Compile source -> bytecode, then run it on the JVM
javac Hello.java     # produces Hello.class (bytecode)
java Hello           # JVM loads, verifies, JIT-compiles, runs
# => Hello, JVM!

Peek at the bytecode with javap -c Hello and you'll see stack-machine ops like getstatic, ldc, invokevirtual. The JVM is a stack machine: operands are pushed/popped rather than living in named registers.

What actually happens when you run java Hello

  1. Class loading — the class loader finds Hello.class, reads the bytecode, and creates a runtime representation. Loading is lazy: a class is loaded the first time it's referenced.
  2. Linking — verify (bytecode is type-safe and can't corrupt the JVM), prepare (allocate static fields with defaults), resolve (turn symbolic references into direct ones).
  3. Initialization — run static initializers and static field assignments, exactly once, thread-safely.
  4. Execution — the interpreter starts running bytecode immediately; the JIT watches for hot code.

Class loaders and the delegation model

Class loaders form a parent chain: Bootstrap (core java.*) → Platform → Application/System (your classpath). Each loader delegates upward first — it asks its parent to load a class before trying itself. This "parent-first" rule prevents your code from shadowing core classes (you can't sneak in a fake java.lang.String), and it means class identity is (name, defining loader) — the same class name loaded by two different loaders is two different types at runtime (the classic ClassCastException in plugin/app-server land).

JIT: interpreter first, then compile the hot paths

The JVM starts by interpreting bytecode (fast startup). A profiler counts how often each method runs. Once a method crosses a threshold it's "hot," and the Just-In-Time compiler compiles it to native machine code. HotSpot uses tiered compilation: C1 (fast to compile, lightly optimized) then C2 (slow to compile, aggressively optimized) for the hottest code.

The JIT sees runtime behavior a static compiler never can, so it does speculative optimizations: inlining, and monomorphic call de-virtualization when a call site has only seen one concrete type. If an assumption is later violated it deoptimizes back to the interpreter. This is why a Java service is slow for the first few seconds (cold JIT) then speeds up — the "warm-up" you'll hear about in latency discussions.

Coming from C++ / Python

  • From C++: no separate compile-and-link-to-a-native-binary step you ship. You ship portable bytecode; the machine code is produced at runtime by the JIT. There's no #include/header/translation-unit model — the unit is the class file, resolved lazily by name.
  • From Python: Java is statically typed and compiled ahead of time to bytecode (like .pyc), but then JIT-compiled to native code, so steady-state throughput is far higher than CPython. There's no GIL — real threads run in parallel (see Concurrency).

Interview angle

Be able to narrate the pipeline in one breath: "javac emits portable bytecode; the JVM loads classes lazily through a parent-first loader chain, verifies them, interprets first for fast startup, and the JIT compiles hot methods to native code with speculative inlining and de-virtualization, deoptimizing if assumptions break." Then connect it to a real concern (cold-start latency, warm-up before load tests). That shows you understand why, not just what.

OOP in Java: classes, interfaces, abstraction

Analogy: an interface is a job description ("must be able to start() and stop()"); a class is a specific employee who can actually do the job. You can hire anyone who fits the description without caring who they are — that's polymorphism.

Tiny runnable example
interface Shape { double area(); }          // the "job description"

record Circle(double r) implements Shape {   // a concrete doer
  public double area() { return Math.PI * r * r; }
}
record Square(double s) implements Shape {
  public double area() { return s * s; }
}

Shape shape = new Circle(2);
System.out.println(shape.area());   // 12.566... — dispatched at runtime

Every non-primitive is a reference to a heap object; every method (unless static, private, or final) is virtual by default — dispatched dynamically via the object's class. This is the opposite of C++, where you opt in to virtual.

Since Java 8 interfaces can carry default methods (a body) so APIs can evolve without breaking implementers, and static helpers. They still hold no instance fields — that's the line that keeps "multiple interfaces, single class inheritance" free of the C++ diamond-of-state problem.

Inheritance vs composition

Inheritance models is-a; composition models has-a. The industry lesson (and a common interview topic) is "prefer composition over inheritance." Deep inheritance trees are fragile: a subclass depends on its parent's internal call sequence, so a harmless parent change silently breaks children (the "fragile base class" problem).

// Inheritance — tight coupling, is-a
class Stack<E> extends ArrayList<E> { ... }   // BAD: exposes add(index), remove...

// Composition — delegate to a field, has-a. Expose only what you mean to.
class Stack<E> {
  private final List<E> items = new ArrayList<>();
  public void push(E e) { items.add(e); }
  public E pop() { return items.remove(items.size() - 1); }
}

Rule of thumb: use inheritance only for a genuine, stable is-a where you also control the superclass (or it's designed for extension). Otherwise compose. Program to interfaces (List<E> x = new ArrayList<>()), not implementations.

equals / hashCode / the object contract

If you override equals you must override hashCode consistently, or hash-based collections break. Records generate both for you (value-based) — one more reason to reach for them.

Coming from C++ / Python

  • From C++: no multiple class inheritance and no diamond problem — you get multiple interface inheritance instead. Methods are virtual by default; mark final to lock. No destructors — cleanup is GC + try-with-resources, not RAII.
  • From Python: no duck typing — a type must formally implements/extends to be substitutable. There's no multiple inheritance of state; interface + default methods is the closest analog to mixins.

Interview angle

When asked "abstract class or interface?", answer by intent: interface for a capability many unrelated types can offer (and you may want multiple of), abstract class when subclasses genuinely share state and partial implementation. Then volunteer "prefer composition over inheritance" with the fragile-base-class reason — it signals you've maintained real systems, not just passed a syntax quiz.

Generics & type erasure

Analogy: generics are a labeled container. A box marked "APPLES ONLY" lets the compiler stop you at packing time from dropping in an orange — but once it's on the truck, the label is peeled off and every box is just "a box." That peeling-off is type erasure.

Tiny runnable example
List<String> names = new ArrayList<>();
names.add("Ada");
// names.add(42);   // compile error — the label is checked at compile time
String first = names.get(0);   // no cast needed; compiler knows it's a String

static <T> T firstOf(List<T> xs) { return xs.get(0); }  // generic method

Type erasure: what the JVM actually sees

Generics are a compile-time only feature. After type-checking, the compiler erases type parameters: List<String> and List<Integer> both become plain List at runtime, and T becomes its bound (Object if unbounded). The compiler inserts the casts for you. This kept generics backward-compatible with pre-2004 bytecode — but it has sharp edges:

// Both print "true" — same runtime class, the <...> is gone
System.out.println(new ArrayList<String>().getClass()
    == new ArrayList<Integer>().getClass());

// Cannot do these because the type isn't there at runtime:
// if (x instanceof List<String>) ...   // illegal
// new T[10];                            // cannot create generic array
// T.class / new T();                    // no reified type

Because arrays are reified (they know their element type at runtime) but generics are erased, mixing them is unsafe — that's why List<String>[] is disallowed and you get "unchecked" warnings. Prefer List<List<String>> over generic arrays.

Bounded types and wildcards (PECS)

<T extends Comparable<T>> T max(List<T> xs)   // upper bound: T must be Comparable

// PECS: Producer Extends, Consumer Super
void copy(List<? extends Src> from,   // producer: we READ Src out of it
          List<? super   Src> to) {   // consumer: we WRITE Src into it
  for (Src s : from) to.add(s);
}

? extends T is a read-only view (you can get a T out, but can't add — the compiler doesn't know the exact subtype). ? super T is write-friendly (you can put a T in). Mnemonic: PECS — Producer Extends, Consumer Super.

Generics are invariant: List<String> is not a List<Object>, even though String is an Object. Wildcards (? extends/? super) are how you regain flexible variance safely. (Arrays, by contrast, are covariant and can throw ArrayStoreException at runtime — a known Java flaw.)

Coming from C++ / Python

  • From C++: generics are not templates. No per-type code generation, no monomorphization, no template metaprogramming — one erased implementation serves all types. You can't compute on the type or specialize; the payoff is smaller code and no template-bloat, the cost is no reified T.
  • From Python: think of it as type hints the compiler actually enforces — but unlike Python, they're checked at compile time and then erased at runtime, so runtime introspection of the parameter type isn't available.

Interview angle

The classic question is "what is type erasure and what can't you do because of it?" Get the list right: no new T[], no new T(), no instanceof List<String>, both parameterizations share one Class. Then show depth with PECS and invariance. Bonus: explain why — backward compatibility with legacy bytecode — which reframes it as a deliberate trade-off, not a bug.

The Collections framework

Analogy: choosing a collection is like choosing storage furniture. A List is a numbered row of lockers (position matters, duplicates fine). A Set is a guest list (each name once, order maybe irrelevant). A Map is a phone book (look up a value by a unique key).

Tiny runnable example
List<String> list = new ArrayList<>(List.of("a", "b", "a")); // [a, b, a]
Set<String>  set  = new HashSet<>(list);                    // {a, b}
Map<String,Integer> freq = new HashMap<>();
for (String s : list) freq.merge(s, 1, Integer::sum);       // {a=2, b=1}

ArrayDeque (backed by a circular array) is the modern choice for both stacks and queues — faster than LinkedList and than the legacy Stack. For a heap, use PriorityQueue.

How HashMap works (a common follow-up): keys are bucketed by hashCode() (then spread and masked to an index). Collisions chain in a bucket; since Java 8 a bucket that grows past a threshold treeifies into a red-black tree, so worst case is O(log n) instead of O(n). This is exactly why a broken hashCode/equals pair silently destroys performance and correctness.

Iteration and fail-fast

// Structurally modifying a collection while iterating it => ConcurrentModificationException
for (String s : list) {
  if (s.equals("a")) list.remove(s);   // throws!
}
// Correct: iterator.remove(), or removeIf, or collect into a new list
list.removeIf(s -> s.equals("a"));

Coming from C++ / Python

  • From C++: ArrayList ≈ vector, HashMap ≈ unordered_map, TreeMap ≈ map, ArrayDeque ≈ deque, PriorityQueue ≈ priority_queue. But Java collections hold boxed objects (Integer, not int) — no value semantics, everything is a reference, so watch autoboxing cost in hot loops.
  • From Python: ArrayList ≈ list, HashMap ≈ dict, HashSet ≈ set. Java's are typed and you pick the implementation explicitly, trading Python's one-size-fits-all for control over ordering and complexity.

Interview angle

A common question is "which collection and why?" Answer in terms of the operation you optimize for and the ordering you need: ArrayList for indexed/iterated data, HashMap for O(1) lookup, TreeMap when you need sorted keys or range queries, LinkedHashMap for LRU. Have the HashMap-internals story (buckets, chaining, Java 8 treeify, hashCode/equals contract) ready — it's a core Java topic worth being fluent in.

Exceptions: checked vs unchecked

Analogy: a checked exception is a form your method must file in advance — "this call may fail to reach the network, and callers are legally warned." An unchecked exception is a slip-and-fall: nobody signs a waiver for it, it just means a bug or a broken precondition.

Tiny runnable example
// try-with-resources auto-closes the reader, even on exception
try (var in = Files.newBufferedReader(path)) {   // IOException is CHECKED
  return in.readLine();
} catch (IOException e) {
  throw new UncheckedIOException(e);            // wrap + rethrow, keep the cause
}

Doing it well

  • Throw specific, catch specific. Never catch (Exception e) {} and swallow — you'll hide the bug. Catch the narrowest type you can act on.
  • Preserve the cause. When wrapping, pass the original: throw new ServiceException("load failed", e). You keep the full stack trace.
  • Clean up with try-with-resources, not finally { close(); } — any AutoCloseable is closed automatically in reverse order, and suppressed exceptions are attached rather than lost.
  • Don't use exceptions for control flow — they're expensive (stack capture) and obscure intent.

The checked-vs-unchecked debate is real: overusing checked exceptions leads to boilerplate catch/rethrow noise, and they don't compose with lambdas/streams (a Function can't throw a checked exception). Many modern APIs favor unchecked exceptions or Optional/result types. Know both sides.

Coming from C++ / Python

  • From C++: Java has no noexcept; instead the checked exception is enforced in the method signature (throws) at compile time — closer to old-style C++ exception specs but actually enforced. There are no exception values to slice; everything is a reference to a Throwable.
  • From Python: Python's exceptions are all "unchecked" — Java adds a compiler-enforced checked category. try-with-resources is Java's with-statement; both guarantee cleanup.

Interview angle

Define both categories precisely, then give the design rule: checked for recoverable external conditions a caller can act on, unchecked for programmer errors. Show maturity by naming the trade-off (checked-exception boilerplate, poor lambda/stream interop) and your habits: preserve causes, catch narrowly, never swallow, use try-with-resources. That balanced take reads as senior.

Memory & garbage collection

You don't free() in Java. Objects live on the heap; the garbage collector reclaims those no longer reachable from live roots (stack locals, statics, active threads). The key insight that makes GC fast is the generational hypothesis: most objects die young.

The JVM runtime memory areas

Here's the memory the JVM manages while your program runs. The heap (shared, GC'd) is split into generations; each thread gets its own stack; class metadata lives in Metaspace (native memory).

Generational GC: young → old promotion, step by step

New objects are allocated in Eden. When Eden fills, a fast minor GC copies the few survivors into a Survivor space and discards the rest. Each survival bumps the object's age; once an object is old enough (the tenuring threshold), it's promoted to the Old generation. Press Step to watch one object's journey.

Collectors you should be able to name

CollectorOptimizes forNote
G1 (default since 9)balanced throughput + bounded pausesregion-based; targets a pause goal
Parallelraw throughputbatch jobs; longer pauses OK
ZGC / Shenandoahultra-low pause (sub-ms), huge heapsmostly concurrent, low pause independent of heap size
Serialsmall heaps / single coresimplest, stop-the-world

Mechanically, most collectors are mark-sweep(-compact): from GC roots, mark everything reachable, sweep the unmarked, and compact to remove fragmentation. The young-gen collector above is a copying collector — a special, very cheap case because so little survives. A memory leak in Java isn't a missing free; it's an unintended reference that keeps an object reachable (e.g. a growing static Map or an unremoved listener).

Coming from C++ / Python

  • From C++: no delete, no manual ownership, no RAII destructors. Deterministic cleanup of non-memory resources uses try-with-resources/AutoCloseable, not destructors. finalize() is deprecated — never rely on it. The cost you trade for safety is GC pauses.
  • From Python: CPython uses reference counting plus a cycle collector, so cleanup is often prompt; the JVM uses tracing GC, so timing is non-deterministic but cycles are collected for free and throughput is far higher.

Interview angle

Lead with the generational hypothesis ("most objects die young"), then explain minor vs major GC, Eden→Survivor→Old promotion, and mark-sweep-compact. Define a Java memory leak correctly (unintended reachability, not a missing free) and name a real cause. If asked about tuning, mention G1 as the default and pause-goal collectors (ZGC/Shenandoah) for latency-sensitive services — but say you'd measure before tuning.

Concurrency & the memory model

Analogy: shared mutable state across threads is a shared whiteboard. If two people write at once without a rule for taking turns, you get garbled results — and worse, each may be looking at a cached photo of the board rather than the live board. Locks give turn-taking; volatile forces everyone to read the live board.

Tiny runnable example
var pool = Executors.newFixedThreadPool(4);
Future<Integer> f = pool.submit(() -> 1 + 1);  // run on a worker thread
System.out.println(f.get());   // 2  — blocks until the result is ready
pool.shutdown();

Java threads are real OS threads and run in parallel on multiple cores — there is no GIL (unlike CPython). That's power and responsibility: you get true parallelism, and you own the correctness of shared state.

The race, and the two fixes

// BROKEN: count++ is read-modify-write, not atomic; two threads lose updates
int count = 0;
void inc() { count++; }

// FIX 1: mutual exclusion — one thread in the critical section at a time
synchronized void inc() { count++; }   // intrinsic lock on 'this'

// FIX 2: lock-free atomic for this simple case
final AtomicInteger count = new AtomicInteger();
void inc() { count.incrementAndGet(); }   // CAS (compare-and-swap) under the hood

synchronized vs volatile — different jobs

synchronizedvolatile
Guaranteesmutual exclusion and visibilityvisibility only (no atomicity)

// volatile is right here: a one-way flag, no compound update
private volatile boolean running = true;
public void stop() { running = false; }        // write is seen by the loop thread
public void loop() { while (running) { work(); } } // without volatile, may spin forever

volatile does not make count++ safe — that's read-modify-write, three operations. Use synchronized, an Atomic*, or a lock for compound updates.

The Java Memory Model (JMM), at a high level

The compiler, JIT, and CPU are all free to reorder and cache operations for speed. The JMM is the contract that says when one thread's writes are guaranteed visible to another — the happens-before relationship:

  • Everything before releasing a lock happens-before the next thread that acquires it.
  • A write to a volatile field happens-before every later read of it.
  • Thread.start() happens-before the thread's code; the thread's code happens-before another thread's join() returning.

Without a happens-before edge, there is no guarantee another thread ever sees your write — even hours later. Data races aren't just "sometimes wrong values"; they're undefined behavior in the model.

Coming from C++ / Python

  • From C++: synchronized ≈ a scoped lock_guard on an intrinsic monitor; volatile in Java is a real memory-model fence (visibility + ordering) — not C/C++ volatile, which only stops the compiler from optimizing away an access (its classic use is memory-mapped I/O; also signal handlers) and gives no thread guarantees. The JMM plays the role of the C++11 memory model.
  • From Python: no GIL, so threads give true CPU parallelism — but you must synchronize shared state yourself (Python leaned on the GIL for coarse safety). ExecutorService ≈ concurrent.futures.ThreadPoolExecutor.

Interview angle

Distinguish the two guarantees crisply: atomicity/mutual exclusion (locks, atomics) vs visibility/ordering (volatile, happens-before). The trap question is "will volatile fix count++?" — no, it's a compound op. Then reach for java.util.concurrent instead of hand-rolling locks, and mention happens-before as the reason a correctly-synchronized program sees consistent state. Naming virtual threads shows you're current.

Modern Java: streams, lambdas, records, var

Analogy: streams are an assembly line for data. Raw items go in one end; each station transforms or filters them; a final station collects the finished result. You describe what each station does, not how to loop.

Tiny runnable example
List<String> names = List.of("Ada", "Bob", "Cara", "Al");

List<String> result = names.stream()
    .filter(n -> n.length() > 2)      // keep longer names
    .map(String::toUpperCase)          // transform
    .sorted()                          // order
    .toList();                         // terminal: collect (Java 16+)
// => [ADA, BOB, CARA]

Lambdas & functional interfaces

A lambda is an instance of a functional interface (one abstract method). Method references (String::toUpperCase) are shorthand. The common built-ins live in java.util.function:

Function<String,Integer> len = String::length;     // T -> R
Predicate<String>   nonEmpty = s -> !s.isEmpty();   // T -> boolean
Supplier<List<String>> make = ArrayList::new;       // () -> T
Consumer<String>    print = System.out::println;    // T -> void
BiFunction<Integer,Integer,Integer> add = Integer::sum;

Streams: intermediate vs terminal, and laziness

Intermediate ops (filter, map, sorted) are lazy — they build a pipeline and do nothing until a terminal op (toList, collect, reduce, forEach, count) runs it. This lets the runtime fuse operations and short-circuit.

Map<Boolean,List<Integer>> parts = nums.stream()
    .collect(Collectors.partitioningBy(n -> n % 2 == 0));

Map<Integer,List<String>> byLen = words.stream()
    .collect(Collectors.groupingBy(String::length));

int total = nums.stream().mapToInt(Integer::intValue).sum();  // primitive stream, no boxing

Streams are single-use (consume once), shouldn't mutate external state from lambdas, and parallelStream() is not free — only worth it for large, CPU-bound, side-effect-free work on splittable sources. For a trivial loop, a plain for is clearer and often faster.

Optional — model "maybe absent" without null

Optional<User> u = repo.findById(id);
return u.map(User::name).orElse("unknown");   // no NullPointerException path

var — local type inference (Java 10)

var list = new ArrayList<String>();   // inferred ArrayList<String>
var entry = map.entrySet().iterator().next();  // avoids a verbose type name
// Still statically typed! var is inference, not dynamic typing.
// Local variables only — not fields, params, or return types.

Records — immutable data carriers (Java 16)

record Point(int x, int y) {}   // that's the whole class
// auto-generated: constructor, x()/y() accessors, equals, hashCode, toString
var p = new Point(3, 4);
System.out.println(p);            // Point[x=3, y=4]
System.out.println(p.equals(new Point(3, 4)));  // true — value equality

// compact constructor for validation:
record Range(int lo, int hi) {
  Range { if (lo > hi) throw new IllegalArgumentException("lo > hi"); }
}

Records shine as DTOs (data transfer objects), map keys, and pattern-matching targets. Recent Java pairs them with sealed types, pattern matching for switch, and text blocks:

sealed interface Shape permits Circle, Square {}
record Circle(double r) implements Shape {}
record Square(double s) implements Shape {}

double area = switch (shape) {                 // exhaustive — compiler checks all cases
  case Circle c -> Math.PI * c.r() * c.r();     // pattern matching + binding
  case Square s -> s.s() * s.s();
};

String json = """
  { "ok": true }""";                          // text block (multi-line string)

Coming from C++ / Python

  • From C++: streams ≈ ranges/views pipelines; lambdas are similar but capture by value of the reference (effectively-final locals only — no [&] by-reference capture). record ≈ an aggregate struct with auto ==; var ≈ auto (locals only).
  • From Python: streams ≈ generator/comprehension pipelines (filter/map), record ≈ @dataclass/namedtuple, Optional ≈ Optional[T], var is still statically typed (inference), not Python's dynamic binding.

Interview angle

Explain stream laziness (intermediate vs terminal, short-circuiting) and when not to use streams or parallelStream. Know that var and records are still fully static typing. If you can sketch sealed + record + pattern-matched switch as exhaustive, type-safe modeling of a closed set of cases, you'll read as current on Java 17–21, which many candidates aren't.

Interview Q&A — likely Java questions

"What happens when you run java MyClass?"

The class loader (parent-first delegation) loads the bytecode; the JVM verifies, prepares, and initializes it; the interpreter starts executing bytecode immediately; the JIT profiles and compiles hot methods to native code with speculative optimizations, deoptimizing if assumptions break. Portable bytecode in, native code out — at runtime.

"Checked vs unchecked exceptions?"

Checked (subclasses of Exception except RuntimeException) must be declared or caught — use for recoverable external failures. Unchecked (RuntimeException) needn't be declared — use for programming errors/broken preconditions. Error is JVM-level; don't catch it. Best practice: catch narrowly, preserve the cause, never swallow, use try-with-resources.

"What is type erasure?"

Generics are compile-time only; type parameters are erased to their bounds at runtime, and the compiler inserts casts. So List<String> and List<Integer> share one runtime class, and you can't do new T[], new T(), or instanceof List<String>. It exists for backward compatibility with pre-generics bytecode.

"HashMap vs TreeMap vs LinkedHashMap?"

HashMap: O(1) average, no order. TreeMap: red-black tree, O(log n), sorted keys and range queries. LinkedHashMap: O(1) with predictable insertion (or access) order — great for LRU. Follow-up: HashMap buckets by hashCode, chains collisions, and treeifies long buckets (Java 8) to O(log n).

"How does garbage collection work?"

Tracing GC reclaims unreachable objects. Generational hypothesis: most die young, so the heap is split into young (Eden + Survivors, cheap copying minor GC) and old (rare, costlier major GC). Survivors are aged and promoted past a threshold. Mark-sweep-compact for the old gen. A "leak" is unintended reachability, not a missing free.

"synchronized vs volatile?"

synchronized gives mutual exclusion and visibility and blocks; use for compound actions. volatile gives visibility/ordering only, no atomicity, doesn't block; use for a single flag. volatile does not make count++ safe — that's read-modify-write; use an Atomic* or a lock.

"Explain happens-before / the memory model."

Compilers and CPUs reorder and cache. Happens-before defines when one thread's writes are guaranteed visible to another: unlock→lock, volatile write→read, start→thread, thread→join. Without such an edge, there's no visibility guarantee — a data race is undefined behavior, not merely a stale value.

"Interface vs abstract class?"

Interface: a capability/contract, no instance state, implement many, has default/static bodies since Java 8. Abstract class: shared state + partial implementation, single inheritance, constructors. Choose interface for flexible capability, abstract class when subclasses genuinely share state. And prefer composition over inheritance to avoid the fragile base class problem.

"What are records and why use them?"

Immutable, transparent data carriers: declare the components and get the constructor, accessors, equals/hashCode/toString for free (value semantics). Great for DTOs, map keys, and pattern matching. Compact constructors validate. With sealed types they enable exhaustive pattern-matched switch.

"Does Java have a GIL?"

No. Java threads are OS threads and run truly in parallel across cores — unlike CPython. That means real parallelism but you own the correctness of shared mutable state (locks/atomics for atomicity, volatile/happens-before for visibility). Java 21 virtual threads add cheap, massively scalable threads for blocking-style code.

Positioning: if you're coming from C++ or Python, lead with the transferable core (memory model, data structures, concurrency reasoning) and show you've internalized the Java-specific shifts: GC instead of manual/RAII lifetime, erasure instead of templates, checked exceptions, virtual-by-default methods, and the modern language (streams, records, sealed types, virtual threads). Depth on the JVM and the memory model is what separates senior Java candidates from syntax-level ones.
