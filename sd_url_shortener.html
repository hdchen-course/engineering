Design a URL Shortener

A classic "warm-up" system-design problem — and a trap, because the easy version hides the real crux: generating short, unique, hard-to-guess keys at scale, and serving billions of redirects with single-digit-millisecond latency. Every number below is computed and re-checked so you can quote it verbatim.
Read this like a story

Sections build from "what are we even building" through the estimation that fixes the key length, into the four ways to generate keys (the part interviewers actually grade), then the redirect path's famous 301-vs-302 decision, caching, cleanup, safety, and a probe-by-probe interview script. The math for the key-space and the base62 encode is boxed so you can find it fast on a re-read.

1. Problem & Requirements

A URL-shortening service takes a long URL and returns a short key that redirects to it. Paste in https://www.example-store.com/products/winter-jacket?ref=spring-sale&variant=42 and get back https://sho.rt/k2Xr9; anyone who opens the short link is redirected to the original. Short links fit in a text message, a printed QR code, or a character-limited post — and let the operator measure clicks.

Functional requirements

  • Shorten: given a long URL, return a unique short key (the whole point). The short URL is base_domain + "/" + key.
  • Redirect: given a short key, redirect the browser to the original long URL. This is the overwhelmingly dominant operation.
  • Custom alias (optional): let a user request a specific key, e.g. /spring-sale, instead of a generated one.
  • Expiration (optional): a link may carry a time-to-live and stop resolving after it lapses; default to a long or infinite lifetime.
  • Analytics (optional): count clicks per short link, with coarse breakdowns (time, referrer, geography) for the owner.

Non-functional requirements

  • High availability. A dead redirect breaks every link already printed on a billboard or embedded in an email. Redirect availability is close to sacred.
  • Low-latency redirect. The redirect is on the hot path of a page load — budget a few milliseconds, ideally < 10 ms end-to-end.
  • Read-heavy. Reads (redirects) dwarf writes (creations) by roughly 100:1; the whole design optimizes the read path.
  • Unguessable (optional/depends). If links must not be enumerable (private content), keys should not be sequential; if public, sequential is fine and denser.
  • At scale. Billions of stored links and over a hundred thousand redirects per second, growing for years.
Clarify before you draw

Ask up front: how many new URLs per day? what read:write ratio? are custom aliases required? must keys be unguessable? do links expire? These four answers pin the key length, the store size, and whether you need a Key Generation Service. Stating them turns a vague warm-up into a scoped problem.

2. Estimation & Scale

The estimation is what makes this problem interesting: it tells you the write QPS, the read QPS you must cache for, the storage bill over years, and — most importantly — how long the key must be. Assume 100 million new URLs/day and a 100:1 read:write ratio.

Write and read QPS

new URLs/day = 100,000,000 (108)
seconds/day = 86,400 ≈ 105
write QPS = 108 / 86,400 ≈ 1,157 QPS # ≈1,000 with the ÷10⁵ shortcut
read QPS = 100 × 1,157 ≈ 115,741 ≈ 116k QPS # 100:1 read:write
peak read = read × (peak factor ~2) ≈ ~230k QPS

So we write ~1.2k/s but must serve ~116k redirects/s (peaking ~2×). That gap is the reason the read path leans on caching and replicas while the write path can stay comparatively simple.

Storage per record, and over years

Each record stores the short key, the long URL, and a little metadata (creation time, expiry, owner, click counter). Long URLs vary; budget ~500 bytes per record including index and per-row overhead.

bytes/record ≈ 500 B # key(7) + long URL(~200–400) + metadata + overhead
per day = 108 × 500 B = 5 × 1010 B = 50 GB/day
per year = 50 GB × 365 = 18,250 GB ≈ 18.25 TB/year
5 years = 18.25 TB × 5 = ≈ 91 TB

Tens of terabytes over five years: comfortably beyond one commodity node's disk, so the store must shard — but it is not so vast that anything exotic is required.

Key-space math — the length decision

Keys use base62: the characters [0-9a-zA-Z], which is 10 + 26 + 26 = 62 symbols. A key of length L can encode 62L distinct values. We must have 62L ≥ the total number of links we will ever mint. Total over 5 years:

total URLs (5 yr) = 108/day × 365 × 5 = 1.825 × 1011 (≈ 182.5 billion)

625 = 916,132,832 ≈ 9.2 × 108 # ~0.9 billion — far too few
626 = 56,800,235,584 ≈ 5.68 × 1010 # ~57 billion — still < 182.5B, insufficient
627 = 3,521,614,606,208 ≈ 3.52 × 1012 # ~3.5 trillion — enough, big margin

Length 6 tops out at ~57 billion < 182.5 billion, so it runs out inside the 5-year horizon. Length 7 gives ~3.5 trillion — plenty:

headroom at L=7 = 627 / total = 3.52×1012 / 1.825×1011 ≈ 19×
key-space used = 1.825×1011 / 3.52×1012 ≈ 5.2%
The answer to "how long is the key?"

7 base62 characters. It encodes ~3.5 trillion links — ~19× our 5-year demand, using only ~5% of the space — while staying short enough to type. Length 6 (~57 B) is too small for this volume; 8 (~218 trillion) is overkill. Deriving this from the numbers, rather than guessing "6 or 7," is the senior signal.

Bandwidth and cache working set

write ingress = 1,157/s × 500 B ≈ 0.58 MB/s # creations carry the long URL
read egress = 116k/s × ~500 B ≈ ~58 MB/s # redirect responses are small
daily reads = 116k/s × 86,400 ≈ ~1.0 × 1010 (≈ 10 billion/day)

Traffic follows an 80/20 shape — a small fraction of links (fresh, viral) draws most clicks. Caching the hot set is what keeps p99 low. A loose upper bound on cache memory (treating 20% of daily reads as if all-distinct):

cache upper bound = 20% × 1010 × 500 B = 2×109 × 500 B = 1012 B = ~1 TB # worst case, no dedup

That is an over-estimate because the same hot key is requested many times — after de-duplication the real hot set is far smaller, so a distributed cache of a few hundred GB (or less) absorbs the vast majority of reads. The point of the bound is to show a cache cluster, not one box, and that it need not hold all 91 TB.

3. High-Level Architecture

Two flows share the same components. Write (create): client sends a long URL → an app server asks the key-generation component for a unique short key → writes {key → long URL} to the KV store → returns the short URL. Read (redirect): client opens a short key → an app server checks the cache → on hit it redirects immediately; on miss it reads the KV store, backfills the cache, and redirects.

Write path uses ①③ (key generation + store); read path uses ②③ (cache-aside: cache first, KV store on a miss, then backfill the cache).
  • App servers are stateless behind a load balancer, so they scale horizontally; all shared state lives in the store and cache.
  • Key generation is the crux (§4) — the write path's job is to obtain a globally unique key.
  • KV store holds the durable key → long URL mapping, sharded by key (§5).
  • Cache fronts the store for reads (§7); most redirects never touch the database.

4. Key Generation — the Crux

Every candidate can draw boxes and arrows; the interview is won or lost on how you generate a short, unique key at scale (and, if required, an unguessable one). Four approaches, each with its failure mode.

4.1 Hash the long URL, take a prefix

Compute a hash of the long URL (e.g. a 128-bit digest), base62-encode it, and keep the first 7 characters as the key. Simple and stateless — the same URL naturally maps to the same key, which is a bonus for de-duplication.

Collisions are the whole problem

Truncating a hash to 7 chars means two different long URLs can produce the same 7-char prefix. You must detect that: before committing, check whether the key already maps to a different URL; if so, perturb the input (append a counter/salt) and re-hash, retrying until the key is free. This adds an extra read on the write path, and under heavy fill the retry rate climbs. It also leaks nothing about ordering, but a raw hash key is still guessable in principle — a large, sparsely-filled keyspace is what keeps random probing impractical.

4.2 Auto-increment counter → base62 encode

Keep a single global counter. Each new URL gets the next integer n; the key is base62(n). Uniqueness is free — distinct integers give distinct keys, with zero collision checks — and keys stay short because base62 is dense.

Guessable
  • Keys are sequential: …, 4c91, 4c92, 4c93. Anyone can enumerate every link — bad when links must be private.
Single point
  • One global counter is a bottleneck and a single point of failure; every write must increment it.

You can blunt guessability by encoding a scrambled counter (e.g. a reversible permutation of the integer) so keys look random while remaining unique, but the counter's centrality remains the real issue — addressed by 4.4.

The base62 encode / decode (with a hand-checked example)

Encoding turns the integer id into the shortest base62 string; decoding inverts it. Use a fixed 62-symbol alphabet — here 0-9, then a-z, then A-Z (indices 0–61).

# alphabet index i -> character; 62 symbols total
ALPHABET = "0123456789abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOPQRSTUVWXYZ"
BASE = 62

def encode(n):              # integer id -> short key
    if n == 0: return ALPHABET[0]
    key = ""
    while n > 0:
        key = ALPHABET[n % BASE] + key   # prepend least-significant digit
        n = n // BASE
    return key

def decode(key):            # short key -> integer id
    n = 0
    for ch in key:
        n = n * BASE + ALPHABET.index(ch)
    return n

Worked by hand for n = 1,000,000 (repeated division by 62, remainders read bottom-up):

1,000,000 ÷ 62 = 16,129 r 2 # 16,129×62 = 999,998; remainder 2 → '2'
16,129 ÷ 62 = 260 r 9 # 260×62 = 16,120; remainder 9 → '9'
260 ÷ 62 = 4 r 12 # 4×62 = 248; remainder 12 → 'c'
4 ÷ 62 = 0 r 4 # remainder 4 → '4'
read remainders bottom→top ⇒ encode(1,000,000) = "4c92"

# decode check: ((4×62 + 12)×62 + 9)×62 + 2 = ((260)×62 + 9)×62 + 2 = 16,129×62 + 2 = 1,000,000 ✓

Index 12 maps to 'c' because indices 0–9 are the digits 0-9 and index 10 is 'a', so 10→a, 11→b, 12→c. A million fits in four base62 chars; our 7-char keys cover up to 627−1 ≈ 3.5 trillion.

4.3 Key Generation Service (KGS) — pre-generate unique keys

Rather than derive keys at write time, a dedicated Key Generation Service generates all possible 7-char keys ahead of time (offline) and stores them in an available-keys pool. When an app server needs a key, it just pops one; the KGS moves that key to a used-keys pool so it is never handed out twice. No collisions, no hashing, no counter on the hot path — the write becomes a cheap "take a pre-made key."

A batch job pre-fills the Available pool. Per write: KGS pops an unused key, moves it to Used, and returns it — uniqueness by construction, no hashing or collision retry.
  • Concurrency: the pop-and-move must be atomic (or the KGS single-threads handing out) so two servers can't get the same key.
  • Throughput: a KGS replica loads a block of keys into memory and serves them without a round-trip per request; when its block is low it fetches another.
  • Single point of failure: run multiple KGS instances, each owning a disjoint block of pre-generated keys, so one dying loses only its unhanded block (a small, acceptable leak of key-space).
  • Unguessability: because pre-generated keys can be pulled in random order (or the space filled randomly), they need not be sequential.

4.4 Distributed counter / per-server ranges

Keep the counter idea's collision-free uniqueness but remove the single bottleneck: a coordination service (for example, a strongly-consistent coordinator such as ZooKeeper) hands each app server a disjoint range of integers, e.g. server A owns 1–1,000,000, B owns 1,000,001–2,000,000, and so on. Each server then encodes locally with base62, coordinating with no one per key, and asks for a fresh range only when its current one is nearly exhausted.

The coordinator leases a non-overlapping integer range to every server; each encodes locally with no per-key coordination, refilling only when its range runs low.
Which one in the interview?

Lead with KGS (4.3) or ranged counters (4.4) — both give collision-free uniqueness without a hot-path collision check, and both scale past a single counter. Mention hashing (4.1) as the simple stateless option whose cost is collision handling, and the plain counter (4.2) as the teaching baseline whose flaws (guessable + single point) motivate the other three.

5. Storage & Data Model

The core record is tiny and the access pattern is a point lookup by key — exactly what a key-value / NoSQL store does best.

FieldExampleNotes
short_key (PK)k2Xr9The partition key; lookups are get(key)
long_urlhttps://www.example-store.com/products/winter-jacket?…The redirect target
created_at1737000000Epoch seconds; for analytics + cleanup
expires_atnull or epochOptional TTL; null = never expire
owner_idu_88213Who created it (quotas, dashboards)
click_count0Updated asynchronously (§9)

Why KV / NoSQL over a relational store

  • Access pattern is a single-key point lookup. There are no joins and no multi-row range scans on the hot path; a KV store's get(key) is O(1) and trivially cacheable.
  • Read-heavy at huge scale. Wide-column / KV stores partition by key across many nodes and add read replicas easily, matching the 100:1 read:write shape.
  • Schema is flat and stable. No relational modeling benefit; the flexibility and horizontal scale of NoSQL fit better than a single big SQL table that must be sharded by hand.
  • Relational is still fine at small scale — a single indexed table works for millions of rows. The KV choice is about the billions-of-rows, hundreds-of-thousands-of-QPS target.

Sharding by key

Partition the data by a hash of the short key (or by a key prefix). Because the key is generated to be uniform across base62, hash-sharding spreads both storage and read load evenly — no natural hot shard from the key itself (hot links are handled by the cache, not by the shard map). This is why generating keys uniformly (§4) pays off twice: uniqueness and balanced shards.

Consistency

A brand-new short link that isn't yet visible on every replica for a few milliseconds is harmless — the create response can return the key from the primary, and reads tolerate slight replication lag. So the store can favor availability/latency (eventual consistency on replicas) rather than strict global consistency, which suits a KV/NoSQL engine.

6. The Redirect Path — 301 vs 302

The redirect looks trivial — return an HTTP redirect whose Location header is the long URL — but which redirect status you send is a genuine trade-off worth reasoning about aloud.

Cache-aside resolve: check cache (①), fall back to the KV store on a miss (②) and backfill, return a redirect to the browser, which then follows Location to the origin site.

301 (permanent) vs 302/307 (temporary)

Aspect301 Moved Permanently302 Found / 307 Temporary
Browser cachingCached aggressively — future clicks may skip your server entirelyNot cached — every click comes back to you
Server loadLower (browser goes straight to the target)Higher (you serve every redirect)
AnalyticsYou miss the cached clicks — undercountsYou see every click — accurate counts
Change target laterHard — cached 301s keep hitting the old URLEasy — you control every resolve
Recommendation

For a shortener, prefer 302 (temporary). The point of a shortener is usually to measure clicks and retain the ability to change or expire a target; a 301 defeats both by letting the browser cache the mapping and bypass you. You pay more server traffic, but that's exactly what the cache and replicas (§7) are for. Choose 301 only if analytics and mutability truly don't matter and you want to shed load. (307 behaves like 302 but forbids changing the HTTP method — for a plain GET redirect they're equivalent for our purposes.)

Cache-aside on the read path

# resolve(key) — cache-aside (lazy-loading) pattern
url = cache.get(key)
if url is None:                 # cache miss
    url = store.get(key)          # read the durable KV store
    if url is None:
        return 404              # unknown or expired key
    cache.set(key, url, ttl=3600)  # backfill so the next click is a hit
emit_click_event(key)             # async, off the hot path (§9)
return redirect(url, status=302)

7. Caching & Read Scaling

With 116k reads/s (peaking ~230k) against a ~1.2k/s write rate, the read path must lean on caching and replication so the database is rarely the bottleneck.

The hot-key LRU cache

An in-memory cache (an LRU keyed by short key) fronts the KV store. Because clicks follow the 80/20 shape, a modest cache captures the vast majority of reads. The hit ratio governs how much load ever reaches the database:

DB reads/s = read QPS × (1 − hit_ratio)
at 116k QPS, hit 0.90 ⇒ 116k × 0.10 = 11,600 DB reads/s
at 116k QPS, hit 0.99 ⇒ 116k × 0.01 = 1,160 DB reads/s # 10× fewer with 9pp more hits

Going from a 90% to a 99% hit ratio cuts database read load ten-fold — which is why tuning the cache (size, TTL, eviction) matters more than adding database replicas. Entries are read-only mappings, so a moderate TTL (say an hour) plus LRU eviction keeps the freshest, hottest links resident; a changed or expired mapping simply falls out or is invalidated.

CDN / edge and read replicas

  • Edge / CDN: because most short links resolve to the same target for everyone, an edge tier close to users can cache the redirect response, cutting latency and offloading origin. (This interacts with the 301/302 choice: a 302 is still cacheable at your edge under your control, unlike an uncontrollable browser-cached 301.)
  • Read replicas: the KV store runs replicas so the (already small) miss traffic spreads across many nodes; writes go to the primary/shard-owner, reads fan out.
  • Stateless app tier: add app servers behind the load balancer to scale request handling independently of the data tier.
Layered reads

Browser/edge cache → distributed hot-key cache → read replicas → primary shard. Each layer absorbs a slice, so by the time a request could reach the primary it's a tiny trickle. The write path stays simple precisely because it isn't fighting the reads for the same resources.

8. Custom Aliases, Expiration & Cleanup

Custom aliases

A custom alias lets a user pick the key (/spring-sale) instead of accepting a generated one. The wrinkle is collision with generated keys and with other aliases: the alias shares the same key namespace, so it must be reserved atomically.

  • Reserve atomically: insert the alias only if the key is free — a conditional/compare-and-set write (insert-if-not-exists). If it already exists, reject with "alias taken."
  • Avoid clashing with the generator: either carve custom aliases into a separate length/prefix range the generator never emits, or simply let the atomic insert be the single source of truth (first writer wins, generator retries on the rare clash).
  • Validate: length bounds, allowed characters, and a denylist for reserved/abusive words.

Expiration & cleanup

Expired links must stop resolving and, eventually, free storage. Two complementary mechanisms:

Lazy deletion (on read)

  • On resolve, if expires_at is set and in the past, return 404 (or a "link expired" page) and optionally delete the row then.
  • Zero background cost; correctness is immediate for anyone who clicks.
  • But dead rows linger until touched — they still occupy storage.

Active sweep (background)

  • A low-priority job scans for expires_at < now and reclaims those rows (and their cache entries), running off-peak.
  • Or lean on the store's native TTL to auto-evict expired rows with no custom job at all.
  • Reclaims space, but adds background load and must be rate-limited so it never competes with live traffic.
Use both

Lazy deletion guarantees an expired link never resolves (correctness on the hot path); the background sweep / native TTL reclaims the space (cost control). A recycled key can, in principle, be returned to the KGS available pool — but re-issuing old keys risks a stale bookmark landing on a new target, so many designs simply retire expired keys rather than recycle them.

9. Analytics, Rate Limiting & Safety

Click analytics — asynchronous by default

Counting clicks must never slow the redirect. Instead of a synchronous UPDATE … click_count+1 on the hot path (which would add a write to every read and contend on a hot row), emit a lightweight click event to a queue/stream and process it out of band.

  • Fire-and-forget event: the resolve handler pushes {key, ts, referrer, coarse geo} onto a queue and returns the redirect immediately.
  • Async aggregation: consumers batch-update counters and roll up time-series/geo breakdowns; the owner dashboard reads the aggregates.
  • Sampling at extreme scale: for very hot links, count 1-in-N and multiply back, trading a little precision for a large drop in event volume — fine for analytics, which tolerate approximation.
click events/day ≈ daily reads ≈ 1010 # one per redirect if unsampled
with 1:100 sampling ⇒ 1010 / 100 = 108 events/day stored, counts ×100 to estimate

Rate limiting abusive shorteners

Creation is the abusable operation: a script could mint millions of links to exhaust key-space or power spam campaigns. Apply a rate limiter (see Part XI, Chapter 1) on the create endpoint, keyed per user/API key/IP, plus per-account quotas. The read/redirect path is generally left open (it must serve everyone), though an edge layer can throttle abusive clients hitting one key abnormally hard.

Malicious-URL safety (generic)

A shortener can hide a dangerous destination

Because the target is hidden behind an opaque key, shorteners are attractive for phishing and malware links. Generic mitigations: check submitted URLs against a reputable threat-intelligence/denylist feed at creation and asynchronously re-scan later; interstitial "you are leaving to <domain>" preview pages for untrusted targets; and takedown tooling to disable a key on report. This is defense-in-depth, framed generically — the point in an interview is to acknowledge the abuse surface, not to over-build it.

10. Trade-offs & Interview Framing

How to drive the conversation

  1. Clarify (1–2 min): new URLs/day? read:write ratio? custom aliases? unguessable? expiration? (§1)
  2. Estimate: write/read QPS, storage over years, and derive the key length from the base62 key-space (§2) — this is the differentiator.
  3. Sketch the architecture: client → app → keygen + KV + cache, write vs. read paths (§3).
  4. Nail key generation: KGS or ranged counters for uniqueness at scale; hashing and the plain counter as the contrast (§4).
  5. Redirect & scale reads: 302 for analytics/control, cache-aside, edge + replicas (§6–§7).
  6. Round out: aliases/expiration/cleanup, async analytics, rate limiting, safety (§8–§9).

What interviewers probe (with one-liners)

Q: Counter vs. hash vs. KGS — which and why?
A plain counter gives free uniqueness but is sequential (guessable) and a single bottleneck. Hashing is stateless but needs a collision check and retry on every write. A KGS pre-generates unique keys into an available pool and hands them out with no hot-path collision work — my default — or ranged counters (a coordinator leases disjoint integer blocks per server) to keep the counter's simplicity while removing the single point.

Q: 301 or 302?
302 (temporary). A 301 is cached by the browser, so future clicks skip my server — I lose analytics and can't change or expire the target. 302 keeps every resolve under my control at the cost of more traffic, which the cache and replicas absorb. Use 301 only if I explicitly want to shed load and don't need counts or mutability.

Q: How do you guarantee uniqueness at scale?
Make uniqueness structural, not checked: KGS pops from a pool of pre-generated distinct keys (moving each to a used pool atomically), or ranged counters give each server a disjoint integer range to base62-encode. Both avoid the read-check-write race a naive "is this key taken?" would hit under concurrency.

Q: How did you pick the key length?
From the key-space math: total links over 5 years ≈ 1.825×10¹¹. 62⁶ ≈ 5.7×10¹⁰ is too small; 62⁷ ≈ 3.5×10¹² gives ~19× headroom (~5% used). So 7 base62 characters — derived, not guessed.

Q: The counter is a single point of failure — fix it?
Don't share one counter on the hot path. Either partition it (ranged counters via a consistent coordinator, each server owning a block and refilling rarely) or replace it with a KGS whose replicas each own disjoint pre-generated blocks — one dying loses only its unhanded block, an acceptable key-space leak.

Q: How do you make keys unguessable?
Avoid raw sequential encoding: draw from a KGS pool filled in randomized order, or encode a scrambled/permuted counter (a reversible transform) so keys look random while staying unique. A longer key or a hash-based key also enlarges the space so enumeration is infeasible. Note the trade-off: unguessable keys can't exploit the counter's density as cheaply.

One-line summary

A URL shortener is a read-heavy key-value lookup: derive a 7-char base62 key from the scale math, generate keys uniquely without a hot-path race (KGS or ranged counters), store key → URL in a sharded KV store, serve redirects via a 302 behind an aggressive cache and replicas, and push analytics, expiration, rate limiting, and safety off the critical path.
