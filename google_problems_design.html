Design & Object-Oriented

Six Google-style data-structure-design problems • original framing, execution-tested classes, and interviewer probes

Note: Representative big-tech-style problems — not sourced from Google. The “Google-style” badge denotes the flavor of question, not its source.

How to read this chapter: these are data-structure-design problems — you build a class with methods rather than a single function, so the interesting behaviour only emerges from a sequence of operations. Every worked example is exactly such a sequence, invented for this book, and each stated output was produced by compiling and running the accompanying Java. Beyond the hand-picked edge cases, each class was cross-checked against an independent reference model across tens of thousands of random operation sequences — the stack against a plain list with a linear min, the LRU cache against an access-ordered LinkedHashMap, the randomized set against a HashSet (plus a 300k-draw uniformity check on getRandom), the logger against a per-message last-allowed map, the tree codec against a structural round-trip signature over random trees with negatives, and the autocomplete trie against a brute-force prefix scan — asserting identical results and invariants at every step. The recurring idea below is to trade memory for O(1) operations: an auxiliary structure (a second stack, a hash map beside an array, a doubly-linked list, a trie) that keeps the expensive query answerable in constant or near-constant time.

Min Stack

Medium Google-style

Problem

Design a stack that supports push, pop, top and, in addition, a getMin that returns the smallest element currently in the stack — all four in O(1).

  • getMin and top are only ever called on a non-empty stack; every pop matches a prior push.
  • Values may repeat, so the minimum can be held by several elements at once — popping one of them must not lose the min prematurely.

Example: the sequence push(-2), push(0), push(-3), getMin(), pop(), top(), getMin() produces getMin=-3, then after the pop top=0 and getMin=-2 (computed by running it). A duplicate-min case — push(1), push(1), getMin(), pop(), getMin() — keeps getMin=1 both times, because the two equal mins are tracked independently.

Approach & Intuition

Carry the running minimum alongside every element with a parallel “min stack.” The one hard part of a min-tracking stack is that after a pop the minimum may need to revert to an older, larger value — and a single scalar cannot remember what the min was before the current one arrived. The fix is a second stack that, at each level, stores the minimum of everything from the bottom up to that level. On push(x) we push min(x, currentMin); then getMin is just the top of that auxiliary stack, and every pop discards both tops together so the min automatically rolls back. Because each push stores min(x, currentMin), duplicate minimums roll back correctly on their own — no special comparison needed. (The <=-vs-< subtlety only bites in the space-optimised variant below.)

class MinStack {
    private Deque<Integer> stack = new ArrayDeque<>();
    private Deque<Integer> mins  = new ArrayDeque<>();  // min from bottom up to this level

    public void push(int x) {
        stack.push(x);
        // push the running minimum for this level (x or the current min, whichever is smaller)
        if (mins.isEmpty() || x <= mins.peek()) mins.push(x);
        else mins.push(mins.peek());
    }
    public void pop() { stack.pop(); mins.pop(); }   // discard both tops together
    public int top() { return stack.peek(); }
    public int getMin() { return mins.peek(); }  // current min in O(1)
}

Complexity: Time O(1) for every operation — each is a constant number of stack pushes/peeks, no scanning. Space O(n): the auxiliary min-stack doubles the storage, holding one tracked minimum per element.

Common pitfalls / interviewer probes: Duplicate minimums (space-optimised variant). The always-push version above sidesteps this, but in the memory-saving variant that pushes only when x <= min, you must use <= (not <): with <, equal minima are pushed only once, so popping the later duplicate wrongly reverts the min. Pushing on <= (so equal values are recorded again) keeps getMin correct until every copy is popped. Don’t recompute the min by scanning. A getMin that loops over the stack is O(n) and defeats the point; the whole design exists to make it O(1). Pop both stacks together. Forgetting to pop the min-stack leaves it misaligned and every later getMin is wrong. Space-optimised variant. If asked to avoid storing a min per element, you can push onto the min-stack only when x <= min and pop it only when the popped value equals its top — same O(1) time, less memory on mostly-increasing inputs.

LRU Cache

Medium Google-style

Problem

Design a fixed-capacity cache with O(1) get and put that evicts the least-recently-used entry when it is full. get(key) returns the value or -1 if absent; put(key, value) inserts or updates. Both a get and a put count as using a key, refreshing its recency.

  • On a put that exceeds capacity, evict the entry that has gone longest without being read or written.
  • A capacity of 0 is legal — the cache stores nothing and every get returns -1.

Example: with capacity 2: put(1,1), put(2,2), get(1)→1 (now key 1 is most-recent), put(3,3) evicts the least-recent key 2, so get(2)→-1; then put(4,4) evicts key 1, so get(1)→-1, get(3)→3, get(4)→4 (computed by running it). With capacity 0, put(1,1) stores nothing and get(1)→-1.

Approach & Intuition

A hash map for O(1) lookup, backed by a doubly-linked list that keeps entries in recency order. The map takes you from a key to its list node instantly; the list orders nodes from most-recent (front) to least-recent (back). Every access — both get and put — unlinks the touched node and re-inserts it at the front, so the back of the list is always the true eviction victim. Two sentinel nodes (a permanent head and tail) remove all the null-checking around the ends: inserting at the front and removing the last real node become branchless pointer swaps. When a fresh insert would exceed capacity, we drop the node just before tail and erase its key from the map.

class LRUCache {
    private class Node { int key, val; Node prev, next; Node(int k, int v){ key=k; val=v; } }
    private final int capacity;
    private final Map<Integer,Node> map = new HashMap<>();
    private final Node head = new Node(0,0), tail = new Node(0,0);  // sentinels

    public LRUCache(int capacity) {
        this.capacity = capacity;
        head.next = tail; tail.prev = head;      // empty list: head <-> tail
    }
    private void remove(Node n){ n.prev.next = n.next; n.next.prev = n.prev; }
    private void addFront(Node n){ n.next = head.next; n.prev = head; head.next.prev = n; head.next = n; }

    public int get(int key) {
        Node n = map.get(key);
        if (n == null) return -1;
        remove(n); addFront(n);                  // reading refreshes recency
        return n.val;
    }
    public void put(int key, int value) {
        if (capacity <= 0) return;                  // capacity 0: store nothing
        Node n = map.get(key);
        if (n != null) { n.val = value; remove(n); addFront(n); return; }
        if (map.size() == capacity) {             // full: evict least-recently-used
            Node lru = tail.prev; remove(lru); map.remove(lru.key);
        }
        Node fresh = new Node(key, value); map.put(key, fresh); addFront(fresh);
    }
}

Complexity: Time O(1) for both get and put — a hash lookup plus a constant number of pointer rewires. Space O(capacity): one map entry and one list node per stored key.

Common pitfalls / interviewer probes: Refresh recency on get too, not just put. The most common bug is treating reads as free; then a frequently-read key is wrongly evicted. Every access must move the node to the front. Capacity 0. Guard it explicitly — otherwise put tries to evict from an empty list (tail.prev is the head sentinel) and corrupts the structure. Update-in-place still counts as a use. A put on an existing key must both overwrite the value and move it to the front. Sentinel nodes are worth it. Without head/tail dummies you special-case inserting into an empty list and removing the only node; the sentinels make every splice uniform. Why not a LinkedHashMap? In an interview you implement the map-plus-list by hand to prove you understand the O(1) mechanics; LinkedHashMap with accessOrder=true and removeEldestEntry is the real-world shortcut.

Insert Delete GetRandom O(1)

Medium Google-style

Problem

Design a set of distinct integers supporting three operations in average O(1): insert(val) (returns true only if the value was newly added), remove(val) (returns true only if it was present), and getRandom() returning an element uniformly at random from the current set.

  • The set holds no duplicates; insert of a present value and remove of an absent value both return false and change nothing.
  • getRandom is only called when the set is non-empty and must give every element equal probability.

Example: insert(1)→true, remove(2)→false (absent), insert(2)→true, insert(1)→false (already present), remove(1)→true, insert(2)→false (already present), getRandom()→2 (the only element left) — all computed by running it. A separate 300,000-draw uniformity check over {10, 20, 30} gave roughly 100,000 hits each (100015 / 100508 / 99477).

Approach & Intuition

Store the values in a growable array for uniform random indexing, and a hash map from value to its array index for O(1) find and delete. Random access needs a contiguous array (pick a random index); membership and deletion need a map. The clever part is remove: deleting from the middle of an array is normally O(n), so instead we swap the doomed element with the last one, fix the moved element’s index in the map, then pop the tail — all O(1). getRandom then just returns array[random(0, size)], uniform because the array is dense with no holes.

class RandomizedSet {
    private final List<Integer> vals = new ArrayList<>();       // dense array of values
    private final Map<Integer,Integer> idx = new HashMap<>(); // value -> index in vals
    private final Random rnd = new Random();

    public boolean insert(int val) {
        if (idx.containsKey(val)) return false;   // already present
        idx.put(val, vals.size());
        vals.add(val);
        return true;
    }
    public boolean remove(int val) {
        Integer i = idx.get(val);
        if (i == null) return false;          // absent
        int last = vals.size() - 1;
        int lastVal = vals.get(last);
        vals.set(i, lastVal);      // move the last element into the hole
        idx.put(lastVal, i);       // and fix its index in the map
        vals.remove(last);         // drop the tail — O(1)
        idx.remove(val);
        return true;
    }
    public int getRandom() { return vals.get(rnd.nextInt(vals.size())); }
}

Complexity: Time average O(1) for all three — hash operations are expected constant and the swap-with-last removal avoids shifting. Space O(n): the array and the index map each hold one entry per element.

Common pitfalls / interviewer probes: Update the moved element’s index. After copying the last value into the hole you must write idx.put(lastVal, i); forgetting it leaves a stale index and later removals corrupt the array. Order of the removal steps. Read the last value before you pop the tail, and erase val from the map last — and note the edge case where the element being removed is the last one (the overwrite is a harmless self-copy). Return the booleans faithfully. Re-inserting a present value returns false; removing an absent value returns false; conflating these with “always true” is a classic slip. Uniformity depends on density. getRandom is only uniform because the array has no gaps — a design that leaves tombstones would bias the draw. Follow-up: duplicates allowed. If the multiset variant is asked, the map’s value becomes a set of indices per value, and removal swaps out any one of them.

Logger Rate Limiter

Easy Google-style

Problem

Design a logger that decides whether a message may be printed. shouldPrintMessage(timestamp, message) returns true and prints the message only if the same message has not been printed in the last 10 seconds; otherwise it returns false. Timestamps arrive in non-decreasing order.

  • The 10-second window is per distinct message, not global — different messages don’t interfere.
  • The boundary is inclusive of re-printing: a message last printed at t may print again at exactly t + 10.

Example: (1,"foo")→true, (2,"bar")→true, (3,"foo")→false (only 2s since foo), (8,"bar")→false (6s since bar), (10,"foo")→false (9s since foo), (11,"foo")→true (exactly 10s after its last print at t=1) — computed by running it.

Approach & Intuition

Remember only the last timestamp at which each message was allowed. A hash map from message to its last-allowed time is all the state needed: on a call, if the message is unseen or the gap since its stored time is at least 10, we allow it and overwrite the stored time; otherwise we reject and leave the map untouched. Because we store the last allowed time (not merely the last seen time), rejected calls in between don’t slide the window forward — the window is anchored to the actual print.

class Logger {
    private final Map<String,Integer> lastAllowed = new HashMap<>(); // message -> last printed ts

    public boolean shouldPrintMessage(int timestamp, String message) {
        Integer last = lastAllowed.get(message);
        // allow if never seen, or >= 10s since last print (exactly 10s prints)
        if (last == null || timestamp - last >= 10) {
            lastAllowed.put(message, timestamp);   // anchor the window to this print
            return true;
        }
        return false;
    }
}

Complexity: Time O(1) per call — a single hash lookup and possible insert. Space O(m) where m is the number of distinct messages ever allowed (the map never shrinks in this simple version).

Common pitfalls / interviewer probes: The exactly-10-seconds boundary. Use >= 10, not > 10: a message last printed at t is allowed again at t + 10. Off-by-one here is the single most common bug. Store last allowed, not last seen. If you update the timestamp on rejected calls too, a steady stream of the same message keeps pushing the window and it never prints again. Per-message windows. The map key is the message, so distinct messages are rate-limited independently. Unbounded memory follow-up. The map grows with distinct messages forever; if asked to bound it, evict entries older than the window (e.g. a queue of (ts, message) pairs purged lazily) — useful when messages are effectively unique. Concurrency follow-up. Under real concurrent callers the check-then-put must be atomic (synchronize, or use ConcurrentHashMap with a compare-style update) or two threads can both print.

Serialize and Deserialize Binary Tree

Hard Google-style

Problem

Design a codec that turns an arbitrary binary tree into a string and reconstructs the identical tree from that string. The two operations are inverses: deserialize(serialize(root)) must yield a tree with the same shape and node values as root.

  • The tree may be empty (a null root), a single node, or wildly unbalanced; node values may be negative.
  • The string format is your choice, as long as the round trip is faithful.

Example: the tree with root 1, left child 2, right child 3, and 3’s children -4 and 5 serializes to "1,2,#,#,3,-4,#,#,5,#,#,"; deserializing that string and re-serializing it yields the identical string (verified true by running it). The empty tree serializes to "#," and deserializes back to null.

Approach & Intuition

Preorder traversal with explicit null markers. Preorder (root, then left subtree, then right subtree) has a decisive property: if every missing child is written as a sentinel such as #, the sequence uniquely determines the tree — no second traversal is needed to disambiguate. Serialization is a straight recursive walk emitting value, for a node and #, for null. Deserialization consumes those tokens in the same order from a queue: pull a token; if it’s # return null, otherwise create the node and recursively build its left then right subtree — the recursion mirrors the write exactly. Values are parsed as integers, so negatives round-trip for free.

class TreeNode { int val; TreeNode left, right; TreeNode(int v){ val = v; } }

class Codec {
    // --- serialize: preorder with '#' for nulls, comma-separated ---
    public String serialize(TreeNode root) {
        StringBuilder sb = new StringBuilder();
        ser(root, sb);
        return sb.toString();
    }
    private void ser(TreeNode n, StringBuilder sb) {
        if (n == null) { sb.append("#,"); return; }   // null marker
        sb.append(n.val).append(',');
        ser(n.left, sb); ser(n.right, sb);              // preorder recursion
    }
    // --- deserialize: consume tokens in the same preorder ---
    public TreeNode deserialize(String data) {
        Deque<String> q = new ArrayDeque<>(Arrays.asList(data.split(",")));
        return de(q);
    }
    private TreeNode de(Deque<String> q) {
        String t = q.poll();
        if (t.equals("#")) return null;                  // rebuild null
        TreeNode n = new TreeNode(Integer.parseInt(t)); // negatives parse fine
        n.left = de(q); n.right = de(q);                // same order as writing
        return n;
    }
}

Complexity: Time O(n) for both directions — each node (and each null slot) is written once and read once. Space O(n) for the string and the token queue, plus the recursion stack up to the tree height O(h).

Common pitfalls / interviewer probes: Null markers are mandatory. A preorder without them can’t be inverted uniquely (you couldn’t tell a left child from a right one); the # sentinels are exactly what make the single traversal reversible. Negative values. Parse with a real integer parse and separate tokens with a delimiter — a scheme that keys off a leading - or concatenates digits without separators mis-reads negatives and multi-digit numbers. Empty tree. A null root must serialize to a single marker and rebuild to null; don’t special-case it out and crash on the split. Consume tokens in the write order. Deserialization must read left before right, matching serialization — swap them and the tree comes back mirrored. BFS alternative. A level-order codec (LeetCode’s bracket format) is equally valid; preorder is usually the shortest to write recursively.

Design Search Autocomplete System

Hard Google-style

Problem

Design an autocomplete that learns from history. Initialize with a list of past sentences and their frequencies. Then input(c) streams one character at a time: for an ordinary character, append it to the current query and return the top 3 historical sentences that start with the query so far, ranked by frequency (highest first) and breaking ties by ASCII order (lexicographically smaller first). The special character '#' ends the current sentence: record it (adding 1 to its frequency), reset the query, and return an empty list.

  • Sentences may contain spaces; matching is a strict prefix match on the accumulated query.
  • Return fewer than 3 when fewer match; return an empty list once no historical sentence has the query as a prefix.

Example: initialized with island(5), idea(3), ironman(2), inbox(2): input('i')→[island, idea, inbox] (5 > 3 > then the 2-2 tie broken lexicographically, inbox < ironman); input(' ')→[] (nothing starts with "i "); input('#')→[] (commits "i " with frequency 1 and resets). Then input('i')→[island, idea, inbox], input('r')→[ironman], input('#')→[] (commits "ir"). All computed by running it.

Approach & Intuition

Store every sentence in a trie, and at each trie node keep a running map of the frequencies of all sentences passing through it. Walking one character deep in the trie corresponds exactly to extending the query by one character, so answering input(c) is: follow the child edge for c, then read that node’s frequency map and pick the top 3. Keeping the frequency table at each node (rather than only at sentence ends) means we never re-scan the subtree — the candidates for the current prefix are sitting right there. A running StringBuilder accumulates the query; once the walk falls off the trie (a child is missing) we can short-circuit to an empty list because no sentence can match. On '#' we add the accumulated query to the trie with +1 frequency, reset the query, and point back at the root.

class AutocompleteSystem {
    private static class Node {
        Map<Character,Node> children = new HashMap<>();
        Map<String,Integer> counts = new HashMap<>();  // freq of every sentence through here
    }
    private final Node root = new Node();
    private Node curNode = root;                 // node for the current prefix (null if fallen off)
    private final StringBuilder cur = new StringBuilder();

    public AutocompleteSystem(String[] sentences, int[] times) {
        for (int i = 0; i < sentences.length; i++) add(sentences[i], times[i]);
    }
    private void add(String sentence, int freq) {
        Node n = root;
        for (int i = 0; i < sentence.length(); i++) {
            char c = sentence.charAt(i);
            n = n.children.computeIfAbsent(c, k -> new Node());
            n.counts.merge(sentence, freq, Integer::sum);   // bump freq along the path
        }
    }
    public List<String> input(char c) {
        if (c == '#') {                       // commit the current sentence, reset
            add(cur.toString(), 1);
            cur.setLength(0);
            curNode = root;
            return new ArrayList<>();
        }
        cur.append(c);
        if (curNode != null) curNode = curNode.children.get(c);   // walk one char
        if (curNode == null) return new ArrayList<>();       // no sentence has this prefix
        // rank by frequency desc, then lexicographic asc; take top 3
        List<Map.Entry<String,Integer>> list = new ArrayList<>(curNode.counts.entrySet());
        list.sort((x, y) -> x.getValue().equals(y.getValue())
                ? x.getKey().compareTo(y.getKey())      // tie -> lexicographic
                : y.getValue() - x.getValue());         // else higher freq first
        List<String> res = new ArrayList<>();
        for (int i = 0; i < Math.min(3, list.size()); i++) res.add(list.get(i).getKey());
        return res;
    }
}

Complexity: Let p be the length of the current prefix and k the number of sentences sharing it. Each ordinary input is O(1) to walk one edge plus O(k log k) to rank the node’s candidates (only 3 are kept). A '#' commit is O(L) for a sentence of length L to update the counts along its path. Space is O(total characters × distinct sentences per node) in the worst case — the per-node count maps trade memory for fast queries.

Common pitfalls / interviewer probes: Tie-break direction. Higher frequency wins, but equal frequencies break to the lexicographically smaller sentence (ascending ASCII) — reversing this is the most common bug, and why inbox beats ironman at frequency 2. The '#' commit. On hash you must add the accumulated query with +1 (creating it if new, or bumping an existing sentence), then clear the query and return an empty list — not the matches. Reset the walk pointer, not just the string. After '#' point curNode back at the root; leaving it stale makes the next character walk from the wrong place. Short-circuit once off the trie. As soon as a child is missing the answer is empty for the rest of the sentence — keep curNode == null and return early instead of re-searching. Spaces are ordinary characters. They are part of the prefix and sort before letters in ASCII, so don’t strip or special-case them. Storing counts per node vs. at leaves. Holding the frequency map at every node makes queries fast but costs memory; the leaner alternative stores frequencies only at sentence ends and does a subtree scan per query — simpler, but slower for hot prefixes.
